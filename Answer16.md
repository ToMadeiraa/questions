# Вопрос 16. Может ли конструктор быть шаблонной функцией?

> **Кратко:** да, может. Конструктор-шаблон (`constructor template`) — обычный член класса с собственными параметрами шаблона, он широко применяется для perfect forwarding и конвертирующих конструкторов (`std::pair`, `std::shared_ptr`, `std::optional`). Главная особенность: он **никогда** не является копирующим, перемещающим или конструктором по умолчанию, а потому не отменяет их неявную генерацию.

---

## Синтаксис и базовый пример

Параметры шаблона объявляются прямо перед конструктором; класс при этом шаблоном не является.

```cpp
#include <string>
#include <utility>

class Person {
public:
    template <class S>                                   // конструктор-шаблон
    explicit Person(S&& name) : name_(std::forward<S>(name)) {}

private:
    std::string name_;
};

Person a("Ann");                     // S выведется как const char (&)[4]
Person b(std::string{"Bob"});        // S = std::string, значение перемещается
```

Типичное применение — «прозрачная» передача аргумента в поле без промежуточных копий: `S&&` в шаблоне является **универсальной ссылкой**, а `std::forward` сохраняет категорию значения.

---

## Шаблон не подменяет копирующий и перемещающий конструкторы

Стандарт прямо говорит: шаблон функции-члена **никогда не инстанцируется так, чтобы стать** копирующим или перемещающим конструктором ([class.copy.ctor]). Даже если при подстановке получается сигнатура `Box(const Box&)`, это всё равно обычный конструктор-шаблон, а не copy-ctor.

```cpp
class Box {
public:
    template <class T>                                   // конструктор-шаблон
    explicit Box(T&& value) : value_(std::forward<T>(value)) {}

    Box(const Box&) = default;                           // всё равно нужен явно
    Box(Box&&) noexcept = default;

private:
    std::string value_;
};
```

| Неявный конструктор | Подавляется ли шаблонным? | Комментарий |
|---|---|---|
| Копирующий `Box(const Box&)` | **нет** | генерируется как обычно (memberwise copy) |
| Перемещающий `Box(Box&&)` | **нет** | генерируется, если нет объявленных copy-операций и деструктора |
| По умолчанию `Box()` | **да** | конструктор-шаблон — это объявленный пользователем конструктор, поэтому `Box b;` без `Box() = default;` не скомпилируется |

Отсюда практическое правило: **наличие конструктора-шаблона не освобождает от правила пяти** — копирование и перемещение всё равно надо объявить или осознанно оставить сгенерированными.

## Классическая ловушка: «жадный» конструктор-шаблон

Неограниченный `template <class T> X(T&&)` выигрывает разрешение перегрузки у копирующего конструктора, когда аргумент — **неконстантный lvalue**: привязка `X&` к `X&` — точное совпадение, а копирующий конструктор требует добавления `const`.

```cpp
class Wrapper {
public:
    template <class T>
    Wrapper(T&& value) : value_(std::forward<T>(value)) {}   // без ограничения

private:
    std::string value_;
};

Wrapper w1("a");
Wrapper w2(w1);        // T = Wrapper&, выбирается шаблон, а не копирующий конструктор
                       // -> std::string(Wrapper&) => ошибка компиляции
```

Лечится ограничением (constraint), которое исключает сам тип из набора кандидатов.

```cpp
#include <concepts>
#include <string>
#include <type_traits>
#include <utility>

class Wrapper {
public:
    // C++20: концепты — читается как требование, а не как «хак»
    template <class T>
        requires std::constructible_from<std::string, T>
              && (!std::same_as<std::remove_cvref_t<T>, Wrapper>)
    explicit Wrapper(T&& value) : value_(std::forward<T>(value)) {}

    Wrapper(const Wrapper&) = default;

private:
    std::string value_;
};

// C++17-вариант того же ограничения через SFINAE:
// template <class T, class = std::enable_if_t<!std::is_same_v<std::decay_t<T>, Wrapper>>>
// explicit Wrapper(T&& value) : value_(std::forward<T>(value)) {}
```

Именно из-за этой ловушки конструкторы `std::any`, `std::optional`, `std::function` в стандартной библиотеке описаны с жёсткими ограничениями (`is_constructible`, «не тот же тип», «не `in_place_t`»).

## Где конструкторы-шаблоны используются в стандартной библиотеке

| Пример | Что делает конструктор-шаблон |
|---|---|
| `std::pair<T, U>` | конвертирующий конструктор из `std::pair<U1, U2>` и из `std::tuple` |
| `std::shared_ptr<T>(Y* p)` | принимает указатель на производный тип, сохраняя корректный deleter |
| `std::optional<T>(U&&)` | конвертирующее создание значения с ограничением `is_constructible` |
| `std::function<Sig>` | конструктор из любого callable, совместимого с сигнатурой |
| `std::vector<T>::emplace_back` | сам не шаблонный конструктор, но использует perfect forwarding в `allocator_traits::construct` |

Важно различать: `emplace_back` — обычная функция-шаблон, а «шаблонный конструктор» — это именно конструктор с собственными параметрами шаблона.

## Тонкости, которые спрашивают

| Вопрос | Ответ |
|---|---|
| Можно ли `= default` для конструктора-шаблона? | Нет, только для нешаблонных специальных членов; `= delete` — можно |
| Может ли он быть `virtual`? | Нет, конструкторы не бывают виртуальными (см. вопрос 17) |
| Может ли он быть `constexpr`? | Да, если тело и поля позволяют |
| Действует ли `explicit` на весь шаблон? | Да, на все инстанциации; в C++20 доступен условный `explicit(bool)` |
| Участвует ли он в CTAD? | Да, конструкторы класса-шаблона участвуют в выводе аргументов; для конструирования из чужих типов добавляют deduction guides |
| Влияет ли он на агрегатность? | Да: любой объявленный конструктор делает класс неагрегатным, и `X x{1, 2}` перестаёт быть агрегатной инициализацией |
| Кто приоритетнее при `{...}`? | Конструктор с `std::initializer_list` — он всегда предпочтительнее шаблонного |

## Типичные ошибки

1. **Ждать, что конструктор-шаблон заменит копирующий/перемещающий** — не заменит; неявные версии генерируются отдельно, и наоборот, объявленный copy-ctor вместе с шаблоном создаёт конкуренцию.
2. **Забыть `X() = default;`** после добавления конструктора-шаблона: `X x;` перестаёт компилироваться.
3. **Не ограничить `template <class T> X(T&&)`** — получаем «жадный» конструктор, который ломает копирование и перехватывает чужие типы.
4. **Отсутствие `explicit`** — неявные преобразования из чего угодно; для конвертирующих конструкторов это почти всегда ошибка.
5. **Передача `std::forward<T>` дважды** — повторное использование перемещённого аргумента (классическая ошибка в конструкторах с несколькими полями).
6. **Ожидание, что `T` выведется из `{1, 2, 3}`** — braced-init-list не выводится в параметр шаблона, кроме случая `std::initializer_list<T>`.
7. **Путать конструктор-шаблон с шаблоном класса**: `template <class T> class X` и `class X { template <class T> X(T); }` — разные вещи.

---

## Что добавить на собеседовании

- Различие «шаблон класса» / «функция-шаблон» / «конструктор-шаблон» — базовый признак того, что человек понимает механику шаблонов.
- Ограничения на forwarding-конструктор — не бюрократия: они нужны, чтобы шаблон не подменял специальные члены и не ломал SFINAE-дружественные проверки `std::is_constructible`.
- Конструктор-шаблон часто совмещают с `std::enable_if` в возвращаемом типе или в параметре шаблона по умолчанию — это стандартный C++17-приём.
- Стоит упомянуть, что конструктор-шаблон **не** участвует в виртуальной диспетчеризации и не может быть точкой переопределения.

## Итог

| Утверждение | Верно? |
|---|---|
| Конструктор может быть шаблонной функцией | Да |
| Такой конструктор является копирующим при `T = const X&` | Нет, никогда |
| Он подавляет неявный конструктор по умолчанию | Да, как любой объявленный конструктор |
| Он подавляет неявные копирующий и перемещающий конструкторы | Нет |
| Может быть `virtual` | Нет |
| Может быть `= default` | Нет |
| Требует ограничения, если принимает `T&&` | Как правило, да |
