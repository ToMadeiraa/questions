# 107. Что такое принцип KISS?

## Определение

**KISS** (Keep It Simple, Stupid — «не усложняй, глупец») — принцип проектирования, согласно которому система должна оставаться максимально простой, а сложность следует добавлять только при реальной необходимости. В контексте OOP/OOD это означает: выбирайте простейшее решение, которое удовлетворяет текущим требованиям, вместо «универсального» и «на вырост».

Ключевая идея: простота — это не отсутствие функциональности, а отсутствие *неоправданной* сложности.

## Почему это важно в ООП

- Простой код легче читать, тестировать, отлаживать и сопровождать.
- Меньше сущностей — меньше связей — ниже связность (coupling) и риск побочных эффектов.
- Сложные иерархии и абстракции трудно менять: чем больше «предусмотрительности», тем дороже эволюция.
- Принцип хорошо сочетается с **YAGNI** (You Aren't Gonna Need It) и **DRY**, но не заменяет их.

## Как проявляется нарушение KISS в ООП

1. **Преждевременная абстракция.** Создание интерфейсов, фабрик, стратегий «на будущее», хотя сейчас есть один-единственный вариант реализации.
2. **Избыточные паттерны.** Применение паттерна там, где достаточно обычного метода или структуры данных (например, полноценный Command там, где нужен простой вызов).
3. **Глубокая иерархия наследования.** Многоуровневые цепочки `A → B → C → D`, где проще было бы использовать композицию.
4. **«Универсальные» классы.** Класс с десятком флагов и переключателей режимов вместо нескольких простых классов.
5. **Оверинжиниринг конфигурации.** Внешние конфиги и DI-контейнеры для проекта из трёх классов.

## Пример (нарушение → исправление)

**Плохо (нарушение KISS):**

```java
interface DiscountStrategy { BigDecimal apply(BigDecimal price); }
class NoDiscount implements DiscountStrategy { ... }
class FixedDiscount implements DiscountStrategy { ... }
class DiscountStrategyFactory { ... }
class DiscountService {
    private final DiscountStrategyFactory factory;
    DiscountService(DiscountStrategyFactory f) { this.factory = f; }
    BigDecimal price(BigDecimal base, String type) {
        return factory.create(type).apply(base);
    }
}
```

Здесь на 4 класса и фабрику — ради одной скидки. Если вариантов скидки пока один-два и они не меняются динамически, это оверинжиниринг.

**Хорошо (KISS):**

```java
class PriceCalculator {
    BigDecimal applyDiscount(BigDecimal base, BigDecimal percent) {
        return base.subtract(base.multiply(percent).divide(BigDecimal.valueOf(100)));
    }
}
```

Абстракцию (интерфейс + фабрику) вводим **только когда** появляется реальная потребность: несколько взаимозаменяемых алгоритмов, конфигурируемость во время выполнения, тестируемая подмена.

## Когда простота — не самоцель

KISS не означает «пишите примитивный код любой ценой». Он не отменяет:
- необходимых абстракций, продиктованных **текущими** требованиями (например, полиморфизм там, где действительно есть несколько реализаций);
- инкапсуляции и разделения ответственности (это тоже способ *упростить* понимание системы);
- SOLID-принципов — они и есть инструменты управления сложностью, а не её источник.

Баланс: **минимальная достаточная сложность** — ровно столько абстракций, сколько нужно сейчас, и не больше.

## Практические признаки соблюдения KISS

- Класс/метод решает одну понятную задачу, имя отражает суть.
- Нет «запасных» параметров и флагов, которые никто не использует.
- Число уровней абстракции минимально и оправдано.
- Новый разработчик понимает код без «экскурса в архитектуру».
- Рефакторинг к абстракции делается **по факту** дублирования/вариативности, а не заранее.

## Итог

**KISS** — принцип проектирования, требующий выбирать простейшее рабочее решение и избегать преждевременного усложнения. В OOP/OOD он проявляется в умеренном использовании наследования, паттернов, абстракций и конфигураций: сложность вводится только тогда, когда она окупается реальными требованиями, а не гипотетическим будущим.
