# 150. Расскажите об интерактивном rebase.

**Интерактивный rebase** (команда `git rebase -i` или `git rebase --interactive`) — это мощный инструмент в Git, который позволяет не просто перенести последовательность коммитов на новую базовую точку, но и **отредактировать саму историю** перед этим переносом. В отличие от обычного rebase, который автоматически применяет коммиты «как есть», интерактивный режим открывает редактор со списком («todo list») коммитов, давая вам полный контроль над тем, что с ними произойдет .

В контексте CI/CD этот инструмент критически важен на этапе **подготовки кода к слиянию**, так как позволяет привести историю фича-ветки в чистый, логичный и читаемый вид перед отправкой в основную ветку (например, в `main` или `master`).

### 🛠️ Как это работает

Вы запускаете команду, указывая коммит, *после* которого хотите начать изменения:

```bash
git rebase -i HEAD~3
# или
git rebase -i <commit-hash>^
```

Git открывает ваш текстовый редактор со списком коммитов в обратном хронологическом порядке. Каждая строка начинается с команды (по умолчанию `pick`), хеша и сообщения коммита. Вы можете менять порядок строк, заменять команды и даже удалять строки, чтобы удалить коммиты .

### 📋 Основные команды в todo-листе

| Команда | Сокращение | Действие |
| :--- | :--- | :--- |
| **pick** | `p` | Использовать коммит как есть (по умолчанию). |
| **reword** | `r` | Использовать коммит, но **изменить сообщение** коммита. |
| **edit** | `e` | Использовать коммит, но **остановиться** для правки файлов (например, чтобы разбить коммит на части или что-то исправить). |
| **squash** | `s` | **Объединить** коммит с предыдущим, сохранив оба сообщения (Git предложит отредактировать итоговое сообщение). |
| **fixup** | `f` | **Объединить** коммит с предыдущим, но **отбросить** сообщение текущего коммита (идеально для мелких правок типа «fix typo»). |
| **drop** | `d` | **Удалить** коммит (или просто удалите строку из списка). |
| **exec** | `x` | **Выполнить** произвольную shell-команду (например, `make test`) после применения коммита. Полезно для проверки, что промежуточные состояния сборки не сломаны . |

### 🔄 Типичные сценарии использования в CI/CD

1.  **Очистка истории перед Pull Request**: Разработчик сделал 10 мелких коммитов («wip», «fix», «еще один фикс»). Перед созданием PR он запускает интерактивный rebase и с помощью `squash`/`fixup` превращает их в 2–3 логически завершенных коммита. Это упрощает код-ревью и делает историю основной ветки чище.
2.  **Исправление ошибок в старых коммитах**: Если в коммите, сделанном три дня назад, найдена опечатка, не обязательно делать новый коммит «fix typo». Можно запустить `rebase -i`, пометить нужный коммит как `edit`, исправить файл, сделать `git commit --amend` и продолжить (`git rebase --continue`). История останется линейной и аккуратной.
3.  **Разбиение одного большого коммита**: Если вы случайно закоммитили слишком много изменений одним куском, можно пометить коммит как `edit`, затем сбросить его (`git reset HEAD^`), после чего создавать несколько отдельных коммитов по частям.
4.  **Перестановка коммитов**: Если логичнее, чтобы исправление шло *перед* фичей, а не после, вы можете просто поменять строки местами в todo-листе.

### ⚠️ Важные меры предосторожности

- **Не переписывайте публичную историю**: Никогда не делайте интерактивный rebase для коммитов, которые уже были отправлены в общую ветку (если только вы не уверены, что никто другой на них не опирается). Это меняет хеши коммитов и ломает историю для всех остальных.
- **Разрешение конфликтов**: Если при ребейзе возникают конфликты, процесс останавливается. Вы разрешаете конфликты, добавляете файлы (`git add`) и продолжаете с помощью `git rebase --continue`. Если что-то пошло не так, всегда можно отменить всё командой `git rebase --abort` и вернуться в исходное состояние .
- **Резервная копия**: Перед сложным rebase полезно создать временную ветку на текущем состоянии (например, `git branch backup-branch`), чтобы иметь точку возврата.

Интерактивный rebase — это не просто «перебазирование», а полноценный редактор истории, который помогает поддерживать гигиену репозитория, что напрямую влияет на качество автоматических проверок и удобство работы команды в CI/CD-процессах.
