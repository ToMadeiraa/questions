# 153. Как тестировать код? Какой используете фреймворк?

В контексте SCM / CI / CD тестирование строится по принципу **тестовой пирамиды** и стратегии **Shift-Left**: чем раньше и дешевле обнаруживается дефект, тем ниже стоимость его исправления. Тесты встраиваются в пайплайн поэтапно, а конкретный фреймворк выбирается в зависимости от языка, типа теста и инфраструктуры.

## 1. Стратегия тестирования в CI/CD

### Тестовая пирамида

Майк Кон рекомендует распределять тесты следующим образом:

- **Основание (≈70%)** — модульные тесты (unit tests). Самые быстрые и дешёвые, выполняются на каждом коммите.
- **Середина** — интеграционные, компонентные и сервисные тесты. Проверяют взаимодействие модулей, работу с БД, API и внешними сервисами.
- **Вершина** — end-to-end (E2E), UI-тесты, приёмочные тесты. Самые медленные и дорогие, запускаются реже (например, перед мержем в основную ветку или перед релизом).

### Shift-Left

Тестирование начинается **до** написания кода: статический анализ, линтеры и проверка стиля запускаются ещё в IDE или на этапе pre-commit. Это позволяет отловить синтаксические ошибки, уязвимости и нарушения код-стайла до того, как они попадут в общий репозиторий.

### Размещение тестов в пайплайне

| Этап пайплайна | Типы тестов | Триггер |
|---|---|---|
| Pre-commit / локально | Линтеры, статический анализ, быстрые unit-тесты | `git commit` |
| CI (pull request) | Unit-тесты, интеграционные тесты, SAST | Push / PR |
| Staging / pre-release | E2E, нагрузочные, DAST, тесты безопасности | Merge в main / тег |
| Production | Canary-тесты, синтетический мониторинг | После деплоя |

Быстрые тесты запускаются первыми, чтобы «отсеять» плохие изменения до того, как ресурсоёмкие проверки начнут выполняться.

## 2. Фреймворки по типам тестов

### Модульные тесты (Unit)

| Язык / стек | Фреймворки |
|---|---|
| Java | JUnit 5, TestNG, Mockito (моки), AssertJ (ассерты) |
| JavaScript / TypeScript | Jest, Vitest, Mocha + Chai |
| Python | pytest, unittest, Hypothesis (property-based) |
| C# / .NET | MSTest, NUnit, xUnit |

### Интеграционные тесты

| Стек | Инструменты |
|---|---|
| API (REST / SOAP) | Postman / Newman, Supertest (Node.js), REST Assured (Java) |
| Java + Spring | JUnit + Spring Boot Test, Testcontainers |
| Базы данных | Testcontainers (изолированные инстансы БД в Docker) |
| Компонентные (фронтенд) | React Testing Library, Vue Test Utils |

### End-to-End (E2E) тесты

- **Cypress** — современный фреймворк для веб-приложений, работает в браузере, хорошо подходит для интеграционных и E2E-сценариев.
- **Playwright** — кросс-браузерное тестирование, поддерживает Chromium, Firefox, WebKit, удобен для параллельного запуска.
- **Selenium** — классический инструмент автоматизации браузеров, часто используется в связке с Selenium Grid для кросс-браузерных прогонов.

### Нагрузочные и performance-тесты

- **k6** — современный инструмент для нагрузочного тестирования с хорошей интеграцией в CI.
- **JMeter** — классика для нагрузочного и стресс-тестирования.
- **Gatling** — нагрузочное тестирование на Scala/Java с генерацией отчётов.

### Безопасность

- **SAST** (статический анализ): SonarQube, CodeQL, Snyk Code.
- **DAST** (динамический анализ): OWASP ZAP, Burp Suite.
- **Сканирование зависимостей**: Snyk, `npm audit`, Dependabot.

### Инфраструктурные тесты (IaC)

- **Terratest** — тестирование Terraform-конфигураций.
- **KitchenCI** — проверка конфигураций Ansible / Chef / Puppet.

## 3. Практические рекомендации для CI/CD

1. **Изолированность и детерминизм.** Тесты не должны зависеть от порядка запуска, внешних сервисов или текущего времени. Внешние зависимости заменяются моками или Testcontainers.
2. **Параллелизация.** Разделяйте тестовые наборы на шарды и запускайте параллельно в CI, чтобы сократить общее время пайплайна.
3. **Кэширование зависимостей.** Восстановление `node_modules`, Maven/Gradle-кэша и Docker-слоёв ускоряет прогоны.
4. **Чёткие quality gates.** Определите, какие падения блокируют мерж/деплой, а какие являются лишь предупреждением. Например, падение unit-теста блокирует PR, а незначительное визуальное расхождение может быть проверено вручную.
5. **Карантин flaky-тестов.** Нестабильные тесты временно изолируются, чтобы не блокировать релизы, но с обязательством починить их.

## 4. Резюме

Универсального «одного фреймворка» нет: выбор зависит от стека и типа проверки. На практике чаще всего используется комбинация:

- **Jest / Vitest** или **JUnit / pytest** — для unit-тестов;
- **Testcontainers / Supertest / REST Assured** — для интеграционных;
- **Cypress / Playwright** — для E2E и UI;
- **k6 / JMeter** — для нагрузки;
- **SonarQube / OWASP ZAP / Snyk** — для безопасности.

Главный принцип в CI/CD: **быстрые и дешёвые тесты выполняются на каждом коммите, медленные и дорогие — на этапе pre-merge или pre-release**, а результаты всех проверок агрегируются в едином отчёте пайплайна.
