# 103. Что такое Dependency Injection? Приведите пример.

## Определение

**Dependency Injection (DI, внедрение зависимостей)** — это паттерн проектирования (и одновременно принцип инверсии управления, IoC), при котором объект не создаёт свои зависимости самостоятельно, а получает их извне — от внешнего кода («инжектора»). В контексте OOP/OOD это форма реализации принципа **Inversion of Control (IoC)** и способ соблюдения **Dependency Inversion Principle (DIP)** из SOLID: модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба должны зависеть от абстракций.

Ключевая идея: класс должен **зависеть от абстракций (интерфейсов)**, а конкретные реализации подставляются снаружи. Это уменьшает связанность (coupling), повышает тестируемость, гибкость и переиспользуемость кода.

## Проблема, которую решает DI

Без DI класс жёстко «прибит» к конкретной реализации зависимости:

```java
// Плохо: жёсткая связь с конкретным классом
class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();

    void placeOrder(Order order) {
        repository.save(order);
    }
}
```

Здесь `OrderService`:
- нельзя протестировать без реальной БД (нужен мок);
- нельзя заменить `MySqlOrderRepository` на `InMemoryOrderRepository` или `PostgresOrderRepository` без правки кода;
- нарушает DIP — зависит от конкретики, а не от абстракции.

## Решение через DI

Зависимость выносится в интерфейс и передаётся извне (обычно через конструктор):

```java
// Абстракция
interface OrderRepository {
    void save(Order order);
}

// Конкретные реализации
class MySqlOrderRepository implements OrderRepository {
    public void save(Order order) { /* ... */ }
}

class InMemoryOrderRepository implements OrderRepository {
    private final List<Order> orders = new ArrayList<>();
    public void save(Order order) { orders.add(order); }
}

// Класс зависит от абстракции, а не от реализации
class OrderService {
    private final OrderRepository repository;

    // Внедрение через конструктор
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    void placeOrder(Order order) {
        repository.save(order);
    }
}
```

Сборка объекта — снаружи:

```java
// Production
OrderService service = new OrderService(new MySqlOrderRepository());

// Тест
OrderService testService = new OrderService(new InMemoryOrderRepository());
```

## Способы внедрения зависимостей

1. **Через конструктор (Constructor Injection)** — предпочтительный вариант: зависимости обязательны и неизменяемы (`final`), объект всегда в валидном состоянии.
2. **Через сеттер (Setter Injection)** — для опциональных или изменяемых зависимостей; объект может существовать в неполном состоянии.
3. **Через интерфейс (Interface Injection)** — объект реализует интерфейс с методом внедрения; используется редко.
4. **Через поле (Field Injection)** — часто встречается во фреймворках (например, `@Autowired` в Spring), но не рекомендуется: скрывает зависимости, затрудняет тестирование и не позволяет сделать поля `final`.

## Виды DI-контейнеров

- **Ручной DI (Pure DI)** — зависимости внедряются вручную в точке входа (`main`). Просто, прозрачно, без магии; подходит для небольших приложений.
- **DI-контейнер (IoC-контейнер)** — фреймворк (Spring, Guice, Dagger, .NET DI, NestJS), который автоматически разрешает граф зависимостей, управляет жизненным циклом (singleton, prototype, scoped) и конфигурацией.

## Преимущества

- **Слабая связанность (loose coupling)** — классы зависят от интерфейсов.
- **Тестируемость** — легко подставлять моки/стабы.
- **Гибкость и расширяемость** — замена реализации без изменения потребителя.
- **Соблюдение SOLID** — прежде всего DIP и OCP.
- **Управление жизненным циклом** — контейнер сам решает, когда создавать и уничтожать объекты.

## Недостатки / подводные камни

- Усложнение кода и «церемоний» (особенно с контейнерами).
- Скрытая сложность графа зависимостей (циклы, порядок инициализации).
- Избыточность для маленьких проектов.
- «Service Locator» — антипаттерн, который часто путают с DI: объект сам запрашивает зависимости у реестра, что скрывает зависимости и ухудшает тестируемость.

## Итог

DI — это не «магия фреймворка», а принцип проектирования: **не создавай зависимости внутри, а получай их снаружи через абстракции**. Контейнеры лишь автоматизируют ручную сборку графа объектов. Главная ценность — слабая связанность и тестируемость, а не сам факт использования Spring/Guice.
