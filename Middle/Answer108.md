# 108. Какие преимущества композиции перед наследованием?

Композиция («has-a» / «использует») и наследование («is-a» / «является») — два ключевых механизма переиспользования в ООП. Принцип «Composition over Inheritance» (предпочитай композицию наследованию) из книги «Design Patterns» (GoF) отражает, что в большинстве случаев композиция даёт более гибкий и устойчивый дизайн. Разберём преимущества подробно.

## 1. Более слабая связанность (low coupling)

При наследовании подкласс жёстко зависит от реализации родителя: изменениеprotected-членов, сигнатур или внутренней логики базового класса может сломать наследников («хрупкий базовый класс», fragile base class problem). Это нарушает инкапсуляцию — подкласс знает о деталях реализации родителя.

При композиции класс зависит только от **публичного интерфейса** встроенного объекта. Внутренняя реализация компонента может меняться свободно, пока контракт интерфейса соблюдается.

```java
// Плохо: наследование ради переиспользования кода
class ArrayListStack<T> extends ArrayList<T> {
    public void push(T item) { add(item); }
    public T pop() { return remove(size() - 1); }
    // Наследуются ВСЕ методы ArrayList: add(index, e), removeRange и т.д.
    // Клиент может вставить элемент в середину — инвариант стека нарушен!
}

// Хорошо: композиция
class Stack<T> {
    private final List<T> storage = new ArrayList<>();
    public void push(T item) { storage.add(item); }
    public T pop() { return storage.remove(storage.size() - 1); }
    public int size() { return storage.size(); }
    // Наружу виден только контракт стека
}
```

## 2. Инкапсуляция сохраняется

Наследование раскрывает наследнику `protected`-детали родителя — это «белая коробка». Композиция — «чёрная коробка»: класс работает с компонентом только через его публичный API, не залезая во внутренности.

## 3. Гибкость на этапе выполнения (runtime)

Наследование фиксируется **статически** на этапе компиляции. Композиция позволяет подставлять разные реализации через конструктор или сеттер — это основа паттернов **Strategy**, **Decorator**, **State**, **Bridge**, а также внедрения зависимостей (DI).

```java
interface Notifier { void send(String msg); }

class Service {
    private final Notifier notifier;
    Service(Notifier notifier) { this.notifier = notifier; } // можно подставить Email/SMS/Push
}
```

## 4. Отсутствие проблем множественного наследования

В Java, C#, C++ (для классов) множественное наследование классов запрещено или чревато «ромбовидной проблемой» (diamond problem). Композиция позволяет собрать объект из произвольного числа компонентов без подобных конфликтов.

## 5. Переиспользование без иерархии «is-a»

Наследование оправдано только при истинном отношении «является» (LSP — принцип подстановки Лисков). Часто наследование используют просто ради переиспользования кода — и тогда рождаются искусственные иерархии вроде `class Manager extends Employee`, где Manager не должен наследовать всё поведение Employee. Композиция позволяет переиспользовать функциональность без лживой таксономии.

## 6. Устойчивость к изменениям и тестируемость

- Композиция позволяет подменять зависимости **моками/стабами** в юнит-тестах — наследование от конкретного класса часто тянет за собой нежелательную инициализацию.
- Меньше каскадных изменений: правка компонента не «протекает» в десятки наследников.
- Соответствует принципу **Open/Closed**: новое поведение добавляется новым компонентом, а не правкой базового класса.

## 7. Упрощение иерархии классов

Глубокие иерархии наследования трудно понимать и сопровождать (проблема «классов-божеств» наверху). Композиция даёт плоскую структуру: объекты собираются из небольших специализированных компонентов, каждый с одной ответственностью (SRP).

## 8. Позднее связывание и динамическая конфигурация

Поведение объекта можно менять во время выполнения (например, декораторы навешиваются в рантайме), тогда как с наследованием поведение «зашито» в тип.

---

## Когда наследование всё же уместно

Композиция — не серебряная пуля. Наследование оправдано, когда:

- отношение действительно **«is-a»** и выполняется **LSP** (квадрат не наследует прямоугольник!);
- нужен **полиморфизм через общий базовый тип** (абстрактный класс/интерфейс) и подклассы дополняют, а не ломают контракт;
- используется **шаблонный метод** (Template Method) или каркас фреймворка, спроектированный под наследование;
- нужен доступ к `protected`-хукам, сознательно предоставленным автором базового класса.

## Итоговая сравнительная таблица

| Критерий | Наследование | Композиция |
|---|---|---|
| Связность | Сильная (white-box) | Слабая (black-box) |
| Момент связывания | Compile-time | Compile-time + runtime |
| Инкапсуляция | Частично нарушается | Сохраняется |
| Множественное переиспользование | Ограничено (diamond problem) | Свободное |
| Гибкость замены поведения | Низкая | Высокая |
| Тестируемость | Ниже | Выше |
| Риск «хрупкого базового класса» | Есть | Нет |
| Типичное отношение | is-a | has-a |

**Правило большого пальца:** начинайте с композиции; вводите наследование только при доказанном отношении «is-a» и стабильном контракте базового класса.
