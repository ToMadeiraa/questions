# 84. Что такое Undefined behavior? Приведите примеры.

**Undefined behavior (неопределённое поведение, UB)** в C++ — это ситуация, когда программа нарушает правила языка, и стандарт C++ не накладывает **никаких** требований на поведение такой программы . Это означает, что компилятор не обязан выдавать ошибку или предупреждение (хотя может), а скомпилированная программа не обязана делать что-либо осмысленное. Результат может быть любым: от «правильной» работы до падения, порчи данных или, в теории, «демонов из носа».

Ключевой момент: в C++ наличие UB в любой точке программы (даже в недостижимой ветке кода) даёт компилятору право предполагать, что эта ситуация **никогда не возникнет**. На этом основываются агрессивные оптимизации, которые могут привести к «путешествию во времени» — когда код, выполняющийся *до* операции с UB, ведёт себя не так, как написано .

### Примеры Undefined Behavior

Ниже приведены классические примеры, которые часто встречаются в коде на C++.

#### 1. Выход за границы массива
Чтение или запись за пределами выделенной памяти — классический UB.

```cpp
int arr[4] = {0};
int x = arr[4]; // UB: индекс 4 выходит за границы (допустимы 0..3)
```

Компилятор с оптимизацией может «вывести», что `arr[4]` недостижим, и удалить проверки или весь код вокруг .

#### 2. Переполнение знакового целого
В отличие от беззнаковых типов, переполнение `int` — это UB.

```cpp
int x = INT_MAX;
x = x + 1; // UB: знаковое переполнение
```

Компилятор может предположить, что `x + 1 > x` всегда истинно для `int`, и оптимизировать функцию `foo(x) { return x + 1 > x; }` в безусловный `return true` .

#### 3. Разыменование нулевого указателя
```cpp
int* p = nullptr;
int x = *p; // UB
```

Многие компиляторы вставляют ловушку (trap) или предполагают, что эта ветка не выполняется, что может привести к удалению проверок на `nullptr` в других местах .

#### 4. Чтение неинициализированной переменной
```cpp
int x;      // неинициализирована
if (x > 0)  // UB: чтение indeterminate value
    do_something();
```

Значение может быть «ловушечным» (trap representation), и даже чтение без использования может быть UB для некоторых типов.

#### 5. Нарушение правил strict aliasing
Доступ к объекту через указатель несовместимого типа (кроме `char*`/`std::byte*`) — UB.

```cpp
float f = 1.0f;
int* p = reinterpret_cast<int*>(&f);
int i = *p; // UB: нарушение strict aliasing
```

Компилятор может кэшировать значение `f` в регистре, не подозревая, что `*p` его меняет.

#### 6. Гонка данных (data race)
Одновременный доступ из разных потоков, где хотя бы один — запись, без синхронизации.

```cpp
int global = 0;
// Поток 1: global = 42;
// Поток 2: int x = global;
// UB: data race
```

Стандарт C++ прямо говорит, что любая гонка данных ведёт к UB .

#### 7. Изменение константного объекта
```cpp
const int x = 10;
const_cast<int&>(x) = 20; // UB, если объект изначально был const
```

Попытка изменить объект, определённый как `const`, через `const_cast` — UB .

### Важно: UB и оптимизации

Поскольку компилятор вправе предполагать, что UB не произойдёт, наличие UB может «отравить» всю программу. Например, если в функции есть ветка с разыменованием `nullptr`, компилятор может удалить проверку `if (p == nullptr)` *до* этого места, рассуждая, что раз код дошёл до разыменования, `p` не может быть нулевым . Именно поэтому UB нужно избегать любой ценой, а не полагаться на то, что «сейчас работает».
