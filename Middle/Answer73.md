# 73. Зачем используют exceptions?

Исключения в C++ — это механизм передачи информации об ошибке из точки её обнаружения в точку, где её можно обработать, без использования кодов возврата и без ручного проброса ошибки через все промежуточные уровни вызовов.

Главная идея: **обычный ход программы и обработка ошибок разделяются**. Функция, обнаружившая проблему, не обязана знать, что с ней делать; функция, умеющая обработать проблему, не обязана находиться рядом с местом её возникновения.

## 1. Основные причины использования исключений

### 1.1. Ошибку трудно случайно проигнорировать

При использовании кодов возврата можно забыть проверить результат:

```cpp
int rc = do_something();
// забыли проверить rc и продолжили работу
use_result();
```

Исключение же либо обрабатывается, либо автоматически распространяется вверх по стеку. Если обработчик не найден вообще, вызывается `std::terminate`, и программа аварийно завершается. Это лучше, чем молча продолжать работу с некорректными данными.

Конечно, никто не мешает написать `catch (...)` и ничего не сделать, но для этого нужно явное действие, а не случайная забывчивость.

### 1.2. Разделение нормальной логики и обработки ошибок

Без исключений код часто выглядит так:

```cpp
Result r1 = step1();
if (!r1.ok) return r1.error;

Result r2 = step2(r1.value);
if (!r2.ok) return r2.error;

Result r3 = step3(r2.value);
if (!r3.ok) return r3.error;
```

При этом основная логика — последовательность шагов — тонет в проверках. С исключениями:

```cpp
auto r1 = step1();
auto r2 = step2(r1);
auto r3 = step3(r2);
```

Ошибка «всплывает» сама, а проверки сосредоточены в одном месте:

```cpp
try {
    auto r1 = step1();
    auto r2 = step2(r1);
    auto r3 = step3(r2);
    // ...
} catch (const std::exception& e) {
    std::cerr << "Ошибка: " << e.what() << '\n';
}
```

### 1.3. Проброс ошибки через промежуточные слои

Исключение позволяет функции среднего уровня не знать о типах ошибок нижнего уровня. Ей не нужно объявлять «универсальный» код ошибки, расширять его при добавлении нового типа сбоя и обновлять все сигнатуры.

Например, функция `load_config()` вызывает парсер, тот вызывает функцию чтения файла, та — системный вызов. Ошибка чтения может быть выброшена глубоко внутри, а обработана на уровне приложения. Промежуточным функциям не нужно протаскивать `error_code` через каждый слой.

### 1.4. Конструкторы не могут возвращать код ошибки

Конструктор не имеет возвращаемого значения. Если объект не удалось создать, сообщить об этом можно:

- через исключение;
- через отдельный флаг/метод `init()`;
- через фабричную функцию, возвращающую `std::optional` или `std::expected`.

Исключение — самый естественный и безопасный вариант: если конструктор выбросил исключение, объект считается не созданным, его деструктор не вызывается, но уже созданные члены и базовые подобъекты корректно разрушаются.

То же касается перегруженных операторов: у `operator+`, `operator[]`, `operator*` и т.п. нет удобного способа вернуть ошибку, кроме исключения.

### 1.5. RAII и автоматическое освобождение ресурсов

При выходе из функции по исключению выполняется **раскрутка стека** (`stack unwinding`): для всех полностью созданных локальных объектов вызываются деструкторы. Это позволяет использовать RAII:

```cpp
void process() {
    std::lock_guard<std::mutex> lock(mtx);
    auto buffer = std::make_unique<char[]>(1024);

    may_throw(); // исключение

    // lock и buffer будут корректно освобождены
}
```

Без исключений пришлось бы вручную освобождать ресурсы на каждом пути выхода, и любая ошибка или ранний `return` могли бы привести к утечке или взаимной блокировке.

### 1.6. Богатая диагностическая информация

Исключение — это объект. Он может нести:

- тип ошибки;
- текстовое описание;
- код ошибки;
- имя файла и строку;
- вложенную причину;
- произвольные данные.

```cpp
class ConfigError : public std::runtime_error {
public:
    explicit ConfigError(const std::string& msg, std::string path)
        : std::runtime_error(msg), path_(std::move(path)) {}

    const std::string& path() const noexcept { return path_; }

private:
    std::string path_;
};
```

Благодаря наследованию можно ловить ошибки по базовому типу:

```cpp
try {
    load_config("app.cfg");
} catch (const ConfigError& e) {
    std::cerr << e.what() << " in " << e.path() << '\n';
} catch (const std::exception& e) {
    std::cerr << "Другая ошибка: " << e.what() << '\n';
}
```

Это гораздо информативнее, чем один `int rc`.

### 1.7. Единообразие со стандартной библиотекой

Исключения активно использует сам C++ и его стандартная библиотека:

- `std::vector::at()` бросает `std::out_of_range`;
- `std::stoi()` и родственные функции — `std::invalid_argument` / `std::out_of_range`;
- `new` — `std::bad_alloc`;
- `dynamic_cast` для ссылок — `std::bad_cast`;
- `std::filesystem` — `std::filesystem::filesystem_error`;
- `std::thread` — `std::system_error`;
- `std::function`, `std::any`, `std::variant` — соответствующие исключения при неверном доступе.

Если код использует стандартные компоненты, он так или иначе сталкивается с исключениями. Последовательное использование того же механизма делает код единообразным.

### 1.8. Совместимость с обобщённым кодом

Шаблонные функции и контейнеры не могут заранее знать, какой тип ошибки вернёт пользовательский тип. Исключения позволяют передавать ошибку через обобщённый код, не «зашивая» в интерфейсы конкретный `enum class Error`.

### 1.9. Производительность на успешном пути

В распространённых реализациях (table-based unwinding) исключения устроены по принципу **zero-cost exceptions**: при нормальном выполнении не нужно проверять код возврата после каждого вызова, а таблицы раскрутки используются только при фактическом `throw`.

Отсюда типичная формулировка: на успешном пути исключения почти бесплатны, но **выброс исключения дорог**. Это не абсолютная бесплатность: таблицы увеличивают размер бинарника, а некоторые оптимизации могут быть затруднены. Но по сравнению с постоянными проверками кодов ошибок в горячем коде исключения часто выгодны, если ошибки действительно редки.

## 2. Что дают исключения по сравнению с кодами ошибок

| Критерий | Коды возврата | Исключения |
|---|---|---|
| Проверка ошибки | Обязанность вызывающего, легко забыть | Автоматическое распространение до обработчика |
| Проброс через слои | Нужно вручную возвращать код на каждом уровне | Происходит автоматически |
| Конструкторы | Не могут вернуть код | Могут сообщить об ошибке |
| Освобождение ресурсов | Вручную на каждом пути выхода | Через RAII и раскрутку стека |
| Информативность | Обычно число или enum | Объект с типом и данными |
| Ветвление кода | Проверки вперемешку с логикой | Логика отдельно, обработка отдельно |
| Цена на успешном пути | Проверка после каждого вызова | Обычно отсутствует |
| Цена при ошибке | Небольшая | Высокая |

При этом коды ошибок тоже имеют право на существование: они предсказуемы, не требуют раскрутки стека, удобны на границах ABI и в системах, где исключения отключены.

## 3. Как это работает механически

Упрощённо:

1. Выполняется `throw выражение;`.
2. Создаётся объект исключения (копированием или перемещением).
3. Начинается раскрутка стека: разрушаются локальные объекты.
4. Ищется подходящий `catch` вверх по стеку.
5. Если найден — управление передаётся в обработчик.
6. Если не найден — вызывается `std::terminate`.

```cpp
#include <stdexcept>
#include <string>

double divide(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("division by zero");
    }
    return a / b;
}

int main() {
    try {
        double x = divide(10.0, 0.0);
        // ...
    } catch (const std::invalid_argument& e) {
        // обработка
    }
}
```

Важные детали:

- ловить исключения следует **по ссылке** (`const std::exception&`), а не по значению, чтобы избежать срезания (`slicing`) и лишнего копирования;
- обработчики проверяются в порядке объявления, поэтому более конкретные типы должны идти раньше базовых;
- `catch (...)` ловит всё, но не даёт доступа к объекту ошибки;
- повторный выброс делается через `throw;`;
- вложенную причину можно сохранить через `std::throw_with_nested` и `std::exception_ptr`.

## 4. Гарантии безопасности относительно исключений

Исключения тесно связаны с понятием **exception safety guarantees**:

1. **No-throw guarantee** — функция не бросает исключений; обычно помечается `noexcept`.
2. **Strong guarantee** — при ошибке состояние программы остаётся прежним (операция либо выполнена, либо нет).
3. **Basic guarantee** — при ошибке сохраняется валидное состояние, но конкретные данные могли измениться; утечек и нарушения инвариантов нет.
4. **No guarantee** — худший случай, обычно признак плохого дизайна.

Например, `std::vector::push_back` при нехватке памяти обычно даёт сильную гарантию, если перемещение элементов не бросает исключений. Именно поэтому перемещающие конструкторы часто помечают `noexcept`: контейнер может выбрать перемещение вместо копирования при перераспределении.

`noexcept` — это не «пожелание», а жёсткое обещание: если функция, помеченная `noexcept`, всё-таки выбросит исключение, будет вызван `std::terminate`.

## 5. Когда исключения не нужны или опасны

Исключения — не универсальная замена всем механизмам ошибок.

### 5.1. Ожидаемые и частые ошибки

Если ошибка является нормальной частью работы (например, пользователь ввёл неверный символ, файл не найден в штатном сценарии, парсер встретил конец данных), исключение на каждом таком событии может быть дорогим и неудобным. Здесь лучше подходят:

- `std::optional<T>` — «значения может не быть»;
- `std::expected<T, E>` (C++23) — значение или конкретная ошибка;
- `std::error_code` — системные и библиотечные ошибки;
- `std::variant<T, Error>` — альтернатива до C++23.

### 5.2. Управление потоком исполнения

Не стоит использовать исключения как замену `break`, `return` или обычному ветвлению. Это делает код неочевидным и может быть медленным.

### 5.3. Деструкторы

Бросать исключение из деструктора опасно: деструктор может вызываться во время раскрутки стека из-за другого исключения, и тогда программа завершится через `std::terminate`. Деструкторы по умолчанию неявно `noexcept`. Если деструктор может выполнять «опасную» операцию, её нужно обрабатывать внутри, а не выпускать наружу.

### 5.4. Границы ABI и C-код

Нельзя допускать, чтобы исключение проходило через C-функции и другие внешние интерфейсы, не рассчитанные на C++-исключения. На границах библиотек исключения нужно преобразовывать в коды ошибок.

### 5.5. Системы без исключений

Во встраиваемых системах, ядрах, некоторых игровых и высоконагруженных проектах исключения могут быть отключены (`-fno-exceptions`) ради размера кода, предсказуемости и отсутствия раскрутки стека. Там используют коды ошибок, `std::expected` или собственные типы результата.

## 6. Типичный пример: исключения и RAII вместе

```cpp
#include <fstream>
#include <stdexcept>
#include <string>

std::string read_file(const std::string& path) {
    std::ifstream in(path);
    if (!in) {
        throw std::runtime_error("cannot open file: " + path);
    }

    std::string content;
    std::string line;
    while (std::getline(in, line)) {
        content += line;
        content += '\n';
    }

    if (in.bad()) {
        throw std::runtime_error("read error: " + path);
    }

    return content;
}
```

Здесь исключение:

- сообщает о невозможности открыть файл;
- не требует возвращать специальное значение;
- автоматически закрывает `std::ifstream` при выходе;
- позволяет вызывающему коду решить, что делать: показать сообщение, повторить попытку, использовать файл по умолчанию или завершить работу.

## 7. Краткий итог

Исключения используют потому, что они:

1. **Автоматически распространяют ошибку** вверх по стеку, не требуя ручного проброса через каждый уровень.
2. **Разделяют нормальную логику и обработку ошибок**, делая код чище.
3. **Позволяют сообщать об ошибках из конструкторов и операторов**, где нет возвращаемого значения.
4. **Работают вместе с RAII**, обеспечивая корректное освобождение ресурсов при раскрутке стека.
5. **Передают богатую информацию** об ошибке в виде объекта и иерархии типов.
6. **Соответствуют стилю стандартной библиотеки C++**.
7. **Не нагружают успешный путь** проверками, если ошибки действительно исключительны.

При этом исключения — это инструмент для **исключительных ситуаций**, а не для обычного ветвления. Для ожидаемых частых ошибок, границ ABI и систем без поддержки раскрутки стека лучше подходят `std::expected`, `std::error_code`, `std::optional` или коды возврата.
