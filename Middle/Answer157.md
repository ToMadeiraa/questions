# 156. Сколько тестов нужно написать на одну функцию?

Универсального числа не существует: количество тестов на функцию определяется её сложностью, количеством ветвлений и критичностью, а не фиксированной нормой. В контексте SCM/CI/CD это означает, что политика тестирования должна быть настраиваемой и обоснованной, а не жёстко заданной.

## Основные ориентиры

**Минимум — один тест на функцию.** Это базовое требование для покрытия: каждая публичная функция с нетривиальной логикой должна иметь хотя бы один тест. Однако одного теста недостаточно, если функция содержит ветвления: в таком случае одна реализация с фиксированным ответом может пройти единственный тест, не будучи корректной.

**Практический ориентир — по одному тесту на каждую ветвь или путь исполнения.** Если функция содержит условные операторы, циклы или обработку исключений, каждый значимый путь должен быть покрыт отдельным тестом (или параметризованным кейсом). Для простых функций с одним выходом и без ветвлений достаточно 1–3 тестов; для функций с несколькими ветвями и граничными случаями — 5–10 и более.

**Верхняя граница требует обоснования.** Превышение 10 тестов на одну функцию обычно сигнализирует либо о избыточности (дублировании проверок), либо о том, что функция делает слишком много и её стоит декомпозировать. В CI/CD-пайплайне избыточные тесты увеличивают время выполнения без пропорционального роста уверенности.

## Что важнее количества

**Покрытие ветвей, а не строк.** Метрика покрытия строк легко достигается минимальным числом тестов, но не гарантирует проверку всех логических путей. Для SCM/CI/CD разумно настроить quality gate на покрытие ветвей (branch coverage) с порогом, зависящим от критичности модуля.

**Отсутствие дублирования.** Если два теста проверяют одну и ту же ветвь с одинаковыми входными данными, второй избыточен. Параметризованные тесты (один тест-метод, несколько наборов входных данных) предпочтительнее дублирования кода.

**Регрессионная ценность.** Каждый тест должен отвечать на вопрос: «Какой дефект он поймает, если появится?» Если ответ неочевиден — тест, вероятно, не нужен.

## Рекомендация для CI/CD-политики

Зафиксируйте в конфигурации пайплайна не количество тестов на функцию, а **требования к покрытию** (например, branch coverage ≥ 70% для обычных модулей, ≥ 90% для критичных) и **запрет на падение покрытия** при мерже. Количество тестов на функцию оставьте на усмотрение разработчика в рамках code review: ревьюер оценивает, покрыты ли граничные случаи и ветви, а не считает тесты.

Если же нужен формальный ориентир для настройки линтера или чек-листа ревью: **1–3 теста для простых функций, 5–10 для функций с несколькими ветвями, более 10 — только с письменным обоснованием в описании PR**.
