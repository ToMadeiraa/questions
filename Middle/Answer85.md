# 85. Как определить, что в программе есть memory leak?

Обнаружение утечки памяти в C++ обычно происходит на двух уровнях: **наблюдение за симптомами во время выполнения** и **инструментальный анализ кода**. Утечка возникает, когда память, выделенная в куче (через `new` или `malloc`), не освобождается (через `delete` или `free`), и указатель на неё теряется, из-за чего программа больше не может её освободить .

### 1. Первичные признаки (мониторинг)

Самый простой способ заподозрить утечку — отслеживать потребление памяти процессом. Если график RSS (Resident Set Size) или объёма кучи (heap) демонстрирует **непрерывный рост без стабилизации** на протяжении длительного времени работы (особенно в циклах или при обработке повторяющихся запросов), это верный признак проблемы . В Linux для быстрой проверки можно использовать `top` или `ps`:
```bash
watch -n 1 ps -o pid,rss,comm -p <PID>
```
Если значение RSS постоянно растёт, это указывает на потенциальную утечку .

### 2. Инструменты динамического анализа (основной метод)

Для точного определения места утечки используются специализированные инструменты.

#### Valgrind (Memcheck)
Это де-факто стандарт для Linux. Он запускает программу в виртуальной машине и отслеживает все операции с памятью .
*   **Как использовать**: Скомпилируйте программу с флагом `-g` (отладочная информация), затем запустите:
    ```bash
    valgrind --leak-check=full --show-leak-kinds=all ./your_program
    ```
*   **Интерпретация**: Valgrind выдаст отчёт в конце работы. Ключевые категории:
    *   **definitely lost**: память точно потеряна (нет указателей на неё) — это и есть утечка .
    *   **indirectly lost**: потеряна из-за потери родительского блока.
    *   **possibly lost**: возможная утечка (указатель указывает не на начало блока).
    Отчёт содержит стек вызовов, указывающий на функцию и строку, где была выделена память .

#### AddressSanitizer (ASan) / LeakSanitizer (LSan)
Встроен в компиляторы GCC и Clang, работает значительно быстрее Valgrind (замедление ~2x против 10-30x у Valgrind) . Идеален для регулярного тестирования.
*   **Как использовать**: Компилируйте с флагом санитайзера:
    ```bash
    g++ -fsanitize=address -g your_program.cpp -o your_program
    ```
    На Linux LeakSanitizer встроен в ASan и включён по умолчанию .
*   **Результат**: При выходе программа выведет отчёт с указанием размера утечки и точным стеком вызовов (файл:строка), где произошло выделение памяти .

### 3. Специфичные для платформы средства

#### Windows (Visual Studio / CRT)
Microsoft предоставляет отладочные функции в CRT (C Runtime Library) .
*   **Включение**: В начале программы (до включения заголовков) добавьте:
    ```cpp
    #define _CRTDBG_MAP_ALLOC
    #include <stdlib.h>
    #include <crtdbg.h>
    ```
    В `main` вызовите `_CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);` .
*   **Анализ**: При выходе в окне Output появится отчёт. Если используется `_CRTDBG_MAP_ALLOC`, отчёт будет содержать имена файлов и строки, где произошло выделение памяти (`new` будет заменён на `_malloc_dbg`) .
*   **Точка останова**: Если в отчёте указан номер выделения (например, `{18}`), можно использовать `_crtBreakAlloc = 18;`, чтобы отладчик остановился прямо в момент выделения этой памяти .

### 4. Дополнительные методы

*   **Пользовательские библиотеки**: Существуют библиотеки, такие как **MemPlumber**, которые встраиваются в код и позволяют включать/выключать отслеживание в определённых участках кода (удобно для юнит-тестов) .
*   **Профилировщики кучи (tcmalloc/jemalloc)**: В production-среде можно использовать `gperftools` с tcmalloc для создания профилей кучи (`HEAPPROFILE`), которые затем анализируются через `pprof` .

### Резюме

Для быстрой диагностики на Linux используйте **AddressSanitizer** (быстро, встроен в компилятор). Для глубокого анализа с классификацией типов утечек — **Valgrind**. В среде Windows — встроенные средства **CRT Debug Heap**. Помните, что лучший способ борьбы с утечками — профилактика: используйте умные указатели (`std::unique_ptr`, `std::shared_ptr`) вместо сырых `new`/`delete` .
