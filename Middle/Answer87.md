# 87. Что будет, если выделить один объем памяти, а записать больше?

## Краткий ответ

Это **неопределённое поведение (undefined behavior, UB)**. Программа может:

- «тихо» работать, испортив соседнюю память;
- упасть с ошибкой сегментации (segmentation fault);
- выдать неверный результат;
- повредить кучу (heap corruption) и упасть позже — при `delete`/`free` или при следующем `new`/`malloc`;
- быть использована для эксплуатации уязвимости (перезапись управляющих данных, return-адресов).

Гарантий **никаких** нет. Компилятор вправе предполагать, что выхода за границы не происходит, и оптимизировать код соответствующим образом.

## Что именно происходит на уровне памяти

### 1. Стек (локальный массив)

```cpp
void f() {
    int arr[10];
    arr[10] = 42;   // выход за границу на 1 элемент
}
```

Запись попадает в соседнюю область стекового фрейма: может затереть другую локальную переменную, сохранённый регистр, адрес возврата. Последствия — от «ничего не заметно» до падения или выполнения чужого кода (классический stack smashing). Стек-канарейки (`-fstack-protector`) и ASan могут это поймать, но не обязаны.

### 2. Куча (`new[]`, `malloc`)

```cpp
int* p = new int[10];
p[10] = 42;         // за пределами выделенного блока
```

- Перезаписывается служебная информация аллокатора (заголовок следующего блока, метаданные free-list) либо данные соседнего объекта.
- Часто падение происходит **не в момент записи**, а позже — при `delete[] p`, `free`, следующем `new`/`malloc`: аллокатор обнаруживает повреждённые метаданные (`heap corruption detected`, `double free or corruption`, `malloc(): corrupted top size`).
- Если размер превышает выделенный блок на много байт — возможен выход за отображённую страницу и `SIGSEGV`.

### 3. Глобальные/статические массивы

Выход за границу задевает соседние глобальные переменные или секцию `.bss`/`.data`. Обычно не падает сразу, но данные портятся молча.

## Почему это UB, а не «просто ошибка»

Стандарт C++ ([expr.add], [basic.stc]) определяет, что арифметика указателей и доступ к элементам допустимы только внутри массива (плюс один элемент за концом). Выход за эти границы — UB. Из этого следует, что:

- компилятор может оптимизировать код, «зная», что выхода нет (например, удалить проверки, развернуть циклы, переупорядочить доступы);
- поведение может меняться между версиями компилятора, уровнями оптимизации (`-O0` vs `-O2`), платформами;
- программа, которая «работала годами», может сломаться после безобидного рефакторинга.

## Как это ловить

- **AddressSanitizer** (`-fsanitize=address`) — детектирует переполнения буфера в куче, стеке и глобальных объектах.
- **Valgrind (memcheck)** — для кучи.
- **`_GLIBCXX_ASSERTIONS`**, `-D_GLIBCXX_DEBUG` — проверки для контейнеров STL.
- **`-fstack-protector-strong`** — канарейки на стеке.
- **`std::array`/`std::vector` с `.at()`** — контролируемый доступ с исключением `std::out_of_range`.
- **`-fsanitize=undefined`** (UBSan) — часть случаев арифметики указателей.

## Как правильно

- Использовать контейнеры STL (`std::vector`, `std::array`, `std::string`) и `.at()` там, где важна проверка границ.
- При работе с сырой памятью — явно проверять индекс перед записью.
- Для C-API — `memcpy` с корректным размером, `strncpy`/`snprintf` вместо небезопасных аналогов.
- Не полагаться на «повезло»: любая запись за границу — дефект, который нужно исправлять, даже если сейчас «работает».

## Итог

Запись за пределы выделенного блока — это **undefined behavior**: программа может продолжить работу, испортив данные, упасть сразу или позже, а может быть эксплуатирована злоумышленником. Единственный корректный подход — не допускать выхода за границы и использовать инструменты санитайзеров при тестировании.
