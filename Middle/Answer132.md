# 132. Как избежать состояния гонки?

Состояние гонки (race condition) в C++ — это не просто «возможность получить неверное значение». Согласно стандарту, если несколько потоков обращаются к одной и той же ячейке памяти без синхронизации, и хотя бы один из них выполняет запись, это **неопределённое поведение (UB)** . Компилятор вправе оптимизировать код, исходя из предположения, что гонок не существует, поэтому последствия могут быть самыми неожиданными.

Избежать состояния гонки можно двумя стратегиями: **исключить совместный доступ** или **сделать доступ безопасным**.

### 1. Проектирование без разделяемого изменяемого состояния

Самый надёжный способ — вообще не иметь данных, которые одновременно изменяются несколькими потоками.

- **Независимые данные**: если каждый поток работает со своей локальной копией или своим объектом, гонки не возникает.
- **Передача владения**: вместо совместного использования одного объекта, передавайте его между потоками (например, через очередь сообщений), так чтобы в каждый момент времени с объектом работал только один поток.
- **Иммутабельные данные**: если данные только читаются после инициализации, гонки за данные нет. Для случая «читают многие, пишет один» используйте `std::shared_mutex` (C++17) .

### 2. Взаимное исключение через мьютекс

Если разделяемые изменяемые данные всё же необходимы, критическая секция должна быть защищена мьютексом.

**Основное правило C++**: никогда не вызывайте `lock()` / `unlock()` вручную. Используйте RAII-обёртки, чтобы мьютекс освобождался даже при исключении .

| Обёртка | Когда использовать |
| :--- | :--- |
| `std::lock_guard` | Один мьютекс в пределах области видимости |
| `std::scoped_lock` (C++17) | Несколько мьютексов одновременно (безопасно от deadlock) |
| `std::unique_lock` | Нужно освободить/захватить повторно или передать в `condition_variable` |

**Пример типичной ошибки и исправления**:
```cpp
// Опасно: операция -- не является атомарной на уровне машины
// (чтение -> изменение -> запись), два потока могут перезаписать результат друг друга
int counter = 0;
void bad_increment() { ++counter; }

// Безопасно: мьютекс защищает критическую секцию
std::mutex mtx;
int counter = 0;
void safe_increment() {
    std::lock_guard<std::lock_guard> lock(mtx);
    ++counter;
}
```

**Важное замечание о гранулярности**: защищайте данные, а не код. Мьютекс должен соответствовать группе данных, которые должны изменяться согласованно. Не удерживайте мьютекс во время ввода-вывода или вызова внешнего кода .

### 3. Атомарные операции для простых случаев

Если защищаемая сущность — одна переменная (счётчик, флаг), и инвариант не требует согласованного изменения нескольких переменных, используйте `std::atomic`.

```cpp
#include <atomic>
std::atomic<int> counter{0};
void atomic_increment() {
    counter.fetch_add(1, std::memory_order_relaxed);
}
```

**Ограничения `std::atomic`**:
- Он не заменяет мьютекс, если нужно обновить **две или более** переменных согласованно. Две последовательные атомарные операции не являются одной атомарной транзакцией .
- `volatile` **не является** инструментом синхронизации в C++. Он не даёт ни атомарности, ни нужных гарантий порядка памяти .

### 4. Дисциплина блокировок: предотвращение deadlock

Сам по себе мьютекс может привести к взаимной блокировке, если потоки захватывают несколько мьютексов в разном порядке. Рекомендации:

1.  **Избегайте вложенных блокировок**: не захватывайте второй мьютекс, удерживая первый, если это возможно.
2.  **Фиксированный порядок**: если несколько мьютексов всё же нужны, все потоки должны захватывать их в одном и том же порядке .
3.  **`std::scoped_lock` / `std::lock`**: для одновременного захвата нескольких мьютексов используйте алгоритм, который библиотека применяет для избежания deadlock .

### 5. Ожидание событий: условные переменные вместо активного ожидания

Если поток должен ждать, пока другой поток что-то сделает, не используйте цикл `while (!flag);`. Это активное ожидание (busy-wait), которое сжигает процессорное время и может не увидеть изменение флага из-за оптимизаций/переупорядочивания памяти.

Правильный инструмент — `std::condition_variable`. Он позволяет потоку «спать» до уведомления, атомарно освобождая мьютекс на время сна.

```cpp
std::mutex mtx;
std::condition_variable cv;
bool ready = false;

// Ожидающий поток
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, []{ return ready; }); // predicate защищает от ложных пробуждений
    // ... работа с данными ...
}

// Уведомляющий поток
{
    std::lock_guard<std::mutex> lock(mtx);
    ready = true;
}
cv.notify_one();
```
**Обязательно используйте версию `wait` с предикатом**: условные переменные могут просыпаться «ложно» (spurious wakeup) без уведомления .

### Резюме

| Ситуация | Инструмент |
| :--- | :--- |
| Данные можно не разделять | Локальные копии, передача владения |
| Разделяемая переменная-счётчик/флаг | `std::atomic` |
| Группа данных с инвариантом | `std::mutex` + RAII (`lock_guard`/`scoped_lock`) |
| Ожидание события | `std::condition_variable` + предикат |
| Читают многие, пишет один | `std::shared_mutex` (C++17) |

Главный принцип: **минимизируйте объём разделяемого изменяемого состояния**. Чем меньше данных требует синхронизации, тем меньше вероятность ошибиться.
