# 101. Что такое SOLID? Что означает каждый из этих принципов?

**SOLID** — это аббревиатура пяти базовых принципов объектно-ориентированного проектирования (OOD), сформулированных (в основном) Робертом Мартином («Uncle Bob») и популяризированных Майклом Фэзерсом. Они не являются догмой и не «законами» — это эвристики, помогающие строить гибкий, расширяемый и сопровождаемый код. Нарушение принципов обычно проявляется в виде «хрупкости» кода: изменения в одном месте ломают другое, классы разрастаются, тесты становятся сложными, появляется дублирование.

Ниже — каждый принцип по отдельности.

---

## S — Single Responsibility Principle (SRP), принцип единственной ответственности

**Формулировка (Мартин):** «У класса должна быть только одна причина для изменения».

**Суть:** «ответственность» здесь — это не «метод/функция», а **актор** (заинтересованное лицо/роль), ради которого класс существует. Если у класса несколько причин для изменения (несколько акторов), значит, он смешивает несколько ответственностей.

**Признак нарушения:** класс одновременно содержит бизнес-логику, форматирование вывода, доступ к БД и валидацию.

**Пример нарушения:**
```java
class Report {
    void calculate() { /* бизнес-логика расчёта */ }
    String formatAsPdf() { /* формирование PDF */ }
    void saveToDatabase() { /* работа с БД */ }
}
```
Здесь три причины для изменения: изменились правила расчёта, изменился формат отчёта, изменилась схема БД.

**Как исправить:** разделить на `ReportCalculator`, `ReportFormatter`, `ReportRepository`.

**Выгода:** локализация изменений, меньшая связанность, проще тестировать.

> Важно: SRP — про *акторов*, а не про количество методов. Класс с 20 методами, но одной ответственностью, — нормально; класс с 3 методами, обслуживающими разные роли, — нарушение.

## O — Open/Closed Principle (OCP), принцип открытости/закрытости

**Формулировка:** «Программные сущности (классы, модули, функции) должны быть **открыты для расширения**, но **закрыты для модификации**».

**Суть:** новое поведение должно добавляться через *новый код* (наследование, композиция, реализация интерфейса), а не через правку существующего проверенного кода. Это снижает риск регрессий.

**Признак нарушения:** «лестница» `if/switch` по типу/категории, которую приходится править при каждом новом варианте.

**Пример нарушения:**
```java
double area(Shape s) {
    if (s.type == CIRCLE) return PI * s.r * s.r;
    else if (s.type == SQUARE) return s.a * s.a;
    // добавили треугольник — снова правим этот метод
}
```

**Как исправить:** полиморфизм — абстракция `Shape` с методом `area()`, новые фигуры реализуют её без изменения существующего кода (паттерн «Стратегия», «Фабричный метод» и т.п.).

**Выгода:** расширяемость без риска сломать работающее; плагинная архитектура.

> Оговорка: OCP нельзя соблюсти «абсолютно» — полностью закрытых систем не бывает. Принцип требует предвидеть *наиболее вероятные* оси изменений и защитить их абстракцией.

## L — Liskov Substitution Principle (LSP), принцип подстановки Барбары Лисков

**Формулировка:** «Объекты подтипа должны быть подставляемы вместо объектов базового типа без нарушения корректности программы». Формально — про **контракты**: предусловия, постусловия и инварианты.

**Суть:** наследник не должен *усиливать* предусловия (требовать больше), *ослаблять* постусловия (гарантировать меньше) и нарушать инварианты базового класса. Клиент, написанный против базового типа, должен работать с любым наследником, не зная об этом.

**Классический пример нарушения:** `Square extends Rectangle`. Для `Rectangle` клиент вправе независимо менять `width` и `height`. Для квадрата `setWidth` меняет и высоту — ломается инвариант ожиданий клиента:
```java
Rectangle r = new Square();
r.setWidth(5); r.setHeight(4);
assert r.area() == 20; // падает: 16
```

Другие типичные нарушения: наследник бросает `UnsupportedOperationException` на унаследованный метод (`ImmutableList` vs `List.add`), усиливает проверки аргументов, возвращает `null` там, где базовый тип гарантировал не-`null`.

**Выгода:** полиморфизм работает предсказуемо; клиентский код не обрастает проверками `instanceof`.

> LSP — это про *поведенческий* подтип, а не про синтаксическое наследование. Композиция часто позволяет избежать нарушения (квадрат *содержит* прямоугольник или оба реализуют общий интерфейс `Shape`).

## I — Interface Segregation Principle (ISP), принцип разделения интерфейсов

**Формулировка:** «Клиенты не должны зависеть от интерфейсов, которые они не используют» / «Много специализированных интерфейсов лучше, чем один универсальный».

**Суть:** «толстые» интерфейсы заставляют реализующие классы писать пустые или бросающие исключения методы, а клиентов — зависеть от методов, которые им не нужны (лишняя связанность, хрупкость при изменениях).

**Пример нарушения:**
```java
interface Worker {
    void work();
    void eat();
}
class Robot implements Worker {
    public void work() { ... }
    public void eat() { throw new UnsupportedOperationException(); } // запах
}
```

**Как исправить:** разбить на `Workable` и `Eatable`; каждый класс реализует только нужное.

**Выгода:** слабая связанность, меньше «балласта», проще моки в тестах.

> ISP — это SRP, применённый к интерфейсам. Разделять стоит по *клиентам* (кто и что вызывает), а не механически «по одному методу».

## D — Dependency Inversion Principle (DIP), принцип инверсии зависимостей

**Формулировка (две части):**
1. Модули верхнего уровня не должны зависеть от модулей нижнего уровня — оба должны зависеть от **абстракций**.
2. Абстракции не должны зависеть от деталей — **детали** должны зависеть от абстракций.

**Суть:** направление зависимостей «переворачивается»: бизнес-логика (high-level) не знает о конкретной БД/HTTP/UI (low-level); оба работают через интерфейс, который объявлен «на стороне» высокоуровневого модуля. Внедрение зависимостей (DI) — типичный способ реализации.

**Пример нарушения:**
```java
class OrderService {
    private MySQLOrderRepository repo = new MySQLOrderRepository(); // жёсткая зависимость от детали
}
```

**Как исправить:**
```java
interface OrderRepository { void save(Order o); }

class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; } // зависимость от абстракции
}
// MySQLOrderRepository implements OrderRepository — деталь зависит от абстракции
```

**Выгода:** тестируемость (подставляем fake/mock), смена инфраструктуры без правки логики, независимость слоёв (гексагональная/чистая архитектура).

> Не путать DIP с DI: DIP — *принцип проектирования* (кто от кого зависит), DI — *техника* передачи зависимостей извне. DI можно применять и без DIP (внедрять конкретный класс), но тогда выгода меньше.

## Сводная таблица

| Принцип | Кратко | Главный симптом нарушения |
|---|---|---|
| **S**RP | Одна причина для изменения (один актор) | «Божественный класс», смешение слоёв |
| **O**CP | Открыт для расширения, закрыт для модификации | Каскад `if/switch` по типам |
| **L**SP | Наследник подставляем за базовый тип | `UnsupportedOperationException`, усиление предусловий |
| **I**SP | Много узких интерфейсов вместо одного широкого | Пустые/бросающие реализации |
| **D**IP | Зависимость от абстракций, а не от деталей | `new` конкретных инфраструктурных классов внутри логики |

## Практические замечания

- Принципы **взаимосвязаны**: SRP и ISP уменьшают связанность; OCP и DIP опираются на абстракции; LSP гарантирует, что полиморфизм (основа OCP) не сломается.
- Это **эвристики, а не самоцель**: слепое следование порождает «астронавтную архитектуру» (лишние интерфейсы и фабрики). Применять там, где ожидаются изменения, и соизмерять с реальной сложностью.
- Хорошо сочетаются с **DRY, KISS, YAGNI** и паттернами GoF; на практике проверяются через тестируемость (если класс трудно тестировать — часто нарушен DIP/SRP) и через частоту правок (если при каждом новом варианте правится старый код — нарушен OCP).
