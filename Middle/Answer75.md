# 75. Расскажите о логике catch-блоков.

`catch`-блок — это обработчик исключения. Его «логика» складывается из трёх вещей: **как выбирается обработчик**, **что происходит с объектом исключения** и **что происходит после выхода из обработчика**. Ключевой момент, который любят спрашивать: обработчики просматриваются **сверху вниз**, срабатывает **первый подходящий**, и выбор делается по **типу объекта исключения**, а не по типу выражения в `throw` и не по динамическому типу указателя.

## 1. Пошаговая модель работы

1. Выполняется `throw expr` — создаётся **объект исключения**: копия (или перемещение) операнда, размещённая в специальной области, контролируемой runtime. Тип объекта исключения — статический тип операнда после array-to-pointer/function-to-pointer преобразований и снятия top-level cv-квалификаторов.
2. Начинается **раскрутка стека** (stack unwinding): вызываются деструкторы автоматических объектов, пока не будет найден объемлющий `try`.
3. Для найденного `try` его `catch`-блоки проверяются **по порядку объявления**. Первый, который подходит по типу, выбирается; остальные игнорируются.
4. Параметр обработчика инициализируется из объекта исключения — как обычный параметр функции из аргумента.
5. Выполняется тело `catch`.
6. Выход из обработчика:
   - нормальный выход (`return`, `break`, `goto`, конец блока) — исключение считается **обработанным**, управление продолжается после последнего `catch` этого `try`;
   - `throw;` — исходное исключение **перевыбрасывается** и поиск обработчика продолжается снаружи;
   - `throw новое_выражение` — наружу уходит **новое** исключение.

Важно: к моменту входа в обработчик объекты, объявленные внутри `try`, уже уничтожены — обработчик выполняется в кадре своего `try`, а не в кадре места `throw`.

## 2. Правила сопоставления типов

Обработчик `catch (cv T)` или `catch (cv T&)` подходит для объекта исключения типа `E`, если выполнено одно из условий:

| Ситуация | Подходит? | Пример |
|---|---|---|
| `T` и `E` — один и тот же тип (с точностью до top-level cv у `E`) | да | `throw MyErr{}` → `catch (const MyErr&)` |
| `T` — однозначный **публичный базовый** класс `E` | да | `throw Derived{}` → `catch (const Base&)` |
| `T` — указатель, и `E` конвертируется в `T` стандартным преобразованием указателей (включая `Derived*`→`Base*`, `T*`→`const T*`, `T*`→`void*`) | да | `throw dptr` → `catch (Base*)`, `catch (void*)` |
| `E` — `std::nullptr_t`, `T` — указатель | да | `throw nullptr` → `catch (int*)` |
| Арифметические преобразования (`int`→`double`, `int`→`long`) | **нет** | `throw 42` **не** ловится `catch (double)` |
| Пользовательские преобразования (конструкторы, `operator T`) | **нет** | — |
| Понижающее преобразование `Base*`→`Derived*`, `Base`→`Derived` | **нет** | — |
| Непубличный или неоднозначный базовый класс | **нет** | приватное/виртуальное множественное наследование с неоднозначностью |

Следствия, которые стоит проговорить:

- **Динамический тип указателя не учитывается.** Если `Base* p = new Derived; throw p;`, тип объекта исключения — `Base*`, поэтому `catch (Derived*)` его **не** поймает, а `catch (Base*)` — поймает.
- Строковый литерал: `throw "error";` бросает `const char*` (массив распадается в указатель), поэтому `catch (char*)` не подойдёт, а `catch (const char*)` — да.
- `catch (const void*)` поймает `const char*`, но `catch (void*)` — уже нет (нельзя отбросить `const`).
- Обработчик может быть ссылкой на **абстрактный** класс (ссылка не требует копирования), а вот `catch (AbstractBase)` по значению просто не скомпилируется.

## 3. Порядок обработчиков — главная практическая логика

Поскольку выбирается первый подходящий блок, порядок критичен: **от частного к общему**. Классическая ошибка — поставить базовый класс раньше производного:

```cpp
try {
    throw std::runtime_error("bad");
}
catch (const std::exception& e) { /* сработает ЭТО */ }
catch (const std::runtime_error& e) { /* мёртвый код, никогда не выполнится */ }
```

Правильно:

```cpp
try {
    throw std::runtime_error("bad");
}
catch (const std::runtime_error& e) { /* самое конкретное — первым */ }
catch (const std::exception& e)      { /* общий случай */ }
catch (...)                          { /* всё остальное — последним */ }
```

Три правила:

1. Производные — до базовых.
2. Конкретные стандартные исключения — до `std::exception`.
3. `catch (...)` — всегда последним.

Недостижимый обработчик — это **не ошибка компиляции** (в отличие от недостижимого кода после `return`), но компиляторы могут предупреждать (`-Wunreachable-code` у Clang, аналоги у GCC), а по смыслу это баг.

Ещё нюанс: в C++ **нет** «разрешения перегрузки» для обработчиков и нет «наилучшего совпадения» — только первый подходящий по списку. Поэтому же нельзя написать два одинаковых `catch` подряд «для разных случаев» — второй недостижим.

## 4. Параметр обработчика: по значению, по ссылке, по указателю

Параметр инициализируется из объекта исключения по правилам инициализации параметра функции.

**По значению** — создаётся копия:

```cpp
catch (Base b) { ... }   // срезка (slicing), если брошен Derived
```

При срезке теряется не только «хвост» объекта, но и динамический тип: скопированный подобъект `Base` получает vptr `Base`, поэтому виртуальный `what()` вернёт уже базовую реализацию. Копия также может быть дорогой.

**По ссылке** — предпочтительный вариант:

```cpp
catch (const std::exception& e)   // без копирования, без срезки
catch (MyError& e)                // можно изменить объект исключения
```

Ссылка связывается **непосредственно с объектом исключения**, поэтому изменения, сделанные через неконстантную ссылку, увидит внешний обработчик после `throw;`. Это стандартом разрешено специально (в отличие от обычных функций, где неконстантную lvalue-ссылку на временный объект не создать). `const&` — выбор по умолчанию, если менять ничего не нужно.

**По указателю** — редко и опасно:

```cpp
catch (MyError* e) { ... }   // объект исключения — копия указателя
```

Нужно проверять на `nullptr` (можно бросить `(MyError*)nullptr`), неясен владелец объекта, легко получить утечку или двойное удаление. Обычно это признак плохого дизайна; бросать надо по значению, ловить — по ссылке.

Имя параметра можно опустить, если объект не нужен: `catch (const std::exception&)`. Это не «поймать и забыть», а способ избежать предупреждения о неиспользуемой переменной.

## 5. `catch (...)`

Ловит **всё**: стандартные исключения, пользовательские типы, `int`, `const char*`, словом, любой объект исключения. Это «последняя линия обороны»:

```cpp
try {
    risky();
}
catch (...) {
    log("unknown failure");
    throw;              // не глотаем, а пробрасываем дальше
}
```

Особенности:

- у `catch (...)` нет имени — доступа к объекту нет; чтобы его получить, используют `std::current_exception()` внутри обработчика;
- `catch (...)` не ловит ошибки, не являющиеся C++-исключениями (например, структурные исключения Windows при `/EHsc`; при `/EHa` MSVC ловит и их — это платформозависимо);
- «проглотить» `catch (...)` без повторного `throw` — почти всегда ошибка: программа продолжает работу в неизвестном состоянии.

## 6. Повторный `throw` (rethrow)

`throw;` без операнда перевыбрасывает **тот же самый объект исключения**, не создавая новый:

- сохраняется динамический тип (важно: `catch (const std::exception&)` + `throw;` донесёт до внешнего обработчика исходный `runtime_error`);
- сохраняются изменения, сделанные через неконстантную ссылку;
- работает и внутри `catch (...)`.

Правила:

- `throw;` допустим только пока исключение «обрабатывается» — в теле `catch` или в функции, вызванной из него. Вне обработки исключения `throw;` вызывает `std::terminate()`.
- Исключение, брошенное **внутри** обработчика, не ловится соседними `catch` того же `try` — оно уходит наружу (нужен вложенный `try`, если хочется поймать локально).

Типовые сценарии:

```cpp
// 1. Логирование с пробросом
catch (const std::exception& e) {
    log(e.what());
    throw;
}

// 2. Добавление контекста (обёртка)
catch (...) {
    std::throw_with_nested(std::runtime_error("parse failed"));
}

// 3. Транспорт между потоками/отложенная обработка
std::exception_ptr ep;
try { work(); }
catch (...) { ep = std::current_exception(); }
// позже, в другом месте:
if (ep) std::rethrow_exception(ep);
```

`std::throw_with_nested` / `std::rethrow_if_nested` позволяют строить цепочки «причина → следствие», не теряя исходное исключение.

## 7. Время жизни и взаимодействие с раскруткой

- Объект исключения создаётся в точке `throw` и живёт до выхода из **последнего** обработчика, который его поймал (или до уничтожения `exception_ptr`).
- Локальные объекты `try` уничтожаются **до** входа в `catch`; порядок — обратный порядку создания.
- Если деструктор, вызванный при раскрутке, сам бросит исключение — вызывается `std::terminate()`. Начиная с C++11 деструкторы неявно `noexcept`, так что это в основном про явно помеченные `noexcept(false)`.
- Если исключение не поймано нигде — `std::terminate()` (по умолчанию печатается сообщение вида `terminate called after throwing an instance of ...`). Обработчик можно заменить через `std::set_terminate`.

## 8. Function-try-block

`catch` можно навесить на всё тело функции, включая список инициализации конструктора:

```cpp
Widget::Widget(int x) try : base_(x), res_(acquire()) {
    // ...
} catch (const std::exception& e) {
    log("Widget ctor failed: ", e.what());
    throw;   // для конструктора — фактически обязательно
}
```

Специфика:

- для **конструктора и деструктора** при выходе из обработчика исключение перевыбрасывается **неявно**; «проглотить» его нельзя, `return` из такого обработчика запрещён. Причина: объект не построен (или уже разрушен), и продолжать с ним нельзя;
- в обработчике конструктора **нельзя обращаться к членам и базе** — они уже разрушены; можно логировать, освобождать «сырые» ресурсы, захваченные в списке инициализации;
- для обычных функций (включая `main`) function-try-block ведёт себя как обычный `try` вокруг тела: обработчик может вернуть значение, и тогда исключение считается обработанным.

## 9. Взаимодействие с `noexcept` и `terminate`

- Если исключение выходит за пределы функции, помеченной `noexcept` (а также деструктора по умолчанию, точки входа потока, `main` до/после?), вызывается `std::terminate()`. Обработчики внутри такой функции всё равно работают — важно лишь, чтобы наружу ничего не улетело.
- Динамические спецификации исключений (`throw(A, B)`) удалены в C++17; для «эта функция не бросает» есть только `noexcept`.
- Исключение, покидающее функцию потока (`std::thread`), — немедленный `terminate`: в точке входа потока нужен свой `try/catch`.

## 10. Практические правила и антипаттерны

**Делать:**

- ловить по `const&` (без копии и срезки), по значению — только для мелких типов, которые вы намеренно копируете;
- располагать обработчики от частного к общему, `catch (...)` — последним;
- в `catch (...)` всегда делать `throw;` после логирования;
- обрабатывать исключения на границах: `main`, точка входа потока, колбэки из C-кода, обработчики событий, деструкторы — не давать исключению выйти наружу;
- для гарантированного освобождения ресурсов использовать RAII, а не `finally` (в C++ его нет);
- логировать `e.what()` и, при необходимости, вложенные исключения через `std::rethrow_if_nested`.

**Не делать:**

- `catch (std::exception e)` по значению — срезка и потеря динамического типа;
- `catch (const std::exception&)` раньше `catch (const std::runtime_error&)` — недостижимый код;
- пустой `catch (...) {}` — молчаливое проглатывание ошибок;
- ловить по указателю без чёткой модели владения;
- бросать из деструктора (риск `terminate` при раскрутке);
- использовать исключения как обычный поток управления — раскрутка стека дорога;
- полагаться на `catch (Base)` для полиморфных иерархий — только ссылка/указатель сохраняют динамический тип.

## Краткий итог

Логика `catch`-блоков сводится к следующему: обработчики привязаны к `try` и проверяются **по порядку**; подходящим считается первый, чей тип совпадает с типом объекта исключения по правилам «точное совпадение / публичный базовый класс / стандартные преобразования указателей»; срабатывает **ровно один** обработчик; параметр инициализируется из объекта исключения (лучше всего — `const&`); после нормального выхода исключение считается обработанным, а `throw;` передаёт **тот же** объект дальше по стеку. Отсюда и главные практические требования: правильный порядок «от частного к общему», `catch (...)` в конце, ловля по ссылке и осмысленная обработка вместо проглатывания.
