# Вопрос 72. Как компилятор различает члены класса и обычные переменные в функциях?

> **Кратко:** никакого «различения» в рантайме нет — это чисто семантическая задача этапа компиляции. Компилятор строит цепочку областей видимости (блок → параметры → класс → базовые классы → пространство имён → глобальная область) и ищет имя по ней; первое найденное объявление выигрывает. Если имя нашлось в классе, узел AST помечается как обращение к члену и кодогенерируется через `this` (смещение от объекта) или как статический символ; если в блоке — как локальная переменная.

---

## Что на самом деле означает вопрос

Синтаксически `x` — это просто *id-expression*. В нём нет пометки «это член» или «это локальная переменная». Различие появляется только в момент **разрешения имён** (name lookup) и **семантического анализа**, когда компилятор знает все объявления в области видимости.

```
x            // что это? — зависит от того, где компилятор найдёт объявление
```

Поэтому вопрос корректнее переформулировать так: *по каким правилам компилятор решает, на какое объявление ссылается имя внутри функции-члена?*

---

## Цепочка областей видимости

Для тела функции-члена компилятор просматривает области **изнутри наружу**:

1. текущий блок `{ ... }` (включая вложенные);
2. параметры функции;
3. область видимости класса (и его базовых классов);
4. объемлющее пространство имён;
5. глобальная область.

```cpp
int x = 100;                       // глобальная

struct S {
    int x = 1;                     // член

    void f(int x) {                // параметр
        int y = x;                 // параметр x
        x = 2;                     // параметр x
        this->x = 3;               // член S::x
        ::x = 4;                   // глобальная
        std::cout << y;            // 1 (значение параметра до присваивания)
    }
};
```

Важно: локальные имена **перекрывают** (hide) члены, а члены — глобальные имена. Компилятор не «предпочитает члены»: он просто идёт по цепочке и останавливается на первом совпадении.

```cpp
int value = 10;

struct Config {
    int value = 20;                // член перекрывает глобальную

    void print() {
        std::cout << value;        // 20, а не 10
        std::cout << ::value;      // 10
    }
};
```

## Локальная переменная перекрывает член

Классическая ловушка — инициализация «сама собой»:

```cpp
struct S {
    int x = 42;

    void f() {
        int x = x;      // правая часть — только что объявленная локальная x,
                        // а не член; значение неопределённое (UB при чтении)
        this->x = x;    // уже осознанно
    }
};
```

Точка объявления (point of declaration) локальной переменной — сразу после её имени, поэтому в инициализаторе имя уже ссылается на саму переменную. Компиляторы предупреждают об этом (`-Wshadow`, `-Wuninitialized`), но это именно предупреждение, а не ошибка.

Такое же перекрытие даёт параметр:

```cpp
struct Widget {
    int width = 0;
    void resize(int width) {       // параметр перекрывает член
        width = width;             // присваивание параметру самому себе — бессмысленно
        this->width = width;       // правильно
    }
};
```

## Как указать адресат явно

| Запись | Что означает |
|---|---|
| `x` | поиск по цепочке: блок → параметры → класс → пространство имён |
| `this->x` | только член текущего объекта (не работает в `static`-методе) |
| `S::x` | член именно `S` (обходит перекрытие локальными именами) |
| `::x` | имя из глобальной области |
| `using Base::x;` | ввести член базового класса в область производного |

```cpp
struct S {
    int x = 1;
    void f() {
        int x = 2;
        S::x = 3;                  // явно член, хотя локальная x перекрывает имя
    }
};
```

## Где поиск начинается сразу с класса

Есть контексты, в которых компилятор ищет имя **сначала в области класса**, а не в блоке:

**Определение метода вне класса:**

```cpp
struct S {
    int x = 0;
    void f();
};

void S::f() {          // тело находится в области видимости S
    x = 1;             // это S::x, this->x подставляется неявно
}
```

**Список инициализации конструктора** — здесь важное разделение:

```cpp
struct S {
    int x;
    S(int x) : x(x) {}   // слева от скобок имя ищется в классе → член,
                         // справа — в области конструктора → параметр
};
```

Именно поэтому идиома `x(x)` работает: `mem-initializer-id` резолвится в член, а выражение — в параметр.

**Инициализаторы по умолчанию и default-аргументы** — это *complete-class context*: в них видны члены, объявленные **позже**:

```cpp
struct S {
    int a = 1;
    int b = a + 1;     // a виден, хотя объявлен раньше; здесь всё в порядке
};
```

А вот в теле метода порядок объявления членов не важен вообще — тело функции-члена тоже относится к complete-class context, поэтому метод может использовать поля, объявленные ниже:

```cpp
struct S {
    void f() { y = 1; }   // y объявлен ниже — это допустимо
    int y = 0;
};
```

Для локальных переменных такого нет: имя должно быть объявлено **до** использования.

## Что видит компилятор: символы и кодогенерация

При разборе компилятор ведёт таблицу символов со «слоями». Найдя имя, он получает не просто «переменную», а вид сущности, и дальше строит разные узлы AST:

| Что найдено | Узел AST | Как генерируется код |
|---|---|---|
| локальная переменная / параметр | `DeclRefExpr` | слот в стеке кадра или регистр |
| нестатический член данных | `MemberExpr` (неявно `this->x`) | загрузка по адресу `this + offset` |
| статический член данных | `DeclRefExpr` на `S::x` | глобальный символ с искажённым именем |
| нестатический метод | `CXXMemberCallExpr` | вызов с неявным `this` (ABI: первый скрытый параметр) |
| статический метод | обычный вызов | как свободная функция, без `this` |

```cpp
struct S {
    int a;                 // offset 0
    double b;              // offset 8 (с учётом выравнивания)
    static int counter;    // отдельный глобальный объект, не в объекте S

    void f() {
        a = 1;             // mov [this+0], 1
        b = 2.0;           // movsd [this+8], ...
        counter++;         // inc [S::counter]
    }
};
```

Смещения членов вычисляются на этапе компоновки класса (layout): компилятор знает размеры и выравнивания полей. Для виртуальных базовых классов смещение может быть динамическим — тогда адрес берётся через таблицу виртуальных баз (vbtable), а не как константа.

Именно поэтому вопрос «как компилятор различает» — про **семантику**, а не про машинный код: в готовом бинарнике уже нет имён, есть только `this + offset` или адрес символа.

## Наследование: поиск идёт и по базовым классам

В методе производного класса имя ищется сначала в производном классе, затем в базовых:

```cpp
struct Base { int x = 1; };
struct Derived : Base {
    void f() { x = 2; }    // найдено в Base → this->Base::x
};
```

Проблемы начинаются при множественном наследовании:

```cpp
struct A { int x = 1; };
struct B { int x = 2; };
struct C : A, B {
    void f() {
        // x = 3;          // ошибка: ambiguous, x есть и в A, и в B
        A::x = 3;          // нужно уточнение
        B::x = 4;
    }
};
```

`using`-объявление может внести член базового класса в производный и снять неоднозначность:

```cpp
struct C : A, B {
    using A::x;            // теперь неквалифицированное x означает A::x
};
```

Отдельный случай — **зависимые базовые классы в шаблонах**. Там работает двухфазный поиск: на первой фазе (при определении шаблона) базовый класс ещё неизвестен, поэтому его члены не находятся.

```cpp
template <class T>
struct D : T {
    void f() {
        // x = 0;         // ошибка: x не найден на первой фазе
        this->x = 0;      // правильно: откладывается до инстанциации
        T::x = 0;         // тоже правильно
    }
};
```

## Статические члены

Статический член принадлежит классу, а не объекту, поэтому `this` для него не нужен:

```cpp
struct S {
    static int counter;
    static void reset() { counter = 0; }   // this отсутствует

    void f() {
        counter++;        // допустимо: статический член
        S::counter++;     // эквивалентно
        // this->counter; // тоже скомпилируется: this просто не используется
    }
};
```

Компилятор отличает статический член от нестатического по объявлению в классе (`static` — часть типа сущности), и в кодогенерации это отражается: объект `S` не содержит поля `counter`, память под него выделяется отдельно.

## Доступ проверяется после поиска имени

Важный порядок: сначала имя **находится**, потом проверяется **доступ**. Поэтому сообщение об ошибке бывает «is private», а не «not found»:

```cpp
class S {
    int secret = 0;
public:
    void f() { secret = 1; }   // ok: внутри класса доступ есть
};

int main() {
    S s;
    // s.secret = 1;           // error: 'secret' is private
}
```

То же и с локальными: если локальная переменная перекрыла член, обращение к «private-члену» через `this->` всё равно проверяется на доступ.

---

## Типичные ошибки

1. **Думать, что компилятор «знает по имени», что это член.** Он узнаёт это только из результата поиска в области класса.
2. **Забывать про перекрытие локальными именами** и получать `int x = x;` вместо `this->x = x;`.
3. **Использовать `this->` в статическом методе** — там нет `this`, будет ошибка компиляции.
4. **Путать `mem-initializer-id` и выражение в списке инициализации** — слева имя ищется в классе, справа — в области конструктора.
5. **Ожидать, что член будет найден в зависимом базовом классе шаблона** без `this->` или `T::`.
6. **Считать, что порядок объявления членов влияет на тело метода** — в теле видны все члены класса, но порядок инициализации всё равно определяется порядком объявления.
7. **Игнорировать неоднозначность при множественном наследовании** — компилятор не выбирает «правильный» `x`, а выдаёт ошибку.

---

## Что добавить на собеседовании

- Различение членов и локальных переменных — это **name lookup**, а не свойство объектов; в рантайме никакой информации о «членстве» нет.
- Полезно знать точный порядок: блок → параметры → класс → базы → namespace → global, и что первое совпадение выигрывает.
- Понимать, что `x` в методе — это синтаксический сахар для `this->x`, а `this` — скрытый параметр метода; отсюда и разница в кодогенерации.
- Уметь объяснить `x(x)` в списке инициализации и ловушку `int x = x;`.
- Знать про complete-class context: тела методов, default-аргументы, DMI и `noexcept` видят члены, объявленные позже.
