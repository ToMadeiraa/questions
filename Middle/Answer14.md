# 14. Какая разница между исполнительным файлом и динамической библиотекой?

## Краткий ответ

**Исполняемый файл** — это программа, которую можно запустить напрямую: у неё есть точка входа (`main`), и ОС загружает её как отдельный процесс. **Динамическая библиотека** (`.dll` в Windows, `.so` в Linux, `.dylib` в macOS) — это набор скомпилированного кода и данных, который сам по себе не запускается, а подгружается в адресное пространство уже работающего процесса (при старте программы или по явному запросу через `dlopen`/`LoadLibrary`).

## Подробное сравнение

### 1. Наличие точки входа

| | Исполняемый файл | Динамическая библиотека |
|---|---|---|
| Точка входа | Обязательна (`main`/`WinMain`) | Обычно отсутствует (есть лишь `DllMain`/конструкторы, но не «главная» функция) |
| Запуск | `./program`, двойной клик | Не запускается напрямую; загружается другой программой |

```cpp
// executable.cpp — компилируется в программу
int main() {
    // ...
    return 0;
}
```

```cpp
// library.cpp — компилируется в .so/.dll
extern "C" __attribute__((visibility("default")))
int add(int a, int b) { return a + b; }
// main здесь нет
```

### 2. Способ компоновки и загрузки

- **Исполняемый файл** содержит (или подтягивает при старте) весь необходимый код. Бывает статически слинкованным (весь код внутри) или динамически слинкованным (зависит от `.so`/`.dll`, которые загружает загрузчик ОС).
- **Динамическая библиотека** — это отдельный модуль, который:
  - при **неявной линковке** (implicit linking) загружается автоматически при старте программы, если она указана в зависимостях;
  - при **явной загрузке** (explicit linking) подгружается в рантайме через `dlopen()`/`dlsym()` (POSIX) или `LoadLibrary()`/`GetProcAddress()` (Windows).

```cpp
// Явная загрузка .so в Linux
#include <dlfcn.h>
#include <iostream>

int main() {
    void* handle = dlopen("./libmath.so", RTLD_LAZY);
    if (!handle) { std::cerr << dlerror() << "\n"; return 1; }

    using AddFn = int(*)(int, int);
    auto add = reinterpret_cast<AddFn>(dlsym(handle, "add"));
    if (!add) { std::cerr << dlerror() << "\n"; dlclose(handle); return 1; }

    std::cout << add(2, 3) << "\n"; // 5
    dlclose(handle);
}
```

### 3. Экспорт символов

- В исполняемом файле символы обычно не предназначены для внешнего использования (хотя экспорт возможен, например `-rdynamic` в GCC).
- В динамической библиотеке явно помечаются экспортируемые функции/переменные:
  - GCC/Clang: `__attribute__((visibility("default")))`, версионные скрипты;
  - MSVC: `__declspec(dllexport)` / `__declspec(dllimport)`.

```cpp
// Переносимая схема экспорта/импорта
#ifdef _WIN32
  #ifdef BUILDING_MYLIB
    #define MYLIB_API __declspec(dllexport)
  #else
    #define MYLIB_API __declspec(dllimport)
  #endif
#else
  #define MYLIB_API __attribute__((visibility("default")))
#endif

extern "C" MYLIB_API int add(int, int);
```

### 4. Адресное пространство и разделение кода

- Каждый **исполняемый файл** при запуске получает собственное адресное пространство (процесс).
- **Динамическая библиотека** одна и та же физическая копия кода в памяти может использоваться несколькими процессами (разделяемые страницы, copy-on-write для данных). Это экономит память и ускоряет загрузку.

### 5. Формат файла

Оба формата — по сути один и тот же контейнер (ELF в Linux, PE/COFF в Windows, Mach-O в macOS). Различие — в флагах и структуре:

- у исполняемого файла указан **entry point** и есть таблица сегментов для запуска процесса;
- у `.so`/`.dll` ключевую роль играют таблицы экспорта/импорта, релокаций, PLT/GOT, но нет «запускаемого» entry point.

### 6. Зависимости и версионирование

- Исполняемый файл фиксирует список нужных библиотек (например, `NEEDED libfoo.so.1` в ELF).
- Динамическая библиотека может сама зависеть от других библиотек; поддерживает **SONAME** и версионирование символов (`libfoo.so.1.2.3`), что позволяет обновлять её без пересборки программы (при совместимом ABI).

### 7. Практические следствия для C++

- **ABI-совместимость** критична для динамических библиотек: разные компиляторы/стандартные библиотеки/флаги (`-D_GLIBCXX_USE_CXX11_ABI`) могут сделать `.so` несовместимой с программой.
- Для стабильного интерфейса библиотеки часто используют `extern "C"` и «плоские» типы (без STL в сигнатурах), либо стабильный C++ ABI (например, COM-подобные интерфейсы с виртуальными деструкторами).
- **RTTI и исключения** через границу `.so` работают не всегда одинаково на разных платформах — это ещё одна причина прятать C++-детали за C-интерфейсом.
- **Статическая библиотека** (`.a`/`.lib`) — третий вариант: это просто архив объектных файлов, который целиком вкомпоновывается в исполняемый файл; в рантайме отдельного модуля нет.

## Итоговая таблица

| Критерий | Исполняемый файл | Динамическая библиотека |
|---|---|---|
| Точка входа | Есть (`main`) | Нет |
| Можно запустить напрямую | Да | Нет |
| Загружается | ОС как процесс | Программой/загрузчиком в процесс |
| Экспорт символов | Обычно нет | Да, явный |
| Разделение между процессами | Нет | Да (общий код в памяти) |
| Типичные расширения | `.exe`, (нет) в Unix | `.dll`, `.so`, `.dylib` |
| Обновление без пересборки клиента | — | Да (при совместимом ABI) |
