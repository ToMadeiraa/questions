# 122. Является ли С++ thread-safe?

Короткий ответ: **Сам язык C++ не является «thread-safe» в смысле автоматической защиты от гонок данных, но он предоставляет строгую модель памяти и набор примитивов, позволяющих писать потокобезопасный код.** Потокобезопасность в C++ — это не свойство языка «из коробки», а **контракт**, который программист обязан соблюдать.

Ниже — подробный разбор в контексте многопоточности C++.

## 1. Что вообще означает «Thread-Safe» в C++

В терминах стандарта C++ (начиная с C++11) «потокобезопасная программа» — это программа, которая **не выполняет конфликтующих неатомарных операций над одной и той же областью памяти и, следовательно, не содержит гонок данных (data races)**.

Ключевой момент: стандарт гарантирует отсутствие гонок данных **только при корректном использовании** библиотеки и языковых средств. Если программист разделяет изменяемый объект между потоками без синхронизации, это **неопределённое поведение (UB)**, и язык не обязан ничего защищать.

## 2. Базовые гарантии стандартной библиотеки

Стандартная библиотека C++ следует модели, которую можно назвать **«базовая потокобезопасность»** (basic thread safety):

| Сценарий | Гарантия |
|---|---|
| Чтение одного объекта из нескольких потоков одновременно | **Безопасно** |
| Запись в объект из одного потока + чтение/запись из других потоков | **Требуется внешняя синхронизация** (мьютекс и т.п.) |
| Разные объекты одного типа в разных потоках | **Безопасно** (независимые экземпляры не мешают друг другу) |

Это правило применяется ко всем классам стандартной библиотеки, включая контейнеры (`std::vector`, `std::map` и т.д.), `std::string` и `std::shared_ptr`.

**Важное уточнение:** стандарт **не даёт «сильной» гарантии** (strong thread safety), при которой каждый вызов метода автоматически блокируется. Это сделано осознанно: блокировка на каждый вызов метода убила бы производительность и создала бы **иллюзию безопасности**, поскольку реальная атомарность часто требуется на уровне нескольких вызовов, а не одного.

## 3. Исключения и особые случаи

### `std::atomic` и мьютексы
Типы из `<atomic>` и операции lock/unlock над мьютексами из `<mutex>` — это **единственные** компоненты, которые по умолчанию позволяют конкурентный доступ к одному и тому же объекту без гонки данных. Они являются строительными блоками для написания потокобезопасного кода.

### `std::shared_ptr`
Разные экземпляры `std::shared_ptr` можно безопасно читать и изменять из разных потоков, даже если они разделяют владение одним и тем же объектом. Однако **один и тот же экземпляр** `shared_ptr` нельзя изменять из разных потоков без синхронизации.

### Потоки ввода-вывода (`iostream`)
Стандартные объекты `std::cout`, `std::cin`, `std::cerr` и т.д. допускают **параллельную запись из разных потоков** без явной синхронизации (хотя вывод может перемешиваться). Это исключение из общего правила. Чтение из потокового буфера при этом рассматривается как операция записи, поскольку меняет состояние класса.

## 4. Языковые средства, а не автоматическая защита

C++ даёт программисту инструменты для **самостоятельного** обеспечения потокобезопасности:
- **Модель памяти** (memory model), определяющая отношения «happens-before» и порядок операций.
- **Атомарные операции** (`std::atomic`).
- **Мьютексы и условные переменные** (`std::mutex`, `std::condition_variable`).
- **Потоколокальное хранилище** (`thread_local`).

Но ни один из этих инструментов не включается автоматически. Если вы разделяете `std::vector` между потоками и один поток вызывает `push_back`, а другой — `size()`, **это гонка данных и UB**, если вы не защитили доступ мьютексом.

## 5. Итог

**C++ не является thread-safe в том смысле, что язык не предотвращает гонки данных автоматически.** Он является **«thread-aware»**: предоставляет формальную модель памяти, атомарные типы и синхронизационные примитивы, а также определяет контракт для стандартной библиотеки. Потокобезопасность конкретной программы на C++ — это **ответственность программиста**, который должен корректно использовать эти средства и не разделять изменяемые данные без синхронизации.
