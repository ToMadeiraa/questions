# 42. При каких условиях в конструкторе можно выбросить exception?

В C++ выбрасывать исключение из конструктора **можно и нужно** для сигнализации о том, что объект не может быть корректно создан. Это стандартный и рекомендуемый способ сообщения об ошибках, поскольку конструктор не возвращает значение, и альтернатив (например, возврата кода ошибки) нет .

Однако существуют важные условия и ограничения, связанные с тем, **когда** это допустимо и **как** это работает.

### 1. Общие условия допустимости

Выброс исключения из конструктора разрешён в следующих случаях:

*   **Нарушение постусловий или инвариантов:** Конструктор не смог выделить ресурс, открыть файл, установить соединение или создать объект, удовлетворяющий инвариантам класса .
*   **Сбой предусловий:** Конструктор зависит от внешних данных, которые оказались некорректными (например, неверные аргументы, хотя для аргументов чаще используют `assert`, если это ошибка программиста, а не среды выполнения) .
*   **Исключение из вызываемых функций:** Конструктор вызывает другие функции (например, конструкторы полей или базовых классов), которые могут выбросить исключение. Оно автоматически распространится наружу.

### 2. Что происходит при выбросе исключения (механика)

Если конструктор выбрасывает исключение, объект считается **недостроенным**. Это влечёт важные последствия:

*   **Деструктор не вызывается:** Для самого объекта, чей конструктор выбросил исключение, деструктор **не будет вызван**, поскольку объект так и не стал полноценным .
*   **Разрушение полей и баз:** Все **полностью сконструированные** к этому моменту подобъекты (базовые классы и нестатические поля) будут корректно уничтожены в порядке, обратном их созданию, в процессе раскрутки стека . Это означает, что если вы используете RAII для управления ресурсами в полях, утечек не будет.
*   **Освобождение памяти:** Если объект создавался через `new`, и конструктор выбросил исключение, будет вызвана соответствующая функция освобождения памяти (`operator delete`), чтобы избежать утечки самой памяти под объект .

### 3. Критическое ограничение: Глобальные и статические объекты

Это главное ограничение, о котором нужно помнить. Выбрасывать исключение из конструктора **формально можно**, но если объект имеет **статическую продолжительность хранения** (глобальные переменные, статические поля классов), то исключение **не будет перехвачено** стандартным `try/catch` вокруг `main` или в теле функции.

Согласно стандарту, исключения, выброшенные из конструкторов объектов со статической или потоковой продолжительностью хранения, приводят к вызову `std::terminate` . Это означает аварийное завершение программы.

**Пример проблемы:**
```cpp
struct Global {
    Global() { throw std::runtime_error("Fail"); }
};

Global g_obj; // Исключение вылетит здесь, до main()

int main() {
    try {
        // ...
    } catch (...) {
        // Этот блок НЕ поймает исключение от g_obj
    }
}
```
**Решение:** Избегайте сложной инициализации глобальных объектов. Используйте ленивую инициализацию (функция, возвращающая ссылку на статический локальный объект), чтобы иметь возможность перехватить исключение .

### 4. Спецификация `noexcept`

Если конструктор объявлен как `noexcept` (или является таковым по умолчанию, например, для большинства implicitly-declared конструкторов), но внутри него выбрасывается исключение, программа также вызовет `std::terminate` . Поэтому, если конструктор потенциально может выбросить исключение (например, из-за выделения памяти), он **не должен** быть помечен как `noexcept`.

### Резюме

Выбрасывать исключение в конструкторе **можно и нужно**, чтобы предотвратить создание невалидного объекта. Это безопасно с точки зрения утечек (подобъекты и память очищаются). **Нельзя** позволять исключению вылетать из конструктора глобального/статического объекта (это приведёт к `terminate`), и нельзя выбрасывать исключение из конструктора, помеченного `noexcept`.
