# 145. Расскажите о протоколах верхнего уровня.

В контексте сетевого программирования на C++ под «протоколами верхнего уровня» обычно понимаются протоколы **прикладного уровня (Application Layer)** модели OSI (7-й уровень) и, в более широком смысле, протоколы, реализуемые поверх транспортного уровня (TCP/UDP). Именно на этом уровне происходит взаимодействие с сетевыми приложениями: разработчик на C++ чаще всего работает не с «сырыми» пакетами IP, а с API сокетов и библиотеками, реализующими конкретные прикладные протоколы.

Ниже разобраны ключевые аспекты: место верхних уровней в модели, основные протоколы и их особенности с точки зрения реализации на C++.

---

### Место верхних уровней в модели OSI/TCP-IP

В классической модели OSI к верхним уровням относят три уровня:
- **Прикладной (Application, 7)** — интерфейс между приложением и сетью.
- **Представления (Presentation, 6)** — кодирование, сжатие, шифрование.
- **Сеансовый (Session, 5)** — установление, поддержание и завершение сеансов связи.

На практике в стеке TCP/IP функции представления и сеанса часто реализуются внутри прикладных протоколов или библиотек, а не выделяются в отдельные уровни . Например, шифрование (аналог уровня представления) реализуется через TLS/SSL поверх TCP, а управление сессией — через механизмы cookies в HTTP или идентификаторы сессий в протоколах удалённого доступа.

С точки зрения C++-разработчика, «протокол верхнего уровня» — это, как правило, **спецификация формата сообщений и последовательности обмена**, которая реализуется поверх `SOCK_STREAM` (TCP) или `SOCK_DGRAM` (UDP). Библиотеки вроде `Boost.Asio`, `POCO` или `cpp-httplib` предоставляют готовые реализации этих протоколов, но понимание их устройства необходимо для отладки, настройки производительности и выбора правильной транспортной основы.

### Основные прикладные протоколы и их характеристики

Ниже приведены наиболее распространённые протоколы верхнего уровня, с которыми сталкивается C++-разработчик.

#### HTTP / HTTPS
**Назначение:** передача гипертекста и произвольных данных (REST API, веб-сервисы).
**Транспорт:** TCP (порт 80 для HTTP, 443 для HTTPS).
**Особенности для C++:**
- HTTP — текстовый протокол с запрос-ответной моделью. На C++ удобно реализуется через сокеты с построчным разбором заголовков (метод, URI, версия, заголовки, тело).
- HTTPS требует интеграции с TLS-библиотекой (OpenSSL, mbedTLS, wolfSSL). Популярный стек: `Boost.Asio` + `Boost.Beast` (HTTP) + `OpenSSL` (TLS).
- Для высоконагруженных систем важно учитывать keep-alive, конвейеризацию (pipelining) и мультиплексирование в HTTP/2 (реализуется через библиотеки вроде `nghttp2`).

#### FTP / FTPS / SFTP
**Назначение:** передача файлов.
**Транспорт:** TCP (управляющее соединение — порт 21, данные — порт 20 в активном режиме).
**Особенности для C++:**
- FTP использует два соединения (control и data), что усложняет реализацию по сравнению с HTTP. Пассивный режим (PASV) предпочтителен за NAT/firewall.
- FTPS (FTP over TLS) требует TLS-обёртки для обоих каналов.
- SFTP — это не FTP over SSL, а подсистема протокола SSH (порт 22). На C++ реализуется через `libssh2` или `libssh`.

#### SMTP / POP3 / IMAP
**Назначение:** отправка и получение электронной почты.
**Транспорт:** TCP (SMTP — 25/465/587, POP3 — 110/995, IMAP — 143/993).
**Особенности для C++:**
- SMTP — текстовый протокол команд/ответов (HELO, MAIL FROM, RCPT TO, DATA). Часто используется в связке с MIME для вложений (кодирование Base64, quoted-printable).
- POP3 прост для реализации (аналог «скачать и удалить»), IMAP сложнее из-за поддержки папок и флагов сообщений.
- Для безопасной отправки почты критично использовать TLS (порты 465/587) и аутентификацию (AUTH PLAIN/LOGIN/CRAM-MD5).

#### DNS
**Назначение:** разрешение доменных имён в IP-адреса.
**Транспорт:** UDP (порт 53) для обычных запросов, TCP — для зонных трансферов и больших ответов (DNSSEC, EDNS0).
**Особенности для C++:**
- Формат DNS-сообщения бинарный (заголовок, вопрос, ответы, авторитетные записи, дополнительные записи). Поля имеют сетевой порядок байт (`htons`/`htonl`).
- На C++ удобно реализовывать собственный резолвер или использовать `getaddrinfo` (блокирующий) либо асинхронные обёртки (например, `asio::ip::tcp::resolver`).
- Для высокопроизводительных систем (CDN, балансировщики) часто требуется кэширование DNS-ответов и поддержка EDNS Client Subnet.

#### DHCP
**Назначение:** автоматическая выдача IP-адресов и сетевых параметров.
**Транспорт:** UDP (сервер — порт 67, клиент — 68).
**Особенности для C++:**
- Сообщения DHCP — бинарные структуры с фиксированным заголовком и опциями TLV (Type-Length-Value). На C++ требуют аккуратной работы с упаковкой структур (`#pragma pack`) и сетевым порядком байт.
- Широковещательные запросы (DHCPDISCOVER) отправляются на `255.255.255.255:67`. Для приёма ответов нужно уметь открывать сокет на `0.0.0.0:68` до назначения адреса (требует привилегий или `SO_BINDTODEVICE` на Linux).

#### SNMP
**Назначение:** мониторинг и управление сетевыми устройствами.
**Транспорт:** UDP (порт 161 для запросов, 162 для traps).
**Особенности для C++:**
- Сообщения SNMP кодируются в ASN.1 BER (Binary Encoding Rules). На C++ обычно используют готовые библиотеки (`net-snmp`, `libsnmp`), так как ручная реализация BER трудоёмка.
- SNMPv3 добавляет аутентификацию и шифрование, что увеличивает сложность реализации.

#### WebSocket
**Назначение:** двунаправленная связь в реальном времени поверх одного TCP-соединения.
**Транспорт:** TCP (порт 80/443 при использовании HTTP Upgrade).
**Особенности для C++:**
- Начинается как HTTP-запрос с заголовком `Upgrade: websocket`, затем выполняется рукопожатие (Sec-WebSocket-Key/Accept).
- После установления соединения кадры WebSocket имеют бинарный формат с маскированием (клиент → сервер) и опкодами (text, binary, ping, pong, close).
- Популярные C++-библиотеки: `Boost.Beast` (WebSocket), `uWebSockets`, `websocketpp`.

### Выбор транспорта: TCP vs UDP для протоколов верхнего уровня

При проектировании собственного протокола верхнего уровня на C++ ключевым решением является выбор транспортного протокола.

| Критерий | TCP | UDP |
| :--- | :--- | :--- |
| **Надёжность** | Гарантирует доставку, порядок, отсутствие дублирования | Не гарантирует ничего; всё это должно быть реализовано на прикладном уровне |
| **Установление соединения** | Требует handshake (3-way) | Без установления соединения |
| **Заголовок** | 20+ байт | 8 байт |
| **Подходит для** | HTTP, FTP, SMTP, SSH, WebSocket | DNS, DHCP, SNMP, потоковое видео/аудио, игры |
| **Сложность на C++** | Проще (ядро ОС берёт на себя надёжность) | Сложнее, если нужна надёжность (реализация подтверждений, таймаутов, окон) |

Если протокол верхнего уровня требует гарантированной доставки сообщений (например, RPC, файловый обмен), проще использовать TCP и не изобретать подтверждения на уровне приложения. Если важна минимальная задержка и допустима потеря отдельных сообщений (телеметрия, игры, DNS), выбирают UDP.

### Практические рекомендации для C++

1. **Не реализуйте прикладной протокол вручную, если есть проверенная библиотека.** Для HTTP/1.1 и WebSocket — `Boost.Beast`; для TLS — `OpenSSL`; для SSH/SFTP — `libssh2`; для DNS — `ldns` или `c-ares` (асинхронный резолвер); для SNMP — `net-snmp`.
2. **Учитывайте порядок байт.** Все многобайтовые поля в бинарных протоколах (DNS, DHCP, заголовки TCP/UDP) передаются в сетевом порядке (big-endian). Используйте `htonl`/`htons`/`ntohl`/`ntohs` или `std::byteswap` (C++23).
3. **Будьте осторожны с выравниванием структур.** При разборе бинарных протоколов (DHCP, DNS-заголовки) используйте `#pragma pack(push, 1)` или читайте поля побайтово, чтобы избежать неожиданного паддинга.
4. **Для асинхронных приложений** используйте `Boost.Asio` или `asio` (standalone) с корутинами (C++20) — это упрощает обработку множества одновременных соединений без создания потока на каждое.
5. **Таймауты и обработка ошибок** на прикладном уровне критичны: даже поверх TCP возможны «зависшие» соединения из-за разрыва сети. Устанавливайте `SO_RCVTIMEO`/`SO_SNDTIMEO` или используйте таймеры в event loop.
