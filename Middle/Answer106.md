# 106. Что такое принцип DRY?

## Определение

**DRY (Don't Repeat Yourself — «не повторяйся»)** — принцип разработки ПО, сформулированный Энди Хантом и Дэйвом Томасом в книге «The Pragmatic Programmer». Формулировка:

> Каждый фрагмент знания в системе должен иметь единственное, однозначное, авторитетное представление.

Ключевое слово — **знание** (knowledge), а не код. DRY — это не про «меньше символов», а про то, что **бизнес-правило, формула, конфигурация или алгоритм должны быть описаны в одном месте**.

## Суть принципа

Если одно и то же знание дублируется в нескольких местах, то при изменении требований придётся править все копии. Пропущенная копия → баг. DRY устраняет этот класс ошибок: изменение делается в одном месте и автоматически распространяется везде.

## Примеры нарушения и исправления

### Пример 1: дублирование бизнес-правила

Плохо — формула НДС продублирована:

```java
class OrderService {
    BigDecimal total(Order o) {
        return o.sum().multiply(new BigDecimal("1.20")); // 20% НДС
    }
}

class InvoiceService {
    BigDecimal amount(Order o) {
        return o.sum().multiply(new BigDecimal("1.20")); // снова 20%
    }
}
```

Хорошо — единственный источник истины:

```java
class TaxPolicy {
    static final BigDecimal VAT = new BigDecimal("0.20");
    BigDecimal withVat(BigDecimal net) { return net.multiply(BigDecimal.ONE.add(VAT)); }
}
```

Теперь при смене ставки правится одно место.

### Пример 2: магические числа и строки

```java
if (status.equals("ACTIVE")) { ... }   // в 15 файлах
```

Лучше — константа или enum:

```java
enum Status { ACTIVE, BLOCKED }
```

### Пример 3: дублирование структуры в DTO

Ручное копирование полей между слоями (`Entity → DTO → ViewModel`) — тоже нарушение DRY. Решается мапперами (MapStruct, AutoMapper) или единым слоем преобразования.

## Связь с OOP/OOD

DRY напрямую связан с другими принципами и механизмами ООП:

| Механизм / принцип | Как помогает DRY |
|---|---|
| **Наследование** | Вынести общее поведение в базовый класс |
| **Композиция** | Переиспользовать поведение через делегирование |
| **Полиморфизм** | Заменить `switch`/`if` по типу единой абстракцией |
| **Инкапсуляция** | Скрыть знание внутри одного класса, не размазывая его |
| **SRP (Single Responsibility)** | Одна причина изменения → одно место хранения знания |
| **Шаблоны проектирования** | Strategy, Template Method, Factory устраняют повторяющиеся ветвления |

Пример устранения дублирования через полиморфизм:

```java
// Плохо: повторяющаяся логика в ветках
if (type == PDF) renderPdf(doc);
else if (type == HTML) renderHtml(doc);

// Хорошо: полиморфизм
interface Renderer { void render(Doc d); }
class PdfRenderer implements Renderer { ... }
class HtmlRenderer implements Renderer { ... }
```

## Важные оговорки (чего DRY не означает)

1. **DRY ≠ «убрать любой похожий код»**. Совпадение кода не всегда означает совпадение знания. Два метода могут выглядеть одинаково, но меняться по разным причинам — их объединение нарушит SRP и создаст **преждевременную абстракцию**. Правило: дублирование дешевле неверной абстракции (см. «Rule of Three» — абстрагировать после третьего повторения).

2. **DRY не про код, а про знание**. Два разных класса с одинаковым `toString()` могут быть совершенно не связаны — это не нарушение.

3. **Не путать с WET** (Write Everything Twice / We Enjoy Typing) — антипаттерн копипасты, но иногда оправдан как временный шаг (duplication before abstraction).

4. **DRY vs DIE** (Duplication Is Evil) — по сути синоним, акцент на вреде дублирования.

## Итог

DRY — принцип **единого источника истины для каждого знания** в системе. В ООП достигается через инкапсуляцию, наследование, композицию и полиморфизм, а также тесно связан с SRP. Применять его нужно осмысленно: устранять дублирование **знаний**, а не случайное сходство кода, чтобы не плодить лишние абстракции.
