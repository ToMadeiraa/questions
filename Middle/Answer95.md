# 95. Что такое паттерн Visitor?

**Visitor (Посетитель)** — это поведенческий паттерн проектирования, который позволяет добавлять новые операции к существующей иерархии объектов, не изменяя сами классы этих объектов . Он относится к группе классических паттернов «Банды четырёх» (GoF).

## Основная идея

Паттерн решает проблему, когда у вас есть стабильная структура классов (например, дерево разбора, документ или граф сцены), но набор операций над этой структурой может часто меняться или расширяться. Вместо того чтобы «размазывать» каждую новую операцию по всем классам элементов (нарушая принцип открытости/закрытости), Visitor выносит логику операции в отдельный класс-посетитель .

## Ключевой механизм: двойная диспетчеризация

Сердце паттерна — это **двойная диспетчеризация** (double dispatch). Обычный вызов метода в ООП выбирает реализацию на основе типа объекта, у которого вызывается метод (одинарная диспетчеризация). Visitor добавляет второй уровень выбора: тип посетителя.

Это реализуется через два шага:
1.  Элемент предоставляет метод `accept(Visitor v)`.
2.  Внутри `accept` элемент вызывает у посетителя метод `v.visit(this)`, передавая себя.

Таким образом, конкретный метод `visit` выбирается на основе **и типа элемента, и типа посетителя** .

## Структура участников

| Роль | Описание |
| :--- | :--- |
| **Visitor** | Интерфейс или абстрактный класс, объявляющий методы `visit` для каждого типа конкретного элемента. |
| **ConcreteVisitor** | Реализует конкретную операцию. Один класс посетителя = одна операция над всей структурой. |
| **Element** | Интерфейс, объявляющий метод `accept(Visitor)`. |
| **ConcreteElement** | Реализует `accept`, вызывая соответствующий метод посетителя. |
| **ObjectStructure** | (Опционально) Контейнер, который хранит элементы и позволяет обходить их (например, коллекция или дерево). |

## Главное преимущество и главный недостаток

**Преимущество:** Легко добавлять новые операции. Нужно просто создать нового наследника `Visitor`. Классы элементов остаются нетронутыми .

**Недостаток:** Трудно добавлять новые типы элементов. Если в иерархию добавляется новый класс `ElementC`, придётся изменить интерфейс `Visitor` и реализовать новый метод `visit` **во всех** существующих посетителях. Это нарушает принцип открытости/закрытости в обратную сторону .

## Когда использовать

Паттерн оправдан, когда:
*   Иерархия классов элементов **стабильна** (редко меняется).
*   Над элементами нужно выполнять **много различных, несвязанных операций**.
*   Логика операций не должна «загрязнять» классы элементов (например, сериализация в разные форматы, компиляция, статический анализ) .

Если же иерархия классов часто меняется, а операции стабильны, Visitor, скорее всего, усложнит поддержку.

## Пример (псевдокод)

```java
// Интерфейс посетителя
interface Visitor {
    void visit(Book book);
    void visit(Fruit fruit);
}

// Интерфейс элемента
interface Item {
    void accept(Visitor v);
}

// Конкретные элементы
class Book implements Item {
    public void accept(Visitor v) { v.visit(this); }
}
class Fruit implements Item {
    public void accept(Visitor v) { v.visit(this); }
}

// Конкретный посетитель: подсчёт калорий
class CalorieVisitor implements Visitor {
    public void visit(Book book) { /* логика для книги */ }
    public void visit(Fruit fruit) { /* логика для фрукта */ }
}
```

## Связь с «Expression Problem»

В более широком смысле Visitor — это один из способов решения (или обхода) так называемой **Expression Problem**, сформулированной Филипом Уодлером. Суть в том, что в типичном ООП-языке вы можете легко добавлять новые типы (классы), но добавление новых операций требует правки всех классов. Visitor «переворачивает» эту ситуацию: он делает лёгким добавление операций, но сложным — добавление типов .
