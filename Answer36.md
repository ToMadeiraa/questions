# Вопрос 36. Какие варианты использования volatile знаете?

> **Кратко:** `volatile` запрещает компилятору кешировать значение в регистре и выбрасывать «лишние» чтения и записи: каждый доступ к объекту должен реально произойти. Это нужно для **регистров устройств (MMIO)**, **флагов в обработчиках сигналов**, переменных вокруг `setjmp`/`longjmp` и данных, изменяемых прерыванием. Для многопоточности `volatile` **не годится** — там нужны `std::atomic` или мьютекс.

---

## Что гарантирует и чего не гарантирует volatile

Гарантия ровно одна: все обращения к объекту, записанные в исходнике, присутствуют в машинном коде и выполняются в том же порядке **относительно друг друга**.

`volatile` **не** даёт:

- атомарности — `v++` остаётся чтением-изменением-записью;
- взаимного исключения;
- отношения *happens-before* между потоками;
- барьеров памяти для обычных (не volatile) обращений вокруг.

> Формулировка стандарта: `volatile` — подсказка реализации, что объект может изменяться способами, не обнаруживаемыми компилятором. Про потоки в определении нет ни слова.

---

## 1. Регистры устройств, MMIO, драйверы

Регистр статуса по фиксированному адресу меняется аппаратурой. Без `volatile` цикл ожидания был бы оптимизирован в бесконечный цикл с одним чтением.

```cpp
#include <cstdint>

// Регистр статуса, отображённый на память (пример адреса)
volatile std::uint32_t* const kStatus =
    reinterpret_cast<volatile std::uint32_t*>(0x4000'0000u);

void waitReady() {
    // Каждая итерация обязана перечитать регистр: компилятор не вправе
    // закешировать *kStatus и превратить цикл в while (1)
    while ((*kStatus & 0x1u) == 0) { /* spin */ }
}
```

Так же оформляют запись: без `volatile` запись «в никуда» (результат никто не читает) может быть удалена как мёртвый код, а для железа она — значимое действие.

---

## 2. Флаги в обработчиках сигналов

Обработчик сигнала асинхронный: компилятор не видит, что переменная меняется «извне».

```cpp
#include <csignal>

// sig_atomic_t — тип, запись и чтение которого не разрываются сигналом
volatile std::sig_atomic_t g_stop = 0;

extern "C" void onSignal(int) { g_stop = 1; }

int main() {
    std::signal(SIGINT, onSignal);
    while (!g_stop) { /* полезная работа */ }
}
```

Современная альтернатива — `std::atomic<bool>` с `is_always_lock_free`: операции над lock-free `atomic` разрешены в обработчике сигнала и дают корректную семантику.

---

## 3. Переменные вокруг setjmp / longjmp

Если локальная переменная изменяется между `setjmp` и `longjmp`, её значение после прыжка неопределено — если она не `volatile`. Это прямо записано в стандарте.

```cpp
#include <csetjmp>
std::jmp_buf g_env;

void run() {
    volatile int step = 0;   // без volatile значение после longjmp теряется
    if (setjmp(g_env) != 0) {
        // step гарантированно содержит записанное до прыжка
    }
    step = 1;
    std::longjmp(g_env, 1);
}
```

---

## 4. Данные, изменяемые прерыванием (embedded)

В прошивках ISR и основной цикл — не потоки ОС, а разные контексты на одном ядре. Гонки данных в смысле модели памяти C++ здесь формально нет (прерывание — не поток), поэтому `volatile` достаточно.

```cpp
volatile std::uint32_t g_ticks = 0;      // увеличивается в ISR таймера

void loop() {
    while (g_ticks < 100) { /* ... */ }  // каждое чтение идёт в память
}
```

## Чего volatile не делает: многопоточность

```cpp
volatile bool g_ready = false;
int g_data = 0;

// Поток 1
g_data = 42;
g_ready = true;

// Поток 2 — некорректно!
while (!g_ready) { }
use(g_data);            // гонка данных: UB, g_data может быть не виден
```

Проблем три: нет атомарности, нет *happens-before* (запись `g_data` может «всплыть» после `g_ready`), нет гарантии, что поток вообще увидит изменение. Правильно:

```cpp
#include <atomic>

std::atomic<bool> g_ready{false};
int g_data = 0;

// Поток 1
g_data = 42;
g_ready.store(true, std::memory_order_release);

// Поток 2
while (!g_ready.load(std::memory_order_acquire)) { }
use(g_data);            // корректно: release/acquire даёт синхронизацию
```

| Свойство | `volatile` | `std::atomic` | `mutex` |
|---|---|---|---|
| Атомарность доступа | нет | да | да |
| Порядок между потоками (happens-before) | нет | да, через `memory_order` | да |
| Запрет кеширования в регистре | да | да | да (барьер на lock/unlock) |
| Подходит для MMIO | да | нет | нет |
| Устраняет гонку данных | нет (остаётся UB) | да | да |
| Стоимость | нулевая | атомарная инструкция / барьер | системный вызов |

`std::atomic` **не** заменяет `volatile` для MMIO: атомарная операция может быть реализована через `lock`-префикс или `cmpxchg`-цикл, то есть обращение к регистру будет не одно и не то, что нужно железу. Комбинировать (`volatile std::atomic<T>`) бессмысленно — у членов `atomic` нет `volatile`-перегрузок.

## Синтаксис: где именно ставить volatile

| Объявление | Что квалифицируется |
|---|---|
| `volatile int* p;` | данные по указателю (указатель обычный) |
| `int* volatile p;` | сам указатель (данные — обычные) |
| `volatile int* volatile p;` | и указатель, и данные |
| `const volatile int* p;` | данные: программа не пишет, железо может |
| `void f() volatile;` | метод: `this` имеет тип `volatile T*` |

`volatile`-объект требует `volatile`-квалифицированных методов, а стандартные алгоритмы (`std::copy`, `std::sort`) с `volatile`-диапазонами не работают — нужны ручные циклы. Копирование требует конструктора `T(const volatile T&)`, иначе он не генерируется.

---

## Что изменилось в стандартах

**C++20** объявил устаревшими ряд бессмысленных применений: `volatile`-квалифицированные параметры и возвращаемые типы, `volatile` в structured bindings и лямбда-захватах, составные присваивания и `++`/`--` для `volatile`-объектов. Рабочие применения (MMIO, сигналы) остались. В C# и Java `volatile` имеет другую семантику — путать нельзя.

## Типичные ошибки

1. **`volatile` вместо `std::atomic`/мьютекса.** Самая частая ошибка: `volatile` не делает код потокобезопасным.
2. **`volatile int counter; ++counter;` в двух потоках.** Операция не атомарна, инкременты теряются, поведение — UB.
3. **Ожидание барьера памяти.** `volatile` не запрещает переупорядочивание обычных обращений вокруг него.
4. **`volatile` «для производительности».** Он не ускоряет, а мешает оптимизациям: запрещает вынос чтения из цикла, векторизацию, размещение в регистре.
5. **Забыть `volatile` в обработчике сигнала** — цикл `while (!g_stop)` превращается в вечный.
6. **Попытка защитить `std::vector` через `volatile`.** Квалификатор не про контейнеры и инварианты, а про отдельные обращения.

## Что добавить на собеседовании

- Формула ответа: «`volatile` — про **наблюдаемость доступа**, а не про **потокобезопасность**». Сказать это явно — половина ответа.
- Назвать конкретные применения: MMIO в драйверах, `volatile sig_atomic_t` в обработчике, `setjmp`/`longjmp`, ISR в embedded. Плюс два «бытовых»: `volatile`-переменная как «чёрная дыра» в бенчмарках (чтобы компилятор не выбросил вычисление — правильнее `DoNotOptimize`) и затирание секретов перед `free` (иначе `memset` удаляется как мёртвый код; правильнее `explicit_bzero`/`SecureZeroMemory`).
- Показать корректную замену: `std::atomic<bool>` с `release`/`acquire` или `std::mutex`.
- Для embedded добавить, что порядок обращений к регистрам иногда дополнительно фиксируют барьерами (`std::atomic_signal_fence`, `asm volatile("" ::: "memory")`).

## Итог

| Ситуация | Нужен `volatile`? | Правильный инструмент |
|---|---|---|
| Регистр устройства (MMIO) | да | `volatile` (+ барьеры при необходимости) |
| Флаг в обработчике сигнала | да | `volatile sig_atomic_t` или lock-free `std::atomic` |
| Переменная вокруг `setjmp`/`longjmp` | да | `volatile` |
| Данные, изменяемые в ISR | да | `volatile` |
| Бенчмарк, «чёрная дыра» | да, как костыль | `DoNotOptimize` / `asm volatile` |
| Передача данных между потоками | **нет** | `std::atomic`, `mutex`, `condition_variable` |
| Защита контейнера или инварианта | **нет** | инкапсуляция, синхронизация |
