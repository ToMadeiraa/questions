# 167. Разница между git fetch и git pull?

Оба инструмента используются для синхронизации локального репозитория с удалённым (`origin`), но делают это по-разному. Ключевое отличие — **`git fetch` только скачивает изменения, а `git pull` скачивает и сразу сливает их в текущую ветку**.

## Кратко

| Команда | Что делает | Изменяет рабочую директорию? | Изменяет текущую ветку? |
|---|---|---|---|
| `git fetch` | Скачивает объекты и обновляет `remote-tracking` ветки (`origin/main`) | ❌ Нет | ❌ Нет |
| `git pull` | `git fetch` + `git merge` (или `git rebase`) в текущую ветку | ✅ Да (при merge/rebase) | ✅ Да |

Формально `git pull` — это сокращение:

```bash
git pull = git fetch + git merge origin/<current-branch>
```

(или `git rebase`, если настроено `pull.rebase = true`).

## git fetch — подробно

```bash
git fetch origin
```

- Скачивает все новые коммиты, ветки и теги с удалённого репозитория.
- Обновляет **remote-tracking** ветки: `origin/main`, `origin/feature-x` и т.д.
- **Не трогает** вашу локальную ветку `main` и рабочую директорию.
- Безопасен: можно посмотреть, что изменилось, прежде чем что-то делать.

Что можно сделать после fetch, чтобы «увидеть» изменения:

```bash
git log HEAD..origin/main --oneline      # что нового в origin/main
git diff HEAD origin/main                # разница с локальной веткой
git merge origin/main                    # влить вручную, когда готовы
```

Fetch также можно делать для конкретной ветки:

```bash
git fetch origin main
```

Или «сушить» без обновления тегов:

```bash
git fetch --no-tags origin
```

## git pull — подробно

```bash
git pull origin main
```

- Делает fetch, а затем **автоматически** вливает изменения в текущую ветку.
- По умолчанию используется `merge`, что создаёт merge-коммит при расхождении истории.
- Может привести к **merge-конфликтам**, которые нужно разрешать сразу.
- Может неожиданно изменить рабочую директорию и создать merge-коммит.

Варианты поведения:

```bash
git pull --rebase origin main   # вместо merge — rebase (линейная история)
git pull --ff-only origin main  # влить только fast-forward, иначе ошибка
```

Настроить поведение по умолчанию:

```bash
git config --global pull.rebase true       # всегда rebase
git config --global pull.ff only           # всегда только fast-forward
```

## Когда что использовать

**`git fetch`:**
- В CI/CD-пайплайнах, где нужен контроль: сначала проверить `origin/main`, потом решить, что делать.
- Когда хотите посмотреть чужие изменения перед вливанием.
- Когда рабочая директория «грязная» и вы не хотите случайных конфликтов.
- В скриптах, где важна предсказуемость и отсутствие неожиданных merge-коммитов.

**`git pull`:**
- В повседневной работе, когда вы уверены, что локальных расхождений нет (или они тривиальны).
- Для быстрого обновления перед началом работы.
- С `--ff-only` или `--rebase` — как более безопасная альтернатива «голому» pull.

## Практический совет для SCM/CI/CD

В автоматизации (CI-джобы, деплой-скрипты) **предпочтителен `git fetch`** с явным последующим `merge`/`reset`/`checkout` — это делает пайплайн детерминированным и предотвращает неожиданные merge-коммиты в артефактах сборки. «Голый» `git pull` в скриптах опасен: он может зависеть от глобальных настроек `pull.rebase`/`pull.ff` конкретной машины и создать конфликт посреди пайплайна.

Типичный безопасный паттерн в CI:

```bash
git fetch origin main
git checkout main
git reset --hard origin/main   # чистое состояние = origin/main
```

## Итог

- `git fetch` — **только скачивание**, ничего не меняет в вашей работе; безопасно и предсказуемо.
- `git pull` — **скачивание + слияние**; удобно, но может создать merge-коммит или конфликт.
- `git pull` = `git fetch` + `git merge` (по умолчанию), поэтому fetch — «строительный блок» pull.
