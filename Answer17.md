# Вопрос 17. Может ли виртуальная функция быть шаблонной?

> **Кратко:** нет. Функция-член не может быть одновременно шаблоном и виртуальной — стандарт запрещает это прямым текстом: «A member function template shall not be virtual» ([temp.mem]). Причина в механике: виртуальная диспетчеризация требует фиксированной таблицы слотов, известной на момент определения класса, а множество инстанциаций шаблона в этот момент неизвестно и потенциально бесконечно.

---

## Почему запрещено: механика `vtable`

Виртуальный вызов компилируется в «загрузить `vptr` из объекта, вызвать слот с индексом N». Раскладка таблицы фиксируется, когда компилятор видит **определение класса**, и одинакова во всех единицах трансляции — иначе объект, созданный в одном `.cpp`, нельзя было бы корректно использовать в другом.

| Причина | Пояснение |
|---|---|
| Фиксированная раскладка `vtable` | каждый слот занимается при определении класса; сколько будет инстанциаций `f<T>` — неизвестно, а таблица должна быть одной |
| Раздельная компиляция | компилятор обрабатывает один `.cpp` и не знает, какие `T` используют другие единицы трансляции |
| Момент вызова | вызов `v->f<int>()` должен резолвиться через слот, но шаблон инстанцируется только по факту использования |
| ODR | разные TU сгенерировали бы разные наборы слотов → несовместимые представления одного класса |
| Цена | шаблон и так генерирует код под каждый тип; добавлять к этому ещё и косвенный вызов смысла нет |

Диагностика компиляторов прямолинейна: `error: member function templates cannot be virtual` (GCC/Clang), аналогичная ошибка у MSVC.

```cpp
struct Bad {
    template <class T>
    virtual void f(T) {}          // ОШИБКА КОМПИЛЯЦИИ: member function templates cannot be virtual
};
```

## Что можно перепутать: шаблон класса с виртуальной функцией

Запрет касается **функции-шаблона**. Виртуальные функции внутри **шаблона класса** — совершенно нормальная конструкция: для каждого набора аргументов шаблона получается отдельный класс со своей `vtable`.

```cpp
#include <string>

template <class T>
class Repository {                            // шаблон класса
public:
    virtual ~Repository() = default;
    virtual void save(const T& item) = 0;     // виртуальная функция — можно
    virtual T load(int id) const = 0;
};

class InMemoryRepo : public Repository<std::string> {
public:
    void save(const std::string&) override {}
    std::string load(int) const override { return {}; }
};
```

Здесь `Repository<std::string>` и `Repository<int>` — два независимых класса, у каждого свой набор виртуальных слотов. Никакого противоречия с запретом нет.

## Что ещё разрешено и запрещено виртуальной функции

| Свойство | Виртуальная функция |
|---|---|
| `constexpr` | да, начиная с C++20 |
| `noexcept` | да |
| `final` / `override` | да |
| `private` / `protected` | да (идиома NVI: публичный невиртуальный интерфейс + приватная виртуальная реализация) |
| Чистая (`= 0`) с телом | да |
| `static` | нет: статическая функция не имеет `this` |
| Конструктор | нет: объект ещё не создан, `vptr` не установлен |
| Функция-шаблон | нет |

```cpp
class Base {
public:
    virtual ~Base() = default;

    // NVI: невиртуальный интерфейс с проверками, виртуальная — только реализация
    int size() const {
        int n = sizeImpl();
        return n < 0 ? 0 : n;
    }

private:
    virtual int sizeImpl() const = 0;
};
```

## Обходные пути, если «шаблонный полиморфизм» всё-таки нужен

| Задача | Решение |
|---|---|
| Вызывать «шаблонное» поведение через базовый интерфейс | нешаблонная виртуальная функция + **стирание типа** (`std::any`, `void*`, свой интерфейс) |
| Набор типов известен заранее | несколько нешаблонных виртуальных перегрузок |
| Полиморфизм без накладных расходов `vtable` | **CRTP** (статический полиморфизм) |
| Замкнутый набор типов | `std::variant` + `std::visit` |
| Двойная диспетчеризация | паттерн **Visitor** |

**Стирание типа через `std::any`:**

```cpp
#include <any>
#include <string>

class Formatter {
public:
    virtual ~Formatter() = default;
    // нешаблонная виртуальная точка входа; конкретный тип «спрятан» внутри std::any
    virtual std::string format(const std::any& value) const = 0;
};

class JsonFormatter : public Formatter {
public:
    std::string format(const std::any& value) const override {
        if (value.type() == typeid(int))
            return std::to_string(std::any_cast<int>(value));
        if (value.type() == typeid(std::string))
            return '"' + std::any_cast<std::string>(value) + '"';
        return "null";
    }
};
```

**CRTP — полиморфизм на этапе компиляции:**

```cpp
#include <numbers>

template <class Derived>
class Shape {
public:
    double area() const { return static_cast<const Derived*>(this)->areaImpl(); }
};

class Circle : public Shape<Circle> {
public:
    explicit Circle(double r) : r_(r) {}
    double areaImpl() const { return std::numbers::pi * r_ * r_; }

private:
    double r_;
};
```

**`std::variant` + `std::visit` — без виртуальности вообще:**

```cpp
#include <string>
#include <variant>

using Key = std::variant<int, std::string>;

struct Describe {
    std::string operator()(int v) const { return "int:" + std::to_string(v); }
    std::string operator()(const std::string& s) const { return "str:" + s; }
};

std::string describe(const Key& k) { return std::visit(Describe{}, k); }
```

## Типичные ошибки

1. **Пытаться объявить `template <class T> virtual void f(T);`** — не компилируется ни в одном стандарте, включая C++20.
2. **Путать «шаблон класса с виртуальной функцией» и «виртуальную функцию-шаблон»** — первое разрешено, второе нет.
3. **Думать, что шаблонный метод можно переопределить** — переопределение работает только для виртуальных функций, а шаблон в наследнике лишь скрывает базовый (name hiding), если не написать `using Base::f;`.
4. **Считать, что `std::any`-обход бесплатен** — там `RTTI`, динамическая аллокация и потеря типобезопасности на границе.
5. **Забывать виртуальный деструктор** в базе, через которую удаляют наследника.
6. **Считать виртуальный вызов «всегда дорогим»** — при `final`-классах, LTO и известном динамическом типе компилятор девиртуализирует вызов и инлайнит его.

## Что добавить на собеседовании

- Виртуальный вызов — косвенный переход через `vptr`, он мешает инлайну и предсказанию ветвлений; `final` и LTO возвращают часть оптимизаций.
- Для шаблона класса `vtable` генерируется в каждой единице трансляции, где класс используется, а линкер склеивает дубликаты (COMDAT / слабые символы).
- **NVI** (non-virtual interface) — идиоматичный способ совместить проверки инвариантов с виртуальной реализацией.
- Если интерфейс действительно требует «любого типа» — это признак того, что тип должен быть параметром **класса**, а не функции.

## Итог

| Вопрос | Ответ |
|---|---|
| Виртуальная функция может быть шаблоном | Нет, запрещено стандартом |
| Шаблон класса может иметь виртуальные функции | Да, это отдельный класс на каждую инстанциацию |
| Виртуальная функция может быть `constexpr` | Да, с C++20 |
| Виртуальная функция может быть `noexcept` / `final` | Да |
| Может ли конструктор быть виртуальным | Нет |
| Как получить «шаблонный полиморфизм» | CRTP, стирание типа, `std::variant` + `std::visit` |
