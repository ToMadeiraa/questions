# 73. Что будет, если забыть вызвать `delete`? Когда освободится эта память?

## Краткий ответ

Если забыть вызвать `delete` для памяти, выделенной через `new`, возникает **утечка памяти (memory leak)**. В общем случае эта память **не освободится** до завершения работы программы (а в некоторых случаях — вообще никогда в рамках жизни процесса). Операционная система вернёт физическую память только после завершения процесса.

## Что происходит на практике

### 1. Память остаётся занятой

```cpp
void foo() {
    int* p = new int[1000]; // выделили 4000 байт
    // забыли delete[] p
} // указатель p уничтожен, но память по-прежнему занята
```

После выхода из функции локальная переменная `p` (сам указатель) уничтожается — это обычная переменная на стеке. Но **выделенный блок в куче остаётся помеченным как занятый**. У программы больше нет способа до него добраться, поэтому освободить его она уже не сможет. Это и есть утечка.

### 2. Утечка накапливается

Если такая функция вызывается в цикле или repeatedly, объём утёкшей памяти растёт:

```cpp
for (int i = 0; i < 1'000'000; ++i) {
    foo(); // каждая итерация "теряет" 4000 байт
}
// суммарно утекло ~4 ГБ
```

В какой-то момент `new` начнёт бросать исключение `std::bad_alloc` (или вернёт `nullptr`, если используется `new(std::nothrow)`) — программа аварийно завершится.

### 3. Когда память реально освобождается

| Сценарий | Когда освобождается память |
|---|---|
| Обычная программа (процесс) | При завершении процесса — ОС забирает всю его память целиком |
| Долгоживущий сервер/демон | Может никогда не освободиться за время работы, пока процесс не перезапустят |
| Долгая работа с накоплением утечек | Программа падает по `bad_alloc` раньше завершения |

**Важно:** ОС освобождает память **по завершении процесса**, а не по завершении функции/области видимости. Пока процесс жив — утёкшая память недоступна ни программе, ни (в общем случае) другим процессам.

## Нюансы, которые стоит упомянуть на собеседовании

### Утечка ≠ «память исчезла навсегда» для ОС
Физические страницы остаются выделенными процессу. Даже если вы «потеряли» указатель, ОС не знает, что эта память больше не нужна — для неё это всё ещё валидная память процесса.

### Деструкторы не вызываются
При утечке объекта, выделенного через `new`, **не вызывается деструктор**:

```cpp
class Resource {
public:
    Resource() { /* открыли файл, сокет, захватили мьютекс */ }
    ~Resource() { /* закрыли, освободили */ }
};

void leak() {
    Resource* r = new Resource();
    // забыли delete r — деструктор НЕ вызовется!
}
```

Это приводит не только к утечке памяти, но и к утечке **других ресурсов**: файловых дескрипторов, сокетов, блокировок (что может вызвать дедлок), памяти внутри самого объекта и т.д.

### Утечка может быть «логически безопасной»
Если память выделяется один раз при старте и живёт до конца программы (например, глобальный синглтон), утечка формально есть, но практического вреда почти нет. Инструменты вроде Valgrind/ASan всё равно её покажут, но такие случаи иногда намеренно игнорируют («still reachable»).

## Как обнаружить утечки

- **Valgrind (memcheck)** — классический инструмент для Linux.
- **AddressSanitizer (ASan)** с флагом `-fsanitize=address` — встроен в GCC/Clang, ловит утечки (`LeakSanitizer`).
- **Visual Studio** — встроенный CRT debug heap (`_CrtDumpMemoryLeaks`).
- **Dr. Memory** для Windows.

Пример с ASan:

```bash
g++ -fsanitize=address -g main.cpp -o app
./app
# при выходе LeakSanitizer выведет отчёт об утечке
```

## Как избежать проблемы

1. **RAII и умные указатели** — главное средство в современном C++:

```cpp
#include <memory>

void safe() {
    auto p = std::make_unique<int[]>(1000); // память освободится автоматически
} // delete[] вызовется в деструкторе unique_ptr
```

2. **Контейнеры STL** (`std::vector`, `std::string`) вместо ручного `new[]`.
3. **Правило: каждому `new` — `delete`, каждому `new[]` — `delete[]`** (несовпадение — неопределённое поведение).
4. **Не использовать голые `new`/`delete`** без крайней необходимости.

## Резюме

- Забытый `delete` → **утечка памяти**: блок остаётся занятым, но недоступным программе.
- Память **не освобождается** при выходе из функции/области видимости — только при завершении процесса (ОС).
- Дополнительно **не вызываются деструкторы**, что ведёт к утечке прочих ресурсов.
- В долгоживущих программах утечки накапливаются и приводят к `std::bad_alloc` / падению.
- Решение — **RAII, умные указатели, STL-контейнеры**; для поиска — Valgrind/ASan.
