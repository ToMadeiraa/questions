# Вопрос 45. Для чего используют realloc?

> **Кратко:** `realloc` меняет размер уже выделенного блока памяти, сохраняя его содержимое, и возвращает указатель на блок нового размера. Он нужен, чтобы динамический массив рос или ужимался без ручной связки `malloc` + `memcpy` + `free`: аллокатор сам решает, удастся ли расширить блок на месте. Главная ловушка — возвращённый адрес может отличаться от исходного, а при ошибке возвращается `NULL`, но старый блок остаётся живым.

---

## Зачем он вообще нужен

Типичная задача: размер данных заранее неизвестен — читаем строки из файла, накапливаем результаты, парсим протокол. Без `realloc` пришлось бы каждый раз выделять новый блок, копировать туда старое содержимое, освобождать старый и где-то хранить его текущий размер. `realloc` делает это одной операцией и знает старый размер сам — он хранится в метаданных блока у аллокатора.

```cpp
#include <cstdlib>

// Было выделено 4 int, хотим 1024 int — одним вызовом, с сохранением данных
void grow(int*& p) {
    int* tmp = static_cast<int*>(std::realloc(p, 1024 * sizeof(int)));
    if (tmp == nullptr) return;   // ошибка: p по-прежнему валиден, данные на месте
    p = tmp;                      // только теперь старый указатель можно забыть
}
```

---

## Контракт функции

```cpp
void* realloc(void* ptr, size_t new_size);   // C
```

| Ситуация | Поведение |
|---|---|
| `ptr == NULL` | эквивалентно `malloc(new_size)` |
| `new_size == 0` | до C23 — поведение зависит от реализации: `NULL` либо уникальный указатель, который надо освободить; в C23 это UB. На практике вызывайте `free` |
| Блок удалось расширить на месте | возвращается тот же адрес, копирования нет |
| Блок пришлось перенести | старые данные скопированы, старый блок освобождён, вернулся новый адрес |
| Ошибка выделения | возвращается `NULL`, старый блок **не тронут** и остаётся валидным |
| Новый размер больше старого | байты `[old_size, new_size)` **не инициализированы** |
| Новый размер меньше | хвост отброшен, память может вернуться аллокатору |

Функция работает в байтах и ничего не знает о типах: содержимое переносится побайтово, никакие конструкторы и деструкторы не вызываются.

---

## Почему это лучше, чем malloc + memcpy + free

- Аллокатор уже знает размер старого блока — не нужно хранить его вручную и не нужно передавать.
- Если сразу за блоком есть свободное место, расширение происходит **без копирования**: в glibc блок просто сливается с соседним свободным чанком.
- Для крупных блоков, полученных через `mmap`, используется `mremap` — страницы «переезжают» без копирования данных.
- Если перенос всё-таки нужен, копирование неизбежно, и стоимость операции становится `O(n)`.

То есть `realloc` не «всегда быстрее», но часто дешевле и заметно проще для программиста.

## Типичный динамический массив

```cpp
#include <cstddef>
#include <cstdlib>

typedef struct {
    int*   data;
    size_t size;   /* сколько элементов реально лежит */
    size_t cap;    /* сколько элементов помещается */
} IntVec;

int int_vec_push(IntVec* v, int value) {
    if (v->size == v->cap) {
        size_t new_cap = v->cap ? v->cap * 2 : 4;      /* геометрический рост */
        int* tmp = (int*)realloc(v->data, new_cap * sizeof(int));
        if (tmp == NULL)
            return 0;                                   /* старый блок цел, данные не потеряны */
        v->data = tmp;                                  /* меняем указатель только после успеха */
        v->cap  = new_cap;
    }
    v->data[v->size++] = value;
    return 1;
}
```

Здесь видны два обязательных правила: проверять результат и не затирать старый указатель до проверки.

## Классическая ошибка: потеря указателя

```cpp
// ПЛОХО: при неудаче старый блок потерян — утечка, дальше работа с nullptr
int* p = static_cast<int*>(std::malloc(4 * sizeof(int)));
p = static_cast<int*>(std::realloc(p, 1'000'000 * sizeof(int)));
```

Если `realloc` вернёт `NULL`, присваивание затрёт единственный адрес старого блока: память утечёт, а `p` станет нулевым. Правильный шаблон — промежуточная переменная и `free(p)` в ветке ошибки:

```cpp
int* tmp = static_cast<int*>(std::realloc(p, 1'000'000 * sizeof(int)));
if (tmp == nullptr) {
    std::free(p);        // освобождаем старый блок, если продолжать уже нельзя
    return;
}
p = tmp;
```

## Уменьшение размера — тоже применение

`realloc` умеет не только расти. Если известно, что данных больше не будет, «подрезка» возвращает память аллокатору и снижает потребление:

```cpp
char* shrink_to_fit(char* buf, size_t used) {
    char* tmp = (char*)realloc(buf, used + 1);   /* ужимаем под фактический размер */
    return tmp ? tmp : buf;                      /* ошибка не критична: старый буфер цел */
}
```

Так же поступают контейнеры при `shrink_to_fit`, только в C++ это лишь подсказка реализации, а не гарантия.

---

## Стоимость и стратегия роста

| Стратегия | Перевыделений при `n` вставках | Суммарное копирование | Амортизированная цена вставки |
|---|---|---|---|
| прибавлять по 1 элементу | `O(n)` | `O(n^2)` | `O(n)` |
| удваивать (`×2`) | `O(log n)` | `O(n)` | `O(1)` |
| растить в 1.5 раза | `O(log n)` | `O(n)` | `O(1)` |

Именно поэтому все динамические массивы растут геометрически: `std::vector` в libstdc++/libc++ удваивает ёмкость, в MSVC — умножает на 1.5 (это экономит память при перевыделении за счёт возможности переиспользовать освобождённый блок).

---

## Ловушки, о которых спрашивают

- **Старый указатель инвалидируется** после успешного `realloc`, если блок переехал. Любое обращение к нему — use-after-free.
- **Указатели внутрь блока** (например, `p + 10`) тоже инвалидируются при переносе — их нельзя кэшировать между вызовами.
- **Самоссылающиеся структуры.** Если внутри блока лежит указатель на другую часть этого же блока, после переноса он станет висячим. Храните смещение (`offset`), а не адрес.
- **`realloc` нельзя применять к памяти из `new`** и наоборот — семейства аллокации не смешиваются.
- **Переполнение размера.** `n * sizeof(T)` может переполниться до вызова; в BSD и glibc есть `reallocarray`, который проверяет произведение.

## Почему в C++ realloc почти не нужен

`std::vector` уже реализует ту же стратегию роста, но корректно с точки зрения типов: он переносит элементы конструкторами перемещения и вызывает деструкторы.

```cpp
#include <vector>

void cpp_way() {
    std::vector<int> v;
    v.reserve(1024);              // одно выделение вместо серии перевыделений
    for (int i = 0; i < 1024; ++i)
        v.push_back(i);           // capacity уже достаточно — роста не будет
    v.shrink_to_fit();            // необязывающая просьба вернуть лишнюю ёмкость
}
```

Для нетривиального типа (например, `std::string`) `realloc` — **undefined behavior**: байтовое копирование объекта, у которого есть конструктор копирования и внутренний указатель на собственный буфер, ломает инварианты. Даже если «на практике работает», полагаться на это нельзя.

| Что нужно | C | C++ |
|---|---|---|
| Динамический массив | `realloc` + ручной рост | `std::vector`, `reserve` |
| Точечно изменить размер буфера | `realloc` | `std::vector::resize`, `std::string::resize` |
| Сырая память под C API | `realloc` | `std::unique_ptr<T[]>` + новый массив |

## Типичные ошибки

1. **`p = realloc(p, n)` без промежуточной переменной** — утечка при ошибке и потеря рабочего указателя.
2. **Использование старого указателя после успешного `realloc`** — висячий указатель, если блок переехал.
3. **Забыть, что новый хвост не обнулён:** `realloc` не обнуляет добавленные байты.
4. **`realloc(p, 0)` как способ освободить** — поведение зависит от стандарта и реализации; используйте `free`.
5. **`realloc` для объектов C++ с нетривиальным конструктором** — UB, хотя компилятор не жалуется.
6. **`realloc` для памяти, полученной `new`**, и наоборот.
7. **Рост по одному элементу** (`+1`) — квадратичная суммарная сложность.

---

## Что добавить на собеседовании

- `realloc` — пример того, что аллокатор хранит метаданные блока: именно поэтому он может вырасти на месте и не требует передавать старый размер.
- «Правило промежуточной переменной» — общий шаблон для всех функций, которые возвращают новый ресурс и могут отказать (то же самое в `fopen`, `strdup`, `vector::data`).
- Стоит связать тему с амортизированной сложностью: геометрический рост превращает серию дорогих перевыделений в `O(1)` на операцию.
- В C++ `realloc` вытеснен контейнерами, но понимание его семантики объясняет, почему `std::vector` при росте инвалидирует итераторы и ссылки на элементы.

## Итог

| Аспект | Суть |
|---|---|
| Назначение | изменить размер существующего блока, сохранив данные |
| Типичный сценарий | рост/ужатие динамического массива |
| Успех | вернулся указатель (возможно, другой), данные сохранены до `min(old, new)` |
