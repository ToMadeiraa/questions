# Вопрос 25. Как работает директива include?

> **Кратко:** `#include` заставляет препроцессор найти указанный файл и подставить его содержимое в текущий поток токенов на месте директивы; включённый файл проходит фазы трансляции 1–4 заново и рекурсивно. Это именно текстовая вставка, а не импорт сущностей: никаких модулей, пространств имён и проверок типов не происходит. Отсюда все следствия — дублирование кода заголовков в каждой единице трансляции, необходимость защиты от повторного включения и требование к определениям в заголовках быть `inline`.

---

## Что делает препроцессор по шагам

1. Находит в строке директиву `#include` и следующий за ней токен-имя заголовка (`<...>` или `"..."`).
2. Определяет файл по правилам поиска для выбранной формы.
3. Прогоняет этот файл через фазы 1–4: склейка строк, разбиение на лексемы, выполнение его собственных директив.
4. Подставляет получившийся текст вместо строки с `#include` и продолжает разбор текущего файла — уже после вставленного текста.

Важная деталь: включённый файл — это **отдельный поток лексем**, который вставляется в точку директивы. Поэтому `#include` в середине функции или класса технически возможен (и иногда применяется в X-макросах), хотя почти всегда это ошибка проектирования.

К концу фазы 4 директив в тексте не остаётся: компилятор видит один сплошной поток токенов — единицу трансляции.

---

## Две формы записи

| Форма | Пример | Смысл |
|---|---|---|
| Угловые скобки | `#include <vector>` | файл из каталогов заголовков реализации (системный) |
| Кавычки | `#include "config.h"` | сначала «свой» файл, затем системные каталоги |

Порядок поиска **определяется реализацией**, но на практике он такой:

| Компилятор | `"file.h"` | `<file.h>` |
|---|---|---|
| GCC / Clang | каталог текущего файла → `-iquote` → `-I` → системные | `-I` → системные |
| MSVC | каталог текущего файла → `/I` → `INCLUDE` | `/I` → `INCLUDE` |

«Текущий файл» — это файл, в котором стоит директива, а не тот, с которого началась компиляция. Поэтому одинаковый `#include "util.h"` в разных заголовках может находить разные файлы.

## Что может стоять после `#include`

```cpp
#include <vector>              // имя заголовка в угловых скобках
#include "config.h"            // имя заголовка в кавычках

#define HEADER "generated.h"
#include HEADER                 // допустимо: аргумент раскрывается как макрос
```

После раскрытия макросов директива обязана получить либо `<...>`, либо строковый литерал. Форма `#include HEADER` используется генераторами кода, хотя читаемость от неё страдает.

Проверить наличие заголовка без ошибки позволяет `__has_include` (C++17):

```cpp
#if defined(__has_include)
#  if __has_include(<optional>)
#    include <optional>
#    define HAS_OPTIONAL 1
#  endif
#endif
```

## Пример: что происходит на самом деле

`config.h`:

```cpp
#pragma once
inline constexpr int kBufferSize = 4096;
```

`main.cpp`:

```cpp
#include "config.h"
#include "config.h"   // благодаря защите второй раз ничего не вставится

int buffer[kBufferSize];
```

Результат `g++ -E main.cpp` — строка `#include` исчезла, вместо неё стоит содержимое заголовка ровно один раз:

```cpp
inline constexpr int kBufferSize = 4096;
int buffer[kBufferSize];
```

Если убрать `#pragma once`, текст вставится дважды, и мы получим повторное определение `kBufferSize` — ошибку компиляции.

## Повторное включение и его защита

Классическая ситуация — «ромб»: `main.cpp` включает `a.h` и `b.h`, а оба включают `common.h`. Без защиты `common.h` попадёт в текст дважды.

| Способ | Как работает | Плюсы | Минусы |
|---|---|---|---|
| Include guard | `#ifndef X_H` / `#define X_H` / `#endif` | стандарт, работает везде | нужно уникальное имя, лишние строки |
| `#pragma once` | компилятор сам запоминает файл | короче, быстрее, нет коллизий имён | не стандарт, опирается на идентичность файла (симлинки, копии) |

Полное отсутствие защиты не приводит к «зависанию»: стандарт гарантирует лишь минимум 15 уровней вложенности `#include`, после чего компилятор выдаёт ошибку о превышении предела включений.

## Следствия текстовой природы

**1. Заголовок компилируется заново в каждой единице трансляции.** Проект из 500 `.cpp`, каждый из которых тянет 200 заголовков, — это сотни тысяч повторных разборов. Отсюда предкомпилированные заголовки, вынос реализации в `.cpp` и сокращение транзитивных включений.

**2. Определения в заголовке должны допускать повторение.** Правило одного определения (ODR) требует, чтобы сущность с внешним связыванием определялась в программе один раз:

```cpp
// bad.h — ошибка при включении в два .cpp: два определения counter
int counter = 0;

// good.h — C++17: одно определение на программу
inline int counter = 0;

// good.h — альтернатива: только объявление, определение в одном .cpp
extern int counter;
```

Функции в заголовке помечают `inline`, шаблоны и `constexpr`-функции допускают повторное определение по правилам ODR автоматически, а `static`-переменная в заголовке даёт **отдельную копию в каждой единице трансляции** — частая причина «почему счётчик не растёт».

**3. Порядок включения влияет на смысл.** Если заголовок не самодостаточен, он компилируется только после «правильного» предшественника:

```cpp
// a.h — плохо: использует std::string, не включая <string>
struct A { std::string name; };   // зависит от того, что включили раньше

// a.h — хорошо: заголовок самодостаточен
#include <string>
struct A { std::string name; };
```

Правило: **каждый заголовок должен компилироваться первым**. Проверяется привычкой ставить свой заголовок первой строкой в соответствующем `.cpp`.

**4. Транзитивные включения — скрытая связанность.** Заголовок, который «случайно» работает за счёт чужого `#include`, ломает сборку при любом изменении в чужом коде. Лечится принципом *include what you use*.

## include против модулей C++20

| Свойство | `#include` | `import` (модули) |
|---|---|---|
| Механизм | текстовая вставка на фазе 4 | компиляция интерфейса модуля отдельно |
| Повторная обработка | в каждой единице трансляции | один раз, результат переиспользуется |
| Видимость сущностей | всё, что попало в текст | только экспортированные имена |
| Макросы | протекают между файлами | не экспортируются |
| Скорость сборки | падает с ростом включений | существенно выше |
| Поддержка | везде | C++20, зрелость зависит от тулчейна |

Модули решают главную проблему `#include` — квадратичный рост работы компилятора, — но `#include` останется надолго: он нужен для C-совместимых заголовков и для макросов.

| Задача | Средство |
|---|---|
| увидеть дерево включений | `g++ -H file.cpp`, MSVC `/showIncludes` |
| сгенерировать зависимости для сборки | `g++ -M` / `-MM` |
| принудительно включить файл | `-include prelude.h`, MSVC `/FI` |
| найти лишние включения | include-what-you-use, clangd |
| ускорить повторную сборку | предкомпилированные заголовки (`.pch`) |

## Типичные ошибки

1. **Считать `#include` импортом.** Это вставка текста: включить файл дважды — значит получить его дважды.
2. **Забыть защиту от повторного включения** и получить «redefinition» на структуре или константе.
3. **Определять в заголовке переменную без `inline` или `extern`** — нарушение ODR, на которое линкер может и не пожаловаться.
4. **Помещать в заголовок `static`-переменную**, ожидая единое состояние: получится копия в каждой единице трансляции; обратная ошибка — **зависеть от порядка включения**, не включая нужное самому.
5. **Включать `.cpp`** — почти всегда дублирование символов; легально лишь в редких схемах вроде явной инстанциации шаблонов или «amalgamation»-сборки.
6. **Тянуть всё через `#include <bits/stdc++.h>`** (нестандартный заголовок GCC) — медленно и непереносимо.
7. **Включать заголовок внутри `namespace`** «чтобы не писать квалификаторы» — ломает ODR и связывание с C-кодом.

---

## Что добавить на собеседовании

- Точно назвать природу директивы: текстовая подстановка на фазе 4, включённый файл проходит фазы 1–4 рекурсивно.
- Объяснить разницу двух форм записи и что порядок поиска — implementation-defined, а не «кавычки = локально, скобки = системно» на уровне стандарта.
- Связать `#include` с ODR: почему в заголовке нужны `inline`, `extern` или шаблоны.
- Упомянуть цену: дублирование разбора → PCH, forward declaration, include-what-you-use, модули.
- Хороший финал: «`#include` — самое дорогое, что есть в C++-сборке; современный стиль — минимизировать включения в заголовках и выносить зависимости в `.cpp`».

## Итог

| Аспект | Суть |
|---|---|
| Что делает | вставляет содержимое файла вместо директивы, рекурсивно и на уровне текста |
| Формы | `<...>` — системные каталоги, `"..."` — сначала каталог текущего файла |
| Результат | одна единица трансляции, директив в ней уже нет |
| Повторное включение | лечится include guard или `#pragma once` |
| ODR | определения в заголовке — `inline`, шаблоны, `constexpr`; переменные — `inline` или `extern` |
| Цена | повторный разбор в каждом `.cpp`, протекающие макросы, скрытая связанность |
| Будущее | модули C++20 (`import`) вместо `#include` |
