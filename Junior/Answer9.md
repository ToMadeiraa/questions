# Вопрос 9. Что такое паттерны проектирования и для чего их используют?

> **Кратко:** паттерн проектирования — это **именованное описание проверенного решения** типовой задачи проектирования в некотором контексте. Паттерн фиксирует не код, а структуру взаимодействия объектов и её последствия, поэтому его можно реализовать по-разному в разных языках. Используют их ради общего словаря, переиспользования удачных решений и ослабления связности кода.

---

## 1. Что именно называется паттерном

Идея пришла из архитектуры: Кристофер Александер в «A Pattern Language» (1977) описал паттерны как «решение повторяющейся проблемы в контексте». В 1994 году «Банда четырёх» (Gamma, Helm, Johnson, Vlissides) перенесла подход в ООП-проектирование.

Паттерн описывается четырьмя элементами:

| Элемент | Содержание |
|---|---|
| **Имя** | короткий термин для общения: «здесь нужен Observer» |
| **Задача** | в каком контексте возникает проблема и какие силы конфликтуют |
| **Решение** | структура классов и объектов, распределение обязанностей |
| **Последствия** | что выигрываем, чем платим, какие ограничения появляются |

Паттерн — **не библиотека и не фрагмент кода**. Один и тот же паттерн в C++ и в Java выглядит по-разному: в C++ стратегию часто делают шаблонным параметром, в Java — интерфейсом и объектом.

---

## 2. Каталог GoF: 23 паттерна в трёх группах

| Группа | Назначение | Паттерны |
|---|---|---|
| **Порождающие** (5) | как создавать объекты, скрывая детали создания | Factory Method, Abstract Factory, Builder, Prototype, Singleton |
| **Структурные** (7) | как складывать объекты в более крупные структуры | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **Поведенческие** (11) | как распределять обязанности и взаимодействие | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

Деление условное: цель паттерна важнее его категории, а многие паттерны отличаются друг от друга только нюансами (Strategy и State, Decorator и Proxy).

---

## 3. Зачем их используют

1. **Словарь.** «Обернуть в Decorator» короче и точнее, чем абзац объяснений; на ревью и на собеседовании это экономит время.
2. **Переиспользование проверенных решений.** Паттерн уже содержит типичные ошибки и ограничения, на которые указали до вас.
3. **Ослабление связности.** Почти все паттерны вводят уровень косвенности, который убирает жёсткие зависимости между частями системы.
4. **Расширяемость.** Strategy, Decorator, Visitor позволяют добавлять поведение без правки существующего кода (принцип открытости/закрытости).
5. **Обучение проектированию.** Изучая паттерны, новичок видит, как опытные разработчики раскладывают обязанности.

Обратная сторона: паттерн добавляет классы, интерфейсы и переходы по указателям. Если задача простая, паттерн делает код **хуже** — сложнее, медленнее, запутаннее.

---

## 4. Паттерн, идиома и архитектурный стиль

| Уровень | Что это | Примеры |
|---|---|---|
| Архитектурный стиль | структура всей системы | MVC, слоистая архитектура, микросервисы, event-driven |
| Паттерн проектирования | взаимодействие классов в рамках подсистемы | Strategy, Observer, Factory Method |
| Идиома языка | характерный приём конкретного языка | RAII, copy-and-swap, NVI, pimpl, CRTP, SFINAE |
| Антипаттерн | частое, но вредное решение | God Object, спагетти-код, копипаста |

Идиомы C++ (RAII, pimpl, CRTP) формально не входят в каталог GoF: они завязаны на механику языка, а не только на ООП-структуру.

---

## 5. Как паттерн выглядит в современном C++

Многие паттерны GoF родились в эпоху, когда не было лямбд, `std::function` и `std::variant`. Сегодня их часто реализуют компактнее:

| Паттерн | Классическая реализация | Современная альтернатива |
|---|---|---|
| Strategy | иерархия классов + указатель | `std::function`, лямбда, шаблонный параметр |
| Command | иерархия классов | `std::function` + захват состояния |
| Visitor | двойная диспетчеризация | `std::variant` + `std::visit` |
| Observer | список указателей на интерфейс | `std::function`-колбэки, сигналы |
| Iterator | класс с `begin`/`end` | диапазоны и ranges (C++20) |
| Singleton | статический указатель + ленивая инициализация | локальная статическая переменная функции |

Пример: стратегия без единого наследника.

```cpp
#include <functional>
#include <string>
#include <utility>
#include <vector>

// «Стратегия» выражена через std::function: алгоритм — это параметр.
class Report {
public:
    using Renderer = std::function<std::string(const std::vector<int>&)>;

    explicit Report(Renderer r) : render_(std::move(r)) {}

    std::string render(const std::vector<int>& data) const {
        return render_(data);          // выбор алгоритма произошёл при создании
    }

private:
    Renderer render_;
};

// Использование: поведение задаётся лямбдой, иерархия классов не нужна.
Report plain([](const std::vector<int>& v) {
    return std::to_string(v.size()) + " items";
});
```

Классическая версия с базовым классом нужна, когда у стратегии есть состояние, несколько методов или когда её выбирают по типу во время выполнения через фабрику.

## 6. Пример разбора: Adapter

**Задача.** Есть сторонняя библиотека с методом `drawCircle(x, y, r)`, а приложение работает с интерфейсом `Shape::draw()`.

**Силы.** Менять библиотеку нельзя, переписывать клиентский код — дорого.

**Решение.** Класс-адаптер реализует целевой интерфейс и делегирует вызов.

```cpp
#include <memory>
#include <utility>

// Сторонний API, который нельзя менять.
class LegacyRenderer {
public:
    void drawCircle(double x, double y, double r) { /* ... */ }
};

// Целевой интерфейс приложения.
class Shape {
public:
    virtual ~Shape() = default;
    virtual void draw() const = 0;
};

class CircleAdapter : public Shape {
public:
    CircleAdapter(std::shared_ptr<LegacyRenderer> r, double x, double y, double rad)
        : renderer_(std::move(r)), x_(x), y_(y), r_(rad) {}

    void draw() const override { renderer_->drawCircle(x_, y_, r_); }  // делегирование

private:
    std::shared_ptr<LegacyRenderer> renderer_;
    double x_, y_, r_;
};
```

**Последствия:** плюс — совместимость без правок библиотеки и клиента; минус — лишний уровень косвенности и необходимость хранить параметры вызова.

## 7. Как выбирать паттерн

1. Сформулировать проблему **без** имени паттерна: «нужно менять алгоритм в рантайме».
2. Посмотреть, какие силы конфликтуют: расширяемость против простоты, гибкость против производительности.
3. Вспомнить 2–3 подходящих паттерна и сравнить **последствия**, а не только структуру.
4. Проверить, не решается ли задача проще: параметром шаблона, лямбдой, обычной функцией.
5. Если паттерн не окупается — не применять.

---

## Типичные ошибки

1. **Паттерн ради паттерна.** Появляются `AbstractSingletonProxyFactoryBean`-подобные конструкции там, где хватило бы функции.
2. **Путать паттерн с его реализацией.** «Strategy — это класс с виртуальным методом» неверно: это способ сделать алгоритм взаимозаменяемым.
3. **Игнорировать последствия.** У каждого паттерна есть цена: косвенность, аллокации, усложнение отладки.
4. **Применять паттерны Java-эпохи в C++**, где язык даёт более прямые средства (лямбды, `std::variant`, шаблоны).
5. **Считать, что паттерн гарантирует качество.** Плохо спроектированная система останется плохой, даже если в ней есть Observer.
6. **Не знать альтернатив.** На собеседовании ценится умение сказать, когда паттерн **не** нужен.

## Что добавить на собеседовании

- Паттерны связаны с SOLID: Strategy и Decorator реализуют принцип открытости/закрытости, Facade и Adapter уменьшают связанность, Singleton часто нарушает единственную ответственность и затрудняет тестирование.
- Полезно знать, что каталог GoF — не единственный: есть GRASP, POSA, enterprise-паттерны (Repository, Unit of Work, CQRS), интеграционные паттерны (Enterprise Integration Patterns).
- На собеседовании выигрышно звучит мысль: «Паттерн — это словарь для обсуждения, а не цель. Сначала решаю задачу, потом называю решение паттерном, если оно совпало».
- Стоит упомянуть, что в C++ многие паттерны «съедены» возможностями языка: шаблонами, лямбдами, `std::variant`, ranges.
