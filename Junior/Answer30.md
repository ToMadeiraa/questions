# Вопрос 30. Как защитить хедер от повторного включения?

> **Кратко:** обернуть всё содержимое заголовка в **include guard** — условную конструкцию `#ifndef` / `#define` / `#endif` с уникальным для этого файла макросом. При первом включении макрос ещё не определён, тело заголовка попадает в текст и макрос определяется; при повторном `#ifndef` ложно, и препроцессор не выдаёт из файла ни одного токена. Практическая альтернатива — `#pragma once`, но она не входит в стандарт C++.

---

## Include guard целиком

```cpp
// project/core/buffer.h
#ifndef PROJECT_CORE_BUFFER_H_
#define PROJECT_CORE_BUFFER_H_

#include <cstddef>

namespace project {

class Buffer {
public:
    explicit Buffer(std::size_t size);
    std::size_t size() const;

private:
    std::size_t size_;
};

}  // namespace project

#endif  // PROJECT_CORE_BUFFER_H_
```

Схема жёсткая: `#ifndef` — самая первая конструкция файла, `#define` — сразу за ней с **тем же** именем, `#endif` — последняя строка. Всё остальное содержимое оказывается между ними.

---

## Почему это работает

| Ситуация | Что видит препроцессор | Результат |
|---|---|---|
| Первое включение | `PROJECT_CORE_BUFFER_H_` не определён | тело вставлено, макрос определён |
| Повторное включение | макрос уже определён | группа `#ifndef` пропущена целиком |

Классический случай — «ромб»: `main.cpp` включает `a.h` и `b.h`, а оба включают `buffer.h`. Без защиты объявление класса попадёт в текст дважды, и компилятор скажет `redefinition of 'Buffer'`. С защитой второй экземпляр просто не появится.

Важно: заголовок должен быть **идемпотентным** — то, что он объявляет, обязано допускать повторную обработку. Guard решает только проблему повторной вставки текста в одной единице трансляции.

---

## Имя макроса: как не выстрелить себе в ногу

| Требование | Почему |
|---|---|
| Уникально в пределах проекта | совпадение имён — самая частая причина «пропавшего» заголовка |
| Построено из полного пути | `core/buffer.h` → `PROJECT_CORE_BUFFER_H_` |
| Только заглавные буквы, цифры, `_` | обычная практика, читается глазом |
| Без ведущего `_` и без `__` | такие имена зарезервированы за реализацией |
| Одинаково в `#ifndef`, `#define` и комментарии | рассинхронизация ломает защиту |

`clang` предупреждает о расхождении имён флагом `-Wheader-guard`, а `clang-tidy` умеет проверять и генерировать guard целиком (`llvm-header-guard`).

## Что ломает защиту

```cpp
// a.h
#ifndef PROJECT_A_H_
#define PROJECT_A_H_
struct A { int x; };
#endif
```

```cpp
// b.h — скопировали шапку и забыли переименовать
#ifndef PROJECT_A_H_          // должно быть PROJECT_B_H_
#define PROJECT_A_H_
struct B { int y; };          // если a.h уже включён, B не будет объявлен вообще
#endif
```

Такой заголовок компилируется «в одиночку» и молча исчезает в реальной сборке — ошибка проявляется как `unknown type name 'B'` в чужом файле.

Другие способы сломать защиту:

| Ошибка | Симптом |
|---|---|
| Guard охватывает только часть файла | часть объявлений дублируется |
| `#ifndef X_H` + `#define Y_H` | защита не работает, всё дублируется |
| `#endif` стоит раньше конца файла | «хвост» включается повторно |
| Кто-то сделал `#define PROJECT_A_H_` до включения | заголовок выключен целиком |
| Guard стоит после `#include` другого файла | цикл включений не рвётся на первой строке |

## `#pragma once`

```cpp
#pragma once     // первая строка файла, до любых объявлений
struct Buffer { /* ... */ };
```

| Свойство | Include guard | `#pragma once` |
|---|---|---|
| Стандарт | да, обычные директивы препроцессора | нет: `#pragma` implementation-defined |
| Поддержка | везде | GCC, Clang, MSVC, Intel — фактически везде |
| Критерий | имя макроса | идентичность файла (устройство/inode или путь) |
| Коллизии имён | возможны | невозможны |
| Копии и хардлинки файла | работают | считаются разными файлами |
| Симлинки | не важно | современные компиляторы распознают |
| Скорость | файл всё равно читается и лексится | повторное включение пропускается без чтения |
| PCH и инструменты | поддерживаются | поддерживаются |

Практический вывод: `#pragma once` — лучший выбор по умолчанию, но если проект должен собираться неопределённым зоопарком компиляторов, оставляют guard. Совмещать их допустимо: `#pragma once` первой строкой плюс обычный guard — поведение корректно в любом случае, цена — одна лишняя строка.

## Чего guard не делает: ODR

Include guard действует **внутри одной единицы трансляции**. Он никак не мешает включить тот же заголовок в сотню `.cpp` — для объявлений это нормально, но определения с внешним связыванием так писать нельзя.

```cpp
// config.h — guard есть, но ODR он не спасает
#ifndef PROJECT_CONFIG_H_
#define PROJECT_CONFIG_H_
int counter = 0;           // multiple definition: своё определение в каждой .cpp
inline int counter2 = 0;   // правильно (C++17): одно определение на программу
#endif
```

| Что в заголовке | Как оформлять |
|---|---|
| `class`, `struct`, `enum`, шаблоны | как есть: повторное определение в разных TU разрешено |
| `inline`-функция, шаблон функции | `inline` или шаблон |
| Глобальная переменная | `inline` (C++17) или `extern` + определение в одном `.cpp` |
| Константа | `inline constexpr`; `constexpr` в заголовке и так имеет внутреннее связывание |
| `static`-переменная | избегать: получится своя копия в каждой единице трансляции |

## Циклические включения

Guard обрывает бесконечную рекурсию, но **не делает циклические зависимости корректными**:

```cpp
// a.h включает b.h, b.h включает a.h
// Порядок: a.h -> A_H_ определён -> b.h -> a.h пропущен -> b.h видит неполный A
```

В результате `b.h` не знает о типе `A` и падает с `unknown type name`. Лечится не защитой, а разрывом зависимости: предварительным объявлением (`class A;`) и переносом `#include` в `.cpp`, где нужен полный тип.

---

## Альтернатива: модули C++20

```cpp
export module project.buffer;   // импортируется один раз, повторный import безвреден

export class Buffer { /* ... */ };
```

Модуль компилируется отдельно, а `import` идемпотентен по определению: ни guard, ни `#pragma once` не нужны. Пока модули не вытеснили `#include`, защита заголовков остаётся обязательной дисциплиной.

---

## Как проверить, что защита работает

Каждый заголовок должен компилироваться **первым**: свой `#include` ставят первой строкой в соответствующем `.cpp` — это проверяет и самодостаточность, и срабатывание guard. Команда `g++ -H main.cpp` показывает, сколько раз файл реально открывался, а `g++ -E main.cpp | grep -c "class Buffer"` должна дать ровно единицу.

## Типичные ошибки

1. **Одинаковое имя guard в двух заголовках** после copy-paste — второй файл молча выпадает из сборки.
2. **Забыть `#endif`** или поставить его в середине файла — часть объявлений дублируется либо отрезается.
3. **Ожидать, что guard вылечит циклические включения** — он лишь превращает бесконечность в ошибку типа.
4. **Писать `#define __BUFFER_H__`** — имена с `__` и с `_` + заглавная буква зарезервированы реализацией.

---

## Что добавить на собеседовании

- Чётко разделить две задачи: guard защищает **текст** от повторной вставки в одной TU, ODR-правила — от множественных определений в программе. Это разные механизмы, и путать их — типичная ошибка.
- Назвать стоимость: без `#pragma once` компилятор каждый раз читает и лексит файл, чтобы найти `#ifndef`; с ним повторное включение пропускается целиком.
- Упомянуть, что guard — одна из немногих областей, где макросы по-прежнему безальтернативны.
- Хороший финал: «По умолчанию — `#pragma once`, плюс guard для переносимости; в перспективе — модули, где проблемы повторного включения не существует».

## Итог

| Аспект | Суть |
|---|---|
| Механизм | `#ifndef` / `#define` / `#endif` вокруг всего файла |
| Что защищает | повторную вставку текста заголовка в одной единице трансляции |
| Имя макроса | уникальное, из полного пути, без `__` и ведущего `_` |
| Альтернатива | `#pragma once` — быстрее и без коллизий, но вне стандарта |
| Чего не делает | не решает ODR, не устраняет циклические зависимости |
| Практика | guard + `#pragma once`, проверка сборкой заголовка первым |
