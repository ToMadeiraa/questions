# Вопрос 33. Как static влияет на глобальные/локальные переменные?

> **Кратко:** `static` меняет либо **время жизни**, либо **связывание** — в зависимости от места объявления. У локальной переменной он даёт статическое время жизни: объект создаётся один раз и живёт до конца программы. У переменной или функции на уровне файла — внутреннее связывание: имя видно только в своей единице трансляции. Внутри класса `static` означает принадлежность классу, а не конкретному объекту.

---

## Три роли одного слова

| Где стоит `static` | Что меняет | Ключевой эффект |
|---|---|---|
| локальная переменная в функции | время жизни (storage duration) | создаётся один раз, живёт до конца программы |
| переменная/функция в области файла | связывание (linkage) | внутреннее: имя не экспортируется из единицы трансляции |
| член класса: данные | принадлежность | одна переменная на класс, а не на объект |
| член класса: функция | отсутствие `this` | вызов без объекта |

---

## Локальная static: статическое время жизни

```cpp
#include <cstdio>

int nextId() {
    static int counter = 0;    // инициализация — ровно один раз, при первом входе
    return ++counter;
}

int main() {
    std::printf("%d\n", nextId());   // 1
    std::printf("%d\n", nextId());   // 2
}
```

Свойства:

- объект создаётся при **первом** проходе через объявление, а не при каждом вызове;
- живёт до конца программы и уничтожается при выходе из `main` (в обратном порядке создания);
- инициализация **потокобезопасна** с C++11: компилятор вставляет скрытую защиту (в Itanium ABI — `__cxa_guard_acquire`/`__cxa_guard_release`);
- если инициализация бросила исключение, она будет повторена при следующем входе;
- если инициализатор — константное выражение, инициализация выполняется на этапе загрузки, без охраны и без накладных расходов.

| Свойство | Автоматическая (`int x`) | Локальная `static` | Глобальная |
|---|---|---|---|
| Время жизни | до конца блока | до конца программы | до конца программы |
| Инициализация | при каждом входе | один раз | до `main` |
| Потоков | своя у каждого | общая | общая |

> **Важно:** потокобезопасна только **инициализация**. Дальше за общий объект отвечает программист: `static int counter` в многопоточной функции без мьютекса — гонка данных.

## static на уровне файла: внутреннее связывание

```cpp
// counter.cpp
static int g_counter = 0;              // внутреннее связывание: имя не покидает TU

static void reset() { g_counter = 0; } // функция тоже не экспортируется

void bump() { ++g_counter; }           // эта функция — внешняя, её видно снаружи
```

Другой `.cpp` может объявить собственный `static int g_counter` — конфликта не будет: это разные объекты с независимым состоянием. Так же и `static`-функции: две единицы трансляции могут содержать одноимённые `static void helper()`.

| Форма | Связывание | Видимость | Когда использовать |
|---|---|---|---|
| `int g;` в области файла | внешнее | вся программа | действительно общий объект |
| `static int g;` | внутреннее | одна TU | деталь реализации файла |
| `namespace { int g; }` | внутреннее | одна TU | предпочтительная современная запись |
| `inline int g;` (C++17) | внешнее, одно определение | вся программа | общая переменная в заголовке |

Для объектов в области видимости пространства имён `static` объявлен **устаревшим** (deprecated, приложение D стандарта): безымянный `namespace` даёт то же внутреннее связывание, но работает и для типов, и для шаблонов. Для функций `static` по-прежнему распространён и не устарел.

---

## static в классе

```cpp
class Widget {
public:
    Widget()  { ++alive_; }
    ~Widget() { --alive_; }

    static int alive() { return alive_; }   // вызов без объекта: Widget::alive()

private:
    inline static int alive_ = 0;           // C++17: определение прямо в классе
};
```

До C++17 требовалось отдельное определение в `.cpp`:

```cpp
// widget.h
class Widget {
    // ...
    static int alive_;        // только объявление
};

// widget.cpp
int Widget::alive_ = 0;       // единственное определение; без него — undefined reference
```

| | Обычное поле | `static`-поле | `static`-функция |
|---|---|---|---|
| Где хранится | внутри объекта | отдельно, на класс | кода не имеет состояния |
| Нужен объект | да | нет | нет |
| Влияет на `sizeof` | да | нет | нет |
| Виртуальной быть | — | — | нет |
| Типичное применение | состояние объекта | счётчики, константы, кэш | фабрики, колбэки без `this` |

`static`-функция-член не имеет `this`, поэтому не может обращаться к нестатическим членам и не может быть `const`/`volatile`/`virtual`. Зато её удобно передавать в C-API как колбэк: `std::atexit(&Widget::cleanup)`.

## static в шаблонах и с thread_local

```cpp
template <class T>
int& instanceCount() {
    static int count = 0;      // своя переменная для каждой инстанциации T
    return count;
}

thread_local int tls_counter = 0;   // отдельный объект в каждом потоке
```

Статический член шаблонного класса и локальная `static` в шаблонной функции существуют **в экземпляре на каждую специализацию**: `Counter<int>::value` и `Counter<double>::value` — разные объекты. `thread_local` комбинируется со `static`: у каждого потока своё состояние, время жизни — тоже до конца программы (у потока).

## static в заголовке и порядок инициализации

`static` в заголовке — классическая ловушка: каждая единица трансляции получает **свою копию**.

```cpp
// bad.h
static int g_requests = 0;   // у каждого .cpp своя переменная: счётчик «не растёт»

// good.h
inline int g_requests = 0;   // C++17: один объект на программу
// или
extern int g_requests;       // объявление; определение — в одном .cpp
```

Вторая проблема глобальных объектов — **порядок инициализации** между единицами трансляции не определён:

```cpp
// a.cpp
Logger g_logger;

// b.cpp
Config g_config(g_logger);   // может выполниться раньше инициализации g_logger
```

Стандартное решение — инициализация по требованию через локальную `static`:

```cpp
Logger& logger() {
    static Logger instance;   // создаётся при первом обращении, порядок гарантирован
    return instance;
}
```

---

## Типичные ошибки

1. **`static` в заголовке как «общая» переменная.** Получается копия в каждой единице трансляции — счётчик не растёт, состояние расходится.
2. **Ожидание, что локальная `static` инициализируется при каждом вызове** или сбрасывается при выходе из функции.
3. **Забытое определение статического члена класса** (до C++17) — `undefined reference` на этапе линковки.
4. **Обращение к нестатическим членам из `static`-функции** — нет `this`, компилятор справедливо ругается.
5. **Путать `static` с `const`.** `static` не делает объект неизменяемым и не даёт потокобезопасности.
6. **Считать, что защита инициализации защищает данные.** Гонка при последующих обращениях остаётся.
7. **Использовать `static`-объект из деструктора другого статического объекта** после его уничтожения — UB.
8. **Думать, что в рекурсивной функции `static` своя на каждый вызов.** Она одна на всю программу.

## Что добавить на собеседовании

- Сразу разделить три роли: время жизни, связывание, принадлежность классу — это главный критерий понимания.
- Назвать гарантию C++11: инициализация локальной `static` потокобезопасна, а вот её использование — нет.
- Объяснить, что скрытая охрана инициализации — это реальные накладные расходы, и для константных инициализаторов её нет.
- Упомянуть проблему порядка инициализации и каноническое решение через функцию с локальной `static`.
- Сказать про `inline`-переменные (C++17) и безымянный `namespace` как современную замену `static` в заголовках и на уровне файла.

## Итог

| Где `static` | Что даёт | Подвох |
|---|---|---|
| локальная переменная | одно создание, жизнь до конца программы | общая для всех вызовов и потоков |
| глобальная переменная/функция | внутреннее связывание, изоляция TU | копия в каждой TU, если попала в заголовок |
| член класса (данные) | одно состояние на класс | нужно определение (до C++17), не входит в `sizeof` |
| член класса (функция) | вызов без объекта, колбэки | нет `this`, нельзя `const`/`virtual` |
| в шаблоне | отдельный объект на специализацию | легко принять за единый счётчик |
| `thread_local static` | своё состояние в каждом потоке | время жизни привязано к потоку |
