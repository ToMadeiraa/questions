# 136. Как избежать состояния гонки (race condition) в C++

**Состояние гонки (race condition)** — ситуация, когда результат программы зависит от порядка выполнения нескольких потоков, обращающихся к общим данным без должной синхронизации. Чаще всего проявляется как **data race** — одновременное чтение и запись (или две записи) одной и той же ячейки памяти без синхронизации. В C++ это неопределённое поведение (UB).

Ниже — основные способы предотвращения.

---

## 1. Мьютексы (`std::mutex`, `std::recursive_mutex`, `std::shared_mutex`)

Самый базовый способ — защитить критическую секцию блокировкой. В C++11+ используйте RAII-обёртки, чтобы блокировка снималась при исключениях.

```cpp
#include <mutex>

std::mutex mtx;
int counter = 0;

void safe_increment() {
    std::lock_guard<std::mutex> lock(mtx); // блокировка снимается автоматически
    ++counter;
}
```

Варианты RAII-обёрток:

- `std::lock_guard` — простая блокировка на время жизни объекта;
- `std::unique_lock` — гибкая: можно откладывать захват, разблокировать вручную, использовать с condition_variable;
- `std::scoped_lock` (C++17) — для захвата **нескольких** мьютексов без дедлоков;
- `std::shared_lock` (C++14) — разделяемая блокировка для `std::shared_mutex` (много читателей / один писатель).

```cpp
// C++17: захват нескольких мьютексов без взаимной блокировки
std::scoped_lock lock(mtx1, mtx2);
```

**Правила:**
- никогда не забывайте про RAII (не вызывайте `lock()`/`unlock()` вручную);
- минимизируйте критическую секцию — не держите мьютекс во время долгих операций, I/O, вызовов чужих функций;
- соблюдайте единый порядок захвата мьютексов, чтобы избежать **дедлоков**.

---

## 2. Атомарные операции (`std::atomic`)

Для простых операций (счётчики, флаги) атомики дешевле мьютекса и не блокируют поток.

```cpp
#include <atomic>

std::atomic<int> counter{0};

void safe_increment() {
    counter.fetch_add(1, std::memory_order_relaxed); // или просто counter++
}
```

Важно правильно выбирать **модель памяти** (`std::memory_order`):

- `memory_order_relaxed` — только атомарность, без упорядочивания (для счётчиков);
- `memory_order_acquire` / `memory_order_release` — для передачи данных между потоками (флаг готовности + данные);
- `memory_order_seq_cst` — по умолчанию, самое строгое.

```cpp
std::atomic<bool> ready{false};
int data = 0;

// Поток-производитель
data = 42;
ready.store(true, std::memory_order_release);

// Поток-потребитель
while (!ready.load(std::memory_order_acquire)) { /* ждём */ }
assert(data == 42); // гарантировано
```

Атомики защищают **одну переменную**, но не составные инварианты из нескольких переменных — для них нужен мьютекс.

---

## 3. Условные переменные (`std::condition_variable`)

Для ожидания события (очередь не пуста, задача завершена) — в паре с мьютексом. Позволяют избежать «busy-wait» (активного ожидания).

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;

void producer() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        q.push(42);
    }
    cv.notify_one();
}

void consumer() {
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [] { return !q.empty(); }); // защита от ложных пробуждений
    int value = q.front();
    q.pop();
}
```

Всегда используйте предикат в `wait`, чтобы корректно обрабатывать **ложные пробуждения** (spurious wakeups).

---

## 4. Проектирование без разделяемого изменяемого состояния

Лучшая гонка — та, которой нет. Подходы:

- **Иммутабельность**: передавайте данные только для чтения (`const`, `std::shared_ptr<const T>`), не изменяйте их после публикации.
- **Локальные данные потока** (`thread_local`): каждый поток работает со своей копией.
- **Копирование вместо разделения**: передавайте данные по значению или через `std::move`.
- **Message passing**: потоки общаются через очереди сообщений, а не через общую память.
- **Изоляция по владению**: каждая структура данных принадлежит одному потоку (акторная модель).

---

## 5. Правильная публикация объектов между потоками

Даже создание объекта в одном потоке и использование в другом требует синхронизации, иначе другой поток может увидеть **частично сконструированный** объект.

```cpp
// Плохо: data race на указателе и на объекте
Widget* w = nullptr;

// Поток 1
w = new Widget();        // запись

// Поток 2
if (w) w->doSomething(); // чтение — UB
```

Решения:
- публикуйте через `std::atomic<Widget*>`;
- используйте `std::call_once` / `std::once_flag` для однократной инициализации;
- `std::promise` / `std::future` для передачи результата;
- мьютекс или атомик с `release`/`acquire` вокруг публикации.

```cpp
std::once_flag flag;
std::unique_ptr<Widget> w;

void init() {
    std::call_once(flag, [] { w = std::make_unique<Widget>(); });
}
```

## 6. Инструменты обнаружения гонок

Даже аккуратный код стоит проверять:

- **ThreadSanitizer** (`-fsanitize=thread` в GCC/Clang) — находит data races на этапе выполнения;
- **Helgrind** (Valgrind) — анализ блокировок и гонок;
- статические анализаторы (Clang-Tidy, PVS-Studio, Coverity);
- стресс-тесты и запуск под нагрузкой.

```bash
g++ -fsanitize=thread -g -O1 program.cpp -o program -pthread
./program
```

---

## 7. Общие рекомендации

1. **Минимизируйте общее изменяемое состояние** — это главный принцип.
2. **Один объект — один владелец**; делитесь только тем, что действительно нужно.
3. **Инкапсулируйте синхронизацию** внутри класса, не размазывайте мьютексы по коду.
4. **Не удерживайте блокировки дольше необходимого** и не вызывайте под ними чужой код (риск дедлока).
5. **Документируйте** модель потокобезопасности: какие методы можно звать параллельно, какие — нет.
6. **Предпочитайте высокоуровневые примитивы**: `std::async`, `std::future`, пулы задач, параллельные алгоритмы C++17 (`std::execution::par`) — вместо ручного управления потоками.
7. **Помните о ложном разделении (false sharing)**: рядом лежащие в памяти атомики разных потоков могут тормозить — используйте выравнивание (`alignas(64)`).

## Итоговая таблица

| Ситуация | Инструмент |
|---|---|
| Счётчик, флаг | `std::atomic` |
| Составные данные, инварианты | `std::mutex` + `lock_guard` |
| Много читателей / редкая запись | `std::shared_mutex` + `shared_lock` |
| Ожидание события | `std::condition_variable` |
| Однократная инициализация | `std::call_once` / `once_flag` |
| Передача результата между потоками | `std::promise` / `std::future` |
| Нет общего состояния вообще | иммутабельность, message passing, `thread_local` |
| Проверка кода | ThreadSanitizer, Helgrind, статанализ |

**Ключевая мысль:** избежать гонки проще всего, устранив разделяемое изменяемое состояние; если это невозможно — защитите его минимальным по объёму и правильно выбранным примитивом синхронизации и обязательно проверьте код санитайзерами.
