# Вопрос 43. Где может храниться переменная?

> **Кратко:** Стандарт C++ говорит не о «месте», а о **времени жизни** объекта: автоматическое, статическое, потоковое (`thread_local`) и динамическое. Физически это соответствует стеку, сегментам данных (`.data`, `.bss`, `.rodata`), куче и TLS-блоку потока; отдельно стоит регистр процессора — компилятор вправе вообще не выделять память, если адрес объекта не наблюдается. Важно разделять три независимых свойства: сколько объект живёт, откуда видно его имя и в какой области памяти он лежит.

---

## Три разных свойства, которые часто путают

| Свойство | Что определяет | Пример |
|---|---|---|
| Время жизни (storage duration) | когда объект создан и когда разрушен | `int x;` — автоматическое |
| Область видимости (scope) | откуда доступно имя | блок `{}`, пространство имён, класс |
| Компоновка (linkage) | видно ли имя в других единицах трансляции | `extern int g;`, `static int s;` |

Переменная может быть видна в одном файле, но жить всю программу (глобальная `static`), или быть видимой во всём проекте и жить всю программу (`extern`). «Где хранится» — свойство реализации, «сколько живёт» — свойство языка.

---

## Четыре вида времени жизни

| Время жизни | Где создаётся | Когда разрушается | Пример |
|---|---|---|---|
| Автоматическое | стек (или регистр) | при выходе из блока | локальная переменная, параметр |
| Статическое | `.data` / `.bss` / `.rodata` | при завершении программы | глобальная, `static` локальная |
| Потоковое | TLS-блок потока | при завершении потока | `thread_local` |
| Динамическое | куча | по `delete` / `free` | `new`, `malloc` |

---

## Стек: автоматические переменные

Каждый вызов функции получает **кадр** (activation record): в нём лежат параметры, локальные объекты, сохранённые регистры и адрес возврата. Стек растёт вниз, а освобождение кадра — это просто сдвиг указателя стека, поэтому аллокация на стеке почти бесплатна и идеальна по локальности.

```cpp
int sum(int n) {
    if (n <= 0) return 0;
    int partial = n + sum(n - 1);   // у каждого вызова свой кадр со своим partial
    return partial;
}
```

Размер стека ограничен: типично 8 МБ для главного потока в Linux (`ulimit -s`) и 1 МБ в Windows по умолчанию; у создаваемых потоков размер задаётся при создании. Глубокая рекурсия или большой локальный массив переполняют стек — это аварийное завершение, а не исключение.

Массивы переменной длины (`int a[n];`) в C++ не входят в стандарт: это расширение GCC/Clang. Практическая замена — `std::vector` (куча) или `std::array` с константным размером (стек).

## Статическая память: `.data`, `.bss`, `.rodata`

```cpp
#include <cstdint>

int  g_initialized = 42;         // .data: начальное значение есть в файле
int  g_zero;                     // .bss: нулевое значение, места в файле не занимает
const char* g_name = "answer";   // указатель в .data, сам литерал — в .rodata
constexpr int kLimit = 100;      // константа времени компиляции, обычно .rodata

void f() {
    static int calls = 0;        // создаётся один раз, живёт до конца программы
    ++calls;
}
```

| Сегмент | Что попадает | Символ в `nm` |
|---|---|---|
| `.text` | код функций | `T` / `t` |
| `.rodata` | строковые литералы, таблицы виртуальных функций, `const`-данные | `R` / `r` |
| `.data` | инициализированные статические данные | `D` / `d` |
| `.bss` | статические данные без инициализатора (нули) | `B` / `b` |

Проверить это можно командой вида `nm -C app | grep g_zero` — символ окажется помечен `B`, а размеры сегментов покажет `size app` (колонки `text`, `data`, `bss`).

**Инициализация статических объектов:**

- все статические объекты обнуляются **до** запуска программы, ещё до любых конструкторов;
- объекты с динамической инициализацией (нетривиальный конструктор) инициализируются при старте, и порядок между единицами трансляции не определён — это *static initialization order fiasco*. Отчасти лечится «функцией-локальной статикой» или `constinit` (C++20) там, где хватает константной инициализации.

```cpp
struct Registry {
    Registry()  { /* ... */ }
    ~Registry() { /* ... */ }
};

Registry& registry() {
    static Registry instance;   // создаётся при первом вызове, с C++11 потокобезопасно
    return instance;            // разрушится при завершении программы
}
```

С C++11 инициализация локальной статики защищена блокировкой («magic statics»), но каждый вход в функцию после этого проверяет флаг — на горячем пути это заметно.

## Куча: динамические объекты

```cpp
#include <cstdint>
#include <string>

void g() {
    auto* buffer = new std::uint8_t[1024];  // объект в куче, указатель — на стеке
    // ...
    delete[] buffer;                        // время жизни задаём мы

    std::string shortName = "ok";           // символы внутри объекта (SSO), на стеке
    std::string longName(100, 'x');         // буфер вынесен в кучу
}
```

Куча даёт гибкость, но стоит дороже: аллокатор хранит метаданные (обычно 8–16 байт на блок), возможна фрагментация, а общий аллокатор синхронизирует потоки. Именно поэтому небольшие объекты и строки реализуют с оптимизацией малых размеров прямо в объекте.

## TLS: `thread_local`

```cpp
thread_local int counter = 0;   // у каждого потока своя копия

void bump() { ++counter; }
```

Потоковая переменная лежит в блоке, привязанном к потоку (TLS), и разрушается при его завершении. Обращение к ней дороже обычного глобала: в общем случае компилятор вызывает `__tls_get_addr`, хотя для статически слинкованных моделей доступа хватает пары инструкций. TLS уместен там, где раньше был глобальный `errno` или кэш «на поток».

## Регистры и память устройства

```cpp
int square(int x) { return x * x; }   // x, скорее всего, вообще не попадёт в память
```

По правилу *as-if* компилятор вправе держать переменную в регистре или выбросить её, если поведение программы не меняется. Как только берётся адрес (`&x`), объект обязан получить место в памяти.

Ключевое слово `register` удалено из языка в C++17: это была лишь подсказка, а адрес такой переменной брать запрещалось. Отдельный случай — регистры устройств, где память нельзя кэшировать:

```cpp
#include <cstdint>

// Пример для микроконтроллера: адрес условный, в реальном коде берётся из заголовков вендора
volatile std::uint32_t* const statusReg =
    reinterpret_cast<volatile std::uint32_t*>(0x40000000u);

void waitReady() {
    while ((*statusReg & 1u) == 0) {
        // volatile запрещает «оптимизировать» цикл и кэшировать значение в регистре
    }
}
```

## Что от этого зависит на практике

| Место | Стоимость | Риски |
|---|---|---|
| Стек | сдвиг указателя, идеальная локальность | ограниченный размер, переполнение |
| Куча | десятки–сотни наносекунд, метаданные, фрагментация | утечки, висячие указатели |
| `.data` / `.bss` | бесплатно при старте | глобальное состояние, порядок инициализации |
| `.rodata` | бесплатно, доступ только на чтение | попытка записи в литерал — UB |
| TLS | дороже обычного глобала | рост памяти на каждый поток |

Практическое правило: по умолчанию — автоматическое время жизни и value-семантика; статическое — для констант и небольших неизменяемых таблиц; куча — только когда размер неизвестен заранее, объект большой или время жизни переживает создателя.

## Типичные ошибки

1. **Возврат указателя на локальную переменную** — объект уже разрушен, разыменование даёт UB.
2. **Считать, что куча обнулена** — `new int;` и `malloc` дают неинициализированную память.
3. **Большие массивы на стеке** — переполнение стека вместо исключения `std::bad_alloc`.
4. **Полагаться на порядок инициализации глобальных объектов из разных файлов**.
5. **Путать «видно в файле» и «живёт всю программу»**: `static` локальная — обе характеристики сразу, а у глобальной `static` различаются область видимости и linkage.
6. **Писать в строковый литерал** в `.rodata` через `char*` — UB, на современных платформах падение.
7. **Считать `thread_local` бесплатным** и ставить его в горячий цикл.

---

## Что добавить на собеседовании

- Стандарт C++ не упоминает «стек» и «кучу»: это термины реализации, язык определяет только время жизни, поэтому переносимый код не должен зависеть от сегментов.
- Стоит явно назвать связку «время жизни ↔ порядок разрушения»: локальные объекты разрушаются в обратном порядке создания, статические — при завершении программы, `thread_local` — при выходе из потока.
- Уместно вспомнить RAII: время жизни ресурса привязывают к времени жизни объекта, и тогда вопрос «где лежит» перестаёт влиять на корректность.
- Хороший признак глубины — назвать `constinit` (C++20) как лекарство от порядка инициализации и SSO как пример того, что «строка на стеке» может не иметь буфера в куче.

## Итог

| Время жизни | Типичное место | Кто освобождает | Пример |
|---|---|---|---|
| Автоматическое | стек или регистр | выход из блока | локальная переменная |
| Статическое | `.data` / `.bss` / `.rodata` | среда выполнения при завершении | глобальная, `static` локальная |
| Потоковое | TLS-блок потока | завершение потока | `thread_local` |
| Динамическое | куча | вручную или умный указатель | `new`, `malloc` |
