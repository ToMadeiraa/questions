# 91. Можно ли выбрасывать исключения из деструктора в C++?

**Краткий ответ:** Технически можно, но **категорически не рекомендуется**, и на практике это почти всегда приводит к завершению программы.

Начиная со стандарта C++11, деструкторы по умолчанию имеют спецификацию `noexcept(true)`. Это означает, что если исключение покинет деструктор, программа немедленно вызовет `std::terminate()` (что обычно приводит к аварийному завершению через `std::abort()`) .

## Почему это опасно?

Основная проблема связана с механизмом **развёртывания стека (stack unwinding)**.

1.  **Сценарий с уже активным исключением:** Представьте, что в программе возникло исключение. Начинается развёртывание стека — уничтожение локальных объектов. Если в этот момент деструктор одного из объектов сам выбрасывает исключение, возникает ситуация «двух одновременных исключений». Стандарт C++ требует, чтобы в этом случае вызывалась функция `std::terminate()`, так как программа не может корректно обработать два исключения одновременно .
2.  **Сценарий без активного исключения:** Даже если деструктор вызывается в «мирное» время (не во время развёртывания стека), и вы явно указали `noexcept(false)`, чтобы позволить ему выбрасывать исключения, это всё равно считается крайне плохой практикой. Это нарушает гарантии безопасности исключений (exception safety) и может привести к утечкам ресурсов, так как оставшиеся объекты не будут уничтожены .

## Что говорит стандарт?

Согласно стандарту C++, деструктор, объявленный без спецификации исключений, неявно считается `noexcept(true)` . Если вы попытаетесь выбросить исключение из такого деструктора, компилятор сгенерирует код, который вызовет `std::terminate`.

## Как правильно обрабатывать ошибки в деструкторе?

Поскольку деструкторы не могут безопасно сообщать об ошибках через исключения, существуют другие подходы:

1.  **Подавление исключений:** Внутри деструктора можно перехватить все исключения с помощью `try { ... } catch (...) { ... }` и просто проигнорировать их (например, записав в лог).
2.  **Явный `noexcept(false)` (крайне редко):** Если вы абсолютно уверены, что деструктор вызывается не во время развёртывания стека, и хотите использовать исключения для каких-то специфических целей, можно объявить деструктор как `noexcept(false)`. Однако это перекладывает всю ответственность за корректность на плечи программиста и считается плохим тоном.
3.  **Функция `close()`:** Хорошей практикой является вынесение логики, которая может завершиться неудачей (например, закрытие файла с проверкой ошибок), в отдельный метод (например, `close()`), который пользователь должен вызвать явно. Деструктор же должен лишь проверить, был ли вызван `close()`, и если нет — просто освободить ресурсы без выброса исключений.

## Резюме

| Ситуация | Результат |
| :--- | :--- |
| Исключение вылетает из деструктора по умолчанию (`noexcept(true)`) | `std::terminate()` |
| Исключение вылетает из деструктора во время развёртывания стека (даже с `noexcept(false)`) | `std::terminate()` |
| Исключение вылетает из деструктора с `noexcept(false)` вне развёртывания стека | Исключение может быть поймано, но это плохая практика |

**Вывод:** Никогда не позволяйте исключениям покидать деструктор. Если операция в деструкторе может завершиться неудачей, обработайте ошибку внутри деструктора (например, залогируйте её) или предоставьте пользователю отдельный метод для выполнения опасных операций.
