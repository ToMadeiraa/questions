# Вопрос 39. Расскажите об этапах разработки библиотеки или программы.

> **Кратко:** разработка идёт по этапам: требования → проектирование → реализация → тестирование → документация → сборка и поставка → релиз → сопровождение. Это не водопад: этапы повторяются итерациями, а обратная связь с тестов и пользователей возвращает проект на предыдущие шаги. У библиотеки есть дополнительное ограничение — её код компилируют чужие проекты, поэтому публичный API и ABI приходится проектировать и поддерживать годами.

---

## 1. Требования и постановка задачи

Формулируются **функциональные** требования (что умеет) и **нефункциональные**: производительность, потребление памяти, переносимость, безопасность, лицензия.

Для библиотеки отдельно фиксируется:

- целевые платформы и компиляторы (MSVC/GCC/Clang и их версии);
- минимальный стандарт C++ (`C++17`, `C++20`);
- модель распространения: header-only, статическая или разделяемая библиотека;
- политика совместимости: допустимо ли ломать API в минорных версиях.

Ошибка этого этапа дороже всех остальных: неверно понятое требование превращается в переписывание архитектуры.

---

## 2. Проектирование архитектуры

Определяются модули, их ответственности и направления зависимостей; выбираются структуры данных и алгоритмы с учётом сложности; решается, как обрабатываются ошибки (исключения или коды возврата) и как устроена работа с потоками.

- зависимости направлены внутрь, к предметной модели, а не наружу;
- смена реализации не должна менять публичный интерфейс;
- платформенный код изолирован в нескольких точках, а не размазан по проекту.

---

## 3. Публичный API — главный этап для библиотеки

API — это контракт. Его проектируют раньше реализации и проверяют на примерах использования: если писать клиентский код неудобно, API ещё не готов.

| Принцип | Смысл |
|---|---|
| Минимализм | каждая публичная сущность — обязательство поддерживать её годами |
| RAII и value-семантика | ресурсы освобождает деструктор, копирование и перемещение предсказуемы |
| `const`-корректность | методы, не меняющие объект, помечены `const` |
| `noexcept` | явный контракт «не бросает» влияет на оптимизации и на `vector` |
| Единый стиль ошибок | исключения **или** коды/`expected`, но не оба сразу |
| Стабильный ABI | детали реализации спрятаны, изменение поля не ломает клиентов |

Классический приём сокрытия реализации — `pImpl` (pointer to implementation):

```cpp
// include/mylib/widget.hpp — публичный заголовок
#include <memory>

namespace mylib {

class Widget {
public:
    Widget();
    ~Widget();                              // определён в .cpp: там известен полный Impl
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;

    int size() const;

private:
    struct Impl;                            // детали скрыты от клиента
    std::unique_ptr<Impl> impl_;            // изменение Impl не ломает ABI
};

} // namespace mylib
```

---

## 4. Реализация

Код пишется по принятому стилю: именование, форматирование `clang-format`, обязательный `override`, запрет «голых» `new`/`delete`.

Контроль качества включается сразу:

- предупреждения компилятора как ошибки (`-Wall -Wextra -Werror`);
- статический анализ (`clang-tidy`, `cppcheck`, анализатор MSVC);
- санитайзеры в CI (`ASan`, `UBSan`, `TSan`);
- код-ревью для каждого изменения.

---

## 5. Тестирование

| Уровень | Что проверяет | Инструменты |
|---|---|---|
| Модульные | отдельная функция или класс | GoogleTest, Catch2, doctest |
| Интеграционные | взаимодействие модулей | те же фреймворки и тестовые стенды |
| Регрессионные | ранее найденный дефект не вернулся | тест на каждый исправленный баг |
| Фаззинг | устойчивость к «мусорному» вводу | libFuzzer, AFL |
| Бенчмарки | производительность не деградировала | Google Benchmark |

Тесты запускаются в CI на матрице «компилятор × стандарт × ОС», иначе переносимость остаётся обещанием.

---

## 6. Документация

- **README** — что это, зачем, как собрать, минимальный пример.
- **Справочник API** — назначение, параметры, исключения, потокобезопасность (Doxygen/Sphinx).
- **Руководство и примеры** — типовые сценарии, а не пересказ заголовков.
- **CHANGELOG** — что изменилось и что ломается при обновлении.
- **Политика версий** — сколько живут старые ветки.

---

## 7. Сборка и поставка

Сборка описывается декларативно и воспроизводимо. Стандарт де-факто для C++ — CMake с экспортом целей, чтобы клиент писал `target_link_libraries(app PRIVATE mylib::mylib)`:

```cmake
add_library(mylib src/mylib.cpp)
target_compile_features(mylib PUBLIC cxx_std_17)
target_include_directories(mylib PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>)

include(GNUInstallDirs)
install(TARGETS mylib EXPORT mylibTargets)
install(DIRECTORY include/ DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})
install(EXPORT mylibTargets NAMESPACE mylib::
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/mylib)
```

Дальше — публикация: Conan, vcpkg, системные пакеты. Номер версии должен задаваться в одном месте и подставляться в код, а не дублироваться в трёх файлах вручную.

---

## 8. Версионирование и совместимость

Принята схема SemVer: `MAJOR.MINOR.PATCH`.

| Компонент | Когда меняется | Совместимость |
|---|---|---|
| `MAJOR` | сломано API или ABI | клиенту нужна правка кода или пересборка |
| `MINOR` | добавлена функциональность | обратная совместимость сохраняется |
| `PATCH` | исправлены ошибки | поведение не меняется |

Разделяют **API-совместимость** (код клиента компилируется) и **ABI-совместимость** (клиент, собранный со старой версией, работает с новой разделяемой библиотекой). ABI ломают: изменение состава или порядка полей, добавление виртуальной функции, смена сигнатуры, смена настроек стандартной библиотеки. Отсюда `pImpl`, скрытая видимость символов и осторожность с `inline`-кодом в заголовках.

Устаревшее не удаляют сразу: помечают `[[deprecated("use parse_v2")]]`, держат один-два минорных релиза и пишут migration guide.

---

## 9. Релиз и сопровождение

Перед релизом — заморозка функциональности, полная матрица CI, проверка примеров, обновление CHANGELOG и версии, тег, сборка артефактов. После — release notes с явным разделом «breaking changes».

Сопровождение занимает основную часть жизни продукта: исправление дефектов, патчи безопасности, поддержка старых веток, постепенная депрекация и объявление End of Life с датой. Обратная связь с этого этапа становится входом для новых требований, и цикл замыкается.

---

## Чем библиотека отличается от программы

| Аспект | Программа | Библиотека |
|---|---|---|
| Пользователь | конечный пользователь | программист, который её подключает |
| Главный артефакт | исполняемый файл | заголовки + бинарник + CMake-пакет |
| Критичный контракт | поведение и UI | публичный API и ABI |
| Ломающие изменения | обычно допустимы | требуют мажорной версии |
| Тестирование | сценарии использования | плюс компиляция примеров и матрица компиляторов |

---

## Типичные ошибки

1. **Начинать с кода.** API, спроектированный «по ходу», неудобно расширять, и каждая правка становится ломающей.
2. **Нет версии и CHANGELOG.** Клиент не понимает, что изменилось и безопасно ли обновляться.
3. **Смешение стилей ошибок.** Часть функций бросает исключения, часть возвращает код — клиент не знает, что обрабатывать.
4. **Реализация течёт в заголовки.** Публичный заголовок тянет внутренние зависимости, замедляя сборку клиента.
5. **Нет CI-матрицы.** «У меня собирается» не означает «собирается на другом компиляторе».
6. **Игнорирование ABI.** Раздача разделяемой библиотеки, ломающей ABI между патчами.
7. **Документация после релиза.** Написанная «потом», она описывает уже не тот код.

---

## Что добавить на собеседовании

- Этапы — не водопад: «проектирование API» для библиотеки может занять больше времени, чем первая реализация.
- Стоимость ошибки растёт по ходу: правка требования — минуты, архитектуры — недели, опубликованного API — годы поддержки.
- Хороший ответ показывает разницу между «код работает» и «код поставляется»: сборка, упаковка, версия и документация — часть продукта.
- Уместно назвать инструменты: CMake, GoogleTest, Google Benchmark, clang-tidy, ASan/UBSan, Conan/vcpkg.

## Итог

| Этап | Суть в одном предложении |
|---|---|
| Требования | Зафиксировать, что и для кого делаем, включая ограничения платформ и стандарта |
| Проектирование | Разложить систему на модули и спроектировать публичный контракт |
| Реализация | Написать код под ревью, предупреждения и статический анализ |
| Тестирование | Доказать корректность модульными, интеграционными тестами и фаззингом |
| Документация | Сделать библиотеку применимой без чтения её исходников |
| Сборка и поставка | Дать воспроизводимую сборку и удобное подключение через пакет |
| Версионирование | Сохранить совместимость API/ABI и объяснить изменения в CHANGELOG |
| Сопровождение | Поддерживать, депрецировать и выводить из эксплуатации по плану |
