# Вопрос 12. Какая разница между модульными и интеграционными тестами?

> **Кратко:** Модульный тест проверяет один компонент в изоляции, подменяя все внешние зависимости заглушками. Интеграционный тест проверяет, что несколько реальных компонентов правильно работают **вместе**: согласованы контракты, запросы к БД, сериализация, конфигурация. Разница — в области проверки, степени изоляции, скорости и в том, какие дефекты ловит каждый уровень.

---

## Где проходит граница

Граница определяется не размером кода, а **числом реальных участников**: модульный тест проверяет ровно один модуль (всё остальное подменено), интеграционный — два и более реальных компонента, соединённых «как в бою» (класс + БД, сервис + очередь, парсер + файл). Тест класса, который ходит в реальную БД, — уже не модульный, даже если он маленький.

---

## Основное сравнение

| Критерий | Модульный тест | Интеграционный тест |
|---|---|---|
| Объект проверки | Одна функция, класс, метод | Совместная работа нескольких компонентов |
| Зависимости | Stub, fake, mock | Реальные: БД, ФС, сеть, брокер, время |
| Скорость | Миллисекунды, тысячи тестов за секунды | Секунды и десятки секунд |
| Детерминизм | Полный | Зависит от окружения и состояния данных |
| Локализация дефекта | Высокая: видно конкретный метод | Низкая: видно «связку», причина ищется вручную |
| Стоимость поддержки | Низкая | Выше: фикстуры, схема БД, контейнеры, очистка |
| Что ловит | Логические ошибки, границы, исключения | Несовпадение контрактов, SQL, сериализацию, wiring, миграции |
| Когда запускать | На каждое сохранение, в pre-commit | В CI, перед merge и релизом |
| Кто обычно пишет | Разработчик | Разработчик, QA, иногда отдельная команда |

## Пирамида тестов

```
        /\
       /e2e\          единицы: медленные, дорогие, хрупкие
      /------\
     /integr.\       десятки: проверяют стыки и инфраструктуру
    /----------\
   /   unit     \    сотни-тысячи: быстрые, точные, дешёвые
  /--------------\
```

Смысл пирамиды: основную массу проверок дают модульные тесты, интеграционные закрывают места, которые в изоляции проверить нельзя, end-to-end — небольшое число ключевых пользовательских сценариев. Перевёрнутая пирамида («ice-cream cone»: много e2e, мало unit-тестов) даёт медленный CI и невнятные падения.

---

## Что видит только интеграционный тест

| Дефект | Почему модульный тест его пропускает |
|---|---|
| Несовпадение контрактов между модулями | Обе стороны по отдельности корректны, ошибочна стыковка |
| Неверный SQL, схема, типы колонок | Заглушка репозитория «всегда возвращает пользователя» |
| Ошибки сериализации и кодировок | JSON/CSV в тесте не участвует |
| Ошибки конфигурации и DI-связывания | В тесте объекты собираются вручную |
| Транзакции, блокировки, изоляция | В фейке транзакций нет |
| Порядок миграций и совместимость схемы | Миграции не выполняются |
| Таймауты, ретраи, сетевые ошибки | Сети нет |

## Один сценарий на двух уровнях

**Модульный тест:** курс валют подменён заглушкой, проверяется только логика форматирования.

```cpp
#include <gtest/gtest.h>
#include <string>

// Шов для подмены: зависимость за интерфейсом
struct RateProvider {
    virtual ~RateProvider() = default;
    virtual double usdToEur() const = 0;
};

class PriceTag {
public:
    explicit PriceTag(const RateProvider& rates) : rates_(rates) {}

    std::string label(double usd) const {
        const int eur = static_cast<int>(usd * rates_.usdToEur() + 0.5);
        return std::to_string(eur) + " EUR";
    }

private:
    const RateProvider& rates_;
};

struct FixedRate : RateProvider {          // тест-дублёр, никакой сети
    double usdToEur() const override { return 0.5; }
};

TEST(PriceTagTest, RoundsConvertedPrice) {
    FixedRate rates;
    PriceTag tag{rates};
    EXPECT_EQ(tag.label(10.0), "5 EUR");
}
```

**Интеграционный тест:** два реальных компонента — сериализатор CSV и настоящая файловая система.

```cpp
#include <cstddef>
#include <filesystem>
#include <fstream>
#include <gtest/gtest.h>
#include <string>
#include <vector>

class CsvWriter {
public:
    explicit CsvWriter(std::filesystem::path path) : out_(path) {}

    void writeRow(const std::vector<std::string>& cells) {
        for (std::size_t i = 0; i < cells.size(); ++i) {
            if (i) out_ << ',';
            out_ << cells[i];
        }
        out_ << '\n';
    }

    bool ok() const { return out_.good(); }

private:
    std::ofstream out_;
};

TEST(ReportIntegrationTest, WritesRowsToRealFile) {
    const auto path = std::filesystem::temp_directory_path() / "dsh_report_it.csv";

    {
        CsvWriter writer{path};
        writer.writeRow({"name", "score"});
        writer.writeRow({"alice", "10"});
        ASSERT_TRUE(writer.ok());
    }                                       // поток закрыт

    std::ifstream in{path};
    std::vector<std::string> lines;
    for (std::string line; std::getline(in, line); )
        lines.push_back(line);

    ASSERT_EQ(lines.size(), std::size_t{2});
    EXPECT_EQ(lines[0], "name,score");
    EXPECT_EQ(lines[1], "alice,10");

    std::filesystem::remove(path);          // тест убирает за собой
}
```

Одна и та же функциональность проверяется на разных уровнях: первый тест отвечает на вопрос «правильно ли считается цена», второй — «правильно ли всё это попадает в файл».

## Как выбрать уровень

| Признак | Куда писать |
|---|---|
| Ветвления, границы, арифметика, парсинг | Модульный тест |
| Обработка исключений и кодов ошибок | Модульный тест |
| SQL-запросы, схема, миграции | Интеграционный тест |
| Сериализация в файл/сеть, кодировки | Интеграционный тест |
| Сборка объекта через DI-контейнер | Интеграционный (или smoke) тест |
| Пользовательский сценарий от UI до БД | E2E, в малом количестве |

Практическое правило: **логику — в unit, стыки — в integration**. Если для «модульного» теста нужны БД или сеть, это интеграционный тест, который стоит держать отдельно и запускать реже.

---

## Типичные ошибки

1. **Называть интеграционным тест, где всё замокано** — проверяется композиция заглушек, а не реальная стыковка.
2. **Интеграционные тесты на каждую ветку логики** — CI замедляется, диагностика ухудшается.
3. **Медленные «модульные» тесты**: сеть, `sleep`, реальные таймауты.
4. **Общая БД между тестами без изоляции** — тесты зависят от порядка и данных друг друга.
5. **Только интеграционные тесты** — дефект локализуется плохо, обратная связь медленная.
6. **In-memory СУБД вместо реальной** и убеждённость, что SQL проверен: диалект и поведение отличаются.
7. **Забытая очистка** временных файлов, схем и контейнеров — «мусорные» падения на другом окружении.

---

## Что добавить на собеседовании

- Помимо двух уровней полезно знать **контрактные тесты** (согласованность API между сервисами) и **end-to-end**; их место — на вершине пирамиды.
- Для интеграционных тестов инфраструктуру поднимают в контейнерах (Testcontainers, docker-compose) и пересоздают на каждый прогон, чтобы тесты были воспроизводимы.
- В CI уровни разделяют: unit — на каждый commit, integration — на pull request или nightly, с кэшем зависимостей и параллельным запуском.
- Хороший ответ показывает понимание компромисса: «чем выше уровень, тем выше доверие к результату и ниже скорость и точность диагностики».

## Итог

| Параметр | Модульные | Интеграционные |
|---|---|---|
| Участников | Один модуль | Несколько реальных компонентов |
| Изоляция | Полная, зависимости подменены | Нет, работа с реальной инфраструктурой |
| Скорость | Миллисекунды | Секунды |
| Ловят | Логику и границы | Стыки, SQL, сериализацию, конфигурацию |
| Диагностика | Точная | Требует разбора связки |
| Роль в пирамиде | Основа, большинство тестов | Середина, ключевые стыки |
