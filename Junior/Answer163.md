# 163. Какие есть виды SCM?

В контексте SCM/CI/CD под «видами SCM» обычно понимают две пересекающиеся классификации: **типы систем контроля версий (VCS)** как ядра SCM и **модели ветвления (branching models)**, которые определяют, как изменения интегрируются в пайплайн CI/CD.

### 1. Типы систем контроля версий (VCS)

Это историческая и архитектурная классификация, определяющая, где хранится история и как разработчики взаимодействуют с ней.

**Локальные VCS**
История хранится в локальных файлах на одной машине. Подходит для одиночной работы, не поддерживает параллельную разработку. Примеры: SCCS, RCS .

**Централизованные VCS (CVCS)**
Единый сервер хранит всю историю и файлы. Разработчики получают рабочие копии, но коммиты требуют подключения к серверу. Есть риск единой точки отказа. Примеры: CVS, Subversion (SVN) .

**Распределённые VCS (DVCS)**
Каждый разработчик имеет полную копию репозитория с историей. Коммиты локальны, синхронизация — через push/pull. Устойчивее к сбоям сервера, быстрее для ветвления. Примеры: Git, Mercurial, Bazaar . В современных CI/CD де-факто стандартом является Git.

### 2. Модели ветвления (Branching Models) в контексте CI/CD

Выбор модели ветвления напрямую влияет на частоту интеграции и скорость доставки.

**Git Flow**
Строгая модель с двумя долгоживущими ветками (`master` и `develop`) и вспомогательными (`feature`, `release`, `hotfix`). Хорошо подходит для версионного ПО с редкими релизами, но **плохо совместим с непрерывной поставкой (CD)** из-за накладных расходов на слияния .

**GitHub Flow**
Упрощённая модель: одна стабильная ветка `main`, все изменения — через короткоживущие feature-ветки и Pull Request. `main` всегда готова к деплою. Оптимальна для SaaS и проектов с частыми релизами, требует высокой культуры тестирования .

**Trunk-Based Development (TBD)**
Радикальная модель для максимально быстрого CI/CD: разработчики коммитят в `main` («ствол») как можно чаще (несколько раз в день). Долгоживущие ветки считаются антипаттерном. Для скрытия незавершённого функционала используются Feature Toggles. Лучший выбор для зрелых DevOps-команд с высоким покрытием автотестами .

**GitLab Flow**
Гибрид: добавляет к GitHub Flow ветки окружений (например, `production`) или release-ветки для управления несколькими средами развёртывания. При исправлениях действует принцип «upstream first» (сначала фикс в `main`, затем в нижестоящие ветки) .

### Резюме для CI/CD

Если стоит задача выбрать SCM-практику для нового проекта с пайплайном CI/CD, ориентируйтесь на **Git + Trunk-Based Development или GitHub Flow**. Git Flow уместен только при жёстком требовании версионирования и редких релизах.
