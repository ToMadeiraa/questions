# 151. Разница между TCP и UDP

**TCP (Transmission Control Protocol)** и **UDP (User Datagram Protocol)** — два основных транспортных протокола стека TCP/IP. Оба работают поверх IP и обеспечивают передачу данных между приложениями, но принципиально по-разному: TCP — надёжный, ориентированный на соединение, а UDP — быстрый и «лёгкий», без гарантий доставки.

## Сравнительная таблица

| Критерий | TCP | UDP |
|---|---|---|
| Соединение | Устанавливается (handshake, 3 шага) | Без соединения |
| Надёжность | Гарантирует доставку, порядок, отсутствие дублей | Не гарантирует ничего |
| Подтверждения | ACK, повторная передача потерянных пакетов | Нет |
| Порядок данных | Сохраняется (нумерация сегментов) | Не гарантируется |
| Управление потоком | Есть (window, скользящее окно) | Нет |
| Контроль перегрузки | Есть (slow start, congestion avoidance) | Нет |
| Границы сообщений | Поток байт, границы не сохраняются | Датаграммы, границы сохраняются |
| Заголовок | 20–60 байт | 8 байт |
| Скорость / накладные расходы | Ниже скорость, больше overhead | Выше скорость, минимум overhead |
| Широковещание / multicast | Не поддерживает | Поддерживает |
| Типичное применение | HTTP/HTTPS, SSH, FTP, SMTP, DNS (TCP) | DNS, DHCP, VoIP, видеостриминг, онлайн-игры, QUIC (поверх UDP) |

## TCP подробнее

- **Ориентирован на соединение**: перед обменом данными выполняется трёхстороннее рукопожатие (SYN → SYN-ACK → ACK), а по завершении — закрытие соединения (FIN/ACK).
- **Надёжность**: каждый сегмент нумеруется; получатель подтверждает приём (ACK). При потере или таймауте отправитель повторяет передачу. Дубликаты отбрасываются.
- **Порядок**: байты доставляются приложению в том же порядке, в котором были отправлены (если сегмент пришёл не по порядку, он буферизуется).
- **Управление потоком и перегрузкой**: скользящее окно не даёт «затопить» получателя; алгоритмы congestion control адаптируют скорость к состоянию сети.
- **Потоковая модель**: для приложения это непрерывный поток байт — границы сообщений нужно задавать самому (например, длиной в префиксе или разделителем).
- **Минусы**: задержки на установку соединения, повторные передачи, ожидание потерянных пакетов (head-of-line blocking) — плохо для реального времени.

## UDP подробнее

- **Без соединения**: датаграмма отправляется сразу, без предварительного handshake. Каждая датаграмма независима.
- **Без гарантий**: нет подтверждений, повторов, упорядочивания. Пакеты могут теряться, дублироваться, приходить не по порядку — приложение само решает, нужно ли это обрабатывать (например, реализовать надёжность на уровне приложения, как в QUIC).
- **Сохраняет границы сообщений**: одна отправка — одна датаграмма; получатель читает её целиком (до размера, ограниченного MTU/буфером).
- **Минимальный overhead**: заголовок 8 байт (порты, длина, контрольная сумма), нет состояния соединения.
- **Поддержка broadcast/multicast**: удобно для обнаружения сервисов (DHCP, mDNS).
- **Плюсы**: низкая задержка, высокая пропускная способность, контроль над таймингом — идеален для VoIP, видео, игр, телеметрии, DNS-запросов.

## Что выбрать

- Нужна **гарантированная и упорядоченная доставка** (файлы, HTTP, БД, SSH) → **TCP**.
- Важна **низкая задержка**, допустимы потери, или нужен **broadcast/multicast** (стриминг, игры, VoIP, DHCP, DNS) → **UDP**, при необходимости добавляя надёжность на уровне приложения.
- Современные решения часто строятся **поверх UDP** с собственной логикой надёжности и контроля перегрузки — например, QUIC (основа HTTP/3) и WebRTC.

## Пример на C++ (разница в API сокетов)

```cpp
#include <sys/socket.h>
#include <netinet/in.h>

// TCP-сокет: потоковый, с установкой соединения
int tcp_fd = socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
// далее: connect()/bind()+listen()+accept(), send()/recv() — поток байт

// UDP-сокет: датаграммный, без соединения
int udp_fd = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
// далее: sendto()/recvfrom() — каждая датаграмма независима
```

Ключевое отличие на уровне API: для TCP используется `SOCK_STREAM` (поток байт, `connect`/`accept`, `send`/`recv`), для UDP — `SOCK_DGRAM` (датаграммы, `sendto`/`recvfrom`, соединение не требуется).

**Короткий ответ:** TCP — надёжный, упорядоченный, с установкой соединения и контролем потока/перегрузки, но с большими накладными расходами; UDP — без соединения и гарантий, с минимальным overhead и сохранением границ сообщений, зато максимально быстрый и подходящий для реального времени и multicast.
