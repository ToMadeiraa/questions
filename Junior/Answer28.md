# Вопрос 28. Что такое оптимизация компилятора?

> **Кратко:** это набор преобразований программы, которые компилятор выполняет, чтобы получить более быстрый или более компактный код, не меняя наблюдаемого поведения. Компилятор обязан вести себя так, «как если бы» он честно выполнил программу по исходнику (правило *as-if*), поэтому менять можно всё, что не наблюдается: промежуточные переменные, лишние копии, порядок независимых вычислений. Обратная сторона — оптимизатор опирается на отсутствие неопределённого поведения: там, где стандарт поведение не определяет, он вправе считать «невозможные» ветки недостижимыми.

---

## Правило as-if

| Что менять разрешено | Что обязано сохраниться |
|---|---|
| локальные переменные, лишние копии и временные объекты | обращения к `volatile` — ровно в порядке абстрактной машины |
| порядок независимых вычислений | записанные в файлы и потоки данные |
| наличие и число вызовов функций (встраивание) | наблюдаемые побочные эффекты и их последовательность |

Из-за as-if оптимизацию не видно в отладчике: переменной может не быть вовсе, потому что её значение вычислено на месте.

---

## Уровни оптимизации

| Флаг | Что включает | Когда уместен |
|---|---|---|
| `-O0` | ничего, прямой код «строка в строку» (по умолчанию) | отладка, анализ ассемблера |
| `-O1` | базовые преобразования, быстро собирается | быстрый цикл разработки |
| `-O2` | почти все безопасные оптимизации, без агрессивного роста кода | стандарт для релиза |
| `-O3` | + агрессивное встраивание, разворачивание, векторизация | «горячие» численные участки |
| `-Os` / `-Oz` | приоритет размера кода (Clang: `-Oz` ещё агрессивнее) | embedded, мобильные, icache-чувствительный код |
| `-Ofast` | `-O3` + `-ffast-math`: IEEE-семантика нарушается | только если NaN/Inf не важны |

Уровни не вложены строго и не монотонны по скорости: `-O3` иногда проигрывает `-O2` из-за размера кода и промахов icache. Уровень выбирают замером, а не по названию.

---

## Основные преобразования

| Преобразование | Идея | Пример |
|---|---|---|
| Свёртка констант | вычислить всё, что известно на компиляции | `2 * 21` → `42` |
| Распространение констант и копий | подставить известные значения | `const int n = 8;` → цикл до 8 |
| Удаление мёртвого кода (DCE) | выбросить вычисления без эффекта | неиспользуемая переменная |
| Общая подвыраженность (CSE) | считать один раз | `a*b + a*b` → `t + t` |
| Встраивание (inlining) | подставить тело вместо вызова | мелкие геттеры, `inline`-функции |
| Возврат по значению без копий | RVO/NRVO, гарантированное копирование-исключение (C++17) | `return Widget{...};` |
| Вынос инвариантов из цикла (LICM) | поднять неизменное наружу | `for (...) sum += v.size();` |
| Разворачивание цикла | уменьшить накладные расходы на итерацию | цикл с известным малым числом шагов |
| Векторизация (SIMD) | обрабатывать несколько элементов за инструкцию | сумма массива `float` |
| Девиртуализация | заменить косвенный вызов прямым | `final`-класс, объект по значению |

## Как это выглядит в коде

**Свёртка констант и удаление мёртвого кода:**

```cpp
constexpr int kBufferSize = 64 * 4;      // посчитано компилятором

int sumFirst(const int* data, int n) {
    int unused = 42;                     // будет выброшено
    int s = 0;
    for (int i = 0; i < n; ++i) s += data[i];
    return s + kBufferSize;
}
```

**Гарантированное копирование-исключение (C++17):**

```cpp
struct Widget {
    Widget() = default;
    Widget(const Widget&) = delete;      // копирование запрещено — и это законно
};

Widget make() { return Widget{}; }       // prvalue создаётся прямо на месте результата

int main() {
    Widget w = make();                   // ни копии, ни перемещения не требуется
}
```

До C++17 это была «оптимизация, которую компилятору разрешено делать», с `-fno-elide-constructors` её можно было отключить. В C++17 для prvalue это уже не оптимизация, а требование языка, и `-fno-elide-constructors` на такие случаи не действует.

**Девиртуализация:**

```cpp
struct Base { virtual ~Base() = default; virtual int value() const = 0; };

struct Impl final : Base { int value() const override { return 42; } };

int use() {
    Impl obj;                 // тип известен статически — виртуальный вызов не нужен
    return obj.value();       // компилятор вызывает Impl::value() напрямую
}

int useViaRef(const Base& b) { return b.value(); }  // девиртуализация — с LTO и `final`
```

Векторизация (SIMD) — отдельный случай того же анализа: цикл `out[i] = a[i] + b[i]` на `-O3` превращается в инструкции по 4–8 элементов за раз, но только если компилятор доказал отсутствие пересечения буферов (`__restrict`, `std::assume_aligned`).

## Где оптимизация ломается: undefined behavior

Для оптимизатора UB — это разрешение сузить множество допустимых поведений. Три классических примера, которые «работают на `-O0` и падают на `-O2`»:

```cpp
// 1. Переполнение знакового int — UB: компилятор вправе считать, что его не бывает
bool alwaysTrue(int x) {
    return x + 1 > x;      // на -O2 свернётся в true, хотя для INT_MAX это ложь
}

int sumUpTo(int n) {
    int s = 0;
    for (int i = 0; i < n; ++i) s += i;   // переполнение => любой результат «законен»
    return s;
}

// 2. Нарушение strict aliasing: доступ к float через int* — UB
int pun(float f) {
    return *reinterpret_cast<int*>(&f);    // невалидно, нужен std::bit_cast / memcpy
}

// 3. Разыменование nullptr — UB; проверка после него становится «мёртвой»
int deref(int* p) {
    int v = *p;            // отсюда оптимизатор выводит p != nullptr
    if (!p) return 0;      // эта ветка будет выброшена
    return v;
}
```

| Проблема | Диагностика | Лечение |
|---|---|---|
| Переполнение знаковых | `-fsanitize=signed-integer-overflow` | беззнаковая арифметика, `-fwrapv` |
| Strict aliasing | `-Wstrict-aliasing` | `std::memcpy`, `std::bit_cast` (C++20), `-fno-strict-aliasing` |
| Разыменование `nullptr`, выход за границы | `-fsanitize=address`, `-D_GLIBCXX_ASSERTIONS` | контейнеры STL, `.at()`, проверки до доступа |

Правило: **симптом «исчезает под отладчиком / появляется только с `-O2`» — это почти всегда UB**, а не баг компилятора.

---

## Что мешает оптимизатору

| Барьер | Почему |
|---|---|
| `volatile` | обращения обязаны произойти в точности по абстрактной машине |
| Вызов внешней функции без LTO | компилятор не знает, что она делает с памятью |
| Атомарные операции | жёсткие гарантии порядка памяти |

Компиляторный барьер без реальных инструкций: `asm volatile("" ::: "memory")`; в стандартном C++ — `std::atomic_signal_fence(std::memory_order_seq_cst)`.

---

## Оптимизация и отладка

- `-g -O2` — рабочая комбинация: отладочная информация не мешает оптимизации, но переменные могут быть «optimized out», а стек — без кадров встроенных функций. `-Og` — компромисс, когда код хочется читать в отладчике построчно.
- Профилировать нужно **релизную** сборку: `-O2` меняет распределение времени радикально, а профиль с `-O0` почти бесполезен.

---

## Межфайловая оптимизация

| Средство | Что даёт |
|---|---|
| `-flto` | оптимизатор видит все TU, работает межфайловое встраивание и девиртуализация |
| PGO (`-fprofile-generate` / `-fprofile-use`) | раскладка ветвей и блоков по реальному профилю, до 10–20 % |
| `-march=native` | доступ к AVX/AVX-512, но бинарник перестаёт быть переносимым |
| BOLT | перекладка готового бинарника по профилю исполнения |

---

## Типичные ошибки

1. **Считать, что оптимизация не меняет поведение вообще.** Она сохраняет наблюдаемое поведение корректной программы; UB она вправе «оптимизировать в ничто».
2. **Искать причину бага в компиляторе.** «Работает на `-O0`, падает на `-O2`» — это UB в коде.
3. **Отлаживать релиз без `-g`.** Получаем стек из адресов и никаких имён.
4. **Ставить `-O3` и `-march=native` «на всякий случай»** — теряется переносимость, а выигрыш может быть отрицательным.
5. **Полагаться на `-Ofast`** в коде, где важны NaN, `Inf` или точность — `-ffast-math` ломает IEEE-семантику.

---

## Что добавить на собеседовании

- Сформулировать **as-if rule** и тут же связать её с UB: оптимизатор не «ломает» программу, он использует свободу, которую даёт неопределённое поведение.
- Назвать типичный конвейер: фронтенд → IR → машинно-независимые оптимизации → выбор инструкций → распределение регистров.
- Упомянуть, что RVO в C++17 перестало быть оптимизацией и стало требованием языка, — это показывает знание современного стандарта.

## Итог

| Понятие | Суть |
|---|---|
| Оптимизация компилятора | преобразования кода без изменения наблюдаемого поведения (as-if) |
| Уровни | `-O0`/`-O1`/`-O2`/`-O3`, `-Os`/`-Oz`, `-Og`, `-Ofast` |
| Типичные приёмы | свёртка констант, DCE, CSE, встраивание, LICM, разворачивание, SIMD, девиртуализация |
| Граница допустимого | UB даёт оптимизатору право «сузить» программу |
| Барьеры | `volatile`, внешние вызовы без LTO, атомики, inline-asm |
| Межфайловое | `-flto`, PGO, BOLT |
| Практика | релиз с `-O2 -g`, профилирование, санитайзеры, замеры вместо догадок |
