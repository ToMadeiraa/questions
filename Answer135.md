# 135. Что такое race condition (состояние гонки)?

## Определение

**Race condition** (состояние гонки) — это ошибка проектирования многопоточной (или многопроцессной) программы, при которой результат работы программы зависит от того, в каком порядке и в какой момент времени потоки (или процессы) обращаются к общим (разделяемым) данным. Иными словами, поведение программы недетерминировано и зависит от «гонки» потоков за доступ к ресурсу.

Классическое условие возникновения: **два или более потока одновременно обращаются к одному и тому же участку памяти, причём хотя бы один из них выполняет запись, и обращение не синхронизировано**.

## Как это выглядит на практике

Рассмотрим типичный пример — инкремент счётчика из нескольких потоков:

```cpp
#include <iostream>
#include <thread>

int counter = 0;  // разделяемая переменная

void increment() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;  // НЕ атомарная операция!
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();

    std::cout << "counter = " << counter << "\n";
    // Ожидалось 200000, но результат будет меньше и разным от запуска к запуску
}
```

### Почему это ломается

Операция `++counter` на уровне процессора — это не одна инструкция, а последовательность из трёх шагов:

1. **Чтение** значения `counter` из памяти в регистр.
2. **Инкремент** значения в регистре.
3. **Запись** результата обратно в память.

Если два потока выполнят эти шаги в «неудачном» порядке, получим **потерянное обновление** (lost update):

```
Поток A: читает counter = 5
Поток B: читает counter = 5
Поток A: прибавляет 1 → 6, записывает 6
Поток B: прибавляет 1 → 6, записывает 6   // обновление A потеряно!
```

Итог: два инкремента дали прирост всего на единицу. Чем больше потоков и итераций — тем сильнее расхождение с ожидаемым результатом.

## Типичные проявления race condition

- **Потерянные обновления** (lost update) — как в примере выше.
- **Порча данных** (data corruption) — например, при работе со связным списком или `std::vector`, когда один поток изменяет структуру (reallocation, вставка), а другой в это время её читает.
- **Нарушение инвариантов** — объект временно находится в несогласованном состоянии, и другой поток это «видит».
- **Проблема «check-then-act»** (TOCTOU — time-of-check to time-of-use):

```cpp
if (!cache.contains(key)) {        // проверка
    cache[key] = loadValue(key);   // действие — между этими строками
                                   // другой поток мог всё изменить
}
```

- **Гонки при инициализации** (lazy initialization без синхронизации).
- **Порядок операций с памятью** — компилятор и процессор вправе переупорядочивать обращения к памяти (memory reordering), что на многоядерных системах без барьеров памяти также приводит к неожиданным результатам.

## Ключевая идея: атомарность

Участок кода, в котором программа обращается к разделяемым данным и который должен выполняться как единое целое, называется **критической секцией**. Чтобы устранить гонку, критическую секцию нужно сделать **взаимоисключающей** (mutual exclusion) — тогда только один поток в единицу времени может её выполнять.

## Способы предотвращения в C++

### 1. Мьютексы (`std::mutex`, `std::lock_guard`, `std::unique_lock`)

```cpp
#include <mutex>

std::mutex mtx;
int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(mtx);  // RAII-захват мьютекса
        ++counter;
    }  // автоматическое освобождение при выходе из области видимости
}
```

### 2. Атомарные операции (`std::atomic`)

```cpp
#include <atomic>

std::atomic<int> counter{0};

void increment() {
    for (int i = 0; i < 100000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);  // атомарный инкремент
    }
}
```

`std::atomic` гарантирует атомарность отдельной операции и позволяет управлять моделью памяти через `memory_order` (`relaxed`, `acquire`, `release`, `seq_cst` и др.), что помогает избежать и гонок, и лишних издержек синхронизации.

### 3. Другие примитивы синхронизации

- **`std::condition_variable`** — ожидание события.
- **`std::shared_mutex`** (C++17) — множество читателей / один писатель.
- **`std::once_flag` + `std::call_once`** — потокобезопасная однократная инициализация.
- **`std::counting_semaphore`**, **`std::latch`**, **`std::barrier`** (C++20).
- Блокировки на уровне данных (data-level locking), lock-free структуры на основе `std::atomic` и compare-exchange (`compare_exchange_weak/strong`).

### 4. Проектные приёмы

- **Не разделять изменяемое состояние** между потоками (передавать данные по значению, использовать message passing, очереди).
- **Иммутабельность** (const-данные безопасны для параллельного чтения).
- **Thread-local storage** (`thread_local`) для данных, не требующих совместного доступа.
- **Минимизация критических секций** — держать блокировку как можно короче.
- **Соблюдение единого порядка захвата блокировок** — иначе получите **deadlock**.

## Инструменты обнаружения

- **ThreadSanitizer** (`-fsanitize=thread` в GCC/Clang) — обнаруживает гонки данных на этапе выполнения.
- **Helgrind / DRD** из состава Valgrind.
- Статический анализ (Clang Static Analyzer, PVS-Studio, Coverity).
- Стресс-тесты и повторные прогоны под нагрузкой.

## Итоговая формулировка для ответа

> **Race condition (состояние гонки)** — это ситуация в многопоточной программе, когда корректность результата зависит от непредсказуемого порядка выполнения потоков, обращающихся к общим данным без должной синхронизации. Чаще всего возникает из-за неатомарности операций «чтение-изменение-запись» над разделяемой памятью. Для устранения используются мьютексы, атомарные операции (`std::atomic`), условные переменные, а также проектные приёмы вроде иммутабельности и изоляции состояния. Обнаруживается с помощью ThreadSanitizer, Valgrind и статического анализа.
