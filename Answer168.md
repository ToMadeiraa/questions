# 168. Какие есть этапы решения merge conflict?

Разрешение конфликта слияния (merge conflict) — это процесс, который в контексте SCM/CI/CD обычно выполняется локально разработчиком до того, как изменения попадут в общую ветку и запустят пайплайн. Ниже приведена стандартная последовательность этапов.

### 1. Обнаружение и идентификация конфликта
Конфликт возникает, когда Git не может автоматически объединить изменения (например, две ветки изменили одну и ту же строку файла или одна ветка изменила файл, а другая удалила его) . На этом этапе необходимо:
- Понять, какая операция вызвала конфликт (`merge`, `rebase`, `pull` или `cherry-pick`).
- Выполнить `git status`, чтобы увидеть список файлов в состоянии `Unmerged paths` . Эти файлы и есть те, которые требуют ручного вмешательства.

### 2. Анализ конфликтующих участков (чтение маркеров)
Откройте конфликтующий файл в редакторе. Git вставит специальные маркеры, показывающие конфликтующие версии :
- `<<<<<<< HEAD`: начало ваших локальных изменений (текущая ветка).
- `=======`: разделитель между вашей версией и версией из другой ветки.
- `>>>>>>> <branch-name>`: конец изменений из другой ветки.

Для более сложного анализа рекомендуется включить стиль `diff3` (`git config merge.conflictStyle diff3`). Это добавит маркер `|||||||` и покажет исходный текст (предка), что помогает понять, что именно изменила каждая сторона, а не просто сравнивать два разных результата .

### 3. Принятие решения и редактирование
Это ключевой этап. Необходимо вручную отредактировать файл, удалив маркеры и оставив итоговый вариант кода. Возможные стратегии:
- **Оставить только свои изменения** (Ours).
- **Оставить только чужие изменения** (Theirs).
- **Объединить оба варианта** (написать новый код, который учитывает логику обоих изменений). Это наиболее частый вариант для сохранения работоспособности кода .
- Для бинарных файлов (изображения, архивы) Git не может вставить маркеры. В этом случае нужно выбрать одну из версий целиком (например, через `git checkout --ours <file>` или `--theirs <file>`) .

### 4. Тестирование (локальная валидация)
После редактирования **обязательно** запустите сборку и тесты локально. Конфликт слияния — это не только текст, но и логика. Код может синтаксически компилироваться, но содержать логическую ошибку из-за неверного объединения. В контексте CI/CD это критический этап: если пропустить локальную проверку, пайплайн упадёт уже после пуша, заблокировав работу команды .

### 5. Маркировка как разрешённого
Убедившись, что файл исправлен и протестирован, добавьте его в индекс Git:
```bash
git add <file>
```
Это сигнализирует Git, что конфликт в данном файле исчерпан. Если файлов несколько, процедура (анализ → редактирование → тест → `git add`) повторяется для каждого из них .

### 6. Завершение слияния (Commit)
После того как все конфликты помечены как разрешённые (`git status` больше не показывает `Unmerged paths`), необходимо создать коммит:
```bash
git commit -m "Resolve merge conflict: <описание>"
```
При слиянии Git автоматически подставит стандартное сообщение, но лучше указать, какие именно конфликты и как были решены. Если вы использовали `rebase`, вместо коммита нужно выполнить `git rebase --continue` .

### 7. Пуш и запуск CI/CD
Только после успешного коммита изменения отправляются в удалённый репозиторий (`git push`). В современных процессах (GitHub/GitLab) это действие обновит Pull Request / Merge Request. После этого запускается CI-пайплайн, который выполняет финальную проверку (линтеры, интеграционные тесты, сборка артефактов) . Если пайплайн зелёный, кнопка слияния (Merge) станет доступной для завершения интеграции в целевую ветку.

### Резервный вариант: отмена
Если на любом из этапов вы понимаете, что ситуация слишком сложная или выбрана неверная стратегия, можно откатить процесс в исходное состояние:
- При merge: `git merge --abort`
- При rebase: `git rebase --abort`
