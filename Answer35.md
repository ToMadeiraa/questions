# Вопрос 35. Какие варианты использования extern знаете?

> **Кратко:** `extern` — спецификатор, который объявляет сущность **без определения** (объект или функция определены в другой единице трансляции) либо задаёт **языковое связывание** (`extern "C"`). Основные применения: объявление глобальной переменной из другого `.cpp`, объявление функции, блок `extern "C"` для совместимости с C, `extern template` для подавления лишних инстанциаций и «включение» внешнего связывания у `const`-объектов.

---

## Что именно делает extern

Ключевой момент: `extern` — это **спецификатор linkage и хранения**, а не модификатор типа. Он говорит компилятору: «эта сущность существует, но определена не здесь; её адрес подставит линкер».

Различие объявления и определения:

| Запись | Что это | Память выделяется |
|---|---|---|
| `extern int g;` | объявление (declaration) | нет |
| `int g;` | определение, zero-initialization | да |
| `int g = 5;` | определение с инициализацией | да |
| `extern int g = 5;` | **определение** (инициализатор делает его определением) | да |

> Отсюда главная ловушка: `extern int g = 5;` в заголовке — это определение, и при включении в несколько `.cpp` получите ошибку линковки «multiple definition» (ODR).

---

## 1. Объявление переменной, определённой в другом translation unit

Классическая схема «заголовок — объявление, один `.cpp` — определение»:

```cpp
// config.h
#pragma once

extern int g_verbosity;          // объявление: памяти не выделяет
extern const char* g_logPath;    // указатель тоже можно объявлять

void initConfig();               // объявление функции
```

```cpp
// config.cpp
#include "config.h"

int g_verbosity = 0;                        // единственное определение
const char* g_logPath = "app.log";          // единственное определение
void initConfig() { g_verbosity = 1; }
```

Клиент подключает заголовок и пользуется переменной, не зная, где она лежит: `initConfig(); std::cout << g_verbosity;` — адрес символа подставит линкер.

Так же объявляют **массив без размера**: `extern const int a[];` в заголовке, а размер известен только в определяющем `.cpp` (`const int a[] = {1, 2, 3, 4};`). В другом TU `sizeof` такого массива — **ошибка компиляции**.

---

## 2. Объявление функции: extern избыточен

У функций внешнее связывание и так по умолчанию, поэтому `extern void f();` эквивалентно `void f();`. Писать `extern` у функций смысла нет — только шум. Исторически его писали для симметрии с переменными.

---

## 3. `extern "C"` — языковое связывание

C++ **манглит** имена (кодирует типы параметров в символе, чтобы работала перегрузка). C — нет. `extern "C"` отключает манглинг, и символ `c_add` остаётся `c_add`, а не `_Z5c_addii`.

Заголовок, который годится и для C, и для C++:

```cpp
// api.h
#pragma once

#ifdef __cplusplus
extern "C" {
#endif

int  c_add(int a, int b);
void c_log(const char* msg);

#ifdef __cplusplus
}
#endif
```

Типичные сценарии:

- подключение C-библиотеки из C++ (заголовки системных API, `sqlite3.h`, `zlib.h`);
- экспорт C++-функций для вызова из C, Python (`ctypes`), Rust, `dlsym`/`LoadLibrary`;
- передача callback в C-библиотеку (например, компаратор для `qsort`) — функция-callback обязана иметь C-связывание.

```cpp
// Экспорт точки входа для динамической загрузки по имени "create"
extern "C" void* create() { return new MyObject(); }
extern "C" void  destroy(void* p) { delete static_cast<MyObject*>(p); }
```

Ограничения: с C-связыванием **нельзя перегружать** функции (в C одно имя — один символ), типы в сигнатуре должны быть C-совместимыми (нельзя шаблоны, ссылки в стиле C-ABI, классы с нетривиальной семантикой по значению).

---

## 4. `extern template` — подавление неявной инстанциации (C++11)

Компилятор инстанцирует шаблон в каждом TU, где он используется, а линкер потом склеивает одинаковые инстанциации. Это лишняя работа и раздувание объектных файлов. `extern template` говорит: «здесь не инстанцируй, она уже есть в другом TU».

```cpp
// widget.h
#pragma once
#include <vector>

class Widget { /* ... */ };

extern template class std::vector<Widget>;   // подавляем неявную инстанциацию
void useWidgets(const std::vector<Widget>& ws);
```

```cpp
// widget.cpp
#include "widget.h"

template class std::vector<Widget>;          // единственная явная инстанциация
void useWidgets(const std::vector<Widget>& ws) { /* ... */ }
```

Работает и для функций шаблона: `extern template void sortImpl<int>(int*, int);`.

---

## 5. `extern` и `const`

В C++ `const`-объект на уровне пространства имён по умолчанию имеет **внутреннее** связывание: каждый TU получает собственную копию, а адреса в разных TU различаются. `extern` возвращает внешнее связывание:

```cpp
// limits.h
extern const int kMaxConnections;    // объявление, связывание внешнее
// limits.cpp
extern const int kMaxConnections = 64;   // определение
```

Без `extern` в определяющем файле объект остался бы внутренним, и линкер не нашёл бы символ.

> В C правило другое: `const` на файловом уровне имеет внешнее связывание по умолчанию. Это классический источник путаницы при переносе кода.

Современная альтернатива (C++17) — **inline-переменная**, ей не нужен отдельный `.cpp`:

```cpp
// limits.h — C++17
inline constexpr int kMaxConnections = 64;   // одно определение на всю программу
```

---

## 6. Объявление в блочной области

`extern` можно писать внутри функции — это объявление глобальной сущности в локальной области видимости:

```cpp
void tick() {
    extern int g_counter;   // g_counter определён в другом TU
    ++g_counter;
}
```

Работает, но считается плохим стилем: зависимость не видна в интерфейсе функции.

## Типичные ошибки

1. **`extern int g = 5;` в заголовке.** Инициализатор превращает объявление в определение — множественные определения при линковке.
2. **Забыть определение.** `extern`-объявление без определения в проекте даёт ошибку линкера «undefined reference», а не компиляции.
3. **`extern` у функций «для солидности».** Не влияет ни на что, кроме читаемости.
4. **Ждать от `extern "C"` большего, чем есть.** Оно меняет только связывание имён: внутри блока остаётся C++, но перегрузки запрещены — два символа с одним именем не собрать.
5. **`sizeof` внешнего массива.** Размер неизвестен вне определяющего TU; нужен явный размер или `std::span`.
6. **`extern template` без явной инстанциации.** Получите «undefined reference» на членах шаблона.

---

## Что добавить на собеседовании

- `extern` — про **связывание (linkage)**, а не про «глобальность». Внутреннее связывание даёт `static` на файловом уровне и анонимное пространство имён; внешнее — `extern` (и обычные функции/переменные без `static`).
- Три уровня связывания в C++: внешнее, внутреннее и «нет связывания» (локальные переменные).
- В современном C++ паттерн «`extern` в заголовке + определение в `.cpp`» для констант вытеснен `inline constexpr` (C++17), а для глобального состояния лучше подходят функции-аксессоры или `Singleton`-объект — так проще контролировать порядок инициализации.
- Стоит упомянуть **static initialization order fiasco**: глобальные объекты из разных TU инициализируются в неопределённом порядке, поэтому глобальные переменные, зависящие друг от друга, опасны независимо от `extern`.
- `extern "C"` — единственный практический способ отдать C++ в C-ABI; для экспорта из DLL дополнительно нужны `__declspec(dllexport)` / `visibility("default")`.

## Итог

| Вариант использования | Синтаксис | Зачем |
|---|---|---|
| Объявление внешней переменной | `extern int g;` | объект определён в другом `.cpp` |
| Объявление функции | `extern void f();` | ничего не даёт, избыточно |
| Языковое связывание | `extern "C" { ... }` | C-ABI: библиотеки, `dlsym`, callbacks |
| Подавление инстанциации | `extern template class V<int>;` | убрать повторные инстанциации шаблона |
| Внешнее связывание у `const` | `extern const int N;` | `const` по умолчанию внутренний |
| Массив без размера | `extern int a[];` | размер известен только в определении |
| Определение с `extern` | `extern int g = 5;` | определение; в заголовке — ошибка |
