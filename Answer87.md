# 87. Отличие `delete` от `delete[]`

## Краткий ответ

- **`delete`** — освобождает память, выделенную для **одного** объекта через `new`.
- **`delete[]`** — освобождает память, выделенную для **массива** объектов через `new[]`.

Использование «не той» формы — это **неопределённое поведение** (undefined behavior).

## Подробно

### 1. Как работают `new` / `new[]`

```cpp
int*  p1 = new int;        // один объект
int*  p2 = new int[10];    // массив из 10 объектов

MyClass* o = new MyClass;      // конструктор вызывается 1 раз
MyClass* a = new MyClass[5];   // конструктор вызывается 5 раз
```

Ключевое различие — **что именно нужно сделать при освобождении**:

| Оператор | Что делает |
|----------|-----------|
| `delete p` | вызывает **деструктор одного** объекта, затем освобождает память |
| `delete[] p` | вызывает **деструктор каждого** элемента массива, затем освобождает память |

### 2. Почему нельзя путать формы

Компилятор не хранит тип «рядом с указателем» — он определяет, какую форму вызвать, **только по тому, какой оператор вы написали**. Формы `delete` и `delete[]` — это разные функции освобождения, и они по-разному взаимодействуют с внутренними структурами менеджера памяти (например, со «скрытым» счётчиком элементов массива, который хранит реализация `new[]`).

Поэтому:

- `delete` для памяти из `new[]` → **UB**;
- `delete[]` для памяти из `new` → **UB**.

### 3. Что произойдёт, если вызвать `delete` у объекта, созданного через `new[]`

Поведение **не определено стандартом**. На практике возможны варианты:

1. **Вызовется деструктор только первого элемента** (или ни одного) — остальные элементы не будут разрушены. Если у них есть ресурсы (динамическая память, файлы, мьютексы и т.п.) — **утечка ресурсов**.
2. **Некорректное освобождение памяти** — менеджер памяти получит неверный указатель/размер (потому что `new[]` мог выделить блок с заголовком, хранящим количество элементов). Результат — **повреждение кучи** (heap corruption), падение программы, порча соседних данных.
3. **Всё «сработает» случайно** — например, для тривиальных типов (`int`, `char`) без деструкторов многие реализации не заметят разницы, и память освободится. Но полагаться на это **нельзя** — это всё равно UB, и поведение может измениться при смене компилятора/флагов/версии.

Пример потенциальной проблемы:

```cpp
struct Widget {
    std::string name;
    ~Widget() { /* освобождает ресурсы */ }
};

Widget* arr = new Widget[3];  // 3 конструктора
delete arr;                   // ОШИБКА: UB
// — скорее всего, деструктор вызовется только у arr[0],
//   у arr[1] и arr[2] — нет; память может быть освобождена неверно
```

Правильно:

```cpp
delete[] arr;  // 3 деструктора + корректное освобождение памяти
```

### 4. Асимметрия, о которой стоит помнить

Существует важное исключение из «правила симметрии»: **если тип не имеет деструктора и является тривиальным**, стандарт формально всё равно требует парности `new[]`/`delete[]`, но некоторые компиляторы «прощают» ошибку. Полагаться на это нельзя — **всегда соблюдайте пары**:

| Выделение | Освобождение |
|-----------|--------------|
| `new T` | `delete` |
| `new T[n]` | `delete[]` |
| `new T` (через `malloc`-подобное — не для C++) | — |

### 5. Как избежать ошибок

- Используйте **умные указатели**:
  - `std::unique_ptr<T>` для одиночного объекта (`new T`);
  - `std::unique_ptr<T[]>` (или лучше `std::vector<T>`) для массива;
  - `std::make_unique<T>(...)` и `std::make_unique<T[]>(n)` — форма освобождения выбирается автоматически.
- Для массивов в современном C++ предпочтительнее `std::vector<T>` / `std::array<T, N>`, а не ручные `new[]`/`delete[]`.
- Соблюдайте правило: **одна форма `new` — соответствующая форма `delete`**, и желательно в одном месте (RAII-обёртка).

## Итог

`delete` и `delete[]` — **разные операции**: первая разрушает один объект, вторая — все элементы массива. Вызов `delete` для указателя, полученного из `new[]`, — это **неопределённое поведение**: в лучшем случае «повезёт», в худшем — утечки ресурсов и повреждение кучи. Всегда используйте парные формы, а ещё лучше — умные указатели и контейнеры STL.
