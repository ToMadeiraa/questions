# Вопрос 13. Что такое TDD?

> **Кратко:** TDD (Test-Driven Development) — методика разработки, при которой тест пишется **до** рабочего кода. Работа идёт короткими циклами **red → green → refactor**: сначала падающий тест фиксирует требование, затем минимальная реализация делает его зелёным, затем код приводится в порядок под защитой тестов.

---

## Цикл Red — Green — Refactor

| Фаза | Что делаем | Критерий выхода |
|---|---|---|
| **Red** | Пишем тест на ещё не реализованное поведение и запускаем | Тест падает, причём по ожидаемой причине |
| **Green** | Пишем минимально достаточный код, чтобы тест прошёл | Все тесты зелёные, ничего лишнего не добавлено |
| **Refactor** | Убираем дублирование, улучшаем имена и структуру | Тесты остаются зелёными, поведение не изменилось |

Цикл занимает секунды-минуты. Чем короче шаг, тем меньше кода находится «под подозрением», когда тест внезапно покраснел.

---

## Три закона TDD

1. Нельзя писать рабочий код, пока не написан падающий тест.
2. Нельзя писать тест больше, чем нужно для одного падения — в том числе ошибка компиляции считается падением.
3. Нельзя писать код больше, чем нужно, чтобы пройти текущий падающий тест.

Смысл в том, что каждый фрагмент рабочего кода появляется **только как ответ на конкретное требование**, и этот ответ немедленно проверяется.

---

## Пошаговый пример

**Шаг 1. Red.** Тест на функцию, которой ещё нет, — код не компилируется, это законное падение.

```cpp
#include <gtest/gtest.h>
#include <string>

// fizzbuzz ещё не существует: сборка падает -> RED
TEST(FizzBuzzTest, ReturnsPlainNumberAsString) {
    EXPECT_EQ(fizzbuzz(1), "1");
}
```

**Шаг 2. Green.** Минимальная реализация, проходящая ровно этот тест.

```cpp
std::string fizzbuzz(int n) {
    return std::to_string(n);       // ничего лишнего: только чтобы стало зелёным
}
```

**Шаг 3. Red.** Добавляем следующий тест — на делимость на 3.

```cpp
TEST(FizzBuzzTest, ReturnsFizzForMultiplesOfThree) {
    EXPECT_EQ(fizzbuzz(3), "Fizz");
}
```

**Шаг 4. Green.** Реализация расширяется ровно настолько, чтобы пройти оба теста.

```cpp
std::string fizzbuzz(int n) {
    if (n % 3 == 0) return "Fizz";
    return std::to_string(n);
}
```

**Шаг 5. Red/Green.** Аналогично добавляются случаи для 5 и 15; табличный тест фиксирует всю картину (это называют **триангуляцией** — реализация уточняется по мере появления разных примеров).

```cpp
struct FizzCase {
    int n;
    std::string expected;
};

class FizzBuzzTable : public testing::TestWithParam<FizzCase> {};

TEST_P(FizzBuzzTable, MatchesExpectedOutput) {
    const FizzCase c = GetParam();
    EXPECT_EQ(fizzbuzz(c.n), c.expected);
}

INSTANTIATE_TEST_SUITE_P(Table, FizzBuzzTable,
    testing::Values(FizzCase{1, "1"},   FizzCase{3, "Fizz"},
                    FizzCase{5, "Buzz"}, FizzCase{15, "FizzBuzz"}));
```

**Шаг 6. Refactor.** Поведение не меняется, структура становится яснее — тесты страхуют.

```cpp
std::string fizzbuzz(int n) {
    const bool div3 = (n % 3 == 0);
    const bool div5 = (n % 5 == 0);

    if (div3 && div5) return "FizzBuzz";
    if (div3)         return "Fizz";
    if (div5)         return "Buzz";
    return std::to_string(n);
}
```

## Что TDD даёт и чего не даёт

| Даёт | Не даёт |
|---|---|
| Покрытие тестами «по построению» — код без теста просто не появляется | Гарантии отсутствия ошибок: проверено только то, что придумали проверить |
| Проектирование «снаружи внутрь»: сначала API, потом реализация | Замены интеграционным и end-to-end тестам |
| Тесты как документация требования в момент его формулировки | Автоматического качества: плохой дизайн можно «заTDDить» |
| Короткий цикл отладки: упал последний тест — ошибка почти наверняка в последней правке | Хорошего результата при полностью неясных требованиях |
| Защиту при рефакторинге и меньше времени в отладчике | Бесплатной скорости: тесты — это тоже поддерживаемый код |

Ключевая мысль: **TDD — это техника проектирования**, а не техника тестирования. Побочный продукт — хороший набор тестов; основной — код, который удобно вызывать и менять.

---

## TDD и «тесты после»

| Аспект | TDD | Тесты после кода |
|---|---|---|
| Момент написания | До реализации | После реализации |
| Что проверяется | Требование (поведение) | То, что уже написано |
| Риск «подгонки» теста под баг | Низкий: тест до кода | Высокий: тест описывает текущее поведение |
| Влияние на дизайн | Сильное: API проектируется изнутри использования | Слабое: тестируемость добавляется задним числом |
| Покрытие | Естественное | По остаточному принципу |
| Скорость старта | Медленнее на старте | Быстрее начать |

Оба подхода дают регрессионную защиту, но только TDD системно влияет на качество интерфейсов.

---

## Inside-out и outside-in

| Подход | С чего начинают | Особенности |
|---|---|---|
| **Inside-out** (классический, «детройтский») | С доменной логики и мелких классов | Меньше моков, тесты устойчивее к рефакторингу |
| **Outside-in** (лондонский, mockist) | С внешнего сценария через моки коллабораторов | Быстро проясняется архитектура, но тесты сильнее связаны с реализацией |

На практике чаще смешивают: внешний сценарий задаёт направление, внутренние блоки разрабатываются классическим циклом.

---

## Родственные практики

- **BDD (Behavior-Driven Development)** — тот же цикл, но требования формулируются в терминах поведения: *Given — When — Then*. Инструменты: Cucumber, SpecFlow, в C++ — Catch2 с `SECTION`/`GIVEN`/`WHEN`/`THEN`.
- **ATDD** — тесты пишутся из приёмочных критериев, часто совместно с заказчиком.
- **Рефакторинг без тестов** — это не refactor, а переписывание с риском; TDD-цикл легализует постоянную чистку кода.

---

## Ограничения и критика

- Требует дисциплины и опыта: новички либо пропускают фазу Red, либо пишут сразу большой тест.
- Плохо ложится на исследовательский прототип, UI и код, зависящий от внешних систем без швов для подмены.
- Может привести к **test-induced design damage** — избыточным абстракциям «ради тестируемости».
- Не отменяет проектирования: без понимания модели получается набор мелких классов с тестами и без архитектуры.
- Наследие (legacy) обычно покрывают «characterization-тестами» постепенно, а не переписывают по TDD.

---

## Типичные ошибки

1. **Пропуск фазы Red**: тест, который никогда не падал, не проверен на способность падать.
2. **Большой шаг**: сразу несколько тестов и целая реализация — цикл теряет смысл.
3. **Пропуск рефакторинга** — «зелёный» код накапливает дублирование и грязь.
4. **Тестирование реализации** (проверка вызовов моков) вместо наблюдаемого поведения.
5. **TDD ради покрытия**: тесты пишутся формально, без проверок и границ.
6. **Игнорирование граничных случаев**: проверен только счастливый путь.
7. **Недетерминированные тесты** (время, сеть, случайность без инъекции) ломают ритм цикла.
8. **Отсутствие частого запуска** — цикл работает только при обратной связи в секунды.

---

## Что добавить на собеседовании

- Полезно назвать первоисточник подхода: Kent Beck, «Test-Driven Development: By Example».
- Стоит упомянуть связь с CI: TDD даёт быстрый локальный цикл, CI — общую проверку на интеграционном уровне.
- Хорошо смотрится понимание, что TDD **не про количество тестов**, а про порядок действий и минимальность шага.
- Можно добавить, что качество самих тестов проверяют **мутационным тестированием**: если внесённый в код дефект не роняет ни один тест, такой тест бесполезен.

---

## Итог

| Фаза | Действие | Результат |
|---|---|---|
| **Red** | Пишем тест на новое поведение | Требование зафиксировано, тест падает |
| **Green** | Минимальная реализация | Все тесты зелёные |
| **Refactor** | Чистим код, не меняя поведение | Дизайн улучшен, регрессия исключена |

| Аспект | Суть |
|---|---|
| Что это | Методика разработки через тесты, а не способ тестирования |
| Порядок | Тест → реализация → рефакторинг |
| Главный эффект | Управляемое проектирование API и естественное покрытие |
| Ограничение | Не заменяет интеграционные тесты и не гарантирует отсутствие багов |
