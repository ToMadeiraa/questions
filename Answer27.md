# Вопрос 27. Что именно линкует линкер?

> **Кратко:** линкер связывает **символы**, а не файлы: для каждого имени, которое объектный файл требует извне, он ищет ровно одно определение в других объектных файлах и библиотеках и подставляет вместо символической ссылки реальный адрес. Побочно он объединяет одноимённые секции всех входных файлов в сегменты будущего бинарника, применяет релокации и добавляет то, чего в объектных файлах нет: стартовый код, точку входа и записи о зависимостях.

---

## Что линкер получает на вход

Объектный файл (ELF `ET_REL`, COFF `.obj`) — не «готовая программа», а набор секций и таблиц:

| Часть `.o` | Содержимое |
|---|---|
| `.text` | машинный код функций |
| `.data` | инициализированные глобальные и статические данные |
| `.bss` | неинициализированные данные (места в файле не занимают) |
| `.rodata` | константы, строковые литералы, таблицы переходов |
| `.symtab` | таблица символов: имя, тип, привязка, секция, смещение |
| `.rela.text`, `.rela.data` | релокации: «в это место вписать адрес такой-то сущности» |
| `.debug_*` | отладочная информация DWARF при `-g` |

---

## Три операции компоновки

| Операция | Суть | Симптом сбоя |
|---|---|---|
| Разрешение символов | каждому неопределённому `U` найти ровно одно определение | `undefined reference to 'f(int)'` |
| Релокация | заменить нули-заглушки в коде и данных на реальные адреса | — |
| Слияние секций | `.text` всех файлов → один сегмент; то же для `.data`, `.bss`, `.rodata` | — |

Дополнительно линкер добавляет то, чего нет ни в одном `.o`: стартовый код (`crt1.o` с `_start`), пролог и эпилог (`crti.o`, `crtn.o`), таблицу `.init_array` для глобальных конструкторов, заголовки ELF, а для динамического бинарника — `.dynamic`, `.dynsym`, `.plt`, `.got`.

## Что такое символ на практике

```cpp
// util.h
#pragma once
int  add(int a, int b);      // объявление: символ есть, определения здесь нет
extern int g_counter;        // объявление переменной
```

```cpp
// util.cpp
#include "util.h"
int add(int a, int b) { return a + b; }   // сильный символ T
int g_counter = 0;                        // сильный символ D
```

```cpp
// main.cpp
#include "util.h"
int main() { return add(1, 2); }          // ссылка на add: символ U
```

`nm -C main.o` покажет `U add(int, int)` и `T main`, а в `util.o` — `T add(int, int)` и `D g_counter`.

| Код `nm` | Значение |
|---|---|
| `U` | не определён, требуется извне |
| `T` / `t` | определён в `.text` (глобальный / локальный) |
| `D` / `d`, `B` / `b` | данные: инициализированные / нулевые |
| `R` | константа в `.rodata` |
| `W`, `V` | слабое определение (weak) |

## Сильные, слабые символы и COMDAT

Обычная функция или переменная с внешним связыванием — **сильное** определение. Два сильных определения в разных `.o` — ошибка `multiple definition`: именно так ловится `int counter = 0;` в заголовке.

`inline`-функции, шаблоны и `inline`-переменные (C++17) порождают **слабые** определения, сгруппированные в COMDAT-секции с сигнатурой. Линкер оставляет одну копию, остальные выбрасывает; ошибки при этом нет, даже если копии различаются (это уже нарушение ODR и UB без диагностики).

```cpp
// header.h — корректно для включения в сотни .cpp
inline int counter = 0;          // C++17: одно определение на программу

template <class T>
T twice(T x) { return x + x; }   // инстанцирование тоже weak/COMDAT
```

## Статические библиотеки: почему порядок важен

`libfoo.a` — это архив `.o`-файлов с индексом символов. Линкер идёт по командной строке **слева направо** и вытаскивает из архива только те объектные файлы, которые закрывают уже накопившиеся неопределённые символы. Отсюда классические правила:

```bash
g++ main.o -L. -lfoo -o app            # библиотека после объектов, которые её требуют
g++ -L. -lfoo main.o -o app            # ошибка: на момент разбора libfoo символы ещё не нужны

g++ -Wl,--start-group -la -lb -Wl,--end-group -o app   # взаимные зависимости
g++ -Wl,--whole-archive libfoo.a -Wl,--no-whole-archive # втянуть архив целиком (регистрации)
```

## Динамические библиотеки: работа откладывается

Для `.so`/`.dll` линкер не копирует код, а записывает в `DT_NEEDED` имя библиотеки (SONAME). Разрешение символов и релокации выполняет динамический загрузчик при запуске — обычно лениво, через PLT/GOT при первом вызове.

| Понятие | Смысл |
|---|---|
| `-fPIC` / `-fPIE` | позиционно-независимый код, обязателен для `.so` |
| PLT/GOT | таблицы трамплинов и адресов для ленивого связывания |
| `LD_BIND_NOW`, `-Wl,-z,now` | отказ от ленивости (полный RELRO, предсказуемость) |
| `-fvisibility=hidden` | скрыть внутренние символы: меньше таблиц, нет перехвата |
| `-Wl,--as-needed` | не тащить в `DT_NEEDED` реально неиспользуемые библиотеки |
| `-Wl,--no-undefined` | запретить неразрешённые символы в `.so` (полезная строгость) |
| `rpath` / `LD_LIBRARY_PATH` | где искать `.so` при запуске |

Обратная сторона динамики — **перехват символов** (interposition): определение из `LD_PRELOAD` может подменить вашу функцию, поэтому «неиспользуемый» код всё равно должен быть корректен.

## Что линкер не делает

- **Не читает заголовки и не знает типов.** Он видит имена, часто уже искажённые (name mangling).
- **Не проверяет сигнатуру.** Объявление `void f(int)` и определение `void f(double)` дадут разные имена и `undefined reference`, но «похожие» типы на уровне ABI могут и не дать диагностики.
- **Не разбирает шаблоны** — инстанцирование уже сделано компилятором.
- **Не оптимизирует код** (кроме LTO и слияния одинаковых секций).

## Имя символа: mangling и `extern "C"`

```cpp
// C++ компилятор кодирует пространство имён и типы параметров в имени символа
namespace app { int add(int, int); }   // символ _ZN3app3addEii

extern "C" int c_add(int, int);        // символ c_add — без искажения, как в C
```

```cpp
// c_api.h — заголовок, пригодный и для C, и для C++
#pragma once
#ifdef __cplusplus
extern "C" {
#endif
int c_add(int a, int b);
#ifdef __cplusplus
}
#endif
```

## LTO: когда линкер всё-таки компилирует

С `-flto` объектные файлы содержат не машинный код, а промежуточное представление (GIMPLE/LLVM IR). Линкер собирает IR всех единиц трансляции, видит картину целиком и запускает оптимизатор ещё раз: появляется межфайловое встраивание, девиртуализация, удаление неиспользуемых функций.

Цена — время компоновки и требования к согласованности: все объектные файлы и библиотеки должны быть собраны одним компилятором с совместимыми флагами LTO, иначе получаем ошибки плагина или «смесь байткода и машинного кода».

## Инструменты

| Задача | Средство |
|---|---|
| символы в объектном файле | `nm -C`, `objdump -t`, `readelf -s` |
| релокации | `objdump -dr`, `readelf -r` |
| зависимости бинарника | `ldd`, `readelf -d` |
| карта секций и символов | `-Wl,-Map=app.map` |
| диагностика самого линкера | `-Wl,--verbose`, `g++ -v` |
| быстрый линкер | `gold`, `lld`, `mold` (`-fuse-ld=lld`) |

## Типичные ошибки

1. **Думать, что линкер «собирает файлы» и проверяет их совместимость.** Он сопоставляет имена символов.
2. **Путать ошибку компиляции и линковки.** «Не объявлено» — компилятор; «не определено / определено дважды» — линкер.
3. **Ставить `-lfoo` перед объектными файлами** и получать `undefined reference` при корректном коде.
4. **Определять переменную в заголовке без `inline`/`extern`** — `multiple definition` на этапе компоновки.
5. **Собирать `.so` без `-fPIC`** — ошибка релокации `R_X86_64_32 against ... can not be used when making a shared object`.
6. **Ожидать от линкера оптимизаций** без `-flto` и удивляться, что межфайлового встраивания нет.

## Что добавить на собеседовании

- Формула ответа: «линкер разрешает символы, применяет релокации и сливает секции» — три операции, которые стоит назвать явно.
- Разница между `.a` и `.so` не только в «копировать против подгружать», но и в **моменте** разрешения символов: компоновка против загрузки.
- Полезно знать, что `inline`-функции и шаблоны попадают в COMDAT именно для того, чтобы линкер мог их дедуплицировать.
- Практический навык: по тексту `undefined reference` сразу определять, чего не хватает — определения, объектного файла или библиотеки.

## Итог

| Аспект | Суть |
|---|---|
| Что связывает | символы (имена), а не исходники и не типы |
| Основные шаги | разрешение символов → релокации → слияние секций → стартовый код |
| Вход | `.o` (ELF/COFF) + `.a` + `.so`, каждый со своей таблицей символов |
| Статическая библиотека | вытаскиваются только нужные члены, порядок в командной строке важен |
| Динамическая библиотека | в бинарник идёт запись `DT_NEEDED`, адреса подставляет загрузчик |
| Сильные/слабые символы | сильные — ошибка при дублировании, слабые (inline, шаблоны) — дедупликация COMDAT |
| Чего не делает | не проверяет типы, не читает заголовки, не оптимизирует (кроме LTO) |
