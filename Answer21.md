# Вопрос 21. Как проходит процесс компиляции срр-файлов в бинарный файл?

> **Кратко:** каждый `.cpp` проходит четыре стадии: **препроцессинг** (текстовая подстановка заголовков и макросов), **компиляция** (разбор, проверка семантики, оптимизации, генерация ассемблера), **ассемблирование** (ассемблер → объектный файл с машинным кодом и таблицей символов) и **компоновка** (линкер собирает объектные файлы и библиотеки в исполняемый файл). При запуске программу подгружает ОС и динамический загрузчик.

---

## Единица трансляции

Компилятор никогда не видит «проект целиком»: он обрабатывает **единицу трансляции** (translation unit) — один `.cpp` вместе со всеми рекурсивно включёнными заголовками.

```
.cpp + .h ──[препроцессор]──> .ii ──[компилятор]──> .s ──[ассемблер]──> .o ──[линкер + библиотеки]──> app
```

---

## 1. Препроцессинг

Работает с текстом на уровне лексем, ничего не зная о типах:

- раскрывает `#include` — буквально вставляет содержимое файла;
- раскрывает макросы `#define`;
- включает/выключает фрагменты по `#if` / `#ifdef`;
- удаляет комментарии и выполняет склейку строк через `\`;
- оставляет «метки» вида `# 1 "main.cpp"` — по ним потом строятся сообщения об ошибках.

Результат — предобработанный файл (`.ii` / `.i`).

```bash
g++ -E main.cpp -o main.ii        # остановиться после препроцессора
g++ -E -dM main.cpp               # вывести все определённые макросы
```

---

## 2. Компиляция (собственно компиляция)

Самый содержательный этап, внутри него три фазы:

| Фаза | Что делает |
|---|---|
| Frontend | лексический и синтаксический разбор, построение AST, разрешение имён и перегрузок, проверка типов, инстанцирование шаблонов |
| Optimizer | свёртка констант, встраивание (`inline`), удаление мёртвого кода, разворачивание циклов, векторизация |
| Backend | выбор инструкций, распределение регистров, генерация ассемблера под целевую архитектуру |

Здесь же происходит всё, о чём говорят «ошибка компиляции»: неизвестный идентификатор, несовпадение типов, неоднозначный вызов, отсутствующая точка входа в шаблон.

```bash
g++ -S main.ii -o main.s          # ассемблерный текст для текущей архитектуры
g++ -std=c++20 -O2 -S main.cpp    # с оптимизацией
```

---

## 3. Ассемблирование

Ассемблер (`as`) переводит мнемоники в машинные инструкции и формирует **объектный файл** (`.o` / `.obj`, формат ELF или COFF/PE). В нём есть:

- секции: `.text` (код), `.data` (инициализированные данные), `.bss` (нули), `.rodata` (константы);
- **таблица символов** (`.symtab`): какие имена определены, какие только требуются извне;
- **релокации**: места, где адрес нужно подставить позже (адреса функций и глобальных переменных известны только после компоновки);
- отладочная информация (`.debug_*`, DWARF) при `-g`.

```bash
g++ -c main.s -o main.o           # только ассемблирование
nm -C main.o                      # символы: U — не определён, T — определён в .text
objdump -dr main.o                # дизассемблер + релокации
```

---

## 4. Компоновка (линковка)

Линкер (`ld`, вызывается через `collect2`) делает три вещи:

1. **Разрешает символы**: для каждого неопределённого имени (`U`) ищет ровно одно определение (`T`/`D`/`B`) в других объектных файлах и библиотеках.
2. **Применяет релокации**: подставляет реальные адреса в код и данные.
3. **Добавляет стартовый код** (`crt0`/`crt1`: `_start` → `__libc_start_main` → `main`) и информацию для загрузчика (точка входа, зависимости от `.so`).

Библиотеки: **статическая** (`libfoo.a`) — её объектные файлы буквально копируются в бинарник; **динамическая** (`libfoo.so` / `.dll`) — в бинарник попадает только запись «нужна такая-то библиотека», а код подгружается при запуске.

```bash
g++ main.o util.o -o app                       # свои объектные файлы
g++ main.o -L. -lfoo -o app                    # + библиотека libfoo
g++ main.cpp util.cpp -o app -v                # всё одной командой, -v покажет этапы
ldd ./app                                      # от чего зависит бинарник
```

---

## 5. Загрузка и запуск

`execve` передаёт управление ядру, ядро читает ELF, отображает сегменты в память, запускает **динамический загрузчик** (`ld-linux.so` в Linux, загрузчик PE в Windows), который подгружает зависимости, применяет релокации (лениво — через PLT/GOT) и передаёт управление на `_start`. Дальше стартовый код вызывает `main`, а после возврата — `exit`.

## Сводная таблица этапов

| Этап | Инструмент | Вход → выход | Флаг g++ | Типичные ошибки |
|---|---|---|---|---|
| Препроцессинг | `cpp` / `cc1plus -E` | `.cpp` + `.h` → `.ii` | `-E` | `#include` не найден, `#error`, синтаксис директив |
| Компиляция | `cc1plus` | `.ii` → `.s` | `-S` | синтаксис, типы, шаблоны, `was not declared` |
| Ассемблирование | `as` | `.s` → `.o` | `-c` | ошибки inline-ассемблера |
| Компоновка | `ld` / `collect2` | `.o` + библиотеки → `app` | (без флага) | `undefined reference`, `multiple definition`, `cannot find -lfoo` |
| Загрузка | ОС + `ld.so` | `app` → процесс | — | `error while loading shared libraries` |

## Раздельная компиляция и ошибки этапов

```cpp
// util.h — только объявление
#pragma once
int add(int a, int b);
```

```cpp
// util.cpp — определение
#include "util.h"
int add(int a, int b) { return a + b; }
```

```cpp
// main.cpp
#include "util.h"
int main() { return add(1, 2); }
```

| Что забыли | Этап, где проявится | Сообщение |
|---|---|---|
| `#include "util.h"` в `main.cpp` | компиляция | `'add' was not declared in this scope` |
| `util.cpp` в команде линковки | компоновка | `undefined reference to 'add(int, int)'` |
| `inline`/`extern` у переменной в заголовке | компоновка | `multiple definition of 'counter'` |
| заголовок с объявлением, но без библиотеки | компоновка | `undefined reference` (часто длинный список из шаблонов STL) |

Определение в заголовке без `inline` попадает в каждую единицу трансляции:

```cpp
// bad.hpp — определение в заголовке
int counter = 0;          // multiple definition при двух включающих .cpp

// good.hpp — C++17: inline-переменная, разрешено в нескольких TU
inline int counter = 0;
```

Правило: **объявление — в заголовок, определение — в один `.cpp`**; исключения — `inline`-функции/переменные, шаблоны, `constexpr` и члены класса, определённые внутри класса.

## Что даёт оптимизация и отладка

| Флаг | Эффект |
|---|---|
| `-O0` / `-O1` / `-O2` / `-O3` | уровень оптимизации; влияет на встраивание, векторизацию, время сборки |
| `-g` | отладочная информация (DWARF): имена, строки, переменные для gdb |
| `-flto` | оптимизация при компоновке: линкер видит IR всех TU и встраивает межфайлово |
| `-save-temps` | сохраняет `.ii`, `.s`, `.o` для анализа |
| `-DNDEBUG` | отключает `assert` в релизе |
| `-fsanitize=address,undefined` | инструментирование для поиска ошибок памяти и UB |

Важно: **оптимизация не меняет наблюдаемое поведение корректной программы**, но UB даёт право компилятору выкинуть «невозможную» ветку — поэтому баги, «исчезающие при `-O2`», почти всегда означают UB.

## Типичные ошибки (в понимании процесса)

1. **Считать, что линкер проверяет типы.** Он видит только имена символов, часто уже искажённые (name mangling); отсюда `undefined reference to 'foo(int)'` вместо понятного сообщения.
2. **Путать ошибку компиляции и ошибку линковки.** «Не объявлено» — компилятор, «определено дважды / не определено» — линкер.
3. **Думать, что `#include` — это «подключение библиотеки».** Это текстовая вставка на этапе препроцессинга; библиотеку подключает линкер.
4. **Забывать про независимость TU.** Изменение заголовка пересобирает всё, что его включает, а `.cpp` — только себя (отсюда нужны зависимости в Make/CMake).
5. **Объяснять «медленную сборку» только компилятором**, забывая про линковку, LTO и инстанцирование шаблонов.

---

## Что добавить на собеседовании

- Стадии описаны в стандарте как **фазы трансляции**; `#include` и макросы живут до появления типов — поэтому макросы не типизированы.
- `undefined reference` почти всегда означает «нет определения или не подключён объектный файл/библиотека», а не ошибку в коде.
- Полезно назвать практические инструменты: `nm`, `objdump`, `ldd`, `readelf`, `-save-temps`, `-v`.
- Современные ускорения: предкомпилированные заголовки, `ccache`, единственная единица трансляции (unity build), `-flto`, модули C++20.

## Итог

| Этап | Что происходит | Результат |
|---|---|---|
| Препроцессинг | подстановка `#include` и макросов, условная компиляция | `.ii` |
| Компиляция | разбор, семантика, оптимизации, генерация кода | `.s` |
| Ассемблирование | мнемоники → машинные инструкции, символы, релокации | `.o` |
| Компоновка | разрешение символов, релокации, стартовый код | `app` / `.so` |
| Загрузка | отображение в память, релокации, `_start` → `main` | работающий процесс |
