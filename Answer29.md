# Вопрос 29. Что такое флажки компиляции?

> **Кратко:** флаги компиляции — это параметры командной строки, которые говорят компилятору, **что и как** собирать: какой стандарт языка использовать, насколько агрессивно оптимизировать, добавлять ли отладочную информацию, где искать заголовки, какие макросы определить, что подключить при компоновке. Один и тот же исходник с разными флагами даёт разные бинарники — вплоть до несовместимости по ABI. Поэтому набор флагов — часть контракта проекта, и он должен быть одинаковым у всех, кто собирает код.

---

## Как устроена командная строка

Флаги принимает **драйвер** (`g++`, `clang++`, `cl.exe`), который сам вызывает препроцессор, компилятор, ассемблер и линкер. Часть флагов относится к компиляции, часть — к компоновке, а часть передаётся линкеру через `-Wl,`:

```bash
g++ -std=c++20 -O2 -g -Wall -Wextra -Iinclude -DLOG_LEVEL=2 \
    main.cpp util.cpp -Llib -lmycore -o app
```

`-std`, `-O2`, `-g`, `-Wall`, `-Wextra`, `-I`, `-D` — флаги компиляции; `-L`, `-l` и `-Wl,...` — флаги компоновки, которые драйвер передаёт линкеру.

---

## Группы флагов

| Группа | Примеры | На что влияет |
|---|---|---|
| Стандарт языка | `-std=c++20`, `-std=gnu++17`, `/std:c++20` | какие конструкции допустимы |
| Препроцессор | `-D`, `-U`, `-I`, `-isystem`, `-include` | макросы и пути поиска заголовков |
| Оптимизация | `-O0`…`-O3`, `-Os`, `-Ofast` | скорость и размер кода |
| Отладка | `-g`, `-g3`, `-Og` | отладочная информация DWARF |
| Диагностика | `-Wall`, `-Wextra`, `-Wpedantic`, `-Werror` | какие предупреждения видеть |
| Кодогенерация и ABI | `-fPIC`, `-fno-exceptions`, `-fno-rtti`, `-march`, `-fvisibility=hidden` | совместимость объектов |
| Компоновка | `-l`, `-L`, `-shared`, `-static`, `-Wl,` | что и как линкуется |
| Инструментирование | `-fsanitize=…`, `--coverage`, `-pg` | проверки и профилирование |

---

## Стандарт языка

```bash
g++ -std=c++17 main.cpp        # строгий C++17
g++ -std=gnu++17 main.cpp      # C++17 + расширения GNU (по умолчанию у GCC 11+)
g++ -std=c++20 -pedantic-errors main.cpp   # запретить расширения
```

`cl.exe` использует другую форму: `/std:c++20`; расширения Microsoft выключаются флагом `/permissive-`. Полагаться на дефолтный стандарт нельзя: он зависит от версии компилятора и меняется между релизами.

---

## Предупреждения — самый дешёвый инструмент качества

`-Wall -Wextra` включают большинство полезных проверок, но не все: `-Wconversion`, `-Wshadow`, `-Wold-style-cast` нужно добавлять руками. В CI принято `-Werror`, чтобы предупреждение не превращалось в «потом посмотрю».

```cpp
#include <cstddef>

std::size_t index(int i) {
    unsigned u = i;          // -Wsign-conversion предупредит: отрицательное станет огромным
    return u;
}

int compare(int a, unsigned b) {
    return a < b;            // -Wsign-compare: сравнение знакового с беззнаковым
}
```

Типичная ловушка: `-Werror` ломает сборку из-за предупреждений в сторонних заголовках. Лечится не отключением флага, а подключением чужих путей через `-isystem`.

## Макросы и условная компиляция

```cpp
#include <cassert>

#ifndef NDEBUG
void logDebug(const char* msg);   // соберётся только в отладочной конфигурации
#endif

int checkedDivide(int a, int b) {
    assert(b != 0);               // при -DNDEBUG вызов исчезает целиком
    return a / b;
}
```

Релизная сборка выглядит как `g++ -DNDEBUG -O2 main.cpp`; `-DNAME` эквивалентно `-DNAME=1`. Флаг влияет на **все** единицы трансляции, включая библиотеки, поэтому конфигурационные макросы должны быть согласованы во всём проекте — иначе разные `.cpp` соберут разные определения одного класса, то есть нарушат ODR.

---

## Оптимизация и отладка вместе

`-g` и `-O2` не конфликтуют: `-g` добавляет отладочную информацию, `-O2` её не удаляет. Именно так собирают `RelWithDebInfo` — профилировать и снимать стек из продакшена удобнее всего по такой сборке.

| Конфигурация | Флаги | Назначение |
|---|---|---|
| Debug | `-O0 -g` | пошаговая отладка |
| RelWithDebInfo | `-O2 -g -DNDEBUG` | профилирование, разбор падений |
| Release | `-O2 -DNDEBUG` | поставка, компактный бинарник |

## Санитайзеры и покрытие

```bash
g++ -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app_asan
g++ -g -O0 --coverage main.cpp -o app_cov && ./app_cov && gcov main.cpp
```

| Флаг | Что ищет |
|---|---|
| `-fsanitize=address` | выход за границы, use-after-free, утечки (`ASAN_OPTIONS=detect_leaks=1`) |
| `-fsanitize=undefined` | переполнения, неверные сдвиги, `nullptr`, нарушения выравнивания |
| `-fsanitize=thread` | гонки данных |
| `--coverage` | покрытие строк и ветвей |

`address` и `thread` вместе не собираются, а `-static` с ASan несовместим. Санитайзеры замедляют код в 2–20 раз, поэтому это отдельная конфигурация, а не релиз.

---

## ABI-флаги: несогласованность ломает программу молча

Некоторые флаги меняют не оптимизацию, а **двоичный интерфейс**. Если разные единицы трансляции собраны по-разному, линкер об этом не узнает:

| Флаг | Что меняет |
|---|---|
| `-fno-exceptions` | исчезает раскрутка стека; бросать исключения в таком коде нельзя |
| `-fno-rtti` | нет `dynamic_cast` и `typeid` для полиморфных типов |
| `-D_GLIBCXX_DEBUG` | меняется layout контейнеров libstdc++ |
| `-D_GLIBCXX_USE_CXX11_ABI=0` | старая ABI `std::string` |
| `-m32` / `-m64` | разрядность и размеры типов |
| `-fPIC` | позиционно-независимый код, обязателен для `.so` |

Поэтому ABI-флаги должны совпадать и у вашего кода, и у всех подключаемых библиотек — иначе получаем загадочные падения на границе вызовов.

## GCC/Clang и MSVC: соответствия

| Задача | GCC / Clang | MSVC |
|---|---|---|
| Стандарт | `-std=c++20` | `/std:c++20` |
| Оптимизация | `-O2` / `-O3` | `/O2` / `/Ox`, отключить — `/Od` |
| Отладочная информация | `-g` | `/Zi` (+ `/DEBUG` при линковке) |
| Предупреждения | `-Wall -Wextra` | `/W4`, ошибки — `/WX` |
| Определить макрос | `-DFOO=1` | `/DFOO=1` |
| Путь заголовков | `-Iinclude` | `/Iinclude` |
| Диалект | `-pedantic` | `/permissive-` |
| Исключения | включены по умолчанию | `/EHsc` |
| LTO | `-flto` | `/GL` + `/LTCG` |

## Как флаги попадают в сборку

Ручная командная строка живёт только в маленьких примерах. В проекте флаги задаются в системе сборки:

```cmake
add_executable(app main.cpp util.cpp)
target_compile_features(app PRIVATE cxx_std_20)

target_compile_options(app PRIVATE
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall -Wextra -Wpedantic -Wconversion>
    $<$<CXX_COMPILER_ID:MSVC>:/W4 /permissive->)

target_compile_definitions(app PRIVATE APP_VERSION="1.0")
target_link_libraries(app PRIVATE mycore)
```

Так флаги наследуются всеми целями-потребителями, остаются кроссплатформенными и не расходятся между разработчиками и CI.

---

## Типичные ошибки

1. **Собирать части проекта с разными ABI-флагами** (`-fno-rtti`, `_GLIBCXX_DEBUG`, `-m32`) — ошибка проявляется в лучшем случае падением.
2. **Ставить `-Werror` глобально**, включая чужие заголовки, и получать «сломанную» сборку из-за стороннего кода.
3. **Думать, что `-g` замедляет программу** — он увеличивает размер файла, но не время выполнения.
4. **Собирать релиз с `-O0`** и удивляться, что профиль не соответствует реальности.
5. **Забыть `-pthread`** при работе с `std::thread` в Linux — получаем ошибку линковки или `std::system_error` уже в рантайме.
6. **Полагаться на `-march=native`** в бинарнике, который поедет на другой процессор.

---

## Что добавить на собеседовании

- Разделять флаги по этапам: препроцессор, компиляция, компоновка — и понимать, что `-Wl,` существует именно потому, что драйвер не всё делает сам.
- Назвать «джентльменский набор» для CI: `-Wall -Wextra -Werror`, отдельная сборка с ASan/UBSan, отдельная с `-fsanitize=thread`.
- Упомянуть, что флаги оптимизации и отладки не конфликтуют, а ABI-флаги — конфликтуют, и это разные категории.
- Показать, что флаги — часть воспроизводимости сборки: версия компилятора, стандарт и набор опций должны быть зафиксированы, иначе «у меня собирается» превращается в проблему.

| Аспект | Суть |
|---|---|
| Что это | параметры драйвера компилятора, задающие режим сборки |

| Влияние на результат | меняют скорость, размер, диагностику и двоичную совместимость |

| Практика | флаги живут в системе сборки, а не в голове разработчика |
