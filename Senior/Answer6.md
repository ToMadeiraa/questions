# 6. Что делать, если код работает медленно?

Короткий ответ: **сначала измерить, потом оптимизировать — и только то, что действительно тормозит**. Преждевременная оптимизация почти всегда тратит время впустую и усложняет код. Ниже — подробный разбор по шагам.

---

## 0. Главный принцип

Порядок действий почти всегда одинаков:

1. **Зафиксировать проблему** — что именно медленно и насколько (метрика, а не ощущение).
2. **Найти узкое место** — профилированием, а не догадками.
3. **Понять причину** — алгоритм, память, I/O, блокировки, сеть, БД.
4. **Исправить самое дорогое** — одно изменение за раз.
5. **Проверить, что стало быстрее** — тем же способом, что и мерили.
6. **Закрепить** — бенчмарк/тест, чтобы регрессия не вернулась.

Правило: **не оптимизируйте код, который не в «горячем» пути**. Закон Амдала никто не отменял: ускорение 10× участка, занимающего 5 % времени, даёт выигрыш меньше 5 %.

---

## 1. Уточните, что значит «медленно»

«Медленно» — не техническая характеристика. Нужно перевести её в измеримое:

- **Латентность** — сколько ждёт один запрос/вызов (p50, p95, p99, а не только среднее).
- **Пропускная способность** — сколько операций в секунду.
- **Время старта** — холодный запуск, инициализация.
- **Потребление ресурсов** — CPU, RAM, диск, сеть, батарея.

Полезно сразу ответить на вопросы:

- Медленно **всегда** или только на больших данных / под нагрузкой?
- Медленно **у всех** или у части пользователей (регион, железо, ОС)?
- Это **регрессия** (раньше было быстро) или так было всегда?
- Какие **SLA/бюджеты**: «ответ API < 200 мс», «обработка файла < 1 мин».

Без числового критерия нельзя понять, когда оптимизацию пора прекращать.

---

## 2. Профилирование: найдите горячие точки

Профилировщик показывает, **где реально тратится время**, а не где вам кажется.

### Виды профилирования

| Тип | Что даёт | Когда использовать |
|---|---|---|
| **Sampling** (сэмплирующий) | Стек вызовов с периодом, малые накладные расходы | Почти всегда для первого взгляда |
| **Instrumentation** (трассирующий) | Точные счётчики вызовов и времени | Когда нужны детали по функциям |
| **Профиль памяти** | Аллокации, утечки, пиковое потребление | RAM растёт, GC «душит» |
| **Профиль I/O / syscalls** | Диск, сеть, ожидание | Низкий CPU, но медленно |
| **Профиль блокировок** | Конкуренция за мьютексы | Много потоков, низкая утилизация |

### Инструменты по стекам

- **Python**: `cProfile` + `pstats`, `py-spy` (без перезапуска, в проде), `line_profiler`, `memory_profiler`, `tracemalloc`, `scalene`.
- **JavaScript/Node**: `node --prof`, Chrome DevTools (Performance, Memory), `clinic.js`.
- **Java/JVM**: JFR, async-profiler, VisualVM, JProfiler, `-Xlog:gc`.
- **C/C++**: `perf record/report`, `valgrind --tool=callgrind`, `gprof`, VTune, `-pg`.
- **Go**: `pprof` (`net/http/pprof`), `go tool trace`.
- **Rust**: `perf`, `cargo flamegraph`, `dhat`.
- **C#/.NET**: dotTrace, PerfView, `dotnet-counters`, `dotnet-trace`.
- **SQL**: `EXPLAIN (ANALYZE, BUFFERS)`, slow query log, pg_stat_statements.
- **Система целиком**: `strace`, `ltrace`, `bpftrace`, `iostat`, `vmstat`, `htop`.

### Пример (Python)

```python
import cProfile, pstats

cProfile.run("main()", "prof.out")
pstats.Stats("prof.out").sort_stats("cumulative").print_stats(20)
```

Смотрите на **cumulative** (включая вызываемые функции) и **self** (собственное время). Горячая точка — функция с большим `self`-временем или с огромным числом вызовов.

Важно: профилируйте **на репрезентативных данных** и **в реалистичном окружении** (та же БД, те же объёмы, прод-конфиг). Профиль на 10 строках тестовой таблицы покажет не то, что происходит на миллионе.

## 3. Измеряйте корректно

Плохие замеры ведут к плохим решениям.

- **Прогрев**: JIT, кэши, пулы соединений — первые итерации не показательны.
- **Достаточное число повторений** и статистика: медиана, p95, разброс, а не один запуск.
- **Изоляция**: не мерить при работающей сборке мусора, фоновой индексации, других процессах.
- **Репрезентативные входные данные**: размеры, распределения, худший случай.
- **Микробенчмарки осторожно**: компилятор/JIT может выбросить «бесполезный» код; используйте готовые фреймворки (`JMH` для Java, `pytest-benchmark`, `hyperfine`, `criterion` для Rust, `benchmark` для Go).
- **Сравнивайте одинаковое с одинаковым**: та же машина, тот же билд-режим (не debug против release).

## 4. Алгоритмическая сложность — самый большой выигрыш

Чаще всего «медленно» — это **неверный алгоритм**, а не медленный язык.

- Проверьте асимптотику: `O(n²)` на 100 000 элементов — это 10¹⁰ операций.
- Ищите **вложенные циклы по одним и тем же данным**, повторный пересчёт, линейный поиск в цикле.
- Классика: заменить `list.index()`/`in list` на `set`/`dict` — `O(n)` → `O(1)`.
- Сортировка вместо повторного поиска минимума; префиксные суммы; хеш-таблицы; куча; two pointers; бинарный поиск.
- **Мемоизация** повторяющихся вычислений (`functools.lru_cache`, `@cache`).

```python
# Было: O(n²)
for x in items:
    if x in big_list:      # линейный поиск
        ...

# Стало: O(n)
big_set = set(big_list)
for x in items:
    if x in big_set:
        ...
```

Прежде чем браться за микрооптимизации, оцените сложность по `n` и по объёму данных.

## 5. Структуры данных, память и аллокации

- **Правильная структура данных** важнее микротюнинга: `deque` для очереди, `heapq` для приоритетов, `dict`/`set` для поиска, массивы вместо связных списков там, где важна локальность.
- **Локальность кэша**: обход по строкам матрицы быстрее, чем по столбцам (в C/C++/Rust это критично). Struct of Arrays vs Array of Structs.
- **Аллокации дороги**: переиспользуйте буферы, избегайте создания объектов в горячем цикле, используйте `StringBuilder`/`join` вместо конкатенации строк в цикле.
- **Копирование**: лишние `deepcopy`, срезы больших массивов, передача по значению — всё это стоит.
- **GC-давление**: много短коживущих объектов → частые сборки. Помогает пулирование, уменьшение аллокаций, настройка GC.
- **Кэш-промахи** и **false sharing** — тема для нагруженных многопоточных программ.

```python
# Плохо: O(n²) по копированию
s = ""
for part in parts:
    s += part

# Хорошо: O(n)
s = "".join(parts)
```

## 6. Ввод-вывод, сеть и база данных

Если CPU загружен слабо, а код медленный — почти наверняка вы ждёте I/O.

- **Батчинг**: один запрос на 1000 строк вместо 1000 запросов; bulk insert; пачки HTTP-запросов.
- **N+1 запросов** в ORM — классика. Решается `JOIN`, `select_related`/`prefetch_related`, `IN (...)`, DataLoader.
- **Индексы** в БД, `EXPLAIN ANALYZE`, отсутствие `SELECT *`, пагинация вместо выгрузки всего.
- **Кэширование** результатов: память, Redis/Memcached, HTTP-кэш, CDN.
- **Асинхронность** для сетевых ожиданий (`asyncio`, `async/await`, неблокирующий I/O) — но не для CPU-задач.
- **Сжатие и сериализация**: бинарные форматы (protobuf, msgpack) вместо тяжёлого JSON, если это узкое место.
- **Пулы соединений** и переиспользование дорогих ресурсов (TCP, TLS, файловые дескрипторы).
- **Файловые операции**: буферизация, `mmap`, последовательное чтение вместо случайного, меньше `fsync`.

## 7. Параллелизм и конкурентность

- **CPU-bound** → процессы/потоки/пул воркеров (в Python — `multiprocessing`, т.к. GIL; либо нативные расширения).
- **I/O-bound** → асинхронность или пул потоков.
- **Закон Амдала**: ускорение ограничено долей последовательного кода. 10 ядер не спасут, если 50 % работы последовательны.
- **Блокировки**: избыточная синхронизация, глобальный мьютекс, contention — ищите профилем блокировок; уменьшайте критическую секцию, используйте lock-free/атомики, шардирование.
- **Избегайте oversubscription**: потоков сильно больше, чем ядер, — только хуже.
- **Векторизация**: SIMD, `numpy`/`polars` вместо циклов на Python, batch-операции.

```python
# CPU-bound: пул процессов, а не потоков (обходим GIL)
from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor() as pool:
    results = list(pool.map(heavy_func, data))
```

## 8. Уровень рантайма и компилятора

- **Release-режим**: `-O2`/`-O3`, `--release`, отключённые assert'ы и debug-логи.
- **PGO/LTO**, `-march=native` (осторожно с переносимостью), `-flto`.
- **JIT-прогрев** и настройки JVM/Node: размер heap, GC, `-XX:+UseG1GC`/ZGC.
- **Интерпретируемые языки**: узкие места выносить в нативные расширения (C/Rust/Cython/Numba), использовать векторизованные библиотеки.
- **Логирование**: `DEBUG`-логи в горячем цикле могут стоить дороже самой работы; используйте ленивое форматирование и уровни.
- **Сериализация и рефлексия** в горячих путях — часто неожиданно дорого.

---

## 9. Кэширование и ленивые вычисления

- **Кэш** на уровне функции (memoization), объекта, процесса, распределённый.
- **Ленивые вычисления**: не считайте то, что не нужно; генераторы вместо материализации списков; `yield`.
- **Инвалидация кэша** — главная сложность: TTL, версионирование, ключи.
- Осторожно с **кэшем преждевременным**: он усложняет код и может маскировать проблему. Сначала убедитесь, что вычисление действительно повторяется.

---

## 10. Архитектурные решения

Когда микрооптимизации исчерпаны, а нагрузка растёт:

- **Вынести тяжёлое в фон**: очереди (RabbitMQ, Kafka, Celery, Sidekiq), воркеры, отложенные задачи. Пользователь получает ответ сразу.
- **Разделение чтения и записи**, реплики, денормализация, материализованные представления.
- **Горизонтальное масштабирование** и шардирование.
- **Предвычисление** агрегатов, отчётов, снапшотов.
- **Ограничение объёма работы**: пагинация, лимиты, таймауты, circuit breaker, backpressure.
- **Асинхронная обработка** там, где синхронный ответ не обязателен.

---

## 11. Что делать после оптимизации

- **Закрепите результат бенчмарком** в CI (или хотя бы скриптом), иначе регрессия вернётся.
- **Задокументируйте**, почему код написан именно так (комментарий «почему», а не «что»).
- **Проверьте корректность**: оптимизация не должна менять поведение. Тесты — обязательны.
- **Следите в проде**: APM, метрики латентности, профилирование по расписанию, алерты на p99.
- **Не тащите сложность без выигрыша**: если ускорение 2 % ценой читаемости — скорее всего, не стоит.

## 12. Частые ошибки

| Ошибка | Чем плохо |
|---|---|
| Оптимизация «на глаз» | Ускоряете не тот участок |
| Микрооптимизация без профиля | Время потрачено, эффекта нет |
| Замер на нерепрезентативных данных | Выводы не переносятся на прод |
| Один замер без прогрева | JIT/кэши искажают результат |
| Игнорирование алгоритмической сложности | `O(n²)` не лечится `-O3` |
| Кэш «на всякий случай» | Баги инвалидации, сложность |
| Потоки для CPU-bound в Python | GIL не даёт ускорения |
| Оптимизация ценой читаемости без нужды | Поддержка дороже выигрыша |

---

## 13. Краткий чек-лист

1. Сформулируйте числовой критерий «быстро».
2. Воспроизведите проблему на репрезентативных данных.
3. Снимите профиль (CPU, память, I/O, блокировки).
4. Найдите 1–2 главные горячие точки.
5. Проверьте алгоритмическую сложность и структуры данных.
6. Проверьте I/O: N+1, батчинг, индексы, сеть.
7. Проверьте аллокации, копирование, GC.
8. При необходимости — параллелизм/асинхронность/векторизация.
9. Проверьте release-режим, флаги, логи.
10. Измерьте снова тем же способом.
11. Закрепите бенчмарком и тестами.
12. Задокументируйте решение.

---

**Итог:** медленный код — это почти всегда вопрос **измерения и поиска узкого места**, а не «переписать на другом языке». В 80 % случаев выигрыш даёт правильный алгоритм, структура данных, устранение лишнего I/O и батчинг; оставшиеся 20 % — это уже тюнинг рантайма, памяти и параллелизма.
