# 31. В чем особенности контейнеров std::set, std::map, std::unordered_map, std::hash?

Сразу важное уточнение по формулировке: **`std::hash` — это не контейнер**. Это функциональный объект (хешер) из `<functional>` и одновременно точка кастомизации, которую по умолчанию используют неупорядоченные контейнеры. А `std::set`, `std::map`, `std::unordered_map` — это три ассоциативных контейнера: два упорядоченных и один неупорядоченный.

## Общая картина

| | `std::set` | `std::map` | `std::unordered_map` |
|---|---|---|---|
| Категория | упорядоченный ассоциативный | упорядоченный ассоциативный | неупорядоченный ассоциативный |
| Внутренняя структура (на практике) | красно-чёрное дерево | красно-чёрное дерево | хеш-таблица |
| Упорядоченность | по компаратору | по ключу | порядок не определён |
| Ключи уникальны | да | да | да |
| Требования к ключу | strict weak ordering (`<` или компаратор) | то же | `Hash` + `KeyEqual` |
| Поиск | `O(log n)` | `O(log n)` | `O(1)` в среднем, `O(n)` в худшем |
| Итераторы | bidirectional | bidirectional | forward |
| Узловая модель | да | да | да (ссылки/указатели стабильны) |
| Порядковые операции (`lower_bound` и т.п.) | есть | есть | нет |
| Дополнительно | — | `operator[]`, `at`, `insert_or_assign` | `bucket_count`, `load_factor`, `rehash`, `reserve` |

Все три — **узловые** (node-based): элементы лежат в отдельных узлах, поэтому вставка не инвалидирует итераторы и ссылки на существующие элементы, а `erase` инвалидирует только итераторы/ссылки на удалённые элементы. Плата за это — фрагментация памяти, накладные расходы на узел и плохая локальность (обход дерева/таблицы медленнее обхода `std::vector`).

## std::set

```cpp
template<class Key,
         class Compare = std::less<Key>,
         class Allocator = std::allocator<Key>>
class set;
```

Особенности:

1. **Хранит только ключи**, без «значения». Это математическое множество с уникальными элементами.
2. **Всегда отсортирован** по `Compare`; обход даёт возрастающую последовательность. Компаратор должен задавать *strict weak ordering*: `comp(a,a) == false`, транзитивность, антисимметричность. Нарушение — неопределённое поведение (обычно «потерянные» элементы или падение).
3. **Ключ неизменяем**: `iterator` и `const_iterator` для `set` фактически константные, `*it` нельзя присвоить. Изменить ключ «на месте» нельзя — только извлечь и вставить заново (см. node handle ниже). Попытка `const_cast` — UB.
4. **Вставка**: `insert`/`emplace` возвращают `std::pair<iterator, bool>`; `bool == false`, если эквивалентный ключ уже есть (элемент не заменяется). С hint-версией вставка в «правильную» позицию — амортизированно `O(1)`.
5. **Поиск**: `find`, `count` (0 или 1), `contains` (C++20), `equal_range`, `lower_bound`/`upper_bound` — последние два есть только у упорядоченных контейнеров.
6. **Итераторы**: bidirectional, стабильны при вставке; `erase(it)` возвращает итератор на следующий элемент (C++11).
7. **C++17**: `extract` (node handle), `merge` (перенос узлов без копирования/перемещения элементов; при конфликте ключей узел остаётся в источнике).
8. **C++14 и позже**: прозрачный компаратор (`std::less<>`) включает гетерогенный поиск — можно искать по `const char*` в `set<std::string>` без создания временной строки.
9. **Память**: накладные расходы на узел (обычно 3 указателя + цвет) плюс аллокация на каждый элемент. Для `set<int>` это часто 40+ байт на элемент.

```cpp
std::set<int> s{3, 1, 2};          // {1, 2, 3}
auto [it, ok] = s.insert(2);       // ok == false, it -> существующая 2
s.erase(1);

std::set<std::string, std::less<>> ss;
ss.insert("hello");
ss.find("hello");                  // без временного std::string (C++14)
```

## std::map

```cpp
template<class Key, class T,
         class Compare = std::less<Key>,
         class Allocator = std::allocator<std::pair<const Key, T>>>
class map;
```

Всё сказанное про `std::set` про ключи и компаратор верно и здесь, но есть специфика:

1. **`value_type` — это `std::pair<const Key, T>`**. Ключ (`first`) константный, значение (`second`) изменяемое. Именно поэтому `map` нельзя использовать там, где нужен `std::pair<Key, T>` без конвертаций.
2. **`operator[]`** — не константный и **вставляет** элемент со значением `T{}`, если ключа нет. Требует default-конструируемости `T`. Для поиска без вставки используют `find`, `at` (бросает `std::out_of_range`) или `contains`.
3. **`at` vs `[]`**: `at` не вставляет и безопаснее для чтения; `[]` удобен для «счётчика»/аккумулятора.
4. **Способы вставки**:
   - `insert({k, v})` / `emplace(k, v)` — не перезаписывают существующий ключ;
   - `insert_or_assign(k, v)` (C++17) — перезаписывает;
   - `try_emplace(k, args...)` (C++17) — конструирует `T` только если ключа нет (важно для дорогих `T`);
   - `operator[]` — вставляет default и возвращает ссылку.
5. **Смена ключа**: ключ константный, но с C++17 можно `extract` → изменить `nh.key()` → `insert(std::move(nh))`:

```cpp
std::map<int, std::string> m{{1, "a"}, {2, "b"}};
auto nh = m.extract(1);
nh.key() = 10;
m.insert(std::move(nh));   // {2:"b", 10:"a"}
```

6. **Итерация** — по возрастанию ключа; `begin()->first` — минимальный ключ. `lower_bound`/`upper_bound`/`equal_range` дают диапазонные запросы.
7. `merge` (C++17) переносит узлы из другого `map`/`multimap` без копирования; при совпадении ключа узел не переносится.

```cpp
std::map<std::string, int> freq;
for (auto& w : words) ++freq[w];          // вставка при отсутствии
if (auto it = freq.find("cat"); it != freq.end())
    std::cout << it->second;
```

## std::unordered_map

```cpp
template<class Key, class T,
         class Hash = std::hash<Key>,
         class KeyEqual = std::equal_to<Key>,
         class Allocator = std::allocator<std::pair<const Key, T>>>
class unordered_map;
```

Особенности:

1. **Хеш-таблица**: ключ → бакет (bucket). Средний поиск/вставка/удаление — `O(1)`, но **худший случай `O(n)`** при массовых коллизиях (плохой хеш или атака).
2. **Требования к ключу**: должен быть хешируемым (`std::hash<Key>` или свой `Hash`) и сравнимым на равенство (`std::equal_to<Key>` или свой `KeyEqual`). При этом **равенство обязано быть согласовано с хешем**: если `eq(a, b)`, то `hash(a) == hash(b)`. Иначе — UB: элемент «есть», но `find` его не находит.
3. **Порядок обхода не определён** и может меняться после `rehash`/`insert`. Полагаться на него нельзя.
4. **Инвалидация**: `rehash` инвалидирует итераторы, но **не инвалидирует ссылки и указатели на элементы** (контейнер узловой). `erase` инвалидирует только итераторы/ссылки на удалённые элементы. `insert`, вызвавший rehash, инвалидирует итераторы.
5. **Load factor**: `load_factor() == size() / bucket_count()`, по умолчанию `max_load_factor() == 1.0`. При превышении происходит rehash. `reserve(n)` заранее выделяет бакеты под `n` элементов — полезно, чтобы избежать серии rehash.
6. **Bucket API**: `bucket_count()`, `bucket(key)`, `bucket_size(i)`, `begin(i)`/`end(i)` (`local_iterator`). Это деталь реализации, но она входит в стандартный интерфейс.
7. **`value_type`** — тоже `std::pair<const Key, T>`; `operator[]`, `at`, `insert_or_assign`, `try_emplace` работают аналогично `map`.
8. **C++20**: `contains`, гетерогенный поиск при прозрачных `Hash` и `KeyEqual` (`is_transparent`).
9. **Память**: узел + массив бакетов; обычно дороже по памяти, чем `map`, но быстрее по скорости доступа. Из-за разброса узлов по памяти обход заметно медленнее, чем у вектора.
10. **Худший случай и безопасность**: стандартный `std::hash` не криптостойкий и часто предсказуем (FNV, Murmur и т.п.), поэтому возможны hash-flooding атаки с деградацией до `O(n)`. Для недоверенных входных данных применяют keyed-hash (например, SipHash) через собственный `Hash`.

```cpp
std::unordered_map<std::string, int> m;
m.reserve(1000);
m["a"] = 1;
m.try_emplace("b", 2);
m.insert_or_assign("a", 10);
```

## std::hash

```cpp
template<class Key> struct hash;
```

Это **не контейнер**, а шаблон функционального объекта: `std::size_t h = std::hash<Key>{}(key);`. Он лежит в `<functional>`.

1. **Специализации** есть для фундаментальных типов, указателей, `std::string`, `std::string_view`, `std::thread::id`, `std::error_code`, `std::bitset`, `std::vector<bool>` и др. Для перечислений — с C++14, для `nullptr_t` — с C++17.
2. **Для пользовательского типа** первичный шаблон не даёт рабочей специализации: без своей специализации `std::hash<MyType>` использовать нельзя (ошибка компиляции). Варианты:
   - явная специализация `std::hash<MyType>` в `namespace std` (это разрешено для program-defined типов);
   - передать свой хешер параметром шаблона `unordered_map` (предпочтительнее — не «загрязняет» `std`).
3. **Требования к хешеру** (named requirement `Hash`):
   - default- и copy-constructible, callable на `const` объекте;
   - возвращает `std::size_t`;
   - **детерминирован**: для одного и того же `k` в пределах одного запуска программы результат одинаков;
   - согласован с равенством: `a == b ⇒ hash(a) == hash(b)`;
   - не должен бросать исключений (стандартные специализации `noexcept`).
4. **Не гарантируется**:
   - одинаковый результат между запусками, платформами, реализациями и версиями стандартной библиотеки — хеши нельзя сохранять на диск или передавать по сети;
   - хорошее качество распределения — это ответственность реализации;
   - криптостойкость.
5. **Типичные ловушки**:
   - `std::unordered_map<const char*, int>` хеширует **адрес**, а не строку — почти всегда ошибка; нужен `std::string` или свой хешер;
   - `std::hash<double>` обязан давать одинаковый хеш для `+0.0` и `-0.0` (они равны), но для NaN ограничений нет (NaN ≠ NaN);
   - `std::hash<std::string>` и `std::hash<std::string_view>` не обязаны совпадать — для гетерогенного поиска нужен прозрачный хешер;
   - для `std::pair`, `std::tuple`, `std::vector` и своих агрегатов `std::hash` нет — нужен свой.

Пример для пользовательского типа:

```cpp
struct Point { int x, y; };

struct PointHash {
    std::size_t operator()(const Point& p) const noexcept {
        std::size_t h1 = std::hash<int>{}(p.x);
        std::size_t h2 = std::hash<int>{}(p.y);
        return h1 ^ (h2 + 0x9e3779b97f4a7c15ULL + (h1 << 6) + (h1 >> 2));
    }
};
struct PointEq {
    bool operator()(const Point& a, const Point& b) const noexcept {
        return a.x == b.x && a.y == b.y;
    }
};

std::unordered_map<Point, int, PointHash, PointEq> m;
```

Для упорядоченного варианта достаточно компаратора:

```cpp
struct PointLess {
    bool operator()(const Point& a, const Point& b) const {
        return std::tie(a.x, a.y) < std::tie(b.x, b.y);
    }
};
std::set<Point, PointLess> s;
std::map<Point, int, PointLess> mp;
```

## Прозрачный (гетерогенный) поиск

Упорядоченные контейнеры (C++14):

```cpp
std::map<std::string, int, std::less<>> m;
m.find("key");   // без создания std::string
```

Неупорядоченные (C++20):

```cpp
struct SvHash {
    using is_transparent = void;
    std::size_t operator()(std::string_view sv) const noexcept {
        return std::hash<std::string_view>{}(sv);
    }
};

std::unordered_map<std::string, int, SvHash, std::equal_to<>> m;
m.find(std::string_view{"key"});
```

## Типичные ошибки

1. **Компаратор не strict weak ordering** — UB, «пропадающие» элементы.
2. **Хеш несогласован с `operator==`** — `find` не находит существующий ключ; UB.
3. **Изменение ключа через `const_cast`** — UB; используйте `extract`/`insert`.
4. **`m[key]` для чтения** — молча вставляет элемент; для чтения `find`/`at`/`contains`.
5. **`unordered_map<const char*, ...>`** — хешируется указатель, а не строка.
6. **Ожидание порядка обхода** у `unordered_map` — его нет.
7. **Сохранение `std::hash` в файл/БД** — значения не переносимы между запусками и платформами.
8. **`map`/`set` для маленьких наборов** — часто `std::vector` + `sort` + `binary_search` (или `boost::flat_map`, `std::flat_map` в C++23) быстрее из-за локальности и меньших накладных расходов.
9. **Итераторы после `rehash`** у `unordered_map` — нельзя хранить между вставками.

## Что выбирать

- Нужен **порядок**, диапазонные запросы (`lower_bound`), стабильный обход, детерминированный вывод — `std::map`/`std::set`.
- Нужен **быстрый доступ по ключу**, порядок не важен, ключ хорошо хешируется — `std::unordered_map` (при необходимости с `reserve`).
- Нужно **множество без значений** — `std::set`/`std::unordered_set`; с дубликатами — `multiset`/`multimap`/`unordered_multimap`.
- Нужна **своя политика хеширования/сравнения** — параметры `Hash`, `KeyEqual`, `Compare`; `std::hash` — лишь дефолт для неупорядоченных контейнеров, а не самостоятельный контейнер.
