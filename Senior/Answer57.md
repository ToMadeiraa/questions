# 57. Что делает спецификатор thread_local?

## Кратко

`thread_local` — это спецификатор класса памяти (storage-class specifier) в C++11 и `_Thread_local` в C11, который задаёт переменной **потоковую продолжительность хранения** (thread storage duration). Проще говоря: у каждого потока появляется **свой собственный экземпляр** такой переменной, живущий ровно столько, сколько живёт поток. Один и тот же код, обращающийся к имени `x`, в разных потоках работает с разными объектами `x`.

```cpp
thread_local int counter = 0;

void worker() {
    ++counter;          // у каждого потока свой counter
    // ...
}
```

Если запустить 8 потоков, каждый увидит и увеличит свою копию: взаимных гонок за эту переменную нет просто потому, что данные не разделяются. Это не «магия синхронизации», а именно **раздельные объекты**.

## Формальный смысл

Стандарт C++ ([basic.stc.thread]) формулирует так: все переменные, объявленные с `thread_local`, имеют потоковую продолжительность хранения; хранилище для них существует в течение времени жизни потока, в котором они созданы; **для каждого потока существует отдельный объект или ссылка**, и использование объявленного имени относится к сущности, связанной с текущим потоком.

Отсюда следуют важные свойства:

| Свойство | Значение |
|---|---|
| Время жизни | от создания/инициализации до завершения потока |
| Количество экземпляров | по одному на каждый поток |
| Адрес | у разных потоков, как правило, разный |
| Синхронизация | не требуется, если поток обращается только к своей копии |
| Связь с `std::thread` | нет: привязка к **потоку ОС**, а не к объекту `std::thread` |

Типичный пример из стандартной библиотеки — `errno`: формально это макрос, разворачивающийся в обращение к потоково-локальному объекту, поэтому `errno` в одном потоке не затирает `errno` в другом.

## Синтаксис и где его можно применять

`thread_local` применим **только к переменным** (объектам и ссылкам). Нельзя объявить `thread_local`-функцию, тип или нестатический член класса.

Разрешённые места:

```cpp
// 1. Пространство имён (глобальная переменная)
thread_local int g = 42;

// 2. Статический член класса
struct Cache {
    static thread_local std::vector<int> buffer;
};
thread_local std::vector<int> Cache::buffer;   // определение

// 3. Локальная переменная в блоке
void f() {
    thread_local std::mt19937 rng{std::random_device{}()};
    // ...
}

// 4. Комбинации с другими спецификаторами
static thread_local int a;          // внутреннее связывание
extern thread_local int b;          // объявление, определение в другой TU
const thread_local int c = 1;       // const + thread_local
constexpr thread_local int d = 2;   // постоянно инициализирована
inline thread_local int e = 0;      // C++17: одно определение на программу,
                                    // но по экземпляру на поток
```

Ограничения и правила:

- нельзя применять к параметрам функции;
- нестатический член класса объявить `thread_local` нельзя — только `static thread_local`;
- в блоке `thread_local` неявно даёт статическую продолжительность хранения (переменная переживает выход из функции, но только в пределах своего потока);
- все объявления одной сущности должны быть согласованы по `thread_local`;
- `thread_local` можно комбинировать с `static`, `extern`, `const`, `constexpr`, `volatile`, `alignas`;
- в C++20 `thread_local` совместим с `constinit` (гарантия константной инициализации).

## Инициализация

Здесь C++ и C расходятся, и это ключевой практический момент.

### Переменные в пространстве имён и статические члены

Инициализация выполняется **для каждого потока**. Константная инициализация (например, `thread_local int x = 5;` или `constexpr`) не требует кода во время выполнения. Динамическая инициализация (`thread_local std::string s = make_name();`) происходит до первого использования переменной в данном потоке — стандарт разрешает отложить её, но требует, чтобы она произошла до первого odr-use переменной (на практике реализации либо создают TLS-блок при старте потока, либо инициализируют лениво с проверкой guard-флага).

Если динамическая инициализация переменной с потоковой продолжительностью хранения на уровне пространства имён завершается исключением, вызывается `std::terminate`.

### Локальные (блочные) переменные

Блочная `thread_local`-переменная инициализируется **при первом прохождении управления через её объявление в этом потоке**:

```cpp
void log(const std::string& msg) {
    thread_local std::string prefix = build_prefix(); // вызовется один раз на поток
    std::cout << prefix << msg << '\n';
}
```

Тонкости:

- если поток ни разу не прошёл через объявление, объект не создаётся и деструктор не вызывается;
- если инициализация выбросила исключение, переменная считается неинициализированной, и при следующем проходе инициализация **повторится**;
- если во время инициализации управление рекурсивно снова входит в то же объявление (например, через рекурсию, `std::function`, колбэк), поведение **не определено** — как и для блочных `static`;
- для константно инициализируемых блочных переменных guard-проверка не нужна, доступ дешевле.

### C11

В C `_Thread_local` (или `thread_local` из `<threads.h>`) не имеет ни динамической инициализации, ни деструкторов: инициализатор должен быть константным выражением, а «разрушать» нечего.

```c
#include <threads.h>

_Thread_local int tls_counter = 0;
static _Thread_local char buf[256];

void f(void) {
    static _Thread_local int calls;  // ноль-инициализация, без кода
    ++calls;
}
```

## Уничтожение

Объекты с потоковой продолжительностью хранения уничтожаются **при завершении потока**, в порядке, обратном порядку завершения их конструкторов (аналогично статическим объектам). Для главного потока — после возврата из `main`; взаимный порядок с деструкторами статических объектов стандартом не гарантируется (в glibc, например, статические деструкторы, зарегистрированные через `atexit`, обычно отрабатывают раньше TLS-деструкторов, но полагаться на это нельзя).

Практические следствия:

- деструкторы `thread_local`-объектов не выполняются, если поток завершён аварийно (`std::terminate`, `abort`, `_exit`);
- если деструктор бросает исключение при выходе из потока — `std::terminate`;
- каждый `thread_local`-объект с нетривиальным деструктором требует регистрации в списке деструкторов потока (`__cxa_thread_atexit` в Itanium ABI) — это заметный overhead на создание/уничтожение потока при большом числе таких переменных.

## Типичные применения

1. **Устранение гонок без блокировок.** Счётчики, буферы, кэши, состояние парсера — если данные не должны разделяться, `thread_local` дешевле мьютекса.
2. **Генераторы случайных чисел.** `std::mt19937` — тяжёлый объект, и его общий экземпляр требует синхронизации:
   ```cpp
   thread_local std::mt19937 rng{std::random_device{}()};
   ```
3. **Аллокаторы и арены.** Каждый поток берёт память из своей арены, снижая конкуренцию за общий аллокатор.
4. **Кэши и memoization.** Особенно в шаблонном коде: у каждой инстанциации шаблона своя `thread_local`-переменная.
5. **Диагностика и логирование.** Буферы форматирования, глубина рекурсии, `thread_local`-контекст (например, trace-id), чтобы не блокировать общий лог.
6. **Эмуляция `errno`-подобных интерфейсов.** Функции, возвращающие код ошибки через глобальную переменную, обязаны делать её потоково-локальной.
7. **Оптимизация «дорогих» вычислений на поток.** Например, кэш `std::this_thread::get_id()` или указателя на текущий контекст.

## Производительность: модели TLS

«Бесплатно» `thread_local` не бывает: обращение к нему — это доступ через TLS-регистр (в x86-64 — сегмент `%fs`), а способ вычисления адреса зависит от модели TLS, которую выбирает компоновщик/загрузчик:

| Модель | Когда используется | Стоимость доступа |
|---|---|---|
| `local-exec` | исполняемый файл, статическая линковка | несколько инструкций, самый быстрый |
| `initial-exec` | разделяемая библиотека, загруженная при старте | одно чтение GOT + доступ через `%fs` |
| `general-dynamic` | `dlopen`-библиотека, обычный `-fPIC` | вызов `__tls_get_addr` — десятки–сотни циклов |
| `local-dynamic` | `dlopen`-библиотека с оптимизацией | вызов `__tls_get_addr` с известным смещением |

Код доступа в модели `local-exec` выглядит примерно так:

```asm
mov  %fs:counter@tpoff, %eax
```

Практические выводы:

- в горячем цикле внутри разделяемой библиотеки, загружаемой через `dlopen`, `thread_local` может оказаться неожиданно дорогим из-за `__tls_get_addr`;
- можно зафиксировать модель: `-ftls-model=initial-exec` или `__attribute__((tls_model("initial-exec")))`, но с оговоркой: `initial-exec` расходует ограниченный статический TLS-блок, и при большом числе `dlopen`-библиотек возможна ошибка загрузки «cannot allocate memory in static TLS block»;
- если переменная нужна многократно, иногда выгодно один раз получить её адрес и работать через указатель;
- `thread_local` с динамической инициализацией в блоке добавляет проверку guard-флага при каждом проходе через объявление;
- память на поток: большой `thread_local`-массив увеличивает потребление на каждый поток, а в пуле из тысяч потоков это может быть ощутимо.

## Подводные камни

1. **`thread_local` ≠ потокобезопасность.** Он не защищает данные, а разделяет их. Если передать указатель/ссылку на свою копию в другой поток, получите обычную гонку — объект-то один и тот же.
2. **Привязка к потоку ОС, а не к задаче.** В пуле потоков, у `std::async` (реализация может переиспользовать потоки), в корутинах C++20, которые могут возобновляться на разных потоках, и в файберах состояние «протекает» между задачами: следующая задача на том же потоке увидит остатки предыдущей.
3. **Адрес нестабилен между потоками.** Нельзя сохранить `&tls_var` в одном потоке и рассчитывать, что в другом это будет «та же» переменная.
4. **Порядок инициализации между единицами трансляции.** Если глобальный конструктор в одной TU обращается к `thread_local` из другой, объект может быть ещё не инициализирован — получите нулевое значение или UB. Классическая проблема static initialization order fiasco в потоковом варианте.
5. **`thread_local` в заголовке.** `static thread_local` в заголовке даст **отдельный экземпляр в каждой TU** (и на каждый поток). Нужен один экземпляр на программу — используйте `inline thread_local` (C++17) или шаблон.
6. **`dlclose` и деструкторы.** Если библиотека с `thread_local`-объектами выгружена до завершения потоков, которые их создали, вызов деструктора может привести к падению: код деструктора уже выгружен. Это реальная проблема, а не теоретическая.
7. **`fork()`.** Дочерний процесс наследует TLS только вызвавшего потока; TLS остальных потоков исчезает вместе с потоками. В сочетании с блокировками в `thread_local`-объектах это источник зависаний.
8. **Обработчики сигналов.** Сигнал в том же потоке видит ту же копию, но если он прервал её обновление, состояние будет несогласованным; `thread_local` сам по себе не делает код async-signal-safe.
9. **Рекурсивная инициализация.** Повторный вход в объявление во время инициализации — UB (на практике возможен deadlock на guard-мьютексе).
10. **Исключение при инициализации на уровне пространства имён** — `std::terminate`, а не повторная попытка (в отличие от блочной переменной).
11. **`thread_local` не является `atomic`.** Даже своя копия не даёт атомарности при доступе из сигнала или при ошибочной передаче наружу.
12. **C vs C++.** В C нет динамической инициализации и деструкторов; `_Thread_local` с нетривиальным инициализатором просто не скомпилируется.

## Сравнение с альтернативами

| Средство | Инициализация | Деструкторы | Переносимость |
|---|---|---|---|
| `thread_local` (C++11) | динамическая, ленивая | да | стандарт C++ |
| `_Thread_local` (C11) | только константная | нет | стандарт C |
| `__thread` (GCC/Clang) | только константная | нет | расширение компилятора |
| `__declspec(thread)` (MSVC) | ограниченная | нет | расширение, DLL-ограничения |
| `pthread_key_create` | вручную | да, через destructor | POSIX |
| `TlsAlloc` / `FlsAlloc` | вручную | через колбэки | Windows |

`thread_local` — самый удобный вариант там, где нужны нетривиальные типы (`std::string`, `std::vector`, `std::mt19937`) и автоматическое разрушение. `pthread_key_*` остаётся актуальным для динамически создаваемых «ключей» (например, в библиотеках, которые не знают заранее число TLS-переменных).

## Что `thread_local` **не** делает

- не копирует данные между потоками и не «наследует» их дочерним потокам;
- не синхронизирует доступ и не заменяет `std::atomic`/мьютекс;
- не привязан к `std::thread` как к объекту — привязан к потоку ОС;
- не гарантирует порядок инициализации относительно других TU;
- не делает переменную «локальной для задачи» в пуле потоков или для корутины.

## Итог

`thread_local` даёт каждому потоку отдельный экземпляр переменной с временем жизни потока, ленивой (для блочных) или отложенной (для глобальных) инициализацией и автоматическим разрушением при выходе из потока. Это удобный инструмент для устранения конкуренции за счёт дублирования состояния: счётчики, ГПСЧ, кэши, арены, `errno`-подобные интерфейсы. Но платить приходится памятью на каждый поток, стоимостью TLS-доступа (особенно в `dlopen`-библиотеках) и целым набором ловушек — от пулов потоков и корутин до `fork()` и выгрузки библиотек. Главное правило: `thread_local` — это про **раздельные** данные, а не про **безопасный общий доступ** к одним и тем же.
