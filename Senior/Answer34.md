# 34. Как работают точки остановки?

Точка остановки (breakpoint) — это механизм, который заставляет программу прервать исполнение в заданном месте и передать управление отладчику. Ключевой момент, который часто упускают: **у процессора нет понятия «точка остановки в строке 42»**. Процессор умеет всего несколько вещей: сгенерировать исключение по специальной инструкции (`INT3`, `BRK`, `EBREAK`), сгенерировать отладочное исключение после каждой инструкции по флагу `TF` и сработать по адресам, записанным в отладочные регистры `DR0–DR3`. Всё остальное — работа отладчика: он правит байты в памяти, ловит сигналы, ведёт таблицы адресов, восстанавливает код и создаёт иллюзию, что вы просто нажали F9.

## 1. Две принципиально разные технологии

| | Программные (software) | Аппаратные (hardware) |
|---|---|---|
| Основа | подмена инструкции на `0xCC` / `BRK` | регистры `DR0–DR3` + `DR7` |
| Сколько можно поставить | практически неограниченно | обычно 4 на поток |
| Модификация кода | да, нужен доступ на запись | нет |
| Работает в ROM/Flash | нет | да |
| Тип | только «выполнение» | выполнение, запись, чтение/запись, I/O |
| Стоимость срабатывания | exception + переключение в ядро | тоже exception, но без правки кода |
| Типичное применение | обычные `break file:line` | `watch`/`rwatch`/`awatch`, `hbreak` |

Исторически отладчики комбинируют оба механизма: например, GDB по умолчанию ставит программные точки, но для watchpoint'ов и для кода в read-only памяти использует аппаратные.

## 2. Программные точки остановки

### 2.1 Подмена байта

Отладчик находит адрес нужной инструкции и заменяет её первый байт на однобайтовую инструкцию `INT3` (опкод `0xCC`). Оригинальный байт сохраняется в памяти отладчика.

Было:

```asm
0000000000401136 <main>:
  401136:  55                    push   rbp
  401137:  48 89 e5              mov    rbp,rsp
  40113a:  b8 2a 00 00 00        mov    eax,0x2a
```

Стало (точка на `0x40113a`):

```asm
  40113a:  cc                    int3
  40113b:  00 00                 add    BYTE PTR [rax],al   ; «мусор», до него дело не дойдёт
```

Хвост исходной инструкции остаётся в памяти, но он никогда не выполнится: исключение возникает **до** того, как процессор начнёт исполнять инструкцию по этому адресу. Дизассемблер, читающий память, пока точка вставлена, покажет `int3` — поэтому отладчики умеют «подменять» байт обратно при показе дизассемблера.

### 2.2 Почему именно `0xCC`

- Это **однобайтовая** инструкция: для подмены не нужно трогать соседние байты, и операция получается максимально простой и почти атомарной.
- `INT 3`, записанная как `CD 03`, занимает два байта, а её поведение в некоторых режимах (например, в V86) отличается — генерируется `#GP`. `0xCC` — специально выделенный однобайтовый вариант, одинаково работающий везде.
- `0xCC` не может быть префиксом или частью другой инструкции, поэтому её появление в потоке команд однозначно.

### 2.3 Что происходит при срабатывании

1. Процессор выбирает `0xCC` и генерирует исключение `#BP` (вектор 3). Это **trap**, а не fault: в `CS:RIP` сохраняется адрес **следующей** инструкции (на x86-64 `RIP` уже указывает на байт после `0xCC`).
2. Ядро ОС доставляет трассируемому процессу сигнал `SIGTRAP` (Linux) или генерирует отладочное событие `EXCEPTION_BREAKPOINT` (Windows).
3. Процесс останавливается, отладчик получает управление: `waitpid()` с `WIFSTOPPED` и `WSTOPSIG(status) == SIGTRAP` в Linux, `WaitForDebugEvent()` в Windows.
4. Отладчик смотрит на адрес остановки, ищет его в своей таблице точек, при необходимости **уменьшает `RIP` на 1**, чтобы «вернуть» его на начало исходной инструкции, проверяет условия и либо останавливается и показывает состояние пользователю, либо продолжает выполнение.

Важная тонкость: не всякий `SIGTRAP` — это breakpoint. Single-step тоже даёт `SIGTRAP`, и отладчик различает их по `si_code` (`TRAP_BRKPT`/`SI_KERNEL` для `INT3`, `TRAP_TRACE` для пошагового выполнения). Иначе он «поймал» бы собственный шаг как чужую точку остановки.

### 2.4 Жизненный цикл точки: снять → шаг → поставить

Наивная логика «оставить `0xCC` и продолжить» не работает: программа тут же снова наткнётся на ту же точку. Поэтому при команде `continue`/`step` отладчик делает следующее:

1. Временно восстанавливает оригинальный байт (снимает точку).
2. Выполняет **одну** исходную инструкцию — либо аппаратным single-step (флаг `TF`), либо поставив временную точку на следующий адрес.
3. Вставляет `0xCC` обратно.
4. Продолжает выполнение (`PTRACE_CONT`, `ContinueDebugEvent`).

Именно поэтому «шаг с заходом в функцию» на практике медленнее, чем кажется: каждая строка — это как минимум два переключения в ядро.

Пока программа стоит на точке, GDB по умолчанию обычно **вынимает** её из кода (поэтому `x/i $pc` показывает оригинальную инструкцию); поведение регулируется `set breakpoint always-inserted`. На удалённых целях точки часто держат вставленными постоянно, чтобы не гонять лишние пакеты.

### 2.5 Псевдокод на `ptrace`

```c
/* Поставить точку */
long orig = ptrace(PTRACE_PEEKTEXT, pid, addr, NULL);
long patched = (orig & ~0xffL) | 0xcc;   /* little-endian: младший байт = первый в памяти */
ptrace(PTRACE_POKETEXT, pid, addr, patched);

/* Дождаться и обработать */
int status;
waitpid(pid, &status, 0);
if (WIFSTOPPED(status) && WSTOPSIG(status) == SIGTRAP) {
    struct user_regs_struct regs;
    ptrace(PTRACE_GETREGS, pid, NULL, &regs);
    regs.rip -= 1;                        /* откат с x86-специфики: INT3 — trap */
    ptrace(PTRACE_SETREGS, pid, NULL, &regs);
    /* ... проверка условий, показ пользователю ... */
}
```

На big-endian архитектурах байт для замены — старший, а не младший; на ARM/ARM64 инструкции четырёхбайтовые, и патчить нужно целое слово, а не один байт.

### 2.6 Несколько точек в одном месте

Если на один адрес «повешены» две логические точки (например, `break foo` и `break file:10`, указывающие в одну инструкцию), физически `0xCC` там один. Отладчик хранит счётчик ссылок и восстанавливает байт только после снятия последней логической точки. Отдельная головная боль — точки, чьи байты перекрываются (частично совпадающие адреса), и ситуация, когда оригинальный байт уже был `0xCC` (компилятор любит заполнять промежутки между функциями `int3` — тогда отладчик не должен «восстанавливать» его в что-то другое).

## 3. Откуда отладчик берёт адрес

Пользователь оперирует именами и строками, процессор — адресами. Преобразование делается по отладочной информации:

- **DWARF** (`.debug_info`, `.debug_line`) в ELF, **PDB** в MSVC, **CodeView/STABS** — таблицы, сопоставляющие адреса с файлами, строками, функциями и переменными.
- `break file.c:42` превращается в один **или несколько** адресов. Одна строка может дать несколько «locations»: из-за инлайна, шаблонов, размножения кода, пролога функции.
- `break func` ставится не обязательно на самый первый байт: отладчик умеет перепрыгивать пролог (`skip prologue`), чтобы аргументы уже были доступны.
- **PIE и ASLR**: в исполняемом файле адреса относительные, реальный адрес = база загрузки + смещение. База берётся из `/proc/pid/maps`, из `AT_PHDR`/`DT_DEBUG`, у Windows — из событий загрузки модулей. Отладчики по умолчанию отключают рандомизацию, чтобы адреса были стабильны.
- **Ещё не загруженные библиотеки**: точка становится *pending* и разрешается при `dlopen` (Linux, через rendezvous-точку компоновщика) или `LOAD_DLL_DEBUG_EVENT` (Windows).
- **JIT-код**: статической отладочной информации нет, поэтому JIT-движок сам регистрирует сгенерированный код и его соответствие исходнику (как это делает, например, V8 или LLVM JIT).

## 4. Аппаратные точки остановки

На x86 это регистры отладки:

- `DR0–DR3` — до четырёх адресов;
- `DR7` — управление: включён ли слот, тип доступа (`00` — выполнение, `01` — запись, `11` — чтение/запись, `10` — I/O), длина (`1/2/4/8` байт);
- `DR6` — статус: какой слот сработал.

Свойства:

- **Код не модифицируется** — работает для прошивок, ROM и страниц «только чтение».
- **Лимит — 4 слота** на поток. Регистры `DR` — часть контекста потока, поэтому при отладке многопоточной программы отладчик должен прописать их в каждый поток (Linux: `PTRACE_POKEUSER` со смещениями `offsetof(struct user, u_debugreg[i])`).
- **Точка на исполнение** срабатывает как fault: сохраняется адрес **самой** инструкции, «откатывать» `RIP` не нужно (в отличие от `INT3`).
- **Watchpoint** (`watch`, `rwatch`, `awatch`) — это data breakpoint: процессор срабатывает после обращения к памяти, сохраняя адрес следующей инструкции. Отсюда ограничения: длина 1/2/4/8 байт и требование выравнивания адреса; «чистого чтения» на x86 нет — `rwatch` реализуется как «чтение/запись» и ловит также записи.
- Если 4 слота кончились, GDB может эмулировать watchpoint программно: single-step и сравнение памяти после каждой инструкции. Работает, но замедление — на порядки.

## 5. Условные точки, счётчики и команды

`break foo if x == 5`, `ignore 1 100`, `commands ... end`, `dprintf` — всё это **не** аппаратные механизмы. Условие вычисляется отладчиком уже после остановки, обычно путём выполнения выражения в адресном пространстве отлаживаемой программы (иногда — с вызовом функций inferior'а). Следствия:

- каждое попадание — полный цикл «останов → вычисление → продолжение», поэтому условная точка в горячем цикле может замедлить программу в десятки раз;
- вычисление условия может иметь побочные эффекты (вызов функции, аллокация памяти);
- в оптимизированном коде переменная условия может быть «`<optimized out>`» — условие просто не вычислится.

Для логирования без остановки используют `dprintf`/tracepoints: отладчик печатает данные и сразу продолжает, не отдавая управление пользователю.

## 6. Пошаговое выполнение

Это «точка остановки на каждой инструкции», реализованная флагом `TF` (Trap Flag) в `EFLAGS`/`RFLAGS`: после каждой инструкции процессор генерирует `#DB`, ядро превращает его в `SIGTRAP` с `si_code == TRAP_TRACE`.

- `stepi`/`nexti` — ровно одна машинная инструкция;
- `step`/`next` — одна строка исходника: отладчик сам решает, где остановиться, по таблице строк, а `next` ставит временную точку на адрес возврата/следующую строку и «отпускает» программу;
- `finish`, `until`, `advance` — временные точки на вычисленные адреса;
- на архитектурах без `TF` (некоторые встраиваемые) отладчик эмулирует шаг, ставя временную точку на следующий адрес («software single step»).

## 7. Потоки и процессы

- В классическом **all-stop** режиме при срабатывании точки останавливаются все потоки процесса. Это необходимо: код общий, и если один поток продолжит исполнение, он может пройти через временно снятую точку.
- В **non-stop** режиме потоки живут независимо; тогда важны «per-thread» условия и аккуратность с временным снятием байта.
- `fork`/`clone`/`exec` обрабатываются через `PTRACE_O_TRACEFORK/TRACECLONE/TRACEEXEC` и настройки `follow-fork-mode`/`detach-on-fork`. При `exec` отладчик перечитывает символы и заново разрешает точки: старые адреса недействительны.

## 8. Подводные камни и особые случаи

- **Оптимизация.** `-O2` тасует строки, инлайнит функции, выбрасывает переменные. `break file:42` может встать «не туда» или размножиться на несколько адресов; шаг прыгает; точка внутри inline-функции физически стоит в вызывающем коде.
- **Read-only код.** Чтобы записать `0xCC` в `.text`, отладчик снимает защиту (`mprotect`/`VirtualProtect`), пишет, возвращает. На системах с подписью кода и W^X (macOS, iOS, современные Windows) это может быть запрещено — тогда остаются только аппаратные точки.
- **ARM и кэш инструкций.** Инструкции 4-байтовые, патчится слово целиком; после записи нужно сбросить I-cache (`__builtin___clear_cache`), иначе процессор может выполнить старый код. На AArch64 `BRK` сохраняет адрес **самой** инструкции (в отличие от x86), а single-step — следующей; поэтому «поправить PC» — архитектурно-зависимая операция.
- **Разные архитектуры — разные ловушки:** x86 — `0xCC`; ARM32 — `0xE7F001F0`/`0xBE00`; AArch64 — `BRK #0` (`0xD4200000`); RISC-V — `EBREAK` (`0x00100073`); MIPS — `BREAK`; PowerPC — `trap`.
- **Атомарность.** Патч на несколько байт не атомарен относительно других потоков; поэтому в all-stop все потоки уже стоят.
- **Самомодифицирующийся код, упаковщики, JIT.** Байт может быть перезаписан программой — точка «исчезнет»; наоборот, случайный `0xCC` в данных, если туда попадёт управление, вызовет ложную остановку.
- **`int3` как заполнитель.** MSVC в отладочных сборках заполняет промежутки между функциями `0xCC`; прыжок в такое место даёт «непонятную» остановку.
- **Антиотладка.** Программа может считать контрольную сумму `.text` (и увидеть `0xCC`), проверять `IsDebuggerPresent`, `ptrace(PTRACE_TRACEME)`, `TracerPid` в `/proc/self/status`, тайминги. На Linux также важен `kernel.yama.ptrace_scope`.
- **Сигналы.** Настоящий `SIGTRAP`, посланный программой через `raise`, неотличим от точки без анализа `si_code`; отладчик должен уметь передавать «чужие» сигналы программе.
- **Ядро.** В ядре Linux точки реализованы похожим образом: kprobes подменяют инструкцию на breakpoint-инструкцию (на x86 — `int3`), uprobes — то же для пользовательских бинарников, ftrace использует патчинг по месту (`nop` ↔ `call`). eBPF-программы на uprobes — это, по сути, «точки остановки без остановки».
- **Выгруженные библиотеки.** Точка в `dlclose`-нутой библиотеке становится висячей; отладчик должен отслеживать выгрузку.

## 9. Что ещё называют «точками остановки»

- **Catchpoints**: `catch syscall`, `catch throw`, `catch signal` — остановка не по адресу, а по событию (перехват на границе ядра или через раскрутку исключений).
- **Tracepoints**: запись данных без остановки.
- **`__debugbreak()`**, `__builtin_trap()`, `raise(SIGTRAP)`, а в C++26 — `std::breakpoint()` из `<debugging>`: «зашитая» в код ловушка, не требующая патчинга. Именно так обычно реализуют `assert`.
- **Intel PT / branch tracing**: запись потока управления без остановок — альтернативный способ «увидеть, где программа была».

## 10. Практические выводы

- Отлаживайте с `-g -O0` (или `-Og`), иначе точки и переменные ведут себя непредсказуемо.
- `hbreak` — когда память только для чтения или когда нужен watchpoint.
- `set breakpoint pending on` — для точек в ещё не загруженных библиотеках.
- `info breakpoints`, `info line file:42`, `disassemble /m` помогают понять, куда именно встала точка и сколько у неё locations.
- Не рассчитывайте на точку внутри `inline`-функции как на отдельный адрес; и помните, что `watch` ограничен четырьмя аппаратными слотами.

**Итог.** Точка остановки — это не функция процессора, а договорённость между отладчиком и ОС. Программная точка — подмена инструкции на `INT3`/`BRK` плюс обработка возникшего исключения, с временным снятием и повторной вставкой байта при каждом продолжении. Аппаратная — использование регистров `DR0–DR3`, которых всего четыре, зато они не трогают код и умеют следить за данными. Всё остальное — адреса из DWARF/PDB, учёт PIE/ASLR, потоки, условия и аккуратная работа с памятью — это инфраструктура вокруг этих двух базовых механизмов.
