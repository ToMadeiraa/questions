# 41. Что такое copy elision и когда он становится возможным? Какие особенности для разных стандартов?

## 1. Определение

**Copy elision** (элизия копирования) — это разрешённое стандартом устранение вызова конструктора копирования или перемещения при инициализации объекта. Вместо схемы «создать временный объект → скопировать/переместить его в нужное место → уничтожить временный» компилятор конструирует объект **сразу в той области памяти, где он должен оказаться**.

Ключевой момент: это не обычная оптимизация по правилу «as-if». Стандарт явно разрешает copy elision **менять наблюдаемое поведение программы** — например, пропускать побочные эффекты конструктора копирования. Это, по сути, единственная (до C++14) оптимизация, которой позволено нарушать as-if.

Разновидности:

* **URVO / RVO** (unnamed return value optimization) — `return T(...);`
* **NRVO** (named return value optimization) — `T t; ... return t;`
* элизия при инициализации из prvalue (в C++17 стала обязательной);
* элизия при `throw` и при инициализации параметра `catch`.

Формально в стандарте (C++11 и позже) это раздел `[class.copy.elision]`; в C++17 часть случаев из него «переехала» в правила инициализации `[dcl.init]`, потому что там уже не оптимизация, а семантика.

## 2. Базовые примеры

### 2.1 Инициализация из prvalue того же типа

```cpp
struct T { T(); T(const T&); T(T&&); };

T x = T();            // одно T()
T y = T(T(T()));      // всё равно только одно T()
void f(T);
f(T());               // параметр инициализируется напрямую
T* p = new T(T());
```

### 2.2 URVO

```cpp
T make() { return T(1, 2); }

T x = make();  // результат make() строится прямо в x
```

### 2.3 NRVO

```cpp
T make() {
    T t(1, 2);
    // ...
    return t;   // t может быть построен прямо в возвращаемом объекте
}
```

При NRVO локальная переменная `t` — это и есть возвращаемый объект; её деструктор вызывается не в конце функции, а там, где заканчивается жизнь объекта у вызывающего кода. Это наблюдаемо, но стандарт разрешает такое поведение.

### 2.4 Исключения

```cpp
throw T();   // объект исключения инициализируется прямо из prvalue
```

```cpp
try { ... }
catch (T e) { ... }  // копия из объекта исключения может быть элидирована;
                     // тогда e — фактически псевдоним объекта исключения
```

## 3. Когда элизия становится возможной

Общие условия:

1. **Классовый тип.** Для скалярных типов элидировать нечего.
2. **Совпадение типов** источника и приёмника с точностью до cv-квалификации. Если типы разные (например, `Derived` → `Base`), происходит преобразование или срез (slicing), и элизии нет.
3. **Источник — либо prvalue того же типа, либо именованный автоматический объект** в `return`/`throw`. Именованный объект — только необязательные случаи; prvalue в C++17 — обязательные.
4. Для **необязательных** случаев конструктор копирования/перемещения должен быть **доступен и не удалён**, даже если фактически не вызывается. Это классическая ловушка C++11/14.
5. Для **NRVO**: объект должен быть автоматическим, не `volatile`, не параметром функции и не параметром обработчика исключения; тип — совпадать с возвращаемым (cv не учитывается). NRVO не применяется к членам класса, глобальным/статическим объектам, подъобъектам и к выражениям вроде `std::move(t)`.

Пример, где элизия невозможна:

```cpp
struct T { T(); T(const T&); T(T&&); };

T f1(T t)        { return t; }        // параметр: копии нет только за счёт move, NRVO нельзя
T f2()           { static T t; return t; }  // статический объект — копия
struct S { T m; };
T f3(S& s)       { return s.m; }      // подъобъект — копия
T f4()           { T t; return std::move(t); }  // xvalue, NRVO не применяется
```

## 4. Особенности стандартов

### C++98/03

* Элизия разрешена для `return`, `throw`, `catch` и для инициализации объекта временным — это было прописано в `[class.copy]`.
* Копирующий конструктор должен быть доступен.
* Разрешено пропускать копирование **даже если конструктор копирования имеет побочные эффекты** — на это прямо указывает стандарт.
* Термина «copy elision» в современном виде ещё нет; до C++14 это единственная разрешённая оптимизация, меняющая наблюдаемое поведение.

### C++11/14

* Появляется move-семантика. В `return` именованный локальный объект или параметр рассматривается как rvalue для выбора конструктора (**implicit move**), даже если NRVO не применилась. То есть `return t;` без элизии — это перемещение, а не копирование.
* Правила элизии те же, что в C++03, но теперь проверяется доступность **и** копирующего, **и** перемещающего конструктора.
* Главная особенность: **конструктор обязан существовать, даже если копия гарантированно элидируется**.

```cpp
struct Immovable {
    Immovable() = default;
    Immovable(const Immovable&) = delete;
    Immovable(Immovable&&) = delete;
};

Immovable make() { return Immovable(); }  // C++11/14: ОШИБКА (нужен move/copy ctor)
```

Именно поэтому до C++17 нельзя было фабриковать «неперемещаемые» типы вроде `std::mutex` возвратом по значению.

* `-fno-elide-constructors` (GCC/Clang) отключает необязательную элизию.

### C++17 — «guaranteed copy elision»

Самое важное изменение. В C++17 **prvalue — это уже не объект, а «инициализатор»**; временный объект материализуется только при необходимости (привязка к ссылке, доступ к члену, `sizeof` и т.п.). Отсюда:

**Обязательные случаи (копии не существует вообще):**

* инициализация объекта из prvalue того же типа — переменная, параметр функции, элемент агрегата, объект в `new`, возвращаемое значение;
* `return` с prvalue того же типа;
* `throw` с prvalue того же типа (объект исключения инициализируется напрямую).

```cpp
T x = T();          // C++17: никакого копирования/перемещения
f(T());             // параметр создаётся на месте
return T();         // result object создаётся на месте
```

**Необязательные (по-прежнему оптимизация):**

* NRVO;
* `throw` именованного объекта;
* инициализация параметра `catch`.

Следствия:

```cpp
struct Immovable {
    Immovable() = default;
    Immovable(const Immovable&) = delete;
    Immovable(Immovable&&) = delete;
};

Immovable make() { return Immovable(); }   // C++17: OK
Immovable make2() { Immovable x; return x; } // C++17: всё ещё ОШИБКА — NRVO не гарантирован
```

* Для обязательных случаев конструктор копирования/перемещения **не нужен вообще** — тип может быть полностью неперемещаемым.
* `-fno-elide-constructors` на обязательные случаи не действует.
* Термин «guaranteed copy elision» неточен: копирования нет не потому, что его «оптимизировали», а потому что его нет в семантике.
* NRVO остаётся необязательной и по-прежнему требует доступного конструктора.

### C++20

* P1825 расширил **implicit move**: rvalue-ссылки и rvalue-ссылочные параметры тоже рассматриваются как кандидаты на перемещение в `return`. Это не элизия, но тесно связано с темой.
* Собственно правила элизии не менялись.

### C++23

* P2266 «Simpler implicit move»: операнд `return`, являющийся id-выражением, трактуется как xvalue; `return std::move(x);` перестал давать какой-либо выигрыш (и раньше мешал NRVO).
* NRVO по-прежнему **не гарантирован**.

## 6. Подводные камни и практические следствия

* **Не полагайтесь на побочные эффекты конструктора копирования.** До C++17 компилятор вправе их пропустить; после — для prvalue их просто нет.
* **`return std::move(x);` — антипаттерн.** Явный `std::move` делает операнд xvalue, а не именем объекта, и запрещает NRVO (GCC/Clang предупреждают `-Wpessimizing-move`). Правильно: `return x;`.
* **Нельзя элидировать возврат параметра.** `T f(T t) { return t; }` — это перемещение, а не NRVO: параметр живёт в кадре вызывающего.
* **Возврат подъобъекта/члена** (`return s.m;`) — всегда копия/перемещение, NRVO не применяется.
* **`const`-локальная переменная** не мешает элизии (типы сравниваются без учёта cv), но если элизия не применилась, переместить её нельзя — будет копирование.
* **Элизия не «проходит» через ссылку.** Если объект передан по `const T&` и возвращён по значению, внутри функции создаётся копия — цепочка элизии рвётся.
* **`return {1, 2};`** инициализирует возвращаемый объект напрямую (list-initialization) и работает даже с удалённым конструктором копирования в C++17.
* **На практике** GCC/Clang/MSVC выполняют NRVO почти всегда, в том числе на `-O0`, но стандарт этого не гарантирует — переносимость требует доступного конструктора.
* **ABI.** Обязательная элизия в C++17 не изменила ABI: для нетривиальных возвращаемых типов по-прежнему передаётся скрытый указатель на result object.
* **Не путать с assignment:** `T x; x = T();` — это перемещающее присваивание, элизии здесь нет.
* Любопытный факт: начиная с C++14 copy elision — уже не единственная оптимизация, меняющая наблюдаемое поведение (появилась элизия выделений памяти).

## 7. Коротко

* **Copy elision** — построение объекта сразу на месте назначения, без промежуточной копии/перемещения; стандарт разрешает ей менять побочные эффекты.
* **Возможна**, когда источник — prvalue того же типа или именованный автоматический объект в `return`/`throw`/`catch`; тип должен совпадать с точностью до cv.
* **C++98/03–C++14:** элизия всегда необязательна, но конструктор копирования/перемещения должен быть доступен и не удалён — даже если не вызывается.
* **C++17:** инициализация из prvalue того же типа (включая аргументы, `return`, `new`, объект исключения) — **обязательна**; конструктор не нужен; NRVO, `throw` именованного и `catch` остаются необязательными.
* **C++20/23:** менялись только правила implicit move (P1825, P2266); NRVO так и не стал гарантированным.
