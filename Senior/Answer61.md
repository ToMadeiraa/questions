# 61. Расскажите о стратегии разветвления (branching).

## 1. Что такое стратегия ветвления и почему это не только про Git

**Стратегия ветвления (branching strategy)** — это соглашение команды о том, какие ветки существуют в репозитории, сколько они живут, кто и как в них вливает изменения, какие ветки считаются «источником истины» и как изменения продвигаются от коммита до продакшена.

Ключевая мысль: в контексте SCM/CI/CD branching — это **не просто набор команд `git branch`**, а контракт между несколькими подсистемами:

- **SCM** (Git, Mercurial, TFVC, Perforce) — модель истории, слияний, тегов, прав доступа;
- **Code Review / политики** — protected branches, required approvals, CODEOWNERS;
- **CI** — какие пайплайны и на каких событиях (`push`, `pull_request`, `tag`) запускаются;
- **CD** — как собираются и продвигаются артефакты между средами;
- **Release management** — как нумеруются версии, как поддерживаются старые релизы, как выпускаются hotfix.

Поэтому выбор стратегии — это компромисс между **скоростью интеграции**, **стабильностью**, **сложностью поддержки** и **требованиями бизнеса** (регуляторика, mobile-приложения, несколько поддерживаемых версий продукта).

---

## 2. Базовые понятия, на которых строятся все стратегии

| Понятие | Смысл |
|---|---|
| **Trunk / main / master** | Главная ветка — «источник истины», из неё собираются релизы (в идеале) |
| **Feature branch** | Короткоживущая ветка под задачу/фичу |
| **Release branch** | Ветка стабилизации конкретного релиза, отделённая от trunk |
| **Hotfix branch** | Ветка для срочного исправления в проде |
| **Long-lived branch** | Ветка, живущая недели/месяцы (develop, release, environment) |
| **Short-lived branch** | Ветка, живущая часы/дни, вливается обратно в trunk |
| **Merge commit / squash / rebase** | Способы интеграции, определяющие форму истории |
| **Tag** | Неизменяемая метка релиза (например, `v2.4.1`) |
| **Protected branch** | Ветка с запретом прямого push, обязательными проверками и ревью |
| **Merge queue / merge train** | Механизм сериализации слияний, чтобы trunk оставался зелёным |

Важное различие: **долгоживущие ветки — это стоимость**. Каждая долгоживущая ветка — это расходящаяся история, риск конфликтов, дублирование пайплайнов и «merge hell». Современные высокопроизводительные команды (по исследованиям DORA) стремятся к **малому числу активных веток и короткому времени их жизни**.

---

## 3. Классификация стратегий

Стратегии удобно раскладывать по двум осям:

1. **Сколько долгоживущих веток** (одна / две / много).
2. **Как часто изменения интегрируются в trunk** (непрерывно / по релизам / по средам).

Условно выделяют семейства:

- **Trunk-Based Development (TBD)** — одна главная ветка, короткоживущие ветки, непрерывная интеграция.
- **GitHub Flow** — trunk + feature-ветки + PR, релиз с main.
- **GitLab Flow** — trunk + feature-ветки + опциональные environment/release-ветки.
- **Git Flow** — две долгоживущие ветки (main + develop) + feature/release/hotfix.
- **Release Flow (Azure DevOps / TFS-подход)** — trunk + release-ветки, hotfix через cherry-pick.
- **Environment branching** — ветки под среды (dev/test/stage/prod).
- **Forking workflow** — форки вместо веток (open source).
- **Ship / Show / Ask** — не про ветки, а про политику ревью и релиза (надстройка над trunk-based).

Ниже — детально по каждой.

## 4. Trunk-Based Development (TBD)

### Схема

```
main   ●──●──●──●──●──●──●──●──●──►   всегда зелёный, релизы = теги
        \  /  \  /  \  /
feature  ●●    ●●    ●●              живут часы, максимум ~1–2 дня
```

### Правила

- Одна долгоживущая ветка — `main` (trunk).
- Изменения интегрируются **не реже раза в день** (в идеале — несколько раз в день).
- Ветки фич короткоживущие; допускаются «ветки на несколько часов».
- Незаконченный функционал скрывается за **feature flags (feature toggles)**, а не за долгой веткой.
- Релиз — это **тег на коммите** (или сборка артефакта из конкретного коммита), а не отдельная ветка.
- Обязательны: быстрый CI, автоматические тесты, **branch by abstraction** для крупных рефакторингов, обратно-совместимые изменения схемы БД (expand/contract, миграции в несколько шагов).

### Плюсы

- Минимум конфликтов и «merge hell».
- Непрерывная интеграция работает по-настоящему: trunk всегда собирается.
- Быстрый feedback, короткий lead time.
- Простая и понятная история; удобно делать `git bisect`.
- Идеально ложится на CD, canary/blue-green, feature flags.
- Коррелирует с высокой производительностью по DORA.

### Минусы

- Требует **зрелой инженерной культуры**: тесты, флаги, ревью, быстрый пайплайн.
- Нужна дисциплина: незаконченный код в trunk должен быть безопасно выключен.
- Сложнее, если продукт поддерживает **много параллельных версий** (например, мобильные приложения, on-premise).
- Требует продуманного управления feature flags (технический долг флагов).

### Когда применять

- Веб-сервисы, SaaS, микросервисы, команды с CD.
- Большие команды, где важна скорость интеграции.
- Когда есть возможность быстро откатывать и использовать флаги.

## 5. GitHub Flow

### Схема

```
main  ●──────●──────────●────────●──►   деплой из main
       \    /          /        /
feature ●─●─●●         /        /
       \             /        /
feature ●─●─●────────●────────●
```

### Правила

- Одна долгоживущая ветка — `main`.
- Под каждую задачу — ветка (`feature/…`, `fix/…`) от `main`.
- Открывается Pull Request; обязательны ревью и зелёный CI.
- После мержа — деплой (часто автоматически) из `main`.
- Релизы — теги/артефакты; отдельные release-ветки не обязательны.

### Плюсы

- Очень простой и понятный процесс; низкий порог входа.
- Хорошо сочетается с PR-based review и CI на каждый PR.
- Подходит для небольших и средних команд, веб-продуктов.

### Минусы

- Нет формального механизма поддержки нескольких релизов.
- Ветки могут «зависать», если команда не ограничивает их жизнь.
- Нет явной модели окружений/стабилизации — всё держится на дисциплине.

### Когда применять

- Продукты с непрерывным деплоем, где поддерживается только последняя версия.
- Open-source и небольшие команды.

## 6. GitLab Flow

GitLab Flow — это «GitHub Flow + правила продвижения изменений по окружениям/релизам». Два варианта:

**Вариант A: environment branches (продвижение по средам)**

```
main ──► pre-production ──► production
```

Коммиты продвигаются merge-ом (или cherry-pick) из `main` в ветку среды, деплой триггерится на ветку среды.

**Вариант B: release branches (продвижение по версиям)**

```
main ──► release/2.4 ──► теги 2.4.x, hotfix в release/2.4 и обратно в main
```

### Плюсы

- Гибко: можно выбрать модель под зрелость CI/CD.
- Явные правила «что куда мержится» (merge upstream/downstream).
- Удобно, когда есть несколько сред и нужен контроль продвижения.

### Минусы

- Environment-ветки приводят к расхождению кода и «двойной правде» (что в ветке `production`, не всегда равно тому, что реально задеплоено).
- Больше долгоживущих веток → больше merge-операций.
- Требует дисциплины cherry-pick и обратных слияний.

### Когда применять

- Когда нужен контролируемый promotion между средами, но нет полноценного artifact-promotion в CD.
- Когда есть несколько поддерживаемых релизов.

## 7. Git Flow (классика Vincent Driessen)

### Схема

```
main      ●──────────────●──────────────────●────────►  только релизы + hotfix
           \            /                  /
release     \──●──●──●─/                  /
                 \   /                   /
develop   ●──●───●─●───●──●───●──●──●───●──►  интеграционная ветка
           \    /    \    /
feature     ●──●      ●──●
```

### Ветки

- `main` — только релизные коммиты, каждый коммит = версия (тег).
- `develop` — интеграция фич, «следующий релиз».
- `feature/*` — от `develop`, мержатся в `develop`.
- `release/*` — от `develop`, стабилизация, затем merge в `main` **и** обратно в `develop`.
- `hotfix/*` — от `main`, merge в `main` и в `develop`.

### Плюсы

- Чёткое разделение «в разработке» и «в проде».
- Удобно для версионируемых продуктов с длинным циклом релиза.
- Формализованный hotfix.

### Минусы

- Две долгоживущие ветки → постоянные merge-конфликты и расхождение.
- `develop` часто «полузелёная», CI/CD усложняется.
- Много ритуалов (merge release → main, обратно в develop) — легко забыть, легко ошибиться.
- Плохо сочетается с непрерывным деплоем и trunk-based CI.
- Сам автор позже отметил, что модель плохо подходит для веб-продуктов с непрерывной доставкой.

### Когда применять

- Продукты с **версионными релизами** и необходимостью поддерживать несколько версий (desktop, on-premise, embedded, библиотеки).
- Команды с формальным релизным циклом и QA-стадией.

## 8. Release Flow (подход Azure DevOps)

Компромисс между Git Flow и trunk-based:

- `main` — trunk, сюда мержатся короткоживущие feature-ветки.
- При подготовке релиза от `main` отводится `release/<номер>`.
- Дальнейшая стабилизация и hotfix — **в release-ветке**, затем cherry-pick/merge обратно в `main`.
- Релизы помечаются тегами; поддерживаются несколько релизных веток параллельно.

**Плюсы:** нет второй постоянной ветки (`develop`), trunk остаётся главным, при этом есть управляемая поддержка версий.
**Минусы:** cherry-pick требует аккуратности (риск «потерянных» фиксов), нужна автоматизация обратных слияний.

**Когда:** мобильные приложения, enterprise-продукты, несколько поддерживаемых версий.

## 9. Environment branching (ветки под среды)

```
feature → develop → test → stage → prod
```

Идея: каждая среда имеет свою ветку, деплой — по push в ветку.

**Почему это считается антипаттерном в зрелом CD:**

- Ветка среды ≠ реальное состояние среды (drift).
- Изменения «протекают» через цепочку merge, теряются при cherry-pick.
- Нельзя гарантировать, что в prod уехал тот же артефакт, что тестировали (пересборка из другой ветки).
- Много долгоживущих веток → конфликты.

**Современная альтернатива:** **один артефакт, продвигаемый между средами** (build once, deploy many) + окружения как конфигурация (GitOps, Helm values, параметры деплоя), а не как ветки.

## 10. Прочие модели

**Forking workflow (open source).** Каждый контрибьютор работает в своём форке, изменения приходят через PR в upstream. Плюсы: изоляция прав, безопасность (CI для PR из форков без секретов). Минусы: сложнее синхронизация, больше overhead.

**Ship / Show / Ask.** Политика поверх trunk-based:
- *Ship* — мелкое безопасное изменение, мержится сразу;
- *Show* — мержится сразу, но с пост-фактум ревью;
- *Ask* — требует ревью до мержа.
Смысл — не тормозить поток мелочей обязательным ревью.

**Branch by abstraction.** Не ветка, а техника: вместо долгой ветки вводится абстракция (интерфейс/флаг), старая и новая реализация сосуществуют в trunk, переключение — флагом/конфигом. Это способ делать крупные изменения в trunk-based мире.

**Patch-based / cherry-pick workflow.** Изменения переносятся cherry-pick между ветками (часто в release flow). Требует автоматизации и проверки, что фикс не потерялся.

## 12. Влияние branching на CI/CD

Это самая важная часть для экзаменационного ответа: стратегия ветвления **напрямую определяет архитектуру пайплайнов**.

### 12.1 Триггеры пайплайнов

- **PR-пайплайн** (`pull_request`): быстрые проверки — lint, unit, сборка, security scan. Цель — не пропустить плохой код в trunk.
- **Post-merge пайплайн** (`push` в `main`): полная сборка, интеграционные тесты, публикация артефакта, деплой в dev/stage.
- **Release-пайплайн** (`push tag` / `release/*`): сборка релизного артефакта, подпись, публикация, деплой в prod.
- **Nightly / scheduled**: тяжёлые e2e, performance, dependency-сканы.

Пример концептуально:

```yaml
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
    tags: ['v*']
```

### 12.2 Артефакт как единица продвижения

Ключевой принцип зрелого CD: **build once, deploy many**. Артефакт (контейнер, пакет, бинарь) собирается один раз из конкретного коммита/тега и продвигается между средами без пересборки. Ветки при этом — лишь способ организовать исходники, а не «версии артефакта».

Плохо: «в ветке `prod` пересоберём — вроде то же самое». Хорошо: «в prod едет образ с digest, который прогнали через stage».

### 12.3 Trunk остаётся зелёным

- **Required status checks** на protected branch.
- **Merge queue / merge train** (GitHub Merge Queue, GitLab Merge Trains, Bors/Bors-NG): PR-ы проверяются в «очереди» на актуальном trunk, чтобы не ломать main при массовых мержах.
- **Автоматический revert** при падении post-merge пайплайна.

### 12.4 Эфемерные окружения (preview environments)

Для каждой PR можно поднимать изолированное окружение (preview app) — это естественно для GitHub Flow/GitLab Flow и сильно ускоряет ревью. Требует инфраструктурной автоматизации (IaC, namespaces, TTL).

### 12.5 Feature flags вместо долгих веток

Флаг позволяет мержить незаконченную фичу в trunk, но не включать её в проде. Это ключевой инструмент, делающий trunk-based реальным. Важно управлять жизненным циклом флагов (удалять после раскатки), иначе появляется «флаговый долг».

### 12.6 Схема БД и обратная совместимость

При частых мержах в trunk миграции должны быть **обратно совместимыми**:
1. expand: добавить новую колонку/таблицу;
2. dual-write / backfill;
3. переключить чтение;
4. contract: удалить старое.

Это позволяет деплоить и откатывать без простоя.

## 13. Merge-стратегии и форма истории

Выбор branching неотделим от выбора способа слияния.

| Способ | Что даёт | Когда использовать |
|---|---|---|
| **Merge commit** (`--no-ff`) | сохраняет историю ветки, явный факт слияния | когда важна трассируемость фичи/PR |
| **Squash merge** | один коммит на PR, чистая линейная история в trunk | GitHub Flow, trunk-based; удобно для revert |
| **Rebase + fast-forward** | линейная история, без merge-коммитов | trunk-based, требование linear history |
| **Cherry-pick** | перенос отдельных коммитов между ветками | release flow, hotfix, backport |

Практические следствия:
- **Squash** упрощает `git bisect`, но теряет промежуточную историю и усложняет перенос фикса в другую ветку (нужен отдельный cherry-pick).
- **Rebase** требует force-push в личной ветке — допустимо, но нельзя rebase общих веток.
- **Merge commit** удобен для release-веток и трассировки «какой PR куда попал».

Рекомендуется зафиксировать правило в CONTRIBUTING и включить нужные опции в настройках репозитория, чтобы не было зоопарка.

## 14. Политики и защита веток

Минимальный «гигиенический» набор:

- **Protected branches**: `main`, `release/*` — запрет прямого push (кроме service accounts), запрет force-push и удаления.
- **Обязательные ревью**: N approvers, «dismiss stale approvals», CODEOWNERS для критичных путей.
- **Обязательные проверки CI**: build, tests, lint, SAST, dependency scan, лицензии.
- **Подпись коммитов/тегов** (GPG/Sigstore) — для релизов и regulated-сред.
- **Правила именования**: `feature/<ticket>-<slug>`, `fix/…`, `release/<semver>`, `hotfix/…`.
- **TTL веток и автоудаление** после мержа.
- **Semantic versioning** и теги на релизах (`v2.4.1`), желательно annotated/signed.

## 15. Версионирование, релизы и hotfix

- **SemVer** (`MAJOR.MINOR.PATCH`) + теги — единый язык версий.
- **Trunk-based**: релиз = тег на `main`; hotfix — коммит в `main`, затем тег patch-версии (и, при необходимости, backport в поддерживаемые release-ветки).
- **Release flow**: hotfix — в `release/N.x`, cherry-pick в `main`, тег patch.
- **Git Flow**: hotfix — от `main`, merge в `main` и `develop`.
- **Несколько поддерживаемых версий** (LTS) требуют release-веток — это единственный случай, когда долгоживущие ветки оправданы.
- **Mobile/desktop**: старые версии живут у пользователей → release-ветки и backport обязательны, чисто trunk-based не получится.

## 16. Метрики, по которым судят о стратегии

Стратегия должна оцениваться не «на вкус», а по метрикам (DORA + локальные):

- **Lead time for changes** — от коммита до прода.
- **Deployment frequency** — частота релизов.
- **Change failure rate** — доля неудачных изменений.
- **MTTR** — время восстановления.
- **Время жизни ветки** (branch age) — цель: часы/дни, не недели.
- **Размер PR** (число строк/файлов) — маленькие PR мержатся быстрее и ревьюятся качественнее.
- **Частота конфликтов и «застрявших» PR**.
- **Доля кода, покрытого тестами на trunk**.

Полезные ориентиры из практики высокопроизводительных команд: **мало активных веток, ветки живут меньше суток, trunk всегда зелёный, релизы маленькими порциями**.

---

## 17. Антипаттерны

1. **Долгоживущие feature-ветки** («сделаю фичу за месяц в ветке») → конфликты, поздняя интеграция, «big bang merge».
2. **Environment-ветки как основной механизм продвижения** → дрейф сред, невозможность гарантировать артефакт.
3. **«Ветка на разработчика»** вместо ветки на задачу.
4. **Прямые push в main** без ревью и проверок.
5. **Пересборка артефакта под каждую среду** — нарушение build once, deploy many.
6. **Git Flow для веб-сервиса с ежедневным деплоем** — лишние ритуалы и merge-конфликты.
7. **Отсутствие политики удаления веток** — сотни «мёртвых» веток.
8. **Cherry-pick без автоматизации** — потерянные фиксы, расхождение веток.
9. **Feature flags без жизненного цикла** — «флаговый долг» и непредсказуемое поведение.
10. **Нет required checks / merge queue** → trunk периодически красный, CI теряет доверие.

## 18. Как выбирать: практический чек-лист

Задайте вопросы:

1. **Сколько версий продукта поддерживается одновременно?** Одна → trunk-based/GitHub Flow; несколько → release-ветки (release flow / Git Flow).
2. **Как часто деплой?** Несколько раз в день → trunk-based; раз в квартал → допустимы release-ветки.
3. **Есть ли зрелые автотесты и быстрый CI?** Нет → сначала инвестируйте в это, иначе trunk-based превратится в «красный main».
4. **Можно ли использовать feature flags?** Да → trunk-based; нет → короткие ветки + Ship/Show/Ask.
5. **Требуется ли формальный аудит изменений?** Да → protected branches, подписи, обязательные ревью, трассируемость PR.
6. **Мобильные/embedded/on-prem?** Скорее всего, нужны release-ветки и backport.
7. **Размер и распределённость команды?** Большая команда → строгие политики, merge queue, CODEOWNERS.
8. **Монорепозиторий?** Стратегия та же, но нужны path-фильтры и affected-based CI (собирать/тестировать только затронутое).

**Практическая рекомендация по умолчанию для современного веб/SaaS:** trunk-based development с короткоживущими ветками, PR-ревью, обязательным CI, merge queue, feature flags, тегами как релизами и артефактом, продвигаемым между средами. Release-ветки добавляются **только** при необходимости поддерживать старые версии.

## 19. Краткий итог (для ответа на собеседовании)

- **Branching strategy** — соглашение о ветках, их времени жизни и правилах интеграции; оно определяет архитектуру CI/CD и релизный процесс.
- Основные модели: **Trunk-Based**, **GitHub Flow**, **GitLab Flow**, **Git Flow**, **Release Flow**, **environment branching**, **forking**.
- Тренд — **минимизация долгоживущих веток** и **непрерывная интеграция в trunk**; долгие ветки и environment-ветки — источники merge hell и дрейфа.
- Ключевые enabling-практики trunk-based: быстрый зелёный CI, автотесты, **feature flags**, **branch by abstraction**, обратно совместимые миграции БД, **merge queue**.
- Выбор зависит от: числа поддерживаемых версий, частоты релизов, зрелости тестов, требований аудита и типа продукта.
- Метрики успеха: короткое время жизни веток, маленькие PR, зелёный trunk, высокая частота деплоя, низкий change failure rate.
