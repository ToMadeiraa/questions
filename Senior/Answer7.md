# 7. Какие есть способы и методологии измерения быстродействия кода? Как можно устранить/уменьшить влияние замеров на быстродействие?

Ниже — системный разбор: сначала о том, **что** измерять, затем **чем** (инструменты и уровни), затем **как** (методологии), и в конце — главное: **почему замер всегда искажает измеряемое** и как это искажение минимизировать.

---

## 1. Что именно мы измеряем: метрики

Прежде чем выбирать инструмент, надо понять, какую величину мы вообще хотим получить. «Быстродействие» — это не одна метрика, а семейство:

| Метрика | Что показывает | Типичный инструмент |
|---|---|---|
| **Wall-clock latency** (время «на часах») | сколько ждёт пользователь/вызывающий | `steady_clock`, `perf`, внешний таймер |
| **CPU time** | сколько процессорного времени сожжено | `CLOCK_PROCESS_CPUTIME_ID`, `getrusage` |
| **Throughput** (пропускная способность) | операций/запросов в секунду | нагрузочные генераторы, счётчики |
| **Tail latency** (p95, p99, p99.9, max) | «хвосты» распределения | HdrHistogram, гистограммы |
| **Аллокации / GC-паузы** | давление на память и паузы | профайлеры памяти, GC-логи |
| **Инструкции, циклы, IPC** | работа на уровне микроархитектуры | PMU: `perf stat`, VTune |
| **Cache misses, branch mispredicts** | эффективность кэшей и предсказателя | PMU, `cachegrind` |
| **Энергопотребление** | стоимость в ваттах/джоулях | RAPL, `powerstat` |

Важно сразу зафиксировать **уровень**: замер одной инструкции, функции, сервиса или всей системы — это разные эксперименты с разными источниками шума. Нельзя оптимизировать «вообще»; оптимизируется конкретная метрика на конкретном уровне.

## 2. Способы измерения

### 2.1 Прямое измерение времени (таймеры в коде)

Самый простой и самый коварный способ: поставить два вызова таймера вокруг участка кода.

```cpp
// C++: монотонные часы, предпочтительно
auto t0 = std::chrono::steady_clock::now();
work();
auto t1 = std::chrono::steady_clock::now();
auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(t1 - t0).count();
```

```java
// Java: System.nanoTime(), не currentTimeMillis()
long t0 = System.nanoTime();
work();
long t1 = System.nanoTime();
```

```python
# Python: perf_counter_ns (монотонный, высокое разрешение)
import time
t0 = time.perf_counter_ns()
work()
t1 = time.perf_counter_ns()
```

```csharp
// .NET: Stopwatch / Stopwatch.GetTimestamp(), не DateTime.Now
var t0 = Stopwatch.GetTimestamp();
Work();
var t1 = Stopwatch.GetTimestamp();
var ns = (t1 - t0) * 1_000_000_000L / Stopwatch.Frequency;
```

Ключевые требования к таймеру:
- **монотонность** (не должен прыгать при смене системного времени);
- **высокое разрешение** (`clock_getres`; у `steady_clock` на Linux обычно наносекунды через vDSO);
- **низкие накладные расходы** (десятки наносекунд; `DateTime.Now` в .NET — сотни наносекунд и хуже);
- **правильная сериализация** при использовании `rdtsc` (см. §5.2).

### 2.2 Микробенчмарки

Измеряют маленький изолированный участок: функцию, алгоритм, одну операцию. Плюс — контроль и повторяемость; минус — риск «оторваться от реальности» (кэш прогрет, данные идеальны, ветвления предсказуемы).

Готовые харнессы (не пишите свой цикл `for` — почти наверняка получите оптимизированный в ноль код):

| Язык | Инструмент |
|---|---|
| C++ | Google Benchmark, nanobench, Celero |
| Java/Scala/Kotlin | **JMH** (Java Microbenchmark Harness) |
| Rust | **Criterion**, divan |
| Python | `timeit`, **pyperf**, `pytest-benchmark`, `asv` |
| Go | `testing.B`, `benchstat` |
| .NET | **BenchmarkDotNet** |
| JS/TS | `tinybench`, `mitata`, `benchmark.js` |
| Shell/CLI | **hyperfine** |

Пример JMH, где аккуратно решены почти все проблемы микробенчмарков:

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(3)                     // отдельные JVM: изоляция профиля
@State(Scope.Thread)
public class MyBench {
    @Benchmark
    public long parse(Blackhole bh) {
        return parseNumber(INPUT);   // результат потребляется, не выкидывается
    }
}
```

### 2.3 Макробенчмарки и нагрузочное тестирование

Измеряют систему целиком: время ответа сервиса, пропускную способность, поведение под нагрузкой. Инструменты: `wrk2`, `hey`, k6, Gatling, JMeter, Locust, `vegeta`, `ab`.

Здесь критичны две вещи:
- **модель нагрузки**: closed-loop (фиксированное число клиентов) vs open-loop (фиксированная интенсивность прихода). Closed-loop искажает хвосты из-за *coordinated omission* — когда система «просела», генератор перестаёт слать запросы и «не замечает» очередь;
- **разделение генератора и системы под тестом**: если генератор упирается в CPU, вы измеряете генератор, а не сервис.

### 2.4 Профилирование

Профилировщик отвечает не на вопрос «сколько», а на вопрос «**где**»:

- **Семплирующие (sampling)**: периодически снимают стек (`perf record -F 99 -g`, async-profiler, py-spy, VTune, `pprof`). Низкие накладные, но есть *skid* (сэмпл «съезжает» на соседнюю инструкцию) и статистическая погрешность.
- **Инструментирующие (instrumenting)**: вставляют хуки в каждую функцию (`-finstrument-functions`, `callgrind`, трассировщики). Точнее по стеку, но замедление в разы — это классический *probe effect*.
- **Аппаратные счётчики (PMU)**: `perf stat -e cycles,instructions,cache-misses,branch-misses`, PEBS/IBS для точной привязки к инструкции.
- **eBPF/bpftrace**: динамические пробы в ядре и用户-space с низкими накладными, on-CPU и off-CPU анализ.
- **Flame graphs**: визуализация стека — ширина = доля времени.

### 2.5 Трассировка

Трассировка фиксирует **последовательность событий** с временными метками: ftrace, LTTng, ETW, Chrome tracing, OpenTelemetry, DTrace. Даёт таймлайн и позволяет увидеть, где время «проваливается» (блокировки, I/O, планировщик), но глобальное включение трассировки заметно замедляет систему — включать надо точечно.

### 2.6 Мониторинг в продакшене

Реальные метрики на реальной нагрузке: APM (Datadog, New Relic, OpenTelemetry), RUM, логи, гистограммы latency. Плюс — нет искусственности; минус — нет контроля над переменными, шумно, и «наблюдатель» уже встроен в систему. Методологии: **RED** (Rate, Errors, Duration) для сервисов и **USE** (Utilization, Saturation, Errors) для ресурсов.

### 2.7 Измерение без запуска

Иногда лучший способ избежать искажений — **вообще не запускать код**:
- асимптотическая оценка сложности (O-нотация);
- аналитические модели: **закон Литтла** `L = λW`, **закон Амдала**, **модель Roofline** (арифметическая интенсивность против пиковых FLOPs и пропускной способности памяти);
- симуляторы микроархитектуры (gem5) — дорого и не всегда репрезентативно, но полностью детерминировано;
- статический анализ и оценка числа инструкций.

### 2.8 Счётчики вместо времени

Мощный приём: измерять **инструкции/циклы**, а не секунды. Количество инструкций детерминировано, не зависит от турбо-режима, соседей и фонового шума — идеально для CI. Минус: не учитывает промахи кэша, предсказания ветвлений и реальные задержки памяти, поэтому счётчики — **прокси**, а не замена времени.

```bash
perf stat -r 10 -e cycles,instructions,cache-misses,branch-misses ./bench
```

## 3. Методологии

### 3.1 Контролируемый эксперимент (научный метод)

Базовая методология, без которой остальное не работает:

1. Сформулировать **гипотезу** («изменение X уменьшит p99 на 10 %»).
2. Зафиксировать **все** переменные: версия компилятора, флаги, железо, ОС, governor, размер данных, прогрев.
3. Менять **ровно одну** переменную за раз.
4. Иметь **контроль** (baseline) и **повторять** эксперимент.
5. Проверить результат статистически и воспроизвести на другой машине/другой день.

### 3.2 Статистическая методология

Время выполнения — случайная величина с **правосторонним** (скошенным) распределением. Поэтому:

- **Не среднее арифметическое**, а **медиана** и **перцентили**; для «чистой» скорости часто берут **минимум** — шум почти всегда только добавляет время, поэтому минимум из многих прогонов ближе всего к «истинной» нижней границе.
- **Дисперсия и MAD** (median absolute deviation) — мера шума.
- **Доверительные интервалы** — бутстрап (ресемплинг) устойчив к ненормальности.
- **Непараметрические тесты** — Mann–Whitney U, Wilcoxon signed-rank (t-тест предполагает нормальность, которой тут нет).
- **Размер эффекта** (Cohen's d, относительная разница) важнее p-value: статистически значимая разница в 0,3 % может быть практически бессмысленной.
- **Мощность и MDE** (minimum detectable effect): сначала измерьте «шумовой пол» пустым бенчмарком. Если харнесс шумит на ±5 %, гоняться за улучшением в 2 % бессмысленно.
- **Поправка на множественные сравнения** (Holm/Bonferroni), если сравниваете много вариантов.
- **Change point detection** для продакшн-метрик — чтобы отличить реальную деградацию от дрейфа.

### 3.3 Парные и интерливед сравнения

Очень действенный приём против дрейфа (тепловой троттлинг, «соседи» по VM, деградация со временем):

```
A B A B A B ... (чередование, порядок рандомизирован)
```

Сравниваются **пары** «A против B в одинаковых условиях», а не «A утром, B вечером». Это резко снижает влияние нестационарности среды. В идеале — «слепой» прогон, когда вы не знаете, какой бинарник запускаете.

### 3.4 Бенчмарк-харнессы и регрессионное тестирование в CI

Перф-тесты как обычные тесты:
- baseline-файлы (`criterion --save-baseline`, `pytest-benchmark --benchmark-compare`, `asv`);
- автоматическое сравнение с предыдущим коммитом и падение сборки при регрессии;
- `benchstat` (Go) для корректного сравнения распределений;
- **важно**: CI-раннеры шумные (shared VM, noisy neighbors). Для стабильности либо выделенное железо, либо переход на счётчики инструкций, либо порог с учётом измеренного шума.

### 3.5 Методологии нагрузочного тестирования

- **Open vs closed model** и борьба с coordinated omission.
- **Little's law** для проверки согласованности: если вы знаете throughput и latency, вы знаете среднюю конкурентность (и наоборот).
- **Ramp-up, soak, spike, stress** — разные профили нагрузки отвечают на разные вопросы.
- **HdrHistogram** и перцентили вместо средних; среднее по latency почти всегда лжёт.

### 3.6 Аналитические законы

- **Амдал** — предел ускорения от параллелизации доли программы.
- **Густафсон** — масштабирование при росте задачи.
- **Roofline** — упёрлись в память или в вычисления?
- **USE/RED** — что именно насыщено.

### 3.7 Performance-driven development

Подход, при котором перф-цель ставится **до** реализации (как acceptance-критерий), а не «потом оптимизируем». Включает бюджет latency, бюджет аллокаций, перф-тесты в PR, профилирование «горячего пути» на каждом релизе.

## 4. Источники искажений: эффект наблюдателя

Любое измерение **воздействует** на измеряемую систему (в физике — принцип неопределённости, в перф-инженерии — *probe effect*, *observer effect*, *Heisenberg effect*). Основные источники:

| Источник | Механизм искажения | Порядок величины |
|---|---|---|
| Накладные расходы таймера | сам вызов таймера стоит времени и портит конвейер/кэш | ~10–100 нс на вызов |
| Разрешение и гранулярность часов | квантование: ошибка до половины тика | мкс и хуже у старых API |
| Инструментирование | хуки в каждой функции, логирование | замедление 2–100× |
| Семплирование | skid, статистическая ошибка, смещение к «горячим» местам | 1–10 % |
| Прогрев кэшей | повторные прогоны живут в L1/L2, реальность — нет | до 10–100× на микроуровне |
| Предсказатель ветвлений | после прогрева предсказывает идеально | сильно завышает скорость |
| Turbo Boost / DVFS / троттлинг | частота плавает между прогонами | 10–30 % |
| SMT / «соседи» по VM | конкуренция за исполнительные порты и кэш | до 2× |
| NUMA | удалённая память медленнее локальной | 1,5–2× |
| GC / JIT / деоптимизация | паузы и «разогрев» рантайма | паузы мс–сотни мс |
| Аллокатор и состояние страниц | first-touch, page faults, фрагментация | мкс–мс |
| Фоновые процессы, антивирус, индексация | шум | произвольно |
| Порядок запусков, дрейф | тренд температуры и состояния машины | до десятков % |
| Оптимизации компилятора | мёртвый код и свёртка констант удаляют замеряемое | «0 нс» |
| Отладчик / strace / ltrace | ptrace и остановки | 10–1000× |

Плюс методологические искажения: **предвзятость отбора** (удобные данные), **предвзятость подтверждения** (мерим, пока не получим желаемое), **закон Гудхарта** («когда метрика становится целью, она перестаёт быть хорошей метрикой»), **эффект Хоторна** (наблюдение меняет поведение системы).

## 5. Как устранить или уменьшить влияние замеров

### 5.1 На уровне дизайна эксперимента

1. **Измеряйте снаружи, а не внутри.** Внешний таймер (`hyperfine`, `/usr/bin/time`, eBPF uprobe, PMU) не вторгается в горячий код. Внутренний таймер оставляйте только там, где нужна разбивка по фазам.
2. **Амортизируйте.** Один замер на N итераций: `(t_work·N + t_timer)/N = t_work + t_timer/N`. При N = 10⁴ накладные таймера становятся пренебрежимо малы. Это самый надёжный приём.
3. **Измеряйте «нулевой» бенчмарк.** Пустой цикл/пустая функция даёт **шумовой пол** харнесса — с ним и надо сравнивать.
4. **Разделяйте прогрев и измерение.** Отдельно фиксируйте *cold start* (важно для сервисов, JIT, кэшей) и *steady state* (важно для алгоритмов).
5. **Чередуйте A/B и рандомизируйте порядок** — против дрейфа и эффекта порядка.
6. **Повторяйте в разных процессах** (JMH `@Fork`, отдельные запуски) — против «загрязнения» профиля и состояния кучи.
7. **Делайте замер репрезентативным**: реальные размеры данных, реальный рабочий набор (влезает ли он в кэш?), реальные паттерны доступа, реальные флаги сборки (Release + LTO/PGO — то, что шипится).
8. **Планируйте статистику заранее**: сколько прогонов нужно, чтобы обнаружить ожидаемый эффект при известном шуме.

### 5.2 На уровне кода и таймеров

1. **Не давайте компилятору выбросить работу.** Барьеры и «поглотители» результата:

```cpp
// C++: не дать оптимизировать вычисление
template <class T>
inline void do_not_optimize(T const& v) {
    asm volatile("" : : "r,m"(v) : "memory");
}
// В Google Benchmark: benchmark::DoNotOptimize(x); benchmark::ClobberMemory();
```

```rust
// Rust
let y = std::hint::black_box(compute(x));
```

```java
// JMH: результат нужно «потребить»
bh.consume(result);
```

2. **Берите входные данные извне** (`volatile`, аргумент командной строки, файл), чтобы компилятор не свернул всё в константу.
3. **Не логируйте и не печатайте внутри замеряемого участка** — I/O на порядки дороже вычислений.
4. **Выносите подготовку данных за пределы замера** (но не обманывайте себя: подготовка — тоже часть реальной стоимости).
5. **Правильный таймер**: `steady_clock` / `CLOCK_MONOTONIC_RAW` / `QueryPerformanceCounter` / `perf_counter_ns`; избегайте `gettimeofday`, `DateTime.Now`, `clock()`.
6. **`rdtsc` — только с сериализацией** (`lfence; rdtsc` или `rdtscp`), иначе процессор переставит инструкции и замер «съедет». Учитывайте миграцию между ядрами (у `rdtscp` есть `IA32_TSC_AUX`) и разные TSC на разных сокетах.
7. **Замеряйте батчами**, а не одиночные вызовы, если только вам не нужна именно per-call latency; для latency — гистограммы, а не средние.
8. **Помните, что вычитание baseline не всегда корректно**: накладные расходы не строго аддитивны из-за out-of-order выполнения и перекрытия. Амортизация надёжнее вычитания.

### 5.3 На уровне окружения

1. **Изоляция CPU**: `taskset`/`cpuset`, `isolcpus`, отключение SMT (Hyper-Threading), `chrt` для real-time приоритета.
2. **Фиксация частоты**: `cpupower frequency-set -g performance`, отключение Turbo, контроль троттлинга. Либо наоборот — измерять в **циклах** через PMU, чтобы частота не влияла.
3. **NUMA-привязка** (`numactl --cpunodebind --membind`), локальная память.
4. **Тихая машина**: без антивируса, индексации, обновлений, браузера; по возможности выделенный стенд.
5. **Один и тот же стенд для A и B** и фиксация «отпечатка» окружения (CPU, RAM, ОС, компилятор, флаги) в отчёте.
6. **Не мерить под отладчиком/`strace`** и в debug-сборке.

### 5.4 На уровне инструментов

1. Предпочитайте **семплирующие** профайлеры инструментирующим; частоту сэмплирования — умеренную (например, 99 Гц), чтобы не создавать нагрузку.
2. Для аппаратных счётчиков учитывайте **мультиплексирование**: если событий больше, чем счётчиков, `perf` масштабирует значения — смотрите `%` времени включения счётчика.
3. Используйте **PEBS/IBS** для точной привязки сэмпла к инструкции (меньше skid).
4. **eBPF** — минимальные накладные, но не нулевые: включайте только нужные пробы.
5. Трассировку включайте **точечно** и на короткое время; глобальная трассировка всех событий искажает картину.
6. Для архитектурных исследований — симулятор (gem5), где эффекта наблюдателя нет вовсе (ценой скорости и реализма).

### 5.5 На уровне статистики и отчётности

1. Отчёт: **медиана ± MAD**, перцентили, **n**, минимум, максимум — не только среднее.
2. Доверительные интервалы (бутстрап) и непараметрические тесты.
3. Явно указывайте **шумовой пол** и **MDE**; не заявляйте улучшения ниже шума.
4. Проверяйте **воспроизводимость** на другом запуске, в другой день, на другой машине.
5. Для CI — либо выделенное железо, либо счётчики инструкций как стабильный прокси, либо адаптивный порог.

## 6. Практический чек-лист

- [ ] Метрика и уровень определены (latency/throughput/инструкции; функция/сервис/система).
- [ ] Замеряется **тот артефакт**, который шипится (Release, те же флаги, LTO/PGO).
- [ ] Есть baseline и контрольный «нулевой» замер (шумовой пол).
- [ ] Прогрев отделён от измерения; cold и warm меряются отдельно.
- [ ] Результат работы не оптимизирован компилятором (`DoNotOptimize`/`black_box`/`bh.consume`).
- [ ] Таймер монотонный, с достаточным разрешением, накладные амортизированы.
- [ ] Окружение стабилизировано (pinning, частота, SMT, NUMA, фон).
- [ ] Прогоны чередуются/рандомизированы; проведено ≥ 10–30 повторов.
- [ ] Отчёт содержит медиану, перцентили, разброс, n и описание окружения.
- [ ] Вывод статистически обоснован и воспроизведён.

## 7. Типичные ошибки

- Мерить **один раз** и делать вывод.
- Мерить **среднее** по скошенному распределению и игнорировать хвосты.
- Мерить **микросекунды таймером с разрешением в микросекунды**.
- Забыть про **dead code elimination** и получить «0 нс».
- Мерить **прогретый** кэш и экстраполировать на реальную нагрузку.
- Сравнивать **разные сборки/железо/дни** без контроля.
- Включать **трассировку всего** и удивляться замедлению.
- Верить **p-value** без размера эффекта.
- Оптимизировать **не тот участок** (без профайлера).
- Превращать бенчмарк в **цель** (закон Гудхарта): код оптимизируется под бенчмарк, а не под задачу.

## 8. Итог

Способы измерения образуют лестницу: **таймеры в коде → микробенчмарк-харнессы → профайлеры → трассировка → нагрузочное тестирование → продакшн-мониторинг → аналитические модели**. Методологии — это надстройка: контролируемый эксперимент, корректная статистика (медианы, перцентили, бутстрап, непараметрические тесты), парные интерливед-сравнения, регрессионные перф-тесты в CI и отраслевые рамки (Little, Amdahl, Roofline, USE/RED).

Полностью устранить влияние замеров нельзя — измерение всегда возмущает систему. Но можно сделать его **пренебрежимо малым**:
- **амортизировать** накладные (N итераций на замер),
- **измерять снаружи** и **счётчиками** там, где важна стабильность,
- **изолировать** окружение (pinning, частота, SMT, NUMA, фон),
- **стабилизировать** код (барьеры, `black_box`, запрет свёртки),
- **чередовать** A/B и **усреднять статистикой** (медиана, минимум, бутстрап),
- **знать шумовой пол** и не гоняться за эффектами ниже него.

Главный принцип: **сначала измерьте, потом оптимизируйте — и измеряйте так, чтобы измерение не стало главным измеряемым эффектом.**
