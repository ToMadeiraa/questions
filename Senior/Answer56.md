# 56. Что такое coroutine?

**Корутина (coroutine, сопрограмма)** — это обобщение функции, которая умеет **приостанавливать** своё выполнение в явно указанной точке, **сохранять всё своё состояние** (локальные переменные, точку остановки, параметры, контекст) и быть **возобновлена позже** — с того же самого места, возможно, уже из другого потока или другого места программы.

Ключевая формула: **функция + точки приостановки + сохраняемое состояние + внешний планировщик**. Управление передаётся наружу не только при `return`, но и в точках `suspend`; возврат внутрь — не с начала функции, а в сохранённую точку.

Важно сразу отделить корутины от смежных понятий:

- это **не поток** — корутина сама по себе не даёт параллелизма и не создаёт поток ОС;
- это **не параллелизм**, а **конкурентность** (concurrency): несколько логических потоков исполнения, продвигаемых кооперативно;
- это **не колбэк и не конечный автомат**, хотя по смыслу корутина — это автоматически сгенерированный конечный автомат, избавленный от ручного `switch`/состояний.

---

## 1. Идея: suspend / resume

Обычная функция имеет один вход и один выход. Корутина имеет **много выходов и много входов**: каждая точка `co_await`/`co_yield` — это потенциальный выход, и она же — точка входа при возобновлении.

```
вызов корутины
   │
   ▼
[ создание кадра, копирование параметров, promise ]
   │
   ▼
[ тело: ... выполнение ... ] ──suspend──► управление возвращается вызывающему
   ▲                                              │
   └──────────── resume() ◄───────────────────────┘
   │
   ▼
[ продолжение с сохранённой точки ] ── ... ──► завершение
```

Состояние, которое должно пережить приостановку, компилятор складывает в **coroutine frame** (кадр корутины). Именно наличие/отсутствие отдельного стека у этого кадра и делит корутины на два больших класса.

## 2. Два вида корутин: stackful и stackless

### Stackful (со стеком)

У каждой корутины **свой собственный стек**. Приостановка — это переключение указателя стека (как переключение контекста), поэтому «заснуть» можно **в любой вложенной функции**, на любой глубине вызова.

Реализации: `boost::coroutines2` (поверх `boost::context`), POSIX `ucontext_t` (`makecontext`/`swapcontext`), Windows Fibers (`CreateFiber`/`SwitchToFiber`), библиотеки `libco`, `libaco`.

```cpp
#include <boost/coroutine2/all.hpp>
#include <iostream>

using Coro = boost::coroutines2::coroutine<int>;

void producer(Coro::push_type& yield) {
    for (int i = 0; i < 3; ++i)
        yield(i);          // приостановка с сохранением всего стека
}

int main() {
    Coro::pull_type source{producer};
    for (int v : source)
        std::cout << v << '\n';   // 0 1 2
}
```

Плюсы: можно усыпить вызов на любой глубине, не нужно «красить» всю цепочку функций. Минусы: стек стоит памяти (обычно 64 КБ–1 МБ на корутину), переключение дороже, переносимость хуже.

### Stackless (без стека) — это C++20

Отдельного стека нет. Всё, что нужно сохранить, лежит в **кадре в куче** (или на стеке вызывающего при удачном стечении обстоятельств). Приостановиться можно **только в самой корутине**, в точке `co_await`/`co_yield`/`co_return`. Вложенная обычная функция усыпить корутину не может — она должна сама быть корутиной.

Отсюда знаменитая проблема **function coloring**: если вы хотите `co_await` внутри функции, эта функция и все её вызывающие в цепочке обязаны быть корутинами (или мостами между мирами).

C++20 стандартизировал именно stackless-корутины. Это очень дешёвый и очень гибкий механизм — но только механизм, без готовой библиотеки.

## 3. Корутины в C++20: язык, а не библиотека

Стандарт C++20 ([dcl.fct.def.coroutine], [expr.await], [support.coroutine]) даёт **три ключевых слова** и набор правил, по которым компилятор преобразует тело функции в конечный автомат:

| Ключевое слово | Смысл |
|---|---|
| `co_await expr` | приостановиться, пока не будет готов результат `expr` |
| `co_yield expr` | отдать значение наружу и приостановиться (эквивалент `co_await promise.yield_value(expr)`) |
| `co_return [expr]` | завершить корутину (эквивалент `promise.return_value(expr)` или `promise.return_void()`) |

Функция является корутиной **тогда и только тогда**, когда в её теле встречается хотя бы одно из этих слов. Никаких атрибутов и объявлений не нужно — свойство определяется телом.

Ограничения: корутинами **не могут** быть `main`, конструкторы, деструкторы, `constexpr`-функции; `co_await` нельзя использовать в обработчиках исключений (`catch`); лямбда-корутина разрешена.

### 3.1. Что компилятор делает с корутиной

Порядок при вызове:

1. выделяется **coroutine frame** (обычно `operator new`, но может быть и элизия — HALO, heap allocation elision optimization; стандарт её не гарантирует);
2. в кадр **копируются параметры** (по значению; ссылки остаются ссылками);
3. создаётся объект **promise** (`promise_type`);
4. вызывается `promise.get_return_object()` — то, что вернётся вызывающему;
5. выполняется `co_await promise.initial_suspend()`;
6. если не приостановились — исполняется тело до первой точки приостановки/завершения.

Дальше тело — это `switch` по номеру состояния; каждый `resume()` прыгает в сохранённую точку.

### 3.2. `promise_type` — «политика» корутины

Вся семантика корутины задаётся вложенным типом `promise_type` (находится через `std::coroutine_traits`). Обязательный набор:

```cpp
struct promise_type {
    MyTask get_return_object();                 // что вернуть вызывающему
    std::suspend_always initial_suspend();      // запускать тело сразу или лениво
    std::suspend_always final_suspend() noexcept;
    void return_void();                         // или return_value(T)
    void unhandled_exception();                 // обязательно
};
```

Дополнительно может быть `yield_value(T)` (для `co_yield`), перегрузки `operator new`/`operator delete` для кадра, `await_transform` (хук на каждый `co_await` внутри корутины).

Нюансы:
- `return_void` и `return_value` взаимоисключающи;
- `final_suspend` с `suspend_always` оставляет кадр живым — это нужно, чтобы вызывающий мог забрать результат; уничтожать кадр тогда обязан владелец (`handle.destroy()`);
- `final_suspend` с `suspend_never` уничтожает кадр автоматически;
- если управление доходит до конца, а в promise нет `return_void` — поведение не определено.

### 3.3. Протокол `co_await`: awaiter

Операнд `co_await` преобразуется в **awaiter** — объект с тремя методами:

```cpp
struct Awaiter {
    bool await_ready() const noexcept;                 // готов ли результат сразу?
    void await_suspend(std::coroutine_handle<> h);     // что сделать при приостановке
    T    await_resume();                               // результат co_await
};
```

- `await_ready() == true` — приостановки нет, сразу `await_resume()`;
- `await_suspend(h)` получает handle корутины, чтобы её можно было возобновить позже (положить в очередь, подписать на событие, передать в io_context);
- `await_suspend` может вернуть `void` (приостановиться), `bool` (`false` — не приостанавливаться) или `std::coroutine_handle<>` — это **symmetric transfer**: возобновление другой корутины без роста стека, важнейший приём для глубоких цепочек `co_await`.

Готовые тривиальные awaiter'ы: `std::suspend_always` и `std::suspend_never`. Есть также `std::noop_coroutine()`.

### 3.4. Handle

`std::coroutine_handle<Promise>` — это, по сути, типизированный указатель на кадр:

```cpp
h.resume();    // продолжить
h.done();      // завершена ли
h.destroy();   // уничтожить кадр
h.promise();   // доступ к promise
std::coroutine_handle<P>::from_promise(p);
std::coroutine_handle<>                 // type-erased версия
```

Это «сырой» низкоуровневый тип: он не управляет временем жизни, не потокобезопасен, не умеет отмену. Всё это — забота библиотеки-обёртки.

## 4. Пример: генератор

Классический stackless-генератор: ленивое производство последовательности.

```cpp
#include <coroutine>
#include <exception>
#include <utility>

template <class T>
class Generator {
public:
    struct promise_type {
        T value{};

        Generator get_return_object() noexcept {
            return Generator{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; }
        std::suspend_always final_suspend()   noexcept { return {}; }
        std::suspend_always yield_value(T v) noexcept { value = std::move(v); return {}; }
        void return_void() noexcept {}
        void unhandled_exception() { std::terminate(); }
    };

    explicit Generator(std::coroutine_handle<promise_type> h) noexcept : h_(h) {}
    Generator(Generator&& o) noexcept : h_(std::exchange(o.h_, {})) {}
    Generator(const Generator&) = delete;
    ~Generator() { if (h_) h_.destroy(); }

    bool next() { h_.resume(); return !h_.done(); }
    const T& value() const { return h_.promise().value; }

private:
    std::coroutine_handle<promise_type> h_;
};

Generator<int> iota(int n) {
    for (int i = 0; i < n; ++i)
        co_yield i;              // приостановка + значение наружу
}

int main() {
    auto g = iota(3);
    while (g.next())
        std::cout << g.value() << '\n';   // 0 1 2
}
```

Здесь `initial_suspend = suspend_always` делает корутину **ленивой**: тело не начинается до первого `resume()`. Такой генератор — это, по сути, ручной итератор без написания класса-итератора и без хранения состояния в полях.

В C++23 есть готовый `std::generator<T>` из `<generator>` — стандартный ленивый синхронный генератор.

## 5. Пример: задача (task) и планировщик

```cpp
struct Task {
    struct promise_type {
        Task get_return_object() {
            return Task{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; } // ленивая
        std::suspend_always final_suspend()   noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() { std::terminate(); }
    };
    std::coroutine_handle<promise_type> h;
    void start() { h.resume(); }
    ~Task() { if (h) h.destroy(); }
};

struct YieldNow {
    bool await_ready() const noexcept { return false; }
    void await_suspend(std::coroutine_handle<> h) const {
        // положить h в очередь планировщика и вернуться
    }
    void await_resume() const noexcept {}
};

Task worker() {
    std::cout << "A\n";
    co_await YieldNow{};        // отдать управление, продолжить позже
    std::cout << "B\n";
}
```

Смысл: **корутина не решает, когда её возобновят**. Это делает планировщик — очередь, `io_context`, пул потоков, event loop. Корутина лишь сообщает «я уснула, вот мой handle».

## 6. Связь с потоками

Корутина и поток ортогональны:

- корутина может **начаться в одном потоке, а продолжиться в другом** — стандарт это разрешает (но не делает потокобезопасным);
- одну и ту же корутину **нельзя** возобновлять одновременно из двух потоков — это гонка/UB, нужна внешняя синхронизация;
- корутины **не создают** параллелизма: чтобы получить многоядерность, нужно несколько потоков + планировщик, раздающий корутины по потокам (модель M:N);
- типичная схема: пул потоков + `io_context`/executor, на котором крутятся тысячи корутин, каждая из которых в каждый момент времени «висит» на `co_await` сетевого I/O.

Это и есть главный практический выигрыш: **тысячи конкурентных задач при десятках потоков ОС**, без колбэков и без ручных конечных автоматов.

---

## 7. Производительность и память

| Операция | Порядок стоимости |
|---|---|
| обычный вызов функции | ~1 нс |
| resume stackless-корутины | единицы нс (косвенный вызов + переход по состоянию) |
| переключение stackful-корутины | ~10–100 нс |
| переключение потока ОС | ~1–10 мкс |

Память:
- stackless: кадр в куче, обычно десятки–сотни байт (promise + параметры + переживающие приостановку локальные). Аллокацию можно убрать/переиспользовать своим `operator new` в promise или HALO-оптимизацией;
- stackful: полноценный стек, 64 КБ–1 МБ на экземпляр;
- поток ОС: стек 1–8 МБ (виртуально) плюс структуры ядра.

---

## 8. Где применяют

- **асинхронный I/O** — сеть, файлы, таймеры: `co_await socket.async_read(...)` вместо цепочки колбэков (Boost.Asio `awaitable<T>`/`co_spawn`, cppcoro, libunifex);
- **генераторы и ленивые последовательности** — парсеры, обходы деревьев, бесконечные последовательности, пайплайны;
- **конечные автоматы в явном виде** — протоколы, игры, UI-сценарии;
- **акторы/задачи** — структурированная конкурентность, отмена, таймауты;
- **C++26 `std::execution`** (senders/receivers, P2300) — корутины как один из способов писать асинхронный код поверх общей модели исполнения.

## 9. Подводные камни

1. **Время жизни.** Handle — сырой указатель. Уничтожение кадра, пока он приостановлен в `await_suspend`, — UB. Нужен владелец (RAII-обёртка) и дисциплина отмены.
2. **Висячие ссылки.** Параметры копируются в кадр, но ссылки остаются ссылками. Классическая ошибка: `co_await f(const T&)` с временным объектом, который умрёт до возобновления.
3. **Лямбда-захваты.** Лямбда-корутина копирует замыкание в кадр, но захваты по ссылке (`[&]`) после приостановки могут указывать на уже мёртвые объекты.
4. **Function coloring.** Один `co_await` заражает всю цепочку вызовов; мосты (`blocking_wait`, `sync_wait`) нужны явно.
5. **Нет стандартной библиотеки.** В C++20 нет стандартных `task`, `generator`, `sync_wait` — каждый пишет свои или берёт cppcoro/unifex/Asio. Отсюда несовместимость типов задач между библиотеками.
6. **Отладка.** Стек-трейсы обрываются на границах корутин, профайлеры и санитайзеры видят «странные» стеки; точки приостановки надо логировать.
7. **Исключения.** `unhandled_exception()` обязателен; при `-fno-exceptions` семантика урезана; исключение, выброшенное из `await_resume`, приходит в тело корутины.
8. **Аллокация.** Каждый запуск — потенциальный `new`; в горячем цикле это заметно, нужен пул/кастомный аллокатор.
9. **Потоковая привязка.** Возобновление не в том потоке, где ждали, ломает инварианты (например, thread-local, GUI-поток).
10. **Рекурсия.** Прямая рекурсивная корутина легко переполняет стек; нужен trampoline/symmetric transfer.

## 10. А что в C?

В стандарте **C корутин нет** — ни в C11, ни в C17, ни в C23. Язык даёт только функции, и «приостановиться» в середине функции средствами стандарта нельзя.

Практические варианты для C-кода:

- **stackful-библиотеки**: POSIX `ucontext.h` (`makecontext`/`swapcontext`), Windows Fibers, `libaco`, `libco`, `libtask`;
- **`setjmp`/`longjmp`** — технически возможно, но опасно: не раскручиваются деструкторы/cleanup, легко получить UB;
- **явный конечный автомат** — самый переносимый и предсказуемый путь: структура состояния + `switch` + функции-шаги;
- **потоки** (`pthreads`, Win32 threads) — дают параллелизм, но не решают задачу «много дешёвых конкурентных задач»;
- **C-API поверх C++20-корутин** — часто самый прагматичный вариант: реализация на C++, наружу — непрозрачный handle и функции `resume`/`destroy`.

## Итог

**Coroutine** — это функция с точками приостановки, которая сохраняет своё состояние между вызовами и возобновляется внешним планировщиком. В C++20 это **stackless-корутины**: компилятор превращает тело функции с `co_await`/`co_yield`/`co_return` в конечный автомат с кадром в куче, а всю политику (что вернуть, когда стартовать, что делать при исключении, как усыплять) задаёт пользовательский `promise_type` и протокол awaiter'ов. Это не потоки и не параллелизм — это дешёвый инструмент **конкурентности**, поверх которого строят генераторы, асинхронный I/O и задачи; главные практические сложности — отсутствие стандартной библиотеки корутин, «раскрашивание» функций, время жизни кадра и висячие ссылки. В C стандартных корутин нет: там применяют stackful-библиотеки (`ucontext`, fibers), явные конечные автоматы или C-API поверх C++20.
