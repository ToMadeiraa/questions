# 42. Что такое Return Value Optimization?

## Кратко

**Return Value Optimization (RVO)** — это оптимизация (а начиная с C++17 в части случаев — обязательное правило языка), при которой объект, возвращаемый функцией по значению, создаётся **сразу в том месте памяти, где его ожидает вызывающий код**, и при этом не выполняется ни конструктор копирования, ни конструктор перемещения.

Говоря формально, RVO — это частный случай **copy elision** (элизии копирования/перемещения): стандарт разрешает компилятору «выбросить» копирование или перемещение объекта, даже если конструктор копирования/перемещения имеет побочные эффекты. Именно поэтому RVO — редкий пример оптимизации, которая **может изменять наблюдаемое поведение программы** (что стандарт явно разрешает).

## Терминология: URVO и NRVO

Различают два вида:

| | **URVO** (Unnamed RVO, «безымянный») | **NRVO** (Named RVO, «именованный») |
|---|---|---|
| Где возникает | `return T(...);`, `return {…};` — возвращается временный объект (prvalue) | `T t; … return t;` — возвращается именованная локальная переменная |
| Статус | с C++17 **обязателен** (guaranteed copy elision) | **необязателен** во всех версиях стандарта, зависит от компилятора |
| Требования к конструкторам | в C++17 конструктор копирования/перемещения **не нужен вообще** | конструктор копирования/перемещения должен быть **доступен и не удалён**, даже если фактически не вызывается |
| Наблюдаемость | поведение строго определено стандартом | компилятор вправе как применить, так и не применить элизию |

Иногда словом «RVO» называют только URVO, а NRVO выделяют отдельно; в широком смысле RVO — это оба случая.

## Как это работает «под капотом»

Для типа с нетривиальной конструкцией/деструктором компилятор обычно реализует возврат по значению через **скрытый параметр (hidden pointer, `sret` — struct return)**:

```cpp
// Исходный код
T make() {
    T t;
    // ...
    return t;
}

// Примерно во что это превращается на уровне ABI
void make(T* __hidden_result) {
    // T t конструируется прямо по адресу __hidden_result
    new (__hidden_result) T();
}
```

Вызывающий код передаёт адрес своей переменной-приёмника, и функция конструирует результат непосредственно там. Никакого промежуточного объекта и никакого копирования не возникает. Для маленьких тривиально копируемых типов результат может возвращаться в регистрах (например, `RAX:RDX` в System V AMD64), но это уже детали ABI, а не языка.

Именно поэтому при NRVO адрес локальной переменной внутри функции может совпадать с адресом переменной в вызывающем коде — и это законно, поскольку стандарт разрешает элизию, меняющую наблюдаемое поведение.

## Гарантированная элизия в C++17

До C++17 RVO было лишь «разрешённой оптимизацией»: компилятор мог её сделать, но не обязан. Начиная с C++17 (P0135R1, «guaranteed copy elision») в ряде случаев элизия **гарантирована стандартом** и не является оптимизацией в обычном смысле — меняется сама семантика: prvalue больше не обозначает временный объект, а является выражением, которое **непосредственно инициализирует** конечный объект.

Обязательная элизия применяется, в частности, когда:

- prvalue инициализирует объект: `T x = T();`, `T x = f();` (если `f` возвращает `T` по значению);
- prvalue возвращается из функции: `return T(...);`, `return {…};`;
- prvalue передаётся в функцию по значению: `g(T());`;
- prvalue используется в `throw` (инициализация объекта исключения).

Практическое следствие: в C++17 можно возвращать по значению **неперемещаемые и некопируемые** типы.

```cpp
struct P {
    P() = default;
    P(const P&) = delete;
    P(P&&) = delete;
};

P create() { return P(); }   // OK в C++17; ошибка в C++14 (нужен доступный copy/move)
P p = P();                   // OK в C++17

P create_bad() {
    P p;
    return p;                // ОШИБКА и в C++17: NRVO не гарантирован,
}                            // нужен доступный конструктор копирования/перемещения
```

Классический практический пример — типы вроде `std::mutex`, `std::atomic`, `std::condition_variable`, у которых нет ни копирования, ни перемещения: фабрику, возвращающую их по значению, можно написать только в C++17.

## NRVO: когда он срабатывает, а когда нет

NRVO применяется, если выполнены условия (C++17 [class.copy.elision]):

- возвращается **имя** не-volatile автоматической переменной;
- это **не** параметр функции и **не** переменная из `catch`-обработчика;
- тип переменной совпадает с типом возвращаемого значения (с точностью до cv-квалификаторов);
- возврат происходит в `return`-инструкции.

На практике компиляторы чаще всего применяют NRVO, когда в функции **одна** точка возврата (или все `return` возвращают одну и ту же переменную). NRVO **не будет** применён, если:

```cpp
T f(T param)        { return param; }        // параметр — NRVO нет (будет move/copy)
T g()               { return this->member; } // член — NRVO нет (copy/move)
T h()               { static T s; return s; }// статическая — NRVO нет
T i(bool c)         { T a, b; return c ? a : b; } // не id-expression — copy/move
T j()               { T t; return std::move(t); } // std::move мешает NRVO
T k()               { T t; return (t); }     // скобки/иные выражения — как правило, нет
```

Также NRVO обычно не применяется, если возвращаемый тип — базовый класс, а переменная — производного (будет срезка через копирование/перемещение).

## Примеры и наблюдаемые эффекты

```cpp
#include <iostream>

struct S {
    S()         { std::cout << "S()\n"; }
    S(const S&) { std::cout << "copy\n"; }
    S(S&&)      { std::cout << "move\n"; }
    ~S()        { std::cout << "~S()\n"; }
};

S make()       { return S(); }   // URVO
S make_named() { S s; return s; } // NRVO (обычно)

int main() {
    S a = make();        // C++17: только S() и ~S()
    S b = make_named();  // обычно тоже без copy/move
}
```

В C++17 для `make()` вывод строго определён: `S()`, затем `~S()` — конструкторы копирования и перемещения не вызываются. Для `make_named()` на практике то же самое, но стандарт этого не гарантирует.

Если собрать в режиме C++14 с `-fno-elide-constructors` (GCC/Clang), можно увидеть «настоящую» цепочку: временный объект → перемещение в возвращаемый слот → перемещение в `a` → три деструктора. Это полезно, чтобы понять, от чего именно спасает RVO.

Ещё важный нюанс: если NRVO внутри функции не сработал, в C++17 на стороне вызывающего кода **всё равно не будет второй копии**. Вызов `f()` — это prvalue, и `T x = f();` инициализирует `x` напрямую; без NRVO будет ровно одно перемещение/копирование (из локальной переменной в возвращаемый объект), а не два, как в C++14 без элизии.

## RVO и move-семантика

До C++11 RVO был главным способом избежать дорогого копирования при возврате по значению. С появлением move-семантики ситуация изменилась, но RVO не потерял смысла: он позволяет избежать **и копирования, и перемещения**.

Типичный антипаттерн:

```cpp
T f() {
    T t;
    return std::move(t);  // ПЛОХО: запрещает NRVO, гарантируя move
}
```

Правильно — просто `return t;`: если NRVO сработает, не будет ни копии, ни перемещения; если нет — компилятор сам рассмотрит `t` как rvalue и выполнит перемещение (implicit move). Современные компиляторы предупреждают об этом (`-Wpessimizing-move`, `-Wredundant-move`, `-Wreturn-std-move`).

Отметим также, что **параметр функции не участвует в NRVO**, но при возврате он всё равно может быть перемещён, а не скопирован. Формулировки неявного перемещения при возврате в C++20 были переработаны (P1825R0), но вывод один: для параметра NRVO не бывает ни в одной версии стандарта.

## Как это включить/выключить и как заметить

- GCC/Clang: `-fno-elide-constructors` отключает **необязательную** элизию (NRVO и элизию в режиме до C++17). Обязательную элизию C++17 отключить нельзя — она часть семантики языка.
- MSVC: в новых версиях NRVO управляется ключом `/Zc:nrvo` / `/Zc:nrvo-`; исторически в отладочной сборке (`/Od`) NRVO мог отключаться.
- Clang: предупреждение `-Wnrvo` (C++17) сообщает, когда NRVO не применён.
- Наблюдать RVO можно по отсутствию вызовов конструктора копирования/перемещения и по совпадению адресов объектов.

## Частые заблуждения

1. **«RVO — это гарантия для любого возврата по значению».** Нет: гарантирован только URVO (prvalue) в C++17; NRVO — по усмотрению компилятора.
2. **«`return std::move(x)` ускоряет возврат».** Наоборот: обычно это лишает NRVO и добавляет перемещение.
3. **«RVO — это про выделение памяти в куче».** Нет: объект всё равно создаётся, просто сразу в нужном месте; динамической памяти RVO не требует.
4. **«При RVO конструктор копирования не нужен».** В C++17 — верно для гарантированных случаев; для NRVO (и для C++14 и раньше) конструктор должен быть доступен, даже если не вызывается.
5. **«RVO всегда одинаков во всех сборках».** NRVO зависит от компилятора, уровня оптимизации и структуры кода (одна точка возврата, отсутствие `std::move` и т.п.).

## Итог

- **RVO** — устранение копирования/перемещения при возврате объекта по значению за счёт конструирования результата непосредственно в памяти приёмника.
- **URVO** (возврат prvalue) в C++17 **обязателен** и позволяет возвращать некопируемые/неперемещаемые типы.
- **NRVO** (возврат именованной локальной переменной) — **необязательная** оптимизация; для неё нужен доступный конструктор копирования/перемещения.
- RVO экономит и копирование, и перемещение; `return std::move(x)` — антипаттерн, мешающий NRVO.
- Благодаря RVO возврат по значению в C++ — идиоматичный и эффективный способ передачи объектов, а не «дорогая операция».
