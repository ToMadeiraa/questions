# 33. Как размещается в памяти класс со множественным наследованием и виртуальными функциями?

> Кратко: объект — это последовательно уложенные подобъекты баз (для невиртуальных баз — в порядке объявления) плюс собственные поля класса. Каждый **полиморфный** подобъект (подобъект базы, у которой есть виртуальные функции) содержит собственный `vptr`. Одна из баз («первичная») делит `vptr` с производным классом; для остальных баз создаются **вторичные таблицы виртуальных функций**, слоты которых часто заполнены трамплинами (**thunk**), корректирующими `this`. Из-за этого указатели на один и тот же объект через разные базы имеют **разные числовые значения**.

## 0. Важная оговорка: стандарт vs ABI

Стандарт C++ **не фиксирует** ни наличие `vptr`, ни порядок баз, ни формат таблиц виртуальных функций. Всё, что ниже, — это описание распространённых реализаций:

- **Itanium C++ ABI** — GCC, Clang, Linux, macOS, большинство Unix;
- **MSVC ABI** — MSVC, Windows (в основном совместим и с MinGW/Clang-cl).

Обе ABI идеологически похожи, но детали (метаданные перед таблицей, виртуальные базы, деструкторы) различаются. Всё, что гарантирует стандарт: подобъекты одного типа имеют разные адреса, преобразование `Derived* → Base*` корректно корректирует адрес и т.п.

## 1. Отправная точка: одиночное наследование

```cpp
struct A {
    virtual void f();
    void* pa;
};

struct D : A {
    void* pd;
};
```

Типичная раскладка x86-64 (Itanium ABI):

| Смещение | Содержимое |
|---:|---|
| 0 | `vptr` → vtable класса `D` |
| 8 | `pa` |
| 16 | `pd` |
| 24 | конец, `sizeof(D) == 24` |

`vptr` стоит в начале, потому что адрес объекта совпадает с адресом его первичного подобъекта, а `this` внутри `D::f()` указывает на начало `D` — так обращение к `vptr` идёт по смещению 0 без знания динамического типа.

Таблица (`vtable`) для `D`:

```
адрес точки (address point) = vptr
  [-2] : 0                 // offset-to-top
  [-1] : &typeinfo(D)      // RTTI
  [ 0] : &D::f             // слот A::f, перекрытый в D
```

Виртуальный вызов `p->f()` компилируется примерно так:

```asm
mov rax, [rdi]        ; vptr
call qword ptr [rax]  ; слот 0
```

## 2. Множественное наследование **без** виртуальных функций

```cpp
struct A { int a; };
struct B { int b; };
struct C : A, B { int c; };
```

Невиртуальные базы укладываются **в порядке объявления** (рекурсивно, depth-first), затем собственные поля:

| Смещение | Содержимое |
|---:|---|
| 0 | `a` (подобъект `A`) |
| 4 | `b` (подобъект `B`) |
| 8 | `c` (поле `C`) |
| 12 | конец |

```cpp
C c;
B* pb = &c;                  // (char*)&c + 4
assert((void*)pb != (void*)&c);
```

Уже здесь видно ключевое свойство MI: **адрес подобъекта базы — это адрес объекта плюс смещение**. Приведение `C* → B*` — это `+4`, обратное — `-4`.

## 3. Множественное наследование **с** виртуальными функциями

### 3.1 Главное правило

> Число `vptr` в объекте равно числу **полиморфных подобъектов** (подобъектов баз, имеющих виртуальные функции), а не единице.

Каждый такой подобъект должен уметь обслуживать виртуальный вызов, когда на него смотрят через указатель соответствующего базового типа. Значит, у каждого — своя таблица (точнее, свой «вход» в группу таблиц класса).

Одна из баз выбирается **первичной** (primary): это, как правило, первая полиморфная невиртуальная база в порядке объявления. Она размещается по смещению 0 и **делит свой `vptr` с производным классом**; новые виртуальные функции производного класса дописываются в её таблицу.

### 3.2 Пример

```cpp
struct A {
    virtual void fa();
    void* pa;
};

struct B {
    virtual void fb();
    void* pb;
};

struct C : A, B {          // A — первичная база
    void* pc;
    void fa() override;    // перекрывает A::fa
    void fb() override;    // перекрывает B::fb
    virtual void fc();     // новая виртуальная функция
};
```

Раскладка x86-64:

| Смещение | Размер | Содержимое | Принадлежит |
|---:|---:|---|---|
| 0 | 8 | `vptr` → первичная vtable `C` | подобъект `A` |
| 8 | 8 | `pa` | подобъект `A` |
| 16 | 8 | `vptr` → вторичная vtable `C`-в-`B` | подобъект `B` |
| 24 | 8 | `pb` | подобъект `B` |
| 32 | 8 | `pc` | `C` |
| 40 | | конец | |

```
sizeof(C)  == 40
alignof(C) == 8
```

Схематично:

```
C:
+--------------------------------------------------+
| A-подобъект                                      |
|  +0  vptr #1  --> [ primary vtable C ]           |
|  +8  pa                                          |
+--------------------------------------------------+
| B-подобъект                                      |
| +16  vptr #2  --> [ secondary vtable C-in-B ]    |
| +24  pb                                          |
+--------------------------------------------------+
| +32  pc                                          |
+--------------------------------------------------+
```

Важно: `vptr #1` — это одновременно и `vptr` всего объекта `C`, потому что первичный подобъект лежит по смещению 0.

### 3.3 Первичная таблица (primary vtable)

```
address point = vptr #1
  [-2] : 0                    // offset-to-top
  [-1] : &typeinfo(C)         // RTTI полного объекта
  [ 0] : &C::fa               // слот A::fa
  [ 1] : &C::fc               // новый слот, добавленный C
```

Слотов `B::fb` здесь **нет**: они не belong к цепочке первичной базы. Вызовы `fb` через `C*` идут через второй `vptr` (см. ниже), а смещение 16 известно статически.

### 3.4 Вторичная таблица и thunk'и

```
address point = vptr #2
  [-2] : -16                  // offset-to-top: прибавить к this, чтобы получить полный объект
  [-1] : &typeinfo(C)         // тот же typeinfo(C), а не typeinfo(B)!
  [ 0] : thunk для C::fb      // this -= 16; jmp C::fb
```

Трамплин (adjustor thunk) — маленький кусок кода, который пересчитывает `this` и передаёт управление настоящей реализации:

```asm
; rdi = this (указывает на B-подобъект внутри C)
sub rdi, 16        ; теперь это C*
jmp C::fb
```

Если бы `C` **не** перекрывал `fb`, слот указывал бы прямо на `B::fb`: корректировка не нужна, ведь `this` уже указывает на `B`-подобъект.

Обратите внимание на `offset-to-top = -16`: это смещение, которое надо **прибавить** к адресу подобъекта, чтобы получить адрес полного объекта. Именно на нём держится `dynamic_cast<void*>` и корректная навигация по иерархии.

### 3.5 Как компилируется вызов

```cpp
void g1(B* pb) { pb->fb(); }
```

```asm
mov rax, [rdi]        ; vptr из B-подобъекта (смещение 0 внутри B)
jmp qword ptr [rax]   ; слот 0 -> thunk -> sub rdi,16; jmp C::fb
```

```cpp
void g2(C* pc) { pc->fb(); }
```

```asm
mov rax, [rdi+16]     ; vptr B-подобъекта: смещение B в C известно статически
jmp qword ptr [rax]
```

То есть при MI появляется не только лишняя косвенность, но и (для вторичных баз) лишний переход через thunk.

## 4. Следствия: указатели, приведения, RTTI

```cpp
C c;
A* pa = &c;    // смещение 0
B* pb = &c;    // смещение 16

assert((void*)pa == (void*)&c);
assert((void*)pb != (void*)&c);                       // +16
assert((void*)dynamic_cast<void*>(pb) == (void*)&c);  // полный объект

C* p1 = static_cast<C*>(pb);       // корректно: -16
C* p2 = reinterpret_cast<C*>(pb);  // ОШИБКА: адрес не скорректирован

typeid(*pb) == typeid(C);          // true: typeinfo берётся из vtable
```

Ключевые моменты:

1. **`static_cast` корректирует адрес**, `reinterpret_cast` — нет. Downcast через `reinterpret_cast` — классический источник UB.
2. **Сравнение указателей на разные базы**: `pa == pb` даже не скомпилируется (нет общего типа), а `(void*)pa == (void*)pb` даст `false`, хотя объект один. Это известная ловушка; надёжный способ получить адрес полного объекта — `dynamic_cast<void*>`.
3. **`dynamic_cast` между «братьями»** (`B* → A*`) напрямую невозможен: сначала нужно привести к `C*`, потом к `A*` (или использовать `dynamic_cast`, который умеет ходить по RTTI-графу).
4. **`typeinfo` во вторичной таблице указывает на полный тип** (`C`), а не на `B` — поэтому `typeid` и `dynamic_cast` работают корректно через любой базовый указатель.
5. **Указатели на функции-члены** в MI хранят ещё и поправку `this`: в Itanium это пара `{ptr, adj}` (16 байт на x64), где для виртуальной функции вместо адреса лежит смещение в vtable (с младшим битом-признаком).

## 5. Виртуальные деструкторы

Виртуальный деструктор тоже занимает слоты в таблице, причём в MI они тоже могут требовать thunk'ов.

- **Itanium ABI**: два слота — *complete object destructor* (`D1`) и *deleting destructor* (`D0`). `D0` вызывает `D1` и затем `operator delete`.
- **MSVC ABI**: один слот — *scalar deleting destructor* (при необходимости — vector deleting destructor).

Если `B` имеет виртуальный деструктор, а `C` его перекрывает, то вторичная таблица `C`-в-`B` будет содержать thunk, который корректирует `this` на `-16` перед вызовом `~C()`. Поэтому `delete pb;` корректно уничтожает весь объект `C` и освобождает память по правильному адресу.

## 6. Ромб: множественное наследование с виртуальными базами

Отдельный, более сложный случай — виртуальное наследование.

```cpp
struct V {
    virtual void f();
    void* pv;
};

struct L : virtual V { void* pl; };
struct R : virtual V { void* pr; };
struct D : L, R { void* pd; void f() override; };
```

Типичная раскладка x86-64 (Itanium):

| Смещение | Содержимое |
|---:|---|
| 0 | `vptr` (`L`-в-`D`) |
| 8 | `pl` |
| 16 | `vptr` (`R`-в-`D`) |
| 24 | `pr` |
| 32 | `pd` |
| 40 | `vptr` (`V`-в-`D`) |
| 48 | `pv` |
| 56 | конец, `sizeof(D) == 56` |

Что здесь важно:

1. **`V` существует в одном экземпляре** и размещается в конце объекта.
2. Смещение `V` **не известно на этапе компиляции** для кода, который видит только `L` или `R` (оно зависит от полного объекта). Поэтому оно хранится в таблице:
   - **Itanium**: «vbase offsets» — отрицательные слоты vtable (перед `offset-to-top`), плюс «vcall offsets» для вызовов виртуальных функций, унаследованных из виртуальной базы;
   - **MSVC**: отдельный указатель `vbptr` и таблица смещений виртуальных баз (`vbtable`).
3. Поэтому даже класс **без собственных виртуальных функций**, но с виртуальной базой, всё равно получает `vptr` (`vbptr`) — ему нужно где-то хранить смещения.
4. Перекрытие `f` в `D` порождает thunk'и в таблицах `L` и `R`: вызов `pl->f()` должен в итоге прийти в `D::f` с `this`, указывающим на `D`.
5. **MSVC + `vtordisp`**: если класс перекрывает виртуальную функцию, унаследованную из виртуальной базы, MSVC добавляет скрытое поле `vtordisp` (4 байта) после `vbptr`. Оно нужно adjustor-thunk'ам во время конструирования/разрушения, когда реальный динамический тип ещё не «доехал» до конечного. Управляется `#pragma vtordisp(0|1|2)`.
6. **Construction vtable / VTT** (Itanium): пока выполняется конструктор базового класса, `vptr` указывает на специальную «строительную» таблицу. Поэтому виртуальные вызовы в конструкторе не уходят в ещё не сконструированный производный класс, а `typeid` в конструкторе даёт тип текущего конструируемого класса.

Упрощённая схема «ромба»:

```
D:
+--------------------------------------+
| L-подобъект:  vptr(L-in-D), pl       |  0..15
+--------------------------------------+
| R-подобъект:  vptr(R-in-D), pr       | 16..31
+--------------------------------------+
| pd                                   | 32
+--------------------------------------+
| V-подобъект:  vptr(V-in-D), pv       | 40..55   <-- один на весь объект
+--------------------------------------+
```

## 7. Порядок размещения, выравнивание, пустые базы

Порядок (типичный для обеих ABI):

1. невиртуальные базы — в порядке объявления, рекурсивно;
2. собственные нестатические поля класса;
3. виртуальные базы — в конце объекта.

Дополнительно:

- Каждый подобъект выравнивается по своему `alignof`, между ними возможны **дыры (padding)**.
- `alignof` всего класса = максимум из `alignof` всех подобъектов; `sizeof` кратен `alignof`.
- Хвостовой padding (tail padding) базового класса **может переиспользоваться** полями производного, если база не POD (в Itanium это различие `dsize`/`size`). Поэтому не стоит вручную считать размеры «на бумажке» — только через `sizeof`.
- **EBO (empty base optimization)**: пустая база не занимает места:
  ```cpp
  struct E {};
  struct D : E, A {};   // sizeof(D) == sizeof(A)
  ```
- Два пустых подобъекта **одного и того же типа** не могут иметь один адрес:
  ```cpp
  struct E {};
  struct X : E {};
  struct Y : E {};
  struct Z : X, Y {};   // два E, разные адреса, sizeof(Z) >= 2
  ```
  В C++20 появился `[[no_unique_address]]` для полей, но к базовым классам это не относится.
- `#pragma pack` и полиморфные классы — плохая идея: можно сломать выравнивание `vptr` и получить непредсказуемое поведение/предупреждения.

## 8. Itanium ABI vs MSVC ABI

| Аспект | Itanium (GCC/Clang) | MSVC |
|---|---|---|
| Указатель на таблицу | `vptr` в каждом полиморфном подобъекте | `vfptr` в каждом полиморфном подобъекте |
| Метаданные перед таблицей | `[-2]` offset-to-top, `[-1]` typeinfo | `[-1]` указатель на Complete Object Locator (в нём — смещение `vfptr` и typeinfo) |
| Смещение до полного объекта | в таблице (`-16` для второй базы) | в COL (положительное, `+16`) |
| Thunk'и | adjustor thunks + covariant-return thunks | adjustor thunks |
| Виртуальные базы | vbase/vcall offsets в таблице | отдельный `vbptr` + `vbtable` |
| `vtordisp` | нет | есть |
| Деструктор | 2 слота (`D1`, `D0`) | 1 слот (scalar deleting destructor) |
| Новые виртуальные функции | дописываются в первичную таблицу | дописываются в vftable первой базы |
| RTTI | `typeinfo` в таблице | COL → TypeDescriptor + ClassHierarchyDescriptor |

Идейно обе схемы совпадают: **одна таблица на каждый полиморфный подобъект, корректировка `this` через thunk, RTTI-указатель в таблице**. Различаются формат метаданных и способ хранения смещений виртуальных баз.

## 9. Цена и практические выводы

1. **Размер**: каждый полиморфный подобъект — это +8 байт (`vptr`) на x64. Объект с тремя полиморфными базами уже несёт 24 байта служебных указателей.
2. **Скорость**: виртуальный вызов — две загрузки из памяти + косвенный вызов; для вторичных баз — ещё и переход через thunk. Косвенные переходы хуже предсказываются, особенно при «прыжках» между разными типами.
3. **Идентичность указателей**: `A*` и `B*` на один объект не равны; нельзя сравнивать «в лоб», нельзя хранить в `void*` и ждать, что адреса совпадут.
4. **`memcpy`/`memset`/сериализация** полиморфных объектов — почти всегда ошибка: `vptr` содержит адреса, значимые только в текущем процессе.
5. **ABI-несовместимость**: раскладка зависит от компилятора/версии/флагов; передавать C++-объекты через границу DLL/so, собранных разными компиляторами, нельзя.
6. **Деструктор должен быть виртуальным**, если удаление идёт через базовый указатель, — иначе не будет ни thunk'а, ни корректного `operator delete`.

## 10. Как посмотреть реальную раскладку

- **GCC**: `-fdump-lang-class` (GCC 8+; раньше `-fdump-class-hierarchy`) — печатает vtable, смещения баз, primary-for, thunk'и.
- **Clang**: `-Xclang -fdump-record-layouts`, `-Xclang -fdump-vtable-layouts`.
- **MSVC**: `/d1reportSingleClassLayoutC`, `/d1reportAllClassLayout`.
- **В рантайме**: `sizeof`, `alignof`, `std::is_polymorphic_v<T>`, печать адресов при приведении к разным базам, `dynamic_cast<void*>`.

## 11. Частые заблуждения

1. ❌ «В объекте один `vptr`» — ✔ их столько, сколько полиморфных подобъектов.
2. ❌ «`vtable` одна на класс» — ✔ у класса **группа** таблиц: первичная + по одной вторичной на каждую полиморфную не-первичную базу.
3. ❌ «Указатели на один объект всегда равны» — ✔ только после приведения к общему типу/полному объекту.
4. ❌ «`static_cast` и `reinterpret_cast` при downcast — одно и то же» — ✔ только `static_cast`/`dynamic_cast` корректируют адрес.
5. ❌ «Класс без виртуальных функций не имеет `vptr`» — ✔ имеет, если у него есть виртуальные базы.
6. ❌ «Порядок баз можно менять» — ✔ порядок невиртуальных баз фиксирован порядком объявления.
7. ❌ «Виртуальные вызовы в конструкторе работают полиморфно» — ✔ вызывается версия текущего конструируемого класса.

## 12. Итог

Объект класса с множественным наследованием и виртуальными функциями — это, по сути, **массив подобъектов**, каждый из которых живёт по своим правилам:

- невиртуальные базы идут в порядке объявления, затем поля, затем виртуальные базы;
- каждый полиморфный подобъект несёт свой `vptr`;
- первичная база делит `vptr` с производным классом, её таблица расширяется новыми виртуальными функциями;
- для каждой вторичной базы создаётся своя таблица, слоты которой либо указывают на реализацию напрямую, либо содержат thunk с поправкой `this`;
- поэтому приведение между базами — это арифметика над адресом, а «одинаковость» указателей разных типов — вопрос приведения, а не равенства битов.

Именно эта схема делает возможным полиморфизм при MI, но она же порождает накладные расходы, тонкие ошибки с `reinterpret_cast` и жёсткую зависимость от ABI.

## 13. Небольшое замечание про C

В чистом C классов нет, но ту же схему обычно эмулируют вручную: структура с первым полем — указателем на таблицу функций-указателей, «базовые» структуры вкладываются первыми полями, а приведение типов сопровождается ручной корректировкой адреса. Всё, что компилятор C++ делает автоматически (vptr, thunk'и, RTTI), в C приходится писать и сопровождать руками — и ошибаться в этом месте так же легко, как и в C++.
