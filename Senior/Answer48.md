# 48. Какие есть паттерны проектирования? Почему не советуют использовать Singleton?

## Коротко

**Паттерн проектирования** — это именованное, многократно проверенное решение типовой проблемы проектирования в некотором контексте. Паттерн — не кусок кода и не библиотека: это описание *структуры взаимодействия* объектов/модулей, которое можно реализовать по-разному в зависимости от языка.

Стандартная классификация — **23 паттерна «Банды четырёх» (GoF)**, разбитые на три группы: порождающие, структурные, поведенческие. Поверх них живут архитектурные, конкурентные, корпоративные паттерны и языковые идиомы (особенно важные для C++).

**Singleton** — единственный паттерн, который почти единодушно считают «запашком» (code smell). Причина одна: он смешивает две разные задачи — *обеспечить единственность экземпляра* и *дать к нему глобальный доступ*. Вторая часть превращает его в глобальную переменную с объектным интерфейсом, со всеми последствиями: скрытые зависимости, проблемы тестирования, гонки, порядок инициализации/разрушения, невозможность иметь два экземпляра в процессе.

---

## 1. Что такое паттерн и чего он не делает

Хорошее определение (Александреску): паттерн — это решение проблемы в контексте с учётом сил (forces), действующих в этом контексте.

Важные оговорки:

- Паттерн **не отменяет проектирование**. Применённый не к месту, он делает код хуже: появляются лишние интерфейсы, фабрики фабрик, «паттернит» (patternitis).
- Паттерн **зависит от языка**. Многие GoF-паттерны — обходные пути для отсутствующих возможностей языка. В C++ часть из них схлопывается в идиому, шаблон или вовсе в функцию; в C — в структуру с указателями на функции.
- Паттерн — это **словарь для обсуждения**, а не чек-лист «сделай все 23».

## 2. Классические 23 паттерна GoF

### 2.1. Порождающие (Creational) — 5

Отвечают на вопрос «как создавать объекты, не привязываясь к конкретным классам».

| Паттерн | Суть | Как выглядит в C++ |
|---|---|---|
| **Abstract Factory** | Интерфейс создания семейства связанных объектов | `struct IGuiFactory { virtual IButton* make_button() = 0; ... };` |
| **Builder** | Пошаговое конструирование сложного объекта | `Builder{}.set_host(...).set_port(...).build()`; часто fluent-интерфейс |
| **Factory Method** | Виртуальный метод, создающий объект; решение о типе — в подклассе | `virtual std::unique_ptr<Doc> create_doc() const = 0;` |
| **Prototype** | Клонирование по образцу | `virtual std::unique_ptr<Shape> clone() const = 0;` (в C++ ещё и copy-ctor) |
| **Singleton** | Единственный экземпляр + глобальная точка доступа | `static Foo& instance();` — см. ниже |

В современном C++ «фабрика» часто заменяется на `std::make_unique`, `std::variant`, `std::function`-генератор или ordinary overload set; Builder — на aggregate initialization / designated initializers (C++20).

### 2.2. Структурные (Structural) — 7

Отвечают на вопрос «как составить объекты в более крупные структуры».

| Паттерн | Суть | C++-акцент |
|---|---|---|
| **Adapter** | Превратить один интерфейс в другой | Класс-обёртка над legacy C-API |
| **Bridge** | Разделить абстракцию и реализацию, чтобы менять их независимо | pImpl — вырожденный Bridge |
| **Composite** | Дерево «лист/контейнер» с единым интерфейсом | `std::vector<std::unique_ptr<Node>>` |
| **Decorator** | Динамически добавлять поведение обёртками | Наследование от интерфейса + владение вложенным объектом; в C++ возможен и на шаблонах (stackable policies) |
| **Facade** | Простой интерфейс к подсистеме | Функция/класс, скрывающий 5 модулей |
| **Flyweight** | Разделять общее неизменяемое состояние | Пул/интернирование строк, `std::string_view`, shared immutable data |
| **Proxy** | Суррогат, контролирующий доступ | Ленивая загрузка, удалённый вызов, защита, COW, `operator->` |

### 2.3. Поведенческие (Behavioral) — 11

Отвечают на вопрос «как распределить обязанности и взаимодействие между объектами».

| Паттерн | Суть | C++-акцент |
|---|---|---|
| **Chain of Responsibility** | Цепочка обработчиков, пока кто-то не обработает | Список `std::function<bool(Request&)>` или linked handlers |
| **Command** | Инкапсулировать запрос как объект (undo, очередь, логирование) | `std::function<void()>`, лямбды; для undo — класс с `execute/undo` |
| **Interpreter** | Грамматика как дерево объектов | AST + `visit` |
| **Iterator** | Обход коллекции без раскрытия представления | Идиоматически — `begin()/end()`, ranges |
| **Mediator** | Централизовать взаимодействие объектов | Event bus / диспетчер |
| **Memento** | Снимок состояния для отката | `struct Snapshot { ... };` + `restore()` |
| **Observer** | Подписка на события | `std::function`-колбэки, сигналы/слоты, `std::weak_ptr` для отписки |
| **State** | Поведение зависит от состояния; переходы | `std::variant<StateA, StateB>` + `std::visit`, либо полиморфные состояния |
| **Strategy** | Взаимозаменяемые алгоритмы | `std::function`, шаблонный параметр (policy), указатель на функцию в C |
| **Template Method** | Скелет алгоритма в базовом классе, шаги — в наследниках | NVI (non-virtual interface) — «правильная» C++-версия |
| **Visitor** | Операции над структурой без изменения классов | Двойная диспетчеризация; в C++20 часто `std::variant` + `std::visit` |

## 3. Паттерны за пределами GoF

GoF — только один срез. Реально в проектировании полезны ещё несколько семейств.

### 3.1. Архитектурные

- **Слои (Layered)**, **Hexagonal / Ports & Adapters**, **Clean Architecture**, **Onion**.
- **MVC / MVP / MVVM** — разделение модели, представления и логики представления.
- **Repository**, **Unit of Work**, **Active Record**, **Data Mapper** (Фаулер).
- **Dependency Injection** / **Inversion of Control**, **Composition Root**.
- **CQRS**, **Event Sourcing**, **Saga**, **Circuit Breaker**, **Bulkhead**, **Retry/Backoff** (устойчивость).
- **Microservices**, **API Gateway**, **Service Mesh** — уже системный уровень.

### 3.2. Конкурентные (POSA / «Pattern-Oriented Software Architecture»)

- **Active Object** — асинхронный вызов метода через очередь сообщений.
- **Monitor Object**, **Guarded Suspension**, **Thread Pool**, **Producer–Consumer**.
- **Reactor** (select/epoll, asio `io_context`), **Proactor** (IOCP, overlapped I/O).
- **Half-Sync/Half-Async**, **Leader/Followers**.
- **Future/Promise**, **Actor model** — в C++: `std::future`, `std::promise`, `std::async`.

### 3.3. C++-идиомы (де-факто паттерны)

- **RAII** — краеугольный камень; **Rule of Zero / Three / Five**.
- **Copy-and-swap** — строгая гарантия исключений в `operator=`.
- **pImpl (compilation firewall)** — скрыть реализацию, стабилизировать ABI.
- **NVI** — публичный невиртуальный метод вызывает приватный виртуальный.
- **CRTP** — статический полиморфизм без vtable.
- **Type erasure** — `std::function`, `std::any`, ручной `any_with_vtable`.
- **Policy-based design** (Александреску) — параметризация поведения шаблонными аргументами.
- **Tag dispatch / SFINAE / `if constexpr` / concepts** — выбор реализации на этапе компиляции.
- **Scope guard**, **named constructor**, **non-copyable mixin**, **addressof**, **hidden friend**, **ADL-точки кастомизации** (`swap`, `begin/end`).
- **`enable_shared_from_this`**, **intrusive reference counting**, **small buffer / small string optimization**, **copy-on-write**.

### 3.4. C-идиомы (объектно-ориентированный C)

В C нет классов, но ООП-структуры эмулируются:

- **Opaque pointer / handle**: `struct db; struct db* db_open(...);` — инкапсуляция.
- **Vtable вручную**: `struct file_operations { int (*open)(...); ssize_t (*read)(...); };` — так устроено ядро Linux.
- **Callback + context** — эмуляция замыкания: `void (*cb)(void* ctx, ...)`.
- **`container_of`** — «наследование» через встраивание структуры.
- **X-macros** — генерация таблиц/перечислений/сериализации.
- **Arena / pool allocator**, **intrusive list**, **tagged union**, **state machine на указателях на функции**.

## 4. Ключевая мысль: паттерн часто компенсирует язык

Питер Норвиг в докладе «Design Patterns in Dynamic Languages» показал, что 16 из 23 GoF-паттернов в Lisp/Dylan «невидимы или проще». В C++ это видно ещё сильнее:

| GoF-паттерн | Чем заменяется в современном C++ |
|---|---|
| Strategy | `std::function`, лямбда, шаблонный policy |
| Command | лямбда, `std::function<void()>` |
| Observer | колбэки, сигналы/слоты |
| Visitor | `std::variant` + `std::visit` |
| Iterator | ranges, `begin/end` |
| Factory Method | конструктор, `make_unique`, `std::pmr` |
| Singleton | глобальная переменная / `inline`-переменная / ссылка, переданная в конструктор |

Вывод: **сначала спрашивайте «какая сила (force) здесь действует», а не «какой паттерн вкрутить»**.

## 5. Singleton: что это и как его пишут

**Намерение (GoF):** гарантировать, что у класса есть только один экземпляр, и предоставить глобальную точку доступа к нему.

Классическая реализация в C++ (Meyers singleton):

```cpp
class Config {
public:
    static Config& instance() {
        static Config cfg;   // thread-safe init с C++11
        return cfg;
    }

    std::string get(std::string_view key) const;
    void set(std::string key, std::string value);

private:
    Config() = default;
    Config(const Config&) = delete;
    Config& operator=(const Config&) = delete;

    std::map<std::string, std::string> values_;
};

// использование
auto host = Config::instance().get("db.host");
```

Варианты:

- **Meyers singleton** — локальный `static` в функции. С C++11 инициализация потокобезопасна («magic statics», `[stmt.dcl]/4`). Деструктор вызывается при выходе из программы.
- **Heap + `atexit`** — `static Config* p = new Config;` — «утечка», о которой не сообщает valgrind, зато контролируемый порядок.
- **Double-checked locking (DCLP)** — корректен только на `std::atomic` с acquire/release; `volatile` для синхронизации не годится (до C++11 и в Java до 5-й версии DCLP был сломан).
- **`std::call_once` + `std::once_flag`** — переносимый ленивый вариант.
- **В C** — `pthread_once` (или `call_once` из C11 threads), потому что локальный `static` в C потокобезопасной инициализации не гарантирует.

```cpp
// корректный DCLP
std::atomic<Foo*> g_foo{nullptr};
std::mutex g_mtx;

Foo& foo() {
    Foo* p = g_foo.load(std::memory_order_acquire);
    if (!p) {
        std::lock_guard lk{g_mtx};
        p = g_foo.load(std::memory_order_relaxed);
        if (!p) {
            p = new Foo;
            g_foo.store(p, std::memory_order_release);
        }
    }
    return *p;
}
```

## 6. Почему Singleton не советуют

C++ Core Guidelines прямо говорят: **I.3: Avoid singletons** («Singleton — это по сути усложнённая глобальная переменная»), и **I.2: Avoid global variables**. Ниже — развёрнутые причины.

### 6.1. Скрытая зависимость (hidden coupling)

Сигнатура `void save(User u)` не говорит, что функция лезет в `Config::instance()`, `Logger::instance()` и `Db::instance()`. Зависимость не видна ни компилятору интерфейса, ни ревьюеру, ни тому, кто собирается переиспользовать функцию. Это нарушает **DIP** (зависимость от конкретного класса, а не от абстракции) и делает интерфейс «лгущим».

```cpp
void save(const User& u) {
    auto& db = Db::instance();          // зависимость спрятана
    db.write(u);
    Logger::instance().log("saved");    // и ещё одна
}
```

### 6.2. Глобальное изменяемое состояние

Singleton с мутаторами — это глобальная переменная. Появляются:

- **action at a distance** — кто-то в другом модуле поменял конфиг, и поведение изменилось;
- **порядковая зависимость** — результат зависит от истории вызовов;
- **нереентерабельность** и невозможность использовать код в двух независимых контекстах;
- **гонки данных**, если объект мутируется из нескольких потоков, а потокобезопасен только *доступ к указателю*, а не сам объект.

### 6.3. Проблемы тестируемости

Это самая частая практическая боль:

- нельзя подменить реализацию на mock/stub — конструктор приватный, `instance()` жёстко зашит;
- состояние протекает между тестами: тест A поменял конфиг, тест B упал;
- тесты нельзя запускать параллельно (общий глобальный объект);
- чтобы «сбросить» singleton, приходится добавлять `resetForTests()` / `setInstance()` — то есть **самим превращать его в ещё более глобальное изменяемое состояние**;
- типичный костыль — `#define private public` или `friend` для тестов, что ломает инкапсуляцию окончательно.

### 6.4. Нарушение SRP и размывание ответственности

Класс-одиночка отвечает сразу за: (а) свою бизнес-логику, (б) уникальность экземпляра, (в) время жизни, (г) глобальную точку доступа. Четыре причины менять класс вместо одной.

### 6.5. Проблема порядка инициализации (static initialization order fiasco)

Классическая ловушка C++: динамическая инициализация статических объектов в разных TU идёт в **неопределённом порядке**.

```cpp
// logger.cpp
Logger& logger() { static Logger l; return l; }

// service.cpp
struct Service {
    Service() { logger().log("init"); }   // Logger может быть ещё не создан?
};
Service g_service;   // порядок относительно logger.cpp не определён
```

С Meyers-синглтоном это частично лечится ленивой инициализацией, но не всегда: если `Service` сам является статическим объектом, его конструктор может обратиться к ещё не инициализированному синглтону.

### 6.6. Проблема порядка разрушения (static destruction order)

Обратная сторона: деструкторы статических объектов выполняются в обратном порядке, но межмодульный порядок не гарантирован. Синглтон A в деструкторе обращается к синглтону B, который уже разрушен → **UB**. Классический «crash at exit», который трудно воспроизвести.

Плюс: деструктор Meyers-синглтона срабатывает после `main`, когда фоновые потоки ещё могут работать и обращаться к нему. Отсюда — гонка на разрушении и «использование после разрушения».

### 6.7. Потокобезопасность: инициализация ≠ безопасность

- Потокобезопасная инициализация (C++11) не делает потокобезопасными **методы**.
- DCLP без `std::atomic` (и с `volatile`) — сломан из-за переупорядочивания записи указателя и инициализации объекта.
- Проверка guard-переменной на каждом `instance()` — небольшая, но не нулевая цена в горячем пути.
- Разрушение общего объекта при живых потоках — гонка.
- В C локальный `static` не защищён; нужен `pthread_once`.

### 6.8. Ложное ощущение «одного экземпляра»

«Один на процесс» ≠ «один на систему»:

- **DLL/SO**: каждая динамическая библиотека может иметь свою копию статики (особенно на Windows при статическом CRT, но и с раздельным CRT — свои статические данные у каждого модуля). Два плагина — два «синглтона».
- **`dlclose`/`FreeLibrary`**: статика выгружается, указатели на неё становятся висячими.
- **`fork()`** в Unix: ребёнок получает копию, и «единственность» превращается в «по копии на процесс».
- **Несколько миров/сессий в одном процессе** (игровой сервер, хостинг нескольких тенантов, эмулятор) — Singleton физически не даёт создать два экземпляра.

### 6.9. ODR и заголовки

`static`-член, определённый в заголовке, — нарушение ODR при включении в несколько TU. До C++17 приходилось использовать шаблонный трюк; в C++17 появились `inline`-переменные, но проблема «глобальности» остаётся.

### 6.10. Сложность расширения и подмены

Наследование и полиморфная замена затруднены: конструктор приватный, `instance()` статический (не виртуальный). Чтобы сделать «синглтон с интерфейсом», приходится городить `Singleton<T>`-шаблоны, `setInstance`, `friend`-и — и получается **Service Locator**, который критикуют ровно за то же самое: скрытые зависимости.

### 6.11. Утечки и «вечная жизнь»

Heap-синглтон не освобождается — отчёты анализаторов памяти шумят, а `atexit`-порядок всё равно хрупок. Ленивый синглтон, который так и не создали, — «мёртвый» код инициализации.

### 6.12. Синглтон «заразителен»

Один `instance()` в глубине кода — и все вызывающие его функции тоже становятся нетестируемыми, пока не протащишь зависимость через всю цепочку. Рефакторинг к DI потом стоит дорого, поэтому проще «ещё один синглтон».

### Сводная таблица претензий

| Претензия | Суть | Типичное проявление в C++ |
|---|---|---|
| Скрытые зависимости | сигнатура не отражает связи | `Db::instance()` внутри функции |
| Глобальное состояние | мутации видны всем | «поплывшие» тесты, order-dependence |
| Тестируемость | нельзя подменить | `#define private public`, `resetForTests` |
| SRP | 4 ответственности в одном классе | класс растёт, меняется по любому поводу |
| SIOF | порядок инициализации не определён | падение до `main` |
| Порядок разрушения | деструкторы в неожиданном порядке | crash at exit, UAF |
| Потоки | init ≠ thread safety | data race в методах, гонка на destruction |
| «Один на процесс» | DLL, fork, плагины | несколько копий, висячие указатели |
| ODR | статика в заголовке | multiple definition / несколько копий |
| Расширяемость | нельзя полиморфно подменить | `setInstance` → Service Locator |

## 7. Когда Singleton всё-таки оправдан

Есть узкий класс случаев, где он приемлем (и то — с оговорками):

1. **Реально единственный физический ресурс**: регистры устройства, аппаратный таймер, контроллер прерываний, уникальный OS-хэндл, CUDA-контекст.
2. **Встроенные системы без кучи и без инфраструктуры DI**, где протаскивание зависимости через 50 функций дороже, чем один глобальный объект.
3. **Неизменяемая после инициализации конфигурация** (snapshot) — тогда это не «глобальное изменяемое состояние», а константа.
4. **Фасад над C-библиотекой**, которая сама глобальна (например, обёртка над `getenv`-стилем API).
5. **Логирование/крэш-хендлер** — с обязательной оговоркой: интерфейс должен быть абстракцией, а доступ — по возможности через явно переданную ссылку.

Практическое правило: **оставляйте уникальность, убирайте глобальный доступ**. Один экземпляр, созданный в `main` (composition root) и переданный по ссылке, решает 90 % задач, ради которых тянут Singleton.

## 8. Альтернативы Singleton

| Подход | Как выглядит | Комментарий |
|---|---|---|
| **Dependency Injection** | `Database(Db& db, Logger& log)` | Лучший вариант по умолчанию |
| **Передача по ссылке/указателю** | `void f(Config& cfg)` | Явная зависимость, тестируемо |
| **Composition Root** | всё создаётся в `main`, дальше — по ссылкам | Явное владение и время жизни |
| **Monostate** | все члены `static`, обычный интерфейс | Те же проблемы глобального состояния, но лучше тестируется подменой полей |
| **Service Locator** | `locator.get<Logger>()` | Антипаттерн: снова скрытые зависимости |
| **Пространство имён + free functions** | `namespace config { std::string get(...); }` | Честнее: это просто глобальная функция, без иллюзии ООП |
| **`inline`-переменная (C++17)** | `inline Config g_config;` | Честная глобальная переменная, без «магии» |
| **`thread_local`** | по экземпляру на поток | Если нужна изоляция по потокам |
| **Явный контекст** | `struct AppContext { Config cfg; Logger log; Db db; };` | Удобно для игр/серверов, где нужны несколько «миров» |
| **`std::pmr::memory_resource*`** | явный параметр-аллокатор | Эталон «передай зависимость, а не прячь её» |

### Пример: было / стало

```cpp
// ПЛОХО: скрытая зависимость + глобальное изменяемое состояние
class Db {
public:
    static Db& instance();
    void write(const User& u);
};

void save(const User& u) {
    Db::instance().write(u);   // откуда взялась БД — не видно
}

// ХОРОШО: зависимость в сигнатуре, владение в composition root
class Db {
public:
    virtual ~Db() = default;
    virtual void write(const User& u) = 0;
};

void save(Db& db, const User& u) {   // зависимость явная
    db.write(u);
}

int main() {
    auto db = make_postgres_db(load_config("app.toml"));  // один экземпляр
    Logger log{...};
    save(*db, user);
}
```

Теперь `save` тестируется с `FakeDb`, не зависит от порядка тестов и не требует `resetForTests`.

## 9. Чек-лист: нужен ли вам Singleton

- [ ] Мне нужна именно **уникальность**, или достаточно «один объект, созданный в `main`»?
- [ ] Нужен ли **глобальный доступ**, или зависимость можно передать явно?
- [ ] Состояние **изменяемое**? Если да — кто и когда его меняет, есть ли синхронизация?
- [ ] Что будет при **двух экземплярах** в процессе (тесты, плагины, несколько миров)?
- [ ] Кто **владеет** объектом и когда он **разрушается**?
- [ ] Можно ли **подменить** реализацию в тесте без хаков?
- [ ] Есть ли **DLL/SO**, `fork`, `dlclose` в сценарии?
- [ ] Это **физический ресурс** или просто «удобно достать отсюда»?

Если хотя бы на один из вопросов 2, 3, 4, 6 ответ «неудобно» — скорее всего, Singleton не нужен.

## 10. Итог

1. Паттерны — это **словарь решений**: 23 GoF (порождающие/структурные/поведенческие) плюс архитектурные, конкурентные, корпоративные, языковые идиомы C++ и C.
2. Многие GoF-паттерны в C++ **схлопываются** в возможности языка: лямбды, шаблоны, `std::variant`/`std::visit`, ranges, RAII.
3. **Singleton критикуют не за уникальность, а за глобальный доступ.** Он превращает зависимость в скрытую, состояние — в глобальное, тестирование — в боль, а время жизни — в лотерею порядка инициализации/разрушения.
4. В C++ к этому добавляются: SIOF, порядок разрушения, DCLP/`volatile`, ODR, поведение в DLL/`dlclose`/`fork`, гонки при разрушении.
5. **Правило:** создавайте единственный экземпляр в `main` (composition root) и передавайте его явно — по ссылке или через интерфейс. Оставляйте Singleton только для настоящих физических/системных ресурсов и для неизменяемых конфигураций.
