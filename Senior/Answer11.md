# 11. Как тестировать закрытые методы?

`private` в C++ — это ограничение доступа на этапе компиляции, а не защита во время выполнения. Поэтому «протестировать закрытый метод» можно разными способами, но выбирать стоит не самый быстрый, а самый устойчивый к сопровождению.

Ниже — подходы от предпочтительных к хакам.

## 1. Тестировать через публичный API — основной путь

Если закрытый метод является деталью реализации и вызывается из публичного метода, отдельный тест на него обычно не нужен: его поведение уже проверяется через результат публичной операции.

```cpp
class Calculator {
public:
    int compute(int x) const {
        return normalize(x) * 2;
    }

private:
    int normalize(int x) const {
        return x < 0 ? -x : x;
    }
};
```

```cpp
TEST(CalculatorTest, ComputeHandlesNegative) {
    Calculator c;
    EXPECT_EQ(c.compute(-5), 10);
}
```

Такой тест не знает о существовании `normalize`, поэтому реализацию можно менять, не переписывая тесты. Это главное преимущество.

Ограничение: не все ветки закрытого метода достижимы через публичный API. Если метод вызывается только при особом состоянии объекта или публичный метод слишком крупный, стоит рассмотреть следующие варианты.

## 2. Вынести сложную логику в отдельную тестируемую сущность

Закрытый метод, который хочется тестировать отдельно, часто является самостоятельным алгоритмом. Самый чистый путь — вынести его в свободную функцию во внутреннем namespace или в отдельный класс.

```cpp
// order_detail.h
#pragma once

namespace shop::detail {
int applyDiscount(int price, int percent);
}
```

```cpp
// order_detail.cpp
namespace shop::detail {
int applyDiscount(int price, int percent) {
    return price - price * percent / 100;
}
}
```

```cpp
// order.cpp
int Order::total() const {
    return shop::detail::applyDiscount(subtotal_, discountPercent_);
}
```

```cpp
TEST(OrderDetailTest, AppliesDiscount) {
    EXPECT_EQ(shop::detail::applyDiscount(1000, 10), 900);
}
```

Это уже не закрытый метод, а внутренняя сущность со своим контрактом. Заголовок `order_detail.h` можно не устанавливать вместе с библиотекой и считать его внутренним.

Другие варианты:

- вынести логику в отдельный класс-сервис и внедрять его в основной класс через конструктор;
- использовать pImpl: объявить `Impl` в отдельном внутреннем заголовке и тестировать его напрямую;
- выделить чистую функцию, не зависящую от состояния объекта.

Плюс подхода: тесты не ломаются при изменении доступа и не требуют `friend`. Минус: нужен рефакторинг, иногда появляется больше сущностей.

## 3. Дружественный тестовый класс или структура

Если менять дизайн не хочется, можно точечно открыть доступ для теста. Это классический способ в C++.

```cpp
// widget.h
#pragma once

class Widget {
public:
    explicit Widget(int base) : base_(base) {}

    int compute(int x) const {
        return helper(x) + 1;
    }

private:
    int helper(int x) const {
        return base_ * x;
    }

    friend struct WidgetTestAccess;
};
```

```cpp
// widget_test.cpp
#include <gtest/gtest.h>
#include "widget.h"

struct WidgetTestAccess {
    static int helper(const Widget& w, int x) {
        return w.helper(x);
    }
};

TEST(WidgetTest, HelperMultiplies) {
    Widget w(10);
    EXPECT_EQ(WidgetTestAccess::helper(w, 3), 30);
}
```

`WidgetTestAccess` объявлен другом, поэтому его метод имеет доступ к `helper`. Обычные клиенты `Widget` доступа не получают.

Важные детали:

- `WidgetTestAccess` должен находиться в том же namespace, что и `Widget`. Если `Widget` лежит в `namespace ui`, то и аксессор должен быть в `namespace ui`, иначе friend-декларация будет ссылаться на другую сущность.
- Не кладите аксессор в анонимный namespace: friend-декларация в классе объявляет имя в ближайшем именованном namespace, и это будет уже другой класс.
- Дружба открывает все закрытые члены, а не только один метод. Поэтому аксессор стоит делать минимальным и использовать только в тестах.

### 3.1. `FRIEND_TEST` в GoogleTest

В GoogleTest есть готовый макрос для этого:

```cpp
// widget.h
#pragma once
#include <gtest/gtest_prod.h>

class Widget {
public:
    explicit Widget(int base) : base_(base) {}

    int compute(int x) const {
        return helper(x) + 1;
    }

private:
    int helper(int x) const {
        return base_ * x;
    }

    FRIEND_TEST(WidgetTest, HelperMultiplies);
};
```

```cpp
TEST(WidgetTest, HelperMultiplies) {
    Widget w(10);
    EXPECT_EQ(w.helper(3), 30);
}
```

`FRIEND_TEST(WidgetTest, HelperMultiplies)` разворачивается в friend-декларацию для сгенерированного класса `WidgetTest_HelperMultiplies_Test`, поэтому тело теста получает доступ напрямую.

Минусы:

- в production-заголовок добавляется зависимость от `gtest/gtest_prod.h`;
- при переименовании теста нужно менять и заголовок;
- макрос рассчитан на простые имена тестовых классов; если тесты находятся в namespace, иногда проще использовать отдельный аксессор.

Можно спрятать friend за `#ifdef`:

```cpp
#ifdef WIDGET_TESTING
    friend struct WidgetTestAccess;
#endif
```

Но здесь появляется нюанс ODR: определение класса в тестовой и production-сборке будет различаться. Формально это нарушение ODR, хотя friend-декларация обычно не влияет на layout. Если использовать такой подход, макрос должен быть согласован во всех translation unit, которые видят этот класс, а не только в одном тестовом файле. На практике проще сделать friend безусловным либо применять `FRIEND_TEST`.

### 3.2. Дружба не наследуется

Это частая ошибка. Если объявить:

```cpp
class WidgetTest; // необязательно, friend-декларация сама объявит класс

class Widget {
    // ...
private:
    int helper(int x) const;

    friend class WidgetTest;
};
```

и написать:

```cpp
class WidgetTest : public ::testing::Test {
protected:
    Widget w{10};
};

TEST_F(WidgetTest, HelperMultiplies) {
    EXPECT_EQ(w.helper(3), 30); // ошибка: доступа нет
}
```

то тест не скомпилируется. Тело `TEST_F` находится в производном классе `WidgetTest_HelperMultiplies_Test`, а дружба не наследуется. Работать будет только обращение через метод самой фикстуры:

```cpp
class WidgetTest : public ::testing::Test {
protected:
    static int helper(const Widget& w, int x) {
        return w.helper(x);
    }

    Widget w{10};
};

TEST_F(WidgetTest, HelperMultiplies) {
    EXPECT_EQ(helper(w, 3), 30);
}
```

Здесь `WidgetTest::helper` — член класса, который является другом `Widget`, поэтому доступ есть. Альтернатива — использовать `FRIEND_TEST`, который дружит непосредственно сгенерированный тестовый класс.

## 4. Если метод `protected`, а не `private`

Для `protected` можно обойтись наследником:

```cpp
class Widget {
protected:
    int helper(int x) const {
        return x * 2;
    }
};

class WidgetForTest : public Widget {
public:
    using Widget::helper; // открываем protected-метод
};

TEST(WidgetTest, Helper) {
    WidgetForTest w;
    EXPECT_EQ(w.helper(3), 6);
}
```

Для `private` такой код не скомпилируется: `using Widget::helper;` не сможет открыть закрытый член. Менять `private` на `protected` только ради тестов не стоит: это расширяет контракт класса для всех наследников.

Отдельный случай — `private virtual` метод. Его можно переопределить в тестовом наследнике, потому что для override доступ не требуется, и вызвать через публичную обёртку базового класса. Но это тестирует скорее взаимодействие через публичный интерфейс, а не сам закрытый метод.

## 5. `#define private public`

Самый известный хак:

```cpp
// widget_test.cpp
#include <gtest/gtest.h>

// По возможности сначала подключаем всё, что тянет стандартную библиотеку.
#include <string>
#include <vector>

#define private public
#include "widget.h"
#undef private

TEST(WidgetTest, Helper) {
    Widget w(10);
    EXPECT_EQ(w.helper(3), 30);
}
```

Препроцессор заменяет токен `private` на `public` до разбора C++, поэтому закрытые члены становятся доступными.

Почему это плохой способ:

- **Нарушение ODR.** Определение класса в этом translation unit отличается от определения в остальных. Формально программа становится ill-formed, диагностика не требуется (IFNDR), даже если ABI на практике совпадает.
- **Меняются все классы.** Макрос действует на весь заголовок и на все транзитивно включённые заголовки. Если `widget.h` подключает `<vector>` уже после `#define`, то private-члены `std::vector` тоже станут public в этом translation unit.
- **Зависимость от порядка include.** Если заголовок уже был включён раньше, повторный include с макросом ничего не даст из-за include guard или `#pragma once`.
- **Меняется не только доступ к членам.** `private` используется и для наследования: `class D : private B` превратится в `class D : public B`, что может изменить доступность преобразований и type traits.
- **Могут измениться type traits.** Например, `std::is_standard_layout` зависит от того, имеют ли все нестатические поля одинаковый доступ. Макрос может сделать класс standard-layout в одном translation unit и не сделать в другом.
- **Маскируются ошибки доступа.** Код, который не должен компилироваться, внезапно компилируется, и тесты начинают проверять не то, что разрешено контрактом.
- **Не помогает для `protected`.** Для него нужен отдельный `#define protected public`, что ещё хуже.
- **Хрупко.** Любое изменение структуры заголовков может сломать сборку теста.

Если всё же использовать этот способ, то только как временный локальный костыль:

- в отдельном тестовом translation unit;
- только для собственного заголовка, а не для чужих библиотек;
- после всех системных include, насколько это возможно;
- с немедленным `#undef private`;
- никогда в production-коде и, желательно, не в CI.

Даже если тесты проходят, это не делает код корректным по стандарту.

## 6. Экзотические варианты

### 6.1. Флаг компилятора

В Clang есть флаг `-fno-access-control`, который отключает проверки доступа во всём translation unit. Это нестандартно, непереносимо и подходит только для локальных экспериментов. В обычном проекте лучше не использовать.

### 6.2. Трюк с указателем на член

Существует известный трюк: explicit instantiation шаблона с `&Class::private_member` и friend-инъекция. Он эксплуатирует то, что на имена в explicit instantiation не действуют обычные правила доступа. Работает на популярных компиляторах, но выглядит как магия, сложен в сопровождении и не нужен в обычном коде.

### 6.3. `#include "widget.cpp"`

Иногда советуют включать `.cpp` прямо в тест. Для закрытых методов класса это не помогает: объявление класса всё равно содержит `private`, и доступ не появится. Такой приём может быть полезен только для функций в анонимном namespace, но создаёт риск duplicate symbols, если этот `.cpp` ещё и компилируется отдельно.

## 7. Сравнение подходов

| Способ | Вторжение в код | Формальная корректность | Когда применять |
|---|---|---|---|
| Через публичный API | нет | высокая | по умолчанию |
| Вынос в `detail` или отдельный класс | рефакторинг | высокая | сложная логика |
| `friend`-аксессор | + friend в заголовке | высокая | точечный white-box-тест |
| `FRIEND_TEST` | + friend + `gtest_prod.h` | высокая | проекты на GoogleTest |
| `protected` + наследник | меняет дизайн | высокая | если метод уже `protected` |
| `#define private public` | нет, но нарушает ODR | низкая | крайний случай, не в production |
| `-fno-access-control` | флаг сборки | низкая, непереносимо | локальный эксперимент |

## 8. Что выбрать на практике

1. **Сначала проверьте, нужен ли отдельный тест.** Закрытый метод — не часть контракта класса. Если он вызывается из публичного метода, тестируйте публичное поведение.
2. **Если логика сложная и чистая — вынесите её.** Свободная функция в `detail` или отдельный класс дадут более устойчивые тесты, чем `friend` или макрос.
3. **Если нужен прямой доступ — используйте friend-аксессор.** Это явно, локально и не меняет доступ для обычных клиентов.
4. **`FRIEND_TEST` удобен в GoogleTest**, но добавляет тестовую зависимость в production-заголовок.
5. **`#define private public` — не решение, а временный обход.** Он нарушает ODR и делает тесты хрупкими.
6. **Не делайте методы public только ради тестов.** Это разрушает инкапсуляцию и провоцирует использование деталей реализации.
7. **Не гонитесь за 100% coverage.** Покрытие закрытого метода само по себе не гарантирует, что протестировано поведение класса.

Главный критерий: хороший тест проверяет наблюдаемое поведение и переживает рефакторинг. Тест, который напрямую вызывает закрытый метод, часто фиксирует текущую реализацию, а не контракт класса. Поэтому к нему стоит прибегать только тогда, когда это действительно оправдано.
