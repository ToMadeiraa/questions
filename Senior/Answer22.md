# 22. Что такое статический анализатор кода? Какие знаете?

## Короткое определение

**Статический анализатор кода** — это инструмент, который исследует исходный код (или промежуточное представление, полученное из него) **без запуска программы** и находит потенциальные дефекты: ошибки, ведущие к неопределённому поведению, утечки ресурсов, нарушения стиля и соглашений, уязвимости, избыточный или мёртвый код.

«Статический» здесь противопоставляется «динамическому»: динамический анализ (санитайзеры, Valgrind, отладчик, покрытие) требует **выполнения** программы на конкретных входных данных, а статический — нет. Отсюда главное свойство: анализатор видит **все** ветки, включая те, что на тестах никогда не исполнятся, но ничего не знает о реальных входных данных.

Формально задача нетривиальна: по теореме Райса любое нетривиальное семантическое свойство программ неразрешимо, а значит каждый анализатор — это компромисс между **полнотой** (soundness: не пропустить ошибку) и **точностью** (precision: не ругаться на корректный код). Компилятор и анализатор всегда «режут» одно из двух.

## Где анализатор стоит в цепочке препроцессор → компиляция

Это ключевой момент в контексте вашего курса. Классическая цепочка:

```
исходник .cpp/.h
      │  препроцессор (cpp): #include, #define, #if, #pragma
      ▼
препроцессированная единица трансляции (после gcc -E / clang -E)
      │  лексический анализ → токены
      ▼
      │  синтаксический анализ → AST
      ▼
      │  семантический анализ: типы, перегрузки, шаблоны, ODR
      ▼
      │  генерация IR / CFG и оптимизации
      ▼
   объектный код
```

Статический анализатор обычно **не работает с «сырым» текстом** — он встраивается в эту цепочку и использует её результаты:

| Уровень | Что видит анализатор | Примеры проверок |
|---|---|---|
| Текст / токены | сырой текст, регулярные выражения | стиль, табы/пробелы, `cpplint`, форматтеры |
| Препроцессированный код | раскрытые макросы, подключённые заголовки | гигиена `#include` (IWYU), мёртвые `#ifdef` |
| AST | синтаксис + типы | `clang-tidy`, PC-lint, PVS-Studio, Cppcheck |
| CFG (граф потока управления) | пути исполнения | Clang Static Analyzer, Coverity, `-fanalyzer` |
| Межпроцедурный уровень / вся программа | вызовы между функциями | Coverity, Infer, Klocwork, Polyspace |
| Формальная модель | математическая семантика | Astrée, CBMC, Frama-C |

Из-за препроцессора возникают специфические сложности, которых нет в «чистых» языках:

1. **Один и тот же файл компилируется по-разному** в зависимости от `-D`, `-I`, `-std`, целевой платформы. Поэтому анализатору нужны те же флаги, что и компилятору, — на практике ему скармливают `compile_commands.json` (генерируется CMake: `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`).
2. **Диагностика должна указывать на исходный файл**, а не на результат `-E`. Для этого в препроцессированном коде остаются директивы `#line` (маркеры `file:line`), и анализатор по ним восстанавливает исходные позиции.
3. **Макросы «размывают» типы и синтаксис**. `#define SQUARE(x) x*x` формально корректен для препроцессора, но `SQUARE(a+b)` даёт неверную формулу; анализатор видит уже раскрытое выражение и может потерять связь с исходным макросом. Часть инструментов (Cppcheck, PVS-Studio) держит **собственный препроцессор**, чтобы не зависеть от окружения сборки.
4. **Условная компиляция** (`#ifdef _WIN32`, `#if __cplusplus >= 202002L`) означает, что анализировать надо каждую реальную конфигурацию сборки — иначе половина кода просто не попадёт в анализ.
5. **`#pragma` и атрибуты** используются как канал управления анализатором: `[[nodiscard]]`, `gsl::suppress`, `// NOLINT`, `// cppcheck-suppress`.

## Как анализаторы работают внутри (основные техники)

- **Сопоставление с шаблоном (pattern matching) по AST.** Ищутся синтаксические конструкции: `if (x = 0)`, вызов `delete` вместо `delete[]`, отсутствие `virtual` у деструктора базового класса. Так устроены `clang-tidy`, PC-lint, большинство «линтеров».
- **Потоковый анализ данных (dataflow).** Отслеживается, откуда пришло значение и где оно используется: «переменная объявлена, но не инициализирована», «указатель получен из `malloc`, но не проверен на `NULL`», «ресурс захвачен, но не освобождён на одной из веток».
- **Символьное исполнение (symbolic execution).** Анализатор «проходит» пути исполнения, подставляя символьные значения и накапливая ограничения; если ограничения противоречивы — путь недостижим, если на пути возникает разыменование `NULL` — выдаётся предупреждение (Clang Static Analyzer, KLEE).
- **Абстрактная интерпретация.** Значения переменных приближаются абстрактными доменами (интервалы, octal-домены); позволяет **доказывать** отсутствие ошибок, но требует аннотаций и даёт много ложных срабатываний (Astrée, Polyspace).
- **Межпроцедурный анализ / анализ указателей.** Строится граф вызовов и отслеживаются алиасы: «кто на самом деле может писать в этот объект».
- **Проверка моделей (model checking).** Код разворачивается в конечный автомат, и свойство проверяется исчерпывающе в заданной глубине (CBMC, ESBMC).
- **Типовые системы и контракты.** Часть ошибок ловится ещё компилятором: `[[nodiscard]]`, `constexpr`, `std::span`, `gsl::not_null`, `static_assert`.

## Что ищут в C++ (типичные категории)

| Категория | Пример |
|---|---|
| Неопределённое поведение | разыменование `nullptr`, выход за границы массива, знаковое переполнение, чтение неинициализированной переменной |
| Управление памятью | утечки, `new[]`/`delete`, двойное освобождение, висячие ссылки (`dangling`) |
| Владение и время жизни | возврат ссылки на локальную переменную, `c_str()` после модификации строки |
| Ресурсы | не закрыт файл/сокет, забыт `release()` у мьютекса |
| ООП | невиртуальный деструктор в полиморфном базовом классе, срезка объекта (`slicing`) при передаче по значению |
| Шаблоны | ошибки инстанцирования, нарушение ODR, неверный `enable_if` |
| Исключения | `throw` в деструкторе, отсутствие `noexcept` у перемещающего конструктора |
| Многопоточность | гонки данных, захват `this` в лямбде, удержание блокировки при вызове чужого кода |
| Стиль и соглашения | `using namespace` в заголовке, отсутствие `#include guard`/`#pragma once`, магические числа |
| Безопасность (SAST) | переполнение буфера, форматная строка `printf(user_input)`, taint-анализ |

Небольшой пример — что реально ловят разные инструменты:

```cpp
int* p = nullptr;
*p = 42;                       // clang-analyzer-core.NullDereference

if (x = 0) { /* ... */ }       // -Wparentheses, bugprone-assignment-in-if-condition

int a[10];
a[10] = 0;                     // -Warray-bounds, cppcheck: arrayIndexOutOfBounds

struct Base { ~Base(); };      // нет virtual — ошибка при delete через Base*
struct Derived : Base {};

void f() {
    std::string s = "abc";
    const char* q = s.c_str();
    s += "def";                // q может стать висячим
}
```

## Классификация статических анализаторов

1. **Линтеры стиля** — проверяют форматирование и соглашения, работают по тексту или токенам: `cpplint`, `clang-format` (форматтер, но входит в тот же конвейер), правила SonarLint.
2. **Компиляторные предупреждения** — самый доступный «статический анализатор»: `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`, MSVC `/W4`. Многие считают их частью статического анализа, и формально это верно.
3. **Анализаторы на AST/CFG** — основная масса: `clang-tidy`, Clang Static Analyzer, Cppcheck, PC-lint Plus, PVS-Studio.
4. **Межпроцедурные/whole-program** — Coverity, Klocwork, Infer, SonarQube.
5. **Формальные/«доказывающие»** — Astrée, Polyspace, Frama-C, CBMC: либо доказывают отсутствие ошибок, либо дают ложное срабатывание, но не пропускают.
6. **Специализированные** — Include What You Use (гигиена `#include`), анализаторы метрик (Understand, SourceMonitor), анализаторы MISRA/AUTOSAR (Helix QAC).

## Конкретные инструменты

| Инструмент | Лицензия | Основа | Чем известен |
|---|---|---|---|
| **clang-tidy** | open source (Apache 2.0) | Clang AST, AST-matchers | наборы `bugprone-*`, `modernize-*`, `readability-*`, `performance-*`, `cppcoreguidelines-*`, `cert-*`; умеет `--fix`; нужен `compile_commands.json` |
| **Clang Static Analyzer** | open source | символьное исполнение по CFG | `scan-build`, чекеры `core`, `deadcode`, `security`, `unix`, `cplusplus`; встроен в `clang --analyze` |
| **Cppcheck** | open source (GPL) | собственный препроцессор и парсер | не требует полной сборки, `--enable=all`, suppression-файлы, GUI |
| **PVS-Studio** | коммерческая (бесплатно для open source) | собственный фронтенд | диагностики Vxxx, интеграция с MSVC/GCC/Clang/Keil/IAR, поддержка C++20 |
| **Coverity (Synopsys)** | коммерческая; Coverity Scan бесплатен для OSS | межпроцедурный анализ | поиск дефектов в масштабе всей программы, «defect density» |
| **SonarQube / SonarLint** | Community / коммерческая | правила + taint-анализ | метрики, дублирование, уязвимости, CI-гейты |
| **MSVC `/analyze` + CppCoreCheck** | в составе Visual Studio | фронтенд MSVC | проверки C++ Core Guidelines, интеграция в IDE |
| **GCC `-fanalyzer`** | open source (GCC 10+) | анализ путей в GCC | бесплатный аналог для проектов на GCC |
| **Facebook Infer** | open source (MIT) | абстрактная интерпретация, separation logic | C/C++/Java/ObjC, поиск `nullptr` и утечек |
| **Klocwork** | коммерческая (Perforce) | межпроцедурный | безопасность, MISRA, большие проекты |
| **PC-lint Plus** | коммерческая (Gimpel) | AST | классика для C/C++, тонкая настройка |
| **Parasoft C/C++test** | коммерческая | правила + покрытие | MISRA, AUTOSAR, unit-тесты |
| **Helix QAC** | коммерческая (Perforce) | правила | сертификация по MISRA/AUTOSAR |
| **Polyspace** | коммерческая (MathWorks) | абстрактная интерпретация | доказательство отсутствия runtime-ошибок, авионика/авто |
| **Astrée** | коммерческая (AbsInt) | sound abstract interpretation | safety-critical embedded, доказательство отсутствия UB |
| **CBMC / ESBMC** | open source | bounded model checking | проверка assertions и границ массивов |
| **Frama-C** | open source | контракты ACSL, C | формальная верификация C-кода |
| **Include What You Use (IWYU)** | open source | Clang | лишние/недостающие `#include` |
| **cpplint** | open source | регулярные выражения | Google C++ Style Guide |

Важно понимать разницу в философии: `clang-tidy` — **эвристический**, он оптимизирован против ложных срабатываний и потому кое-что пропускает; `Astrée`/`Polyspace` — **sound**, они не пропускают ошибок, но могут требовать аннотаций и шумят на корректном коде. Для учебного проекта обычно достаточно `clang-tidy` + `-Wall -Wextra` + `cppcheck`.

## Чем статический анализ не является

- **Не динамический анализ.** ASan/UBSan/TSan, Valgrind, fuzzing — это выполнение программы; они точнее (видят реальные данные), но зависят от покрытия тестами.
- **Не только «поиск ошибок».** Метрики (цикломатическая сложность), дублирование, мёртвый код, соответствие coding standard — тоже статический анализ.
- **Не замена code review и тестам.** Анализатор не знает требований и предметной области; он ловит типовые паттерны.
- **Не «компилятор, который всё знает».** Предупреждения компилятора — подмножество статического анализа, ограниченное одним TU и скоростью компиляции.

## Как это встраивают в процесс

```bash
# генерация базы компиляции
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# clang-tidy по всему проекту
clang-tidy -p build src/*.cpp --warnings-as-errors='*'

# clang static analyzer
scan-build --status-bugs cmake --build build

# cppcheck
cppcheck --enable=all --project=build/compile_commands.json \
         --suppress=missingIncludeSystem --error-exitcode=1
```

Практические правила: запускать в CI на каждом PR, хранить baseline/подавления с обоснованием, не включать сразу все проверки (иначе команда утонет в шуме), для C++ обязательно передавать те же `-D`/`-I`/`-std`, что и сборке, и анализировать **все** реальные конфигурации, потому что препроцессор делает из одного файла несколько разных программ.

## Формулировка для ответа на экзамене

> Статический анализатор кода — это программа, которая анализирует исходный код без его выполнения и выявляет потенциальные ошибки, уязвимости и нарушения соглашений. В C++ он обычно работает после препроцессора, используя AST, граф потока управления и, для сложных инструментов, межпроцедурный анализ или символьное исполнение. Примеры: clang-tidy, Clang Static Analyzer, Cppcheck, PVS-Studio, Coverity, SonarQube, MSVC `/analyze`, GCC `-fanalyzer`, а также формальные Astrée, Polyspace, CBMC. Главные проблемы — ложные срабатывания и неразрешимость задачи в общем виде, поэтому анализ всегда компромисс между полнотой и точностью.
