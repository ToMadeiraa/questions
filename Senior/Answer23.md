# 23. Что такое динамический анализатор кода? Какие знаете?

## Короткое определение

**Динамический анализатор кода** — это инструмент, который исследует программу **во время её выполнения**, а не по исходному тексту. Он наблюдает за реальными процессами: выделением и освобождением памяти, обращениями по адресам, значениями переменных, переключениями потоков, системными вызовами, блокировками, временем выполнения участков кода — и по этим наблюдениям делает выводы о дефектах, производительности или покрытии.

Ключевая идея: анализатору не нужно «догадываться», что произойдёт при выполнении ветки, — он видит, что произошло фактически. Плата за это — анализ только тех путей, которые действительно были исполнены на конкретных входных данных.

В контексте C++ это особенно важно, потому что язык даёт программисту много способов получить неопределённое поведение (UB), которое статически доказать крайне трудно: выход за границы массива, чтение неинициализированной памяти, висячие указатели, гонки данных, переполнение знакового целого, нарушение strict aliasing.

## Место динамического анализа в цепочке «препроцессор → компилятор → линковка → выполнение»

Динамический анализ — это этап **после** сборки, но готовится он зачастую ещё на этапе компиляции:

```
исходники → препроцессор → компилятор (+ инструментирование) → линковщик (+ runtime-библиотека анализатора) → запуск под анализатором
```

1. **Препроцессор** управляет тем, какие проверки вообще попадут в код. Классические примеры:
   - `_DEBUG`, `NDEBUG` — включают/выключают `assert`;
   - `_ITERATOR_DEBUG_LEVEL` (MSVC STL) и `_GLIBCXX_DEBUG` / `_GLIBCXX_ASSERTIONS` (libstdc++) — проверяемые итераторы и контейнеры;
   - `_CRTDBG_MAP_ALLOC` — обязателен **до** `#include <crtdbg.h>`, иначе отчёт CRT-кучи не будет содержать имён файлов и строк;
   - макросы-детекторы: GCC определяет `__SANITIZE_ADDRESS__`, Clang — `__has_feature(address_sanitizer)`, что позволяет условно компилировать код под санитайзеры.

2. **Компилятор** при флагах вида `-fsanitize=address` вставляет в код проверки и подключает runtime-библиотеку (`libasan`, `libubsan`, `libtsan`). Это самый распространённый и самый дешёвый по трудозатратам способ динамического анализа в C++.

3. **Линковщик** соединяет инструментированный код с runtime анализатора; при этом важно, чтобы **все** модули были собраны согласованно (например, для MemorySanitizer — вообще весь код, включая сторонние библиотеки).

4. **Выполнение** — собственно анализ: либо под специальной средой (Valgrind, Dr. Memory), либо прямо в процессе с встроенным runtime (ASan/TSan/UBSan).

Отдельно стоит помнить: часть «динамических анализаторов» **не требует перекомпиляции** (Valgrind, Dr. Memory, DynamoRIO, Pin, strace, perf), а часть **требует** (санитайзеры, `_GLIBCXX_DEBUG`, CRT debug heap). Это важное практическое различие.

## Как работает динамический анализатор

Можно выделить четыре механизма, которые комбинируются:

1. **Инструментирование (instrumentation)** — вставка проверок в код:
   - на уровне исходников (макросы, `assert`, проверяемые контейнеры);
   - на уровне компилятора (санитайзеры, `-fstack-protector`, `_FORTIFY_SOURCE`, CFI);
   - на уровне бинарного кода (DynamoRIO, Pin, Valgrind — динамическая бинарная трансляция, DBI);
   - на уровне «теневой памяти» (shadow memory): ASan/Valgrind хранят для каждого байта программы метаданные «можно ли к нему обращаться».

2. **Перехват и эмуляция** — анализатор подменяет `malloc/free`, `operator new/delete`, системные вызовы, примитивы синхронизации, эмулирует процессор (QEMU, Valgrind) или исполняет код через JIT-трансляцию (DynamoRIO, Pin).

3. **Сбор событий** — трассировка обращений к памяти, блокировок, вызовов, сэмплов профилировщика, счётчиков покрытия.

4. **Диагностика** — сопоставление событий с правилами: «освободили — потом обратились» (use-after-free), «два потока обратились к одной ячейке без синхронизации» (data race), «прочитали байт, который не был записан» (uninitialized read), «взяли блокировку A, потом B, а в другом потоке — B, потом A» (lock-order inversion).

## Что обычно находят динамические анализаторы

- **Ошибки работы с памятью:** переполнение буфера (heap/stack/global-buffer-overflow), use-after-free, use-after-scope, double free, утечки, обращение по нулевому/битому указателю, выход за границы при `memcpy`.
- **Неинициализированные чтения** — классика, которую «глазами» почти не видно.
- **Неопределённое поведение:** знаковое переполнение, сдвиг на отрицательную/слишком большую величину, деление на ноль, misaligned access, нарушение выравнивания, вызов по неверному типу (vptr), `nullptr`-разыменование.
- **Ошибки многопоточности:** гонки данных, инверсия порядка блокировок, deadlock, обращение к разрушенному объекту из другого потока, ошибки условных переменных.
- **Утечки ресурсов:** память, файловые дескрипторы, handles (Windows), сокеты, GDI-объекты.
- **Производительность:** горячие функции, лишние аллокации, кэш-промахи, время в системных вызовах.
- **Покрытие:** какие строки/ветки реально исполнялись.
- **Нарушения контрактов и инвариантов:** сработавшие `assert`, проверки стандартной библиотеки, пользовательские runtime-проверки.

## Классификация динамических анализаторов

| Класс | Что делает | Примеры |
|---|---|---|
| **Memory checkers** | Ищут ошибки доступа к памяти, утечки, неинициализированные чтения | Valgrind Memcheck, Dr. Memory, AddressSanitizer, LeakSanitizer, Application Verifier, Deleaker, VLD |
| **UB-санитайзеры** | Проверяют неопределённое поведение по стандарту языка | UndefinedBehaviorSanitizer, `-ftrapv`, `_GLIBCXX_ASSERTIONS` |
| **Thread checkers** | Гонки данных, deadlock, инверсия блокировок | ThreadSanitizer, Helgrind, DRD, Intel Inspector |
| **Профилировщики** | Где тратится время/память/кэш | perf, VTune, Callgrind, Cachegrind, Massif, gprof, heaptrack |
| **Трассировщики** | Системные вызовы, API, события ядра | strace, ltrace, ETW, DTrace, eBPF/BCC, Process Monitor |
| **Fuzzer'ы** | Генерируют входы и ищут падения/санитайзер-репорты | libFuzzer, AFL++, honggfuzz, OSS-Fuzz |
| **Символическое/конколическое исполнение** | Исследует пути через решатель | KLEE, angr, S2E, Manticore |
| **Taint-анализ** | Отслеживает распространение «заражённых» данных | DFSan, Triton, Dr. Checker |
| **Runtime-верификация** | Проверка инвариантов и контрактов во время работы | assert, договоры, проверяемые итераторы STL |

## Конкретные инструменты

### 1. Санитайзеры (sanitizers) — основной инструмент для C++

Это компиляторное инструментирование: код пересобирается с флагами, runtime печатает отчёт с трассой.

**AddressSanitizer (ASan)** — переполнения буферов, use-after-free, double free, use-after-scope, ошибки при `memcpy`/`memmove`. Стоимость — примерно 2× по времени и памяти.

```bash
g++ -std=c++20 -g -O1 -fno-omit-frame-pointer \
    -fsanitize=address -fsanitize-address-use-after-scope main.cpp -o app
ASAN_OPTIONS=detect_leaks=1:abort_on_error=1:symbolize=1 ./app
```

**LeakSanitizer (LSan)** — утечки; на Linux входит в ASan, отдельно включается `-fsanitize=leak`.

**UndefinedBehaviorSanitizer (UBSan)** — знаковое переполнение, сдвиги, деление на ноль, `nullptr`, misaligned, `vptr`, выход за границы массивов с известным размером.

```bash
g++ -g -O1 -fsanitize=undefined -fno-sanitize-recover=all main.cpp -o app
UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1 ./app
```

**ThreadSanitizer (TSan)** — гонки данных, deadlock, инверсия блокировок. Несовместим с ASan, требует отдельной сборки.

```bash
g++ -g -O2 -fsanitize=thread main.cpp -o app
```

**MemorySanitizer (MSan)** — чтение неинициализированной памяти; только Clang, и **весь** код (включая библиотеки) должен быть инструментирован. Даёт меньше ложных срабатываний, чем Valgrind, но сложнее в настройке.

**HWASan** — аппаратно-тегированный вариант ASan для AArch64, с существенно меньшими накладными расходами.

**DFSAN** — data-flow sanitizer, taint-анализ на уровне компилятора.

Комбинировать можно так: `-fsanitize=address,undefined` (совместимы), а TSan и MSan — отдельными сборками. В MSVC аналог ASan включается `/fsanitize=address` (начиная с VS 2019 16.9), а для отладочной кучи используется CRT.

**Проверяемые контейнеры и итераторы** — «лёгкий» динамический анализ без внешнего runtime:

```cpp
// libstdc++
g++ -D_GLIBCXX_DEBUG -D_GLIBCXX_ASSERTIONS ...
// MSVC
// _ITERATOR_DEBUG_LEVEL=2 в Debug-конфигурации
```

Они ловят выход за границы `std::vector`, использование инвалидированных итераторов, неверные диапазоны.

### 2. Valgrind (Linux, x86/ARM)

Набор инструментов, работающих через динамическую бинарную трансляцию, **без перекомпиляции** (но с `-g` отчёты читабельнее):

- `memcheck` — ошибки памяти и утечки (`--leak-check=full --show-leak-kinds=all`);
- `helgrind`, `drd` — гонки и блокировки;
- `callgrind` — профиль вызовов;
- `cachegrind` — кэш и ветвления;
- `massif` — профиль кучи;
- `dhat` — аллокации;
- `sgcheck` — экспериментальная проверка границ стековых/глобальных массивов.

```bash
valgrind --tool=memcheck --leak-check=full --track-origins=yes ./app
```

Цена — замедление в десятки раз (Memcheck обычно 10–30×), поэтому Valgrind применяют к тестам, а не к «прогону в бою». На Windows официально не работает.

### 3. Инструменты Windows

- **Application Verifier** — проверки кучи, handles, блокировок, TLS, `HeapValidate`; включается без пересборки, хорошо ловит порчу кучи.
- **Debug heap CRT**: `_CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF)`, `_CrtMemCheckpoint`/`_CrtMemDifference`, `_CrtDumpMemoryLeaks`; с `_CRTDBG_MAP_ALLOC` в отчёте будут файл и строка.
- **PageHeap** (`gflags /p /enable app.exe /full`) — каждая аллокация на отдельной странице, мгновенно ловит выход за границы.
- **Dr. Memory** — аналог Valgrind для Windows/Linux/macOS на DynamoRIO.
- **Deleaker**, **Visual Leak Detector (VLD)** — детекторы утечек, интеграция с Visual Studio.
- **WinDbg** (`!heap`, `!analyze -v`), **Process Monitor**, **ETW/WPR** — трассировка и разбор падений.

### 4. Профилировщики и трассировщики

- **perf** (Linux): `perf record -g`, `perf report`, `perf stat`; сэмплирование, аппаратные счётчики, flame graphs.
- **Intel VTune**, **AMD uProf** — микроархитектурный анализ.
- **gprof**, **Callgrind**, **KCachegrind** — профиль по вызовам.
- **heaptrack**, **Massif**, **DHAT** — профиль памяти.
- **strace**, **ltrace** — системные вызовы и библиотечные вызовы.
- **rr** — запись и обратное воспроизведение выполнения (reverse debugging), очень удобно для «редких» багов.
- **GDB/LLDB**: watchpoints, `catch throw`, `record`, условные точки останова.
- **eBPF/BCC**, **DTrace**, **LTTng** — динамическая трассировка ядра и пользовательских процессов.

### 5. Fuzzing и исследование путей

- **libFuzzer** (`-fsanitize=fuzzer,address`) — покрытийно-управляемый фаззинг прямо в процессе, идеально сочетается с ASan/UBSan.
- **AFL++**, **honggfuzz**, **OSS-Fuzz** — массовый фаззинг, часто с persistent-режимом.
- **KLEE**, **angr**, **S2E**, **Manticore** — символическое/конколическое исполнение: строят входы, ведущие в интересующие ветки.
- **Triton**, **DFSan**, **Dr. Checker** — taint-анализ и отслеживание зависимостей данных.

## Плюсы и минусы

**Плюсы:**
- Видит реальные адреса, реальные значения, реальное чередование потоков — то, что статике недоступно.
- Ловит дефекты, которые статический анализатор «не докажет»: неинициализированную память, гонки, утечки.
- Обычно меньше ложных срабатываний: если ASan написал `heap-use-after-free`, это почти наверняка реальный баг.
- Хорошо интегрируется в CI: отдельная job-сборка с санитайзерами, прогон тестов, падение на первом отчёте.

**Минусы:**
- **Зависимость от входных данных:** неисполненный путь — не проверенный путь; баг в непокрытой ветке анализатор не увидит.
- **Недетерминизм:** гонки и утечки могут не воспроизводиться от запуска к запуску.
- **Накладные расходы:** от 2× (ASan) до 30× и более (Valgrind, TSan, MSan).
- **Требования к сборке:** нужны `-g`, часто `-O1`, согласованное инструментирование всех модулей; смешивание инструментированного и «чистого» кода даёт пропуски.
- **Ложные срабатывания тоже бывают** (например, TSan на самодельных примитивах синхронизации, Valgrind на нестандартных аллокаторах), хотя их меньше, чем у статики.
- Не заменяет тесты и code review, а дополняет их.

## Статический и динамический анализ: сравнение

| Критерий | Статический | Динамический |
|---|---|---|
| Когда работает | До запуска, по коду/IR | Во время выполнения |
| Покрытие | Все ветки формально | Только исполненные пути |
| Входные данные | Не нужны | Нужны тесты/фаззинг |
| Ложные срабатывания | Часто много | Обычно мало |
| Пропуски (false negative) | Есть, особенно межмодульные | Есть, если путь не исполнялся |
| Накладные расходы | Время сборки/анализа | Время выполнения, память |
| Типичные находки | Стиль, опасные паттерны, утечки по владению | Реальные UAF, гонки, неинициализированные чтения |

На практике их сочетают: статический анализ в ревью и CI, динамический — на тестах, фаззинге и ночных прогонах.

## Практический рабочий набор для C++

1. **Debug/RelWithDebInfo** сборка с `-g -O1 -fno-omit-frame-pointer`.
2. Отдельные CI-джобы:
   - `-fsanitize=address,undefined` — базовая, самая частая;
   - `-fsanitize=thread` — отдельно, для многопоточного кода;
   - `-fsanitize=memory` (Clang) — если критична неинициализированная память;
   - `-D_GLIBCXX_DEBUG` / `_ITERATOR_DEBUG_LEVEL=2` — для STL-ошибок;
   - Valgrind Memcheck — на Linux, для модульных тестов;
   - Application Verifier + PageHeap — на Windows.
3. Фаззинг ключевых парсеров и API через libFuzzer/AFL++ с ASan.
4. Профилирование (perf/VTune/Callgrind) — отдельно от поиска дефектов.
5. Чтение отчётов: символьные имена, `addr2line`/`llvm-symbolizer`, `ASAN_SYMBOLIZER_PATH`, сохранение логов как артефактов CI.

Важная деталь из области препроцессора: санитайзеры и отладочные проверки — это **разные конфигурации сборки**, и их нельзя «включать наполовину». Если один объектный файл собран с `-fsanitize=address`, а другой без, поведение будет непредсказуемым (в лучшем случае — ошибка линковки, в худшем — пропуски и ложные отчёты). Поэтому флаги анализатора должны быть согласованы на уровне всей системы сборки (CMake-опции, presets, отдельный toolchain-файл), а не задаваться точечно в одном `#define`.

## Итог

Динамический анализатор — это инструмент наблюдения за **работающей** программой, который по реальным событиям (доступам к памяти, блокировкам, вызовам, сэмплам) находит дефекты, неподвластные статике: use-after-free, утечки, неинициализированные чтения, гонки, UB. В мире C++ его «первый эшелон» — компиляторные санитайзеры (ASan, LSan, UBSan, TSan, MSan), «второй эшелон» — Valgrind, Dr. Memory, Application Verifier и профайлеры, «третий» — фаззинг и символическое исполнение. Максимальный эффект даёт комбинация: статический анализ + сборки с санитайзерами в CI + фаззинг + профилирование, причём каждая конфигурация должна быть собрана целиком и согласованно.
