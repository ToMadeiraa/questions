# 16. Опишите принципы lock-free структур данных и свой опыт работы с ними

## 1. Что такое lock-free: гарантии прогресса

Lock-free — это не «без мьютексов» и не «быстро», а формальная гарантия прогресса. Полезно держать в голове лестницу:

| Свойство | Гарантия | Что бывает на практике |
|---|---|---|
| **Blocking** (мьютекс) | Поток, взявший блокировку, может быть вытеснен планировщиком, и все остальные ждут | Простой, но priority inversion и неограниченные задержки |
| **Obstruction-free** | Поток завершает операцию, если ему дать поработать в одиночестве достаточно долго | Основа для более сильных схем |
| **Lock-free** | **Хотя бы один** поток системы продвигается за конечное число шагов; отдельный поток может голодать | CAS-циклы, MPSC-очереди |
| **Wait-free** | **Каждый** поток завершает операцию за ограниченное число **своих** шагов | Счётчики, SPSC-кольцо, некоторые очереди |

Ключевые следствия:

- В lock-free возможна **индивидуальная** голодовка: конкретный поток может повторять CAS бесконечно, но система в целом не стоит.
- Lock-free не отменяет ожидания на уровне железа: CAS-цикл ждёт изменения кэш-линии, а «помогающие» операции ждут чужого прогресса.
- Lock-free **не композиционен**: две корректные lock-free операции нельзя просто объединить в одну атомарную без транзакционной памяти или multi-word CAS.

Зачем это нужно: жёсткий real-time, обработчики сигналов и прерываний (там нельзя брать мьютекс), борьба с priority inversion, предсказуемость хвостовых задержек, масштабирование на много ядер при удачном паттерне доступа.

## 2. Базовые примитивы и модель памяти

Фундамент — `std::atomic<T>` и корректные **memory orders**. Главное правило: гонка данных (два конфликтующих доступа, хотя бы один — запись, не упорядоченные happens-before) — это **UB**, а не «немного неверное значение».

| Порядок | Смысл |
|---|---|
| `relaxed` | Только атомарность и когерентность, никакого упорядочивания |
| `acquire` (load) | Последующие операции не могут «уехать» выше |
| `release` (store) | Предыдущие операции не могут «уехать» ниже |
| `acq_rel` (RMW) | И то, и другое |
| `seq_cst` | Плюс единый глобальный порядок всех seq_cst-операций |

Практическая дисциплина: **начинать с `seq_cst`**, а ослаблять до `relaxed`/`acquire`/`release` только с письменным доказательством. Классическая ловушка — код, который «работает» на x86 (TSO не переставляет store→load), но ломается на ARM/AArch64, где такая перестановка легальна. `memory_order_consume` лучше не использовать вовсе — он фактически вырождается в `acquire`.

Отдельно про переносимость: `std::atomic_flag` гарантированно lock-free, остальные типы — нет. Для 16-байтовых атомиков (tagged pointer) нужен `is_lock_free()` и выравнивание; на 32-битных ARM `atomic<uint64_t>` может внутри брать блокировку. Поэтому «lock-free структура» на одном таргете может оказаться «lock-based» на другом.

## 3. Три главные проблемы

### 3.1. ABA

Поток 1 читает `head = A`, `A->next = B`. Поток 2 делает `pop(A)`, `pop(B)`, затем `push(A)` — и адрес `A` снова в стеке, но `A->next` уже другой. CAS потока 1 `head: A → B` succeeds, хотя состояние изменилось. Для стека это означает потерю узлов и разыменование освобождённой памяти.

Решения: tag/version в указателе (упаковка в 128-битный CAS, `cmpxchg16b`/`caspl`), hazard pointers, epoch-based reclamation, «не переиспользовать» узлы (bounded pool), реже — GC.

### 3.2. Освобождение памяти (safe memory reclamation)

Это самая тяжёлая часть. Сама структура без реклейма тривиальна; сложность — понять, когда узел, снятый с головы, больше никто не читает.

- **Hazard pointers** — поток публикует указатели, которые читает; освобождение после сканирования всех hazard-списков. C++26 даёт `std::hazard_pointer`.
- **Epoch/RCU** — читатели почти бесплатны (нет атомиков на чтении), освобождение откладывается до прохождения quiescent state всеми потоками. Минусы: задержка освобождения, рост памяти, тяжёлые писатели.
- **Reference counting** — интрузивный счётчик, decrement через `fetch_sub(acq_rel)`; `std::atomic<std::shared_ptr<T>>` в C++20 может быть не lock-free.
- **Вообще не освобождать** — валидный инженерный вариант для bounded-пула.

### 3.3. Контеншн и кэш

Lock-free не спасает от физики: CAS по одной cache line сериализуется, линия «пингуется» между ядрами, стоимость доступа — десятки-сотни наносекунд. Под нагрузкой CAS-цикл может быть **медленнее** мьютекса из-за повторов и wasted work. Помогают: `alignas(64)` (или `hardware_destructive_interference_size`), per-thread слоты/счётчики с последующей агрегацией, backoff, batching, шардирование.

## 4. Как выглядят типовые структуры

### Стек Трайбера (Treiber stack)

```cpp
struct Node { T value; Node* next; };
std::atomic<Node*> head{nullptr};

void push(T v) {
    Node* n = new Node{std::move(v), nullptr};
    n->next = head.load(std::memory_order_relaxed);
    // при неудаче compare_exchange_weak сам обновит n->next
    while (!head.compare_exchange_weak(n->next, n,
               std::memory_order_release,
               std::memory_order_relaxed)) {}
}
```

`pop` — это CAS головы плюс hazard pointer, иначе неизбежен ABA/dangling. Важно: `pop` здесь lock-free, но не wait-free — под контеншном поток может крутиться.

### SPSC-кольцо (самый недооценённый инструмент)

```cpp
template <class T, size_t N>   // N — степень двойки
class SpscQueue {
    alignas(64) std::atomic<size_t> head_{0}; // пишет только producer
    alignas(64) std::atomic<size_t> tail_{0}; // пишет только consumer
    alignas(64) std::array<T, N> buf_{};
public:
    bool push(const T& v) {
        size_t h = head_.load(std::memory_order_relaxed);
        size_t t = tail_.load(std::memory_order_acquire);
        if (h - t == N) return false;            // полно
        buf_[h & (N - 1)] = v;
        head_.store(h + 1, std::memory_order_release); // публикация данных
        return true;
    }
    bool pop(T& out) {
        size_t t = tail_.load(std::memory_order_relaxed);
        size_t h = head_.load(std::memory_order_acquire);
        if (t == h) return false;                // пусто
        out = buf_[t & (N - 1)];
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }
};
```

Здесь `release`/`acquire` — не украшение: именно они гарантируют, что запись в `buf_` видна до публикации индекса. С `relaxed` на ARM потребитель может прочитать индекс раньше данных.

### Очередь Майкла–Скотта (MPSC/MPMC)

Идея: фиктивный dummy-узел, `head` и `tail`, enqueue ставит новый узел через CAS `tail->next`, а остальные потоки **помогают**, если видят, что `tail` отстал. Это классический пример lock-free с helping. Попытка сделать то же «в лоб», без dummy-узла и helping, обычно заканчивается либо потерей элементов, либо скрытым мьютексом.

### Seqlock

Писатель: `seq++` (нечётный) → запись данных → `seq++` (чётный). Читатель: прочитать `seq`, данные, снова `seq`; если значения разошлись или нечётное — повторить. Формально это не lock-free (читатель может голодать), но для read-mostly маленьких структур (время, конфиг, снапшот метрик) даёт почти бесплатное чтение.

### Хэш-таблица и список

Полноценная lock-free хэш-таблица — это отдельный проект: resize требует кооперации, удаление — реклейма, итераторы — слабой консистентности. На практике чаще берут **шардирование** (N независимых мьютексов) или **read-mostly снапшоты** (RCU/`atomic<shared_ptr<const Map>>` с copy-on-write), а lock-free оставляют для горячих точечных операций.

## 5. Правила и антипаттерны

- `volatile` вместо `std::atomic` — не атомарность и не ordering.
- «У меня всё на `relaxed`, вроде работает» — работает до смены архитектуры/компилятора.
- CAS-цикл на одном общем счётчике под 32 потоками — почти всегда хуже шардированного счётчика.
- `new`/`delete` на каждую операцию — контеншн в аллокаторе; нужны пулы.
- Отсутствие `is_lock_free()` проверки для широких атомиков.
- Забыть, что lock-free не даёт wait-free: поток всё ещё может «зависнуть» надолго.
- Пытаться строить lock-free там, где достаточно мьютекса, — цена сопровождения обычно выше выигрыша.

## 6. Как это проверять

1. **Инварианты и стресс-тесты**: много потоков, случайные операции, проверка инвариантов после `join`, прогон под нагрузкой и с `-O2`.
2. **ThreadSanitizer** в CI — ловит гонки, но не доказывает корректность атомарных протоколов.
3. **Model checking**: Relacy, CDSChecker, GenMC — перебирают интерливинги и слабые модели памяти; незаменимы для маленьких структур вроде SPSC-кольца.
4. **Инъекция вытеснения**: вставить `yield`/`sleep` внутрь CAS-цикла в debug-сборке — часто мгновенно вскрывает ABA и потерянные обновления.
5. **Прогон на ARM** (Apple Silicon, Graviton) — самый дешёвый способ найти недостающий `acquire`/`release`.
6. **Профилирование**: `perf c2c` для false sharing, замер p99/p999, а не только среднего.

## 7. Мой опыт

Ниже — обобщение задач, с которыми я реально работал; конкретные цифры и названия проектов опускаю.

**Очередь в горячем пути логирования.** Изначально был `std::mutex` + `std::queue`. Средняя задержка устраивала, но p99 прыгал: поток, взявший мьютекс, вытеснялся, и остальные вставали. Заменили на bounded MPSC-очередь с per-producer ячейками и `release/acquire` на публикации индекса. Среднее почти не изменилось, хвост стал предсказуемым, аллокации убрали через пул фиксированного размера. Вывод: в таких задачах выигрыш даёт не «магия lock-free», а устранение блокирующего ожидания и аллокаций.

**SPSC-кольцо между потоками.** Классическая ошибка, которую я поймал только на ARM: индекс публиковался `relaxed`, и потребитель изредка читал ещё не записанный элемент. На x86 не воспроизводилось. После замены на `release`-store / `acquire`-load и прогона в Relacy — стабильно. С тех пор правило: каждый `memory_order` в коде сопровождается комментарием, какую именно пару «запись-публикация» он защищает.

**Счётчики метрик.** Единый `atomic<uint64_t>` на все потоки давал заметный контеншн на одной cache line. Разнесли по per-thread слотам с `relaxed fetch_add` и периодической агрегацией, выровняли по 64 байта — просадка масштабирования ушла. Заодно убедились, что `relaxed` здесь допустим: важен только итог, а не порядок относительно других данных.

**Treiber-стек как free-list.** Поймали ABA после переиспользования узлов: `pop` разыменовывал уже освобождённый узел. Сначала закрыли version-tag в 128-битном CAS (с проверкой `is_lock_free()` на целевых платформах), позже перевели на hazard pointers, потому что тегирование ограничивает разрядность и не решает проблему целиком при долгом удержании ссылки.

**Lock-free хэш-таблица.** Дошли до рабочего прототипа с hazard pointers, но упёрлись в стоимость реклейма и рост памяти при большом числе читателей. В итоге выбрали прагматичное: шардированная таблица на записи + RCU-подобные снапшоты на чтение. Это типичный исход: строгий lock-free оправдан в узком горячем месте, а не «во всей структуре».

**Процесс.** Для каждой структуры писали: инвариант, аргумент линейаризуемости, таблицу «операция → порядок памяти». Держали эталонную реализацию на мьютексе и дифференциальный стресс-тест против неё. Это ловило больше багов, чем любые рассуждения на code review.

## 8. Итог

Lock-free — это инструмент под конкретную цель: убрать неограниченное блокирующее ожидание и priority inversion в местах, где это критично. Плата — сложность доказательства корректности, проблема реклейма памяти, ABA и падение масштабируемости под контеншном. Рабочая стратегия: сначала мьютекс или шардирование, затем SPSC-кольцо/relaxed-счётчики там, где паттерн доступа это позволяет, и только потом полноценные lock-free алгоритмы — маленькие, изолированные за интерфейсом, с тестами на слабой модели памяти и обязательным прогоном на ARM.
