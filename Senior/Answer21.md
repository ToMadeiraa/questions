# 21. Расскажите о работе с сырыми указателями и о ручном управлении памятью.

## 1. Что такое сырой указатель

Сырой указатель (`raw pointer`) — это переменная, значением которой является адрес объекта в памяти. Сам указатель хранится в памяти как целое число разрядности платформы (обычно 4 байта на 32‑битных и 8 байт на 64‑битных системах; стандарт C++ конкретный размер не фиксирует), но с точки зрения типовой системы он несёт ещё и тип объекта, на который указывает:

```cpp
int  x = 42;
int* p = &x;      // p хранит адрес x
*p = 43;          // разыменование: доступ к объекту по адресу
int* q = nullptr; // «нулевой» указатель, никуда не указывает
```

Ключевое отличие «сырого» указателя от умного (`std::unique_ptr`, `std::shared_ptr`) в том, что он **не выражает владения**: компилятор не знает и не проверяет, кто обязан освободить память, когда объект перестаёт быть нужным, и сколько живёт объект. Вся ответственность лежит на программисте.

Основные операции:

- `&obj` — взять адрес; `*p` — разыменовать; `p->member` — доступ к члену;
- арифметика указателей (`p + i`, `p++`, `p - q`) — допустима только в пределах одного массива (плюс один элемент за концом);
- сравнение (`p == q`, `p < q`) — корректно только для указателей на элементы одного массива (или на подобъекты одного объекта);
- приведение типов: `static_cast`, `reinterpret_cast`, `const_cast`, `dynamic_cast`.

## 2. Время жизни и области памяти

Ручное управление памятью имеет смысл только на фоне понимания, где эта память находится:

| Область | Время жизни | Кто освобождает |
|---|---|---|
| Автоматическая (стек) | до выхода из блока | компилятор (код пролога/эпилога) |
| Статическая / TLS | вся программа / поток | среда выполнения |
| Динамическая (куча) | от выделения до явного освобождения | **программист** |
| Память, занятая самим кодом | вся программа | — |

Указатель — это лишь адрес. Он может указывать на стек, на статический объект, на кучу или «в никуда». Компилятор не сопровождает указатель метаданными о времени жизни: он не обязан обнаруживать, что объект уже разрушен.

## 3. Ручное выделение и освобождение памяти

### 3.1. C‑стиль: `malloc` / `free`

```cpp
#include <cstdlib>
#include <cstring>

int* a = static_cast<int*>(std::malloc(10 * sizeof(int))); // сырая память, без конструкторов
if (!a) { /* ошибка: malloc вернул nullptr */ }
std::memset(a, 0, 10 * sizeof(int));
std::free(a);
```

Особенности: `malloc` выделяет **неинициализированную** память и не вызывает конструкторы; возвращает `void*`, поэтому нужно приведение; при неудаче возвращает `nullptr`; `free(nullptr)` допустим; `free` не обнуляет указатель, и после освобождения он становится «висячим».

### 3.2. C++‑стиль: `new` / `delete`

```cpp
int* p = new int(42);        // выделение + инициализация
delete p;                    // разрушение + освобождение
p = nullptr;                 // хорошая привычка

int* arr = new int[100]();   // массив, value-инициализация (нули)
delete[] arr;                // обязательно delete[]!
```

Что важно понимать про этапы компиляции: выражение `new T(args)` — это не «одна инструкция», а конструкция языка, которая **на этапе компиляции** разворачивается в последовательность: вызов `operator new(sizeof(T))` (функция стандартной библиотеки, её символ разрешается на этапе компоновки), затем вызов конструктора `T::T(args)`, а при исключении в конструкторе — автоматический вызов `operator delete`. Аналогично `delete p` — вызов деструктора и затем `operator delete(p)`. Именно поэтому `operator new`/`operator delete` можно перегружать глобально или для класса — это обычные функции с определёнными правилами подстановки.

Отличия от `malloc`: `new` вызывает конструкторы, при неудаче по умолчанию бросает `std::bad_alloc` (а не возвращает `nullptr`), типизирован, не требует приведения, а `new[]` может хранить служебную информацию о числе элементов («cookie»), поэтому смешивать `new[]` с `delete` и `new` с `delete[]` — неопределённое поведение.

### 3.3. Размещающий `new` (placement new)

```cpp
#include <new>
alignas(T) unsigned char buf[sizeof(T)];
T* obj = new (buf) T(...);   // конструктор на готовой памяти
obj->~T();                   // деструктор вызывается вручную
```

Используется в пулах, аллокаторах, `std::vector`‑подобных контейнерах. Память под `buf` не освобождается `delete` — её владелец известен вызывающему коду.

### 3.4. Выравнивание

Помимо размера, у выделения есть требование выравнивания. `malloc`/`operator new` дают выравнивание под `std::max_align_t`; для over‑aligned типов (например, SIMD) в C++17 есть `operator new(size_t, std::align_val_t)` и `new (std::align_val_t{64}) T`, в C — `aligned_alloc`/`posix_memalign`. Ошибка в выравнивании — UB, который может проявляться только на части платформ.

## 4. Как это соотносится с препроцессором и этапами компиляции

Полезно разложить вопрос по стадиям трансляции, потому что разные аспекты указателей «живут» на разных стадиях.

**Препроцессирование (текстовая подстановка).** Здесь ещё нет типов и нет указателей — есть только текст. Что важно:

- `#include <cstdlib>` и `<memory>` подставляют объявления `malloc`, `free`, `operator new`, шаблонов умных указателей. От того, какие заголовки подключены, зависит, какие объявления увидит компилятор; «необъявленная функция» — ошибка именно этой стадии.
- Include guards / `#pragma once` защищают от повторного включения; без них повторное определение структуры или `inline`‑функции приведёт к ошибке.
- `NULL` — это **макрос препроцессора** (`#define NULL 0` или `nullptr`), поэтому он не имеет типа и в перегрузках ведёт себя иначе, чем `nullptr`. В современном C++ используют `nullptr` — это литерал типа `std::nullptr_t`, а не макрос.
- Отладочные аллокаторы часто строятся на макросах, подменяющих `malloc`/`new`, чтобы запомнить `__FILE__` и `__LINE__` места выделения:

```cpp
#define DEBUG_NEW new (__FILE__, __LINE__)
```

  Здесь `__FILE__`, `__LINE__`, `__DATE__` — предопределённые макросы, раскрывающиеся в строковые/числовые литералы ещё до компиляции. Это единственный «бесплатный» способ узнать место утечки без внешних инструментов.
- Условная компиляция (`#ifdef _DEBUG`, `#if defined(...)`) позволяет включать проверки указателей, логирование, `assert` только в отладочной сборке; в релизе код проверок физически отсутствует.
- `#pragma pack` влияет на раскладку структур, а значит — на `offsetof`, на арифметику указателей по полям и на выравнивание; макрос `offsetof` также приходит из `<cstddef>`.
- Макросы не типизированы: `#define CHECK(p) ((p) ? *(p) : 0)` раскрывается текстом и не даёт нормальной диагностики — предпочтительны `inline`‑функции и шаблоны.

**Собственно компиляция.** Здесь проверяется типизация указателей: нельзя неявно привести `int*` к `double*`, нельзя вызвать метод через указатель на несовместимый тип, `const`‑корректность (`const int*` против `int* const`) контролируется именно тут. Компилятор вычисляет `sizeof`, `alignof`, разворачивает `new`/`delete` в вызовы функций, применяет оптимизации. При этом **время жизни объекта не является частью типа**: компилятор не может доказать, что `p` после `delete p` не используется, и по стандарту такая программа просто некорректна (UB). Более того, современные оптимизаторы используют UB как допущение: разыменование указателя позволяет считать его ненулевым, а выход за границы массива — «невозможным», поэтому программа с ошибкой может вести себя совершенно неожиданно, а не «упасть в том же месте».

Важный момент: указатель в заголовке — это **объявление**, а не определение. В каждом `.cpp`, включившем заголовок, появляется своё объявление одного и того же имени; сама переменная определяется в одном месте (ODR). Нарушение ODR (например, неодинаковое определение `inline`‑функции в разных TU) — UB, и линкер может этого не заметить.

**Ассемблирование.** Указатель превращается в обычную машинную адресацию: `[reg + offset]`, `lea`, косвенные вызовы. Здесь уже нет никакой «защиты типов» — только адреса и регистры.

**Компоновка.** Разрешаются внешние символы: `operator new`, `operator delete`, `malloc`, `free`, деструкторы и конструкторы. Если вы объявили функцию, работающую с указателями, но не определили её, ошибка появится именно на этой стадии (`undefined reference`). Имена C++‑функций проходят через mangling, поэтому для C‑библиотек используется `extern "C"` — иначе `malloc` не слинкуется.

## 5. Типичные ошибки ручного управления памятью

| Ошибка | Суть | Последствие |
|---|---|---|
| Утечка (leak) | память выделена, но не освобождена | рост потребления памяти |
| Double free | повторный `delete`/`free` | повреждение кучи, падение |
| Use-after-free | обращение после освобождения | UB, иногда «работает» |
| Dangling pointer | указатель на разрушенный объект (стек, поле, `vector` после реаллокации) | UB при разыменовании |
| Неинициализированный указатель | `int* p; *p = 1;` | запись по случайному адресу |
| Несовпадение `new`/`delete`, `new[]`/`delete[]` | разная семантика освобождения | UB |
| Освобождение не той памяти | `free` на `new`, `delete` на стек/статику | UB |
| Выход за границы массива | арифметика вне массива | UB, порча соседних данных |
| Нарушение strict aliasing | доступ к объекту через указатель несовместимого типа (кроме `char*`, `std::byte*`, `unsigned char*`) | UB при оптимизациях |
| Возврат указателя на локальную переменную | объект уже разрушен | dangling pointer |

Отдельно: `volatile` не делает указатель потокобезопасным; гонки на указателях — это data race, а не проблема «устаревшего значения».

## 6. Правила безопасной работы

1. **Один владелец — один `delete`.** Явно фиксируйте, кто владеет ресурсом; лучше — вообще не владеть сырым указателем, а только наблюдать.
2. **Сразу обнуляйте после освобождения** (`p = nullptr`) — это не панацея, но ловит часть double free.
3. **RAII вместо ручного `delete`.** Деструктор освобождает ресурс автоматически, в том числе при исключениях:

```cpp
{
    std::unique_ptr<int> p = std::make_unique<int>(42); // освободит сам
} // delete здесь, даже при throw
```

`std::unique_ptr` — zero-overhead замена владеющему сырому указателю; `std::shared_ptr` — разделяемое владение со счётчиком; `std::weak_ptr` — наблюдение без владения (разрывает циклы). `std::vector`/`std::string` снимают необходимость в `new[]` почти всегда.

4. **Сырой указатель оставляйте для наблюдения** (`T*` как «может быть null, не владеет»), для реализации самих умных указателей и контейнеров, для C‑API и для необязательных параметров. В интерфейсах полезно документировать: `// не владеет, может быть nullptr`.
5. **`nullptr`, а не `NULL` и не `0`** — типизированно и однозначно в перегрузках.
6. **Проверяйте арифметику и границы**, используйте `std::span`/итераторы, где возможно.
7. **Инструменты**: санитайзеры (`-fsanitize=address,undefined`), Valgrind, `_GLIBCXX_DEBUG`, статические анализаторы — они ловят именно те ошибки, которые компилятор по определению не обязан ловить.
8. **Правило трёх/пяти**: если класс владеет сырым ресурсом, ему нужны согласованные деструктор, копирующий/перемещающий конструктор и присваивание — иначе двойное освобождение или утечки при копировании.

## 7. Итог

Сырой указатель — это адрес плюс тип, но без информации о владении и времени жизни. Ручное управление памятью (`malloc`/`free`, `new`/`delete`, placement new) даёт полный контроль над размещением и освобождением, но перекладывает на программиста всю ответственность за парность операций, выравнивание, границы и корректность типов. В терминах сборки: препроцессор подставляет объявления и макросы (включая `NULL`, `__FILE__`, отладочные обёртки над `new`), компилятор проверяет типы и разворачивает `new`/`delete` в вызовы функций, но **не проверяет время жизни** — ошибки здесь относятся к неопределённому поведению, а не к ошибкам компиляции, и линкер лишь связывает символы вроде `operator new`. Поэтому на практике ручное владение сырым указателем сводят к минимуму, а освобождение поручают RAII‑обёрткам и умным указателям.
