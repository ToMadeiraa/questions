# 29. Можно ли использовать exception в конструкторе/деструкторе?

**Коротко:** в конструкторе — **да**, это штатный и рекомендуемый способ сообщить, что объект создать не удалось. В деструкторе — **технически язык это позволяет лишь с оговорками, но на практике нельзя**: исключение, покинувшее деструктор, почти всегда означает `std::terminate`, утечки и частично разрушенный объект.

---

## 1. Исключения в конструкторе

### 1.1. Да, это нормально

Конструктор — обычная функция, и бросать из него исключение — идиоматичный способ сигнализировать об ошибке инициализации:

```cpp
class File {
public:
    explicit File(const std::string& path)
        : f_(std::fopen(path.c_str(), "rb"), &std::fclose)
    {
        if (!f_)
            throw std::runtime_error("cannot open " + path);
        if (std::fseek(f_.get(), 0, SEEK_END) != 0)
            throw std::runtime_error("seek failed in " + path);
    }

private:
    std::unique_ptr<std::FILE, int (*)(std::FILE*)> f_;
};
```

Здесь при любом `throw` объект `File` «не существует», а `unique_ptr` корректно закроет файл.

### 1.2. Что именно происходит при исключении из конструктора

Стандарт (раздел `[except.ctor]`) задаёт такую картину:

1. Объект считается **недостроенным**, и **его собственный деструктор не вызывается**.
2. Уничтожаются только те подобъекты, которые уже полностью сконструированы: базы и члены — в обратном порядке создания (обычная раскрутка стека).
3. Если создание шло через `new`-выражение, память освобождается соответствующей `operator delete` (для массива — с учётом array cookie).
4. При *placement new* память, разумеется, не освобождается — её владелец решает сам.
5. Исключение уходит вызывающему как обычное.

```cpp
struct Base   { ~Base()   { std::puts("~Base");   } };
struct Member { ~Member() { std::puts("~Member"); } };

struct Derived : Base {
    Member m;
    Derived() { throw std::runtime_error("fail"); }
    ~Derived() { std::puts("~Derived"); }
};

try { Derived d; } catch (const std::exception&) {}
// Вывод: ~Member, ~Base.
// ~Derived НЕ вызывается — объект так и не стал Derived.
```

```cpp
try {
    auto* p = new Derived;      // память будет освобождена, ~Derived не зовётся
} catch (const std::exception& e) { /* ... */ }
```

### 1.3. Главная ловушка: «сырые» ресурсы в членах

Поскольку деструктор самого объекта не вызывается, всё, что он должен был освободить, **не освобождается**:

```cpp
// ПЛОХО
class Socket {
public:
    explicit Socket(const char* host, int port)
        : fd_(::socket(AF_INET, SOCK_STREAM, 0))
    {
        if (fd_ == -1)
            throw std::runtime_error("socket()");
        if (::connect(fd_, /*...*/) == -1)
            throw std::runtime_error("connect()");   // fd_ УТЕЧЁТ
    }
    ~Socket() { if (fd_ != -1) ::close(fd_); }
private:
    int fd_;
};
```

При исключении из тела конструктора `~Socket()` не выполнится, и дескриптор останется открытым. Лечится переносом владения в RAII-член (как в примере с `File`) — тогда при раскрутке стека сработает деструктор члена.

### 1.4. Другие подводные камни

- **`this`, «убежавший» из конструктора.** Если конструктор где-то зарегистрировал `this` (в глобальном списке, в колбэке, в другом объекте), а потом бросил, снаружи останется висячий указатель. Не публикуйте `this` до полного завершения конструирования.
- **`noexcept`-конструкторы.** Если конструктор объявлен `noexcept` (или неявно таков, например defaulted move-конструктор при `noexcept`-членах), исключение приведёт к `std::terminate`, а не к нормальной обработке.
- **Function-try-block.** Обработчик конструктора не может «проглотить» исключение: если управление доходит до конца обработчика, исключение бросается заново. Кроме того, внутри обработчика недоступны члены и базы — объект ещё не построен.

```cpp
Widget::Widget(int x) try : base_(x), m_(x)
{
    // ...
}
catch (const std::exception& e)
{
    log(e.what());
    throw;          // обязательно; либо throw что-то другое
}
```

- **Наследование.** Если бросила база, члены производного ещё не создавались — уничтожатся только уже построенные подобъекты.
- **Массивы.** При `new T[n]` уже созданные элементы уничтожаются, память массива освобождается.

### 1.5. Альтернативы броску из конструктора

- Фабрика, возвращающая `std::optional<T>`, `std::unique_ptr<T>` или (C++23) `std::expected<T, E>`.
- Двухфазная инициализация (`init()`) — как правило, хуже: состояние «наполовину готового» объекта и риск забыть проверку.
- Конструктор, принимающий уже готовый ресурс (внедрение зависимости), — ошибки возникают раньше, вне конструктора.

## 2. Исключения в деструкторе

### 2.1. Начиная с C++11 деструктор по умолчанию `noexcept`

Деструктор неявно объявляется `noexcept(true)`, если ни у одной базы/члена нет потенциально бросающего деструктора. Значит, `throw` из него — это `std::terminate`, а не исключение:

```cpp
struct S {
    ~S() { throw std::runtime_error("boom"); }   // ~S() noexcept(true)
};

int main() {
    try { S s; }
    catch (...) { /* сюда НЕ попадём */ }        // std::terminate
}
```

Можно явно разрешить:

```cpp
~S() noexcept(false);
```

Но это почти всегда ошибка — см. ниже.

### 2.2. При раскрутке стека — гарантированный `std::terminate`

Даже с `noexcept(false)`:

```cpp
struct Bad {
    ~Bad() noexcept(false) { throw std::runtime_error("dtor"); }
};

void f() {
    Bad b;
    throw std::runtime_error("main");   // b.~Bad() во время unwinding → terminate
}
```

Правило `[except.terminate]`: если деструктор, вызванный **во время раскрутки стека**, завершается исключением, вызывается `std::terminate`. Причина проста: одновременно обрабатывать два исключения язык не умеет.

### 2.3. Даже без раскрутки это плохо

- Деструктор вызывается **в самый неожиданный момент**: для временного объекта в выражении, для члена другого объекта, для элемента контейнера, для статического/`thread_local` объекта при выходе из программы.
- К моменту вызова деструктора часть подобъектов уже разрушена; исключение оставляет объект в частично уничтоженном состоянии, а оставшиеся ресурсы — неосвобождёнными.
- Стандартная библиотека **рассчитывает на nothrow-деструкторы**. `std::vector`, `std::shared_ptr`, `std::optional`, `std::variant`, `std::thread` и т. п. имеют `noexcept`-деструкторы; бросающий деструктор элемента приводит к `std::terminate` внутри библиотеки.

```cpp
std::vector<Bad> v;
v.clear();          // если ~Bad() бросит — terminate
```

### 2.4. Function-try-block в деструкторе не спасает

```cpp
~S() try {
    throw std::runtime_error("x");
}
catch (...) {
    log();
}                   // исключение всё равно перебрасывается
```

Если управление доходит до конца обработчика function-try-block деструктора, исключение перебрасывается автоматически. А если это происходило при раскрутке — `terminate`.

### 2.5. C++03 vs C++11

- **C++03:** деструктор имел неявную спецификацию `throw()`; исключение, покидающее его, — неопределённое поведение (на практике — `terminate`); при раскрутке — тоже UB/`terminate`.
- **C++11 и новее:** деструктор явно `noexcept(true)` по умолчанию; нарушение — определённый `std::terminate`.

## 3. Что делать вместо `throw` из деструктора

1. **Явный метод завершения:** `close()`, `flush()`, `commit()`, `cancel()`, который может бросать, и который вызывающий обязан вызвать сам.
2. **Деструктор как страховка:** выполняет ту же операцию в nothrow-режиме; при невозможности — логирует, а в действительно катастрофическом случае осознанно вызывает `std::terminate()`/`std::abort()`.
3. **`std::uncaught_exceptions()`** (C++17; старый `std::uncaught_exception()` объявлен deprecated в C++17 и удалён в C++20) — для аккуратных scope guard'ов, которые решают, делать ли откат:

```cpp
class ScopeGuard {
public:
    explicit ScopeGuard(std::function<void()> rollback)
        : rollback_(std::move(rollback))
        , uncaught_(std::uncaught_exceptions()) {}

    ~ScopeGuard() noexcept(false) {
        if (std::uncaught_exceptions() > uncaught_)
            rollback_();        // rollback_ ОБЯЗАН быть nothrow
    }
private:
    std::function<void()> rollback_;
    int uncaught_;
};
```

Важно: сам `rollback_` всё равно не должен бросать — иначе мы вернёмся к `terminate` при раскрутке.

4. **`std::thread`** иллюстрирует тот же принцип: его деструктор не бросает, а вызывает `std::terminate()`, если поток остался joinable.

## 4. Сводная таблица

| Свойство | Конструктор | Деструктор |
|---|---|---|
| Разрешено языком | Да | Формально да, только с `noexcept(false)` |
| Вызывается деструктор самого объекта | **Нет** | — |
| Уничтожаются уже созданные подобъекты | Да | — |
| Освобождается память `new`-выражения | Да | — |
| Рекомендуется на практике | **Да** (RAII) | **Нет** |
| Поведение при раскрутке стека | Нормальное | `std::terminate` |
| Спецификация по умолчанию | Не `noexcept` (кроме defaulted/явных) | `noexcept(true)` с C++11 |
| Типичные последствия `throw` | Объекта нет; ресурсы членов освобождены | `terminate`, утечки, частичное разрушение |

---

## 5. Итог: практические правила

- **Бросайте из конструктора** — это правильный способ сказать «объект создать не удалось».
- Держите ресурсы в **RAII-членах**, а не в сырых указателях/дескрипторах: тогда исключение из конструктора ничего не утечёт, ведь деструктор самого объекта не вызывается.
- **Не выпускайте `this`** из конструктора до его завершения.
- **Деструкторы делайте `noexcept`.** Всё, что может бросить, выносите в явный `close()`/`flush()`/`commit()`.
- Помните: с C++11 `throw` из деструктора без `noexcept(false)` — это сразу `std::terminate`, а с `noexcept(false)` — всё равно `std::terminate`, если деструктор вызван при раскрутке стека.
- `std::uncaught_exceptions()` — инструмент для очень узкого класса задач (scope guard), а не разрешение бросать из деструктора.
