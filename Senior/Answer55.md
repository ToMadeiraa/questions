# 55. В чем разница между kernel-level и user-level потоками?

## Краткий ответ

Разница прежде всего в том, **кто управляет потоком и знает о его существовании**:

- **Kernel-level thread (native thread, поток уровня ядра)** — поток, который создаётся, планируется и переключается **ядром операционной системы**. Ядро ведёт для него отдельную структуру (TCB), отдельный стек ядра и рассматривает его как самостоятельную единицу планирования. Такой поток может выполняться на другом ядре CPU одновременно с остальными, а его блокировка в системном вызове не останавливает остальные потоки процесса.
- **User-level thread (green thread, поток уровня пользователя)** — поток, который реализован **целиком в библиотеке в пространстве пользователя**. Ядро о нём ничего не знает: для него существует только один (или несколько) «настоящих» потоков процесса. Библиотека сама хранит контексты, сама решает, какой поток запустить следующим, и сама выполняет переключение, не входя в ядро.

Ключевая формула: **kernel-level поток — единица планирования для ОС; user-level поток — единица планирования для библиотеки (runtime)**.

---

## Терминология и важное уточнение

Слова «user-level» не означают, что у потока нет пользовательского стека. Пользовательский стек есть у обоих. Различие в том, **кто принимает решение о переключении и кто владеет состоянием планирования**:

- у kernel-level потока состояние планирования (приоритет, состояние ready/running/blocked, регистры) хранится в ядре;
- у user-level потока оно хранится в структуре данных библиотеки в куче/статической памяти процесса.

Также стоит разделять **API и реализацию**. `pthreads` — это API POSIX, а не модель. На Linux `pthread_create` в glibc (NPTL) создаёт kernel-level поток через `clone()`, на других системах исторически существовали реализации поверх user-level потоков. Аналогично `std::thread` в C++ — это абстракция стандарта, и стандарт **не требует**, чтобы она отображалась в native-поток, хотя на всех мейнстримных платформах (Linux, Windows, macOS) это именно так.

## Три классические модели отображения

| Модель | Схема | Примеры | Свойства |
|---|---|---|---|
| **Многие к одному (N:1)** | N user-level потоков → 1 kernel-level поток | старые «green threads» Java, GNU Pth, ранние реализации | Очень дешёвые переключения и создание, но **нет параллелизма**; блокирующий syscall останавливает весь процесс |
| **Один к одному (1:1)** | 1 user-level поток → 1 kernel-level поток | Linux NPTL, Windows threads, macOS pthreads | Настоящий параллелизм, изоляция блокировок, но дороже создание/переключение и ограничение по числу потоков |
| **Многие ко многим (M:N)** | M user-level потоков → N kernel-level потоков | Go runtime (горутины), Java virtual threads (Loom), Erlang, исторически Solaris LWP и FreeBSD KSE | Комбинация: миллионы лёгких задач на пуле native-потоков, но сложная реализация (нужен собственный планировщик, перехват блокирующих вызовов) |

Историческая ремарка: «чистый» M:N в ОС (Solaris, FreeBSD KSE, scheduler activations) оказался очень сложным и в итоге был вытеснен моделью 1:1, а M:N вернулся уже **внутри runtime** (Go, Loom, Erlang), где библиотека сама управляет пулом native-потоков и неблокирующим I/O.

## Подробное сравнение

| Критерий | Kernel-level | User-level |
|---|---|---|
| Кто знает о потоке | Ядро ОС | Только библиотека |
| Кто планирует | Планировщик ядра (CFS и т.п.) | Планировщик библиотеки |
| Единица планирования ОС | Сам поток | Процесс (или пул native-потоков в M:N) |
| Параллелизм на многоядерном CPU | Да | В чистом N:1 — нет; в M:N — да, через пул native-потоков |
| Создание | Системный вызов (`clone`, `CreateThread`), структуры и стек ядра | Выделение стека и TCB в user space, часто без syscall |
| Стоимость создания | Порядка единиц–десятков микросекунд | Порядка сотен наносекунд – единиц микросекунд |
| Переключение контекста | Через ядро: сохранение/восстановление состояния, переход в режим ядра и обратно; ~1–5 мкс | Целиком в user space: сохранить регистры и `rsp`, загрузить чужие; ~десятки–сотни нс |
| Вытеснение | Принудительное, по таймеру | Обычно кооперативное (поток сам отдаёт управление); принудительное — только если runtime использует сигналы/таймеры |
| Блокирующий syscall (`read`, `futex`, page fault) | Блокирует только этот поток, остальные потоки процесса продолжают работу | В N:1 блокирует **весь процесс**; нужно переписывать вызовы на неблокирующие + `epoll`/`io_uring` или перехватывать их в runtime |
| Приоритеты | Приоритеты ОС (`nice`, приоритеты Windows) | Только внутренние приоритеты runtime, ядру не видны |
| Сигналы | Доставляются конкретному потоку; нужна маска (`pthread_sigmask`) | Обрабатываются процессом на единственном kernel-потоке; обработчик видит «весь процесс» |
| `thread_local` / TLS | Нативный TLS (регистр `%fs`/`%gs`) | Приходится эмулировать: TLS принадлежит native-потоку, а не логическому |
| Учёт CPU-времени | `CLOCK_THREAD_CPUTIME_ID`, `perf`, `top -H` видят каждый поток | Ядро видит только процесс/пул; per-thread учёт — внутри runtime |
| Отладка и профилирование | `gdb` показывает потоки (`info threads`), работают thread-sanitizer, `perf` | Ядро и обычные инструменты видят один поток; нужна поддержка runtime |
| Память | Стек ядра (обычно 8–16 КБ) + структуры ядра + пользовательский стек | Пользовательский стек (часто 4–64 КБ у green threads) + TCB; ядро памяти не тратит |
| Масштабируемость по количеству | Тысячи–десятки тысяч (упирается в память и планировщик) | Миллионы лёгких задач (особенно при сегментированных/растущих стеках) |
| Изоляция сбоев | Общее адресное пространство: падение потока = падение процесса | То же самое; но переполнение стека user-level потока может испортить кучу |
| Переносимость | Зависит от ОС | Библиотека переносима туда, где есть хоть какой-то механизм переключения контекста |

Несколько пояснений к таблице.

**Стоимость переключения.** Переключение kernel-level потоков внутри одного процесса дешевле переключения процессов (не нужно менять адресное пространство и сбрасывать TLB), но всё равно требует перехода в режим ядра, работы планировщика и возврата. User-level переключение — это по сути `save registers; swap stack pointer; restore registers`, поэтому оно на порядки дешевле и не требует syscall. Именно поэтому green threads выгодны для огромного числа коротких задач.

**Блокировки — главный практический водораздел.** В модели 1:1, если поток заблокировался на `read()` или на мьютексе, ядро просто запускает другой поток. В модели N:1 блокировка одного логического потока останавливает весь процесс, потому что у ядра нет другого потока, которому можно отдать CPU. Поэтому runtime green threads вынужден либо использовать неблокирующий I/O и event loop, либо перехватывать (wrap) блокирующие вызовы и превращать их в асинхронные. То же касается page fault: обращение к отсутствующей странице в user-level потоке «замораживает» все потоки процесса.

**Параллелизм vs конкурентность.** User-level потоки в модели N:1 дают **конкурентность** (concurrency) — иллюзию одновременного выполнения, — но не **параллелизм** (parallelism). Чтобы получить параллелизм, нужен либо 1:1, либо M:N с пулом native-потоков.

**Вытеснение.** Kernel-level поток вытесняется таймерным прерыванием: даже бесконечный цикл без yield не захватит CPU навсегда. User-level поток по умолчанию кооперативен: если он не вызовет `yield`/точку переключения, остальные потоки не получат управления. Некоторые runtime решают это периодическими сигналами (`SIGVTALRM`, `setitimer`) или инструментированием кода.

**Сигналы и отмена.** В Linux сигнал доставляется процессу, а ядро выбирает, какому именно потоку его передать; поэтому в многопоточной программе обычно маскируют сигналы во всех потоках, кроме одного. Для user-level потоков «поток» с точки зрения сигналов один, и асинхронный обработчик может прервать любой логический поток в произвольной точке — это усложняет написание signal-safe кода. Аналогично `pthread_cancel` работает с native-потоками, а для green threads нужна кооперативная отмена в точках переключения.

## Как это выглядит в C/C++

**Native-потоки (1:1).** `pthread_create` на Linux/glibc (NPTL) и `std::thread`/`std::jthread`/`std::async` на мейнстримных платформах создают kernel-level потоки. Отсюда практические свойства: `std::thread::hardware_concurrency()` имеет смысл, `thread_local` работает нативно, блокирующий `std::mutex`/`condition_variable` (через `futex`) блокирует только один поток, а `std::this_thread::yield()` — это подсказка планировщику ядра.

**User-level потоки и файберы.** Это библиотеки поверх пользовательского переключения контекста:

```c
// Псевдокод: суть переключения user-level потоков
void switch_to(thread_t *next) {
    save_context(current);   // регистры, rsp, rip
    current = next;
    restore_context(next);   // продолжаем выполнение в next
}
```

Механизмы: `ucontext` (`makecontext`/`swapcontext`), `setjmp`/`longjmp`, Boost.Context/Boost.Fiber, libaco, libco и т.п. Переключение происходит без syscall, но стек каждого потока нужно выделить заранее.

**C++20 корутины — это не user-level потоки в строгом смысле.** Они stackless: у корутины нет собственного стека и нет независимого планировщика; она приостанавливается и возобновляется явно, а решение «когда возобновить» принимает внешний код (event loop, runtime). Корутины — удобный строительный материал для user-level конкурентности, но сами по себе они не являются потоками.

**M:N runtime.** Go-горутины, Java virtual threads, Erlang-процессы — это user-level потоки, мультиплексированные на пул native-потоков, с собственным планировщиком и netpoller'ом. В C++ аналогом по духу являются task-based библиотеки (TBB, Taskflow), но там именно **задачи**, а не потоки: пул native-потоков один, а задачи планируются поверх него.

## Практические следствия

1. **Нужен реальный параллелизм для CPU-bound кода** — берите native-потоки (`std::thread`, пулы, OpenMP, TBB). User-level потоки в N:1 не дадут ускорения на многоядерном CPU.
2. **Очень много одновременных I/O-задач (десятки тысяч соединений)** — native-потоки возможны, но дороги по памяти (стек по умолчанию ~8 МБ виртуальной памяти на поток, хотя её можно уменьшить) и по переключениям. Здесь выигрывают event loop + корутины или M:N runtime.
3. **Блокирующий legacy-код** — при использовании green threads его нельзя просто «навесить» на runtime: блокирующий вызов остановит весь процесс. Нужны неблокирующие аналоги или отдельный пул native-потоков.
4. **Отладка и профилирование** — с native-потоками работают стандартные инструменты (`gdb`, `perf`, TSan, `top -H`). С user-level потоками нужна поддержка со стороны runtime, иначе вы увидите один поток.
5. **Переносимость и стоимость** — user-level переключения дешевле, но реализация сложнее; native-потоки проще и предсказуемее, но дороже в масштабе.

## Типичные заблуждения

- «User-level поток — это поток без стека». Нет, стек есть; вопрос в том, кто им управляет и кто переключает контекст.
- «`std::thread` обязан быть native-потоком». Стандарт C++ этого не требует, хотя на практике это так.
- «User-level потоки всегда быстрее». Быстрее переключаются и создаются, но при блокирующих вызовах и отсутствии параллелизма могут быть медленнее по итоговой производительности.
- «Kernel-level потоки не имеют пользовательского стека». Имеют; у них есть и пользовательский стек, и отдельный стек ядра.
- «M:N — это всегда лучше». Это компромисс: сложность runtime, отладки и взаимодействия с блокирующим кодом.

---

## Итог

Kernel-level и user-level потоки различаются **уровнем, на котором принимается решение о планировании**. Ядро знает о native-потоках и может запускать их параллельно, вытеснять по таймеру и изолировать блокировки — ценой syscall'ов и памяти на каждый поток. User-level потоки живут внутри библиотеки, переключаются на порядки дешевле и позволяют иметь миллионы задач, но в чистом виде не дают параллелизма и требуют неблокирующего I/O и кооперативного планирования. Современные C++-практики обычно используют native-потоки (`std::thread`) для параллелизма и корутины/файберы или M:N runtime — для массовой конкурентности.
