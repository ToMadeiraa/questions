# 24. Проект медленно собирается. Как можно ускорить?

Сборка C++-проекта — это конвейер: **препроцессинг → лексический/синтаксический разбор → семантический анализ → генерация кода → компоновка**. Ускорять надо тот этап, который доминирует, поэтому сначала — измерение, потом — оптимизация. Но есть и общая закономерность: львиная доля времени почти всегда уходит на **повторный препроцессинг и повторный разбор одних и тех же заголовков в каждой единице трансляции (TU)**. Отсюда и главные рычаги: сократить объём включаемого текста, кэшировать результат разбора, распараллелить и не делать лишней работы.

---

## 1. Сначала измерить, где именно теряется время

| Инструмент | Что показывает |
|---|---|
| `gcc -ftime-report` | время по фазам GCC: preprocessing, parsing, template instantiation, optimization, codegen |
| `clang -ftime-trace` | JSON-трейс, открывается в `chrome://tracing` или `ClangBuildAnalyzer`; видно каждый заголовок, каждую инстанциацию шаблона |
| `clang -H` / `gcc -H` | дерево включённых заголовков и их вложенность |
| `clang -E file.cpp \| wc -l` | сколько строк «раздувается» TU после препроцессора (часто сотни тысяч) |
| MSVC: `/Bt+`, `/d1reportTime`, `vcperf` + WPA | время по файлам/фазам, работа с PCH и линковкой |
| `ninja -d explain`, `ninja -t deps`, `ninja -t graph` | почему пересобирается файл, кто от кого зависит |
| `ccache -s`, `sccache --show-stats` | hit rate кэша |
| `clang-tidy`/`IWYU` (анализ, не сборка) | лишние и транзитивные включения |

Полезный приём: сравнить «холодную» сборку (`ninja clean && time ninja`) с инкрементальной после правки одного `.cpp` и после правки одного популярного заголовка. Это сразу покажет, проблема в полной сборке, в инкрементальной или в компоновке.

---

## 2. Сократить работу препроцессора — самый большой выигрыш

Препроцессор — это текстовый этап: он **заново читает и разворачивает все заголовки в каждом TU**. Include-guards и `#pragma once` экономят только повторный разбор тела файла, но файл всё равно открывается, читается и сканируется. Поэтому:

- **Include what you use.** Не подключайте «на всякий случай»; в `.h` — минимум необходимого, остальное — в `.cpp`.
- **Forward declaration вместо `#include`**, если нужен только указатель/ссылка/параметр по значению в объявлении. (Нельзя forward-declare типы из `std` — это UB; для потоков есть `<iosfwd>`.)
- **Убрать «зонтичные» заголовки** (`common.h`, `all.h`, `stdafx.h` в каждом файле), которые тянут полпроекта.
- **Не использовать `<bits/stdc++.h>`** — это GCC-специфичный монстр на десятки тысяч строк.
- **Тяжёлые заголовки — в `.cpp`, а не в `.h`**: `<iostream>`, `<regex>`, `<filesystem>`, `<thread>`, `<boost/*>`, `<windows.h>`, Qt-заголовки. Вместо `<iostream>` в заголовке — `<iosfwd>` и `<cstdio>`.
- **Разорвать циклы включений** и уменьшить глубину графа: чем «глубже» заголовок, тем больше TU его перечитывают.
- **Делать заголовки самодостаточными** (каждый `.h` компилируется отдельно) — это не ускоряет напрямую, но убирает «случайные» зависимости, из-за которых правка любого файла пересобирает всё.
- **Pimpl / type erasure / стабильные интерфейсы**: изменение приватного поля не должно менять заголовок, который видят сотни TU.
- **Header-only библиотеки** (Catch2, gtest, Boost.Spirit, nlohmann/json) стоят дорого в каждом TU. Для тяжёлых шаблонных библиотек — PCH, `extern template`, явная инстанциация в `.cpp` или вынос в отдельную библиотеку с thin-обёрткой.
- **Диагностика**: `-H` и `-ftime-trace` покажут, какой один заголовок съедает 30–50 % времени; часто это `boost/preprocessor`, `boost/spirit`, `nlohmann/json` или сгенерированный `*_pb.h`.

## 3. Три уровня повторного использования результата

Полезно держать в голове такую схему:

1. **Кэш целой компиляции** — `ccache`/`sccache`: повторный TU с тем же препроцессированным текстом (и теми же флагами) берётся из кэша. Даёт огромный выигрыш при переключении веток, `git rebase`, пересборке после `clean`.
2. **Кэш заголовка** — Precompiled Header (PCH): сериализованное состояние препроцессора + разобранный AST для набора заголовков, которые подключаются в начало каждого TU.
3. **Кэш модуля** — C++20 modules: `import` вместо `#include`, интерфейс компилируется один раз, импорт не требует ни препроцессинга, ни повторного парсинга.

### ccache / sccache

```bash
export CCACHE_DIR=/fast/nvme/ccache
export CCACHE_BASEDIR=$PWD
export CCACHE_SLOPPINESS=time_macros,include_file_mtime,include_file_ctime,pch_defines
ccache -s          # смотреть hit rate
```

- Для CMake: `-DCMAKE_CXX_COMPILER_LAUNCHER=ccache` (или `sccache`, который умеет и MSVC, и распределённый кэш).
- Уберите из кода `__DATE__`/`__TIME__` или переопределите их (`-D__DATE__="..."`), иначе кэш будет промахиваться.
- `-fdebug-prefix-map`/`-ffile-prefix-map` и `hash_dir = false` улучшают переиспользование между разными путями.
- Кэш должен лежать на быстром локальном SSD, а не на сетевой шаре.

### Precompiled headers

Идея: один раз разобрать тяжёлые и стабильные заголовки, потом подгружать готовое состояние. Выигрыш особенно велик для `<vector>`, `<string>`, `<iostream>`, `<memory>`, `<algorithm>`, Boost, Qt, `windows.h`.

```cpp
// pch.hpp
#pragma once
#include <vector>
#include <string>
#include <memory>
#include <unordered_map>
```

```bash
# GCC: PCH ищется рядом как pch.hpp.gch
g++ -std=c++20 -O2 -x c++-header pch.hpp -o pch.hpp.gch
g++ -std=c++20 -O2 -include pch.hpp main.cpp   # PCH подхватится автоматически
```

```cmake
# CMake 3.16+: переносимый способ
target_precompile_headers(app PRIVATE
    <vector> <string> <memory>
    "src/pch.hpp"
)
```

Правила и подводные камни:
- **PCH должен подключаться первым** и быть одинаковым для всех TU; флаги компиляции должны совпадать, иначе PCH молча игнорируется (`-Winvalid-pch` у Clang помогает это заметить).
- Обычно **один PCH на проект/группу файлов** (GCC — один PCH на компиляцию; MSVC — `/Yc` создаёт, `/Yu` использует, один общий `pch.h`).
- PCH **маскирует забытые include** — новый разработчик на другой машине может получить ошибку; лечится дисциплиной и `-Winvalid-pch`.
- PCH **не помогает инкрементальной сборке** после правки самого PCH — он пересоберётся и потянет всё.
- С `ccache` PCH дружит, но требует настроек sloppiness (см. выше) и не всегда даёт выигрыш — проверяйте на своём проекте.

### C++20 modules

`import std;` (или `import <vector>;` как header unit) заменяет текстовое включение на импорт бинарного интерфейса:

```cpp
// math.cppm
export module math;
export int add(int a, int b) { return a + b; }

// main.cpp
import math;
import std;      // вместо десятка #include
int main() { return add(1, 2); }
```

Что даёт:
- **нет повторного препроцессинга** и повторного разбора интерфейса в каждом TU;
- **изоляция макросов** — `#define` из модуля не «протекает» в импортёр;
- лучшая масштабируемость: интерфейс компилируется один раз, BMI переиспользуется;
- ускоряется и параллельная сборка (меньше зависимости от порядка include).

Ограничения: поддержка различается (MSVC — наиболее зрелая, Clang/GCC — с ограничениями), сборка модулей требует явного управления порядком (CMake 3.28+ `FILE_SET CXX_MODULES`, `import std` в MSVC 17.6+), а старые библиотеки придётся оборачивать в header units. Тем не менее это стратегически главное направление для больших проектов.

## 4. Параллелизм и распределённая сборка

- **`-j N`** по числу физических ядер (не потоков); при нехватке RAM начинается своп и сборка *замедляется* — `-j` надо подбирать под память (тяжёлые шаблонные TU легко съедают 1–2 ГБ).
- **Ninja вместо Make**: лучше планирует, меньше накладных расходов, точнее инкрементальность. `cmake -G Ninja`.
- **`distcc` / `icecc`** — размазывание компиляции по сети (нужны одинаковые компилятор и окружение).
- **`Incredibuild`** — коммерческое решение для Windows, умеет и компиляцию, и линковку.
- **Bazel / Buck2 с remote cache/execution** — если проект готов к этому архитектурно; в CI даёт кратный выигрыш.
- **Unity build (jumbo)**: несколько `.cpp` склеиваются в один TU — экономит фиксированные накладные расходы на TU и повторный разбор общих заголовков.

```cmake
set_target_properties(app PROPERTIES UNITY_BUILD ON)
set_target_properties(app PROPERTIES UNITY_BUILD_BATCH_SIZE 8)
```

Минусы unity: падение инкрементальности (правка одного файла пересобирает весь батч), конфликты `static`/анонимных namespace, `using namespace`, макросов, ODR-нарушения. Иногда наоборот полезно **разбить гигантский TU на несколько**, чтобы получить параллелизм.

## 5. Флаги компилятора, которые чаще всего «съедают» время

| Что | Почему медленно | Что делать в dev-сборке |
|---|---|---|
| `-O3` / `-O2` в повседневной сборке | оптимизация дороже парсинга | `-O0` или `-Og` для отладки, `-O2` — только для релиза/бенчмарков |
| Полный `-g3` | огромный объём debug info, медленная компоновка | `-g1`, `-gz`, `-gsplit-dwarf` |
| `-fvar-tracking` (GCC, при `-g`) | очень дорогой анализ | `-fno-var-tracking -fno-var-tracking-assignments` |
| LTO в отладочной сборке | дорогая межмодульная оптимизация | выключить; в релизе — `-flto=thin` (Clang) |
| Санитайзеры, coverage, `-fprofile-*` | инструментация каждого TU | отдельный конфиг, не в горячем цикле |
| Тяжёлые шаблоны и `constexpr` | инстанцирование и вычисления | `extern template`, явные инстанциации, упрощение метапрограмм, `-fconstexpr-steps` при необходимости |
| `/analyze` (MSVC) | статический анализ поверх компиляции | вынести в отдельный job |

Плюс:

- **`-pipe`** (GCC/Clang) — не писать промежуточные файлы на диск, мелочь, но бесплатная.
- **`-fvisibility=hidden` / `-fvisibility-inlines-hidden`** — меньше символов, быстрее компоновка.
- **`/Zc:inline`** (MSVC) — убирает неиспользуемые inline-функции, заметно ускоряет линковку.
- **`-Wfatal-errors`** — не про скорость сборки, но ускоряет цикл «правишь — проверяешь».
- **`-fsyntax-only`** — для быстрых проверок в CI/IDE, без кодогенерации.

## 6. Компоновка

Линковка часто становится узким местом, особенно с отладочной информацией и LTO.

- **Современный линкер**: `-fuse-ld=lld` (LLVM lld) или `-fuse-ld=mold` — многопоточные и кратно быстрее GNU `ld`; `gold` с `-Wl,--threads`.
- **`-gsplit-dwarf`** + `-Wl,--gdb-index` — вынести debug info из объектников, резко ускорить линковку и уменьшить размер.
- **`-Wl,--no-keep-memory`, `-Wl,--reduce-memory-overheads`** — если не хватает RAM.
- **`-Wl,--icf=all`** (lld) и `/OPT:REF /OPT:ICF` (MSVC) — удаление дубликатов.
- **Инкрементальная линковка** MSVC: `/INCREMENTAL` (по умолчанию в Debug), `/DEBUG:FASTLINK` (или `/Z7` вместо `/Zi`, если FASTLINK не подходит).
- **Меньше статических библиотек-гигантов** в dev-сборке; динамические библиотеки линкуются быстрее.
- Не включайте LTO «на всякий случай»: `-flto` в Debug — почти всегда ошибка.

## 7. Инфраструктура и «внешние» факторы

Их часто недооценивают, а на Windows они могут давать больше, чем все флаги вместе:

- **Антивирус / Windows Defender**: добавьте каталог сборки, каталог `ccache`/`sccache`, `vcpkg`, `%TEMP%` в исключения. Real-time scanning объектных файлов — классическая причина «всё медленно».
- **Диск**: сборка на локальном NVMe, а не на сетевой шаре, OneDrive/Dropbox-папке или HDD. На Linux — `tmpfs` под `obj/` и `ccache`.
- **RAM**: при нехватке начинается своп; уменьшайте `-j`, а не терпите.
- **Пути**: очень длинные и глубокие пути на Windows замедляют файловые операции; короткий путь к билд-каталогу помогает.
- **Версия компилятора**: новые GCC/Clang/MSVC заметно быстрее старых на том же коде.
- **CMake**: используйте Ninja, не делайте `CONFIGURE_DEPENDS` на больших glob-ах, не переконфигурируйте проект без нужды, не собирайте тесты/примеры по умолчанию (`EXCLUDE_FROM_ALL`).
- **Генераторы кода** (protobuf, Qt `moc`, flex/bison, flatbuffers): кэшируйте результаты и запускайте только при изменении входных файлов; `moc` в сотнях файлов — заметная статья расходов.
- **Правильные depfiles** (`-MMD -MP`) и точные зависимости: лишние пересборки — такая же проблема, как медленная компиляция.

## 8. Архитектурные меры (дают эффект вдолгую)

- **Разбиение на библиотеки/модули с узкими интерфейсами**: правка внутренностей не должна пересобирать полпроекта.
- **Стабильные публичные заголовки**, Pimpl, непрозрачные указатели, type erasure — меньше зависимостей по include.
- **Явные инстанциации шаблонов**:

```cpp
// vector_mytype.h
extern template class std::vector<MyType>;

// vector_mytype.cpp
template class std::vector<MyType>;
```

- **Отказ от тяжёлых header-only решений** там, где важна скорость сборки: `<regex>` (печально известен), `std::function` в заголовках, глубокие шаблонные иерархии, рекурсивный `constexpr`/метапрограммирование.
- **Модуляризация** постепенно: начать с обёртки стандартной библиотеки (`import std;` / header units) и самых «горячих» внутренних заголовков.

## 9. Практический чек-лист по приоритету

1. **Замерить**: `-ftime-trace` / `-ftime-report` / `vcperf`, найти топ-10 файлов и топ-10 заголовков.
2. **Включить кэш**: `ccache`/`sccache` + `CMAKE_CXX_COMPILER_LAUNCHER`; проверить hit rate.
3. **Убрать лишние include** (IWYU, `-H`, forward declarations), разорвать зонтичные заголовки.
4. **PCH** для стабильных тяжёлых заголовков (`target_precompile_headers`).
5. **Dev-флаги**: `-O0/-Og`, `-g1`, без LTO, без санитайзеров.
6. **Линкер**: lld/mold, `-gsplit-dwarf`, MSVC `/Zc:inline` + `/DEBUG:FASTLINK`.
7. **Параллелизм**: Ninja, `-j` по числу ядер и по RAM; при необходимости — distcc/icecc/Incredibuild.
8. **Инфраструктура**: исключения антивируса, локальный NVMe, tmpfs, отключить синхронизацию облака для билд-каталога.
9. **Unity build** — точечно, для мелких файлов, с осторожностью.
10. **Стратегически**: модули C++20, разбиение на библиотеки, сокращение шаблонной «тяжёлой» header-only логики.

Главная мысль: препроцессор и парсер выполняют одну и ту же работу в каждом TU, поэтому выигрыш дают не микрооптимизации флагов, а **устранение повторной работы** — меньше включаемого текста, кэш (ccache → PCH → модули), параллелизм и аккуратная архитектура заголовков.
