# 26. Как работают шаблоны?

Сразу уточнение по формулировке: в **C** шаблонов нет вообще — там параметризация достигается макросами, `void*` и `_Generic`. Всё описанное ниже относится к **C++**.

## 1. Суть: параметрический полиморфизм на этапе компиляции

Шаблон (template) — это не функция и не класс, а **описание семейства функций/классов**, параметризованное типами, значениями или другими шаблонами. Компилятор сам «достраивает» конкретную сущность, когда видит её использование с конкретными аргументами. Этот процесс называется **инстанцированием** (instantiation), а результат — **специализацией** (specialization), точнее — неявно сгенерированным экземпляром.

```cpp
template <typename T>
T max(T a, T b) { return a < b ? b : a; }

int   i = max(1, 2);        // T = int    -> компилятор создаёт max<int>
double d = max(1.0, 2.0);   // T = double -> компилятор создаёт max<double>
```

Ключевая мысль: **в рантайме шаблонов не существует**. Есть только сгенерированные обычные функции и классы. Это называют **мономорфизацией**: для каждого набора аргументов появляется отдельный машинный код (в отличие от «стирания типов» — type erasure — в Java/C#, где один код работает с `Object`).

Следствия мономорфизации:

- максимальная скорость: всё разрешается статически, возможен полный инлайнинг, нет виртуальных вызовов и боксинга;
- **раздувание кода** (template bloat): `std::vector<int>` и `std::vector<double>` — совершенно разные, никак не связанные типы;
- время компиляции растёт, ошибки всплывают при инстанцировании.

## 2. Модель компиляции: почему шаблоны живут в заголовках

Компилятору нужно **видеть полное определение** шаблона в каждой единице трансляции, где он используется, — иначе он не сможет его инстанцировать. Поэтому шаблоны обычно определяют прямо в `.h` (или в `.hpp`/`.tpp`, подключаемом из заголовка), а не разносят на `.h` + `.cpp`.

Формально это не нарушает ODR: инстанцированные функции шаблонов неявно **inline** (`[basic.def.odr]`), а одинаковые экземпляры в разных объектных файлах «склеиваются» линкером (COMDAT/weak-секции). Но есть нюанс: если определение шаблона в разных единицах трансляции отличается, получается **IFNDR** (ill-formed, no diagnostic required) — линкер молча выберет один вариант.

Управлять этим можно явно:

```cpp
// Явное инстанцирование — генерация кода здесь и только здесь:
template int max<int>(int, int);

// Запрет неявного инстанцирования в других TU (C++11):
extern template int max<int>(int, int);
```

`extern template` + явное инстанцирование в одном `.cpp` — стандартный приём борьбы с раздуванием кода и временем сборки.

## 3. Виды параметров шаблона

```cpp
// 1) Параметр-тип
template <typename T> struct Box { T value; };

// 2) Параметр-значение (non-type): целые, enum, указатели, ссылки, nullptr,
//    с C++20 — плавающая точка и структурные классы
template <int N> struct Array { int data[N]; };
template <auto N> struct Const { static constexpr auto value = N; };

// 3) Параметр-шаблон (template template parameter)
template <template <typename> class Container> struct Wrapper {};

// 4) Пакет параметров (variadic)
template <typename... Ts> struct Tuple {};

// 5) Параметры по умолчанию
template <typename T, typename Alloc = std::allocator<T>> class vector;
```

Пример с шаблон-шаблонным параметром:

```cpp
template <template <typename, typename> class C, typename T>
void fill(C<T, std::allocator<T>>& c) { /* ... */ }
```

`typename` и `class` в роли параметра-типа **полностью эквивалентны** (`class` остался исторически).

### Вариадические шаблоны и свёртки (C++11/17)

```cpp
template <typename... Ts>
void print(const Ts&... xs) {
    ((std::cout << xs << ' '), ...);   // fold expression, C++17
}

template <typename... Ts>
constexpr auto sum(Ts... xs) { return (xs + ... + 0); }

static_assert(sizeof...(int) == 0);    // sizeof... — число элементов пакета
```

Пакет раскрывается на этапе инстанцирования; рекурсивное «разворачивание» через голову и хвост (`head, tail...`) — классический приём до C++17.

## 4. Вывод аргументов шаблона (deduction)

Для функций компилятор выводит `T` из типов аргументов по правилам сопоставления с образцом:

```cpp
template <typename T> void f(T);        // по значению: array/function decay
template <typename T> void g(T&);       // ссылка: массив остаётся массивом
template <typename T> void h(const T&); // const-ссылка
template <typename T> void k(T&&);      // forwarding reference

int a[3];
f(a);   // T = int*
g(a);   // T = int[3]
k(1);   // T = int,  T&& = int&&
int x = 0;
k(x);   // T = int&, T&& = int& (свёртка ссылок) -> идеальная передача
```

Правила кратко:

- по значению — снимаются `const`/`volatile` и ссылки, массив и функция «decay» до указателя;
- `T&` — выводится точный тип, массив сохраняется, `const` сохраняется;
- `const T&` — принимает всё, включая rvalue, `T` без cv;
- `T&&` в шаблоне — **универсальная (forwarding) ссылка**: для lvalue `T` выводится как `U&`, для rvalue — как `U`; отсюда `std::forward<T>(x)`.

Также аргументы можно указывать явно: `max<double>(1, 2)` — при этом `1` и `2` конвертируются в `double`; смешение `max(1, 2.0)` не выведется (конфликт `T = int` и `T = double`) — нужно два параметра или `std::common_type`.

Для **классов** до C++17 аргументы всегда указывались явно (`std::vector<int> v;`). В C++17 появился **CTAD** — вывод из аргументов конструктора:

```cpp
std::pair p(1, 2.0);            // std::pair<int, double>
std::vector v{1, 2, 3};         // std::vector<int>
```

Плюс **deduction guides** — пользовательские правила вывода, в том числе для своих классов и alias-шаблонов.

## 5. Двухфазный поиск имён и зависимые имена

Это самая «тонкая» часть темы и источник большинства загадочных ошибок.

Шаблон проверяется **дважды**:

1. **В точке определения** — проверяется синтаксис и все **независимые** (non-dependent) имена: они ищутся обычным поиском + ADL *здесь и сейчас*.
2. **В точке инстанцирования** — проверяются **зависимые** (dependent, т.е. зависящие от `T`) имена: для них выполняется ADL в контексте аргументов шаблона.

Из этого следуют синтаксические требования:

```cpp
template <typename T>
void f(T t) {
    typename T::value_type x;      // typename: T::value_type — зависимый тип
    t.template get<int>();         // template: зависимый шаблон-член
    this->base_member();           // члены зависимого базового класса — только через this-> или Base<T>::
}

template <typename T>
struct Derived : Base<T> {
    void g() {
        // Base<T>::foo();   // не найдётся обычным поиском
        this->foo();         // правильно
    }
};
```

Без `typename` компилятор по умолчанию считает `T::value_type` значением/статическим членом, а не типом; без `template` — что `<` это оператор сравнения. Исторически MSVC не реализовывал двухфазный поиск (включается ключом `/permissive-`), из-за чего код, собранный MSVC, мог не собираться на GCC/Clang.

## 6. Специализация: как выбирается нужный вариант

Есть три «уровня»:

```cpp
template <typename T> struct Trait { /* общий случай */ };          // primary
template <>           struct Trait<bool> { /* полная специализация */ };
template <typename T> struct Trait<T*>  { /* частичная специализация */ };
```

- **Полная специализация** (`template<>`) — фиксированы все аргументы.
- **Частичная специализация** (`template<typename T> struct X<T*>`) — фиксирована «форма», часть параметров остаётся.
- Частичная специализация **классов** разрешена, **функций** — нет; для функций вместо неё используют перегрузку.

Порядок выбора для классов: сначала полная специализация, затем частичные (выбирается **наиболее специализированная** по правилам partial ordering), иначе — primary-шаблон.

Для **функций** работает обычное разрешение перегрузок среди всех шаблонов, а среди одинаково подходящих — **partial ordering** (более специализированный шаблон выигрывает):

```cpp
template <typename T> void f(T);     // #1
template <typename T> void f(T*);    // #2 — более специализирован, выигрывает для указателей
```

Важный практический совет: **не специализируйте шаблоны функций полностью** — такая специализация не участвует в выводе аргументов и ведёт себя неинтуитивно; используйте перегрузку или `if constexpr`/concepts.

## 7. Ограничения и диагностика: SFINAE и concepts

Долгое время единственным способом «включить/выключить» шаблон была **SFINAE** (Substitution Failure Is Not An Error): если подстановка аргументов в *непосредственный контекст* сигнатуры даёт недопустимый тип, это не ошибка — перегрузка просто отбрасывается.

```cpp
// Классика: включить перегрузку только для целочисленных типов
template <typename T,
          typename = std::enable_if_t<std::is_integral_v<T>>>
void f(T);

// Или через возвращаемый тип
template <typename T>
std::enable_if_t<std::is_floating_point_v<T>, T> g(T x) { return x; }

// Detection idiom / void_t
template <typename T, typename = void>
struct has_size : std::false_type {};
template <typename T>
struct has_size<T, std::void_t<decltype(std::declval<T>().size())>> : std::true_type {};
```

Начиная с **C++20** для этого есть **концепты** (concepts) и `requires`:

```cpp
template <typename T>
concept Addable = requires(T a, T b) { a + b; };

template <Addable T>
T add(T a, T b) { return a + b; }

// Сокращённая запись (abbreviated function template)
void add(Addable auto a, Addable auto b);

// requires-выражение с проверкой требований
template <typename T>
    requires std::is_integral_v<T> && (sizeof(T) >= 4)
void h(T);
```

Концепты дают три вещи: **раннюю и понятную диагностику** (вместо простыни «no matching function»), **участие в разрешении перегрузок** по степени выполнения ограничений (subsumption — более строгий концепт выигрывает) и **явное выражение требований** к типу вместо «утиной типизации» на уровне тела.

## 8. `if constexpr` и метапрограммирование

До C++17 ветвление по типу делали рекурсией шаблонов и специализациями; теперь часто достаточно `if constexpr` — ветка **отбрасывается** на этапе инстанцирования, и её код даже не проверяется на корректность для данного `T`:

```cpp
template <typename T>
auto serialize(const T& v) {
    if constexpr (std::is_arithmetic_v<T>) {
        return std::to_string(v);
    } else if constexpr (has_to_string_v<T>) {
        return v.to_string();
    } else {
        static_assert(always_false_v<T>, "unsupported type");
    }
}
```

Шаблоны + `constexpr` образуют **метапрограммирование на этапе компиляции**: `std::integral_constant`, `std::tuple`, рекурсивные вычисления, генерация типов. Исторически шаблоны Тьюринг-полны (отсюда лимиты глубины инстанцирования, например `-ftemplate-depth`), но современный код всё чаще заменяет рекурсию на `fold`-выражения и `constexpr`-функции.

## 9. Что важно знать про классовые шаблоны

- **Ленивая инстанцирование членов**: при инстанцировании `std::vector<T>` генерируются только те методы, которые реально вызываются. Поэтому `vector<T>` с типом без `operator<` нормально объявляется, а ошибка возникнет только при вызове `sort`.
- **`std::vector<int>` ≠ `std::vector<const int>` ≠ `std::vector<int*>`** — разные типы без общего базового класса.
- **Шаблонные члены**: `template <typename U> void push(U&&)`; шаблонные конструкторы не бывают копирующими/перемещающими.
- **Шаблонные члены не могут быть `virtual`** — виртуальность требует фиксированного числа специализаций в таблице виртуальных функций. (Виртуальным может быть сам класс-шаблон и его нешаблонные методы.)
- **CRTP** — любопытно рекурсивный шаблон, статический полиморфизм:

```cpp
template <typename Derived>
struct Base {
    void interface() { static_cast<Derived*>(this)->impl(); }
};
struct Impl : Base<Impl> { void impl() { /* ... */ } };
```

- **Traits и `type_traits`** — шаблоны как «вычисления над типами»: `std::is_same`, `std::conditional`, `std::decay`, `std::common_type`.
- **Alias-шаблоны** (`template <typename T> using Vec = std::vector<T>;`) и **переменные-шаблоны** (C++14: `template <typename T> constexpr T pi = ...;`).
- **`friend`-трюки** и ADL позволяют «регистрировать» типы в шаблонных механизмах (например, сериализация, `swap`, `get` для structured bindings).

## 10. Типичные подводные камни

1. **Определение шаблона в `.cpp`** → ошибка линковки `undefined reference` в другом TU.
2. **`T::something` без `typename`**, `t.foo<T>()` без `template` → синтаксические ошибки.
3. **Члены зависимого базового класса** не видны без `this->`.
4. **Полная специализация функции** вместо перегрузки — не участвует в выводе, «не срабатывает».
5. **Специализация после первого использования** → IFNDR (программа формально некорректна, диагностики может не быть).
6. **Разные определения шаблона в разных TU** → нарушение ODR, тихая ошибка линковки.
7. **Раздувание кода и времени сборки**; лечится `extern template`, выносом в `.cpp` для известных типов, `if constexpr`, type erasure.
8. **Утиная типизация**: требования к `T` проверяются только в теле, поэтому ошибки появляются глубоко в стеке инстанцирования — отсюда ценность concepts и `static_assert` с осмысленным сообщением.
9. **Forwarding reference vs rvalue reference**: `T&&` в шаблоне — не то же самое, что `int&&`; перегрузка по `const T&`/`T&&` может «съесть» копирующий конструктор (нужен `std::enable_if`/`requires`).
10. **`export template`** (C++98) не был реализован почти никем и удалён в C++11 — не рассчитывайте на «шаблоны в отдельной TU».

## 11. Сравнение с другими механизмами

| Механизм | Когда разрешается | Проверка типов | Цена |
|---|---|---|---|
| Шаблоны C++ | компиляция (мономорфизация) | после подстановки (concepts — раньше) | код на каждый тип, время сборки |
| Перегрузки | компиляция | строгая, до тела | нет |
| `virtual` | рантайм (vtable) | строгая | косвенный вызов, vtable |
| `void*` + cast (C) | рантайм/вручную | нет | ошибки в рантайме |
| Макросы (C) | препроцессор | нет | нет типовой безопасности |
| Generics Java/C# | рантайм/стирание (Java) | строгая, до тела | бокс/потери, нет примитивов |
| `_Generic` (C11) | компиляция | по типу выражения | только выбор выражения |

Шаблоны — это **статический полиморфизм**: цена переносится на компиляцию, а рантайм получает максимально оптимизированный, «специализированный» код. Именно поэтому контейнеры и алгоритмы STL одновременно и универсальны, и быстры.

## 12. Итог

Шаблон в C++ — это **инструкция компилятору по генерации кода**, а не рантайм-сущность. Компилятор:

1. в точке определения проверяет независимые имена и синтаксис;
2. при использовании **выводит** аргументы (или берёт явные);
3. выполняет **подстановку** и, если нужно, **SFINAE/concepts**-отбор;
4. **инстанцирует** конкретную функцию/класс (мономорфизация);
5. генерирует обычный машинный код, который дальше живёт по общим правилам ODR и линковки.

Понимание этой цепочки — вывода аргументов, двухфазного поиска, специализации и ограничений — и есть практическое «знание шаблонов».
