# 15. Что такое покрытие кода и как обеспечивается?

**Покрытие кода** (code coverage, тестовое покрытие) — это метрика, показывающая, какая часть исходного кода программы была реально выполнена во время прогона тестов. Это метрика «белого ящика»: она оценивает тесты со стороны реализации, а не со стороны требований.

Ключевая формула для покрытия строк:

```
line coverage = (выполненные исполняемые строки / все исполняемые строки) × 100%
```

При этом комментарии, пустые строки, `#include`, объявления без инициализации и прочий неисполняемый код в знаменатель не входят.

Важно сразу разделить два понятия:

- **покрытие кода** — сколько кода исполнено тестами (метрика реализации);
- **покрытие требований** — сколько требований/сценариев проверено (метрика тест-дизайна).

Высокое покрытие кода само по себе не означает, что требования покрыты, и наоборот.

## Виды покрытия

Разные виды покрытия отличаются «строгостью»: чем строже критерий, тем больше тестов нужно.

| Вид покрытия | Что требует | Типичная «дыра», которую пропускает |
|---|---|---|
| Функций (function) | каждая функция вызвана хотя бы раз | функция ни разу не вызывалась |
| Строк / операторов (line, statement) | каждая исполняемая строка выполнена | тело `if` не выполнялось |
| Ветвей / решений (branch, decision) | каждый исход каждого ветвления (`if`, `switch`, цикл, `&&`, `\|\|`) | `if` всегда истинен |
| Условий (condition) | каждое подвыражение булева выражения было и `true`, и `false` | в `a && b` выражение `b` никогда не вычислялось |
| MC/DC | каждое условие независимо влияет на результат решения | не проверена комбинация, где условие меняет итог |
| Путей (path) | все пути исполнения | комбинаторный взрыв, на практике неприменимо |
| Переключателей (switch) | все `case`, включая `default` | ветка `default` не проверена |

Разница между покрытием строк и ветвей хорошо видна на примере:

```cpp
bool inRange(int x) {
    if (x > 0 && x < 10) return true;  // одна строка, но несколько ветвей
    return false;
}
```

Один тест `inRange(5)` даст 100% покрытия строк, но не проверит случаи `x <= 0` и `x >= 10`; покрытие ветвей при этом будет заметно ниже 100%.

**MC/DC** (Modified Condition/Decision Coverage) — самый строгий из практически используемых критериев: каждое условие должно хотя бы один раз independently изменить результат всего решения. Он требуется, например, стандартом DO-178C для критичного по безопасности ПО уровня A.

## Как измеряется покрытие

Общая схема:

1. **Инструментация** — в код или бинарник внедряются счётчики.
2. **Прогон тестов** — счётчики фиксируют, какие блоки/ветви/функции выполнились.
3. **Сбор данных** — счётчики сохраняются в файлы (`.gcda`, `.profraw` и т.п.).
4. **Постобработка** — данные сопоставляются с исходниками, строится отчёт (текстовый, HTML, XML, lcov).

Способы инструментации:

- **Компиляторная** — самая распространённая в C++: GCC `--coverage`, Clang `-fprofile-instr-generate -fcoverage-mapping`. Компилятор сам расставляет счётчики в базовых блоках и на дугах графа потока управления.
- **Бинарная** — инструментируется уже собранный исполняемый файл (OpenCppCoverage, DynamoRIO). Плюс: не нужна пересборка; минус: сложнее и медленнее.
- **Аппаратная/семплирующая** — по сути профилирование, а не точное покрытие строк; для отчётов о покрытии почти не используется.

Отдельно стоит сказать, что **статический** анализ покрытия (без запуска) возможен, но неточен: он не знает, какие ветви реально достижимы.

### GCC / gcov

Флаг `--coverage` эквивалентен паре `-fprofile-arcs -ftest-coverage` и должен передаваться и при компиляции, и при линковке.

- при компиляции создаются файлы `.gcno` — граф потока управления (notes);
- при завершении программы — `.gcda` — накопленные счётчики (data);
- утилита `gcov` объединяет `.gcno`, `.gcda` и исходник и выдаёт аннотированный `.gcov`-файл;
- `lcov`/`genhtml` или `gcovr` собирают всё в HTML/XML и считают проценты.

### Clang / LLVM

```bash
clang++ -fprofile-instr-generate -fcoverage-mapping -O0 -g ...
./tests                     # создаёт default.profraw
llvm-profdata merge -sparse default.profraw -o default.profdata
llvm-cov report ./tests -instr-profile=default.profdata
llvm-cov show   ./tests -instr-profile=default.profdata --format=html > coverage.html
```

`llvm-cov` умеет экспортировать и в формат lcov (`-format=lcov`), что удобно для интеграции с CI.

### MSVC / Visual Studio

- Visual Studio Enterprise: `Test → Analyze Code Coverage`;
- `vstest.console.exe /EnableCodeCoverage`;
- в Community-версии часто используют OpenCppCoverage:
  ```bat
  OpenCppCoverage.exe --sources MyProject -- .\build\tests.exe
  ```
- для подготовки бинарника к покрытию используется линкерный ключ `/PROFILE`.

### Сводка инструментов

| Инструмент | Экосистема | Назначение |
|---|---|---|
| `gcov` | GCC | аннотированные исходники, базовые проценты |
| `lcov` + `genhtml` | GCC/Clang | сбор и HTML-отчёт |
| `gcovr` | GCC/Clang | HTML/XML/Cobertura, пороги в CI |
| `llvm-cov`, `llvm-profdata` | Clang/LLVM | покрытие в стиле LLVM |
| OpenCppCoverage | Windows/MSVC | покрытие без пересборки |
| Codecov, Coveralls, SonarQube | CI | хранение истории, дифф-покрытие, quality gates |

## Практический пример: CMake + GoogleTest + gcovr

`calc.h`:

```cpp
#pragma once

int divide(int a, int b);
```

`calc.cpp`:

```cpp
#include "calc.h"
#include <stdexcept>

int divide(int a, int b) {
    if (b == 0) {
        throw std::invalid_argument("division by zero");
    }
    return a / b;
}
```

`tests.cpp`:

```cpp
#include <gtest/gtest.h>
#include "calc.h"

TEST(Calc, DividesPositive) {
    EXPECT_EQ(divide(6, 3), 2);
}

TEST(Calc, ThrowsOnZero) {
    EXPECT_THROW(divide(1, 0), std::invalid_argument);
}
```

`CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.16)
project(coverage_demo CXX)

set(CMAKE_CXX_STANDARD 17)

option(ENABLE_COVERAGE "Enable coverage instrumentation" OFF)
if(ENABLE_COVERAGE)
    add_compile_options(--coverage -O0 -g)
    add_link_options(--coverage)
endif()

add_library(calc calc.cpp)
target_include_directories(calc PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

enable_testing()
find_package(GTest REQUIRED)

add_executable(calc_tests tests.cpp)
target_link_libraries(calc_tests PRIVATE calc GTest::gtest_main)

include(GoogleTest)
gtest_discover_tests(calc_tests)
```

Сборка, тесты и отчёт:

```bash
cmake -S . -B build -DENABLE_COVERAGE=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
ctest --test-dir build --output-on-failure

gcovr --root . --filter . --html-details build/coverage.html \
      --fail-under-line 80 --fail-under-branch 70
```

Альтернатива через lcov:

```bash
lcov --capture --directory build --output-file coverage.info
lcov --remove coverage.info '/usr/*' '*/tests/*' --output-file coverage.info
genhtml coverage.info --output-directory coverage_html
```

## Как читать отчёт

Пример аннотированного вывода `gcov` для `calc.cpp`:

```
        -:    0:Source:calc.cpp
        -:    0:Graph:calc.gcno
        -:    0:Data:calc.gcda
        -:    0:Runs:1
        -:    1:#include "calc.h"
        -:    2:#include <stdexcept>
        -:    3:
        2:    4:int divide(int a, int b) {
        2:    5:    if (b == 0) {
        1:    6:        throw std::invalid_argument("division by zero");
        -:    7:    }
        1:    8:    return a / b;
        -:    9:}
```

Как читать колонки:

- первая колонка — сколько раз выполнена строка;
- `-` — строка неисполняемая (директивы, скобки, объявления);
- `#####` — строка ни разу не выполнялась;
- во второй колонке — номер строки, далее исходный текст.

Если бы теста `ThrowsOnZero` не было, строка 6 была бы помечена `#####`, а покрытие ветвей упало бы примерно до 50%: ветвь `b == 0 → true` не проверена.

## Как обеспечивать покрытие в проекте

1. **Отдельная конфигурация сборки.** Инструментация замедляет код и меняет оптимизации, поэтому покрытие снимают в отдельной Debug-сборке (`-O0 -g --coverage`), а не в релизной.
2. **Прогонять все тесты под инструментированной сборкой.** В покрытие попадает всё, что реально исполнялось: unit-, интеграционные и end-to-end тесты. Обычно в CI считают покрытие от unit-тестов, но это зависит от политики команды.
3. **Задавать пороги в CI.** Разумная отправная точка — 70–85% строк и не менее 60–70% ветвей; для нового кода — 80–90%. Важнее не абсолютный процент, а то, что он не падает.
4. **Использовать diff coverage.** Проверять покрытие только изменённых строк в pull request — это гораздо полезнее, чем гнаться за общим процентом в старом проекте.
5. **Исключать из отчёта то, что не имеет смысла покрывать:** тесты, сгенерированный код, сторонние библиотеки, платформенные заглушки, `main()`-обвязку. В `gcovr` это `--exclude`, в `lcov` — `--remove`.
6. **Смотреть не только на цифру, но и на непокрытые места.** Особенно на обработку ошибок, исключения, `default` в `switch`, граничные значения. Именно там чаще всего скрываются баги.
7. **Хранить историю и тренд.** Codecov, Coveralls, SonarQube, встроенные отчёты GitLab/GitHub Actions позволяют видеть динамику и не давать покрытию деградировать.
8. **Комбинировать с другими техниками:** санитайзеры (`-fsanitize=address,undefined`), Valgrind, fuzzing (libFuzzer/AFL++), статический анализ, мутационное тестирование (например, Mull для LLVM). Покрытие показывает, что код *исполнялся*, но не что он *проверялся корректно*.

Пример шага CI (GitHub Actions):

```yaml
- name: Configure
  run: cmake -S . -B build -DENABLE_COVERAGE=ON -DCMAKE_BUILD_TYPE=Debug

- name: Build
  run: cmake --build build -j

- name: Test
  run: ctest --test-dir build --output-on-failure

- name: Coverage
  run: |
    gcovr --root . --filter src/ --xml-pretty -o coverage.xml \
          --fail-under-line 80 --fail-under-branch 70
```

## Ограничения и типичные ошибки

- **100% покрытия ≠ отсутствие багов.** Покрытие измеряет исполнение, а не правильность проверок. Тест может вызвать функцию и ничего не проверить (`EXPECT_TRUE(true)`), а может проверять не то поведение.
- **Покрытие строк завышает картину.** Высокое line coverage при низком branch coverage — классическая ситуация: все строки выполнены, но половина ветвей ни разу не проверена.
- **Оптимизации искажают отчёт.** При `-O2` код встраивается, мёртвый код удаляется, ветви перестраиваются. Для покрытия нужна предсказуемая сборка `-O0 -g`.
- **Исключения и аварийные пути часто остаются непокрытыми.** `throw`, `catch`, `std::terminate`, `assert` — типичные «серые зоны»; современный gcov помечает такие пути отдельно, но не все инструменты это учитывают.
- **Шаблоны и header-only код дублируются.** Каждая инстанциация считается отдельно, а заголовочный код может попадать в отчёт из разных единиц трансляции. Помогают `-fprofile-abs-path` (GCC) и корректная настройка `gcovr`/`lcov`.
- **Многопоточность.** Счётчики gcov не атомарны, поэтому точные значения в многопоточной программе могут «плыть»; факт выполнения (0 или больше) обычно сохраняется, но на точные цифры лучше не полагаться.
- **Долгоживущие процессы.** Для демонов и сервисов `.gcda` может не записаться при завершении — нужен явный `__gcov_dump()` (или `__gcov_flush()` в старых GCC) по сигналу, а также переменные `GCOV_PREFIX`/`GCOV_PREFIX_STRIP` для управления путями.
- **Покрытие не заменяет тест-дизайн.** 100% покрытия достигается и тестами, которые не проверяют граничные случаи, конкурентность, переполнения и обработку ошибок.

## Итог

Покрытие кода — это измеримая метрика того, насколько полно тесты исполняют программу. В C++ её получают через компиляторную инструментацию (GCC `--coverage` + `gcov`/`lcov`/`gcovr`, Clang `llvm-cov`, MSVC/OpenCppCoverage), собирают данные в отдельной Debug-сборке, строят отчёты и контролируют пороги в CI. Обеспечить покрытие — значит регулярно прогонять тесты под инструментацией, следить за покрытием ветвей, разбирать непокрытые участки и использовать покрытие вместе с санитайзерами, статическим анализом и мутационным тестированием, а не как самоцель.
