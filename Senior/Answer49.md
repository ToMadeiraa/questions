# 49. Что такое статический и динамический полиморфизмы?

**Полиморфизм** — это свойство системы позволять единому интерфейсу (имени, выражению, вызову) работать с объектами разных типов, причём конкретная реализация выбирается либо **на этапе компиляции**, либо **во время выполнения**. Именно момент выбора и разделяет полиморфизм на статический и динамический.

В классификации Карделли–Вегнера (Cardelli, Wegner) выделяют четыре вида полиморфизма:

| Вид | Механизм в C++ | Когда выбирается |
|---|---|---|
| Ad-hoc (перегрузка) | overloading функций/операторов | компиляция |
| Параметрический | шаблоны (templates), concepts | компиляция |
| Включения (subtyping) | виртуальные функции | выполнение |
| Приведения (coercion) | неявные преобразования типов | компиляция |

Статический полиморфизм покрывает первые два (и отчасти четвёртый), динамический — третий.

---

## 1. Статический (compile-time) полиморфизм

Решение о том, какая функция будет вызвана, принимается компилятором на основе **статических типов** выражений. Никаких дополнительных данных в объекте не хранится, накладных расходов во время выполнения нет.

### 1.1. Перегрузка функций и операторов

```cpp
struct Printer {
    void print(int x)               { std::cout << "int: "    << x << '\n'; }
    void print(double x)            { std::cout << "double: " << x << '\n'; }
    void print(const std::string& s){ std::cout << "string: " << s << '\n'; }
};

Printer p;
p.print(42);        // компилятор выбрал print(int)
p.print(3.14);      // print(double)
p.print("hello");   // print(const std::string&) — через преобразование
```

Компилятор выполняет **разрешение перегрузки** (overload resolution): строит множество кандидатов, отбрасывает неподходящие, ранжирует оставшиеся по точности преобразований. Всё это — чистая работа компилятора, в машинном коде остаётся прямой вызов конкретной функции.

То же самое — перегрузка операторов (`operator+` для `Vector`, `Matrix`, `std::string`): синтаксис один, реализации разные, выбор статический.

> Важная тонкость: перегрузка **не является** полиморфизмом в смысле подтипов. Если функция `void f(Base)` и `void f(Derived)` — вызов `f(d)` для объекта `Derived` выберет `f(Derived)`, но через указатель `Base*` — уже `f(Base)`. Это статическое связывание, а не виртуальный вызов.

### 1.2. Шаблоны (параметрический полиморфизм)

```cpp
template <class T>
T twice(T v) { return v + v; }

twice(21);              // T = int,    инстанцируется twice<int>
twice(1.5);             // T = double, инстанцируется twice<double>
twice(std::string("ab")); // T = std::string — работает, если есть operator+
```

Шаблон — это «фабрика типов»: для каждого набора аргументов компилятор порождает отдельную функцию/класс. Это так называемая **compile-time duck typing**: важно не то, от какого класса унаследован `T`, а то, что для `T` существуют нужные операции.

С C++20 ограничения формализуются через **concepts**:

```cpp
template <class T>
concept Addable = requires(T a, T b) { { a + b } -> std::same_as<T>; };

template <Addable T>
T twice(T v) { return v + v; }
```

Ошибка несоответствия требованиям выдаётся на этапе компиляции с внятным сообщением, а не в недрах инстанцирования.

### 1.3. CRTP — статический аналог виртуальных функций

**Curiously Recurring Template Pattern**: базовый класс параметризован производным и вызывает его методы через `static_cast`, без виртуальной таблицы.

```cpp
template <class Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->areaImpl();
    }
};

struct Circle : Shape<Circle> {
    double r;
    double areaImpl() const { return 3.14159265 * r * r; }
};

struct Square : Shape<Square> {
    double side;
    double areaImpl() const { return side * side; }
};

template <class S>
void printArea(const S& s) { std::cout << s.area() << '\n'; } // мономорфно, инлайнится
```

Здесь `Shape<Circle>` и `Shape<Square>` — **разные типы**, между ними нет отношения наследования в обычном смысле, нет vptr, вызов `areaImpl` разрешается статически и обычно инлайнится. Это основа policy-based design (например, аллокаторы и трейты в STL).

### 1.4. `if constexpr`, `std::variant`, `_Generic`

```cpp
template <class T>
void describe(const T& v) {
    if constexpr (std::is_integral_v<T>)       std::cout << "integer\n";
    else if constexpr (std::is_floating_point_v<T>) std::cout << "float\n";
    else                                        std::cout << "other\n";
}
```

`std::variant` + `std::visit` — интересный гибрид: набор типов **замкнут** и известен компилятору, поэтому `visit` генерирует таблицу переходов (по сути `switch` по индексу), а не виртуальные вызовы. Это «закрытый» полиморфизм с семантикой значения, без кучи и без vptr:

```cpp
using Shape = std::variant<Circle, Square>;
Shape s = Circle{2.0};
double a = std::visit([](const auto& sh){ return sh.area(); }, s);
```

В C аналог статического выбора — `_Generic` (C11) и макросы, но это скорее имитация.

## 2. Динамический (run-time) полиморфизм

Решение о том, какая реализация будет вызвана, принимается **во время выполнения** на основе **динамического типа** объекта, на который указывает ссылка/указатель. В C++ это прежде всего **виртуальные функции**.

### 2.1. Виртуальные функции

```cpp
class Shape {
public:
    virtual double area() const = 0;      // чисто виртуальная — интерфейс
    virtual void   scale(double k) = 0;
    virtual ~Shape() = default;           // КРИТИЧНО: виртуальный деструктор
};

class Circle : public Shape {
    double r_;
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.14159265 * r_ * r_; }
    void   scale(double k) override { r_ *= k; }
};

class Square : public Shape {
    double s_;
public:
    explicit Square(double s) : s_(s) {}
    double area() const override { return s_ * s_; }
    void   scale(double k) override { s_ *= k; }
};

void printAll(const std::vector<std::unique_ptr<Shape>>& shapes) {
    for (const auto& s : shapes)
        std::cout << s->area() << '\n';   // выбор реализации — в рантайме
}
```

`Shape` — абстрактный класс (есть хотя бы одна чисто виртуальная функция), создать его объект нельзя. `printAll` ничего не знает о `Circle`/`Square` — это и есть **открытый для расширения, закрытый для изменения** принцип (OCP).

### 2.2. Как это устроено внутри: vtable и vptr

Практически все компиляторы реализуют это через:

- **vptr** — скрытый указатель в каждом объекте полиморфного класса (обычно первый член, размер — размер указателя);
- **vtable** — статическая таблица на **класс** (не на объект), содержащая адреса виртуальных функций в фиксированном порядке, плюс служебные слоты (RTTI-указатель, обычно по индексу `-1`, offset-to-top, адрес деструктора).

Схематично:

```
Circle obj:                 vtable для Circle:
+-----------+               +---------------------------+
| vptr -----|-------------->| RTTI (type_info*)         |  [-1]
+-----------+               +---------------------------+
| r_ = 2.0  |               | &Circle::area             |  [0]
+-----------+               | &Circle::scale            |  [1]
                            | &Circle::~Circle (D1/D0)  |  [2]
                            +---------------------------+
```

Вызов `s->area()` компилируется примерно в:

```asm
mov rax, [rcx]          ; загрузить vptr из объекта
call qword ptr [rax+0]  ; косвенный вызов слота 0
```

Отсюда свойства динамического полиморфизма:

- **цена** — два разыменования памяти + косвенный вызов (плохо для предсказателя переходов), невозможность инлайна через границу вызова;
- **размер объекта** — +1 указатель на каждый объект;
- **гибкость** — можно подменять реализацию во время выполнения (плагины, DLL/SO, стратегии);
- **ABI** — vtable-раскладка зависит от компилятора, что ограничивает бинарную совместимость.

При **множественном наследовании** объект может содержать несколько vptr (по одному на каждый полиморфный базовый подобъект), а при **виртуальном наследовании** добавляются vbtable/vbptr для доступа к общему подобъекту (решение «ромба»).

### 2.3. `override`, `final` и правила переопределения

```cpp
struct Base {
    virtual void f(int);
    virtual void g() const;
    virtual ~Base() = default;
};

struct Derived : Base {
    void f(int) override;        // ок: точное совпадение сигнатуры
    void g() override;           // ОШИБКА: потерян const — это не override
};
```

Ключевое слово `override` заставляет компилятор проверить, что функция действительно переопределяет виртуальную функцию базы. Без него легко получить **сокрытие имени** (name hiding) вместо переопределения — классический источник багов.

`final` запрещает дальнейшее переопределение (для функции) или наследование (для класса) и даёт компилятору право на **девиртуализацию** — замену косвенного вызова прямым.

```cpp
struct Circle final : Shape { ... };  // наследников не будет
```

### 2.4. Перегрузка vs переопределение vs сокрытие

Это три разных механизма, и их постоянно путают на собеседованиях:

| Термин | Где | Условие | Связывание |
|---|---|---|---|
| **Overloading** (перегрузка) | один класс/скоуп | одинаковое имя, разные параметры | статическое |
| **Overriding** (переопределение) | база → наследник | `virtual` + точно та же сигнатура | динамическое |
| **Hiding** (сокрытие) | база → наследник | одинаковое имя без `virtual`/с другой сигнатурой | статическое |

Иллюстрация сокрытия:

```cpp
struct Base { void f(int); void f(double); };
struct Derived : Base { void f(const char*); };

Derived d;
d.f(42);      // вызовет f(const char*) через преобразование? Нет — ошибка/или f(const char*)
              // f(int) и f(double) из Base СКРЫТЫ
// лечится так:
struct Derived2 : Base {
    using Base::f;          // вернуть перегрузки базы в область видимости
    void f(const char*);
};
```

Ещё одна тонкость: **аргументы по умолчанию** подставляются статически, по типу указателя/ссылки, а не по динамическому типу:

```cpp
struct B { virtual void f(int x = 1) { std::cout << "B" << x; } };
struct D : B { void f(int x = 2) override { std::cout << "D" << x; } };

B* p = new D;
p->f();     // напечатает "D1" — тело из D, а значение по умолчанию из B
```

## 3. Сравнение

| Критерий | Статический полиморфизм | Динамический полиморфизм |
|---|---|---|
| Момент выбора | компиляция | выполнение |
| Механизм | перегрузка, шаблоны, CRTP, `if constexpr` | `virtual` + vtable/vptr |
| Накладные расходы | нулевые (часто инлайн) | vptr в объекте, косвенный вызов |
| Размер кода | растёт от инстанцирований шаблонов | одна копия функции на класс |
| Расширяемость | новые типы — только перекомпиляция | новый наследник — без изменения клиента |
| Набор типов | обычно открытый (любой подходящий `T`) | иерархия классов, часто закрытая на момент сборки |
| Семантика | значения, мономорфный код | ссылки/указатели, гетерогенные контейнеры |
| Диагностика | ошибки компиляции (иногда «простыня») | ошибки в рантайме (`dynamic_cast` → `nullptr`) |
| ABI/бинарь | шаблоны «зашиты» в вызывающего | vtable зависит от компилятора |

## 4. Как это выглядит в C (эмуляция вручную)

В C нет классов и виртуальных функций, но динамический полиморфизм моделируется **структурой с указателями на функции** — это ровно то, что компилятор C++ делает автоматически.

```c
/* shape.h */
typedef struct Shape Shape;

typedef struct {
    double (*area)(const Shape*);
    void   (*destroy)(Shape*);
} ShapeVtbl;

struct Shape {
    const ShapeVtbl* vptr;   /* аналог vptr */
};

double shape_area(const Shape* s) { return s->vptr->area(s); }
void   shape_destroy(Shape* s)    { s->vptr->destroy(s); }

/* circle.c */
typedef struct { Shape base; double r; } Circle;

static double circle_area(const Shape* self) {
    const Circle* c = (const Circle*)self;   /* аналог static_cast вниз */
    return 3.14159265 * c->r * c->r;
}
static void circle_destroy(Shape* self) { free(self); }

static const ShapeVtbl CIRCLE_VTBL = { circle_area, circle_destroy };

Shape* circle_new(double r) {
    Circle* c = malloc(sizeof *c);
    c->base.vptr = &CIRCLE_VTBL;   /* «конструктор» выставляет vptr */
    c->r = r;
    return (Shape*)c;
}
```

Здесь `vptr` инициализируется вручную, нет RTTI, нет проверки типов — всё, что C++ даёт бесплатно (и безопасно), в C приходится делать руками. Похожий приём — `qsort` с компаратором (`int (*)(const void*, const void*)`): это тоже рантайм-полиморфизм через указатель на функцию, но без иерархии типов.

## 5. Типичные ошибки и подводные камни динамического полиморфизма

**Срезка (object slicing).** При копировании по значению копируется только базовый подобъект, vptr «объекта-наследника» теряется:

```cpp
Circle c(2.0);
Shape s = c;          // ошибка компиляции, если Shape абстрактный;
                      // если нет — срезка: s имеет тип Shape, полиморфизма нет
std::vector<Shape> v; // хранить полиморфные объекты по значению нельзя!
std::vector<std::unique_ptr<Shape>> ok;  // правильно
```

**Невиртуальный деструктор.** `delete` через указатель на базу без `virtual ~Base()` — неопределённое поведение: не вызовется деструктор наследника, возможна утечка.

```cpp
struct Bad  { ~Bad() {} };
struct D : Bad { std::string s; };
Bad* p = new D;
delete p;              // UB: ~D() не вызван
```

**Вызов виртуальной функции в конструкторе/деструкторе.** Во время выполнения конструктора базового класса динамический тип объекта — это ещё `Base`, поэтому вызовется версия базы (а чисто виртуальная — приведёт к UB/`pure virtual call`).

**Отсутствие `override`** — см. выше: опечатка в сигнатуре молча создаёт новую функцию вместо переопределения.

**Игнорирование производительности.** Виртуальный вызов в горячем цикле на миллионах объектов может стоить заметно дороже; помогают: хранение по значению + `std::variant`, `final`, вынос инварианта из цикла, девиртуализация, профилирование.

## 6. Практические рекомендации по выбору

- **Статический полиморфизм** выбирайте, когда набор типов известен на этапе компиляции, важна производительность (HPC, embedded, игровые движки, ядра STL), и допустима перекомпиляция при добавлении типа. Шаблоны + concepts + CRTP дают нулевую цену абстракции.
- **Динамический полиморфизм** — когда иерархия должна быть **открыта** для расширения без изменения клиентского кода: плагины, загружаемые `.dll`/`.so`, GUI-виджеты, обработчики событий, Стратегия/Команда/Посетитель, гетерогенные коллекции `unique_ptr<Base>`.
- **Гибрид**: `std::variant` + `std::visit` для закрытого набора типов с семантикой значения; **type erasure** (`std::function`, `std::any`, собственные обёртки вроде `Shape::Concept`) — динамический полиморфизм без наследования, с value-семантикой и копируемостью.
- В C++ принято «не платить за то, что не используешь»: обычный класс без `virtual` не несёт vptr, а `virtual` — это осознанный выбор с известной ценой.

**Резюме.** Статический полиморфизм — это выбор реализации компилятором на основе статических типов (перегрузка, шаблоны, CRTP): быстро, мономорфно, но требует известности типов при компиляции. Динамический полиморфизм — это выбор реализации в рантайме через виртуальные функции и vtable: гибко и расширяемо, ценой vptr в объекте и косвенного вызова. Оба механизма решают одну задачу — «один интерфейс, много реализаций», — но с разными компромиссами, и грамотный C++-дизайн состоит в осознанном выборе между ними (а иногда и в их комбинации).
