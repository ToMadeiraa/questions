# 35. Что такое уязвимости? Каков механизм их работы?

## 1. Определение и терминология

**Уязвимость (vulnerability)** — это дефект в коде, конфигурации или архитектуре программы, который позволяет нарушить политику безопасности системы: получить доступ к чужим данным (конфиденциальность), изменить их (целостность) или вывести систему из строя (доступность). Важно: не всякий баг — уязвимость. Опечатка в сообщении об ошибке безвредна; уязвимостью баг становится тогда, когда его можно **использовать** (exploit) для достижения целей атакующего.

Связанные понятия:

| Термин | Смысл |
|---|---|
| **Эксплойт** | Программа или набор данных, реализующий атаку через уязвимость |
| **Вектор атаки** | Путь, которым входные данные атакующего попадают в уязвимый код (сеть, файл, argv, переменная окружения, IPC) |
| **Поверхность атаки** | Совокупность всех таких путей |
| **Примитив** | Ограниченная возможность, полученная из бага: чтение за границей, запись по адресу, управление потоком выполнения |
| **CWE / CVE / CVSS** | Классификация типов дефектов / конкретные экземпляры / оценка серьёзности |

Ключевая идея: уязвимость — это **нарушение инварианта** (границ буфера, времени жизни объекта, типа, атомарности операции), при котором данные, контролируемые извне, начинают влиять на то, что программа трактует как адрес, длину, индекс или команду. Именно превращение «данных» в «управляющее воздействие» (data-to-code) и составляет суть механизма.

## 2. Почему C и C++ — благоприятная среда для уязвимостей

C/C++ дают программисту прямой контроль над памятью и при этом почти не защищают его:

- нет проверки границ массивов и указателей;
- ручное управление временем жизни (`malloc`/`free`, `new`/`delete`);
- арифметика указателей и неявные преобразования типов;
- неопределённое поведение (UB) вместо диагностики: переполнение знаковых целых, разыменование «повисшего» указателя, выход за границы — компилятор вправе считать, что этого не происходит, и **удалять проверки**;
- небезопасные функции стандартной библиотеки: `strcpy`, `strcat`, `sprintf`, `gets`, `memcpy` с длиной извне;
- отсутствие сборки мусора и обязательной инициализации.

Именно поэтому большинство критических CVE в системном ПО (ядра, OpenSSL, SMB, sudo) — это дефекты работы с памятью.

## 3. Общая модель механизма эксплуатации

Механизм удобно описывать как цепочку из пяти шагов.

1. **Нарушение инварианта.** Программа пишет/читает не туда, освобождает объект дважды, не проверяет длину, переполняет счётчик.
2. **Контроль данных в опасной позиции.** Атакующий подбирает вход так, чтобы «неправильные» байты оказались в памяти, которая позже используется как адрес, размер, индекс или указатель на функцию.
3. **Получение примитива.** Из бага извлекается одно из:
   - OOB read → утечка адресов (обход ASLR) или секретов;
   - OOB write → порча соседних данных, относительная или произвольная запись;
   - control-flow hijack → перехват `rip`/указателя на функцию;
   - arbitrary free / double free → управление аллокатором.
4. **Построение цепочки.** Примитивы комбинируются: утечка → вычисление адресов → запись → перехват выполнения.
5. **Закрепление.** Выполнение полезной нагрузки: shellcode, ROP-цепочка, вызов `system`, обход песочницы, эскалация привилегий, persistence.

Ключевой момент: современный эксплойт — это почти всегда **не** «запись шелл-кода в стек и прыжок на него», а многошаговая конструкция из утечек и относительных записей, обходящая конкретный набор защит.

## 4. Анатомия памяти процесса

Чтобы понимать механизм, нужно помнить раскладку адресного пространства:

```
высокие адреса
+------------------+
|   stack (растёт ↓)|  локальные переменные, сохранённый rbp, адрес возврата
+------------------+
|   mmap / libs     |  разделяемые библиотеки, GOT/PLT
+------------------+
|   heap (растёт ↑) |  malloc/new, метаданные аллокатора
+------------------+
|   .bss / .data    |  глобальные и статические переменные
+------------------+
|   .text (RO)      |  код, таблицы переходов, vtables
+------------------+
низкие адреса
```

Уязвимость «интересна» атакующему, когда позволяет дотянуться до **управляющих данных**: адреса возврата, сохранённого `rbp`, указателей на функции, таблиц виртуальных функций, GOT-записей, метаданных кучи, дескрипторов и флагов.

## 5. Классы уязвимостей и их механизмы

### 5.1 Переполнение буфера в стеке (stack buffer overflow)

```c
void greeting(const char *name) {
    char buf[64];
    strcpy(buf, name);   /* нет ограничения длины */
    printf("Hello, %s\n", buf);
}
```

`strcpy` копирует до NUL-байта. Если `name` длиннее 63 символов, запись выходит за `buf` и последовательно затирает: соседние локальные переменные → сохранённый `rbp` → **адрес возврата**.

До вызова `greeting("AAAA...")`:

```
buf[64] | saved rbp (8) | return address (8) | аргументы вызывающего
```

После подачи строки из 72 байт + адреса:

```
buf[64] | 0x4141414141414141 | 0x00007f....  <-- подменённый адрес возврата
```

При выполнении `ret` значение из стека попадает в `rip` — поток управления перехвачен. Классика: перезапись адреса возврата на буфер со шелл-кодом (работает только при исполняемом стеке).

### 5.2 Переполнение кучи (heap overflow)

```c
char *p = malloc(32);
strcpy(p, attacker_data);   /* > 32 байт */
```

Здесь затираются не адреса возврата, а **метаданные аллокатора** и соседние блоки. Механизм эксплуатации: порча заголовка следующего чанка (размер, указатели списков свободных блоков) → при последующем `malloc`/`free` аллокатор возвращает указатель на произвольный адрес (относительная или произвольная запись). В современных аллокаторах (tcache, fastbins) эксплуатируются «отравленные» списки свободных чанков.

### 5.3 Use-after-free и double free

```c
char *p = malloc(16);
free(p);
strcpy(p, data);   /* запись в освобождённую память */
```

Механизм: после `free` блок попадает в список свободных и может быть выдан повторно. Если программа продолжает писать через «повисший» указатель, она портит данные нового владельца блока. Обратный сценарий — чтение через освобождённый указатель — даёт утечку. `double free` ломает инварианты аллокатора и позволяет получить один и тот же блок двум разным объектам (type confusion на уровне памяти).

Особенно опасно в C++: если по освобождённому объекту вызывается виртуальный метод, читается **указатель на vtable** из переиспользованной памяти — атакующий подставляет туда свой адрес и получает вызов произвольной функции с контролируемым `this`.

### 5.4 Целочисленные ошибки

```c
size_t total = count * sizeof(Item);   /* переполнение size_t */
Item *arr = malloc(total);             /* слишком маленький буфер */
for (size_t i = 0; i < count; ++i)
    arr[i] = items[i];                 /* переполнение кучи */
```

Механизм: переполнение (знаковое — UB, беззнаковое — взятие по модулю), усечение при приведении `size_t` → `int`, ошибка в проверке (`if (len - 1 < MAX)` при `len == 0` даёт огромное значение). Итог — неверный размер буфера, который затем переполняется. Это типичный «первый шаг» многих цепочек: сам по себе integer overflow безвреден, опасен его результат.

### 5.5 Форматная строка (format string)

```c
printf(user_input);        /* вместо printf("%s", user_input) */
```

Механизм: атакующий управляет строкой формата. Спецификаторы `%x`/`%p` читают аргументы, которых не передавали, — утечка стека и адресов; `%n` **записывает** число выведенных байт по адресу, взятому из аргумента. Комбинируя позиционные спецификаторы (`%7$n`) и ширину поля, получают произвольную запись по почти произвольному адресу.

### 5.6 Off-by-one, отсутствие инициализации, OOB read

- **Off-by-one**: `for (i = 0; i <= n; i++) a[i] = 0;` — один лишний байт. В куче он может испортить младший байт размера следующего чанка, что достаточно для перекрытия блоков.
- **Неинициализированная память**: `char buf[64]; send(fd, buf, 64, 0);` — утечка остатков стека (адреса, ключи).
- **OOB read**: чтение за границей буфера без записи. Сам по себе не перехватывает поток управления, но даёт утечку — основу обхода ASLR. Пример из реальности — Heartbleed в OpenSSL: длина в heartbeat-запросе не сверялась с фактическим размером буфера, и сервер возвращал до 64 КБ чужой памяти.

### 5.7 Специфика C++: vtable, type confusion, наследование

```cpp
struct Base { virtual void f(); };
struct Evil { void (*fptr)(); };

Base *b = new Base;
/* ... UAF или OOB write ... */
b->f();   /* читает vptr, вызывает [vptr + offset] */
```

Механизм: виртуальный вызов — это косвенный вызов по указателю, прочитанному из объекта. Порча `vptr` (через UAF, overflow или `reinterpret_cast` в чужой тип) превращает обычный вызов метода в вызов произвольного адреса. Родственные проблемы: `delete` через указатель на базовый класс без виртуального деструктора (UB), срезка объектов (object slicing), небезопасные `reinterpret_cast`/union-чтение, «сырые» `new`/`delete` в паре с исключениями (утечки и двойное освобождение).

### 5.8 Логические ошибки, гонки, TOCTOU

- **TOCTOU** (time-of-check to time-of-use): между проверкой прав и использованием объекта его подменяют (символическая ссылка, файл, сокет). Механизм — не memory corruption, а разрыв во времени.
- **Гонки данных**: отсутствие атомарности/блокировки → двойное освобождение, повторная инициализация, обход проверки счётчика.
- **Небезопасные сигналы**: вызов не async-signal-safe функций из обработчика.
- **Логические ошибки**: неверная проверка прав, целочисленный «обход» условия, доверие к длине из заголовка протокола.

### 5.9 NULL-разыменование и отказ в обслуживании

Разыменование `NULL` обычно даёт падение (DoS). В ядре при разрешённом отображении нулевой страницы (`mmap_min_addr = 0`) атакующий может разместить данные по низким адресам и превратить NULL-deref в перехват управления. Рекурсивный вызов без ограничения глубины — переполнение стека и также DoS.

## 6. От примитива к выполнению кода

Когда адрес возврата перехвачен, исторически использовались три техники:

1. **Shellcode в стеке** — прямая передача управления на внедрённый код. Умерла вместе с NX/DEP.
2. **ret2libc** — возврат в `system()` внутри libc, аргумент (`"/bin/sh"`) кладётся через стек/регистры (гаджеты вида `pop rdi; ret`).
3. **ROP/JOP** — сборка программы из коротких последовательностей инструкций, заканчивающихся `ret` (или `jmp`). Цепочка гаджетов вызывает `mprotect`, чтобы сделать память исполняемой, либо сразу выполняет нужные вызовы. Это универсальный механизм обхода NX.

Для кучи механизм иной: сначала получают **утечку** (libc/heap/stack), затем добиваются выделения блока по нужному адресу (tcache poisoning, House of …), затем перезаписывают управляющий указатель (например, `__free_hook` в старых glibc или vtable) — и получают вызов при следующей операции.

Типичная последовательность реального эксплойта:

```
1. OOB read  -> адрес libc / heap / stack
2. расчёт    -> база, адреса гаджетов, system, "/bin/sh"
3. OOB write -> порча vptr / return address / hook
4. вызов    -> ROP-цепочка -> system("/bin/sh")
5. post-exploit -> чтение файлов, эскалация, persistence
```

## 7. Защиты и как их обходят

| Защита | Что делает | Типичный обход |
|---|---|---|
| **Stack canary** (`-fstack-protector`) | Случайное значение перед адресом возврата, проверяется при выходе | Утечка канарейки; атака на другие цели (указатели, vptr); брутфорс в fork-сервере |
| **NX/DEP** | Стек и куча неисполняемы | ROP/JOP, ret2libc |
| **ASLR** | Рандомизация баз библиотек, стека, кучи | Info leak, частичная перезапись, брутфорс (особенно 32-bit) |
| **PIE** | ASLR для основного бинарника | Утечка адреса кода, частичный overwrite |
| **RELRO** | GOT только для чтения (full) | Атака на другие указатели, `__free_hook`/`__malloc_hook` (до glibc 2.34) |
| **Fortify / `_FORTIFY_SOURCE`** | Проверки в обёртках libc | Логические ошибки, обход через нестандартные пути |
| **CFG / CET (shadow stack, IBT)** | Легальные цели косвенных переходов, аппаратная защита `ret` | Сложнее, но не абсолютно: JOP, атаки на данные |
| **ASan/UBSan/MSan** | Диагностика в отладке, не в релизе | Не является защитой в продакшене |
| **Seccomp, sandbox, привилегии** | Ограничивают ущерб после эксплуатации | Атака на сам sandbox, утечки через side channels |

Ни одна из мер не устраняет причину — они лишь повышают стоимость эксплуатации. Надёжнее устранять сам дефект.

## 8. Как снижать риск

- **Границы и типы**: `std::vector`, `std::array`, `std::string`, `std::span`; вместо `strcpy` — `snprintf`/`strlcpy` с явной проверкой; проверять результат и длину до копирования.
- **Владение ресурсами**: RAII, `std::unique_ptr`/`shared_ptr`, никаких «сырых» `new`/`delete`; виртуальные деструкторы в полиморфных базовых классах.
- **Целочисленная арифметика**: проверять переполнение (`__builtin_mul_overflow`), использовать беззнаковые типы для размеров, валидировать вход до выделения памяти.
- **Форматный вывод**: всегда `printf("%s", s)`, никогда `printf(s)`.
- **Инициализация**: `= {}`, `calloc`, не отправлять наружу неинициализированные буферы.
- **Компилятор и линкер**: `-Wall -Wextra -Wconversion`, `-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-fPIE -pie`, `-Wl,-z,relro,-z,now`, `-fcf-protection`.
- **Процесс**: code review, статический анализ (Coverity, clang-tidy, cppcheck), фаззинг (AFL++, libFuzzer), тесты с ASan/UBSan в CI, минимизация привилегий и sandboxing, своевременное обновление зависимостей.

## 9. Резюме

Уязвимость в C/C++ — это, как правило, нарушение инварианта памяти, времени жизни или типа, возникающее из-за ручного управления ресурсами и отсутствия проверок. Механизм её работы сводится к цепочке: **дефект → контролируемые данные попадают в управляющую позицию → примитив (утечка/запись/перехват потока) → обход защит → выполнение кода или эскалация привилегий**. Понимание этой цепочки важно не только для атакующих: каждая её ступень — это точка, где защита (проверки, безопасные типы, RAII, санитайзеры, sandbox, аппаратные механизмы) может разорвать эксплуатацию.
