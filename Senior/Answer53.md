# 53. Опишите назначение execution policy для параллельных алгоритмов.

## 1. Контекст: что такое параллельные алгоритмы

В C++17 в `<algorithm>`, `<numeric>` и `<memory>` появились перегрузки классических алгоритмов, первым аргументом которых принимается **execution policy** — объект, задающий «разрешение» и рамки распараллеливания:

```cpp
#include <algorithm>
#include <execution>
#include <vector>

std::vector<int> v = /* ... */;

std::sort(std::execution::par, v.begin(), v.end());          // разрешено параллельно
std::sort(std::execution::seq, v.begin(), v.end());          // строго последовательно
std::for_each(std::execution::par_unseq, v.begin(), v.end(), f);
```

Важно понимать: **это не отдельные функции с другими именами**, а именно перегрузки. Политика — первый параметр, передаваемый по значению; сами объекты политик — `inline constexpr` в пространстве имён `std::execution` (заголовок `<execution>`).

## 2. Назначение execution policy

Назначение можно сформулировать пятью пунктами.

**1) Разрешение (а не требование) на параллельное выполнение.**
Политика сообщает реализации: «тебе *разрешено* распараллелить этот алгоритм и/или векторизовать его». Это именно разрешение: реализация вправе выполнить алгоритм последовательно (например, при малом `N` или при нехватке ресурсов). Поэтому `par` **не гарантирует** ни параллелизма, ни числа потоков, ни порядка.

**2) Выбор степени агрессивности через тип политики.**
Разные типы политик дают разные контракты: от «не параллель ни при каких условиях» (`seq`) до «можно и потоки, и SIMD-векторизацию, и чередование вызовов в одном потоке» (`par_unseq`). Реализация может специализировать код под каждый тип.

**3) Контракт на пользовательский код.**
Тип политики определяет, что *обязан* гарантировать вызывающий: отсутствие гонок данных, отсутствие блокирующих операций, «vectorization-safe» код и т. д. Это часть интерфейса, а не пожелание.

**4) Удобство обобщённого программирования.**
Политику можно протаскивать параметром через шаблонный код, переключая режим исполнения без изменения тела:

```cpp
template <class Policy>
void normalize(std::vector<double>& v, Policy&& pol) {
    std::transform(pol, v.begin(), v.end(), v.begin(),
                   [](double x) { return x / 255.0; });
}
```

**5) Расширяемость.**
Стандарт определяет трейт `std::is_execution_policy<T>` (`_v`), который можно специализировать для собственных типов политик — так реализация или библиотека может добавить, например, политику с GPU-бэкендом, не ломая перегрузки.

## 3. Стандартные политики

| Политика | Тип | Потоки | Векторизация (SIMD) | Порядок вызовов |
|---|---|---|---|---|
| `std::execution::seq` | `sequenced_policy` | нет, вызывающий поток | нет | последовательный, как у обычного алгоритма |
| `std::execution::par` | `parallel_policy` | да | не гарантируется | не определён |
| `std::execution::par_unseq` | `parallel_unsequenced_policy` | да | да | не определён; вызовы могут **чередоваться в одном потоке** |
| `std::execution::unseq` (C++20) | `unsequenced_policy` | нет | да | один поток, вызовы неупорядочены между собой |

Ключевые нюансы:

- `seq` — не «пустышка»: она даёт **гарантию отсутствия параллелизма**, а значит, вызовы `f` происходят в вызывающем потоке, и можно безопасно работать с `thread_local`, отлаживать, использовать мьютексы.
- `par` — потоки, но внутри одного потока вызовы по-прежнему упорядочены (sequenced), поэтому блокировки формально допустимы (хотя опасны).
- `par_unseq` и `unseq` — вызовы **неупорядочены** (unsequenced) даже в пределах одного потока, компилятор вправе их перемешивать и сливать в SIMD-инструкции.

## 4. Что политика НЕ гарантирует

Это частая тема на собеседованиях, поэтому перечислим явно:

- не гарантирует, что код действительно выполнится параллельно;
- не определяет число потоков, размер чанков, привязку к ядрам;
- не определяет порядок обработки элементов (кроме `seq`);
- не делает код потокобезопасным автоматически — гонки данных остаются UB;
- не отменяет требований к самим алгоритмам (например, компаратор `sort` всё так же должен быть строгим слабым порядком).

## 5. Требования к коду: главное практическое следствие

### 5.1 Общие требования (все политики, включая `seq`)

Функциональные объекты, переданные в параллельный алгоритм, должны быть **копируемыми** (copy-constructible и copy-assignable) и не иметь состояния, разделяемого между копиями без синхронизации. Захват по ссылке на изменяемую переменную — классическая гонка:

```cpp
int sum = 0;
std::for_each(std::execution::par, v.begin(), v.end(),
              [&](int x) { sum += x; });   // UB: гонка данных
```

Корректно — `std::reduce`/`transform_reduce` или атомики/локальные аккумуляторы. Также нельзя:

- обращаться к элементам контейнера в обход переданных итераторов (например, по индексу в глобальном массиве), если это создаёт гонку;
- блокироваться на неограниченное время (ожидание другого потока того же алгоритма → взаимоблокировка);
- вставлять/удалять элементы контейнера, менять его размер.

### 5.2 Специфика `unseq` / `par_unseq`

Здесь действует дополнительное требование **vectorization-safe**: вызовы не должны содержать операций, несовместимых с векторизацией и с чередованием в одном потоке. Запрещены (точнее, ведут к UB/`terminate`/дедлоку):

- взятие и удержание мьютексов и любых блокирующих примитивов (один поток может захватить мьютекс, «переключиться» на другой вызов и попытаться захватить его снова → дедлок);
- блокирующая синхронизация вообще, вызовы `std::this_thread::sleep_for`, ожиданиеfuture и т. п.;
- небезопасные с точки зрения векторизации аллокации памяти и вызовы, зависящие от `thread_local` (нет гарантии, что все вызовы пойдут в один поток);
- `volatile`-доступы «для синхронизации».

Практическое правило: для `par_unseq` функция должна быть **чистой, без блокировок и без побочных эффектов**, работающей только со своими аргументами.

### 5.3 Исключения

Если элемент-функция выходит по исключению при `par`, `par_unseq` или `unseq`, вызывается `std::terminate` — исключение не «долетает» до вызывающего кода. Поэтому такие функции должны быть фактически `noexcept` либо ловить исключения внутри. Дополнительно реализация может бросить `std::bad_alloc`, если не смогла выделить память под внутренние структуры.

## 6. Как это выглядит на практике

```cpp
#include <execution>
#include <numeric>
#include <vector>

std::vector<double> xs = /* ... */, ys = /* ... */;

// accumulate НЕ имеет перегрузки с политикой — используем reduce
double dot = std::transform_reduce(std::execution::par_unseq,
                                   xs.begin(), xs.end(), ys.begin(),
                                   0.0);

// префиксные суммы: partial_sum -> inclusive_scan
std::vector<double> pref(xs.size());
std::inclusive_scan(std::execution::par, xs.begin(), xs.end(), pref.begin());
```

Стоит запомнить пары «старый → параллельный»:

| Последовательный | Параллельный (C++17) |
|---|---|
| `accumulate` | `reduce`, `transform_reduce` |
| `partial_sum` | `inclusive_scan`, `exclusive_scan` |
| `inner_product` | `transform_reduce` (у самого `inner_product` перегрузки с политикой **нет**) |

Для `reduce` операция должна быть **ассоциативной и коммутативной** — иначе результат недетерминирован (типичная ловушка при суммировании `double`: порядок сложения не фиксирован, ответ зависит от разбиения на блоки).

## 7. Реализация и производительность

- **GCC/libstdc++**: параллельные политики работают только при сборке с Intel TBB (`-ltbb`), иначе — ошибка компоновки/`std::bad_alloc`/последовательное исполнение в зависимости от версии. Проверяйте макросы `__cpp_lib_execution` (`201603`, `201902` для `unseq`) и `__cpp_lib_parallel_algorithm` (`201603`).
- **MSVC**: использует Concurrency Runtime (PPL), параллельные перегрузки доступны «из коробки».
- **libc++ (Clang)**: долгое время параллельные алгоритмы просто отсутствуют — код с `std::execution::par` не компилируется; ориентируйтесь на feature-test макросы.
- Накладные расходы: для маленьких диапазонов `par` часто **медленнее** `seq` (создание задач, синхронизация). Порог окупаемости — обычно десятки тысяч элементов и «тяжёлая» операция на элемент.
- Ложное разделение (false sharing) при записи в соседние элементы и переподписка (oversubscription) при вложенном параллелизме могут съесть весь выигрыш.

## 8. Типичные ошибки

1. Ожидание, что `par` гарантирует ускорение (это лишь разрешение).
2. Захват по ссылке с записью в общий счётчик → гонка.
3. Мьютекс или `sleep` внутри `par_unseq` → дедлок/UB.
4. Исключение из лямбды при `par` → `std::terminate`.
5. `std::reduce` с неассоциативной операцией → «плавающий» результат.
6. Использование `std::execution::par` без TBB в GCC → ошибка сборки.
7. Попытка передать политику в ranges-алгоритмы C++20 — они **не поддерживают** execution policy (это отдельное предложение, ещё не вошедшее в стандарт).

## 9. Резюме: какую политику выбирать

- `seq` — по умолчанию, когда нужна детерминированность, отладка, работа с `thread_local`, блокировки или когда данных мало.
- `par` — «тяжёлые» независимые вычисления над большими диапазонами; допустимы атомики и осторожная синхронизация.
- `par_unseq` — чистые vectorization-safe функции без блокировок и побочных эффектов; максимум производительности.
- `unseq` — один поток, но с векторизацией: когда параллельные потоки нежелательны (например, уже находимся внутри параллельной области), а SIMD полезен.

Главная мысль: **execution policy — это часть контракта**. Она одновременно (а) выбирает перегрузку и разрешает реализации распараллелить/векторизовать код, (б) задаёт уровень агрессивности, (в) накладывает на пользовательский код строгие требования, нарушение которых — не «медленно», а undefined behavior или `std::terminate`.
