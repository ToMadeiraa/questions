# 12. Как считать покрытие тестами? Нужно ли это делать?

## Коротко

Покрытие (code coverage) — это доля кода программы, которая была выполнена во время прогона тестов. Считать его **нужно**, но как **диагностический инструмент**, а не как KPI. Покрытие отвечает на вопрос «какой код тесты вообще не трогают», но ничего не говорит о том, **проверяют** ли тесты правильность поведения. Поэтому гнаться за 100% бессмысленно и вредно, а вот включить измерение в CI и следить за покрытием **нового** кода — очень полезно.

## Что именно измеряют

Инструменты инструментируют код: в каждую ветку/строку/функцию вставляется счётчик, при прогоне тестов счётчики увеличиваются, после чего строится отчёт.

| Вид покрытия | Что означает | Строгость |
|---|---|---|
| Function / method | каждая функция была вызвана хотя бы раз | слабое |
| Statement / line | каждая исполняемая строка выполнена | базовое |
| Branch / decision | каждая ветка `if`, `switch`, цикла выполнена в обе стороны | сильнее line |
| Condition | каждое подвыражение в условии было true и false | сильнее branch |
| MC/DC | каждое условие **независимо** влияет на результат решения | очень сильное, для авионики/авто |
| Path | все возможные пути исполнения | комбинаторный взрыв, на практике недостижимо |
| Data-flow (def-use) | покрытие цепочек «определение → использование» переменной | нишевое |

Ключевой момент: **100% line coverage ≠ 100% branch coverage**. Строка

```cpp
if (a && b) { ... }
```

считается «покрытой», если условие хотя бы раз вычислилось, но при этом `b` могло ни разу не вычисляться из-за short-circuit. Branch coverage это покажет, line — нет.

## Инструменты для C++

- **GCC + gcov** — встроено в компилятор, бесплатно, работает везде.
- **lcov / genhtml** — сборка и HTML-отчёт по gcov-данным.
- **gcovr** — более удобная альтернатива lcov, умеет HTML/XML/JSON, хорошо дружит с CMake и CI.
- **Clang/LLVM `llvm-cov`** — source-based coverage, точнее и быстрее gcov; стандарт де-факто для clang-проектов.
- **OpenCppCoverage** — Windows, MSVC-бинарники без пересборки.
- **Visual Studio Enterprise** — встроенное покрытие (только в Enterprise).
- **Коммерческие**: BullseyeCoverage, Squish Coco, VectorCAST, Testwell CTC++ — нужны там, где требуется MC/DC и сертификация (DO-178C, ISO 26262, IEC 62304).
- **Сервисы отчётов**: Codecov, Coveralls, SonarQube/SonarCloud, GitLab Coverage, Jenkins Coverage Plugin.

## Как считать: GCC/gcov

Сборка с инструментированием (`--coverage` = `-fprofile-arcs -ftest-coverage`):

```bash
g++ -O0 -g --coverage -c foo.cpp -o foo.o
g++ -O0 -g --coverage -c tests.cpp -o tests.o
g++ --coverage foo.o tests.o -o tests
./tests
```

После запуска рядом с объектными файлами появляются `.gcda`; `.gcno` создаются при компиляции. Далее:

```bash
# lcov
lcov --capture --directory . --output-file coverage.info
lcov --remove coverage.info '/usr/*' '*/tests/*' '*/third_party/*' \
     --output-file coverage.filtered.info
genhtml coverage.filtered.info --output-directory coverage_html

# или gcovr
gcovr -r . --exclude tests/ --exclude third_party/ \
      --html --html-details -o coverage.html
gcovr -r . --xml -o coverage.xml   # для CI/Codecov
```

Важные флаги: `--rc branch_coverage=1` (lcov 2.x) или `--rc lcov_branch_coverage=1` (lcov 1.x) — иначе branch-данные молча отбрасываются. В gcovr ветки учитываются по умолчанию в свежих версиях.

### CMake

```cmake
option(ENABLE_COVERAGE "Enable coverage instrumentation" OFF)

if(ENABLE_COVERAGE)
  add_library(coverage_flags INTERFACE)
  target_compile_options(coverage_flags INTERFACE
    --coverage -O0 -g -fno-inline -fno-inline-small-functions)
  target_link_options(coverage_flags INTERFACE --coverage)
endif()

# ...
if(ENABLE_COVERAGE)
  target_link_libraries(my_tests PRIVATE coverage_flags)
endif()
```

Сборка: `cmake -B build -DENABLE_COVERAGE=ON && cmake --build build && ctest --test-dir build`.

`-O0 -fno-inline` нужны, чтобы оптимизатор не «схлопывал» строки и ветки: иначе отчёт врёт. Но тогда тестируется не тот бинарник, что уходит в прод, — поэтому имеет смысл гонять тесты дважды: instrumented-сборку для покрытия и Release-сборку для реальных багов/UB.

### Clang/LLVM

```bash
clang++ -O0 -g -fprofile-instr-generate -fcoverage-mapping -c foo.cpp
clang++ -fprofile-instr-generate foo.o tests.o -o tests

LLVM_PROFILE_FILE="tests-%p.profraw" ./tests
llvm-profdata merge -sparse *.profraw -o tests.profdata

llvm-cov report ./tests -instr-profile=tests.profdata
llvm-cov show   ./tests -instr-profile=tests.profdata \
                --format=html --output-dir=coverage_html
llvm-cov export ./tests -instr-profile=tests.profdata -format=lcov > coverage.info
```

`%p` в `LLVM_PROFILE_FILE` разводит профили по процессам — это важно при параллельных тестах, иначе счётчики будут теряться/смешиваться. Для gcov аналог — `GCOV_PREFIX`.

## Подводные камни

1. **Покрытие ≠ проверка.** Тест без единого `assert` прекрасно увеличивает покрытие:

   ```cpp
   TEST(Calc, Add) {
     Calculator c;
     c.add(2, 2);   // вызвали — покрытие выросло, корректность не проверена
   }
   ```

2. **Эффект Гудхарта.** Как только процент покрытия становится планом и премией, люди пишут тесты «чтобы дёрнуть код», а не «чтобы поймать баг». Метрика перестаёт отражать качество.
3. **Недостижимый код.** Защитные `assert`, `default:` в `switch` по `enum`, обработчики `std::terminate`, ветки под `#ifdef _WIN32` — их физически нельзя покрыть с одной платформы. 100% в реальном проекте недостижимы.
4. **Сгенерированный код и header-only.** `*.pb.cc`, `moc_*.cpp`, шаблоны и inline-функции из заголовков инструментируются в каждой единице трансляции; без фильтрации и мержа цифры занижаются/раздуваются. Исключайте сгенерированное, тесты, third-party.
5. **Многопоточность.** Классический gcov не потокобезопасен; для GCC помогает `-fprofile-update=atomic`, для clang — отдельные `.profraw` на процесс.
6. **Исключения и «редкие» пути.** Покрытие не покажет, что тесты не проверяют обработку `std::bad_alloc`, таймаутов, отмены.
7. **Метрика не про требования.** 100% покрытие кода может быть при 0% покрытия требований: код исполняется, но не в тех сценариях, что описаны в спецификации.

## Нужно ли это делать

**Да, но с оговорками.**

Что покрытие реально даёт:

- находит **мёртвый и непротестированный код** — часто это как раз обработчики ошибок;
- показывает **рискованные зоны** в легаси, куда страшно вносить изменения;
- защищает от **регрессий покрытия**: PR, который добавил 300 строк без тестов, видно сразу;
- помогает при **рефакторинге**: упавшее покрытие — сигнал, что тесты отстали;
- для **сертификации** (DO-178C Level A, ISO 26262 ASIL C/D) структурное покрытие, вплоть до MC/DC, — формальное требование, и там это считают коммерческими инструментами с доказательной базой.

Чего покрытие не даёт:

- не измеряет **силу проверок** — для этого есть **мутационное тестирование** (`mull`, Dextool Mutate): инструмент намеренно ломает код и смотрит, падают ли тесты;
- не заменяет ревью, санитайзеры (`-fsanitize=address,undefined`), фаззинг и статический анализ;
- не является целью само по себе.

## Практическая политика

Разумный компромисс, который работает в большинстве C++-проектов:

1. **Измерять line + branch** в отдельной CI-джобе, отчёт — артефактом и в PR-комментарий.
2. **Гейт на новом коде, а не на проекте.** Например, покрытие изменённых строк ≥ 70–80%; общее покрытие не должно падать больше чем на 1–2%. Для легаси это единственный реалистичный путь — иначе порог либо отключат, либо начнут писать пустые тесты.
3. **Дифференциальное покрытие** — самый действенный сигнал. Инструменты: Codecov/SonarQube (анализ нового кода), `diff-cover`, `gcovr --diff`.
4. **Исключать** тесты, third-party, сгенерированный код, `main()`, платформенные `#ifdef`.
5. **Смотреть на непокрытые строки в диффе глазами**, а не только на процент: часто там `if (!ptr) return;` — и это нормально, если путь защитный.
6. **Не требовать 100%** и не сравнивать команды по проценту. Целевые 80–90% для ядра логики — здоровая планка; 100% достигается только тривиальным кодом или самообманом.
7. **Дополнять** мутационным тестированием на критичных модулях, санитайзерами и фаззингом парсеров/протоколов.

## Итог

Считать покрытие стоит — это дешёвый и наглядный способ увидеть, что осталось без тестов. Но относиться к нему нужно как к **лакмусовой бумажке, а не к оценке**: высокое покрытие при слабых проверках хуже, чем 70% при тестах, которые действительно ловят регрессии. Оптимальная стратегия — измерять всегда, ставить порог на **изменяемый** код, не гнаться за абсолютными цифрами и обязательно смотреть, **что именно** осталось непокрытым.
