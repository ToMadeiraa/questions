# 14. Что такое SIMD-инструкции? Какие необходимые условия и способы их использования?

## 1. Определение

**SIMD** (*Single Instruction, Multiple Data* — «одна инструкция, много данных») — это модель параллелизма из таксономии Флинна, при которой **одна машинная инструкция обрабатывает несколько элементов данных одновременно**. Процессор имеет векторные регистры и векторные АЛУ: команда вида `VADDPS` складывает не два числа, а, например, восемь пар `float` за один такт (точнее — за одну инструкцию).

Это форма **параллелизма на уровне данных (DLP)**, в отличие от ILP (параллелизм на уровне инструкций, которым занимается суперскалярное ядро) и TLP (потоки).

Ключевая идея: в обычном скалярном коде

```cpp
for (int i = 0; i < n; ++i)
    c[i] = a[i] + b[i];
```

компилятор генерирует `n` инструкций сложения. Векторизованный код выполняет `n / W` инструкций, где `W` — число элементов, помещающихся в векторный регистр (vector width / SIMD width).

## 2. Как это устроено на уровне железа

| Архитектура | Расширение | Ширина регистра | Кол-во `float` / `double` / `int32` |
|---|---|---|---|
| x86 | SSE, SSE2 | 128 бит (XMM) | 4 / 2 / 4 |
| x86 | AVX | 256 бит (YMM) | 8 / 4 / 8 |
| x86 | AVX2 | 256 бит | + целочисленные 256-битные операции, gather |
| x86 | AVX-512 | 512 бит (ZMM) | 16 / 8 / 16, маски, scatter |
| ARM | NEON (ASIMD) | 128 бит | 4 / 2 / 4 |
| ARM | SVE / SVE2 | 128…2048 бит, **переменная длина** | зависит от реализации |
| RISC-V | RVV | переменная длина (VLEN) | зависит от реализации |
| Power | AltiVec/VSX | 128 бит | 4 / 2 / 4 |

Важные следствия:

- Векторные регистры — отдельный файл регистров; данные надо сначала **загрузить** в него (`load`), потом обработать, потом **выгрузить** (`store`). Отсюда типичная структура векторизованного цикла: загрузка → арифметика → выгрузка.
- Набор операций шире, чем «сложение/умножение»: сравнения, побитовые операции, перестановки (`shuffle`/`permute`), насыщение, `gather`/`scatter`, маски, FMA (`a*b+c` одной инструкцией с одним округлением).
- На x86-64 **SSE2 является частью базовой платформы** (гарантирована), а AVX/AVX2/AVX-512 — нет.

## 3. Необходимые условия

Условия делятся на аппаратные, программные и «свойства самого кода».

### 3.1. Аппаратные условия

1. **Поддержка расширения процессором.** Проверяется через CPUID. На x86: `CPUID.1:EDX.SSE2`, `CPUID.1:ECX.AVX`, `CPUID.7:EBX.AVX2`, `CPUID.7:EBX.AVX512F` и т. д.
2. **Поддержка со стороны ОС.** Для AVX/AVX-512 недостаточно флага CPU: ОС должна сохранять «верхнюю» часть векторных регистров при переключении контекста. Проверяется битами `OSXSAVE` и `XGETBV` (значение `XCR0`), т. е. что ОС включила состояние XMM/YMM/ZMM. Без этого использовать AVX нельзя, даже если CPU его умеет.
3. **Достаточная пропускная способность памяти.** Если цикл упирается в память (memory-bound), а не в вычисления (compute-bound), SIMD даст мало. Векторизация помогает прежде всего там, где на один элемент приходится несколько арифметических операций.

### 3.2. Программные условия

1. **Компилятор должен уметь генерировать векторный код** и ему нужно разрешить соответствующую систему команд:
   - GCC/Clang: `-msse4.2`, `-mavx`, `-mavx2`, `-mfma`, `-mavx512f`, `-march=native`, `-mtune=...`;
   - MSVC: `/arch:SSE2`, `/arch:AVX`, `/arch:AVX2`, `/arch:AVX512`;
   - включённый уровень оптимизации: `-O2`/`-O3` (в GCC автовекторизация включается с `-O3`, в Clang — с `-O2`; в MSVC — с `/O2`).
2. **Целевая архитектура бинарника должна соответствовать машине.** Бинарник, собранный с `-mavx2`, упадёт с `SIGILL` на процессоре без AVX2. Отсюда — либо базовая версия + runtime dispatch, либо `-march=native` только для локальной сборки.
3. **Корректность семантики.** Векторизация не должна менять наблюдаемое поведение: порядок вычислений при сокращениях (reduction), обработка переполнений, исключений, денормалей, `NaN`, алиасинг.

### 3.3. Условия на стороне кода и данных (главное для практики)

Чтобы векторизация была **возможна**:

- **Отсутствие зависимостей по данным между итерациями** (loop-carried dependence). `a[i] = a[i-1] + b[i]` векторизовать «в лоб» нельзя.
- **Регулярный доступ к памяти**: шаг 1 (unit stride) идеален; шаг 2, 4 — хуже; произвольный индекс (`a[idx[i]]`) требует `gather`.
- **Отсутствие ветвлений**, которые нельзя превратить в маски/`select`. Ветвление внутри цикла часто убивает автовекторизацию; иногда помогает `if-conversion`.
- **Отсутствие вызовов функций**, которые не инлайнятся (либо они должны быть объявлены `inline` / векторизуемыми через `declare simd`).
- **Отсутствие потенциального алиасинга** указателей, мешающего переупорядочиванию: `__restrict` / `std::assume_aligned` / `#pragma ivdep` снимают эту неопределённость.
- **Известное выравнивание** (16/32/64 байта) — для выровненных загрузок; иначе используются `loadu`, которые на современных CPU почти так же быстры, но на старых штрафуются, а на границах страниц могут стоить дорого.
- **Счётчик итераций и границы** должны быть выразимы; «хвост» обрабатывается скалярно или маскированно.
- **Достаточная длина цикла**: накладные расходы на пролог/эпилог окупаются при `n` в десятки-сотни элементов; короткие циклы векторизовать невыгодно.

Чтобы векторизация была **полезна**:

- данные лучше хранить в **SoA** (Structure of Arrays), а не **AoS** (Array of Structures): `struct { float x[N], y[N], z[N]; }` вместо `struct P { float x, y, z; } p[N];`;
- желательно избегать `bool`-массивов, «ступенчатых» структур и указателей в горячем цикле;
- стоит помнить про **закон Амдала**: если 90 % времени в векторизуемой части, ускорение ограничено ~10×.

## 4. Способы использования SIMD в C++

Условно пять уровней — от «ничего не делать руками» до «писать явно».

### 4.1. Автоматическая векторизация компилятором

Самый простой путь: написать чистый цикл и включить оптимизации.

```cpp
void saxpy(float a, const float* __restrict x, float* __restrict y, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i)
        y[i] = a * x[i] + y[i];
}
```

С `-O3 -march=native` (или `/O2 /arch:AVX2`) компилятор сам сгенерирует `vmulps`/`vaddps`/`vfmadd...` и развернёт цикл.

Диагностика:

- GCC: `-fopt-info-vec-optimized`, `-fopt-info-vec-missed`, `-fopt-info-vec-all`;
- Clang: `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize`;
- MSVC: `/Qvec-report:1` (только векторизованные), `/Qvec-report:2` (все, с причинами).

Подсказки компилятору:

```cpp
#pragma GCC ivdep          // «зависимостей нет»
#pragma omp simd           // OpenMP SIMD (нужен -fopenmp-simd)
#pragma clang loop vectorize(enable)
```

Также помогают `__restrict`, `const`, `std::assume_aligned<N>(ptr)`, инлайнинг, отказ от указателей на функции в цикле.

Плюсы: переносимо, читаемо, ничего не надо знать про ISA.
Минусы: результат непредсказуем и сильно зависит от компилятора и флагов; тонкий контроль недоступен.

### 4.2. Intrinsics (встроенные функции)

Явные функции, соответствующие машинным инструкциям. На x86 это заголовок `<immintrin.h>` (включает SSE/AVX/AVX-512), на ARM — `<arm_neon.h>`.

```cpp
#include <immintrin.h>
#include <cstddef>

// dst[i] = a[i] + b[i], AVX2, по 8 float за итерацию
void add8(float* __restrict dst, const float* __restrict a,
          const float* __restrict b, std::size_t n)
{
    std::size_t i = 0;
    for (; i + 8 <= n; i += 8) {
        __m256 va = _mm256_loadu_ps(a + i);   // без требования выравнивания
        __m256 vb = _mm256_loadu_ps(b + i);
        _mm256_storeu_ps(dst + i, _mm256_add_ps(va, vb));
    }
    for (; i < n; ++i)                        // скалярный «хвост»
        dst[i] = a[i] + b[i];
}
```

Типичный набор: `_mm256_set1_ps`, `_mm256_load_ps`/`_mm256_loadu_ps`, `_mm256_add_ps`, `_mm256_mul_ps`, `_mm256_fmadd_ps`, `_mm256_cmp_ps`, `_mm256_blendv_ps`, `_mm256_hadd_ps`, `_mm256_store_ps`.

Плюсы: полный контроль, предсказуемый ассемблер, доступ к FMA/маскам/`shuffle`.
Минусы: непереносимо между архитектурами (x86 ↔ ARM), многословно, легко ошибиться с выравниванием и `vzeroupper`, требуется отдельная обработка хвоста, код надо сопровождать под каждое расширение.

Замечание про переносимость: **Intel intrinsics поддерживаются GCC, Clang и MSVC** на x86, так что между компиляторами x86 код переносится; между архитектурами — нет (для этого есть обёртки вроде `xsimd`, `Highway`, `Vc`).

### 4.3. Векторные расширения компиляторов (GCC/Clang)

Упрощённый, «полуавтоматический» вариант без явных имён инструкций:

```cpp
using v4f = float __attribute__((vector_size(16)));  // 4 float, SSE
using v8f = float __attribute__((vector_size(32)));  // 8 float, AVX

v8f operator+(v8f a, v8f b) { return a + b; }        // покомпонентно

void f(const float* a, const float* b, float* c, std::size_t n) {
    for (std::size_t i = 0; i + 8 <= n; i += 8) {
        v8f va, vb;
        std::memcpy(&va, a + i, sizeof va);          // безопасно по strict aliasing
        std::memcpy(&vb, b + i, sizeof vb);
        v8f vc = va + vb;
        std::memcpy(c + i, &vc, sizeof vc);
    }
}
```

Компилятор сам подберёт инструкции; это переносимее, чем intrinsics, но всё равно нестандартное расширение.

### 4.4. Портативные библиотеки и обёртки

- **`std::experimental::simd`** (Library Fundamentals TS v2, `<experimental/simd>`) и **`std::simd`**, принятый в **C++26** — стандартный, переносимый способ:

  ```cpp
  #include <experimental/simd>
  namespace stdx = std::experimental;

  void add(const float* a, const float* b, float* c, std::size_t n) {
      using V = stdx::native_simd<float>;
      std::size_t i = 0;
      for (; i + V::size() <= n; i += V::size()) {
          V va(a + i, stdx::element_aligned);
          V vb(b + i, stdx::element_aligned);
          (va + vb).copy_to(c + i, stdx::element_aligned);
      }
      for (; i < n; ++i) c[i] = a[i] + b[i];
  }
  ```

  Поддерживается GCC (libstdc++) и Clang (libc++); в MSVC на момент написания — ограниченно.

- **Eigen**, **GLM**, **xsimd**, **Vc**, **Google Highway**, **SLEEF** (векторные математические функции), **oneTBB**/`std::execution` — дают векторные типы и алгоритмы с переносимым API.

### 4.5. Внешние генераторы кода и DSL

- **ISPC** (Intel SPMD Program Compiler) — отдельный язык, компилирующий SPMD-код в SIMD для SSE/AVX/AVX-512/NEON. Удобен для «чисел»: программист пишет программу для одного элемента, а ISPC делает векторизацию и runtime dispatch.
- **OpenMP** `#pragma omp simd` и `std::execution::unseq` / `par_unseq` (C++17/20) — говорят компилятору, что итерации можно выполнять в произвольном порядке и векторизовать.
- **CUDA/OpenCL/HIP/SYCL** — та же идея SIMT на GPU, но это уже другая модель исполнения.

### 4.6. Runtime dispatch (обязателен, если нужна переносимость бинарника)

Нельзя просто собрать всё с `-mavx2` — на старом CPU будет `SIGILL`. Нужно выбирать реализацию во время выполнения:

```cpp
__attribute__((target("avx2")))
void kernel_avx2(const float* a, const float* b, float* c, std::size_t n);

__attribute__((target("default")))
void kernel_scalar(const float* a, const float* b, float* c, std::size_t n);

void dispatch(const float* a, const float* b, float* c, std::size_t n) {
    if (__builtin_cpu_supports("avx2"))
        kernel_avx2(a, b, c, n);
    else
        kernel_scalar(a, b, c, n);
}
```

Варианты: `__builtin_cpu_supports`, `__attribute__((target_clones("avx2","default")))` (GCC/Clang), `cpuid` + указатель на функцию (MSVC), либо готовые библиотеки (Highway, `std::simd` с фиксированным ABI).

## 5. Подводные камни

1. **`SIGILL` из-за флагов.** `-march=native` на сборочной машине → падение на другой. Решение: базовая ISA + dispatch.
2. **Штраф за переход SSE↔AVX.** Смешивание 128-битных SSE-инструкций с «грязной» верхней половиной YMM вызывает пенальти; компилятор вставляет `vzeroupper`. Ручной ассемблерный код должен делать это сам.
3. **Снижение частоты на AVX-512** (на части серверных и клиентских CPU) — иногда AVX2 выгоднее, чем AVX-512. Нужны замеры.
4. **`-ffast-math` и FMA меняют результат.** Переассоциация сокращений и слияние `a*b+c` в FMA меняют биты результата; это ломает воспроизводимость и может ломать сравнения с эталоном. Для точных вычислений — `-ffp-contract=off`, `-fno-fast-math`, явные `std::fma`.
5. **Strict aliasing.** Приведение `float*` к `__m256*` формально нарушает правила алиасинга. Используйте `loadu`/`storeu` или `std::memcpy`.
6. **Выравнивание.** `_mm256_load_ps` требует адрес, кратный 32; иначе — `loadu` или `std::assume_aligned`/`alignas(32)`/`aligned_alloc`.
7. **Денормали и `NaN`.** Векторные блоки могут иметь иные настройки (`FTZ`/`DAZ`), а сравнения с `NaN` ведут себя по-разному в скалярном и векторном коде.
8. **Хвост и малые `n`.** Некорректная обработка остатка — классический источник багов; для AVX-512 есть маскированные операции, для остальных — скалярный цикл.
9. **Иллюзия ускорения.** Если цикл memory-bound, SIMD не поможет; если данных мало — накладные расходы всё съедят. Всегда мерить (`perf`, `VTune`, `benchmark`), а не верить отчёту векторизатора.

## 6. Краткий итог

- **SIMD** — аппаратный параллелизм по данным: одна инструкция обрабатывает вектор элементов в 128/256/512-битных регистрах.
- **Условия:** поддержка ISA процессором **и** ОС; соответствующие флаги/уровень оптимизации компилятора; отсутствие зависимостей по данным и «плохой» адресации в цикле; подходящая раскладка данных (SoA, выравнивание, непрерывность); достаточная длина цикла и вычислительная (а не memory-bound) нагрузка.
- **Способы:** автовекторизация компилятором (+ pragma/`restrict`) → векторные расширения GCC/Clang → intrinsics (`<immintrin.h>`, `<arm_neon.h>`) → портативные библиотеки (`std::simd`/`std::experimental::simd`, Eigen, xsimd, Highway) → специализированные компиляторы (ISPC) и GPU-модели.
- **Для переносимого бинарника** обязателен runtime dispatch по CPUID с базовой скалярной версией; оптимум подтверждается только измерениями.
