# 46. Какие есть подходы к оптимизации кода?

Оптимизация — это не набор трюков, а инженерный процесс: **сначала измерение, потом изменение, потом повторное измерение**. При этом важно помнить закон Амдала: ускорение ограничено той долей времени, которую занимает оптимизируемый участок. Если функция занимает 2 % времени программы, её ускорение в 10 раз даст не более 1,8 % общего выигрыша.

Подходы удобно рассматривать как иерархию: чем выше уровень, тем больше потенциальный выигрыш и тем дешевле изменение.

| Уровень | Типичный выигрыш | Примеры |
|---|---|---|
| Архитектура и алгоритмы | 10–1000× | выбор сложности, устранение лишней работы, кэширование |
| Данные и память | 2–10× | layout, локальность, аллокаторы, AoS/SoA |
| Компилятор и линковка | 1,1–3× | `-O3`, LTO, PGO, `-march=native` |
| Микрооптимизации | 1,05–1,5× | branch hints, unrolling, SIMD, prefetch |

## 1. Методология: без профилирования оптимизации нет

Главная ошибка — оптимизировать «по интуиции». Интуиция плохо предсказывает, где реально проводят время современные процессоры: узким местом часто оказываются не вычисления, а промахи кэша, аллокации, системные вызовы, блокировки или ожидание I/O.

Базовый цикл:

1. **Сформулировать метрику**: wall-time, CPU-time, пропускная способность, latency p99, потребление памяти, энергопотребление, размер кода.
2. **Собрать релизную сборку** с теми же флагами, что в production, и с репрезентативными данными.
3. **Снять профиль**: `perf`, Intel VTune, AMD uProf, Callgrind, Tracy, встроенные счётчики.
4. **Найти горячие точки** и понять их природу: вычисления, память, ветвления, блокировки, I/O.
5. **Внести минимальное изменение** и измерить его эффект.
6. **Проверить корректность**: тесты, sanitizers, сравнение результатов.
7. **Закрепить бенчмарк в CI**, чтобы не допустить регрессии.

Полезные метрики процессора:

- `cycles`, `instructions`, `IPC` — насколько эффективно используются конвейеры;
- `cache-misses`, `LLC-load-misses` — проблемы локальности;
- `branch-misses` — плохо предсказуемые ветвления;
- `page-faults`, `context-switches` — давление на память и ОС;
- число аллокаций и системных вызовов.

Инструменты: `perf stat`, `perf record`, `perf c2c` (false sharing), `perf mem`, VTune, Callgrind/Cachegrind, `heaptrack`, `massif`. Санитайзеры (`ASan`, `UBSan`, `TSan`) — не для ускорения, а для поиска UB и гонок, которые могут ломать оптимизации.

## 2. Алгоритмический и архитектурный уровень

Самый большой выигрыш даёт не микрооптимизация, а правильный алгоритм и устранение ненужной работы.

- **Снижение сложности**: `O(n²)` → `O(n log n)` или `O(n)`. Например, замена вложенного поиска по массиву на `std::unordered_set` или сортировку + бинарный поиск.
- **Устранение лишних вычислений**: вынести инварианты из цикла, не пересчитывать то, что не изменилось, ранний выход.
- **Мемоизация и кэширование**: сохранение результатов дорогих чистых функций; кэш на уровне объекта или системы.
- **Ленивые вычисления**: не считать то, что может не понадобиться; отложенная инициализация.
- **Пакетная обработка**: обрабатывать данные блоками, чтобы амортизировать накладные расходы на вызов, аллокацию, I/O.
- **Изменение постановки задачи**: приближённые вычисления, семплирование, эвристики, предвычисления, асимптотически более дешёвая структура данных.
- **Выбор структуры данных под паттерн доступа**: `vector` для последовательного обхода, `flat_map`/отсортированный массив для статического набора, хеш-таблица для поиска, дерево для упорядоченного обхода.

Важно: алгоритмическая оптимизация почти всегда важнее, чем замена `i++` на `++i`.

## 3. Уровень памяти и данных

Современные процессоры потребляют данные быстрее, чем память успевает их отдавать. Поэтому **локальность данных** часто важнее количества инструкций.

### 3.1 Кэш-локальность

- Обходить данные последовательно, а не «прыгать» по указателям.
- Уменьшать размер рабочих наборов, чтобы они помещались в L1/L2.
- Разделять горячие и холодные данные.
- Избегать «погони за указателями» (pointer chasing) в горячих циклах.

### 3.2 AoS vs SoA и data-oriented design

Классический ООП-подход часто хранит объекты как AoS (Array of Structures):

```cpp
struct Particle {
    float x, y, z;      // горячие данные
    float vx, vy, vz;
    std::string name;   // холодные данные
    Texture* texture;   // ещё одна indirection
};
std::vector<Particle> particles;
```

Если в цикле нужны только координаты и скорости, лучше вынести горячие поля в отдельные массивы (SoA):

```cpp
struct Particles {
    std::vector<float> x, y, z;
    std::vector<float> vx, vy, vz;
    std::vector<std::string> names;
};
```

Это уменьшает stride, улучшает кэширование и позволяет компилятору векторизовать цикл. Такой подход называют **data-oriented design**: проектировать не «объекты», а данные и операции над ними.

### 3.3 Layout структур

Порядок полей влияет на размер и число cache line:

```cpp
struct Bad {
    char c;     // 1 + 3 padding
    int i;      // 4
    char d;     // 1 + 7 padding
    double x;   // 8
};              // sizeof == 24

struct Good {
    double x;   // 8
    int i;      // 4
    char c;     // 1
    char d;     // 1 + 2 padding
};              // sizeof == 16
```

Правило: сортировать поля по убыванию выравнивания. Полезны `alignas`, `[[no_unique_address]]` (C++20), EBO (empty base optimization) и аккуратное использование битовых полей. Но `#pragma pack` и `__attribute__((packed))` могут приводить к невыровненному доступу и падению производительности — применять только осознанно.

### 3.4 Аллокации

Аллокация — одна из самых дорогих операций в горячем коде. Подходы:

- **Резервировать заранее**: `reserve`, `resize`, пулы.
- **Переиспользовать память**: арены, object pool, free list.
- **Уменьшать число аллокаций**: `make_shared` вместо двух `shared_ptr`, `std::pmr`, `small buffer optimization`.
- **Кастомные аллокаторы**: `std::pmr::monotonic_buffer_resource`, arena-аллокаторы, `jemalloc`/`tcmalloc`/`mimalloc` для общего случая.
- **Избегать лишних копий**: move-семантика, `string_view`, `span`, передача по ссылке.

```cpp
std::pmr::monotonic_buffer_resource pool;
std::pmr::vector<int> v(&pool);
v.reserve(1024);
```

### 3.5 False sharing

Если два потока пишут в разные переменные, попавшие в одну cache line, кэш-линия постоянно инвалидируется. Лечится выравниванием и разносом данных:

```cpp
struct alignas(64) Counter {
    std::atomic<long> value{0};
};
```

Порог обычно 64 байта, но лучше использовать `std::hardware_destructive_interference_size` (C++17), если он доступен.

## 4. OOP/OOD-специфика

ООП даёт абстракции, но каждая абстракция имеет цену: виртуальный вызов, indirection, аллокация, копирование, RTTI. Задача — **не убрать абстракции вообще, а сделать их zero-cost там, где это важно**.

### 4.1 Динамический полиморфизм

Виртуальный вызов — это косвенный переход. Сам по себе он не катастрофичен: современные предсказатели хорошо справляются с мономорфными вызовами. Проблема в том, что он **мешает инлайну и оптимизациям**, а в полиморфном цикле может быть плохо предсказуем.

Подходы:

- **`final`** для классов и методов — даёт компилятору право на девиртуализацию.
- **LTO/PGO** — межмодульная и профильная девиртуализация.
- **Группировка по типу** — вместо `for (auto* s : shapes) s->area();` обходить однородные контейнеры и вызывать невиртуальные функции.
- **CRTP** — статический полиморфизм без vtable:

```cpp
template <class Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
};

struct Circle : Shape<Circle> {
    double area_impl() const { return 3.14159 * r * r; }
    double r;
};
```

- **`std::variant` + `std::visit`** — закрытое множество типов без виртуальных вызовов и без динамических аллокаций:

```cpp
using Shape = std::variant<Circle, Square>;

double area(const Shape& s) {
    return std::visit([](const auto& x) { return x.area(); }, s);
}
```

- **Type erasure** (`std::function`, ручная vtable) — когда нужен полиморфизм, но не нужно наследование. Помнить, что `std::function` может аллоцировать память при больших захватах; в горячем коде лучше `function_ref` (C++26) или шаблонный параметр.

### 4.2 Копирование и владение

- **Rule of Zero**: не писать деструктор/копирование/перемещение, если можно использовать RAII-члены.
- **Rule of Five**: если нужен хотя бы один из специальных методов — рассмотреть все пять.
- **Move-семантика**: перемещение должно быть `noexcept`, иначе `std::vector` при реаллокации будет копировать, а не перемещать.
- **Copy elision и RVO**: возвращать объект по значению часто быстрее и безопаснее, чем через выходной параметр; в C++17 для prvalue elision обязателен.
- **`emplace_back` vs `push_back`**: `emplace` конструирует на месте, но может проигрывать при неявных преобразованиях; `push_back` с готовым объектом часто яснее.
- **Передача по значению + move** для sink-параметров; `const&` для чтения; `std::string_view`/`std::span` для невладеющих представлений.

```cpp
std::vector<Foo> v;
v.reserve(n);
for (int i = 0; i < n; ++i) {
    v.emplace_back(args...);   // без промежуточного временного объекта
}
```

### 4.3 Layout объектов и наследование

- Глубокие иерархии и множественное наследование усложняют layout, добавляют padding и indirection.
- Виртуальные базовые классы — дорогая косвенность; применять только при реальной необходимости.
- **Pimpl** (`std::unique_ptr<Impl>`) уменьшает зависимости при сборке и стабилизирует ABI, но добавляет разыменование указателя и отдельную аллокацию. В горячем коде это может быть заметно.
- **EBO** позволяет пустым базовым классам не занимать память; `[[no_unique_address]]` делает то же для членов.
- Композиция часто дешевле наследования: меньше vtable, меньше косвенности, проще layout.

### 4.4 Мелкие объекты

- **Small Buffer Optimization** (SSO) в `std::string`, `std::function`, `std::any`: мелкие объекты хранятся внутри, без heap-аллокации.
- **Пул объектов** для часто создаваемых/удаляемых мелких объектов.
- **Intrusive-контейнеры** и intrusive refcount: меньше отдельных аллокаций и лучше локальность.
- **`std::shared_ptr`**: атомарный refcount — недешёвая операция; копирование `shared_ptr` в горячем цикле может быть узким местом. `std::make_shared` делает одну аллокацию вместо двух. `weak_ptr::lock()` также атомарен.
- **`std::optional`/`std::variant`** могут увеличивать размер объекта; следить за `sizeof`.

### 4.5 Абстракции без накладных расходов

C++ позволяет сохранить абстракцию и получить производительность:

- шаблоны и CRTP вместо виртуальных вызовов;
- `constexpr`/`consteval` для вычислений на этапе компиляции;
- `std::array`, `std::span`, `std::string_view` вместо владеющих контейнеров там, где владение не нужно;
- concepts (C++20) для читаемых ограничений шаблонов;
- `if constexpr` для выбора реализации без runtime-ветвлений;
- policy-based design, когда политика известна на этапе компиляции.

Но у шаблонов есть обратная сторона: **раздувание кода** (code bloat), давление на I-cache и время сборки. Иногда виртуальный вызов выгоднее десяти инстанцирований шаблона.

### 4.6 Исключения, RTTI, `thread_local`

- Исключения в Itanium ABI имеют нулевую стоимость на «счастливом пути», но раздувают бинарник таблицами и мешают некоторым оптимизациям. `noexcept` важен для move-семантики и контейнеров.
- `dynamic_cast` и `typeid` заметно дороже виртуального вызова; в горячем коде их лучше избегать. `-fno-rtti` возможен, но ломает `dynamic_cast`/`typeid` и некоторые библиотеки.
- `thread_local` может быть дорогим из-за TLS-доступа и guard-проверок; не стоит использовать его в tight loop без необходимости.

## 5. Компилятор, линковка и флаги

Компилятор — самый дешёвый источник ускорения, если правильно выбраны флаги.

| Флаг | Что даёт | Оговорки |
|---|---|---|
| `-O2` | базовые оптимизации, хороший баланс | обычно безопасный выбор |
| `-O3` | агрессивная векторизация, инлайнинг | может увеличить код и ухудшить I-cache |
| `-Os` | оптимизация по размеру | полезно для embedded и больших бинарников |
| `-flto` | межмодульный инлайнинг и девиртуализация | дольше сборка, нужен на этапе link |
| `-fprofile-generate` / `-fprofile-use` | PGO: оптимизация под реальный профиль | требует прогона на репрезентативных данных |
| `-march=native` | использование инструкций конкретного CPU | бинарник не переносим на другие машины |
| `-mtune=native` | настройка под CPU без изменения набора инструкций | безопаснее, чем `-march=native` |
| `-ffast-math` | быстрая, но не IEEE-строгая математика | ломает NaN/Inf, ассоциативность, `-0.0` |
| `-fno-exceptions`, `-fno-rtti` | меньше кода и таблиц | ломает стандартную библиотеку и часть API |
| `-fvisibility=hidden` | меньше PLT и символов | нужно явно экспортировать API |
| `-fno-semantic-interposition` | инлайнинг через границы shared library | в основном GCC/Clang |
| `-fno-plt` | прямые вызовы вместо PLT | уменьшает косвенность |
| `-DNDEBUG` | отключает `assert` | меняет поведение, применять осознанно |
| `-g` | отладочная информация | обычно не влияет на скорость, полезно для профилирования |
| `-fno-omit-frame-pointer` | удобные stack traces | небольшой overhead, полезно для профилей |

Дополнительно:

- **LTO** и **PGO** часто дают больше, чем ручные микрооптимизации.
- **BOLT** — пост-линковый оптимизатор для улучшения layout кода.
- **Unity builds**, precompiled headers, C++20 modules — ускоряют сборку, но не runtime.
- **Компоновка**: `-Wl,-O1`, `--as-needed`, удаление неиспользуемых секций (`-ffunction-sections -fdata-sections -Wl,--gc-sections`).
- **Аллокатор**: `jemalloc`, `tcmalloc`, `mimalloc` могут заметно ускорить многопоточные приложения с интенсивными аллокациями.
- **Huge pages** и `madvise(MADV_HUGEPAGE)` уменьшают TLB-промахи на больших рабочих наборах.

## 6. Микрооптимизации

Это самый нижний уровень; к нему стоит переходить, когда алгоритмы и память уже в порядке.

- **Подсказки ветвления**: `[[likely]]`/`[[unlikely]]` (C++20), `__builtin_expect`, `__assume` (MSVC).
- **`restrict`/`__restrict`**: сообщает компилятору об отсутствии алиасинга и помогает векторизации.
- **Разворачивание циклов**: вручную или через `#pragma unroll`; современные компиляторы часто делают это сами.
- **Векторизация**: авто-векторизация при `-O3`, проверка через `-fopt-info-vec` (GCC) или `-Rpass=loop-vectorize` (Clang); при необходимости — intrinsics (`<immintrin.h>`) или `std::simd` (C++26).
- **Prefetch**: `__builtin_prefetch` для предсказуемых обращений; злоупотребление может навредить.
- **Устранение делений и модулей** в горячих циклах: заменять на сдвиги/умножения, если возможно.
- **Strength reduction**: заменять дорогие операции более дешёвыми эквивалентами.
- **Bit tricks**: `std::popcount`, `std::countr_zero`, `std::bit_ceil` (C++20).
- **`memcpy`/`std::bit_cast`** вместо ручного копирования и type punning; не нарушать strict aliasing.
- **Уменьшение зависимостей по данным**: разрывать длинные цепочки вычислений, чтобы загружать конвейер.
- **Горячие/холодные секции**: `[[gnu::hot]]`, `[[gnu::cold]]`, вынос обработки ошибок из горячего пути.

```cpp
if (__builtin_expect(x > 0, 1)) {
    // горячий путь
} else {
    // редкий путь
}
```

```c
void add(int* restrict a, const int* restrict b, const int* restrict c, size_t n);
```

Важно: микрооптимизации почти всегда **специфичны для платформы и компилятора**. Их нужно измерять на целевом железе и защищать бенчмарками.

## 7. Конкурентность

Многопоточность может как ускорить, так и замедлить программу из-за конкуренции за данные.

- **Уменьшать разделяемое изменяемое состояние**: thread-local данные, шардирование, иммутабельность.
- **Уменьшать granularity блокировок**: fine-grained locks, `std::shared_mutex`, lock-free структуры.
- **Избегать false sharing**: выравнивание, padding, разнос горячих переменных по cache line.
- **Правильные memory order**: `relaxed` там, где достаточно; `acquire/release` для синхронизации; `seq_cst` только при необходимости.
- **Батчинг**: собирать работу в пакеты, чтобы амортизировать синхронизацию.
- **Пул потоков** вместо создания потока на задачу.
- **NUMA-aware** размещение данных и affinity потоков.
- **Избегать избыточных `shared_ptr`**: атомарный refcount — точка конкуренции.

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);
```

## 8. Ввод-вывод и системный уровень

Для многих приложений узким местом является не CPU, а I/O.

- **Буферизация**: `std::ios::sync_with_stdio(false)`, `std::cin.tie(nullptr)`, `'\n'` вместо `std::endl`.
- **Батчинг syscall'ов**: `writev`, `readv`, `io_uring`, асинхронный I/O.
- **Zero-copy**: `sendfile`, `splice`, `mmap` вместо копирования через пользовательский буфер.
- **Уменьшение числа копий**: `string_view`, `span`, move-семантика, RVO.
- **Сжатие** — компромисс между CPU и сетью/диском.
- **Кэширование** результатов дорогих запросов.
- **Латентность vs пропускная способность**: иногда лучше пожертвовать throughput ради p99.

## 9. Типичные ошибки и антипаттерны

- **Преждевременная оптимизация** без профиля и метрик.
- **Оптимизация холодного кода**: 90 % времени может быть в 10 % кода.
- **Микробенчмарк, не отражающий реальную нагрузку**: другие данные, размеры, конкурентность, железо.
- **Мёртвый код в бенчмарке**: компилятор выбросил вычисление, и «ускорение» оказалось фикцией. Использовать `DoNotOptimize`/`ClobberMemory` (Google Benchmark) или `asm volatile`.
- **Игнорирование аллокаций**: `std::string` в цикле, `shared_ptr` в горячем пути, `std::function` с большими захватами.
- **`std::endl`** вместо `'\n'` — лишний flush.
- **`std::map`/`std::unordered_map`** там, где достаточно отсортированного `vector` или `flat_map`.
- **`dynamic_cast` и виртуальные вызовы в tight loop** без необходимости.
- **Копирование больших объектов** при передаче по значению.
- **`std::move` на `const`-объекте** — move не произойдёт, будет копирование.
- **Range-for по значению** для тяжёлых объектов.
- **Нарушение strict aliasing** и другие UB — компилятор может «сломать» внешне корректный код.
- **`-ffast-math`** там, где важна IEEE-совместимость.
- **`-march=native`** в бинарнике, который должен работать на других машинах.
- **Отключение исключений/RTTI** без понимания последствий для стандартной библиотеки.
- **Оптимизация ради самой оптимизации** в ущерб читаемости и сопровождаемости.

## 10. Практический порядок действий

1. **Определить цель**: latency, throughput, память, энергия, размер кода.
2. **Собрать релизную версию** и воспроизвести проблему на реалистичных данных.
3. **Снять профиль** и найти топ горячих точек.
4. **Проверить алгоритмическую сложность** и число операций.
5. **Проверить память**: аллокации, копирования, layout, кэш-промахи.
6. **Проверить абстракции**: виртуальные вызовы, `shared_ptr`, `dynamic_cast`, лишние indirection.
7. **Применить минимальное изменение** на самом выгодном уровне.
8. **Измерить** и сравнить с базовой линией, а не с ожиданиями.
9. **Проверить корректность**: тесты, sanitizers, edge cases.
10. **Закрепить результат** бенчмарком в CI и кратко задокументировать решение.

## Итог

Оптимизация в C/C++ — это последовательность:

**алгоритм → структуры данных и память → устранение лишних абстракций и копирований → компилятор и линковка → микрооптимизации → конкурентность и I/O**.

ООП-абстракции не являются злом: виртуальные вызовы, наследование и инкапсуляция дают гибкость и сопровождаемость. Но в горячем коде их стоимость нужно измерять и при необходимости заменять на статический полиморфизм (CRTP, шаблоны, `std::variant`), более компактный layout, move-семантику, пулы и арены. Главное правило: **сначала корректность и измерения, потом оптимизация — и всегда с проверкой, что стало действительно быстрее**.
