# 1. Как вы понимаете SOLID?

**SOLID** — это не набор обязательных правил и не «стандарт языка», а пять эвристик проектирования, собранных в акроним Майклом Фезерсом (Michael Feathers) и популяризированных Робертом Мартином (Robert C. Martin, «Uncle Bob»). Сами принципы появились в разное время и у разных авторов: LSP — у Барбары Лисков (1987), OCP — у Бертрана Мейера (1988), остальные — из работ Мартина 1990-х и начала 2000-х.

Ключевая мысль, которая их объединяет: **управлять зависимостями так, чтобы изменения оставались локальными, а код — понятным и тестируемым**. SOLID — это про стоимость изменения, а не про «красоту» классов. Именно поэтому принципы полезны как вопросы к дизайну, а не как догма.

| Принцип | О чём | Ключевой вопрос | Типичный симптом нарушения |
|---|---|---|---|
| **S** — Single Responsibility | Одна причина для изменения | «Кто/что заставит этот код меняться?» | Класс «на все случаи», конфликтующие изменения |
| **O** — Open/Closed | Открыт для расширения, закрыт для изменения | «Что придётся править при добавлении варианта?» | `switch`/`if` по типу, растущий по мере новых требований |
| **L** — Liskov Substitution | Подтип заменяет надтип без сюрпризов | «Можно ли подставить наследника, не сломав клиента?» | `NotSupportedException`, проверки `is`/`as`, пустые override |
| **I** — Interface Segregation | Много маленьких интерфейсов лучше одного «толстого» | «Зависят ли клиенты от того, что им не нужно?» | Интерфейсы-«швейцарские ножи», заглушки в реализациях |
| **D** — Dependency Inversion | Зависимость от абстракций, а не от деталей | «Куда направлена стрелка зависимости?» | `new` инфраструктуры внутри бизнес-логики |

---

## S — Single Responsibility Principle (принцип единственной ответственности)

**Классическая формулировка:** у класса должна быть одна, и только одна, причина для изменения.

**Уточнение из Clean Architecture:** модуль должен отвечать перед одним и только одним **актором** — группой людей (ролью, отделом), которая формулирует требования к этому коду. Это важно: «ответственность» — не «одно действие» и не «один метод», а **источник изменений**.

```csharp
// Нарушение: три разных актора — бухгалтерия, HR и DBA
public class Employee
{
    public decimal CalculatePay() { /* правила оплаты */ }
    public string ReportHours()  { /* формат отчёта для HR */ }
    public void Save()           { /* схема таблицы в БД */ }
}
```

Проблема проявляется не сразу: бухгалтерия просит изменить расчёт премии, и правка в `CalculatePay` случайно ломает `ReportHours`, потому что оба используют общий приватный метод. Изменения разных акторов начинают конфликтовать, а тестировать и переиспользовать такой класс тяжело.

**Как исправить:** разделить по причинам изменения — `EmployeeData` (данные), `PayCalculator`, `HoursReporter`, `EmployeeRepository`. Каждый класс меняется по своему поводу.

**Нюанс:** SRP не означает «один метод на класс» и не требует дробить всё до бесконечности. Речь о **связности (cohesion)**: всё, что меняется вместе и по одной причине, может жить вместе. SRP применим на любом масштабе — функция, класс, модуль, сервис.

## O — Open/Closed Principle (принцип открытости/закрытости)

**Формулировка Мейера:** программные сущности должны быть открыты для расширения, но закрыты для изменения.

Смысл: добавление нового поведения не должно требовать правок в уже работающем и протестированном коде. Классический антипример:

```csharp
public decimal Area(Shape shape) => shape switch
{
    Circle c => Math.PI * c.Radius * c.Radius,
    Square s => s.Side * s.Side,
    _ => throw new NotSupportedException()
};
```

Каждая новая фигура — это правка метода, а значит, риск сломать существующие ветки и перепроверять всё. Решение — полиморфизм или стратегия:

```csharp
public interface IShape { decimal Area(); }

public sealed class Circle : IShape
{
    public double Radius { get; init; }
    public decimal Area() => (decimal)(Math.PI * Radius * Radius);
}
```

**Практическая оговорка:** нельзя быть закрытым от *любых* изменений — это утопия. OCP всегда означает «закрыт для тех изменений, которые мы предусмотрели», то есть выбранные **оси расширения**. Обычно это становится ясно после второго-третьего реального изменения, а не до написания кода. Поэтому OCP и YAGNI нужно уравновешивать: абстракция «на будущее» без подтверждённой потребности — это преждевременное усложнение.

Технически OCP чаще всего достигается через DIP (абстракция) + LSP (корректная подстановка реализаций), а на уровне архитектуры — через плагины, события, версионируемые API.

## L — Liskov Substitution Principle (принцип подстановки Лисков)

**Формулировка:** если `S` — подтип `T`, то объекты `T` можно заменить объектами `S`, не нарушая корректность программы.

Это самый формальный принцип, и он про **поведение**, а не про синтаксис наследования. Подтип обязан соблюдать контракт надтипа:

- не усиливать предусловия (не требовать от клиента большего);
- не ослаблять постусловия (не обещать меньшего);
- сохранять инварианты;
- не нарушать «историю» (изменения состояния должны быть совместимы).

Хрестоматийный пример:

```csharp
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
}

public class Square : Rectangle
{
    public override int Width  { set => base.Width = base.Height = value; }
    public override int Height { set => base.Width = base.Height = value; }
}
```

Клиент, работающий с `Rectangle`, делает `Width = 5; Height = 4;` и ожидает площадь 20, а получает 16. Формально `Square` — наследник, фактически — нарушитель контракта.

**Симптомы нарушения:** `throw new NotSupportedException()` в переопределённом методе, проверки `if (x is Square)`, пустые реализации, «наследник, который не совсем наследник».

**Как исправить:** не строить иерархию там, где поведение различается; использовать композицию; делать неизменяемые типы; выделять общий интерфейс только по реально общим операциям.

**Нюанс:** LSP касается не только наследования классов, но и любых форм полиморфизма — интерфейсов, утиной типизации, подмены реализаций в тестах. Мок, который ведёт себя не как реальный объект, — тоже нарушение LSP по духу.

## I — Interface Segregation Principle (принцип разделения интерфейсов)

**Формулировка:** клиенты не должны зависеть от методов, которые они не используют; много специализированных интерфейсов лучше одного универсального.

```csharp
// «Толстый» интерфейс
public interface IWorker
{
    void Work();
    void Eat();
}

public class Robot : IWorker
{
    public void Work() { }
    public void Eat() => throw new NotSupportedException(); // запах
}
```

Робот вынужден реализовывать `Eat`, хотя эта операция к нему неприменима. Любое изменение «человеческой» части интерфейса задевает и робота, и всех клиентов, которым нужен только `Work`.

**Как исправить:** разделить по ролям клиентов:

```csharp
public interface IWorkable { void Work(); }
public interface IFeedable { void Eat(); }

public class Robot : IWorkable { public void Work() { } }
public class Human : IWorkable, IFeedable { /* ... */ }
```

**Нюанс:** ISP — это не «интерфейс на каждый метод». Интерфейсы выделяются по **клиентам и их потребностям**, а не по количеству операций. Слишком мелкие интерфейсы дают другую проблему — размытие контракта и трудность понимания. Ориентир: интерфейс должен описывать одну роль в системе. ISP работает и на уровне модулей/сервисов: публичный API, который тянет за собой половину системы ради одной функции, — тоже нарушение.

## D — Dependency Inversion Principle (принцип инверсии зависимостей)

**Две формулировки:**

1. Модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба должны зависеть от абстракций.
2. Абстракции не должны зависеть от деталей; детали должны зависеть от абстракций.

```csharp
// Нарушение: бизнес-логика знает про MySQL
public class OrderService
{
    private readonly MySqlOrderRepository _repo = new MySqlOrderRepository();
}
```

Здесь высокоуровневая политика (оформление заказа) намертво привязана к детали (конкретная СУБД). Заменить хранилище или подставить фейк в тесте можно только правкой самого сервиса.

```csharp
// Абстракция объявлена там, где живёт политика (в домене)
public interface IOrderRepository { void Save(Order order); }

public class OrderService
{
    private readonly IOrderRepository _repo;
    public OrderService(IOrderRepository repo) => _repo = repo;
}
```

**Ключевой момент, который часто упускают:** «инверсия» — это не просто «вынести интерфейс». Это **смена направления зависимости**: интерфейс принадлежит верхнему уровню (клиенту), а нижний уровень (БД, HTTP, файлы) его реализует. Стрелка исходного кода направлена от деталей к политике, а не наоборот. Именно это позволяет домену не зависеть от фреймворка и инфраструктуры.

**Нюансы:**

- **DIP ≠ DI.** Dependency Injection — это техника передачи зависимостей извне; DIP — принцип о направлении зависимостей. Можно применять DI без DIP (инжектить конкретный класс) и наоборот.
- Не каждый класс нуждается в интерфейсе. Абстракция оправдана там, где есть **нестабильность** (реальная вероятность замены) или **граница** между слоями; плодить интерфейсы «на всякий случай» — вред.
- DIP не отменяет композиционный корень (composition root), где конкретные реализации всё же создаются, — важно, чтобы это было в одном месте, а не размазано по логике.

## Как принципы связаны между собой

SOLID — не пять независимых лозунгов, а связная система:

- **SRP и ISP** решают одну задачу с разных сторон: уменьшают связность и количество причин для изменения (класс — по акторам, интерфейс — по клиентам).
- **OCP** почти всегда опирается на **DIP** (абстракция как точка расширения) и **LSP** (расширение обязано быть корректной подстановкой).
- **LSP** — фундамент любого полиморфизма: без него OCP превращается в ловушку, где «расширение» ломает клиентов.
- **DIP** задаёт направление зависимостей, а **SRP/ISP** — их количество и форму.

На уровне архитектуры те же идеи масштабируются: SRP → границы сервисов по бизнес-возможностям, OCP → версионирование API, LSP → совместимость контрактов, ISP → узкие API под конкретных потребителей, DIP → домен не зависит от транспорта и БД (правило зависимостей в Clean Architecture).

## Чего SOLID не означает (типичные заблуждения)

1. **«SRP = один метод на класс».** Нет. Ответственность — это причина изменения, а не размер класса.
2. **«DIP = обязательно DI-контейнер».** Контейнер — удобство, а не суть принципа.
3. **«OCP = никогда не менять существующий код».** Менять можно и нужно; цель — локализовать изменения, а не запретить их.
4. **«ISP = интерфейс на каждый метод».** Дробление ради дробления ухудшает читаемость.
5. **«Нарушение SOLID — всегда ошибка».** В скрипте на 50 строк, в CRUD-эндпоинте или в прототипе «правильный» SOLID-дизайн может стоить дороже, чем приносит пользы.
6. **«SOLID — научная теория».** Это набор эвристик разного происхождения и разной степени формальности (по-настоящему формален только LSP). У него есть обоснованная критика: чрезмерное следование ведёт к лишним абстракциям, «прыжкам» по файлам и усложнению навигации.

## Как я применяю это на практике

- **Рассматриваю SOLID как вопросы, а не как чек-лист.** «Сколько акторов меняют этот класс?», «Что придётся править при добавлении N-го варианта?», «Не зависит ли клиент от лишнего?», «Куда смотрит зависимость?»
- **Абстрагирую по факту изменений, а не по фантазии.** Первый раз пишу просто; увидев второе-третье реальное изменение по одной оси — ввожу точку расширения. Это примирение OCP с YAGNI.
- **Держу границы там, где они окупаются:** домен ↔ инфраструктура, бизнес-логика ↔ UI/транспорт, стабильное ядро ↔ волатильные детали.
- **Проверяю дизайн тестами:** если тест на бизнес-правило требует поднять БД или HTTP-сервер — вероятно, нарушен DIP. Если тест заставляет реализовывать кучу ненужных методов — вероятно, нарушен ISP. Если тест на наследника приходится писать с оговорками — вероятно, нарушен LSP.
- **Помню про цену абстракции.** Каждый интерфейс, слой и «точка расширения» — это стоимость поддержки и когнитивная нагрузка. SOLID — средство снизить стоимость изменений, а не цель сама по себе. Если абстракция не окупается, она вредна ровно так же, как и её отсутствие.

**Итог:** SOLID я понимаю как компактный набор ориентиров о том, как распределять ответственности и направлять зависимости, чтобы система переживала изменения. Сила этих принципов — в осознанном применении: они отвечают на вопрос «где провести границу и в какую сторону направить стрелку зависимости», но не отменяют здравого смысла, чувства меры и знания конкретной предметной области.
