# 5. Какие есть проблемы при написании кроссплатформенного кода? На что обращать внимание?

Кроссплатформенность — это не одно свойство, а целый спектр. Можно говорить о переносимости **исходного кода** (компилируется под разные ОС), **бинарной** (JVM, .NET, WASM), **данных и протоколов** (сеть, форматы файлов) и **пользовательского интерфейса**. Отдельно стоит помнить знаменитую формулу: *«write once, run anywhere»* на практике чаще превращается в *«write once, compile everywhere, test everywhere and fix everywhere»*.

Ниже — основные группы проблем и то, на что смотреть в каждой из них.

---

## 1. Файловая система и пути

Это, пожалуй, источник №1 практических багов.

| Аспект | Windows | Linux | macOS |
|---|---|---|---|
| Разделитель | `\` (но API часто принимает и `/`) | `/` | `/` |
| Регистр | обычно нечувствителен, но с сохранием | чувствителен | обычно нечувствителен (APFS/HFS+) |
| Диски | буквы `C:`, UNC `\\server\share` | единое дерево | единое дерево, `/Volumes` |
| Длина пути | исторически 260 символов | ограничена `PATH_MAX` (обычно 4096) | около 1024 |
| Кодировка имён | UTF-16 | байты (обычно UTF-8) | UTF-8, но с нормализацией Unicode |
| Запрещённые символы | `< > : " / \ | ? *`, имена `CON`, `PRN`, `AUX`, `NUL`, `COM1…`, точки/пробелы в конце | только `/` и `\0` | в основном как в Linux, но `/` и `:` особые |
| Симлинки | требуют прав/режима разработчика | обычное дело | обычное дело |
| Блокировки | мандатные, нельзя удалить открытый файл | advisory (`flock`/`fcntl`) | advisory |
| Смена регистра | нет | да | да (на нечувствительной ФС — нет) |

Типичные ошибки:

- Склеивание путей строками: `dir + "/" + name` — ломается на Windows и при нестандартных разделителях. Используйте `std::filesystem::path`, `pathlib` в Python, `Path.Combine` в .NET.
- Уверенность, что `File.txt` и `file.txt` — разные файлы. На Linux это разные файлы, на Windows/macOS — один. Код, который «случайно работал» на Linux, на Windows может перезаписать файл.
- Забыли, что путь может содержать пробелы (`C:\Program Files`), кириллицу (`C:\Users\Иван`), эмодзи, очень длинный путь.
- Ожидание, что `rename` атомарно заменяет существующий файл. На POSIX — да, на Windows исторически — нет; для атомарной замены нужны `ReplaceFileW`/`MoveFileExW` с `MOVEFILE_REPLACE_EXISTING`.
- Запись «во временный файл и переименование» без `fsync` каталога на POSIX и без учёта особенностей Windows.
- Хардкод `/tmp`, `~`, `/usr/local`. Правильно — `std::filesystem::temp_directory_path()`, `TMPDIR`/`TEMP`/`TMP`, XDG Base Directory на Linux, `~/Library/...` на macOS, `%APPDATA%`/`%LOCALAPPDATA%` на Windows.
- Открытие файла с не-ASCII именем через `std::fopen` на Windows: узкий `fopen` использует ANSI-кодовую страницу и просто не откроет `C:\Users\Иван\...`. Нужны широкие API (`_wfopen`, `std::filesystem`) или манифест с UTF-8 ACP.

```cpp
// Плохо: зависит от разделителя и кодировки
std::string path = dir + "/" + name;

// Хорошо: путь — это тип, а не строка
auto path = std::filesystem::path{dir} / name;
```

## 2. Текст: кодировки, переводы строк, Unicode

- **Переводы строк.** Windows — `CRLF`, Unix — `LF`, старый Mac — `CR`. Если не настроить `.gitattributes`, скрипты с shebang ломаются (`/bin/bash^M: bad interpreter`), а diff'ы «шумят». Помогает:

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.ps1 text eol=crlf
```

- **Кодировки.** Внутри программы лучше везде UTF-8, а на границах (файлы, консоль, аргументы, API ОС) — явно преобразовывать. На Windows «из коробки» живы ANSI-кодовые страницы (CP1251, CP1252), `wchar_t` 16-битный, а `std::string` из `argv` — в ANSI. На Linux/macOS `wchar_t` 32-битный, и `std::wstring` — это UTF-32, а не UTF-16.
- **BOM.** UTF-8 BOM ломает shebang, некоторые парсеры и сравнения строк; при этом MSVC исторически использовал BOM, чтобы понять, что исходник в UTF-8. Сейчас надёжнее флаг `/utf-8` (MSVC) и UTF-8 без BOM везде.
- **Unicode-нормализация.** macOS (HFS+, отчасти APFS) сравнивает имена с учётом нормализации: `é` как один кодпоинт и `e` + combining accent могут считаться одним именем. Сравнение строк «побайтово» даёт сюрпризы.
- **Регистр и локаль.** `tolower`/`toupper` зависят от локали; классическая турецкая проблема `I`/`ı`. Для идентификаторов и протоколов используйте locale-independent операции.
- **Сортировка.** `strcoll` и `std::collate` зависят от локали; для предсказуемости — байтовое сравнение или ICU.
- **Графемы.** «Символ» для пользователя — это grapheme cluster, а не `char` и не code point. Обрезка строки по длине в байтах режет эмодзи и составные символы.

## 3. Локаль, числа, дата и время

- **Десятичный разделитель.** В русской/немецкой локали это запятая. `std::stod`, `printf("%f")`, `strtod` могут вести себя по-разному в зависимости от глобальной локали. Для машинных форматов (JSON, CSV, конфиги) используйте `std::to_chars`/`std::from_chars` или явно локаль `C`.
- **Форматы дат.** `MM/DD/YYYY` vs `DD.MM.YYYY` vs ISO 8601. Внутри и в API — ISO 8601 (`2026-10-29T23:58:55+03:00`), локализация — только на границе с пользователем.
- **Эпоха и тип `time_t`.** Unix-эпоха 1970, Windows `FILETIME` — 1601. `time_t` может быть 32-битным (проблема 2038) на старых 32-битных сборках.
- **Монотонное время.** Для таймаутов и интервалов — `std::chrono::steady_clock`, а не системные часы: пользователь может перевести часы, NTP — прыгнуть.
- **Часовые пояса и DST.** База tzdata обновляется независимо от программы; в Windows свои имена зон, в Linux — IANA. Переход на летнее время даёт неоднозначные и несуществующие локальные времена.
- **Локаль и потоки.** `localtime` не потокобезопасен; `localtime_r` (POSIX) и `localtime_s` (MSVC/C11) имеют разные сигнатуры и порядок аргументов.
- **Календарь.** Первый день недели, выходные, форматы чисел, денег, склонения — всё это лучше отдавать в i18n-библиотеку (ICU, CLDR), а не писать руками.

## 4. Модель данных, ABI и архитектуры

- **Размеры типов.** Windows — LLP64: `long` 32 бита даже на x64. Linux/macOS — LP64: `long` 64 бита. `int` обычно 32, но `size_t`, `ptrdiff_t`, `off_t`, указатели различаются. Для сериализации и протоколов — только `std::int32_t`, `std::uint64_t` и т.п.
- **`char` знаковый или нет.** На x86 обычно signed, на ARM часто unsigned. Это влияет на `isdigit(c)` при отрицательных значениях (формально UB) и на хеши.
- **`wchar_t`.** 16 бит на Windows, 32 на Unix — код, использующий `std::wstring` как «универсальную строку», не переносим.
- **`long double`.** MSVC — 64 бита (как `double`), x86 Linux — 80 бит x87, ARM Linux — 128 бит. Плюс на 32-битном x86 возможна избыточная точность x87.
- **Endianness.** Сейчас почти всё little-endian, но сеть и некоторые ARM-платформы — big-endian. В протоколах — `htonl`/`ntohl`, в файлах — явный порядок байт.
- **Выравнивание и упаковка структур.** `#pragma pack`, битовые поля, `offsetof` могут отличаться между компиляторами. Никогда не пишите сырые структуры в файл/сеть — сериализуйте по полям.
- **UB и оптимизации.** Strict aliasing (MSVC его почти не использует, GCC/Clang — активно), знаковое переполнение, невыровненный доступ, `reinterpret_cast` — всё это может «работать» на одной платформе и падать на другой. Type punning — через `memcpy` или `std::bit_cast`.

```cpp
#include <cinttypes>
std::printf("%" PRIu64 "\n", value);   // переносимо
// std::printf("%I64d\n", value);      // только MSVC
// std::printf("%lld\n", value);       // не везде одинаково
```

## 5. Компиляторы, стандартная библиотека, сборка

- **Разные компиляторы.** MSVC, GCC, Clang по-разному поддерживают стандарты и расширения. GNU-расширения (`__attribute__`, statement expressions, VLA) не работают в MSVC; `__declspec` — не работает в GCC/Clang (хотя Clang частично понимает).
- **Версии стандартной библиотеки.** `std::filesystem` в старом GCC требует `-lstdc++fs`; `std::thread` — `-pthread`; `std::from_chars` для `double` появился в libstdc++ поздно; `std::regex` медленный и по-разному реализован.
- **`char8_t` и `u8"..."`.** В C++20 тип строкового литерала изменился — код, который раньше компилировался, может потребовать правок.
- **Макросы Windows.** `windows.h` определяет `min`, `max`, `ERROR`, `interface` и ломает `std::min`. Обязательно:

```cpp
#define NOMINMAX
#define WIN32_LEAN_AND_MEAN
#include <windows.h>
```

- **Экспорт символов.** `__declspec(dllexport/dllimport)` vs `__attribute__((visibility("default")))`; по умолчанию в GCC/Clang всё видимо, в MSVC — нет. Отсюда `-fvisibility=hidden` и явные макросы экспорта.
- **ABI и границы DLL.** Нельзя передавать `std::string`/`std::vector` через границу DLL, собранных разными CRT/компиляторами; исключения через границу DLL — отдельная боль. Для стабильного C ABI — `extern "C"`, простые типы, явные функции создания/уничтожения.
- **CRT.** `/MD` vs `/MT` в MSVC, статическая vs динамическая линковка, `_ITERATOR_DEBUG_LEVEL`, `_GLIBCXX_DEBUG` — несовместимые пары дают странные падения.
- **Сборка.** CMake обычно лучший выбор; но нужно проверять генераторы (Ninja, Makefiles, MSBuild, Xcode), пути с пробелами и обратными слэшами, кросс-компиляцию (MinGW, clang-cl, sysroot).

## 6. Процессы, консоль, сигналы, shell

- **Запуск процессов.** Windows — `CreateProcess` с одной командной строкой и своими правилами квотинга (`CommandLineToArgvW`); Unix — `fork`/`exec`, `posix_spawn`, массив аргументов. `system()` на Windows идёт через `cmd.exe /C`, на Unix — через `/bin/sh -c`; поведение и экранирование разные.
- **`PATH`.** Разделитель `;` на Windows и `:` на Unix; `PATHEXT` (`.exe`, `.bat`) только на Windows; shebang (`#!/usr/bin/env python3`) на Windows не работает.
- **Сигналы.** На Windows нет полноценных `SIGTERM`/`SIGKILL`/`SIGPIPE`; Ctrl+C обрабатывается console control handler. На Unix `SIGPIPE` может убить процесс при записи в закрытый сокет — его игнорируют или используют `MSG_NOSIGNAL`/`SO_NOSIGPIPE`.
- **Коды возврата.** На Unix код обрезается до 8 бит, на Windows — 32-битный; есть коллизия с `STILL_ACTIVE` (259).
- **Консоль.** Unicode-вывод на Windows требует `SetConsoleOutputCP(CP_UTF8)` или `WriteConsoleW`; ANSI-цвета работают только после включения VT processing (Windows 10+). `isatty`/`_isatty`, `fileno`/`_fileno`, бинарный режим `_setmode(_fileno(stdout), _O_BINARY)` — всё это различается.
- **Переменные окружения.** Имена регистронезависимы на Windows и регистрозависимы на Unix; `HOME` vs `USERPROFILE`; `getenv`/`setenv` vs `_putenv_s`.

## 7. Потоки и синхронизация

- `std::thread`/`std::mutex`/`std::atomic` покрывают 90% случаев, но:
  - размер стека по умолчанию различается (Windows ~1 МБ, glibc ~8 МБ, macOS для вторичных потоков ~512 КБ) — глубокая рекурсия может неожиданно упасть;
  - `std::atomic` не везде lock-free для 64/128-битных типов (`ATOMIC_*_LOCK_FREE`);
  - приоритеты потоков и их поведение различаются;
  - `fork()` в многопоточной программе опасен, а на macOS `fork` без немедленного `exec` несовместим с Objective-C runtime;
  - `sleep` может быть прерван (`EINTR`), условные переменные просыпаются ложно (spurious wakeup) — нужны циклы проверки условия.
- Отдельно: `std::async` может запускать задачу синхронно (implementation-defined), а `std::thread::hardware_concurrency()` возвращает разное.

## 8. Сеть

- **Winsock vs BSD sockets.** На Windows нужен `WSAStartup`, тип `SOCKET` (не `int`), `closesocket` вместо `close`, `WSAGetLastError` вместо `errno`, линковка `ws2_32`.
- **`SO_REUSEADDR`.** Семантика на Windows другая: он позволяет «угнать» занятый порт; для безопасности используют `SO_EXCLUSIVEADDRUSE`. На Unix `SO_REUSEADDR` — обычная практика для TIME_WAIT.
- **`IPV6_V6ONLY`.** Значение по умолчанию различается (Windows — v6-only, Linux — dual-stack), поэтому dual-stack серверы нужно настраивать явно.
- **Мультиплексирование.** `select` ограничен `FD_SETSIZE` (64 на Windows, 1024 на Linux); `poll` на Windows нет (есть проблемный `WSAPoll`); `epoll` — Linux, `kqueue` — BSD/macOS, IOCP — Windows. Кроссплатформенный выбор — libuv, Asio, Boost.Asio.
- **Ошибки.** `errno` vs `WSAGetLastError`, `EINTR`, `EAGAIN`, частичные чтения/записи, `SIGPIPE`.

## 9. GUI и интеграция с ОС

- **Нативный вид и поведение.** На macOS меню глобальное, закрытие окна не завершает приложение, есть `Cmd+Q`; на Windows — своё; в Linux — ещё и разные DE и Wayland/X11.
- **DPI и масштабирование.** Windows требует манифест per-monitor DPI awareness; macOS оперирует points; Linux — дробное масштабирование. Без этого интерфейс «мылится» или разъезжается.
- **Шрифты и текст.** Разные шрифты по умолчанию, метрики, сглаживание, emoji, RTL.
- **Системные интеграции.** Файловые диалоги, буфер обмена, drag&drop, трей, уведомления, глобальные горячие клавиши, ассоциации файлов, автозапуск — везде свои API и ограничения.
- **Жизненный цикл приложения.** macOS-приложение — это `.app`-бандл с `Info.plist`; Windows — `.exe` + ресурсы + манифест; Linux — `.desktop`-файл и иконки.
- **Разрешения и sandbox.** macOS App Sandbox и entitlements, Windows AppContainer, Linux namespaces/seccomp; доступ к камере/микрофону/геолокации требует явных разрешений.

## 10. Динамические библиотеки, зависимости, поставка

- Расширения и формат: `.dll` (Windows), `.so` (Linux), `.dylib` (macOS); импорт-библиотеки `.lib`/`.a`.
- Поиск библиотек: `PATH` и каталог exe в Windows; `RPATH`/`RUNPATH`, `LD_LIBRARY_PATH`, `$ORIGIN` в Linux; `@rpath`, `DYLD_LIBRARY_PATH` в macOS (SIP вырезает `DYLD_*` для защищённых бинарников).
- `LoadLibrary` vs `dlopen`, разные правила поиска и версионирования символов (soname, version scripts).
- **glibc vs musl.** Сборка под Alpine с musl не совместима с glibc-бинарниками; статическая линковка — отдельный компромисс.
- **Поставка.** MSI/MSIX, `.dmg`/`.pkg`, deb/rpm/AppImage/Flatpak/Snap, Homebrew/Chocolatey; автообновление, код-сайнинг (Authenticode, Developer ID + notarization, GPG), антивирусы и SmartScreen на Windows, Gatekeeper на macOS.
- **Версии и ABI.** Обновление системной библиотеки может сломать бинарник; для C++ ABI между MSVC-версиями вообще не гарантирован.

## 11. Права, безопасность, sandbox

- POSIX-права (`rwx`, `umask`, владелец) vs Windows ACL; `chmod` на Windows меняет только read-only.
- Запуск от root/администратора: UAC на Windows, `sudo` на Unix; приложение не должно требовать админа без нужды.
- Симлинки и TOCTOU: проверка пути, затем открытие — гонка; используйте `O_NOFOLLOW`, `openat`, атомарные операции.
- Path traversal: `..`, смешение `/` и `\`, Windows ADS (`file.txt:stream`), зарезервированные имена, trailing dot/space — всё это векторы атаки при работе с пользовательскими путями.
- Sandbox/мандатные политики: SELinux/AppArmor, macOS sandbox, Windows AppContainer; они меняют доступность файлов, сети, процессов.

---

## 12. Тестирование и CI

- **Матрица.** Как минимум Windows + Linux + macOS, x64 + ARM64, MSVC + GCC + Clang, Debug + Release. Одна ОС не заменяет другую.
- **WSL и Docker — не замена.** WSL даёт Linux-ядро, но не полноценный дистрибутив с systemd; Docker на macOS/Windows запускает Linux-контейнеры, а не целевую ОС. macOS-раннеры в CI нужны отдельно.
- **Санитайзеры и анализаторы.** ASan/UBSan/TSan/MSan (где доступны), Valgrind, clang-tidy, PVS-Studio, fuzzing. UBSan особенно полезен для отлова платформозависимого UB.
- **Голден-файлы.** Эталоны с путями и переводами строк нужно нормализовать, иначе тесты «падают только на Windows».
- **Правило:** если код не собирается и не тестируется на платформе в CI, он на ней не работает — он просто ещё не падал.

## 13. Производительность и наблюдаемость

- Размер страницы (4 КБ vs 16 КБ на Apple Silicon), поведение `mmap`, кэши файловой системы, стоимость системных вызовов.
- Разные таймеры и их разрешение; на Windows — `timeBeginPeriod`, `QueryPerformanceCounter`.
- Разные профилировщики и форматы логов: ETW, `perf`, Instruments, DTrace.
- Логирование: Event Log, syslog/journald, unified logging — стоит абстрагировать.

## 14. Языковая специфика (кратко)

- **Python:** `os.path`/`pathlib`, `sys.platform`, `platform.system()`, `subprocess` с `shell=True` опасен и по-разному квотится, `multiprocessing` на macOS/Windows использует `spawn`, а не `fork`, кодировка stdout и `PYTHONUTF8`.
- **Java:** JVM многое абстрагирует, но остаются `File.separator`, `System.lineSeparator()`, нативные библиотеки, `jpackage`.
- **.NET:** `Path.DirectorySeparatorChar`, `Environment.NewLine`, `RuntimeInformation.IsOSPlatform`.
- **JS/Node:** `path.win32`/`path.posix`, `process.platform`, переводы строк, разные браузерные движки и `Intl`.
- **Go:** лёгкая кросс-компиляция, `path/filepath`, build tags; но cgo и системные вызовы возвращают платформенные различия.
- **Rust:** `cfg!(target_os)`, `std::path`, кросс-компиляция с `--target`, `libc` для низкого уровня.

## 15. Как писать переносимо: стратегии

1. **Ядро — переносимое, ОС — тонкий слой.** Бизнес-логика не должна знать про `#ifdef _WIN32`; платформенные различия прячьте за интерфейсами (файлы, сеть, время, процессы, логи).
2. **Минимизируйте `#ifdef`.** Чем меньше условной компиляции в общем коде, тем лучше; выносите её в отдельные файлы `platform_win.cpp`, `platform_posix.cpp`.
3. **Опирайтесь на стандарт и проверенные библиотеки:** `<filesystem>`, `<thread>`, `<chrono>`, `<random>`, `{fmt}`, `spdlog`, Asio, SDL/Qt/GLFW, Catch2/GoogleTest, CMake.
4. **Фиксируйте типы и форматы:** `std::int32_t`, `std::uint64_t`, UTF-8 на границах, ISO 8601, явный endianness в протоколах.
5. **Не полагайтесь на UB.** Strict aliasing, знаковое переполнение, выравнивание, `char` signedness — всё это «работает» на одной платформе и ломается на другой.
6. **Пути — через `std::filesystem::path`**, никогда — конкатенацией строк; не хардкодьте разделители, `/tmp`, `~`.
7. **Локаль — только для пользователя.** Машинные форматы (JSON, CSV, конфиги, логи) — всегда в `C`/UTF-8.
8. **Тестируйте с первого дня на всех целевых платформах** и держите CI-матрицу; «на моей машине работает» — не аргумент.
9. **Документируйте поддерживаемые платформы, компиляторы и версии**, а не пытайтесь поддержать «всё».
10. **Помните про пользователя:** пробелы и кириллица в путях, нестандартные DPI, тёмная тема, RTL, ограниченные права, антивирус, файрвол.

## Чек-лист перед тем, как считать код кроссплатформенным

- [ ] Нет конкатенации путей строками и хардкода `/` или `\`.
- [ ] Нет хардкода `/tmp`, `~`, `/usr/local`, `C:\`.
- [ ] Все внешние данные читаются/пишутся в UTF-8; на Windows учтены широкие API.
- [ ] Переводы строк и BOM оговорены в `.gitattributes`.
- [ ] Даты/числа в машинных форматах не зависят от локали.
- [ ] Используются типы фиксированной ширины; нет сериализации сырых структур.
- [ ] Нет `#ifdef` в бизнес-логике; платформенный код изолирован.
- [ ] Сборка проверена на MSVC, GCC и Clang (хотя бы в CI).
- [ ] Тесты гоняются на Windows, Linux и macOS, а не только на одной ОС.
- [ ] Учтены блокировки файлов, атомарная замена, права доступа и симлинки.
- [ ] Проверены пути с пробелами, кириллицей и длиной > 260.
- [ ] Проверены сетевые настройки: `SO_REUSEADDR`, `IPV6_V6ONLY`, `SIGPIPE`.
- [ ] Есть план поставки: установщик, подпись, обновление, зависимости.

---

**Итог.** Главная проблема кроссплатформенного кода — не в том, что «на другой ОС другой API», а в **неявных допущениях**, которые программист даже не осознаёт: про регистр файлов, про кодировку, про `long`, про локаль, про атомарность `rename`, про сигналы. Хорошая стратегия — свести эти допущения к явным абстракциям, использовать стандартную библиотеку и проверенные кроссплатформенные зависимости, а различия проверять автоматически на всех целевых платформах. Тогда «кроссплатформенность» становится не героическим усилием в конце проекта, а обычным свойством кодовой базы.
