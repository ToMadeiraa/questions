# 43. Объясните принципы SOLID.

**SOLID** — это мнемоника из пяти принципов объектно-ориентированного проектирования, сформулированных Робертом Мартином (статья «Design Principles and Design Patterns», 2000); сам акроним предложил Майкл Физерс. Принципы не являются законами и не заменяют проектирования: их общая цель — управлять зависимостями между модулями так, чтобы изменения в одном месте не вызывали каскада изменений в других, а код оставался тестируемым и расширяемым.

Исторически SOLID вырос из более общей идеи: **зависимости — главный источник жёсткости (rigidity), хрупкости (fragility) и неподвижности (immobility) программы**. Каждый принцип — это правило о том, куда и в какую сторону должны смотреть зависимости.

- **S** — Single Responsibility Principle (принцип единственной ответственности)
- **O** — Open/Closed Principle (принцип открытости/закрытости)
- **L** — Liskov Substitution Principle (принцип подстановки Барбары Лисков)
- **I** — Interface Segregation Principle (принцип разделения интерфейсов)
- **D** — Dependency Inversion Principle (принцип инверсии зависимостей)

Ниже — каждый принцип с формулировкой, типичным нарушением, исправлением на C++ и «подводными камнями».

---

## S — Single Responsibility Principle (SRP)

**Формулировка.** У класса должна быть одна причина для изменения — то есть класс должен отвечать перед одним «актором» (заинтересованным лицом, группой, которая формулирует требования).

Важно: «одна причина для изменения» ≠ «класс делает одну вещь». Правильная трактовка — **один источник требований**. Если бухгалтерия, отдел отчётности и DevOps могут независимо потребовать правок в одном классе, у класса три ответственности, даже если он «делает одно — работает с отчётом».

**Типичное нарушение.** Класс смешивает бизнес-логику, представление и инфраструктуру:

```cpp
// Плохо: три причины для изменения — правила расчёта, формат HTML, способ сохранения
class Report {
public:
    std::string buildBody() const;          // бизнес-правила
    std::string toHtml() const;             // представление
    void save(const std::string& path);     // IO/инфраструктура
};
```

Любое изменение формата отчёта заставляет перекомпилировать и перепроверять расчёты; тестировать расчёты без файловой системы нельзя; класс нельзя переиспользовать с другим форматом вывода.

**Исправление.** Разделить по осям изменения, а не по «строчкам кода»:

```cpp
struct Report {                 // данные и правила
    std::vector<Item> items;
    Money total() const;
};

class HtmlFormatter {           // только представление
public:
    std::string format(const Report& r) const;
};

class ReportRepository {        // только хранение
public:
    virtual ~ReportRepository() = default;
    virtual void save(const Report& r) = 0;
};
```

**В контексте C++.** SRP хорошо ложится на физическую структуру проекта: один класс — один заголовочный файл, минимум `#include` в заголовке (forward declaration, pimpl), чтобы изменение детали не тянуло перекомпиляцию всего проекта. SRP — это ещё и принцип **связности (cohesion)**: класс должен иметь высокую связность внутри и низкую связанность (coupling) снаружи.

**Подводный камень.** Доведённый до абсурда SRP порождает «класс на каждый чих» и взрыв числа сущностей. Границу ответственности определяют требования и акторы, а не желание сделать классы максимально маленькими.

## O — Open/Closed Principle (OCP)

**Формулировка.** Программные сущности должны быть **открыты для расширения, но закрыты для изменения**: новое поведение добавляется новым кодом, а не правкой существующего и уже проверенного.

**Типичное нарушение.** Ручной `switch`/`if` по типу — классический «запах»:

```cpp
enum class ShapeType { Circle, Square };

struct Shape { ShapeType type; double a; };

double area(const Shape& s) {
    switch (s.type) {
        case ShapeType::Circle: return 3.14159 * s.a * s.a;
        case ShapeType::Square: return s.a * s.a;
    }
    return 0.0;
}
```

Каждая новая фигура требует правки `area` (и всех аналогичных функций), а значит — повторной проверки уже работающего кода и риска сломать существующие ветки.

**Исправление.** Инкапсулировать вариативность за полиморфным интерфейсом:

```cpp
class Shape {
public:
    virtual ~Shape() = default;                 // обязателен для полиморфного удаления
    virtual double area() const = 0;
};

class Circle final : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.14159 * r_ * r_; }
private:
    double r_;
};
```

Новая фигура = новый класс, `area` не меняется.

**Ключевой нюанс.** OCP всегда **относителен**: нельзя быть закрытым по всем осям изменения сразу. Добавление новой *операции* (например, `perimeter()` или сериализации) к готовой иерархии снова потребует правки базового класса — это «проблема выражения» (expression problem). Поэтому ось расширения выбирают осознанно:

- новая **операция** важнее новых **типов** → свободные функции, `std::variant` + `std::visit`, паттерн «Посетитель» (Visitor, двойная диспетчеризация);
- новые **типы** важнее операций → виртуальные функции;
- нужна максимальная производительность и статическая проверка → шаблоны и политики (policy-based design), CRTP, `concepts` в C++20.

**В контексте C++.** Инструменты OCP: виртуальные функции, шаблоны (в т.ч. явная/частичная специализация), `std::function` для подменяемого поведения, стирание типов (type erasure), внедрение политик через параметры шаблона.

**Подводный камень.** Преждевременное «расширение ради расширения» (нарушение YAGNI) ведёт к лишним абстракциям и усложнению. Абстракцию вводят там, где изменения уже происходят или ожидаются с высокой вероятностью.

## L — Liskov Substitution Principle (LSP)

**Формулировка (Б. Лисков, 1987).** Если `S` — подтип `T`, то объекты `T` можно заменять объектами `S`, не нарушая корректность программы.

Практически это **поведенческое** (behavioral) наследование, а не только сигнатурное:

1. **Предусловия** в подтипе нельзя **усиливать** (нельзя требовать больше, чем база).
2. **Постусловия** нельзя **ослаблять** (подтип обязан гарантировать не меньше).
3. **Инварианты** базового класса сохраняются.
4. **History constraint**: подтип не должен позволять изменений, запрещённых базой.
5. Подтип не должен бросать новые исключения, не предусмотренные контрактом базы.

**Классическое нарушение** — «квадрат как прямоугольник»:

```cpp
class Rectangle {
public:
    virtual ~Rectangle() = default;
    virtual void setWidth(double w)  { w_ = w; }
    virtual void setHeight(double h) { h_ = h; }
    double area() const { return w_ * h_; }
protected:
    double w_ = 0, h_ = 0;
};

class Square : public Rectangle {          // выглядит как «is-a»
public:
    void setWidth(double w) override  { w_ = h_ = w; }
    void setHeight(double h) override { w_ = h_ = h; }
};

void stretch(Rectangle& r) {               // написано в терминах базы
    r.setWidth(5);
    r.setHeight(4);
    assert(r.area() == 20);                // для Square — 16: контракт нарушен
}
```

**Исправление.** Либо не наследовать (композиция, отдельные типы, общий интерфейс только на чтение — `Shape::area()`), либо сделать операции неизменяемыми (immutable value types), либо явно разделить контракты: `class Rectangle` и `class Square` независимы, а общее — интерфейс `Shape` с `area()`.

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};
```

**Признаки нарушения LSP:** переопределённый метод, который «ничего не делает»; метод, бросающий `std::logic_error("not supported")`; проверки `dynamic_cast`/`typeid` у клиента перед вызовом; флаги «режим работы» внутри базового класса.

**В контексте C++.** В C++ `public`-наследование означает «is-a» плюс подстановочность; переиспользование реализации без подстановочности оформляют **закрытым** наследованием (`private`) или композицией. Специфика:

- **виртуальный деструктор** обязателен, если объект удаляется через указатель на базу, иначе — UB;
- **срезка (slicing)**: передача по значению `void f(Shape s)` теряет полиморфизм — полиморфные объекты передают по ссылке/указателю;
- `const`-методы — часть контракта: наследник не может «снять» `const`;
- `noexcept` входит в контракт: переопределение, бросающее исключения, нарушает LSP на уровне типа;
- ковариантные возвращаемые типы допустимы и не нарушают принцип.

## I — Interface Segregation Principle (ISP)

**Формулировка.** Клиенты не должны зависеть от методов, которые они не используют; интерфейсы должны быть узкими и специализированными. Большой интерфейс следует разбить на несколько маленьких.

**Типичное нарушение** — «толстый» интерфейс, вынуждающий реализовывать лишнее:

```cpp
struct IWorker {
    virtual ~IWorker() = default;
    virtual void work() = 0;
    virtual void eat()  = 0;      // роботу не нужно
    virtual void sleep() = 0;     // и это тоже
};

class Robot : public IWorker {     // вынужден писать заглушки
public:
    void work() override {}
    void eat() override  { throw std::logic_error("no"); }
    void sleep() override { throw std::logic_error("no"); }
};
```

Заглушки и исключения — прямой признак нарушения ISP (и часто одновременно LSP).

**Исправление.** Разделить роли:

```cpp
struct IWorkable { virtual ~IWorkable() = default; virtual void work() = 0; };
struct IFeedable { virtual ~IFeedable() = default; virtual void eat() = 0; };

class Robot    : public IWorkable { /* ... */ };
class Human    : public IWorkable, public IFeedable { /* ... */ };
```

Клиент, которому нужно только `work()`, зависит только от `IWorkable` и не перекомпилируется при изменении `IFeedable`.

**В контексте C++.**

- Множественное наследование **интерфейсов** (абстрактных классов без данных) безопасно и идиоматично; множественное наследование **реализаций** — источник ромбовидных проблем.
- ISP работает и на этапе компиляции: чем меньше зависимостей в заголовке, тем меньше каскад перекомпиляции. Тяжёлый `#include` в интерфейсе — тоже «зависимость от лишнего».
- В шаблонах роль интерфейса играет **набор требуемых операций**: `concepts` (C++20) позволяют сформулировать минимальные требования к параметру шаблона явно и точно.

**Подводный камень.** Чрезмерное дробление даёт «интерфейс на один метод» и усложняет навигацию. Ориентир — реальные клиенты: интерфейс должен соответствовать тому, как его используют, а не тому, как удобно реализовывать.

## D — Dependency Inversion Principle (DIP)

**Формулировка** (две части):

1. Модули верхнего уровня не должны зависеть от модулей нижнего уровня; и те, и другие должны зависеть от **абстракций**.
2. Абстракции не должны зависеть от деталей; детали должны зависеть от абстракций.

То есть направление зависимости «сверху вниз» **инвертируется**: бизнес-логика не знает о базе данных, логгере или HTTP — она объявляет нужные ей интерфейсы, а инфраструктура их реализует.

**Типичное нарушение.**

```cpp
class OrderService {
public:
    void place(const Order& o) {
        MySqlDatabase db;                 // жёсткая зависимость от деталей
        db.insert(o);
        FileLogger::instance().log("ok"); // ещё одна
    }
};
```

Сервис нельзя протестировать без MySQL и файловой системы; смена хранилища правит бизнес-логику.

**Исправление.** Абстракции принадлежат уровню политики, реализации — уровню деталей; зависимости внедряются извне (constructor injection):

```cpp
class OrderRepository {                    // абстракция объявлена "сверху"
public:
    virtual ~OrderRepository() = default;
    virtual void save(const Order& o) = 0;
};

class Logger {
public:
    virtual ~Logger() = default;
    virtual void log(std::string_view msg) = 0;
};

class OrderService {                       // зависит только от абстракций
public:
    OrderService(OrderRepository& repo, Logger& log)
        : repo_(repo), log_(log) {}

    void place(const Order& o) { repo_.save(o); log_.log("ok"); }
private:
    OrderRepository& repo_;
    Logger& log_;
};

// Композиционный корень (main) — единственное место, знающее конкретики:
int main() {
    MySqlRepository repo{/*...*/};
    ConsoleLogger   log;
    OrderService    service{repo, log};
}
```

**Важные уточнения.**

- **DIP ≠ Dependency Injection.** Инверсия зависимостей — принцип проектирования; внедрение зависимостей — технический приём его реализации (конструктор, сеттер, параметр функции). DI-контейнер — уже частная инфраструктура.
- Кто-то всё равно должен знать конкретные типы — это **композиционный корень** (`main`, фабрика, bootstrap). DIP требует изолировать это знание, а не уничтожить.
- В C++ абстракция не обязана быть виртуальным интерфейсом: **шаблонный параметр** или `std::function` дают ту же инверсию без накладных расходов на виртуальные вызовы (статический полиморфизм).

```cpp
template <class Repo, class Log>
class OrderService {                       // инверсия на этапе компиляции
public:
    OrderService(Repo& r, Log& l) : repo_(r), log_(l) {}
    void place(const Order& o) { repo_.save(o); log_.log("ok"); }
private:
    Repo& repo_;
    Log&  log_;
};
```

**Подводный камень.** Абстракция «на всякий случай» и виртуальный вызов там, где нужна максимальная производительность (горячий цикл, embedded), — тоже ошибка. В таких случаях уместны шаблоны, `constexpr`, статическое связывание.

## Как принципы связаны между собой

| Принцип | Вопрос, на который отвечает | Инструменты в C++ |
|---|---|---|
| SRP | *Кто и почему потребует изменения?* | разделение классов, pimpl, минимум `#include` |
| OCP | *Как добавить поведение, не правя старое?* | виртуальные функции, шаблоны, `std::variant` + `visit`, Visitor |
| LSP | *Можно ли подставить наследника?* | `public`-наследование, `override`, виртуальный деструктор, контракты |
| ISP | *От чего клиенту действительно нужна зависимость?* | узкие абстрактные базы, `concepts` |
| DIP | *В какую сторону смотрят зависимости?* | абстрактные интерфейсы, инъекция, шаблоны, `std::function` |

Все пять — про **управление зависимостями и направлением изменения**. SRP и ISP уменьшают количество связей; OCP и DIP задают направление, в котором можно расширяться; LSP гарантирует, что абстракция останется честной и заменимой. Вместе они дают код, который дешевле тестировать (подмена зависимостей, отсутствие IO в юнит-тестах), сопровождать и переиспользовать.

## Критика и границы применимости

- **SOLID — не догма и не самоцель.** Чрезмерное следование порождает «церемонию»: взрыв интерфейсов, лишние уровни абстракции, трудность чтения. Принципы нужно применять там, где ожидается изменение, а не механически.
- **Принципы конфликтуют.** Дробление по SRP/ISP увеличивает число сущностей и связей; OCP-абстракции противоречат YAGNI; DIP добавляет косвенность и накладные расходы. Проектирование — это баланс, а не максимизация одного критерия.
- **SOLID не покрывает всего.** Он молчит о конкурентности, распределённых системах, производительности, API/ABI, владении памятью. В C++ к нему добавляются Rule of Zero/Five, RAII, `const`-корректность, value semantics — и часто именно value-типы и свободные функции дают более простой и быстрый дизайн, чем «правильная» иерархия классов.
- **Не всякое наследование — LSP.** Наследование реализации оформляют композицией или закрытым наследованием; публичное наследование оправдано только при настоящей подстановочности.
- Полезные дополнения к SOLID: DRY, KISS, YAGNI, Law of Demeter, GRASP; альтернативные наборы вроде CUPID (Дэн Норт) делают акцент на композиции, Unix-философии и простоте.

**Практический итог.** SOLID стоит воспринимать как набор эвристик для ответа на вопрос «куда должна смотреть эта зависимость и что произойдёт, когда требование изменится». Признак хорошего результата — не число классов, а стоимость типичного изменения: сколько файлов нужно тронуть, сколько тестов переписать и можно ли заменить инфраструктуру, не открывая бизнес-логику.
