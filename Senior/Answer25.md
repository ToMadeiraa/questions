# 25. Расскажите об использовании realloc в контейнерах.

## Кратко: что ожидает услышать интервьюер

- `realloc` — это **не «изменение размера на месте»**, а запрос «дай блок другого размера с тем же содержимым»; блок может переехать, и тогда все указатели на него становятся невалидными.
- В контейнерах `realloc` — это способ реализовать **геометрический рост динамического массива** (аналог `std::vector`) с амортизированной стоимостью O(1) на `push_back`.
- `realloc` **побайтово** переносит содержимое, поэтому годится только для **memcpy-релокируемых** объектов: C-структур без внутренних указателей, trivially copyable типов. Он не вызывает ни конструкторов, ни деструкторов.
- Именно поэтому **стандартные контейнеры C++ (`std::vector`, `std::string`) не используют `realloc`**: они обязаны работать через аллокатор и конструкторы/деструкторы элементов.
- Главные ловушки: `p = realloc(p, n)` (утечка при ошибке), `realloc(p, 0)`, переполнение `n * sizeof(T)`, невыровненность для over-aligned типов, смешивание с `new`/чужим аллокатором.

## 1. Контракт `realloc`

```c
void *realloc(void *ptr, size_t size);   /* <stdlib.h> */
```

В C++ — `std::realloc` из `<cstdlib>`.

Семантика (C17/C++ по ссылке на C):

1. `ptr == NULL` → ведёт себя как `malloc(size)`.
2. Успех → возвращается указатель на блок размера `size`, **содержимое первых `min(old_size, size)` байт сохранено**. Если новый блок больше — «хвост» **не инициализирован** (не обнуляется!).
3. Указатель может быть **тем же самым** (расширение на месте), а может быть **другим** (выделение нового блока + копирование + освобождение старого).
4. Ошибка → возвращается `NULL`, **старый блок остаётся выделенным и нетронутым**. Освобождать его — ваша обязанность.
5. `realloc` можно применять **только** к памяти из `malloc/calloc/realloc`. Память из `new`, со стека, из арен/пулов, из `mmap` — нельзя (UB).
6. Выравнивание результата — достаточное для любого типа с *фундаментальным* выравниванием (`max_align_t`), но **не** для `alignas(64)` и т.п.
7. `size == 0` и `ptr != NULL`: до C23 — implementation-defined (либо `NULL`, либо уникальный указатель, который нельзя разыменовывать, но можно `free`); в C23 это **UB**. Практический вывод: никогда не передавайте 0, делайте `free(p); p = NULL;`.
8. `errno`: POSIX требует `ENOMEM` при неудаче, но стандарт C про `errno` для `realloc` молчит — в переносимом коде на него не полагайтесь.

Ключевая мысль для контейнера: **`realloc` — это «выдели новый блок и сделай `memcpy` старого»**, просто оптимизированный аллокатором. Отсюда все ограничения.

## 2. Почему в контейнерах это вообще работает: амортизация

Классическая стратегия — увеличивать ёмкость в **геометрической прогрессии** (×1.5 или ×2), а не на +1:

- при `push_back` в заполненный массив делаем `realloc(cap * 2)`;
- суммарное число скопированных элементов за `n` вставок — `1 + 2 + 4 + … + n < 2n`, то есть **амортизированно O(1)** на операцию;
- при коэффициенте `k` суммарно копируется не более `n·k/(k−1)` элементов, а «перерасход» памяти в худший момент — примерно `(k−1)·size`.

Нюансы выбора коэффициента:

| Коэффициент | Плюсы | Минусы |
|---|---|---|
| ×2 | меньше всего перевыделений, быстрый рост | до ~50 % «пустой» памяти, хуже переиспользование блоков аллокатором |
| ×1.5 | меньше пиковая память, аллокатор чаще может переиспользовать освобождённые блоки | больше копирований |

Именно поэтому libstdc++/libc++ растят `vector` вдвое, а MSVC — примерно в 1.5 раза.

Отдельный бонус `realloc` перед «вручную `malloc` + `memcpy` + `free`»: для больших блоков (в glibc — от порога `mmap`, обычно 128 КиБ) рост может быть сделан через `mremap` — **переотображением страниц без копирования**, то есть почти O(1). Для маленьких блоков часто срабатывает расширение на месте, если следующий чанк свободен (top chunk). Но полагаться на это нельзя — это деталь реализации.

## 3. Динамический массив на `realloc` (C)

```c
#include <stdint.h>
#include <stdlib.h>

typedef struct {
    int    *data;
    size_t  size;
    size_t  capacity;
} IntVec;

static int intvec_reserve(IntVec *v, size_t need)
{
    if (need <= v->capacity)
        return 1;

    /* 1. Защита от переполнения при вычислении cap * sizeof(int) */
    if (need > SIZE_MAX / sizeof *v->data)
        return 0;

    /* 2. Геометрический рост */
    size_t cap = v->capacity ? v->capacity : 8;
    while (cap < need) {
        if (cap > SIZE_MAX / 2) { cap = need; break; }  /* не переполнить cap */
        cap *= 2;
    }
    if (cap > SIZE_MAX / sizeof *v->data)
        return 0;

    /* 3. ВАЖНО: результат — в отдельную переменную */
    int *p = realloc(v->data, cap * sizeof *p);
    if (!p)
        return 0;              /* старый блок цел, v->data валиден */

    v->data     = p;           /* publishing только после успеха */
    v->capacity = cap;
    return 1;
}

int intvec_push(IntVec *v, int x)
{
    if (v->size == v->capacity && !intvec_reserve(v, v->size + 1))
        return 0;
    v->data[v->size++] = x;
    return 1;
}

void intvec_free(IntVec *v)
{
    free(v->data);
    v->data = NULL;
    v->size = v->capacity = 0;
}
```

Что здесь принципиально:

- `int *p = realloc(...); if (!p) ...; v->data = p;` — при `v->data = realloc(v->data, ...)` в случае `NULL` указатель теряется и блок утекает. Это ошибка №1 на собеседованиях.
- Проверка переполнения **до** умножения: `need > SIZE_MAX / sizeof *v->data`. Иначе `cap * sizeof(int)` может «свернуться» в маленькое число, и вы получите буфер меньше, чем думаете, — классическая уязвимость.
- Рост от нуля (`capacity == 0`) надо обрабатывать отдельно — иначе `0 * 2 == 0` и цикл не сдвинется.
- Гарантия исключительной безопасности/целостности: при неудаче контейнер остаётся в прежнем состоянии — это фактически *strong guarantee*. В C++ с `realloc` это получается «бесплатно», потому что операция одна и ничего не бросает.
- Если контейнер хранит `begin/end/cap` указателями, после `realloc` надо обновить **все три**, а не только `begin`.
- Если в контейнере есть **SSO** (small-buffer optimization), `data` может указывать на встроенный буфер — тогда ветка «вырасти» должна не `realloc`-ить, а выделять новый блок и копировать.

## 4. Ловушки `realloc` применительно к контейнерам

### 4.1. Инвалидация указателей, итераторов, ссылок

Самое важное следствие для пользователей контейнера: успешный `realloc`, вернувший другой адрес, **освобождает старый блок**. Все указатели/ссылки/итераторы внутрь него становятся висячими:

```c
IntVec v = {0};
intvec_push(&v, 1);
int *p = &v.data[0];
/* ... много push_back, ёмкость выросла ... */
*p = 42;   /* UB: p мог стать висячим */
```

В C++ это ровно правило инвалидации `std::vector`: при реаллокации инвалидируются **все** ссылки, указатели и итераторы; `reserve()` заранее — стандартный способ этого избежать. Даже если аллокатор вернул тот же адрес, формально полагаться на это нельзя (и `vector` всё равно считает итераторы инвалидированными).

Отсюда практический приём: если элементы должны ссылаться друг на друга, храните **индексы/смещения**, а не указатели. Тогда `realloc` безопасен:

```c
typedef struct { size_t next; int value; } Node;  /* индекс вместо указателя */
```

### 4.2. Побитовое перемещение ломает «самоссылающиеся» объекты

`realloc` копирует байты. Поэтому нельзя:

- структуры с указателем на собственное поле (`struct { char *p; char buf[16]; }`, где `p = buf`);
- объекты с `pthread_mutex_t`, `std::mutex`, некоторыми `std::atomic` — их побитовый перенос UB;
- полиморфные объекты с инвариантами, завязанными на адрес;
- любые нетривиально копируемые C++ типы (`std::string`, `std::unique_ptr`, `std::vector` внутри элемента).

Критерий: объект должен быть **memcpy-релокируемым** — тривиально копируемым и без внутренних ссылок на себя. В C++ это примерно `std::is_trivially_copyable_v<T>` (плюс отсутствие самореференций), а в C++23 есть даже `std::is_implicit_lifetime`.

### 4.3. Нет конструкторов/деструкторов

`realloc` не вызывает ни `T()`, ни `~T()`. Для C-структур это норма, для C++ — блокер: новый «хвост» содержит неинициализированные байты, а при уменьшении/освобождении деструкторы элементов просто не выполнятся. Даже «выглядит работающим» для `unique_ptr` — это UB.

### 4.4. Выравнивание

`realloc` гарантирует только фундаментальное выравнивание. Для `struct alignas(64) Vec4` или SIMD-типов он не годится: нужен `aligned_alloc`/`posix_memalign` + ручное копирование (в C23 отдельного `aligned_realloc` нет). То же в C++: `operator new(size, align_val_t)`.

### 4.5. Аллокатор и владение

- Нельзя `realloc`-ить память от `new`/`new[]` (даже для POD) — UB, и `free`/`delete` нельзя смешивать.
- Нельзя `realloc`-ить память из арены/пула/`mmap`: у них нет заголовка, который ожидает `realloc`.
- Если контейнер параметризован аллокатором (C++), `realloc` **обхдит** аллокатор: `allocate`/`deallocate` обязаны быть парными, а `realloc` — нет. Значит, для контейнера с произвольным аллокатором этот трюк неприменим.

### 4.6. `size == 0` и «ложная ошибка»

`realloc(p, 0)` может вернуть `NULL`, и это **не** признак нехватки памяти. Поэтому шаблон проверки всегда такой:

```c
if (new_size == 0) { free(p); p = NULL; }
else {
    void *q = realloc(p, new_size);
    if (!q) { /* настоящая ошибка, p ещё валиден */ }
    else   { p = q; }
}
```

### 4.7. Ошибка не должна терять старые данные

Контейнер обязан либо вернуть код ошибки/исключение, либо оставить прежнее состояние. С `realloc` это просто: старый блок жив до присваивания. С «ручным» `malloc` + `memcpy` + `free` — тоже, но там легко ошибиться с порядком операций. В C++ бросающий `push_back` при `bad_alloc` должен оставить вектор валидным — `realloc`-подход это даёт автоматически (он не бросает, а возвращает `NULL`).

### 4.8. `realloc` не обнуляет новый хвост

Если нужен нулевой хвост (например, для хеш-таблицы с «пустыми» слотами), его надо занулить самому через `memset`. `calloc` тут не поможет — `realloc` не «переcalloc-ит».

### 4.9. Многопоточность

Сам `malloc/realloc/free` потокобезопасны (в типичных реализациях), но контейнер — нет. `realloc` под читателями — гонка и UB, даже если сам вызов «атомарен» внутри аллокатора.

## 5. Почему `std::vector` не использует `realloc`

Стандартные контейнеры C++ строятся на модели «аллокатор + время жизни объектов»:

- память берётся через `allocator_traits<A>::allocate`, а не через `malloc`;
- элементы создаются `construct_at` и уничтожаются `destroy_at`;
- при росте выполняются **поэлементные** move/copy-конструкторы, а при уничтожении — деструкторы;
- должна сохраняться совместимость с пользовательским аллокатором (в т.ч. с fancy pointers, `allocate_at_least` в C++23).

`realloc` не удовлетворяет ни одному пункту: он не знает про аллокатор, не вызывает конструкторы/деструкторы и делает побитовое копирование. Поэтому `std::vector` при нехватке ёмкости делает:

1. `allocate(new_cap)`;
2. перенос/копирование элементов (с `move_if_noexcept` — чтобы дать strong guarantee, если move может бросить);
3. `destroy` старых, `deallocate` старый блок.

Именно поэтому у `vector` есть тонкость с исключениями: если move-конструктор не `noexcept` и копирования нет, вектор вынужден **копировать** элементы ради гарантии. У `realloc`-контейнера этой проблемы нет — но и работает он только для тривиальных типов.

Тем не менее `realloc`-подход легитимен в **кастомных** контейнерах: `llvm::SmallVector`-подобные реализации, векторы для POD в игровых/системных библиотеках, C-контейнеры. Условия: `std::is_trivially_copyable_v<T>`, `alignof(T) <= alignof(std::max_align_t)`, аллокатор совместим с `malloc` (фактически — `std::allocator` или собственный malloc-based), и мы сами отвечаем за lifetime.

Эскиз такого контейнера:

```cpp
template <class T>
class TrivialVector {
    static_assert(std::is_trivially_copyable_v<T>);
    static_assert(alignof(T) <= alignof(std::max_align_t));
    T *data_ = nullptr;
    std::size_t size_ = 0, cap_ = 0;
public:
    void push_back(const T &v) {
        if (size_ == cap_) grow(cap_ ? cap_ * 2 : 8);
        ::new (static_cast<void *>(data_ + size_)) T(v);
        ++size_;
    }
    ~TrivialVector() { std::free(data_); }
private:
    void grow(std::size_t n) {
        if (n > SIZE_MAX / sizeof(T)) throw std::bad_alloc();
        void *p = std::realloc(data_, n * sizeof(T));
        if (!p) throw std::bad_alloc();      // старый блок цел
        data_ = static_cast<T *>(p);
        cap_ = n;
    }
};
```

Важно: это **не** `std::vector` и не замена ему; память обязана быть из `malloc`-семейства, а `std::allocator` здесь не задействован. Для C++20+ дополнительно помогает модель implicit-lifetime (P0593) и `std::start_lifetime_as_array` (C++23), легализующие «создание объектов записью в malloc-память».

## 6. `realloc` vs «allocate + move + free»

| Свойство | `realloc` | `allocate` + поэлементный перенос + `deallocate` |
|---|---|---|
| Перенос | побайтовый (`memcpy`) | move/copy-конструкторы |
| Типы | только memcpy-релокируемые (POD/trivially copyable) | любые |
| Исключения | не бросает, `NULL` | может бросить `bad_alloc` |
| Аллокатор | только `malloc`-семейство | любой, включая арены и fancy pointers |
| Выравнивание | фундаментальное | любое (`aligned new`) |
| Деструкторы | не вызываются | вызываются |
| Цена | иногда O(1) (mremap / рост на месте) | всегда O(n) |
| Strong guarantee | почти бесплатно | требует `noexcept` move или копирования |
| Инвалидация | указатели/итераторы/ссылки | то же самое |

## 7. Родственные инструменты и альтернативы

- **`reallocarray(p, n, size)`** (BSD, glibc ≥ 2.26) — то же, но с проверкой переполнения `n * size`; удобно для массивов.
- **`malloc_usable_size`** (glibc) — узнать фактический размер блока: если там уже есть запас, можно не звать `realloc` и сэкономить копирование. Непереносимо.
- **`jemalloc`/`tcmalloc`**: `xallocx`/`rallocx` умеют «расширить на месте», часто дешевле `realloc`.
- **`std::allocator::allocate_at_least` (C++23)** — аллокатор может вернуть блок **больше запрошенного**; контейнер запоминает фактическую ёмкость и реже растёт. Идейный аналог того, что `realloc`/`malloc_usable_size` дают в C.
- **Arena/пул**: `realloc` неприменим, вместо него — «новая арена + копирование» либо цепочка чанков (как в `deque`/`rope`).
- **Уменьшение (`shrink`)**: `realloc(p, smaller)` может как вернуть тот же блок, так и переехать; в C++ аналог — `shrink_to_fit()` (не обязывающий). Часто выгоднее оставить ёмкость как есть.

## 8. Чек-лист «как правильно использовать `realloc` в контейнере»

1. Результат — в отдельную переменную; `v->data = p` только после проверки на `NULL`.
2. Проверять переполнение `count * sizeof(T)` **до** умножения.
3. Геометрический рост (×1.5…×2), отдельная обработка `capacity == 0`.
4. `size == 0` → `free` + `NULL`, а не `realloc`.
5. Хранить `size`/`capacity`, после роста обновлять все производные указатели (или хранить индексы).
6. Не `realloc`-ить память не из `malloc`-семейства, не смешивать с `new`/аллокаторами.
7. Применять только к тривиально копируемым, не self-referential типам с фундаментальным выравниванием.
8. Помнить про инвалидацию: документировать её и советовать пользователю `reserve()`.
9. Не забывать про SSO: встроенный буфер нельзя `realloc`-ить.
10. При ошибке оставлять контейнер в прежнем состоянии (старый блок цел — используйте это).

## 9. Типичные вопросы-ловушки

**— Чем плохо `p = realloc(p, n)`?**
При неудаче возвращается `NULL`, старый блок остаётся выделенным, но указатель на него потерян → утечка. Нужна временная переменная.

**— `realloc` вернул `NULL`. Что со старым блоком?**
Он жив и не изменён. Освобождать его нужно самостоятельно, данные не потеряны.

**— `realloc(p, 0)` — это ошибка выделения?**
Нет. До C23 — implementation-defined (`NULL` или уникальный указатель), в C23 — UB. Не полагайтесь на `NULL` как на признак OOM.

**— Обнуляет ли `realloc` новый хвост?**
Нет, новые байты неинициализированы; нужен `memset`.

**— Можно ли `realloc`-ить `std::string`/`std::vector`-буфер?**
Нет: память из `operator new`/аллокатора, плюс нетривиальные типы и возможная SSO.

**— Почему `std::vector` не делает `realloc`?**
Потому что стандарт требует аллокатор и конструкторы/деструкторы элементов; `realloc` даёт только побайтовое копирование и обходит аллокатор.

**— Инвалидирует ли `realloc` итераторы, если вернул тот же адрес?**
Формально `vector` считает реаллокацию инвалидирующей в любом случае; полагаться на совпадение адреса нельзя.

**— Что будет с указателями на элементы после роста?**
Висячие (если блок переехал). Внутри контейнера спасают индексы/смещения, снаружи — `reserve` и правило «не держи указатели через `push_back`».

## Итог

`realloc` — это низкоуровневый инструмент роста буфера, идеально ложащийся на **C-контейнеры из POD-элементов**: он даёт амортизированное O(1) расширение, автоматически сохраняет данные и часто оптимизируется аллокатором (рост на месте, `mremap`). Но платой являются жёсткие ограничения: только `malloc`-память, только memcpy-релокируемые типы, никаких конструкторов/деструкторов, фундаментальное выравнивание и обязательная инвалидация всех внешних указателей. В C++ стандартные контейнеры поэтому строятся на аллокаторах и поэлементном переносе, а `realloc` остаётся нишевым приёмом для специализированных POD-векторов — при условии аккуратной проверки `NULL`, `size == 0` и переполнений.
