# 28. Как работает RTTI?

**RTTI (Run-Time Type Information)** — механизм C++, который позволяет во время выполнения узнать **динамический тип** объекта и выполнить **безопасное приведение** указателей/ссылок внутри иерархии наследования. Появился в C++98 и включает три основных элемента: оператор `typeid`, оператор `dynamic_cast` и класс `std::type_info`. В языке C RTTI нет вообще — там тип известен только на этапе компиляции, и его эмулируют вручную (теги, `enum`, размеченные объединения).

Важно понимать: RTTI в C++ — это **не рефлексия**. С его помощью нельзя перечислить поля класса, создать объект по имени типа и т.п.

---

## 1. Статический и динамический тип

- **Статический тип** — тип, который видит компилятор: `Base* p`.
- **Динамический тип** — тип объекта, на который реально указывает `p` (например, `Derived`).

RTTI нужен именно для того, чтобы получить второй из первого. Но работает он **только для полиморфных типов** — классов, у которых есть хотя бы одна виртуальная функция (в частности, виртуальный деструктор). Именно наличие виртуальной функции гарантирует, что в объекте есть `vptr`, а значит, есть за что «зацепить» информацию о типе.

Если класс неполиморфный, `typeid` всё равно применим, но он даёт **статический** тип, а `dynamic_cast` для понижающего приведения использовать нельзя.

---

## 2. Где хранится информация о типе

### 2.1. Идея: указатель на `type_info` в таблице виртуальных функций

У полиморфного объекта первый (или один из) членов — скрытый указатель `vptr` на таблицу виртуальных функций (`vtable`). Ключевая идея RTTI: **рядом с таблицей виртуальных функций кладётся указатель на объект `std::type_info`**, описывающий динамический тип.

В **Itanium ABI** (GCC, Clang, большинство Unix-платформ) `vtable` устроена так:

```
        +--------------------------+
vptr -> | 0: offset_to_top         |   ptrdiff_t — смещение до начала полного объекта
        | 1: typeinfo pointer      |   const std::type_info*
        | 2: &D::f                 |   указатели на виртуальные функции
        | 3: &D::g                 |
        +--------------------------+
```

При этом `vptr` указывает на **первый слот с виртуальной функцией**, а служебные поля лежат по отрицательным индексам. Поэтому:

```cpp
// Псевдокод: как компилятор реализует typeid(*p) для полиморфного *p
const std::type_info* ti =
    *reinterpret_cast<const std::type_info**>(
        *reinterpret_cast<void***>(p) - 1);   // vptr[-1]
```

То есть `typeid(*p)` — это буквально **одна загрузка указателя из `vptr[-1]`**. Очень дёшево.

При множественном наследовании у объекта несколько `vptr` (по одному на каждый подобъект-базу, не являющийся primary base), и каждый ведёт в свою `vtable` со своим `offset_to_top`, но с указателем на **`type_info` полного объекта**. Благодаря этому `typeid(*b)` через любую базу даёт тип самого производного объекта.

### 2.2. Иерархия классов внутри `type_info`

Чтобы `dynamic_cast` мог ходить по иерархии, одной строки с именем типа мало. В Itanium ABI объект RTTI для класса — это не «чистый» `std::type_info`, а объект более богатого типа:

- `__class_type_info` — класс без баз (или с недоступными базами);
- `__si_class_type_info` — одиночное наследование, хранит указатель на typeinfo базы;
- `__vmi_class_type_info` — множественное/виртуальное наследование, хранит флаги и массив описаний баз: `{ typeinfo базы, offset | флаги }`.

Именно эти структуры (они наследуются от `std::type_info`, так что приведение к `type_info*` корректно) и обходит `__dynamic_cast`.

### 2.3. MSVC ABI

В MSVC `vftable[-1]` содержит указатель на `RTTICompleteObjectLocator` (COL). Упрощённо:

```cpp
struct RTTICompleteObjectLocator {
    DWORD signature;
    DWORD offset;                    // смещение этой vftable в полном объекте
    DWORD cdOffset;                  // constructor displacement
    TypeDescriptor* pTypeDescriptor; // описание типа (совместимо с std::type_info)
    RTTIClassHierarchyDescriptor* pClassDescriptor;
};

struct RTTIClassHierarchyDescriptor {
    DWORD signature;
    DWORD attributes;                // флаги: множественное/виртуальное наследование
    DWORD numBaseClasses;
    RTTIBaseClassArray* pBaseClassArray;
};

struct RTTIBaseClassDescriptor {
    TypeDescriptor* pTypeDescriptor;
    DWORD numContainedBases;
    PMD where;                       // mdisp, pdisp, vdisp — смещения подобъекта
    DWORD attributes;                // в т.ч. признак неоднозначности, virtual base
    RTTIClassHierarchyDescriptor* pClassDescriptor;
};
```

`TypeDescriptor` в MSVC устроен как `{ void* vfptr; char* name; }` и **layout-совместим** с `std::type_info`, поэтому `typeid` и там возвращает ссылку на `std::type_info`. Работу `dynamic_cast` выполняет функция `__RTDynamicCast` из CRT.

### 2.4. Сравнение реализаций

| | Itanium ABI (GCC/Clang) | MSVC ABI |
|---|---|---|
| Указатель на RTTI | `vptr[-1]` | `vftable[-1]` |
| Объект RTTI | `std::type_info` + `__class_type_info` и наследники | `TypeDescriptor` (+ отдельные структуры иерархии) |
| Описание баз | внутри `__vmi_class_type_info` | `RTTIClassHierarchyDescriptor` → `RTTIBaseClassArray` |
| Функция приведения | `__dynamic_cast` (`libstdc++`/`libc++abi`) | `__RTDynamicCast` |

## 3. Оператор `typeid`

Синтаксис: `typeid(тип)` или `typeid(выражение)`. Результат — `const std::type_info&` (lvalue со статическим временем жизни; требуется `#include <typeinfo>`).

### 3.1. Когда это статический тип, а когда динамический

| Операнд | Что вернёт | Вычисляется ли операнд |
|---|---|---|
| `typeid(T)` (имя типа) | `type_info` для `T` | нет |
| `typeid(expr)`, статический тип неполиморфный | `type_info` статического типа | **нет** (невычисляемый операнд) |
| `typeid(expr)`, `expr` — glvalue полиморфного типа | `type_info` **динамического** типа | да |
| `typeid(ptr)` | `type_info` типа указателя, а не указываемого типа | нет |

Отсюда классическая ошибка:

```cpp
Base* p = new Derived;
typeid(p).name();   // "Base*" — тип указателя!
typeid(*p).name();  // "Derived" — динамический тип (нужно разыменование)
```

### 3.2. Тонкости `typeid`

- **`bad_typeid`.** Если операнд — это `*p`, где `p` — нулевой указатель на полиморфный тип, `typeid` **бросает `std::bad_typeid`**. Для неполиморфного типа разыменования не происходит, поэтому проверки нет.
- **cv-квалификаторы и ссылки отбрасываются:** `typeid(const Derived&)` → `Derived`.
- **Массивы и функции:** для выражений не применяются lvalue-to-rvalue, array-to-pointer и function-to-pointer преобразования, поэтому `typeid(arr)` даёт тип массива.
- **`typeid(void)`** допустим.
- Время жизни: объекты `type_info` — статические, существуют всё время работы программы, по одному на тип (в пределах одной «единицы» линковки).

### 3.3. Интерфейс `std::type_info`

```cpp
namespace std {
class type_info {
public:
    virtual ~type_info();
    const char* name() const noexcept;        // искажённое (mangled) имя
    bool before(const type_info& rhs) const noexcept; // порядок, зависит от реализации
    size_t hash_code() const noexcept;        // C++11
    bool operator==(const type_info& rhs) const noexcept;
    bool operator!=(const type_info& rhs) const noexcept;
    type_info(const type_info&) = delete;     // копировать нельзя
    type_info& operator=(const type_info&) = delete;
};
}
```

- `name()` возвращает **mangled**-имя (`7Derived` у GCC, `.?AVDerived@@` у MSVC). Для читаемости: `abi::__cxa_demangle` (`<cxxabi.h>`) или `UnDecorateSymbolName` на Windows.
- `hash_code()` и `before()` удобны для `unordered_map`/`map` с ключом-типом.
- **Сравнение на равенство:** обычно сравниваются указатели на имя типа, а в libstdc++ есть ещё и резервное `strcmp` для случаев, когда имена не «слиты» линкером. На границах разделяемых библиотек/DLL возможны сюрпризы: два `type_info` для одного типа могут оказаться разными объектами. Наиболее переносимо — сравнивать `name()` (строки), но это медленнее.

## 4. Оператор `dynamic_cast`

### 4.1. Формы и правила

```cpp
dynamic_cast<T*>(p)   // при неудаче — nullptr (для p == nullptr тоже nullptr)
dynamic_cast<T&>(r)   // при неудаче — исключение std::bad_cast
dynamic_cast<void*>(p) // указатель на наиболее производный объект
```

Требования и ограничения:

- `T` — указатель/ссылка на **полный** класс либо `void*`.
- Для **понижающего** приведения (downcast) и бокового (cross-cast) исходный тип должен быть **полиморфным**, иначе — ошибка компиляции.
- Повышающее приведение (upcast) `dynamic_cast` тоже умеет, но оно эквивалентно `static_cast` — смысла в нём нет.
- `dynamic_cast` **не снимает const**: `dynamic_cast<T*>(const T*)` — ошибка; нужен предварительный `const_cast`.
- Для ссылок нет «нулевого» результата, поэтому неудача — исключение.

### 4.2. Что происходит во время выполнения

Упрощённо алгоритм такой:

1. Из `vptr` объекта берётся `type_info` **динамического (полного) типа**.
2. По описанию иерархии (в Itanium — структуры `__*_class_type_info`, в MSVC — `RTTIBaseClassArray`/`RTTIBaseClassDescriptor`) выполняется поиск целевого типа среди баз.
3. Если цель — база, вычисляется **смещение** соответствующего подобъекта: для невиртуальной базы — константа из описания, для виртуальной — дополнительно через `vbtable`.
4. Если цель не найдена или найдена **неоднозначно** (амбивалентная база), возвращается `nullptr` / бросается `bad_cast`.
5. Если цель найдена, возвращается указатель, **скорректированный** на смещение подобъекта.

В Itanium ABI это вызов вида:

```cpp
__dynamic_cast(p, typeid(Source), typeid(Target), hint);
```

В MSVC — `__RTDynamicCast(p, 0, typeid(Source), typeid(Target), isReference)`.

### 4.3. Примеры

```cpp
struct Base { virtual ~Base() = default; };
struct Derived : Base { void hello() const {} };
struct Other : Base {};

void f(Base* p) {
    if (auto* d = dynamic_cast<Derived*>(p)) {
        d->hello();                 // OK: p действительно указывает на Derived
    }
    // ...
}

void g(Base& r) {
    try {
        Derived& d = dynamic_cast<Derived&>(r);
    } catch (const std::bad_cast&) {
    }
}
```

**Cross-cast (боковое приведение)** — приведение между «братскими» базами одного объекта:

```cpp
struct A { virtual ~A() = default; };
struct B { virtual ~B() = default; };
struct D : A, B {};

B* b = new D;
A* a = dynamic_cast<A*>(b);   // OK: cross-cast, a указывает на A-подобъект того же D
```

**`dynamic_cast<void*>` — идентичность полного объекта.** Очень полезный приём: позволяет узнать, указывают ли два указателя на разные подобъекты одного и того же объекта:

```cpp
bool same_object(Base* x, Base* y) {
    return dynamic_cast<void*>(x) == dynamic_cast<void*>(y);
}
```

**Амбивалентная база.** Если база входит в объект дважды (ромбовидное наследование без `virtual`), приведение к ней неоднозначно и завершается неудачей:

```cpp
struct A { virtual ~A() = default; };
struct B1 : A {};
struct B2 : A {};
struct D : B1, B2 {};

D d;
// dynamic_cast<A*>(&d) — ошибка компиляции: A неоднозначная база
```

### 4.4. `dynamic_cast` против `static_cast`

| | `static_cast` | `dynamic_cast` |
|---|---|---|
| Проверка во время выполнения | нет | да |
| Требует полиморфности | нет | да (для downcast/cross-cast) |
| Стоимость | нулевая (смещение известно) | обход иерархии |
| Ошибка | UB при неверном downcast | `nullptr` / `bad_cast` |
| Виртуальные базы | нельзя | можно |

`static_cast` для downcast допустим только тогда, когда программист **гарантирует** правильность типа. Ошибка здесь — неопределённое поведение, а не исключение.

## 5. RTTI и исключения

Обработка исключений использует ту же информацию о типах: при `throw` компилятор кладёт в объект исключения (или в специальную таблицу) `type_info`, а при поиске подходящего `catch` проверяет совместимость динамического типа брошенного объекта с типом обработчика — с учётом наследования (то есть `catch (const Base&)` поймает `Derived`).

Именно поэтому даже при `-fno-rtti` компилятор GCC/Clang всё равно генерирует `type_info`, необходимые для исключений («as needed»).

---

## 6. Отключение RTTI

Флаги: `-fno-rtti` (GCC/Clang), `/GR-` (MSVC). Проверка в коде: макросы `__GXX_RTTI` / `_CPPRTTI`.

Последствия:

- `typeid` для **полиморфных** типов недоступен (ошибка компиляции); для неполиморфных обычно продолжает работать, так как вычисляется статически.
- `dynamic_cast` работает только для upcast и для `void*`.
- Исключения продолжают работать (информация генерируется по мере необходимости).
- Экономия: минус указатель в каждой `vtable` и минус таблицы описания иерархии в бинарнике. На размер самого объекта это не влияет — `vptr` всё равно есть.

---

## 7. Стоимость и альтернативы

**Стоимость RTTI:**

- +1 указатель (8 байт) в каждой `vtable` — на объект не влияет.
- Таблицы описания иерархии в read-only сегменте — заметный вклад в размер бинарника.
- `typeid` — практически бесплатно (одна загрузка).
- `dynamic_cast` — от «дёшево» до «дорого»: зависит от глубины и ширины иерархии, наличия виртуальных баз и реализации; в худшем случае — обход графа баз.

**Когда `dynamic_cast` — не лучший выбор:**

- Если типов немного и они известны — виртуальная функция (двойная диспетчеризация, паттерн «посетитель») быстрее и чище.
- `std::variant` + `std::visit` — типобезопасная альтернатива для замкнутого набора типов.
- Ручной тег (`enum class Kind`) в базовом классе — самый быстрый, но требует дисциплины.
- `typeid`-сравнение подходит, когда нужно проверить **точный** тип (не «является ли базой»), но не заменяет `dynamic_cast` для иерархий.

**Когда RTTI уместен:** плагины, сериализация/десериализация по именам типов, диагностика, обобщённые контейнеры указателей на базы, `dynamic_cast<void*>` для проверки идентичности объекта.

## 8. Практические подводные камни

1. **`typeid(p)` вместо `typeid(*p)`** — самая частая ошибка; даёт тип указателя.
2. **`typeid(*p)` на нулевом указателе** бросает `std::bad_typeid` — нужна проверка `p != nullptr`.
3. **`typeid` — это точный тип, а не «является ли».** `typeid(*p) == typeid(Base)` истинно только для объекта ровно типа `Base`, но не для `Derived`. Для проверки «является ли» нужен `dynamic_cast`.
4. **`dynamic_cast` в конструкторе/деструкторе.** Пока объект не достроен (или уже начал разрушаться), `vptr` указывает на таблицы текущего класса, поэтому `typeid(*this)` и `dynamic_cast` видят **текущий** тип, а не самый производный. Понижающее приведение к ещё не сконструированному типу даст `nullptr`.
5. **Неполный тип.** `dynamic_cast` к типу, определение которого неизвестно, не компилируется — нужен полный тип.
6. **`const`.** `dynamic_cast` не снимает константность; сначала `const_cast`, потом `dynamic_cast` (и лучше — не снимать вовсе).
7. **Границы DLL/DSO.** Сравнение `type_info` по адресу может не сработать между модулями; безопаснее сравнивать `name()` или использовать `hash_code()` с оговорками.
8. **Ссылочная форма** требует `try/catch`, что не всегда уместно; указательная форма с проверкой на `nullptr` обычно удобнее.
9. **`dynamic_cast<void*>`** — единственный способ надёжно получить адрес полного объекта из указателя на базу (полезно для `unordered_set` по идентичности объекта).

## 9. Сводный пример

```cpp
#include <iostream>
#include <typeinfo>
#include <typeinfo>   // std::bad_cast, std::bad_typeid

struct Base {
    virtual ~Base() = default;
};

struct Derived : Base {
    void hello() const { std::cout << "Derived::hello\n"; }
};

struct Other : Base {};

void inspect(Base* p) {
    if (!p) return;

    // 1. Динамический тип
    std::cout << "dynamic type: " << typeid(*p).name() << '\n';

    // 2. Безопасное понижающее приведение
    if (auto* d = dynamic_cast<Derived*>(p)) {
        d->hello();
    } else {
        std::cout << "not a Derived\n";
    }

    // 3. Приведение к полному объекту
    std::cout << "complete object at " << dynamic_cast<void*>(p) << '\n';
}

int main() {
    Derived d;
    Other   o;
    inspect(&d);
    inspect(&o);

    // typeid для неполиморфного типа — статический, операнд не вычисляется
    int x = 0;
    std::cout << typeid(++x).name() << '\n';  // x останется 0
}
```

## Итог

RTTI в C++ устроен на удивление просто в основе и сложно в деталях:

- **Носитель информации** — `vtable`, рядом с виртуальными функциями которой лежит указатель на `type_info`; сам объект не толстеет.
- **`typeid`** — загрузка этого указателя (для полиморфного операнда) либо константа, вычисленная компилятором.
- **`dynamic_cast`** — обход описания иерархии, хранящегося в объекте RTTI, с вычислением смещения целевого подобъекта; ошибка — `nullptr` или `bad_cast`.
- **Исключения** используют тот же механизм для подбора `catch`.
- Всё это доступно только для полиморфных типов и может быть отключено (`-fno-rtti`/`/GR-`) ценой потери `typeid`/`dynamic_cast` для них.
