# 54. Расскажите о построении API, рассчитанных на многопоточное использование.

## 1. Постановка задачи

«API, рассчитанный на многопоточное использование» — это интерфейс, у которого **контракт по потокобезопасности явно определён, зафиксирован в документации и не заставляет клиента угадывать**, какие операции можно выполнять одновременно, а какие нужно сериализовать снаружи. Хороший многопоточный API решает три задачи:

1. **Корректность** — исключает гонки данных (data races), взаимные блокировки, висячие ссылки и нарушение инвариантов.
2. **Композируемость** — клиент не обязан знать внутреннее устройство блокировок и не должен строить глобальные схемы захвата, чтобы просто вызвать два метода подряд.
3. **Масштабируемость** — синхронизация не превращает программу в однопоточную; стоимость и точка конкуренции предсказуемы.

Ключевая мысль: **потокобезопасность — это не бинарное свойство, а спектр**, и проектирование API начинается с осознанного выбора точки на этом спектре, а не с «навесим мьютекс на каждый метод».

---

## 2. Контракт: уровни потокобезопасности

Классическая классификация, которую полезно явно указывать в документации каждого класса/функции:

| Уровень | Определение | Типичные примеры |
|---|---|---|
| **Thread-safe** (потокобезопасный) | Безопасен при одновременном вызове из нескольких потоков без внешней синхронизации. | `std::mutex`, `malloc`, контрольный блок `std::shared_ptr`, `std::atomic` |
| **Reentrant** (реентерабельный) | Может быть повторно вызван тем же потоком (рекурсия, обработчик сигнала, колбэк) — не использует изменяемого статического/глобального состояния. Обычно, но не обязательно, потокобезопасен. | функции без static-буферов; `_r`-варианты POSIX |
| **Thread-compatible** | Безопасен, если каждый поток работает со **своим** объектом; для разделяемого объекта нужна внешняя синхронизация. | `std::vector`, `std::string`, `std::map` |
| **Thread-hostile** | Небезопасен даже при внешней синхронизации из-за скрытого разделяемого состояния. | `strtok`, `asctime`, `localtime`, `gethostbyname` (static-буферы) |

Отдельно стоит помнить о **гарантиях стандартной библиотеки C++** (C++11, `[res.on.data.races]`, `[container.requirements.dataraces]`):

- `const`-методы стандартных контейнеров можно вызывать **одновременно** из разных потоков над одним объектом;
- разные **элементы** одного контейнера можно изменять одновременно (исключение — `std::vector<bool>` из-за упаковки битов);
- потоки ввода-вывода синхронизированы на уровне **отдельных символов**, но не на уровне форматирования: порядок и целостность «строки» не гарантируются;
- `std::shared_ptr` потокобезопасен только в части **контрольного блока** (счётчик ссылок); сам объект-указатель — нет.

Эти гарантии — хороший образец того, как надо формулировать контракт: точно, по операциям, с указанием исключений.

## 3. Базовая модель: инварианты, гонки, happens-before

Формальный фундамент в C++11+ — **модель памяти**:

- **Data race** (два потока обращаются к одной ячейке, хотя бы один пишет, без синхронизации) — это **undefined behavior**, а не «просто неверное значение».
- Легальная синхронизация задаётся отношением **happens-before**: мьютексы, атомарные операции с нужным `memory_order`, `std::thread::join`, `std::promise/future`, `std::condition_variable`.
- Компилятор и процессор вправе переставлять обращения, поэтому «флаг готовности» обязан быть атомарным с `release/acquire`, иначе публикация данных некорректна.

Практический вывод для API: **каждый класс должен иметь явно сформулированный инвариант** (что всегда истинно между публичными вызовами) и правило, **какая блокировка его защищает**. Тогда проектирование сводится к тому, чтобы ни один публичный метод не мог наблюдать объект в нарушенном состоянии.

## 4. Ключевые принципы проектирования

### 4.1. Явный документированный контракт

Для каждого класса и функции указывается:

- уровень потокобезопасности (см. таблицу выше);
- какие операции **атомарны по отдельности**, а какие — **нет** (важно для составных сценариев);
- можно ли уничтожать объект, пока с ним работают другие потоки;
- гарантии по памяти (например, «после `publish()` данные видны читателям»);
- поведение при конкурентном вызове `close`/`destroy`/`cancel`.

Без этого клиент вынужден либо блокировать всё, либо надеяться на лучшее.

### 4.2. Инкапсуляция синхронизации

Мьютекс — **деталь реализации**, а не часть интерфейса. Если API требует от клиента «захвати мой мьютекс», то:

- клиент может забыть это сделать;
- клиент может захватить его в неверном порядке и получить deadlock;
- анализ блокировок становится глобальным по всей программе;
- нельзя поменять стратегию синхронизации, не сломав ABI/исходники клиентов.

Исключение — явные «scoped» API вида `with_lock(fn)` / `synchronized_value`, где блокировка выдаётся на время выполнения замыкания и не «утекает» наружу.

### 4.3. Минимизация разделяемого изменяемого состояния

Самый быстрый мьютекс — тот, которого нет. Иерархия предпочтений:

1. **Эксклюзивное владение** (объект живёт в одном потоке) — синхронизация не нужна вовсе.
2. **Неизменяемые разделяемые данные** (`const`, `shared_ptr<const T>`) — читать можно без блокировок.
3. **Передача сообщений** (очередь, `future`) — состояние не разделяется, а передаётся.
4. **Разделяемое изменяемое состояние под блокировкой** — крайний случай, когда предыдущие не подходят.

### 4.4. Неизменяемость и передача владения

Иммутабельные объекты — идеальный «разделяемый ресурс»: их можно свободно читать из любого числа потоков. Отсюда два приёма:

- возвращать **значения**, а не ссылки (`std::optional<T>`, `T`, `std::shared_ptr<const T>`);
- обновлять состояние через **замену указателя** на новую неизменяемую версию (copy-on-write / snapshot).

### 4.5. Гранулярность операций: атомарность должна совпадать с вариантом использования

Классическая ошибка — предоставить только «атомарные кирпичики»:

```cpp
// ПЛОХО: между вызовами состояние может измениться — TOCTOU
if (cache.contains(key)) {
    auto v = cache.get(key);   // другой поток мог удалить key
}
```

Клиент вынужден либо брать внешний мьютекс (см. 4.2), либо получать гонку. Правильное решение — **составные операции**, соответствующие реальным сценариям:

```cpp
std::optional<Value> find(const Key&) const;          // вернуть значение или ничего
Value get_or_insert(const Key&, F&& factory);          // атомарно «найти или создать»
template <class F> auto with_entry(const Key&, F&&);   // доступ под блокировкой, без утечки ссылки
```

Правило: **проектируйте API от атомарных сценариев клиента, а не от полей структуры данных**.

### 4.6. Не вызывать пользовательский код под блокировкой

Callback, виртуальный метод, компаратор, аллокатор, `operator<<` — всё это потенциально чужой код, который может:

- вызвать обратно в ваш API (реентерабельность → deadlock на нерекурсивном мьютексе);
- захватить собственную блокировку (инверсия порядка → deadlock);
- заблокироваться надолго (блокировка удерживается, масштабируемость падает).

Решения:

- копировать нужные данные под блокировкой и вызывать callback **после** её освобождения;
- либо явно документировать, что callback вызывается под блокировкой и не должен реентерить (и предусмотреть `_unlocked`-варианты);
- для уведомлений — `notify_one/notify_all` **вне** критической секции (это ещё и устраняет «hurry up and wait»).

### 4.7. Не отдавать внутренние ссылки, указатели и итераторы

Ссылка/итератор на внутренний элемент «живёт» вне блокировки, а значит:

- другой поток может изменить контейнер и инвалидировать её (`std::vector` при реаллокации);
- объект может быть уничтожен, пока клиент держит ссылку.

Возвращайте **копии/значения** или **владеющие умные указатели** (`std::shared_ptr`), либо используйте `with_lock`-паттерн.

### 4.8. RAII и исключения

Блокировка обязана освобождаться при любом выходе, включая исключения:

```cpp
{
    std::lock_guard<std::mutex> lk(m_);   // освободит при unwind
    mutate();                              // может бросить
}
```

`std::unique_lock` — когда нужны `wait`, `unlock`/`lock` вручную, передача владения. `std::scoped_lock` (C++17) — для нескольких мьютексов сразу, без deadlock. Никогда не пишите `m_.lock(); ... m_.unlock();` вручную.

При этом продумайте **гарантию исключительности**: если исключение вылетело на середине изменения, объект должен остаться в согласованном состоянии (базовая гарантия минимум).

### 4.9. Порядок блокировок и предотвращение deadlock

- Ввести **иерархию блокировок** (уровни/ранги) и документировать её.
- Захватывать несколько мьютексов **атомарно**: `std::scoped_lock lk(a.m_, b.m_);` или `std::lock(a, b);` — стандарт сам избегает взаимной блокировки.
- Не захватывать блокировку «наугад» внутри callback.
- `std::recursive_mutex` — почти всегда признак ошибки проектирования: он маскирует проблему, но не решает инверсию порядка.

### 4.10. `const` ≠ потокобезопасность

`const`-метод может менять `mutable`-поля: кэш, ленивую инициализацию, счётчик. Если такой метод вызывается конкурентно, нужна синхронизация:

```cpp
class Image {
public:
    const std::vector<uint8_t>& thumbnail() const {
        std::call_once(once_, [this] { thumb_ = make_thumb(data_); });
        return thumb_;                 // ссылка на внутреннее поле — см. 4.7
    }
private:
    mutable std::once_flag once_;
    mutable std::vector<uint8_t> thumb_;
};
```

`std::call_once` и «магические» статические локальные переменные (C++11) — потокобезопасны по стандарту; самодельный «double-checked locking» без атомиков — нет.

## 5. Приёмы и паттерны

### 5.1. Monitor object (объект-монитор)

Классика: приватный мьютекс + все публичные методы захватывают его. Просто, корректно, но плохо масштабируется при высокой конкуренции.

### 5.2. Thread-safe interface (паттерн Саттера)

Публичные методы захватывают блокировку и вызывают приватные «реализации», которые **предполагают, что блокировка уже удерживается**. Это позволяет строить составные операции без рекурсивного захвата и без внешней синхронизации:

```cpp
class Account {
public:
    void deposit(Money m) {
        std::lock_guard<std::mutex> lk(m_);
        depositImpl(m);
    }
    Money balance() const {
        std::lock_guard<std::mutex> lk(m_);
        return balance_;
    }
    void transfer(Account& to, Money m) {
        std::scoped_lock lk(m_, to.m_);   // оба мьютекса, без deadlock
        if (balance_ < m) throw std::runtime_error("insufficient funds");
        withdrawImpl(m);
        to.depositImpl(m);
    }
private:
    void depositImpl(Money m) { balance_ += m; }
    void withdrawImpl(Money m) { balance_ -= m; }

    mutable std::mutex m_;
    Money balance_{};
};
```

### 5.3. Scoped locking / `synchronized_value`

Когда клиенту нужен именно «составной доступ», отдайте ему не мьютекс, а **замыкание под блокировкой**:

```cpp
template <class T>
class Synchronized {
public:
    template <class F>
    decltype(auto) with_lock(F&& f) {
        std::lock_guard<std::mutex> lk(m_);
        return std::forward<F>(f)(value_);
    }
private:
    mutable std::mutex m_;
    T value_;
};
```

(В стандарт такая обёртка пока не вошла, но есть в Concurrency TS как `std::synchronized_value`; аналоги — `absl::Mutex` + `ABSL_EXCLUSIVE_LOCKS_REQUIRED`.)

### 5.4. Reader-writer locking

Если чтений много, а записей мало — `std::shared_mutex` (C++17) + `std::shared_lock` для читателей, `std::unique_lock` для писателя. Важно: RW-мьютекс не бесплатен, при частых записях он может быть **медленнее** обычного, а также подвержен «голоданию» писателей в некоторых реализациях.

### 5.5. Copy-on-write / snapshot (иммутабельные снимки)

Идеально для конфигураций, таблиц маршрутизации, кэшей «читают все — пишет один»:

```cpp
class Config {
public:
    std::shared_ptr<const Data> snapshot() const {
        return std::atomic_load(&data_);          // C++11 free functions
    }
    void update(Data d) {
        auto p = std::make_shared<const Data>(std::move(d));
        std::atomic_store(&data_, std::move(p));  // публикация нового снимка
    }
private:
    std::shared_ptr<const Data> data_;
};
```

В C++20 то же самое выражается через `std::atomic<std::shared_ptr<const Data>>`. Читатели никогда не блокируются, писатель платит за копию. Ограничение — стоимость копирования и слабая согласованность между снимками.

### 5.6. Шардирование (striping)

Один мьютекс на N сегментов; поток выбирает сегмент по хэшу ключа. Снижает конкуренцию без изменения внешнего API:

```cpp
static constexpr int kShards = 64;
std::array<Shard, kShards> shards_;   // каждая — со своим мьютексом и map
```

### 5.7. Состояние на поток (thread-local)

`thread_local` (C++11) / `_Thread_local` (C11) убирает разделение вовсе: кэши, буферы, генераторы случайных чисел, `errno`-подобные ошибки. Важно: TLS-объекты уничтожаются при завершении потока, и порядок их разрушения относительно других статических объектов не гарантирован.

### 5.8. Передача сообщений и producer-consumer

Вместо «разделяемого объекта с методами» — очередь задач. Клиент не держит блокировку, а **передаёт владение** задачей/данными:

```cpp
template <class T>
class BlockingQueue {
public:
    void push(T v) {
        {
            std::lock_guard<std::mutex> lk(m_);
            q_.push(std::move(v));
        }
        cv_.notify_one();                  // уведомляем вне блокировки
    }
    T pop() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this] { return !q_.empty(); });   // защита от spurious wakeup
        T v = std::move(q_.front());
        q_.pop();
        return v;
    }
    bool try_pop(T& out) {
        std::lock_guard<std::mutex> lk(m_);
        if (q_.empty()) return false;
        out = std::move(q_.front());
        q_.pop();
        return true;
    }
private:
    std::mutex m_;
    std::condition_variable cv_;
    std::queue<T> q_;
};
```

Это самый масштабируемый и самый безопасный по инвариантам способ «поделиться состоянием»: данные не разделяются, а перемещаются.

### 5.9. Ленивая инициализация

- «Магический» статик (C++11) — потокобезопасен по стандарту:

```cpp
Config& config() {
    static Config instance;   // инициализация ровно один раз, потокобезопасно
    return instance;
}
```

- `std::call_once` + `std::once_flag` — когда инициализация не сводится к конструктору.
- Осторожно с порядком разрушения статиков: другие потоки не должны работать с объектом во время `exit`. Глобальные объекты — источник «static destruction order fiasco» и «dead reference problem»; предпочтительны явные `init()/shutdown()` или функциональные статики.

### 5.10. Разделяемые умные указатели

- `std::shared_ptr` — счётчик ссылок потокобезопасен, но **сам указатель — нет**: одновременные чтение и запись одного и того же `shared_ptr` — гонка. Используйте `std::atomic<std::shared_ptr<T>>` (C++20) либо `atomic_load/atomic_store` (C++11, объявлены deprecated в C++20).
- `std::weak_ptr::lock()` — потокобезопасный способ «попытаться продлить жизнь» объекта.

### 5.11. Атомики и lock-free

Атомарные операции — фундамент, но **не** универсальный ответ:

- `std::atomic<T>` для счётчиков, флагов, указателей; `memory_order_relaxed` для статистики, `release/acquire` для публикации.
- `std::atomic_ref<T>` (C++20) — атомарный доступ к обычному объекту.
- Lock-free структуры сложны: ABA-проблема, освобождение памяти (hazard pointers, RCU, epoch-based reclamation), гарантии прогресса (wait-free / lock-free / obstruction-free). Как **публичный API** их стоит предлагать только при доказанной необходимости и с честно описанными гарантиями.

### 5.12. Аннотации потокобезопасности

Компилятор умеет проверять контракт статически (Clang Thread Safety Analysis, аналоги в Abseil):

```cpp
class Counter {
public:
    void inc() {
        std::lock_guard<std::mutex> lk(m_);
        ++value_;
    }
    int get() const {
        std::lock_guard<std::mutex> lk(m_);
        return value_;
    }
private:
    mutable std::mutex m_;
    int value_ GUARDED_BY(m_);   // проверяется компилятором
};
```

Аннотации `GUARDED_BY`, `REQUIRES`, `EXCLUDES`, `PT_GUARDED_BY` превращают документацию в проверяемое свойство.

## 6. Специфика C-API

В C нет ни RAII, ни конструкторов, поэтому правила жёстче:

1. **Непрозрачный дескриптор**: `typedef struct db db_t;` — клиент не видит внутренностей, вы свободны менять синхронизацию.
2. **Никакого глобального изменяемого состояния.** Если очень нужно — `_Thread_local`/TLS.
3. **Никаких static-буферов** для возврата данных: либо буфер вызывающего (`char* out, size_t n`), либо out-параметр, либо владеющий объект.
4. **Ошибки** — код возврата; потокобезопасный «последний код ошибки» — только через TLS (`errno` в POSIX/C11 является thread-local). Глобальная `static char last_error[]` — запрещена.
5. **Явное владение и время жизни**: кто создаёт, кто уничтожает, можно ли вызывать `destroy`, пока другие потоки работают с объектом (обычно — нет, и это надо написать).
6. **Контракт по каждому символу** в заголовке:

```c
/* Потокобезопасно: можно вызывать из нескольких потоков одновременно. */
int  cache_get(cache_t *c, const char *key, char *out, size_t out_len);

/* Требует внешней синхронизации: вызывающий гарантирует отсутствие
 * одновременных вызовов с любыми другими операциями над c. */
void cache_clear(cache_t *c);

/* Не реентерабельно: не вызывать из колбэков, вызванных этим же API. */
void cache_foreach(cache_t *c, void (*fn)(const char *, void *), void *ud);
```

7. **Колбэки** — либо не вызывать под внутренней блокировкой, либо документировать это и давать `_unlocked`-варианты (как `*_unlocked` в glibc).
8. **Инициализация/деинициализация** — `pthread_once`/`call_once`, а teardown — только после остановки всех потоков.
9. **Реентерабельность** — отдельное требование (POSIX прямо перечисляет reentrant-функции); избегайте скрытого разделяемого состояния.

---

## 7. Производительность и масштабируемость

- **Конкуренция**, а не стоимость `lock/unlock`, определяет масштабируемость: неудерживаемый мьютекс почти бесплатен, удерживаемый под нагрузкой — катастрофичен (lock convoy).
- **Гранулярность**: крупные блокировки проще и безопаснее, мелкие — быстрее, но повышают риск deadlock и накладные расходы. Начинайте с крупных, оптимизируйте по измерениям.
- **Ложное разделение (false sharing)**: два независимых атомика в одной кэш-линии сериализуют работу. Лечится выравниванием:

```cpp
struct alignas(std::hardware_destructive_interference_size) PaddedCounter {
    std::atomic<long> value{0};
};
```

- **Не держите блокировку во время ввода-вывода, ожидания сети, `sleep`** — это превращает API в глобальную точку сериализации.
- **Не аллоцируйте под блокировкой без нужды** (аллокатор сам может быть точкой конкуренции).
- Для read-mostly данных предпочитайте snapshot/RCU, для write-heavy — шардирование, для передачи работы — очереди.

---

## 8. Проверка и сопровождение

- **Динамические анализаторы**: ThreadSanitizer (`-fsanitize=thread`), Valgrind Helgrind/DRD.
- **Стресс-тесты** с большим числом потоков и случайными задержками (инъекция задержек резко повышает вероятность поймать гонку).
- **Формальные методы** для lock-free: Relacy Race Detector, CDSChecker, GenMC.
- **Статический анализ**: Clang Thread Safety Analysis, PVS-Studio, Coverity.
- **Ревью контракта**: для каждого публичного метода — «под какой блокировкой он должен вызываться и что гарантирует».

## 9. Чек-лист проектирования многопоточного API

1. Определён и **записан** уровень потокобезопасности каждого класса/функции.
2. У класса есть **явный инвариант** и правило, какая блокировка его защищает.
3. Синхронизация **инкапсулирована**; клиент не обязан брать внешний мьютекс для обычных сценариев.
4. Предусмотрены **составные операции** (`get_or_insert`, `with_lock`), а не только «кирпичики».
5. Наружу не отдаются **ссылки/итераторы/указатели** на внутренние данные без владения.
6. Пользовательский код **не вызывается под блокировкой** (или это явно оговорено).
7. Все блокировки — **RAII**; множественные захваты — через `std::scoped_lock`/`std::lock`.
8. Задан **порядок блокировок**; `recursive_mutex` обоснован.
9. Ленивая инициализация — `call_once`/магический статик; глобального изменяемого состояния нет.
10. Продуманы **время жизни** (кто владеет, можно ли уничтожать под конкурентным доступом) и **порядок разрушения статиков**.
11. `const`-методы не создают скрытых гонок (`mutable`-кэши защищены).
12. Контракт **проверяется** аннотациями, TSan и стресс-тестами.

---

## 10. Резюме

Построение API для многопоточного использования — это прежде всего **проектирование контракта и владения**, а не расстановка мьютексов. Порядок действий:

1. **Сформулировать уровень потокобезопасности** и записать его (thread-safe / reentrant / thread-compatible / thread-hostile).
2. **Убрать разделяемое изменяемое состояние**: эксклюзивное владение → иммутабельные снимки → передача сообщений → и только затем блокировки.
3. **Сделать атомарные операции совпадающими с реальными сценариями клиента**, не заставляя его комбинировать «кирпичики» под внешней блокировкой.
4. **Инкапсулировать синхронизацию**, использовать RAII, избегать вызовов чужого кода под блокировкой и отдачи внутренних ссылок.
5. **Документировать, проверять и измерять**: аннотации, TSan, стресс-тесты, профилирование конкуренции.

Главный критерий качества — **клиент не должен думать о потоках, чтобы корректно пользоваться API в типичных сценариях**, и должен получать внятную ошибку проектирования (а не гонку), если пытается выйти за рамки контракта.
