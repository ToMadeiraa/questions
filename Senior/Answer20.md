# 20. Что такое барьеры памяти?

## Краткое определение

**Барьер памяти (memory barrier / memory fence)** — это средство, которое запрещает переупорядочивание операций доступа к памяти: как компилятору при оптимизации, так и процессору при внеочередном выполнении. Барьер не «сбрасывает кэш» и не «очищает память» — он задаёт **порядок видимости** операций чтения и записи для других потоков и других ядер.

В C++ барьеры встроены в модель памяти языка и выражаются через:

- аргумент `std::memory_order` у атомарных операций (`load`, `store`, `exchange`, `compare_exchange_*`, `fetch_*`);
- явные функции `std::atomic_thread_fence(...)` и `std::atomic_signal_fence(...)`;
- (в системном/низкоуровневом коде) встроенный ассемблер и архитектурные инструкции `MFENCE`, `LFENCE`, `SFENCE`, `DMB`, `DSB`, `ISB`.

## 1. Почему вообще возникает проблема: три уровня переупорядочивания

Программа в исходном виде и программа, реально исполняемая железом, — это разные последовательности операций. Переупорядочивание происходит на трёх независимых уровнях:

| Уровень | Что делает | Пример |
|---|---|---|
| **Компилятор (оптимизатор)** | меняет порядок независимых обращений, выбрасывает «лишние» чтения/записи, держит значения в регистрах | `x = 1; y = 2;` может стать `y = 2; x = 1;` |
| **Процессор (out-of-order execution)** | исполняет инструкции вне программного порядка, пока они не зависят по данным | чтение может выполниться раньше предшествующей записи в *другой* адрес |
| **Подсистема памяти (store buffer, инвалидация кэшей)** | запись попадает в буфер и становится видимой другим ядрам с задержкой; чтение может «проскочить» мимо ещё не применённой записи | StoreLoad-переупорядочивание на x86 |

Ключевой момент: **когерентность кэшей (MESI/MOESI) гарантирует единый порядок изменений одной ячейки, но не порядок между разными ячейками**. Именно межъядерный порядок и обеспечивают барьеры.

Классический пример — цикл «флаг готовности + данные»:

```cpp
// Поток-производитель
data = 42;        // (1) обычная запись
ready = true;     // (2) обычная запись

// Поток-потребитель
while (!ready) {} // (3) обычное чтение
use(data);        // (4) может увидеть старое значение!
```

Без барьеров допустимо, что (2) станет видимой раньше (1), и потребитель прочитает `data` до того, как запись в неё дошла. Формально это гонка данных (data race) и **UB**, но даже с «почти атомарными» `int` на практике такой код ломается.

## 2. Формальная основа: отношения «happens-before»

Модель памяти C++ (C++11 и новее) описывает корректность не через «порядок инструкций», а через отношения:

- **sequenced-before** — порядок вычислений внутри одного потока (внутри одного потока компилятор обязан сохранять наблюдаемое поведение, но межпоточные эффекты — нет);
- **synchronizes-with** — отношение между операцией записи в атомарный объект и операцией чтения, прочитавшей это значение (при нужных `memory_order`);
- **happens-before** = транзитивное замыкание sequenced-before и synchronizes-with;
- **visible sequence / modification order** — единый порядок изменений каждого атомарного объекта.

Если запись `A` happens-before чтения `B`, то `B` **обязано** увидеть `A` (или более позднее значение). Барьер — это механизм, который создаёт ребро synchronizes-with. Гонка данных (data race) — это два конфликтующих доступа, не упорядоченных отношением happens-before; в C++ это UB.

## 3. Уровни строгости: `std::memory_order`

| `memory_order` | Смысл | Типичная аппаратная цена |
|---|---|---|
| `relaxed` | только атомарность и единый порядок изменений; порядок с другими адресами не гарантируется | бесплатно (обычная загрузка/запись + атомарность) |
| `consume` | зависимость по данным (data dependency); в C++17 официально «не рекомендуется», GCC/Clang повышают до `acquire` | практически не используется |
| `acquire` | запрещает переупорядочивание **последующих** чтений/записей раньше данного чтения | на x86 бесплатно; на ARM — `DMB ISH` / `LDAR` |
| `release` | запрещает переупорядочивание **предшествующих** чтений/записей позже данной записи | на x86 бесплатно (`MOV` достаточно); на ARM — `DMB ISH` / `STLR` |
| `acq_rel` | и acquire, и release (для read-modify-write) | комбинация |
| `seq_cst` | последовательная согласованность: единый глобальный порядок всех seq_cst-операций + acquire/release-семантика | самая дорогая: на x86 store требует `MFENCE` или `XCHG`, на ARM — `DMB ISH` |

Правила‑«якоря», которые стоит помнить:

- **release-запись + acquire-чтение той же переменной** → всё, что было записано до release, видно после acquire. Это база для producer/consumer, флагов, `std::mutex` (lock = acquire, unlock = release).
- **relaxed годится только для счётчиков, статистики, «независимых» флагов**, где порядок с другими данными не важен.
- **seq_cst** — значение по умолчанию у `std::atomic`; даёт самую простую для рассуждения модель, но и самый дорогой код. Именно seq_cst делает корректными классические алгоритмы вроде Dekker/Peterson без дополнительных ухищрений.

Пример правильного producer/consumer:

```cpp
std::atomic<bool> ready{false};
int data = 0;

// producer
data = 42;
ready.store(true, std::memory_order_release);   // (1)

// consumer
while (!ready.load(std::memory_order_acquire)) {} // (2)
assert(data == 42);                               // гарантированно
```

Запись `data = 42` не может «уехать» за release-store, а чтение `data` не может «уехать» перед acquire-load. Это и есть барьер, выраженный в терминах языка, а не инструкций.

## 4. Явные барьеры: `atomic_thread_fence` и `atomic_signal_fence`

### `std::atomic_thread_fence(order)`

Барьер, не привязанный к конкретной переменной. Он работает в паре с атомарными операциями по правилам **fence-fence** и **fence-atomic** синхронизации:

- **release-fence → acquire-fence**: если поток A выполнил `atomic_thread_fence(release)` перед атомарной записью `X`, а поток B прочитал значение, записанное `X` (или записью из release sequence), и затем выполнил `atomic_thread_fence(acquire)`, то всё, что было до release-fence в A, видно после acquire-fence в B;
- **release-fence → acquire-операция** и **release-операция → acquire-fence** — аналогично.

```cpp
// producer
data = 42;
std::atomic_thread_fence(std::memory_order_release); // всё выше — до этой точки
flag.store(1, std::memory_order_relaxed);

// consumer
while (flag.load(std::memory_order_relaxed) == 0) {}
std::atomic_thread_fence(std::memory_order_acquire); // всё ниже — после
use(data);
```

Особый случай: `atomic_thread_fence(std::memory_order_seq_cst)` — единственный барьер, который на уровне языка даёт и **StoreLoad**-упорядочивание (то есть «полный» барьер). Его часто используют как «дешёвый seq_cst» для пары операций: два relaxed-доступа + seq_cst-fence между ними могут быть дешевле, чем два seq_cst-доступа.

### `std::atomic_signal_fence(order)`

**Чисто компиляторный** барьер: он запрещает переупорядочивание компилятором, но **не генерирует ни одной инструкции процессора**. Предназначен для синхронизации с обработчиком сигнала в том же потоке (и для борьбы с оптимизациями в bare-metal/драйверном коде). На практике компиляторы реализуют его как `asm volatile("" ::: "memory")`.

## 5. Компиляторный барьер и почему `volatile` — не барьер

Самый распространённый «ручной» барьер в системном коде:

```cpp
asm volatile("" ::: "memory");   // GCC/Clang: пустая инструкция + clobber "memory"
```

Он говорит оптимизатору: «здесь может произойти что угодно с памятью», поэтому компилятор не имеет права переносить через эту точку чтения/записи и не имеет права кэшировать значения в регистрах. Но **процессорной инструкции он не порождает** — на SMP этого недостаточно.

Важные уточнения:

- `volatile` в C++ **не является** средством синхронизации потоков: он не создаёт happens-before, не запрещает переупорядочивание с не-volatile доступами и не гарантирует атомарность. Его смысл — «не оптимизируй этот доступ» (MMIO, `sig_atomic_t`).
- `volatile std::atomic<T>` — антипаттерн, в C++20 такие операции объявлены устаревшими.
- В C++ правильный переносимый компиляторный барьер — `std::atomic_signal_fence(std::memory_order_seq_cst)`; правильный межпоточный — `std::atomic_thread_fence` или acquire/release-операции.

## 6. Аппаратные барьеры: что реально генерируется

### x86 / x86-64 (модель TSO — Total Store Order)

x86 даёт довольно сильные гарантии: чтения не переупорядочиваются с чтениями, записи с записями, записи не переупорядочиваются с более старыми чтениями. Единственное допустимое переупорядочивание — **StoreLoad** (запись может стать видимой позже, чем последующее чтение, из-за store buffer).

| Барьер | Инструкция | Назначение |
|---|---|---|
| LoadLoad / LoadStore | не нужны | гарантированы TSO |
| StoreStore | не нужен | гарантирован TSO |
| **StoreLoad** | `MFENCE`, либо `LOCK`-префикс, либо `XCHG` | полный барьер |
| `LFENCE` | сериализует загрузки (важно для Spectre-митигаций) | порядок чтений |
| `SFENCE` | порядок записей (нужен для non-temporal stores, `movnti`) | порядок записей |

Поэтому `memory_order_acquire`-загрузка на x86 — это обычный `MOV`, а `memory_order_seq_cst`-запись — `MOV` + `MFENCE` (или `XCHG`, если результат нужен). Компиляторы используют `XCHG` как более дешёвый по сравнению с `MFENCE` вариант на многих микроархитектурах.

### ARM / AArch64, POWER (слабая модель)

Слабая модель допускает почти любое переупорядочивание, поэтому барьеры реально стоят инструкций:

- `DMB ISH` — барьер упорядочивания данных для inner shareable domain (аналог `atomic_thread_fence(seq_cst)`/acq_rel);
- `DSB` — более сильный, ждёт завершения всех предшествующих операций (для MMIO, смены таблиц страниц);
- `ISB` — барьер синхронизации инструкций (после изменения кода/системных регистров);
- acquire/release реализуются через `LDAR`/`STLR` (одна инструкция вместо отдельного барьера);
- для зависимостей по данным — `LDAPR`/`RCpc` (аналог ослабленного `consume`).

Именно здесь наглядно видно, зачем нужны барьеры: на x86 многое «работает случайно», на ARM тот же код без acquire/release падает.

### Linux-ядро (для контекста)

В ядре есть собственный набор: `barrier()` (только компиляторный), `smp_mb()`, `smp_rmb()`, `smp_wmb()`, `smp_store_release()`, `smp_load_acquire()`, `READ_ONCE()`/`WRITE_ONCE()`. Это полезно знать, но в прикладном C++ используют `std::atomic`.

## 7. Где это критично: типовые паттерны

| Паттерн | Что нужно | Ошибка новичка |
|---|---|---|
| **Producer/consumer через флаг** | release-store флага / acquire-load флага | обычный `bool` или relaxed с обеих сторон |
| **Double-checked locking (синглтон)** | acquire при чтении указателя + release при публикации | проверка `if (ptr)` без атомарности и барьеров |
| **Spinlock** | `exchange(acquire)` в захвате, `store(release)` в освобождении | `while (flag) {}` + `flag = false` без атомиков |
| **Seqlock** | acquire-fence перед чтением данных, release-fence после записи | счётчик без барьеров — «рваное» чтение |
| **Dekker / Peterson** | seq_cst (или явные `atomic_thread_fence(seq_cst)`) | relaxed — алгоритм ломается на x86 |
| **Публикация структуры** | заполнить поля → release-store указателя | `delete`/`new` без release |

Пример DCLP (правильный вариант):

```cpp
std::atomic<Singleton*> instance{nullptr};
std::mutex m;

Singleton* get() {
    Singleton* p = instance.load(std::memory_order_acquire);
    if (!p) {
        std::lock_guard<std::mutex> lk(m);
        p = instance.load(std::memory_order_relaxed);
        if (!p) {
            p = new Singleton();
            instance.store(p, std::memory_order_release); // поля готовы до публикации
        }
    }
    return p;
}
```

## 8. Связь с препроцессором и компиляцией

Формально барьеры памяти — тема **модели памяти и кодогенерации**, а не препроцессора, но в контексте курса «препроцессор и компиляция C++» полезно зафиксировать:

1. **Препроцессор не создаёт барьеров.** `#define BARRIER` — это лишь текстовая подстановка; барьером становится то, во что макрос раскрывается.
2. **Препроцессор используется для выбора платформенной реализации** барьера:

```cpp
#if defined(__x86_64__) || defined(_M_X64)
  #define CPU_RELAX() _mm_pause()
  #define FULL_FENCE() _mm_mfence()
#elif defined(__aarch64__)
  #define CPU_RELAX() asm volatile("yield")
  #define FULL_FENCE() asm volatile("dmb ish" ::: "memory")
#else
  #define CPU_RELAX() ((void)0)
  #define FULL_FENCE() std::atomic_thread_fence(std::memory_order_seq_cst)
#endif
```

3. **Барьер — это договор с оптимизатором.** Компилятор обязан уважать `std::atomic` и встроенный `asm` с clobber-списком, но не обязан уважать «намерения» программиста, выраженные обычными переменными (даже `volatile`). Поэтому весь межпоточный обмен должен идти через `std::atomic` (или мьютексы/`condition_variable`, которые внутри уже содержат нужные acquire/release).
4. **Оптимизации и Undefined Behavior.** Если в коде есть data race, компилятор вправе предполагать, что его нет, и «ломать» наивные попытки самодельной синхронизации. Барьер, встроенный в атомик, — единственный переносимый способ сказать компилятору правду о параллелизме.

## 9. Практические правила

- **По умолчанию — `std::atomic` с `seq_cst`.** Переходите на `acquire`/`release`/`relaxed` только после того, как поняли, какое ребро happens-before вам нужно и чем вы готовы пожертвовать.
- **`relaxed` — только для независимых счётчиков**; любая публикация данных требует release/acquire.
- **Не используйте `volatile` для синхронизации** — это не барьер и не атомарность.
- **Пишите «happens-before-историю»**: что именно должно быть видно, какой поток что публикует и какой читает. Барьер — следствие, а не отправная точка.
- **Проверяйте на слабой модели.** Код, «работающий» на x86, может не работать на ARM: используйте TSan, `-fsanitize=thread`, тесты под AArch64/QEMU.
- **Помните про StoreLoad на x86** — единственное место, где голый x86-код без `MFENCE`/`XCHG` может удивить.
- **Не смешивайте модели**: C++-атомики и «сырые» барьеры ядра/asm в одном объекте — источник тонких ошибок; при смешивании нужен как минимум компиляторный барьер.

## 10. Резюме

**Барьер памяти** — это ограничение на переупорядочивание обращений к памяти, действующее на двух уровнях: *компиляторном* (запрет переносить/кэшировать доступы через точку барьера) и *аппаратном* (инструкции `MFENCE`/`DMB`/`LDAR`/`STLR`, обеспечивающие видимость в нужном порядке между ядрами). В современном C++ барьеры не пишут руками, а выражают через `std::atomic` и `std::memory_order`: `release`-запись публикует данные, `acquire`-чтение их принимает, `seq_cst` даёт единый глобальный порядок, `relaxed` — только атомарность. Явные формы — `std::atomic_thread_fence` (межпоточный барьер) и `std::atomic_signal_fence` (только компиляторный). Понимание барьеров — это понимание того, что «порядок строк в исходнике» и «порядок, который видят другие потоки», не одно и то же.
