# 44. Объясните принципы KISS.

## 1. Что такое KISS

**KISS** — *Keep It Simple, Stupid* («не усложняй, дурак») — принцип проектирования, требующий выбирать **наименьшую достаточную сложность** решения. Формулировка родилась в Lockheed Skunk Works: по легенде, Келли Джонсон требовал, чтобы конструкцию самолёта мог починить обычный механик в полевых условиях, имея только базовый инструмент. Отсюда суть принципа: **решение должно быть понятно и обслуживаемо средним специалистом в реальных условиях, а не только автором в момент написания.**

Существуют и «мягкие» расшифровки аббревиатуры, которые точнее передают смысл:

- *Keep It Short and Simple* — коротко и просто;
- *Keep It Simple and Straightforward* — просто и прямолинейно.

Ключевое слово — **Simple**, а не **Simplistic**. KISS — это не «писать примитивный код» и не «избегать абстракций». Это требование, чтобы **сложность кода соответствовала сложности задачи**, а не амбициям автора.

## 2. Два вида сложности: существенная и случайная

Полезнее всего объяснять KISS через различение, введённое Фредом Бруксом («No Silver Bullet», 1986):

| | **Essential complexity** (существенная) | **Accidental complexity** (случайная) |
|---|---|---|
| Источник | Сама предметная область: бизнес-правила, физика, протоколы, требования | Наш способ решения: архитектура, инструменты, лишние слои |
| Можно ли устранить | Нет (только переосмыслить требования) | Да, и это главная работа проектировщика |
| Пример | Налоговый расчёт с десятком ставок и льгот | Пять уровней наследования и фабрика фабрик вокруг этого расчёта |

KISS бьёт именно по **случайной** сложности. Он не требует «упростить налоговый код» — он требует не обвешивать его `AbstractSingletonProxyFactoryBean`.

Отсюда ёмкая формулировка: **«Простое решение — это решение, в котором нет ничего, что можно убрать без потери требуемой функциональности»** (перефразировка Сент-Экзюпери: совершенство достигается не тогда, когда нечего добавить, а когда нечего убрать).

## 3. Что KISS **не** означает (частые заблуждения)

1. **KISS ≠ отсутствие абстракций.** Иногда абстракция *упрощает*: `std::vector` проще и надёжнее, чем ручной `realloc`-код. RAII в C++ — это как раз пример упрощения (убирает ручной `delete` и связанные с ним баги), а не усложнения.
2. **KISS ≠ «код для джуниора».** Простота — свойство *модели*, а не уровня владения языком. Идиоматичный для C++ код (умные указатели, value-семантика) эксперту кажется простым, а «C-стиль в C++» — наоборот, сложным.
3. **KISS ≠ преждевременная оптимизация «в лоб».** Простое решение может быть медленным; тогда его оптимизируют, но **осознанно и по измерениям** (Knuth: «преждевременная оптимизация — корень всех зол»).
4. **KISS ≠ знакомое.** «Просто, потому что мы всегда так делаем» — не аргумент. Простота проверяется пониманием, а не привычкой.
5. **KISS ≠ одно решение на все случаи.** Универсальный «швейцарский нож» как раз нарушает KISS: он сложнее любого из частных случаев.

## 4. KISS в контексте OOP/OOD

В объектно-ориентированном проектировании KISS проявляется в нескольких конкретных правилах.

### 4.1. Минимальный интерфейс класса
Класс должен открывать ровно то, что нужно клиенту, и не более. Каждый публичный метод — это обязательство по поддержке, тестированию и совместимости.

```cpp
// Плохо: «на всякий случай» открыто всё
class Account {
public:
    double balance_;
    std::vector<Transaction> history_;
    void recalc();
    void dumpToFile(const std::string&);
    void dumpToJson(const std::string&);
    void dumpToXml(const std::string&);
    void setInternalFlag(int);
};

// Лучше: узкий интерфейс, инварианты под контролем
class Account {
public:
    double balance() const;
    void deposit(double amount);
    bool withdraw(double amount);
private:
    double balance_ = 0.0;
    std::vector<Transaction> history_;
};
```

Это же пересекается с **ISP** (Interface Segregation) и **SRP**: чем меньше класс умеет, тем меньше причин его менять и тем проще его понять.

### 4.2. Не вводить паттерн, пока он не окупается
Паттерны — это словарь для уже существующей сложности, а не лицензия на её создание. Правило: **каждый слой абстракции должен окупаться**. Если «Стратегия» реализует одну-единственную стратегию, это не стратегия, а лишний виртуальный вызов и лишний файл.

Классический антипаттерн — **speculative generality** (преждевременная обобщённость): параметризация «на будущее», интерфейсы «для расширения», конфигурируемость, которой никто не пользуется.

### 4.3. Композиция вместо наследования по умолчанию
Глубокая иерархия — это жёсткая связь и хрупкость (проблема базового класса). Плоское наследование на 2–3 уровня с виртуальным деструктором — обычно достаточно; всё, что глубже, требует веского обоснования.

### 4.4. YAGNI как «мышца» KISS
**YAGNI** (*You Aren't Gonna Need It*, из XP) — практический инструмент: не строить то, что не требуется *сейчас*. Абстракцию вводят, когда появился **третий** повтор (правило трёх), а не первый. Санди Метц: «дублирование намного дешевле неправильной абстракции» — потому что неправильную абстракцию потом дорого разбирать.

### 4.5. «Одна причина для изменения»
Чем больше ответственностей, тем сложнее модель. KISS на уровне архитектуры — это про **малое число связей**, а не про малое число классов.

## 5. KISS в C

C не имеет классов, поэтому здесь KISS — это прежде всего **дисциплина ручного управления ресурсами и данных**.

```c
/* Плохо: свой «ООП-фреймворк» на макросах ради одной структуры */
#define DECLARE_SHAPE(name) \
    typedef struct name##_s { \
        double (*area)(const struct name##_s *); \
        void (*dtor)(struct name##_s *); \
    } name

DECLARE_SHAPE(shape_t);
/* ... 200 строк макросов, vtable, фабрика ... */

/* Лучше: данные + свободные функции, пока нет второй реализации */
typedef struct { double r; } circle_t;
typedef struct { double w, h; } rect_t;

double circle_area(const circle_t *c) { return 3.14159265358979 * c->r * c->r; }
double rect_area(const rect_t *r)   { return r->w * r->h; }
```

Практические проявления KISS в C:

- **Плоские структуры данных** (Data-Oriented Design): массив `struct` вместо связного списка указателей, если не нужны вставки в середину.
- **`goto` для единой точки очистки** — это *упрощение*, а не «плохой стиль»: один путь освобождения ресурсов вместо копипасты.
- **Opaque pointer** (`struct Foo;`) для инкапсуляции — минимальная и дешёвая абстракция, не требующая vtable.
- **Функции вместо макросов**, где это возможно: макрос — это текловая подстановка без типов и отладки; `static inline` обычно проще в сопровождении.
- **Не изобретать «ООП на C»** без реальной потребности в полиморфизме: ручной vtable оправдан в драйверах и плагинных API, но не в прикладном коде на 500 строк.

## 6. KISS в C++

В C++ соблазн случайной сложности максимален: язык позволяет почти всё.

### 6.1. Пример: чрезмерная иерархия вместо данных

```cpp
// Плохо: иерархия, виртуальность и visitor ради «вычислить площадь»
struct IShape {
    virtual ~IShape() = default;
    virtual double area() const = 0;
    virtual void accept(IShapeVisitor&) const = 0;
};
struct Circle : IShape { double r; double area() const override; void accept(...) const override; };
struct Rect   : IShape { double w, h; double area() const override; void accept(...) const override; };
// + Visitor, + фабрика, + shared_ptr<IShape> в контейнере, + RTTI

// Лучше: замкнутый набор типов + std::variant
struct Circle { double r; };
struct Rect   { double w, h; };
using Shape   = std::variant<Circle, Rect>;

double area(const Circle& c) { return std::numbers::pi * c.r * c.r; }
double area(const Rect& r)   { return r.w * r.h; }

double area(const Shape& s) { return std::visit([](const auto& x) { return area(x); }, s); }
```

`std::variant` даёт **замкнутый** полиморфизм без кучи, без виртуальных вызовов и без `accept()`. Наследование стоит вводить, когда набор типов **открыт** (плагины, внешние расширения) — тогда виртуальность оправдана.

### 6.2. Типичные нарушения KISS в C++

| Антипаттерн | Чем плохо | Простое решение |
|---|---|---|
| Шаблонная метапрограммная «магия» (SFINAE-лестницы, рекурсивные `tuple`-хелперы) | Нечитаемо, чудовищные ошибки компиляции, медленная сборка | `if constexpr`, концепты, обычные перегрузки |
| Своя реализация `optional`/`variant`/`function` | Баги, несовместимость, лишний код | Стандартная библиотека |
| `shared_ptr` везде | Атомарный счётчик, циклы владения, неясное время жизни | Стек, значение, `unique_ptr`, ссылки |
| Глубокая множественная иерархия, ромбы | Хрупкость, неоднозначности | Композиция, интерфейсы с одним назначением |
| Singleton как глобальное состояние | Скрытые зависимости, проблемы с тестами | Передача зависимости явно |
| «Менеджеры», «хелперы», «процессоры» на каждый чих | Размытая ответственность, размазанная логика | Функции и маленькие классы по делу |
| Микрооптимизации без профилирования | Сложный код без выигрыша | Сначала измерить, потом усложнять |
| Свои аллокаторы/пулы «на всякий случай» | Сложность, баги, отсутствие выигрыша | `std::vector`, стандартный аллокатор |

### 6.3. Где C++ *упрощает* (KISS через идиомы)

Важно подчеркнуть: идиоматичный современный C++ — это часто **меньше** кода и **меньше** ошибок:

- **RAII** вместо ручных `new`/`delete` и `goto cleanup`;
- **value-семантика** и передача по `const&` вместо указателей;
- **`std::string`/`std::vector`/`std::span`** вместо сырых массивов и длин;
- **`enum class`** вместо `enum` и набора `#define`;
- **`constexpr`/`consteval`** вместо макросов;
- **`std::optional`** вместо «магических» `-1`/`nullptr`-сентинелов.

То есть KISS в C++ — это не «писать как в C», а **использовать язык по назначению**.

## 7. Как измерить простоту

KISS субъективен, но его нарушения неплохо ловятся метриками и код-смеллами.

**Метрики:**

- **Цикломатическая сложность Маккейба** (CC) — число независимых путей в функции; практический порог — около 10 на функцию.
- **Когнитивная сложность** (Cognitive Complexity, Sonar) — учитывает вложенность и «разрывы» потока управления; лучше отражает трудность чтения, чем CC.
- **Глубина вложенности** — больше 3–4 уровней почти всегда сигнал к раннему `return`/выделению функции.
- **Число параметров** — больше 4–5 обычно означает «нужен параметр-объект» или функцию делают слишком много.
- **Размер функции/файла**, число публичных методов класса, **LCOM** (недостаток связности).
- **Fan-out** (сколько типов функция трогает) — косвенно про связность.
- **Время сборки** — в C++ рост шаблонной сложности виден именно здесь.

**Код-смеллы, сигналящие о нарушении KISS:**

- God Object, «класс на 2000 строк»;
- Swiss Army Knife Interface (метод с флагом, меняющим поведение);
- Speculative Generality (абстракция без потребителей);
- Middle Man (класс, который только делегирует);
- Temporary Field, Long Parameter List, Message Chains;
- «Комментарий, объясняющий, что делает код» — часто признак того, что код можно было написать проще.

## 8. Границы применимости и критика KISS

KISS — не догма, и у него есть честные ограничения:

1. **«Просто» — контекстно.** Простое для эксперта в домене может быть непонятным новичку, и наоборот. Ориентир — **команда и сопровождение**, а не абстрактный минимум.
2. **Есть задачи, где сложность существенна.** Криптография, парсеры, конкурентность, real-time, распределённые протоколы: «простое» решение там может быть *некорректным*. Принцип требует не упрощать за счёт правильности.
3. **KISS конфликтует с DRY и с расширяемостью.** Преждевременное устранение дублирования рождает неверную абстракцию; преждевременная гибкость — лишние слои. Разумный компромисс: **сначала простое и дублирующее, обобщать по правилу трёх**.
4. **KISS ≠ единственный критерий.** Он сосуществует с SOLID, YAGNI, LoD, производительностью и требованиями безопасности; в конфликте решает контекст и цена ошибки.
5. **Риск «простоты на словах».** Иногда под KISS маскируют нежелание разбираться в задаче; отличие — в наличии **явных требований**, которые решение покрывает.

Хорошая рабочая формулировка: **«настолько просто, насколько возможно, но не проще»** (приписывается Эйнштейну, но по сути — инженерный здравый смысл).

## 9. Практический чек-лист

Применяя KISS на ревью или при проектировании, спросите:

- [ ] Какую задачу решает этот класс/функция? Формулируется ли она одним предложением?
- [ ] Есть ли у этой абстракции **второй** потребитель уже сейчас? Если нет — нужна ли она?
- [ ] Сколько слоёв между вызовом и реальной работой? Каждый ли слой что-то даёт?
- [ ] Можно ли заменить иерархию на `std::variant`/композицию/обычную функцию?
- [ ] Можно ли убрать параметр, флаг, шаблонный аргумент или `shared_ptr` без потери требований?
- [ ] Понятно ли это человеку, который не писал код и не знает замысла? (Проверка «механиком в поле».)
- [ ] Это сложность **задачи** или **решения**?
- [ ] Есть ли профилирование в пользу этого усложнения (если оно ради скорости)?
- [ ] Что придётся менять, если требование изменится? Если «всё» — вероятно, переусложнено или плохо разделено.

## 10. Связь с другими принципами

| Принцип | Отношение к KISS |
|---|---|
| **YAGNI** | Инструмент достижения KISS: не строить невостребованное |
| **DRY** | Союзник, но в конфликте: неверная абстракция хуже дублирования |
| **SRP** | Малые ответственности → меньше связей → проще модель |
| **ISP** | Узкие интерфейсы = меньше лишнего в контракте |
| **Композиция > наследование** | Плоские, явные связи вместо хрупких иерархий |
| **Бритва Оккама** | Философский аналог: не множить сущности сверх необходимости |
| **Rule of Least Power** | Выбирать минимально выразительный достаточный механизм |
| **«Zero-cost abstractions»** | Абстракция допустима, если не создаёт лишней сложности в рантайме — но KISS смотрит ещё и на сложность *чтения* |

## 11. Короткий итог

**KISS** — это принцип минимизации **случайной** сложности: решение должно содержать только то, что необходимо для выполнения требований, быть понятным среднему члену команды и дешёвым в изменении. В OOD он означает узкие интерфейсы, композицию вместо глубокого наследования, паттерны только по потребности и опору на YAGNI и правило трёх. В C — плоские данные, явное владение ресурсами, отказ от «ООП на макросах» без нужды. В C++ — идиомы и стандартная библиотека вместо самодельных конструкций, `std::variant` вместо лишней виртуальности, отсутствие шаблонной магии и микрооптимизаций без измерений.

Главная мысль для ответа на собеседовании: **KISS — не про примитивность кода, а про соответствие сложности кода сложности задачи; сложность должна окупаться, а всё неокупаемое — удаляться.**
