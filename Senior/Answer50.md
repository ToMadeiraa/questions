# 50. Когда std::vector может использовать std::move?

## Краткий ответ (TL;DR)

`std::vector` применяет перемещение в трёх разных смыслах, и их полезно не смешивать:

1. **Принять rvalue** — перегрузки `push_back(T&&)`, `insert(pos, T&&)`, `emplace_back(...)`; объект-аргумент не копируется, а перемещается/конструируется на месте.
2. **Переместить свои элементы** — при реаллокации (рост `capacity`), при сдвиге хвоста в `insert`/`erase`, в `reserve`/`resize`/`shrink_to_fit`. При **реаллокации** — только через `std::move_if_noexcept`: перемещение используется, если move-конструктор `noexcept` **или** копирование недоступно; иначе вектор **копирует** элементы ради сильной гарантии исключений.
3. **Переместиться самому** — move-конструктор и move-присваивание вектора «украдают» буфер (O(1)), а `swap` меняет указатели.

Главное правило, которое обычно и спрашивают: **при росте вектор перемещает элементы только тогда, когда move-конструктор помечен `noexcept` (или копировать нельзя)**.

---

## 1. Три уровня «move» для вектора

| Что перемещается | Где | Условие |
|---|---|---|
| Аргумент внутрь вектора | `push_back(T&&)`, `insert(pos, T&&)`, `emplace_back` | передана rvalue-ссылка / аргументы для конструирования на месте |
| Элементы внутри вектора | реаллокация, `insert` в середину, `erase` | `noexcept` move-ctor (при реаллокации) / `MoveAssignable` (при сдвиге) |
| Сам вектор как объект | move-ctor, move-assign, `swap`, `return v;` | всегда O(1) для ctor/swap; для assign — с оговоркой про аллокатор |

---

## 2. Приём rvalue: перегрузки на перемещение

С C++11 у вектора есть rvalue-перегрузки:

```cpp
std::vector<std::string> v;
std::string s = "long long long long long string";

v.push_back(s);              // копия (const T&)
v.push_back(std::move(s));   // перемещение (T&&); s — valid but unspecified
v.emplace_back(100, 'x');    // конструирование прямо в буфере, без промежуточного объекта
v.insert(v.begin(), std::move(s2)); // rvalue-перегрузка insert
```

`std::move` сам по себе ничего не перемещает — это лишь `static_cast<T&&>`, который выбирает rvalue-перегрузку. Реальное перемещение делает move-конструктор/присваивание типа.

Важно: `emplace_back` не «перемещает аргумент», он конструирует элемент на месте из аргументов. Перемещение существующих элементов при этом всё равно может произойти — если не хватило `capacity`.

---

## 3. Реаллокация: `std::move_if_noexcept` — сердце вопроса

Когда `size() == capacity()` и нужен ещё один элемент, вектор:

1. выделяет новый буфер (обычно в 2 раза больше, рост геометрический — амортизированно O(1));
2. **переносит** туда существующие элементы;
3. уничтожает старые и освобождает старую память.

На шаге 2 вектор обязан (в общем случае) дать **сильную гарантию**: если конструктор элемента бросит исключение, исходный вектор должен остаться нетронутым. Перемещение ломает это свойство — «откатить» перемещённый элемент нельзя. Поэтому используется `std::move_if_noexcept`:

```cpp
template<class T>
conditional_t<!is_nothrow_move_constructible_v<T> && is_copy_constructible_v<T>,
              const T&, T&&>
move_if_noexcept(T& x) noexcept;
```

Логика:

| Свойства `T` | Что делает `move_if_noexcept` | Что делает вектор |
|---|---|---|
| move-ctor `noexcept` | возвращает `T&&` | **перемещает** |
| move-ctor может бросить, copy-ctor есть | возвращает `const T&` | **копирует** (сильная гарантия) |
| move-ctor может бросить, copy-ctor удалён (`= delete`) | возвращает `T&&` | **перемещает** (иначе никак; гарантия ослабляется) |
| move-ctor нет, copy-ctor есть и `noexcept` | `is_nothrow_move_constructible_v<T>` = `true` (rvalue биндится к `const T&`), возвращает `T&&` | формально «move», фактически вызывается copy-ctor |

Упрощённая модель того, что делает реализация:

```cpp
// псевдокод реаллокации
T* buf = alloc.allocate(new_cap);
size_t i = 0;
try {
    for (; i < n; ++i)
        ::new (buf + i) T(std::move_if_noexcept(old[i])); // ← ключевая строка
} catch (...) {
    std::destroy(buf, buf + i);
    alloc.deallocate(buf, new_cap);
    throw;                       // старый буфер цел → сильная гарантия
}
std::destroy(old, old + n);
alloc.deallocate(old, cap);
```

То есть решение принимается **один раз для всего типа** и применяется ко всей пачке элементов одинаково.

### Пример: почему `noexcept` критичен

```cpp
struct Good {
    Good(const Good&)            { /* дорого */ }
    Good(Good&&) noexcept        { /* дёшево */ }   // vector БУДЕТ перемещать
    Good& operator=(const Good&);
    Good& operator=(Good&&) noexcept;
};

struct Bad {
    Bad(const Bad&)              { /* дорого */ }
    Bad(Bad&&)                   { /* дёшево, но без noexcept */ } // vector БУДЕТ копировать
    Bad& operator=(const Bad&);
    Bad& operator=(Bad&&);
};

static_assert( std::is_nothrow_move_constructible_v<Good>);
static_assert(!std::is_nothrow_move_constructible_v<Bad>);
```

`Bad` при росте вектора будет **молча копироваться**, хотя move-ctor у него есть и он быстрый. Компилятор предупредить не обязан — это одна из самых частых причин неожиданных O(n²) и лишних аллокаций.

### Move-only тип

```cpp
struct MoveOnly {
    MoveOnly() = default;
    MoveOnly(MoveOnly&&) noexcept = default;
    MoveOnly(const MoveOnly&) = delete;
};

std::vector<MoveOnly> v;
v.reserve(1);
v.emplace_back();
v.emplace_back();   // реаллокация: копировать нельзя → перемещает,
                    // даже если move-ctor был бы potentially throwing
```

Именно поэтому `std::vector<std::unique_ptr<T>>` работает: `is_copy_constructible_v` = `false`, ветка копирования отбрасывается.

## 4. Перемещение при сдвиге элементов: `insert` и `erase`

Здесь работает не `move_if_noexcept`, а обычное **move-присваивание** (и move-конструирование для последнего элемента).

### `erase` / `erase_if`

```cpp
std::vector<T> v = /* ... */;
v.erase(v.begin() + 1);   // все элементы после удалённого move-присваиваются влево
```

Требование стандарта: `T` должен быть **MoveAssignable**. Если move-присваивание не бросает — `erase` практически не может бросить; если бросает — гарантия базовая. Перемещения здесь неизбежны: копирования стандарт не требует и не гарантирует.

### `insert` в середину без реаллокации

Типичная реализация:

1. последний элемент **move-конструируется** на новое место (в свободный слот);
2. остальные **move-присваиваются** назад, освобождая место под вставляемый;
3. новый элемент конструируется из аргумента (copy/move).

Требуется `MoveInsertable` (для вставляемого значения — `CopyInsertable` или `MoveInsertable`) и `MoveAssignable` для хвоста. Гарантия: сильная, если исключение брошено не move-конструктором некопируемого `T`; иначе эффекты не определены.

### `insert` с реаллокацией

Сначала реаллокация по правилу `move_if_noexcept` (п. 3), затем сдвиг. То есть судьба старых элементов снова определяется `noexcept` move-конструктора.

## 5. Сводная таблица операций

| Операция | Перемещает элементы? | Когда / чем |
|---|---|---|
| `push_back` / `emplace_back` при `size() < capacity()` | нет (только конструирование нового) | — |
| `push_back` / `emplace_back` при `size() == capacity()` | **да** | `move_if_noexcept` |
| `reserve(n)`, `n > capacity()` | **да** | `move_if_noexcept` |
| `resize(n)` при росте с реаллокацией | **да** | `move_if_noexcept` |
| `resize(n)` при уменьшении | нет (только `destroy`) | — |
| `shrink_to_fit()` (если реаллокация произошла) | **да** | `move_if_noexcept` (запрос необязывающий) |
| `insert` в конец без реаллокации | move/copy-конструирование нового | перегрузка `T&&`/`const T&` |
| `insert` в середину без реаллокации | **да** | move-assign хвоста + move-construct последнего |
| `insert` с реаллокацией | **да** | `move_if_noexcept` + сдвиг |
| `erase`, `erase_if` | **да** | move-assign хвоста |
| `pop_back` | нет (только `destroy`) | — |
| `clear` | нет (только `destroy`) | — |
| `assign` | может | присваивание/конструирование в существующем буфере |
| `swap` | нет перемещения элементов | обмен указателями, O(1) |
| move-ctor / move-assign вектора | нет (кроме случая разных аллокаторов) | «кража» буфера |

## 6. Перемещение самого вектора

### Move-конструктор

```cpp
std::vector<T> a = /* ... */;
std::vector<T> b = std::move(a);  // O(1): b забирает буфер a
```

С C++17 объявлен как `vector(vector&&) noexcept` — безусловно. Это важно: `std::vector<std::vector<int>>` при росте **перемещает** внутренние векторы (их move-ctor noexcept), а не копирует их содержимое. Без этого вложенные векторы давали бы O(n·m) на реаллокацию.

После перемещения источник находится в состоянии «valid but unspecified» (на практике — пустой).

### Move-присваивание

```cpp
b = std::move(a);
```

- если `allocator_traits<A>::propagate_on_container_move_assignment::value == true` **или** `is_always_equal::value == true` — буфер «украдается», O(1);
- иначе (аллокаторы разные и не распространяются) — **поэлементное перемещение** в собственную память `b`, O(n): освобождать память `a` аллокатором `b` нельзя.

Спецификация `noexcept`:

```cpp
noexcept(allocator_traits<A>::propagate_on_container_move_assignment::value ||
         allocator_traits<A>::is_always_equal::value)
```

### `swap` и возврат из функции

```cpp
std::vector<T> make() {
    std::vector<T> v;
    // ...
    return v;              // NRVO, а если не сработал — неявный move
    // return std::move(v); // ПЛОХО: запрещает NRVO, лишний move
}
```

`swap` двух векторов — O(1), обмен указателей на буферы; `noexcept`, если аллокатор не запрещает обмен.

## 7. Требования к типу элемента

Класс `vector` в целом требует от `T` как минимум **Erasable** (корректный деструктор). Дальше — по операциям:

| Операция | Требование |
|---|---|
| `push_back(const T&)` | CopyInsertable |
| `push_back(T&&)`, `emplace_back` | MoveInsertable |
| реаллокация, `reserve`, `resize` (рост) | MoveInsertable (копирование — только если нужно для гарантии) |
| `insert` | MoveInsertable / CopyInsertable для значения; MoveAssignable для сдвига хвоста |
| `erase` | **MoveAssignable** |
| `resize(n)` без значения | DefaultInsertable |

Копируемость **не является** обязательным требованием: вектор прекрасно работает с move-only типами. Но если тип некопируемый, а move-ctor бросает — сильная гарантия при реаллокации теряется.

---

## 8. Гарантии исключений

Стандарт для модификаторов вектора (раздел `[vector.modifiers]`) формулирует это так (по смыслу):

- если исключение брошено **не** конструктором копирования/перемещения, оператором присваивания/перемещения `T` и не операцией итератора — **эффектов нет** (сильная гарантия);
- если исключение брошено при вставке одного элемента в конец и это **не** move-конструктор некопируемого `T` — **эффектов нет**;
- если исключение брошено **move-конструктором некопируемого `T`** — **эффекты не определены** (гарантия базовая/никакая).

Отсюда и весь дизайн с `move_if_noexcept`: он существует ровно для того, чтобы не платить сильной гарантией там, где можно безопасно перемещать.

---

## 9. Различия по версиям стандарта

| Стандарт | Что появилось |
|---|---|
| C++03 | move-семантики нет: при реаллокации всегда копирование; `vector<vector<T>>` — дорого |
| C++11 | rvalue-перегрузки, move-ctor/assign, `std::move_if_noexcept`; вектор стал nothrow-movable де-факто |
| C++14 | `std::move` (и ряд утилит) стал `constexpr` |
| C++17 | `vector(vector&&) noexcept` — **обязательный** `noexcept`; `is_always_equal`; `emplace_back` возвращает ссылку |
| C++20 | `constexpr`-вектор; `std::erase`/`std::erase_if` для контейнеров |
| C++23 | расширенные правила неявного move (P2266), в т.ч. для rvalue-ссылок и параметров |

## 10. Частые ловушки

1. **Move-ctor без `noexcept`.** Вектор копирует — и никакой диагностики. Лечится `noexcept` (и `noexcept` на move-присваивании, иначе `erase`/`insert` могут бросить).
2. **Пользовательский деструктор или copy-ctor «убивает» неявный move-ctor.** Если объявлен `~T()`, `T(const T&)` или `T& operator=(const T&)`, неявный move-конструктор **не генерируется**; rvalue начнёт биндиться к `const T&` — вектор будет копировать. Явно объявите `T(T&&) noexcept = default;`.
3. **`const` и перемещение.** `std::move(const_obj)` даёт `const T&&`, который не биндится к `T(T&&)` — вызывается copy-ctor. `std::vector<const T>` вообще некорректен (элемент должен быть Erasable/присваиваемым).
4. **Перемещение «из» вектора и повторное использование.** После `auto b = std::move(a);` вектор `a` валиден, но пуст (на практике); полагаться на его содержимое нельзя.
5. **Self-move.** `v = std::move(v);` — по LWG 2839 контейнер остаётся в валидном, но неопределённом состоянии; не делайте так.
6. **Перемещение элемента самого себя в `push_back`.** `v.push_back(std::move(v.back()))` — хрупкий угловой случай (ссылка внутрь буфера + возможная реаллокация). Лучше сначала вынести значение в локальную переменную.
7. **`std::vector<bool>`.** Это специализация с прокси-ссылками и упакованными битами: «перемещения элементов» в обычном смысле там нет, при реаллокации копируются машинные слова. Перемещение самого `vector<bool>` буфер всё равно крадёт.
8. **`std::move` — не алгоритм.** `std::move(v.begin(), v.end(), out)` (алгоритм из `<algorithm>`) перемещает элементы **наружу**, оставляя вектор с moved-from элементами. Это не то же самое, что `std::move(v)` (каст).
9. **Аллокатор с `propagate_on_container_move_assignment = false` и неравными аллокаторами.** Move-присваивание вектора становится O(n) поэлементным перемещением, а не O(1).
10. **Ожидание, что `reserve` «переместит».** Если `n <= capacity()`, `reserve` не делает ничего; элементы не двигаются. А `shrink_to_fit` — необязывающий запрос, он может не реаллоцировать.

---

## 11. Практические рекомендации

- Помечайте move-конструктор и move-присваивание `noexcept` — это главный рычаг, включающий перемещение в векторе.
- Не объявляйте деструктор/copy-операции без необходимости; если объявили — явно `= default` move-операции.
- `reserve()` перед массовым `push_back`/`emplace_back`, если размер известен: убирает реаллокации и перемещения вовсе.
- Предпочитайте `emplace_back` там, где объект можно сконструировать на месте, и `push_back(std::move(x))`, когда объект уже есть.
- Не пишите `return std::move(local);` — это отключает NRVO.
- Помните, что после перемещения объект-источник лишь валиден; не читайте из него «старое» значение.
- Для move-only типов вектор — нормальный контейнер; но если move-ctor может бросить, при реаллокации вы теряете сильную гарантию — либо делайте move `noexcept`, либо резервируйте заранее.

## Итог

`std::vector` использует `std::move`:

- **принимая rvalue** — через перегрузки `push_back(T&&)`, `insert(pos, T&&)`, `emplace_back`;
- **перемещая свои элементы при реаллокации** — только если move-конструктор `noexcept` или копирование недоступно (`std::move_if_noexcept`); иначе копирует ради сильной гарантии;
- **перемещая элементы при сдвиге** в `insert`/`erase` — через move-присваивание (нужен `MoveAssignable`);
- **перемещаясь сам** — move-конструктор и move-присваивание крадут буфер за O(1) (move-присваивание — при совместимых аллокаторах).

Ключевая фраза для интервью: **«vector перемещает элементы при реаллокации тогда и только тогда, когда move-конструктор помечен `noexcept` (или тип некопируемый), потому что иначе нельзя дать сильную гарантию исключений»**.
