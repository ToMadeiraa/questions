# 8. Что такое SFINAE? Для чего используется?

**Коротко:** SFINAE — это *Substitution Failure Is Not An Error* («неудачная подстановка не является ошибкой»). Это правило вывода аргументов шаблона в C++: если при подстановке выведенных аргументов в объявление шаблона функции получается некорректный тип или выражение, компилятор не обязан выдавать ошибку — он просто **исключает этого кандидата из набора перегрузок** и продолжает рассматривать остальные.

Именно на этом правиле построена бо́льшая часть техник «условной компиляции» в шаблонном C++: `std::enable_if`, трейты вида `has_member`, проверки валидности выражений и т. п.

## 1. Где и как работает правило

При вызове шаблонной функции компилятор проходит несколько этапов:

1. **Вывод** аргументов шаблона из фактических аргументов вызова.
2. **Подстановка** выведенных аргументов в объявление шаблона: в возвращаемый тип, типы параметров, объявления параметров шаблона, `noexcept`-спецификацию, `explicit`-спецификатор.
3. Если подстановка дала некорректный тип/выражение **в непосредственном контексте** — кандидат отбрасывается (это и есть SFINAE), а не считается ошибкой.
4. Среди оставшихся кандидатов выполняется обычное разрешение перегрузок.
5. Если не осталось ни одного кандидата — вот тогда возникает обычная ошибка «no matching function for call».

Ключевой момент: SFINAE — это не отдельный механизм и не «проверка чего-либо», а **побочный эффект правил вывода аргументов шаблона**. Он не срабатывает «по желанию»; он срабатывает там, где стандарт разрешает deduction failure.

Классический пример-иллюстрация самой идеи:

```cpp
template <typename T>
typename T::value_type first(const T& c) {   // (1)
    return *c.begin();
}

template <typename T>
T first(const T& c) {                        // (2)
    return c;
}
```

Если вызвать `first(std::vector<int>{})`, у `std::vector<int>` есть `value_type`, и кандидат (1) участвует в перегрузке. Если же подставить тип без `value_type` (например, `int*`), выражение `typename T::value_type` некорректно — но это не ошибка компиляции, а повод отбросить (1). Останется (2).

## 2. «Непосредственный контекст» (immediate context)

Это самое важное ограничение. Правило SFINAE действует **только** для ошибок в непосредственном контексте подстановки, то есть в самой сигнатуре шаблона:

- возвращаемый тип;
- типы параметров функции;
- объявления параметров шаблона и их аргументы по умолчанию;
- `noexcept`-спецификация;
- `explicit`-спецификатор (для конструкторов/операторов преобразования).

Ошибки **вне** этого контекста — жёсткие (hard error), даже если возникли «из-за» подстановки:

```cpp
template <typename T>
void print(const T& x) {
    typename T::value_type tmp = x; // ОШИБКА при инстанцировании, не SFINAE
}
```

```cpp
template <typename T>
struct Holder {
    typename T::value_type value; // ОШИБКА при инстанцировании, не SFINAE
};
```

```cpp
template <typename T>
void f(T x, typename T::type y = typename T::type{}); // аргумент по умолчанию
// ошибка в аргументе по умолчанию — тоже жёсткая, это не immediate context
```

Также жёсткой ошибкой будет ошибка, возникшая при инстанцировании чего-то «внутри» подстановки: например, если подстановка типа вызывает инстанцирование другого шаблона, и уже там происходит ошибка. Побочные эффекты подстановки (инстанцирования, генерация функций) в непосредственный контекст не входят.

Отдельно: для **шаблонов классов** правило в чистом виде не работает — некорректная подстановка в шаблон класса при инстанцировании является ошибкой. Похожее «мягкое» поведение есть только при подборе частичных специализаций (неудачный вывод означает, что специализация не подходит), и на этом строится, например, идиома `void_t`.

## 3. Типичные примеры использования

### 3.1. Обнаружение члена типа (detection idiom)

Проверим, есть ли у типа метод `foo()`:

```cpp
#include <type_traits>
#include <utility>

template <typename T>
auto has_foo_impl(int) -> decltype(std::declval<T>().foo(), std::true_type{});

template <typename T>
std::false_type has_foo_impl(...);

template <typename T>
using has_foo = decltype(has_foo_impl<T>(0));
```

Как это работает: при вызове `has_foo_impl<T>(0)` компилятор сначала пробует первую перегрузку. Если `T::foo()` не существует, выражение в `decltype` некорректно — подстановка в возвращаемый тип не удалась, кандидат отброшен. Остаётся вторая перегрузка с многоточием, которая подходит всегда. В результате `has_foo<T>` — это `std::true_type` или `std::false_type`.

Так же устроены `std::is_constructible`, `std::is_assignable`, `std::is_invocable` и множество библиотечных трейтов.

### 3.2. `std::enable_if` — включение и выключение перегрузок

`std::enable_if<Cond, T>` содержит вложенный `::type` только если `Cond == true`. Значит, при `Cond == false` подстановка в сигнатуру проваливается, и перегрузка исчезает:

```cpp
#include <type_traits>

template <typename T,
          typename std::enable_if<std::is_integral<T>::value, int>::type = 0>
const char* kind(T) { return "integral"; }

template <typename T,
          typename std::enable_if<std::is_floating_point<T>::value, int>::type = 0>
const char* kind(T) { return "floating point"; }
```

```cpp
kind(42);    // "integral"
kind(3.14);  // "floating point"
kind("abc"); // ошибка: оба кандидата отброшены -> no matching function
```

Ту же идею можно записать через возвращаемый тип:

```cpp
template <typename T>
typename std::enable_if<std::is_integral<T>::value, T>::type
twice(T x) { return x * 2; }
```

В C++14 появился короткий `std::enable_if_t<...>`, в C++17 — `std::void_t`.

### 3.3. Идиома `void_t` (C++17)

```cpp
template <typename T, typename = void>
struct has_foo : std::false_type {};

template <typename T>
struct has_foo<T, std::void_t<decltype(std::declval<T>().foo())>>
    : std::true_type {};
```

`std::void_t<...>` всегда равен `void`. Если выражение внутри него корректно, частичная специализация подходит (её второй аргумент — `void`, совпадает с умолчанием). Если нет — вывод для частичной специализации не удаётся, и используется основная версия, дающая `false_type`.

### 3.4. Expression SFINAE

Начиная с C++11, SFINAE работает и для некорректных **выражений**, а не только типов, — это называется expression SFINAE. Это позволяет проверять, например, поддерживает ли тип операцию `+`, есть ли у него `begin()`/`end()`, можно ли его сериализовать, и т. д.

```cpp
template <typename T>
auto add(const T& a, const T& b, int) -> decltype(a + b) {
    return a + b;
}

template <typename T>
T add(const T&, const T&, long) {
    return T{}; // запасной вариант
}

add(x, y, 0); // int лучше подходит, чем long
```

## 4. Для чего это используется

1. **Выбор перегрузки по свойствам типа.** Разные реализации для целых, вещественных, указателей, контейнеров и т. п.
2. **Трейты и интроспекция типов.** Проверка наличия членов, методов, операторов, возможности сконструировать/вызвать/присвоить.
3. **Отключение нежелательных перегрузок.** Самый частый бытовой случай — «идеальный» forwarding-конструктор `template<class U> X(U&&)`, который иначе перехватывает копирование/перемещение самого `X`; его ограничивают через `enable_if`.
4. **Условные возвращаемые типы.** Функция существует только для типов, для которых имеет смысл (например, `reserve()`, если он есть у контейнера).
5. **Оптимизация под возможности типа.** Выбор более эффективной реализации, если у типа есть нужный метод, и запасной — если нет.
6. **Построение библиотек.** На SFINAE держатся `std::enable_if`, `std::void_t`, `std::is_constructible`, `std::invoke_result`, механизмы `std::tuple`, `std::function`, аллокаторы, сериализация, reflection-подобные библиотеки и т. д.

## 5. Ограничения и подводные камни

- **Многословность.** Даже простая условная перегрузка превращается в несколько строк с `enable_if` и `declval`.
- **Плохие сообщения об ошибках.** Когда все кандидаты отброшены, компилятор выдаёт длинные «простыни» про невозможность подстановки, а не про суть проблемы.
- **Хрупкость.** Порядок перегрузок, случайные неявные преобразования и различия между компиляторами легко ломают задуманный выбор.
- **Только непосредственный контекст.** Ошибка в теле функции или в теле класса — это по-прежнему жёсткая ошибка; `static_assert` внутри функции тоже не спасает (он срабатывает при инстанцировании).
- **Не работает «напрямую» для шаблонов классов** — там некорректная подстановка является ошибкой (кроме подбора частичных специализаций).
- **Время компиляции.** Большие SFINAE-наборы перегрузок заметно замедляют сборку.
- **Тонкости с проверкой доступа.** В современном C++ проверка доступа выполняется в ходе подстановки, поэтому приватный член в `decltype` обычно приводит к отбрасыванию кандидата, а не к жёсткой ошибке; но полагаться на это в хрупких конструкциях не стоит.

## 6. Чем заменяют в современном C++

- **C++17, `if constexpr`** — не замена SFINAE для выбора перегрузок, но позволяет убрать часть трюков с «запасными» перегрузками внутри одной функции:

  ```cpp
  template <typename T>
  void process(T& x) {
      if constexpr (has_foo<T>::value) {
          x.foo();
      } else {
          // ...
      }
  }
  ```

- **C++20, концепты и `requires`** — прямой и читаемый механизм ограничений:

  ```cpp
  template <typename T>
  concept HasFoo = requires(T t) { t.foo(); };

  template <HasFoo T>
  void call(T& t) { t.foo(); }
  ```

  Это не «синтаксический сахар над SFINAE» один в один, но по назначению — замена: ограничения проверяются до подстановки, ошибки диагностируются гораздо лучше, а код короче.

- **Tag dispatch** (перегрузки с `std::true_type`/`std::false_type`) — старый и более читаемый, чем `enable_if`, способ выбрать реализацию, когда условие известно заранее.

| Подход | Появился | Плюсы | Минусы |
|---|---|---|---|
| SFINAE + `enable_if` | C++11 | гибко, работает для любых проверок | громоздко, плохие ошибки |
| Tag dispatch | C++98 | просто и читаемо | нужны отдельные перегрузки |
| `if constexpr` | C++17 | читаемо | не выбирает перегрузки, только ветвит |
| Concepts / `requires` | C++20 | кратко, отличная диагностика | требуется C++20 |

## 7. Итог

SFINAE — это правило, по которому неудачная подстановка аргументов шаблона в непосредственный контекст сигнатуры функции не является ошибкой, а лишь убирает кандидата из разрешения перегрузок. Используется оно для условного включения перегрузок, построения трейтов, проверки валидности выражений и «мягкой» адаптации к возможностям типа. Техника мощная, но многословная и хрупкая; в современном C++ её всё чаще заменяют `if constexpr` и концептами C++20, а SFINAE остаётся нужным прежде всего в библиотечном коде и в проектах, где C++20 недоступен.
