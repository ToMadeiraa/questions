# 13. Что такое cache miss и как это выявить?

## Короткое определение

**Cache miss (промах кэша)** — это ситуация, когда процессор обращается к данным или инструкции, которых нет в том уровне кэша, куда пришёл запрос. Тогда запрос спускается ниже — в следующий уровень кэша, а в худшем случае в оперативную память (DRAM), — и процессор ждёт сотни тактов вместо нескольких.

Формально: имеется иерархия `L1 → L2 → L3 → DRAM`. Обращение попадает в L1; если тег не совпал (данных нет или они вытеснены), это **L1 miss**, запрос уходит в L2, и т.д. Промах на последнем уровне (LLC, обычно L3) — это уже почти всегда поход в память.

## Почему это дорого: латентности

| Уровень | Типичная латентность | Объём (десктоп) |
|---|---|---|
| Регистры | 0–1 такт | — |
| L1d | ~4–5 тактов | 32–48 КБ на ядро |
| L2 | ~12–20 тактов | 0.5–2 МБ на ядро |
| L3 (LLC) | ~40–70 тактов | 8–32+ МБ, общий |
| DRAM | ~200–350 тактов | гигабайты |

Разница между попаданием в L1 и промахом в DRAM — два порядка. При 3 ГГц один промах в память — это ~100 нс, за которые ядро успело бы выполнить сотни инструкций. Именно поэтому «промахи кэша» — одна из главных причин, почему код с хорошей асимптотикой оказывается медленнее кода с плохой.

Ключевая деталь: кэш работает **не с отдельными байтами, а с линиями (cache line)**, обычно 64 байта. Промах по одному `int` подтягивает всю линию — и следующие 15 `int` из неё будут попаданиями. Отсюда всё значение пространственной локальности.

## Три классических типа промахов (модель 3C)

1. **Compulsory (холодные, обязательные)** — данных ещё ни разу не было в кэше. Неизбежны при первом обращении; лечатся только предзагрузкой (prefetch) или уменьшением объёма данных.
2. **Capacity (по объёму)** — рабочий набор больше кэша, и линии вытесняются из-за нехватки места. Лечится улучшением локальности, блочной обработкой (blocking/tiling), сжатием структур.
3. **Conflict (по конфликту)** — при недостаточной ассоциативности несколько «горячих» адресов претендуют на один и тот же набор (set) и выбивают друг друга, хотя места в кэше полно. Классика — обход матрицы с шагом, равным степени двойки (например, 4096 байт = 64 линии).

Дополнительно выделяют:

- **Coherence miss** — линия была вытеснена или инвалидирована из-за записи другим ядром (актуально для многопоточности и false sharing).
- **TLB miss** — промах не в кэш данных, а в буфер трансляции адресов; при больших рабочих наборах и случайном доступе по страницам это отдельная и очень дорогая проблема.

## Как это проявляется в C++ на практике

Типичные примеры, где промахи убивают производительность:

**1. Порядок обхода многомерного массива.** В C++ `int m[N][N]` хранится по строкам, поэтому обход по столбцам прыгает через `N * sizeof(int)` байт:

```cpp
constexpr int N = 4096;
static int m[N][N];

// Плохо: на каждом шаге внутреннего цикла — новый регион памяти
long long sum = 0;
for (int j = 0; j < N; ++j)
    for (int i = 0; i < N; ++i)
        sum += m[i][j];

// Хорошо: идём по памяти последовательно, линия используется целиком
long long sum2 = 0;
for (int i = 0; i < N; ++i)
    for (int j = 0; j < N; ++j)
        sum2 += m[i][j];
```

Разница на больших `N` — в разы, хотя число операций одинаково. Это, пожалуй, самый частый вопрос-иллюстрация.

**2. Связный список против `std::vector`.** Узлы `std::list`/`std::map` разбросаны по куче; каждый переход — потенциальный промах. `std::vector` даёт последовательный доступ и аппаратный префетчер, который угадывает следующие линии. Поэтому «теоретически O(1) вставка» у списка часто проигрывает вектору из-за константы.

**3. AoS против SoA.** Если в цикле нужны только `x` и `y`, а структура содержит ещё 200 байт «мусора», каждая линия тащит неиспользуемые поля. Разделение на `std::vector<float> xs, ys;` резко повышает плотность полезных данных в линии.

**4. False sharing.** Два потока пишут в разные переменные, попавшие в одну кэш-линию, — линия «пинг-понгует» между ядрами:

```cpp
struct Counters {
    std::atomic<long> a{0};
    std::atomic<long> b{0};   // та же линия, что и a!
};

// Лечится разнесением по линиям:
struct alignas(64) PaddedCounter {
    std::atomic<long> value{0};
};
```

В C++17 есть `std::hardware_destructive_interference_size` (обычно 64), но его значение на практике стоит проверять/задавать явно — оно зависит от платформы.

## Как выявить промахи

### 1. Аппаратные счётчики производительности (PMU) — основной способ

Современные CPU умеют считать события: `cache-references`, `cache-misses`, `L1-dcache-load-misses`, `LLC-load-misses`, `mem_load_retired.l3_miss` и т.д.

Linux, `perf`:

```bash
# Общая картина
perf stat -e cycles,instructions,cache-references,cache-misses,\
L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses ./app

# Где именно промахи: привязка к функциям/строкам
perf record -e cache-misses -g ./app
perf report

# Поиск false sharing (сравнение обращений к одной линии с разных ядер)
perf c2c record ./app
perf c2c report
```

Ключевые производные метрики:

- **Miss rate** = `misses / accesses` (для конкретного уровня).
- **MPKI** = misses per kilo-instruction — удобно сравнивать разные программы.
- **AMAT** (average memory access time) = `hit_time + miss_rate × miss_penalty` — теоретическая оценка среднего времени доступа.

Смотреть надо не на абсолютное число промахов (оно растёт с объёмом работы), а на **долю** и на **cycles per element / IPC**: если IPC низкий, а `stalled-cycles-backend` и LLC-miss высокие — вы упёрлись в память.

### 2. Профилировщики с поддержкой счётчиков

- **Intel VTune** (Memory Access / Cache Miss analysis) — показывает не только промахи, но и «горячие» структуры данных и адреса, а также готовую диагностику false sharing и NUMA.
- **AMD uProf** — аналог для AMD.
- **Windows**: WPA (Windows Performance Analyzer) + ETW, счётчики `Memory\Cache Misses/sec`, а также VTune.
- **PAPI** — кроссплатформенная библиотека, дающая программный доступ к счётчикам (`PAPI_L1_DCM`, `PAPI_L2_DCM`, `PAPI_L3_TCM`); удобна, когда нужны измерения внутри кода и на разных платформах.

### 3. Симуляторы кэша — когда счётчиков нет или нужна детерминированность

**Valgrind / Cachegrind** эмулирует иерархию кэшей и выдаёт точные попадания/промахи по строкам исходника:

```bash
valgrind --tool=cachegrind --cache-sim=yes ./app
cg_annotate cachegrind.out.<pid>
```

Плюсы: не нужен доступ к PMU, результат воспроизводим, видно вклад каждой строки. Минусы: модель идеализирована (не учитывает префетчинг и часть эффектов внеочередного исполнения), работает медленно (десятки раз), конфигурация кэша задаётся вручную (`--I1`, `--D1`, `--LL`) и может не совпадать с реальным железом. Поэтому Cachegrind хорош для **сравнения вариантов кода** между собой, а не для абсолютных чисел.

### 4. «Измерение в лоб» — эксперимент с размером рабочего набора

Самый доступный метод без всякого инструментария: построить график зависимости времени доступа от размера массива.

```cpp
#include <chrono>
#include <vector>
#include <cstdio>

int main() {
    for (std::size_t n = 1 << 10; n <= (1u << 26); n <<= 1) {
        std::vector<int> v(n, 1);
        // «случайный» обход с шагом, ломающим префетчер
        volatile long long sink = 0;
        auto t0 = std::chrono::steady_clock::now();
        for (int rep = 0; rep < 10; ++rep)
            for (std::size_t i = 0; i < n; i += 16)
                sink += v[i];
        auto t1 = std::chrono::steady_clock::now();
        double ns = std::chrono::duration<double, std::nano>(t1 - t0).count();
        std::printf("N=%8zu  %.2f ns/access\n", n, ns / (10.0 * n / 16));
    }
}
```

На графике «время на обращение — размер» будут видны **ступени (cliffs)** примерно на 32 КБ, 256 КБ–1 МБ и 8–32 МБ — это и есть границы L1/L2/L3. Рост времени на ступенях — прямое свидетельство промахов. Для точности лучше использовать `__rdtsc()` или `std::chrono::high_resolution_clock`, отключить шум (закрепление за ядром, `taskset`), прогреть данные и брать медиану.

### 5. Анализ кода и статическая оценка

Часто промахи видны без профилировщика — по структурам данных и паттернам доступа:

- есть ли обход «не по той» оси у многомерных массивов;
- используются ли связные списки/деревья там, где нужен массив;
- нет ли шага доступа, кратного степени двойки (конфликты в set'ах);
- нет ли структур с «раздутыми» полями, где нужен SoA;
- нет ли рядом лежащих изменяемых переменных из разных потоков (false sharing);
- нет ли случайного доступа по огромной таблице.

Компиляторы тут не помощники: `-O2/-O3` и `-march=native` влияют на префетчинг и векторизацию, но layout данных остаётся за вами. Полезны `__builtin_prefetch` для ручной предзагрузки и `std::assume_aligned`/`alignas` для выравнивания.

## Подводные камни при измерении

- Событие `cache-misses` в `perf` — это **не** все промахи: обычно это промахи LLC или «retired loads, missed», уточняйте по `perf list`.
- Аппаратный **префетчер** может скрывать промахи: доступ «выглядит» медленным по счётчикам, но время не растёт, и наоборот.
- Счётчики могут **мультиплексироваться** (событий больше, чем физических регистров) — цифры приблизительны; для стабильности запускайте несколько раз и смотрите разброс.
- **Шум ОС, гипертрединг, виртуализация, NUMA** искажают картину; закрепляйте поток (`taskset`, `numactl`), глушите турбо-режим, если нужна воспроизводимость.
- Микробенчмарк легко «сломать»: компилятор выбросит цикл, данные окажутся в кэше после прогрева, массив в 1 МБ влезет в L2 и промахов не будет вовсе. Проверяйте, что работа не оптимизирована (`volatile`/`DoNotOptimize`), и измеряйте именно то, что собирались.

## Итог: короткий чек-лист

1. **Понять**, что промах — это отсутствие линии в уровне кэша; цена — от ~10 до ~300 тактов в зависимости от глубины.
2. **Заподозрить** по симптому: низкий IPC, высокий `stalled-cycles-backend` / `backend_bound`, время растёт быстрее числа операций.
3. **Измерить**: `perf stat` (доля промахов, MPKI), `perf record` (где), `perf c2c` (false sharing), VTune/uProf/WPA для деталей.
4. **Если счётчиков нет** — Cachegrind для сравнительного анализа или эксперимент «время от размера рабочего набора».
5. **Исправить** через локальность: правильный порядок обхода, SoA вместо AoS, `std::vector` вместо узловых контейнеров, blocking/tiling, выравнивание и padding против false sharing, предзагрузка.

Главная мысль для собеседования: «cache miss» — это не просто «медленно», а конкретное событие в иерархии памяти, у него есть измеримые метрики (miss rate, MPKI, AMAT) и стандартный инструментарий (`perf`, VTune, Cachegrind, PAPI), а лечится оно почти всегда **изменением раскладки данных и порядка обхода**, а не микрооптимизациями арифметики.
