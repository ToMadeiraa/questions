# 38. Опишите назначение и принцип работы std::shared_ptr, std::unique_ptr и std::weak_ptr.

## Кратко

Все три типа — части библиотеки `<memory>` и реализуют идиому **RAII**: владение ресурсом привязывается к времени жизни объекта, а освобождение происходит в деструкторе. Различаются они моделью владения:

- **`std::unique_ptr`** — исключительное (единоличное) владение, zero-overhead замена «голому» указателю.
- **`std::shared_ptr`** — разделяемое владение с подсчётом ссылок; объект живёт, пока на него ссылается хотя бы один `shared_ptr`.
- **`std::weak_ptr`** — **не владеющая** ссылка на объект, которым управляет `shared_ptr`; позволяет наблюдать за объектом, не продлевая его жизнь, и разрывать циклические зависимости.

---

## 1. Зачем вообще нужны умные указатели

«Голый» указатель (`T*`) не выражает владение: по типу невозможно понять, кто обязан вызвать `delete`, когда и должен ли вообще. Отсюда — утечки, двойное освобождение, висячие указатели (use-after-free), особенно при исключениях:

```cpp
void bad() {
    Widget* p = new Widget;
    may_throw();      // если бросит исключение — delete не выполнится, утечка
    delete p;
}
```

Умные указатели решают это, делая владение частью типа и освобождая ресурс в деструкторе при любом выходе из области видимости — в том числе при раскрутке стека.

## 2. `std::unique_ptr`

### 2.1. Назначение

Выражает **ровно одного владельца** динамического объекта. Это тип по умолчанию для владения в современном C++: фабричные функции, элементы контейнеров, `pimpl`, ресурсы с ручным освобождением.

### 2.2. Принцип работы

`unique_ptr<T>` хранит сырой указатель и **deleter** (по умолчанию `std::default_delete<T>`, вызывающий `delete`). Ключевые свойства:

- **Только перемещение, без копирования.** Копирующий конструктор и копирующее присваивание удалены; владение передаётся через `std::move`. Именно это статически гарантирует единственность владельца.
- **Нулевые накладные расходы.** При пустом (stateless) deleter размер обычно равен размеру обычного указателя, а все операции инлайнятся — по производительности `unique_ptr` не уступает `T*`.
- **Deleter — часть типа.** `std::unique_ptr<T, D>`: разные deleter'ы дают разные типы. Если deleter имеет состояние (например, указатель на аллокатор), размер объекта увеличивается.
- **Деструктор вызывает deleter**, если указатель не `nullptr`.

Основные операции: `get()`, `release()` (отдать владение и обнулить), `reset()` (уничтожить текущий объект / заменить), `swap()`, `operator bool`, `operator*`, `operator->`.

### 2.3. Пример

```cpp
#include <memory>
#include <cstdio>

struct Widget {
    Widget()  { std::puts("Widget()"); }
    ~Widget() { std::puts("~Widget()"); }
    void use() const { std::puts("use"); }
};

void demo_unique() {
    auto p = std::make_unique<Widget>();  // C++14
    p->use();

    // auto q = p;             // ошибка компиляции: копирование запрещено
    auto q = std::move(p);     // передача владения
    if (!p) std::puts("p пуст");

    q.reset();                 // здесь вызовется ~Widget()
}                              // повторный delete не нужен
```

### 2.4. Нюансы

- **Массивы:** специализация `std::unique_ptr<T[]>` хранит `T*` и вызывает `delete[]`, поддерживает `operator[]`. Для неё есть `std::make_unique<T[]>(n)`; в C++20 добавлен `std::make_unique_for_overwrite`.
- **`make_unique` vs `new`:** `std::make_unique<T>(args...)` (C++14) безопасен по исключениям и не оставляет «голого» `new` в коде. В C++11 его не было — приходилось писать `std::unique_ptr<T>(new T(...))`.
- **Неполный тип:** `unique_ptr` можно объявлять с неполным типом (удобно для `pimpl`), но деструктор должен инстанцироваться там, где тип уже полон.
- **Полиморфизм:** `std::unique_ptr<Base> p = std::make_unique<Derived>();` корректно только при **виртуальном деструкторе** у `Base`, иначе через `delete Base*` не вызовется `~Derived`.

## 3. `std::shared_ptr`

### 3.1. Назначение

Выражает **разделяемое владение**: несколько `shared_ptr` могут указывать на один объект, и он уничтожается, когда уничтожится последний из них. Применяется, когда время жизни объекта определяется несколькими независимыми участниками (графы, кэши, асинхронные задачи, разделяемые структуры).

### 3.2. Устройство: объект + control block

Типичная реализация `shared_ptr<T>` хранит **два указателя**:

1. на сам объект `T`;
2. на **control block** (блок управления).

Control block содержит как минимум:

- **strong count** — число «сильных» ссылок (`shared_ptr`);
- **weak count** — число «слабых» ссылок (`weak_ptr`) плюс одна служебная;
- **deleter** и **allocator** (стираются по типу — type erasure);
- при необходимости — виртуальный механизм вызова deleter'а.

Счётчики атомарные, поэтому копирование/уничтожение разных экземпляров `shared_ptr`, владеющих одним объектом, безопасно из разных потоков.

### 3.3. Счётчики и порядок уничтожения

- Копирование `shared_ptr` → `strong++`.
- Уничтожение/`reset()` → `strong--`.
- Когда `strong == 0` — вызывается deleter, **объект уничтожается** (в потоке, который отпустил последнюю сильную ссылку).
- Control block освобождается, когда `strong == 0` **и** `weak == 0`: `weak_ptr` ещё могут проверять, жив ли объект.

```cpp
auto a = std::make_shared<Widget>();     // strong = 1
{
    auto b = a;                          // strong = 2
    std::cout << a.use_count() << '\n';  // 2
}                                        // strong = 1
// ...
                                         // strong = 0 -> ~Widget()
```

### 3.4. `make_shared` и стоимость

`std::make_shared<T>(args...)` (C++11) выделяет **одним** `new` и объект, и control block — одна аллокация вместо двух, лучше локальность, безопаснее по исключениям:

```cpp
// Плохо: две аллокации + потенциальная утечка,
// если второй аргумент бросит исключение между new T и конструктором shared_ptr
f(std::shared_ptr<T>(new T), may_throw());

// Хорошо: одна аллокация, исключение безопасно
f(std::make_shared<T>(), may_throw());
```

Обратная сторона `make_shared`: память общего блока не освобождается, пока живы `weak_ptr`, — даже после уничтожения объекта. Кроме того, `make_shared` не позволяет задать кастомный deleter.

Цена `shared_ptr` по сравнению с `unique_ptr`: два указателя вместо одного, атомарные операции со счётчиком при копировании, аллокация control block (если не `make_shared`) и косвенный вызов deleter'а.

### 3.5. Потокобезопасность

Важно понимать границы гарантий:

- **Control block потокобезопасен**: копирование, присваивание, `reset()` разных экземпляров `shared_ptr`, владеющих одним объектом, можно делать concurrently.
- **Сам объект — нет**: `shared_ptr` не делает `T` потокобезопасным. Если несколько потоков вызывают методы `*p`, нужна своя синхронизация.
- **Один и тот же экземпляр `shared_ptr`** нельзя одновременно читать и модифицировать без синхронизации.
- Начиная с C++20 есть `std::atomic<std::shared_ptr<T>>` для атомарной замены самого указателя.

### 3.6. Алиасинг и стирание типа

- **Aliasing constructor** позволяет владеть одним объектом, а указывать на его подобъект, разделяя control block:

```cpp
struct Pair { int a, b; };
auto p  = std::make_shared<Pair>();
std::shared_ptr<int> pa(p, &p->a);  // владеет Pair, указывает на p->a
```

- **`shared_ptr<void>`** может хранить указатель на объект любого типа — deleter «запоминается» в control block, поэтому приведение к `void` не ломает освобождение (type erasure).

## 4. `std::weak_ptr`

### 4.1. Назначение

`weak_ptr` — **наблюдатель без владения**. Он ссылается на объект, управляемый `shared_ptr`, но **не увеличивает strong count** и не продлевает жизнь объекта. Основные применения:

1. **Разрыв циклических зависимостей** (двунаправленные списки, деревья с указателем на родителя, графы).
2. **Кэши**, где запись не должна мешать сборке мусора.
3. **Паттерн «наблюдатель»**: подписчик не держит издателя живым.
4. **Безопасная проверка «жив ли ещё объект»** перед обращением.

### 4.2. Принцип работы

`weak_ptr` хранит указатель на **control block** того же объекта и увеличивает **weak count**. Типично он имеет тот же размер, что и `shared_ptr` (два указателя), но не даёт `operator*`/`operator->` — напрямую разыменовать его нельзя. Чтобы получить доступ, нужно «поднять» слабую ссылку до сильной:

```cpp
std::weak_ptr<Widget> w = some_shared_ptr;
if (auto sp = w.lock()) {   // атомарно: объект ещё жив?
    sp->use();              // sp — shared_ptr, жизнь продлена на время блока
} else {
    // объект уже уничтожен
}
```

Ключевые методы:

- **`lock()`** — атомарно проверяет strong count и возвращает `shared_ptr` (пустой, если объект уже уничтожен). Это правильный способ доступа.
- **`expired()`** — `true`, если объект уже уничтожен (`strong == 0`). В многопоточном коде между `expired()` и последующим обращением объект может исчезнуть, поэтому **проверять и разыменовывать нужно через `lock()`**, а не через `!expired()`.
- **`use_count()`** — приблизительное число сильных ссылок; в многопоточном коде не является надёжной синхронизацией.
- **`reset()`** — отвязаться от объекта.

### 4.3. Пример: циклическая зависимость

```cpp
struct Node {
    std::string name;
    std::shared_ptr<Node> next;   // сильная связь
    std::weak_ptr<Node>   prev;   // слабая связь — разрывает цикл
    explicit Node(std::string n) : name(std::move(n)) {}
    ~Node() { std::cout << "~Node " << name << '\n'; }
};

void list_demo() {
    auto a = std::make_shared<Node>("a");
    auto b = std::make_shared<Node>("b");
    a->next = b;
    b->prev = a;   // weak: цикла владения нет
}                  // оба узла корректно уничтожаются
```

Если бы `prev` был `shared_ptr<Node>`, получился бы цикл: `a` владеет `b`, `b` владеет `a`, strong count никогда не станет нулём — **утечка**. Именно `weak_ptr` делает ссылку «в обратную сторону» невладеющей.

### 4.4. Пример: кэш и наблюдатель

```cpp
class Cache {
    std::unordered_map<int, std::weak_ptr<Widget>> items_;
public:
    std::shared_ptr<Widget> get(int key) {
        if (auto sp = items_[key].lock())   // ещё жив — переиспользуем
            return sp;
        auto sp = std::make_shared<Widget>();
        items_[key] = sp;                   // храним слабую ссылку
        return sp;
    }
};
```

```cpp
void on_event(const std::weak_ptr<Widget>& w) {
    if (auto sp = w.lock()) {
        sp->use();          // объект жив
    } else {
        // издатель уже уничтожен — тихо игнорируем
    }
}
```

Для `shared_ptr`/`weak_ptr` в ассоциативных контейнерах (в качестве ключей) есть `std::owner_less` — сравнение по владению, а не по адресу объекта.

## 5. Сравнительная таблица

| Свойство | `unique_ptr` | `shared_ptr` | `weak_ptr` |
|---|---|---|---|
| Владение | исключительное | разделяемое | отсутствует |
| Копирование | запрещено (только move) | разрешено | разрешено |
| Размер (типично) | 1 указатель | 2 указателя | 2 указателя |
| Доп. память | нет | control block | нет (разделяет control block) |
| Счётчик ссылок | нет | atomic strong + weak | weak |
| Объект жив, пока | жив владелец | `strong > 0` | не влияет |
| Потокобезопасность | нет | control block | control block |
| Разыменование | да | да | только через `lock()` |
| Когда использовать | по умолчанию | несколько владельцев | наблюдение, циклы, кэш |

## 6. Типичные ошибки

1. **Два `shared_ptr` из одного сырого указателя** — два независимых control block, двойное удаление:
   ```cpp
   Widget* raw = new Widget;
   std::shared_ptr<Widget> a(raw);
   std::shared_ptr<Widget> b(raw);  // катастрофа: double delete
   ```
   Внутри класса, который уже управляется `shared_ptr`, для получения `shared_ptr` на себя используют `std::enable_shared_from_this`:
   ```cpp
   struct Session : std::enable_shared_from_this<Session> {
       void ping() {
           auto self = shared_from_this();  // продлевает жизнь на время операции
           // ...
       }
   };
   ```
   Вызывать `shared_from_this()` можно только после того, как объект уже стал owned by `shared_ptr`, иначе — `std::bad_weak_ptr`.

2. **Циклы из `shared_ptr`** — утечка; лечатся `weak_ptr` в одной из связей.

3. **`delete p.get()`** или `reset()` «чужого» указателя — нарушение контракта владения.

4. **`shared_ptr<T>(new T)` вместо `make_shared`** — лишняя аллокация и потенциальная утечка при исключении.

5. **`unique_ptr` с массивом без `T[]`** — вызовется `delete` вместо `delete[]` (UB). Нужен `std::unique_ptr<T[]>` / `make_unique<T[]>(n)`.

6. **`shared_ptr` на массив до C++17** — стандартный deleter вызывал `delete`; в C++17 появился `shared_ptr<T[]>`, в C++20 — `make_shared<T[]>`.

7. **Проверка `!w.expired()` и затем разыменование** — гонка; всегда `lock()`.

8. **`shared_ptr` там, где владение не нужно** — лишние атомики и аллокации; для наблюдения достаточно `T*`, `T&` или `std::weak_ptr`, если нужно отслеживать жизнь.

9. **Копирование `shared_ptr` по значению в горячем пути** — атомарные инкременты; часто лучше передавать `const shared_ptr<T>&`, если владение не забирается.

10. **Полиморфизм с `unique_ptr` без виртуального деструктора** в базовом классе — UB при удалении через базовый указатель.

## 7. Как выбирать

- **По умолчанию — `unique_ptr`**: он дешевле, яснее выражает владение и не требует атомарных операций. Если сомневаетесь, нужен ли `shared_ptr`, — скорее всего, не нужен.
- **`shared_ptr`** — когда владельцев действительно несколько и их время жизни не вложено друг в друга (разделяемые графы, асинхронные цепочки, кэши с продлением жизни).
- **`weak_ptr`** — для обратных/наблюдающих ссылок, разрыва циклов, кэшей и безопасной проверки «жив ли объект».
- **Невладеющее использование** — сырой указатель/ссылка (`T*`, `T&`), а не умный указатель: владение не должно передаваться туда, где оно не нужно.
- **Создание** — через `std::make_unique` / `std::make_shared`, а не через явный `new`.
- **Передача `unique_ptr`** — по значению (с `std::move`) для передачи владения, по ссылке или через `get()`/`T&` — для использования без передачи владения.

Итог: `unique_ptr` — единоличный владелец с нулевыми накладными расходами; `shared_ptr` — разделяемое владение через атомарный подсчёт ссылок и control block; `weak_ptr` — невладеющий наблюдатель, который видит объект, но не удерживает его живым и позволяет корректно разрывать циклы.
