# Вопрос 3. Код работает неправильно. Что делать?

> **Кратко:** Отладка — это управляемое сужение области поиска, а не перебор строк «на удачу». Сначала проблему нужно стабильно воспроизвести, затем локализовать (бинарный поиск по коду, логам и коммитам), сформулировать проверяемую гипотезу и подтвердить её экспериментом. И только потом — исправление, тест на регрессию и включённые предупреждения компилятора, чтобы та же ошибка не вернулась.

---

## 1. Сначала зафиксировать факт

Прежде чем что-то менять, нужно ответить на четыре вопроса:

| Вопрос | Зачем |
|---|---|
| Что должно было произойти? | Без ожидаемого поведения нет критерия «исправлено» |
| Что произошло фактически? | Точный текст ошибки, а не «не работает» |
| Воспроизводится ли стабильно? | Если нет — это отдельная (более сложная) задача |
| Когда заработало в последний раз? | Резко сужает область поиска |

Формулировка «код не работает» бесполезна: она не даёт ни одной зацепки. Рабочая формулировка — «на третьем вызове `parse("")` возвращает `42` вместо ошибки, но только при `-O2`».

---

## 2. Алгоритм действий

1. **Воспроизвести** — минимальными шагами, на том же входе, в том же режиме сборки.
2. **Сократить** — выкидывать код, пока ошибка не исчезнет; последний выкинутый кусок и есть виновник.
3. **Сформулировать гипотезу** — «падает, потому что индекс выходит за границу», а не «что-то с памятью».
4. **Проверить гипотезу** — экспериментом: точка останова, лог, ассерт, санитайзер.
5. **Исправить причину**, а не симптом.
6. **Защититься** — регрессионный тест, `assert`, предупреждения, статический анализ.

> **Правило:** если гипотеза не подтвердилась — это не провал, а информация. Провал — менять код, не имея гипотезы: тогда непонятно, что именно помогло.

---

## 3. Инструменты

| Инструмент | Что даёт | Когда особенно нужен |
|---|---|---|
| Отладчик (`gdb`, `lldb`, Visual Studio) | Остановка, стек вызовов, значения переменных, шаг с заходом | Логическая ошибка, падение, неверная ветка |
| Логи и `printf`-отладка | Хронология событий, значения на длинном прогоне | Многопоточность, «редкий» баг, встраиваемые системы |
| Санитайзеры (`-fsanitize=address,undefined,thread`) | Точное место UB, порчи памяти, гонки | Всё, что пахнет памятью или потоками |
| `valgrind` | Утечки, обращения к освобождённой памяти | Linux, нет санитайзеров |
| Предупреждения компилятора | Часть ошибок видна до запуска | Всегда |
| Статический анализ (`clang-tidy`, PVS-Studio) | Ошибки в редко исполняемых ветках | Большая кодовая база |
| `git bisect` | Коммит, который сломал поведение | Была рабочая версия, стало плохо |
| `std::source_location`, `assert` | Контекст сбоя в логе | Многословные проверки инвариантов |

---

## 4. Категории причин

| Категория | Как проявляется | Чем ловить |
|---|---|---|
| Логическая ошибка | Стабильно неверный результат, без падений | Тест, отладчик, чтение кода |
| Off-by-one, выход за границы | Падение «не в том месте», порча соседних данных | ASan, `at()` вместо `[]` |
| Неинициализированная память | Результат «плавает» между запусками | MSan (clang), `-Wuninitialized`, инициализация полей по умолчанию |
| Use-after-free | Падение при удалении или чтении | ASan |
| Утечка памяти | Растёт RSS, падение через часы | ASan, `valgrind`, `heaptrack` |
| Переполнение знакового, сдвиг, деление на 0 | При `-O2` ведёт себя иначе, чем при `-O0` | UBSan |
| Гонка данных | Нестабильно, зависит от нагрузки | TSan, `helgrind` |
| Различия окружения | Локально работает, на сервере нет | Логи версий, конфигов, локали |

## 5. Отладчик: минимум, который нужно знать

| Действие | gdb | lldb |
|---|---|---|
| Точка останова | `break file.cpp:42` | `breakpoint set -f file.cpp -l 42` |
| Запуск | `run` | `run` |
| Шаг с заходом в функцию | `step` | `step` |
| Шаг через строку | `next` | `next` |
| Стек вызовов | `bt` | `bt` |
| Значение переменной | `print x` | `frame variable x` |
| Наблюдение за переменной | `watch x` | `watchpoint set variable x` |
| До выхода из функции | `finish` | `finish` |

Сборка для отладки: `-g -O0` (но проверить поведение и на релизной сборке — UB часто «исчезает» именно при `-O0`).

---

## 6. Компилятор как первый союзник

Большинство ошибок дешевле предотвратить, чем искать:

```bash
g++ -std=c++20 -g -Wall -Wextra -Wpedantic -Wshadow -Wconversion \
    -Wsign-conversion -Wnull-dereference -Wdouble-promotion \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    main.cpp
```

`std::vector::at()` проверяет границы и бросает `std::out_of_range`, `operator[]` — нет. В отладочной сборке полезно гонять тесты с `_GLIBCXX_ASSERTIONS` или `_ITERATOR_DEBUG_LEVEL`, а контракты функций фиксировать через `assert` или префиксы вроде `Expects:` в документации.

## 7. Пример: ошибка «через раз»

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v(10, 0);
    for (int i = 0; i <= 10; ++i) {
        v[i] = i;              // off-by-one: v[10] — выход за границы (UB)
    }
    for (int x : v) std::cout << x << ' ';
}
```

Код может «работать»: запись попадёт в соседнюю память, и проявится это позже и в другом месте. Компилятор промолчит, а `-fsanitize=address` укажет точную строку:

```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
WRITE of size 4 at 0x... thread T0
    #0 0x... in main main.cpp:7
```

Это и есть правильная стратегия: не гадать, а получить машиночитаемое указание на причину.

## 8. Когда не воспроизводится

| Приём | Суть |
|---|---|
| Усилить логирование | Логировать вход, состояние и время, а не только ошибку |
| Запустить под нагрузкой | `-fsanitize=thread`, повторить 1000 раз, включить стресс-тест |
| Убрать недетерминизм | Зафиксировать seed, время, порядок обхода, размеры буферов |
| Воспроизвести окружение | Та же ОС, компилятор, версия библиотеки, те же данные |
| Собрать дамп и стек | `core dump` + `bt full`, `addr2line` по адресу |
| Проверить инварианты | `assert` в местах, где «не может быть» — часто именно там и ломается |

```cpp
// «Плавающий» баг часто начинается с недетерминированного источника данных
#include <random>
std::mt19937 rng(2024);          // фиксированный seed вместо std::random_device{}
```

## 9. `git bisect`: поиск сломавшего коммита

```bash
git bisect start
git bisect bad                 # текущая версия плохая
git bisect good v1.2.0         # здесь ещё работало
git bisect run ./run_test.sh    # автоматически найти первый плохой коммит
git bisect reset
```

Логарифмический поиск: 1000 коммитов проверяются за ~10 запусков теста. Главное — чтобы тест был детерминированным и быстрым.

---

## 10. Чего не делать

- **Менять код наугад.** «Поправил — заработало» без понимания причины означает, что ошибка вернётся.
- **Игнорировать предупреждения.** Проект с 300 предупреждениями уже не читает их; для нового кода уместен режим «предупреждения как ошибки» (`-Werror`).
- **Отлаживать в релизной сборке.** Переменные оптимизированы, поведение UB искажено; отлаживать нужно на `-O0 -g`, но обязательно проверять и на релизе.
- **Лечить симптом.** Проверка `if (p != nullptr)` там, где `p` не должен быть пустым, скрывает нарушенный инвариант.
- **Читать сообщение об ошибке по диагонали.** Последняя строка шаблонной ошибки обычно и есть суть; стек вызовов читается снизу вверх.
- **Не писать тест после исправления.** Без регрессионного теста фикс не закреплён.

## Типичные ошибки

1. **Отсутствие минимального воспроизводимого примера** — отладка на 40 тысячах строк вместо 20.
2. **Работа без гипотезы**: изменение кода в надежде, что «само пройдёт».
3. **Неверная интерпретация симптома**: падение в `std::string` не значит, что виноват `std::string`.
4. **Отключение предупреждений и санитайзеров** «чтобы не мешали» — именно они экономят часы.
5. **Сборка релиза с `-O2` при отладке** и удивление, что переменная «не существует».
6. **Игнорирование различий окружений** — локальная машина не равна серверу.
7. **Отсутствие `assert`** там, где инвариант очевиден для автора и неочевиден для кода.

## Что добавить на собеседовании

- Хороший ответ описывает **процесс**, а не список инструментов: воспроизвести → сузить → гипотеза → проверка → фикс → защита.
- Уместно упомянуть, что **большая часть времени уходит на локализацию**, а не на исправление: строка фикса часто одна.
- Ценно понимание, что **UB может не проявляться** — отсутствие падения не означает корректность.
- Плюс — опыт с конкретными инструментами: каким санитайзером ловили гонку, как искали утечку, как настраивали `core dump`.
- Здоровый подход — **не «кто виноват», а «какая информация нужна, чтобы сузить область»**: вопрос в терминах гипотез, а не в терминах авторов кода.

## Итог

| Этап | Ключевое действие | Результат |
|---|---|---|
| Воспроизведение | Минимальный вход, тот же режим сборки | Есть над чем работать |
| Локализация | Сокращение кода, `git bisect`, логи | Узкая область поиска |
| Гипотеза | Одна проверяемая причина | Понятно, что проверять |
| Проверка | Отладчик, санитайзер, ассерт | Причина подтверждена |
| Исправление | Правка причины, а не симптома | Ошибка устранена |
| Защита | Тест, предупреждения, статический анализ | Ошибка не вернётся |
