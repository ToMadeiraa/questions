# Вопрос 10. Патерны Singleton, Strategy, Template-Method, Decorator?

> **Кратко:** это четыре паттерна GoF с разными задачами. **Singleton** (порождающий) гарантирует единственный экземпляр класса. **Strategy** (поведенческий) делает алгоритм взаимозаменяемым объектом. **Template Method** (поведенческий) задаёт скелет алгоритма в базовом классе, оставляя шаги наследникам. **Decorator** (структурный) добавляет объекту обязанности через обёртку с тем же интерфейсом.

---

## 1. Singleton — единственный экземпляр

**Назначение:** гарантировать, что у класса существует ровно один экземпляр, и дать к нему глобальную точку доступа.

```cpp
#include <mutex>
#include <string>

class Logger {
public:
    static Logger& instance() {
        static Logger inst;                  // инициализация потокобезопасна с C++11
        return inst;
    }

    Logger(const Logger&) = delete;          // копирование и присваивание закрыты
    Logger& operator=(const Logger&) = delete;

    void log(const std::string& msg);        // данные всё равно защищаем сами

private:
    Logger() = default;
    std::mutex mutex_;
};
```

Это «Meyers singleton»: локальная статическая переменная создаётся при первом вызове, уничтожается при выходе из `main` в обратном порядке инициализации. Гарантия потокобезопасной инициализации статических локальных переменных появилась в C++11.

**Когда уместен:** действительно единственный ресурс процесса — логгер, реестр конфигурации, пул соединений. Часто лучше вообще обойтись без него: внедрение зависимости (объект передаётся в конструктор) тестируемо, явно и не создаёт глобального состояния.

**Недостатки:**

- скрытая зависимость: по сигнатуре функции не видно, что она обращается к глобальному состоянию;
- трудное тестирование: нельзя подменить реализацию без «взлома» через `#define private public`;
- проблемы порядка инициализации и уничтожения между несколькими синглтонами;
- потокобезопасно только создание; сами данные требуют отдельной синхронизации;
- нарушает единственную ответственность: класс и логика, и управление временем жизни.

## 2. Strategy — взаимозаменяемые алгоритмы

**Назначение:** выделить семейство алгоритмов, инкапсулировать каждый и сделать их взаимозаменяемыми; выбор — во время выполнения.

```cpp
#include <memory>
#include <utility>
#include <vector>

class Compression {                                   // интерфейс стратегии
public:
    virtual ~Compression() = default;
    virtual void compress(const std::vector<char>& data) const = 0;
};

struct Zip final : Compression {                     // конкретная стратегия
    void compress(const std::vector<char>& data) const override;
};

class Context {                                       // контекст делегирует работу
public:
    explicit Context(std::unique_ptr<Compression> c) : strategy_(std::move(c)) {}

    void setStrategy(std::unique_ptr<Compression> c) { strategy_ = std::move(c); }
    void run(const std::vector<char>& data) const {
        strategy_->compress(data);                    // виртуальный вызов
    }

private:
    std::unique_ptr<Compression> strategy_;
};
```

**Плюсы:** алгоритм меняется в рантайме, новый алгоритм не требует правки контекста, вместо `switch` — полиморфизм. **Минусы:** лишний объект и виртуальный вызов; клиент должен знать о стратегиях; при двух-трёх жёстко заданных вариантах это оверинжиниринг.

## 3. Template Method — скелет алгоритма

**Назначение:** определить скелет алгоритма в методе базового класса, а отдельные шаги отдать наследникам, не меняя структуру алгоритма.

```cpp
class DataMiner {
public:
    virtual ~DataMiner() = default;

    // Шаблонный метод: порядок шагов зафиксирован и не переопределяется.
    void mine() const {
        openSource();
        extractData();
        parseData();
        analyzeData();          // «крючок» — обязательный шаг наследника
        closeSource();
    }

protected:
    virtual void extractData() const = 0;
    virtual void parseData()   const = 0;
    virtual void analyzeData() const = 0;

    void openSource()  const { /* общий шаг */ }
    void closeSource() const { /* общий шаг */ }
};
```

**Ключевые свойства:**

- инверсия управления: не наследник вызывает базу, а база вызывает наследника («принцип Голливуда»), и общая часть алгоритма живёт в одном месте;
- **NVI-идиома** — развитие идеи: публичный невиртуальный метод вызывает приватные виртуальные, проверяя предусловия и инварианты.

**Минусы:** жёсткая связь через наследование, «хрупкий базовый класс»; поведение фиксируется на этапе компиляции, а не в рантайме.

---

## 4. Decorator — динамическое добавление обязанностей

**Назначение:** динамически добавлять объекту новые обязанности, не меняя его класс и не порождая комбинаторный взрыв наследников.

```cpp
#include <memory>
#include <string>
#include <utility>

class Stream {                                     // общий интерфейс
public:
    virtual ~Stream() = default;
    virtual void write(const std::string& data) = 0;
};

class FileStream final : public Stream {
public:
    void write(const std::string& data) override;   // запись в файл
};

class CompressedStream : public Stream {           // декоратор: тот же интерфейс
public:
    explicit CompressedStream(std::unique_ptr<Stream> inner) : inner_(std::move(inner)) {}
    void write(const std::string& data) override {
        inner_->write(data);                       // здесь могло бы быть сжатие
    }

private:
    std::unique_ptr<Stream> inner_;
};
```

Обёртки складываются: `CompressedStream(std::make_unique<FileStream>())` — поведение добавлено без нового класса; вторая обёртка добавит ещё одно. Именно так устроены потоки ввода-вывода в Java; в C++ похожую роль играют `std::streambuf` и манипуляторы.

**Отличие от соседей по каталогу:** Decorator добавляет поведение, Proxy с тем же интерфейсом контролирует доступ (ленивая загрузка, права), Adapter согласует **другой** интерфейс.

**Минусы:** много мелких классов, которые трудно отлаживать; порядок обёрток имеет значение; нужен виртуальный деструктор и ясное владение внутренним объектом.

## 5. Сравнение

| | Singleton | Strategy | Template Method | Decorator |
|---|---|---|---|---|
| Категория | порождающий | поведенческий | поведенческий | структурный |
| Идея | один экземпляр | алгоритм — объект | скелет в базе, шаги в наследниках | обёртка с тем же интерфейсом |
| Механизм | локальная `static` | композиция + делегирование | наследование + `virtual` | композиция + наследование интерфейса |
| Что расширяется | — | весь алгоритм | отдельные шаги | поведение до/после |
| Главный риск | глобальное состояние | лишняя косвенность | хрупкий базовый класс | разрастание обёрток |

Strategy и Template Method решают одну задачу — инкапсуляцию алгоритма — но разными средствами: Strategy предпочитает **композицию** и позволяет менять алгоритм в рантайме, Template Method использует **наследование** и фиксирует структуру на этапе компиляции.

---

## Типичные ошибки

1. **Синглтон как глобальная переменная** и ленивая инициализация без `std::atomic`/`std::call_once`: скрытые зависимости, нетестируемость, гонка данных.
2. **Strategy с сырым указателем**, когда неясно, кто владеет стратегией, — утечка или двойное удаление; и вообще паттерн там, где хватает лямбды или шаблонного параметра.
3. **Template Method, вызывающий виртуальный шаг из конструктора**: вызов уйдёт в базовую версию, наследник ещё не сконструирован.
4. **Decorator без виртуального деструктора** (удаление через указатель на базу — UB) и **срезка объекта** при передаче декоратора по значению.

---

## Что добавить на собеседовании

- Singleton критикуют именно за скрытые зависимости; современная практика — внедрение зависимости плюс один экземпляр, созданный в `main`.
- Strategy и Template Method — классическая пара для вопроса «чем отличаются композиция и наследование при переиспользовании алгоритма».
- Decorator — пример принципа открытости/закрытости, а современные замены паттернов — `std::function` вместо Strategy, `std::variant` + `std::visit` вместо Visitor, локальная `static` вместо ручного синглтона.

---

## Итог

| Паттерн | Одной фразой | Когда использовать |
|---|---|---|
| Singleton | единственный экземпляр и точка доступа | действительно уникальный ресурс процесса |
| Strategy | алгоритм как подменяемый объект | несколько вариантов, выбор в рантайме |
| Template Method | скелет алгоритма, шаги в наследниках | общий каркас, различающиеся детали |
| Decorator | обёртка добавляет поведение | комбинации обязанностей без взрыва наследников |
