# Вопрос 11. Для чего нужны модульные тесты?

> **Кратко:** Модульные (unit) тесты проверяют небольшие изолированные фрагменты кода — обычно одну функцию, класс или метод — без базы данных, сети и файловой системы. Они нужны, чтобы мгновенно узнавать о регрессии, локализовать дефект до конкретного модуля, зафиксировать требования в исполняемом виде и получить страховку для рефакторинга.

---

## Что считается «модулем»

Модуль — минимальная осмысленная единица поведения: функция, класс, метод. Тест обращается к ней через **публичный интерфейс** и проверяет наблюдаемый результат: возвращаемое значение, изменение состояния, выброшенное исключение.

Ключевое свойство — **изоляция**: все внешние зависимости (БД, HTTP, время, файлы, случайность) подменяются заглушками, поэтому тест не зависит от окружения и работает за микросекунды.

---

## Какие задачи решают модульные тесты

| Задача | Что это даёт на практике |
|---|---|
| Защита от регрессии | Изменение кода сразу показывает, что именно сломалось |
| Локализация дефекта | Падает конкретный тест конкретного класса, а не «приложение не работает» |
| Исполняемая спецификация | Тест документирует ожидаемое поведение точнее комментария и не устаревает |
| Безопасный рефакторинг | Можно менять реализацию, не меняя контракт |
| Давление на дизайн | Код, который трудно протестировать, обычно плохо развязан |
| Быстрая обратная связь | Секунды вместо минут ручной проверки сценария |
| Отладка | Тест воспроизводит баг в одну строку, вместо долгого клика по UI |

## Свойства хорошего модульного теста

Классический набор требований — **FIRST**:

| Буква | Свойство | Смысл |
|---|---|---|
| **F** | Fast | Миллисекунды; иначе тесты перестают запускать |
| **I** | Isolated | Не зависит от других тестов, порядка запуска и общего состояния |
| **R** | Repeatable | Одинаковый результат на любой машине и в любое время |
| **S** | Self-validating | Сам сообщает «прошёл/упал», без ручного разбора логов |
| **T** | Timely | Пишется вместе с кодом, а не «когда-нибудь потом» |

Структура теста обычно следует шаблону **AAA** — Arrange (подготовка), Act (действие), Assert (проверка). Один тест — одно проверяемое поведение; имя теста описывает сценарий и ожидание, а не имя метода.

---

## Что стоит и что не стоит покрывать

| Стоит покрывать | Не даёт пользы |
|---|---|
| Ветвления и граничные значения (`0`, `n-1`, пустой ввод) | Тривиальные геттеры и сеттеры без логики |
| Обработку ошибок и исключений | Приватные методы в отрыве от поведения |
| Инварианты класса (например, «баланс не отрицателен») | Сторонние библиотеки и стандартную библиотеку |
| Найденные баги — регрессионным тестом | Автогенерированный код, обёртки без логики |
| Публичные контракты и форматы данных | Детали реализации (последовательность внутренних вызовов) |

## Пример на GoogleTest

```cpp
#include <charconv>
#include <gtest/gtest.h>
#include <stdexcept>
#include <string>
#include <system_error>
#include <vector>

// Разбирает строку в номер порта: только цифры, 1..65535, иначе std::invalid_argument.
int parsePort(const std::string& s) {
    int value = 0;
    const auto [ptr, ec] = std::from_chars(s.data(), s.data() + s.size(), value);
    // from_chars не пропускает пробелы и не принимает знак '+'
    if (ec != std::errc{} || ptr != s.data() + s.size() || value < 1 || value > 65535)
        throw std::invalid_argument("bad port: " + s);
    return value;
}

// Arrange / Act / Assert в одном тесте
TEST(ParsePortTest, AcceptsValidPort) {
    EXPECT_EQ(parsePort("8080"), 8080);
}

// Проверяем именно исключение, а не «как-нибудь упало»
TEST(ParsePortTest, RejectsBoundaryBelowRange) {
    EXPECT_THROW(parsePort("0"), std::invalid_argument);
}

// Табличный тест: один код набора данных — много случаев
struct BadPort : testing::TestWithParam<std::string> {};

TEST_P(BadPort, Throws) {
    EXPECT_THROW(parsePort(GetParam()), std::invalid_argument);
}

INSTANTIATE_TEST_SUITE_P(InvalidPorts, BadPort,
    testing::ValuesIn(std::vector<std::string>{"", "-1", "0", "65536", "80a", " 80"}));
```

## Подмена зависимостей: виды test doubles

| Вид | Что делает | Когда использовать |
|---|---|---|
| **Dummy** | Заполнитель, который не используется | Нужен только для полноты параметров |
| **Stub** | Возвращает заранее заданные ответы | Нужен предсказуемый вход зависимости |
| **Spy** | Stub, записывающий вызовы | Проверить, что взаимодействие было |
| **Mock** | Проверяет ожидания по вызовам | Проверяем протокол общения с зависимостью |
| **Fake** | Упрощённая рабочая реализация (in-memory репозиторий) | Нужно поведение, а не запись вызовов |

Правило: подменяйте **внешние границы** (I/O, время, случайность, чужие сервисы), а не собственные классы проекта — иначе тест начнёт проверять моки вместо логики.

## Покрытие кода: что оно показывает

Покрытие (line/branch coverage) измеряет, **какой код был выполнен**, а не **какое поведение проверено**. Строка может выполниться, а `ASSERT` в ней — отсутствовать.

| Метрика | Что отражает |
|---|---|
| Line coverage | Доля выполненных строк |
| Branch coverage | Доля пройденных ветвей условий |
| Mutation coverage | Долю искусственно внесённых дефектов, которые тесты поймали (самая честная) |

Гонка за 100 % покрытия вредна: она стимулирует тесты без проверок. Ориентир — покрыт весь код с ветвлениями и обработкой ошибок, а не каждая строка формально.

## Стоимость и цена отсутствия

| Ситуация | Без тестов | С тестами |
|---|---|---|
| Правка в общем коде | Ручная проверка всех сценариев | Запуск набора за секунды |
| Поиск дефекта | Просмотр всего приложения | Падает конкретный тест |
| Рефакторинг | Страх что-то сломать | Свобода при неизменном контракте |
| Документация поведения | Устаревшая вики | Исполняемая спецификация |

Тесты — тоже код: они требуют поддержки. Нестабильный («flaky») тест хуже отсутствующего — ему перестают верить и отключают весь набор.

## Типичные ошибки

1. **Тесты зависят от порядка запуска** и общего состояния (статический счётчик, общий файл, БД между тестами).
2. **Проверка реализации, а не поведения**: тест ломается от любого рефакторинга, хотя контракт не менялся.
3. **Один тест — десять проверок** разных сценариев: при падении непонятно, что именно сломалось.
4. **Реальные время, сеть и случайность** без инъекции зависимости — недетерминированные тесты.
5. **Тестирование приватных методов** вместо публичного поведения: тест закрепляет внутреннее устройство.
6. **Отсутствие тестов на границы и ошибки** — проверен только «счастливый путь».
7. **Погоня за процентом покрытия** вместо проверки поведения.
8. **Тесты без `ASSERT`** — код выполнился, результат никто не проверил.

## Что добавить на собеседовании

- Тесты — это **инструмент дизайна**: если класс невозможно протестировать без обращения к сети, у него слишком много ответственности.
- На практике используют фреймворки: GoogleTest, Catch2, doctest, Boost.Test; в CI тесты гоняют на каждый push вместе со **sanitizer'ами** (ASan/UBSan) и статическим анализом.
- Полезно помнить, что тесты **не доказывают отсутствие ошибок** — они лишь повышают уверенность и фиксируют уже известные требования.
- Хороший ответ отличает **проверку поведения** от **проверки реализации**: «я проверяю результат работы функции, а не то, какие методы она вызвала внутри».

## Итог

| Вопрос | Ответ |
|---|---|
| Что проверяет | Поведение одного изолированного модуля через публичный интерфейс |
| Главная цель | Быстро обнаруживать регрессию и защищать рефакторинг |
| Побочные выгоды | Документация, локализация дефекта, давление на дизайн |
| Требования | Быстрые, независимые, воспроизводимые, самопроверяемые |
| Чего не заменяют | Интеграционных, end-to-end и нагрузочных тестов |
| Главный принцип | Проверяем поведение, а не реализацию |
