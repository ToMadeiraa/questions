# Вопрос 20. Расскажите об имплементации шаблонных классов в срр-файле?

> **Кратко:** шаблон — это не код, а «чертёж»: компилятор получает настоящий код только при инстанцировании, а значит ему нужна **полная реализация** в той единице трансляции, где шаблон используется. Поэтому реализацию обычно держат в заголовке (часто в отдельном `.tpp`), а если её всё же выносят в `.cpp`, то обязаны заранее перечислить нужные специализации явной инстанциацией (`template class Stack<int>;`) и погасить неявную инстанциацию в остальных единицах трансляции через `extern template`.

---

## Почему «просто положить реализацию в .cpp» не работает

Единица трансляции (translation unit, TU) — это один `.cpp` со всеми рекурсивно включёнными заголовками. Файлы компилируются **независимо**, и каждый `.cpp` должен получить готовый машинный код.

```cpp
// stack.hpp
#pragma once
#include <vector>

template <typename T>
class Stack {
public:
    void push(const T& value);       // только объявление
private:
    std::vector<T> data_;
};

// stack.cpp
#include "stack.hpp"
template <typename T>
void Stack<T>::push(const T& value) { data_.push_back(value); }   // определение здесь
```

```cpp
// main.cpp
#include "stack.hpp"
int main() { Stack<int> s; s.push(1); }
// $ g++ main.cpp stack.cpp -o app
// undefined reference to `void Stack<int>::push(int const&)`
```

Причина: в `stack.cpp` шаблон **не инстанцировался** (им там никто не пользуется), поэтому кода `Stack<int>::push` в объектном файле нет. В `main.cpp` компилятор видит только объявление — сгенерировать вызов он может, а тело — нет.

Вывод: шаблон нужно **либо определять там, где он используется**, либо явно инстанцировать там, где определение доступно.

---

## Вариант 1. Всё в заголовке (header-only)

Самый распространённый подход: определения сразу в `.hpp`. Функции-члены, определённые внутри класса, неявно `inline`, а шаблонные сущности стандарт разрешает определять в нескольких TU, поэтому ошибки «multiple definition» не возникает.

```cpp
#pragma once
#include <stdexcept>
#include <vector>

template <typename T>
class Stack {
public:
    void push(const T& value) { data_.push_back(value); }
    void pop() {
        if (data_.empty()) throw std::underflow_error("pop on empty Stack");
        data_.pop_back();
    }
    const T& top() const { return data_.back(); }
    bool empty() const noexcept { return data_.empty(); }

private:
    std::vector<T> data_;
};
```

Плюсы: работает всегда, ничего не надо настраивать, видна вся реализация. Минусы: время компиляции, раздувание заголовков, раскрытие деталей реализации, ошибки шаблонов «прилетают» в чужой файл.

## Вариант 2. Заголовок + файл реализации `.tpp`

Чтобы не держать сотни строк в `.hpp`, реализации выносят в отдельный файл, который **включается в конец заголовка** (расширения `.tpp`, `.ipp`, `.inl` — просто соглашение).

```cpp
// stack.hpp
#pragma once
#include <stdexcept>
#include <vector>

template <typename T>
class Stack {
public:
    void push(const T& value);
    void pop();
    const T& top() const;

private:
    std::vector<T> data_;
};

#include "stack.tpp"        // реализации подключаются в конце заголовка
```

```cpp
// stack.tpp — только определения, без include guard и без #include этого файла
template <typename T>
void Stack<T>::push(const T& value) { data_.push_back(value); }

template <typename T>
void Stack<T>::pop() {
    if (data_.empty()) throw std::underflow_error("pop on empty Stack");
    data_.pop_back();
}

template <typename T>
const T& Stack<T>::top() const {
    if (data_.empty()) throw std::underflow_error("top on empty Stack");
    return data_.back();
}
```

Файл `.tpp` **не добавляют** в список исходников сборки — он подключается только через `#include`.

## Вариант 3. Явная инстанциация: реализация действительно в `.cpp`

Если набор типов известен заранее, шаблон можно «заморозить» в обычные символы.

```cpp
// stack.cpp — единственное место, где видны определения
#include "stack.hpp"       // объявления (в этом варианте .tpp из заголовка НЕ включается)
#include "stack.tpp"       // определения, нужные для инстанциации

template class Stack<int>;         // явная инстанциация определения
template class Stack<double>;
```

```cpp
// stack.hpp — в конце файла, после определения класса
extern template class Stack<int>;      // C++11: «инстанциация будет в другом TU»
extern template class Stack<double>;
```

Варианты 2 и 3 несовместимы: если заголовок подключает `.tpp`, то `extern template` в нём бессмыслен — определения всё равно видны каждому клиенту.

Теперь в `main.cpp` компилятор генерирует только вызов, а тело приходит из `stack.o` при линковке.

| Свойство | Header-only | `.tpp` | Явная инстанциация |
|---|---|---|---|
| Работает для любых типов | да | да | **нет — только для перечисленных** |
| Реализация скрыта от клиента | нет | нет | да |
| Время компиляции | высокое | высокое | ниже |
| Риск `undefined reference` | нет | нет | **да**, если тип забыли |
| Дублирование кода в TU | есть (схлопывается линкером) | есть | устранено |

**Как это устроено на практике:**

- `extern template` — это **объявление** явной инстанциации: запрещает неявную инстанциацию в данном TU и не порождает код;
- `template class Stack<int>;` — **определение** явной инстанциации: порождает код для всех нешаблонных членов класса (включая те, что нигде не вызываются, — если член не компилируется для `int`, ошибка вылезет сразу);
- `extern template` должен стоять **после** определения класса-шаблона и до первого использования;
- в объявлении и определении инстанциации аргументы пишутся одинаково, иначе поведение не определено (ODR).

## Нюансы, о которых спрашивают

- **Вывод типа возвращаемого значения.** `auto f() { ... }` и `auto`-возврат из шаблона требуют видимого тела: клиент не сможет вывести тип по одному объявлению.
- **`constexpr`-функции и вычисления на этапе компиляции** тоже требуют определения в точке использования.
- **Специализации.** Полную специализацию класса можно держать в заголовке целиком (это обычное определение класса); её функции-члены, определённые **вне** класса в заголовке, нужно помечать `inline`. Полную специализацию функции можно объявить в заголовке и определить в `.cpp`. **Частичную** специализацию вынести в `.cpp` нельзя — она должна быть видна там, где выбирается.
- **Динамические библиотеки.** На Windows экспорт явной инстанциации делают через `template class __declspec(dllexport) Stack<int>;`; MSVC при этом предупреждает `C4251` про члены-данные, экспортируемые из DLL.
- **Раздувание кода.** Линкер схлопывает одинаковые инстанциации (COMDAT / weak-символы), поэтому `extern template` экономит прежде всего **время компиляции**, а не размер бинарника.
- **C++20 modules.** `export template` в модуле — штатное решение проблемы: определение шаблона компилируется один раз и импортируется, а не пересканируется в каждом TU.

---

## Типичные ошибки

1. **Реализация в `.cpp` без явной инстанциации** — `undefined reference` при использовании из другого TU. Сообщение линкера выглядит как «метод существует, но его нет», что сбивает с толку.
2. **`#include "stack.cpp"` в конце заголовка.** Иногда «работает», но ломает раздельную компиляцию: если `.cpp` попадёт ещё и в список исходников, получите дубли определений и странные ошибки.
3. **`extern template` без явной инстанциации** — та же ошибка линковки, но уже «по вине» `extern`.
4. **Забыли явную инстанциацию для нового типа.** Шаблон перестал быть универсальным, а ошибка возникает только на сборке у клиента.
5. **Специализация объявлена после места использования** — формально ill-formed без обязательной диагностики.
6. **Функция-специализация в заголовке без `inline`** — множественные определения при линковке.
7. **`static` у шаблонной функции в заголовке** — своя копия в каждом TU, «невидимая» для остальных.

---

## Что добавить на собеседовании

- Двухфазный поиск (two-phase lookup): часть ошибок шаблона видна сразу при разборе, часть — только при инстанцировании, поэтому «ошибка в чужом заголовке» появляется именно в вашем TU.
- Практическое правило: **шаблон — это интерфейс с открытой реализацией**; если реализацию нужно спрятать, меняют дизайн — type erasure (`std::function`, pimpl, виртуальный интерфейс), а не «выносят шаблон в cpp».
- `extern template` — стандартный способ ускорить сборку больших проектов с тяжёлыми шаблонными библиотеками; его же использует стандартная библиотека.
- Стоит упомянуть, что `template class X<int>;` инстанцирует **все** члены и потому может «поймать» ошибки в редко используемых методах.

## Итог

| Подход | Где реализация | Когда использовать |
|---|---|---|
| Header-only | в `.hpp` | библиотеки для произвольных типов (основной случай) |
| `.hpp` + `.tpp` | в `.tpp`, включённом из заголовка | большие шаблоны, желание разделить объявление и реализацию |
| Явная инстанциация | в `.cpp`, клиенты видят `extern template` | закрытый набор типов, ускорение сборки, сокрытие кода |
| Модули (C++20) | в интерфейсе модуля | современная замена `#include`-подходу |
| Не работает | в `.cpp` без инстанциации | `undefined reference` при линковке |
