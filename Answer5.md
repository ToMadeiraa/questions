# Вопрос 5. Какие книги, связанные с программированием, читали? Чему с них научились?

> **Кратко:** Вопрос мягкий по форме, но проверяет главное — учитесь ли вы системно и умеете ли превращать прочитанное в решения. Правильный ответ — не список из пятнадцати названий, а три-четыре книги с конкретным выводом по каждой и примером, как этот вывод изменил ваш код. Ценится честность: «читал выборочно», «эту главу не осилил», «вот что взял в работу».

---

## 1. Что на самом деле проверяет вопрос

| Что оценивают | Хороший сигнал | Плохой сигнал |
|---|---|---|
| Системность обучения | Есть порядок: база → практика → углубление | Случайный набор бестселлеров |
| Способность извлекать смысл | «После этой главы перестал делать X» | Пересказ оглавления |
| Применение в коде | Конкретный пример до/после | «Стало лучше понимать C++» |
| Честность | «Прочитал 4 главы из 12» | «Прочитал Страуструпа целиком за месяц» |
| Актуальность | Книги по C++11/17/20, а не только по C++98 | Только «книги для начинающих» |

> Собеседующий почти наверняка попросит: «Расскажи подробнее». Поэтому книг должно быть столько, сколько вы реально помните.

---

## 2. Структура ответа

Один и тот же шаблон работает для каждой книги:

1. **Название и автор** — без пафоса.
2. **Зачем взял** — какая задача была в тот момент.
3. **Одна-две идеи**, которые запомнились.
4. **Что изменилось в коде** — самое важное.
5. **Оценка** — что устарело или с чем не согласен.

## 3. Книги по C++

| Книга | Уровень | Что даёт |
|---|---|---|
| «C++ Primer», С. Липпман, Ж. Лажойе, Б. Му | База | Системное изложение языка и STL, порядок «от ссылок к шаблонам» |
| «Effective C++» и «Effective STL», С. Мейерс | База+ | Правила-эвристики: копирование, исключения, алгоритмы вместо циклов |
| «Effective Modern C++», С. Мейерс | Средний | Вывод типов `auto`, move-семантика, `unique_ptr`/`shared_ptr`, ловушки лямбд |
| «A Tour of C++», Б. Страуструп | Обзор | Компактный срез современного языка, удобно для повторения |
| «The C++ Programming Language», Б. Страуструп | Справочник | RAII, исключения, дизайн библиотек; читать выборочно, не подряд |
| «C++ Concurrency in Action», Э. Уильямс | Продвинутый | Модель памяти, `atomic`, мьютексы, lock-free структуры |
| «C++ Templates: The Complete Guide», Д. Вандевурд | Продвинутый | Шаблоны, специализация, SFINAE, перегрузка |

**Что обычно выносят из них:** «правило нуля» вместо ручного `delete`, `unique_ptr` по умолчанию, алгоритмы STL вместо самописных циклов, понимание, что `auto` — это не «любой тип», а вполне конкретный вывод по правилам.

## 6. Три вывода, которые реально меняют код

### 6.1 RAII и «правило нуля» (Страуструп, Мейерс)

```cpp
#include <memory>

// Как писал раньше: ресурс освобождается вручную
void processBefore() {
    Buffer* b = new Buffer(1024);
    doWork(b);                 // если бросит исключение — утечка
    delete b;
}

// Как пишу теперь: владение выражено типом
void processNow() {
    auto b = std::make_unique<Buffer>(1024);
    doWork(*b);                // освобождение на любом выходе, включая исключение
}
```

Вывод: «если ресурс не выражен типом, его освобождение рано или поздно забудут».

### 6.2 `auto` и невидимые копии (Мейерс, «Effective Modern C++»)

```cpp
std::vector<std::string> names = loadNames();

for (auto s : names)        // копия каждой строки — лишние аллокации
    use(s);

for (const auto& s : names) // без копирования
    use(s);
```

Вывод: `auto` выводит тип по тем же правилам, что и шаблон, — и иногда это `std::string`, а не `std::string&`.

### 6.3 Локальность важнее «теоретической» сложности (CSAPP)

```cpp
#include <list>
#include <numeric>
#include <vector>

std::vector<int> v = makeVector();   // элементы лежат подряд
std::list<int>   l(v.begin(), v.end());

long long a = std::accumulate(v.begin(), v.end(), 0LL);  // быстрее
long long b = std::accumulate(l.begin(), l.end(), 0LL);  // узлы разбросаны
```

Вывод: у обоих контейнеров обход `O(n)`, но последовательный доступ к памяти и префетчер дают `vector` кратную фору.

## 7. Как читать техническую книгу, чтобы был результат

| Приём | Зачем |
|---|---|
| Начать с оглавления и выбрать 20% нужного | Книга — не роман, линейное чтение редко оправдано |
| Воспроизводить примеры и ломать их | Понимание появляется при попытке сломать, а не прочитать |
| Один вывод — одна заметка или коммит | Иначе через месяц останется «читал, было интересно» |
| Пересказать главу вслух или в конспекте на страницу | Проверка, что понял, а не узнал |
| Возвращаться как к справочнику | `Effective C++` и `Effective STL` — именно формат справочника |

## 8. Если книги пока не читал

Врать нельзя: следующий вопрос будет «а что там в главе про...». Рабочие варианты:

- «Целиком — нет, читал главы про X и Y, вот что взял».
- «Сейчас в процессе: X, прочитал половину, пока главное — Z».
- «Основной источник — cppreference и доклады CppCon, книги использую точечно».
- «Формально не книга, но курс X дал Y, а статью Z разбирал на практике».

Честный ответ вида «читаю `Effective Modern C++`, пока разобрался с выводом типов и `unique_ptr`, до lock-free ещё не дошёл» звучит сильнее, чем список из десяти названий без содержания.

## Типичные ошибки

1. **Перечислять 15 книг**, из которых помнишь две, — первый же уточняющий вопрос всё вскрывает.
2. **Пересказывать содержание** вместо вывода: «там про SOLID» ничего не говорит о вас.
3. **Называть только «Чистый код»** и не иметь ни одного примера применения.
4. **Утверждать, что прочитал книгу целиком**, когда читал выборочно, — риск провалиться на деталях.
5. **Путать авторов и названия** — мелочь, но заметная.
6. **Приписывать книге то, чего в ней нет**, например что «C++ Primer» учит lock-free программированию.
7. **Не упоминать критику**: умение сказать «этот совет устарел» показывает, что вы думали, а не заучивали.

## Что добавить на собеседовании

- Связать книгу с **конкретным решением в проекте**: «после `Effective Modern C++` перевёл владение на `unique_ptr`, утечек в модуле больше нет».
- Упомянуть, **что читаете сейчас** и почему именно это, — видно направление роста.
- Показать **фильтр**: «Страуструпа читаю как справочник, а не подряд; GoF использую как словарь, а не как рецепт».
- Честно сказать, **что не осилили** и почему: это плюс к доверию, а не минус.
- Для джуна уместен план: база по языку → `Effective`-серия → concurrency → алгоритмы и системы.

| Книга | Тема | Чему научился |
|---|---|---|
| «C++ Primer» | Язык и STL | Целостная картина языка, аккуратная работа с ссылками и контейнерами |
| «Effective Modern C++» | Современный C++ | Вывод типов `auto`, move-семантика, умные указатели по умолчанию |
| «Effective C++» / «Effective STL» | Практика | Правило нуля, алгоритмы вместо ручных циклов |
| «Чистый код» | Качество кода | Малые функции с единым уровнем абстракции, говорящие имена |
| «Рефакторинг» | Эволюция кода | Маленькие шаги под защитой тестов вместо «перепишем всё» |

> Формула ответа: **3–4 книги × (идея + применение + критика)**. Этого достаточно, чтобы показать и кругозор, и инженерную зрелость.
