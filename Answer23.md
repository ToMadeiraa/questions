# Вопрос 23. Как работает препроцессор?

> **Кратко:** Препроцессор — первая фаза трансляции, которая обрабатывает текст программы до синтаксического разбора: раскрывает макросы, подставляет содержимое заголовочных файлов вместо `#include` и отбрасывает фрагменты, отключённые условиями. На выходе получается один «плоский» поток токенов — единица трансляции, в которой директив уже нет. Типов, областей видимости и перегрузок для препроцессора не существует: он видит только лексемы.

---

## Место в цепочке сборки

Стандарт описывает трансляцию как 9 последовательных фаз; препроцессору принадлежит **фаза 4**.

| Фаза | Что происходит |
|---|---|
| 1 | символы файла приводятся к базовому набору символов, концы строк нормализуются |
| 2 | физические строки склеиваются в логические: `\` в конце строки удаляется вместе с переводом строки |
| 3 | текст разбивается на **preprocessing tokens**, каждый комментарий заменяется одним пробелом |
| 4 | **выполняются директивы, раскрываются макросы, рекурсивно включаются файлы** |
| 5–6 | литералы переводятся в кодировку выполнения, соседние строковые литералы склеиваются |
| 7 | лексемы становятся токенами: синтаксический и семантический анализ, генерация кода |
| 8 | инстанцирование шаблонов |
| 9 | компоновка объектных файлов |

Важная деталь: файл, включённый через `#include` на фазе 4, проходит **фазы 1–4 заново и рекурсивно**. В конце фазы 4 все директивы из текста удалены — компилятор их уже не увидит. Вложенность включений ограничена (стандарт гарантирует минимум 15 уровней), поэтому циклический `#include` без защиты обрывается диагностикой, а не «зависает».

## Что препроцессор видит и чего не видит

| Понимает | Не понимает |
|---|---|
| лексемы и пробелы между ними | типы, `class`, `template`, области видимости |
| строки и символьные литералы (внутрь не лезет) | значения `constexpr`-переменных, `sizeof`, перегрузки |
| арифметику в `#if` (целочисленную) | выражения C++ с плавающей точкой, вызовы функций |
| имена макросов и их параметры | смысл идентификаторов: `std::vector` для него — три лексемы |

Из этого следуют три свойства:

- **директивы построчные** — начинаются с `#` (перед ним допустимы пробелы), действуют до конца логической строки, точки с запятой не требуют;
- **макрос не раскрывается** внутри строкового литерала и внутри комментария (комментарии к этому моменту уже стали пробелами);
- **препроцессор ничего не оптимизирует и не проверяет типы** — он только переставляет текст.

---

## Модель работы

Упрощённо это построчный обработчик: строка, начинающаяся с `#`, — директива, она выполняется; в остальных строках раскрываются встреченные макросы, а прочий текст копируется в вывод без изменений.

Два ключевых механизма — **подстановка текста** (`#include`, `#define`) и **условное исключение текста** (`#if`, `#ifdef`). Всё остальное (строкизация `#`, склейка `##`, `#pragma`, `#error`) — надстройки над этими двумя.

---

## Алгоритм раскрытия макроса

Порядок шагов важен, потому что от него зависят неожиданные результаты:

1. **Сбор аргументов.** Препроцессор находит парную `)` и режет аргументы по запятым **только на верхнем уровне скобок**. Фигурные скобки и угловые скобки не защищают запятую.
2. **Предварительное раскрытие аргументов.** Каждый аргумент раскрывается как самостоятельный текст — **кроме** случаев, когда параметр используется с `#` или `##`.
3. **Подстановка** в тело макроса вместо имён параметров.
4. **Повторное сканирование** (rescan) результата вместе с остатком файла: если в подставленном тексте появились новые имена макросов, они раскрываются.

Отсюда два классических следствия — макрос не раскрывается сам в себе (защита от бесконечной рекурсии, «синяя краска») и раскрытие идёт до полного исчерпания, но с ограничением глубины.

```cpp
#define A 1
#define B A + 2

int x = B * 3;   // препроцессор: 1 + 2 * 3 == 7, а не 9
```

Это не ошибка препроцессора, а честная текстовая подстановка: скобки обязан расставить автор макроса.

## Пример: что видит компилятор

`demo.h`:

```cpp
#pragma once
#define SQUARE(x) ((x) * (x))
inline int twice(int v) { return 2 * v; }
```

`main.cpp`:

```cpp
#include "demo.h"

int f(int a) {
    return SQUARE(a + 1);   // станет ((a + 1) * (a + 1))
}
```

Результат `g++ -E main.cpp` (сокращённо):

```cpp
inline int twice(int v) { return 2 * v; }
int f(int a) {
    return ((a + 1) * (a + 1));
}
```

Ни `#include`, ни `#define`, ни `#pragma` в потоке токенов больше нет — только код.

## Условная компиляция

`#if` вычисляет **целочисленное константное выражение** по своим правилам:

- `defined(X)` / `defined X` — 1, если макрос определён;
- неизвестные идентификаторы заменяются на `0` (поэтому `#if FOO` не ошибка, а `0`);
- `true` и `false` — ключевые слова и доступны;
- все знаковые целые ведут себя как `std::intmax_t`, беззнаковые — как `std::uintmax_t`;
- `sizeof`, приведения типов, вызовы функций и переменные **недоступны** — это не C++-выражение.

```cpp
#if defined(__cpp_lib_optional) && __cpp_lib_optional >= 201606L
#include <optional>
#endif
```

Ветви, не прошедшие условие, удаляются на фазе 4: внутри них может находиться любой текст, даже синтаксически некорректный — компилятор его не увидит.

## Почему препроцессор считается опасным

| Свойство | Последствие |
|---|---|
| нет областей видимости | `#define` действует до конца единицы трансляции и «протекает» в чужие заголовки |
| нет типов | ошибки видны только после подстановки, сообщения указывают не туда |
| нет отладки | макрос не существует как сущность в отладочной информации |
| двойное вычисление аргументов | `SQUARE(i++)` увеличит `i` дважды |
| порядок включения влияет на смысл | одинаковый код компилируется по-разному в зависимости от `#include` |
| ODR | разные определения макроса в разных единицах трансляции дают разное поведение без диагностики |

## Чем заменять в современном C++

| Было (макрос) | Стало |
|---|---|
| `#define PI 3.14` | `inline constexpr double kPi = 3.14;` |
| `#define MAX(a, b) ...` | `template<class T> T max(T a, T b)` или `std::max` |
| `#define SIZE 10` для массива | `constexpr std::size_t kSize = 10;` |
| `#define LOG(x)` | функция с `std::source_location` (C++20) |
| `#ifdef` для платформы | `if constexpr` + feature-test-макросы, `std::endian` |
| `#include`-барьеры | модули C++20 (`import`) |

Макросы остаются оправданными там, где нужна именно **текстовая** природа: include guards, `__FILE__`/`__LINE__`, строкизация, условная компиляция, кодогенерация.

| Действие | GCC / Clang | MSVC |
|---|---|---|
| только препроцессинг | `g++ -E file.cpp` | `cl /E file.cpp` (с `#line`), `cl /P` (без) |

| добавить макрос из командной строки | `-DNDEBUG`, `-DFOO=1` | `/DNDEBUG` |

Умение показать `-E` и объяснить вывод — сильный практический аргумент на собеседовании.

## Типичные ошибки

1. **Считать, что препроцессор «понимает» код.** Он не знает ни типов, ни пространств имён; `#define max(a,b)` ломает `std::max` и любой метод `max`.
2. **Забывать скобки** вокруг параметров и всего тела макроса — приоритеты операторов другого не простят.
3. **Ожидать вычисления C++-выражений в `#if`** — там нет `sizeof` и переменных, только целочисленная арифметика.
4. **Думать, что `#if` «выключает» код физически** — текст остаётся в файле, но до компилятора не доходит; ошибки в нём не диагностируются.
5. **Путать `#define` с объявлением сущности**: у макроса нет адреса, он не участвует в линковке и ODR-проверках, но может их нарушить.
6. **Использовать макросы для констант и «инлайнов»**, хотя есть `constexpr`, `inline`-функции и шаблоны.

## Что добавить на собеседовании

- Препроцессор — отдельный **текстовый** проход, а не часть парсера; поэтому ошибки в макросах диагностируются в терминах уже раскрытого кода.
- Полезно назвать номер фазы (4 из 9) и то, что включённый файл проходит фазы 1–4 рекурсивно.
- Хороший ответ упоминает цену: дублирование текста заголовков в каждой единице трансляции — причина медленной сборки, отсюда предкомпилированные заголовки и модули.
- Стоит сказать, что раскрытие макросов — это подстановка с последующим rescan, а не «вызов»: в этом корень и мощи, и всех проблем.
- Идеологически верная позиция: препроцессор — инструмент для того, что **нельзя** выразить средствами языка (условная компиляция, включение файлов, диагностика окружения), и его нужно держать под контролем.

## Итог

| Аспект | Суть |
|---|---|
| Что это | текстовый проход до компиляции, фаза 4 трансляции |
| Вход / выход | исходный текст → поток токенов без директив (единица трансляции) |
| Основные операции | подстановка (`#include`, `#define`) и условное исключение (`#if…`) |
| Механизм раскрытия | аргументы → предраскрытие → подстановка → rescan, без рекурсии |
| Чего не знает | типов, областей видимости, выражений C++ |
| Цена | дублирование текста, отсутствие отладки, протекающие имена, рост времени сборки |
| Замена | `constexpr`, `inline`, шаблоны, `if constexpr`, модули |
